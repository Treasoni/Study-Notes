# 第四章：HAOS 国内换源（Docker / Supervisor / OTA 三层全解）

> [!summary] 本章讲什么
> HAOS 有 **三条独立的下载通道**，大陆网络下每一条都要换源，缺一不可：
> - **Docker 换源**（4.2，容器镜像层）：改 `/etc/docker/daemon.json`，加速 docker.io 镜像拉取，仅普通 Linux / Supervised 适用；
> - **Supervisor 换源**（4.3，HA 组件层）：改 `/usr/share/hassio/docker.json`，把 ghcr.io 映射到国内镜像——**官方 HAOS 的核心**；
> - **OTA 换源**（4.4，系统固件层）：系统升级 `.raucb` 包走国内节点，官方原版做不通，用 `rauc install` 或换 [[05_HAOS-CN极速版|HAOS-CN]]。
>
> 4.1 先讲清三层区别，4.5 补充 Add-on 商店与 NTP，4.6 给出进不去宿主 shell 时的替代路线。每一节都给出可直接复制的配置片段与验证命令。

## 0 先看这里：三层换源速查

| 层 | 换源对象 | 配置文件 | 官方 HAOS 怎么用 |
|----|---------|---------|----------------|
| 容器镜像（4.2） | docker.io 镜像 | `/etc/docker/daemon.json` | ❌ 根只读，仅普通 Linux / Supervised |
| HA 组件（4.3） | ghcr.io 镜像 | `/usr/share/hassio/docker.json` | ✅ 官方 HAOS 主线 |
| 系统固件（4.4） | OTA `.raucb` 包 | Supervisor 内置（写死） | ⚠️ 官方改不了，用 `rauc install` 或 HAOS-CN |

> [!tip] 一秒判断你在不在宿主 shell
> 提示符形如 `[ad19d24a-ssh hassio]$`、或敲 `systemctl` 报 `command not found` → 你在**加载项容器**里，先看 4.6（有 docker 权限可直接改，不用进宿主）。

> [!warning] 时效性说明
> 所有镜像站地址、仓库地址均为采集时间（2026-08）可用的社区源，公益镜像站隔天失效是常态，以实际拉取结果为准；失效回到 4.2 / 4.3 换源即可。udev 覆盖方案已随 2026.2.1 失效，详见 4.2。

> [!note] 先读：改系统文件要进「宿主 shell」，不是加载项
> 本章要改的都是**系统级配置文件**，`ha` 命令（如 `ha core restart`）只能控制服务，不能编辑 `/etc/` 下的文件。真正能改文件的是**宿主 shell**，只有两个入口：
> - **VM 控制台 `login`**（零配置、随时可用）：控制台输入 `login` 进 root shell；
> - **宿主 SSH 22222**：`ssh root@<IP> -p 22222`，需先开启（见下）。
>
> ⚠️ **加载项 Terminal & SSH 不是宿主 shell**——它是**容器**（提示符 `[xxx-ssh hassio]$`、`systemctl` 不可用），只能跑 `ha` 命令，改不了宿主文件。
>
> **宿主 SSH（22222）怎么开？**（开发者功能，无 Web 开关）
> - **① CONFIG 分区放公钥（官方，推荐）**：卷标 `CONFIG`（全大写）的分区/U 盘根目录放 `authorized_keys`（无扩展名、LF 换行、ASCII），插上重启（或 `ha os import`），无需先完成引导；
> - **② VM 控制台 `login`**：零配置，适合一次性改文件。
>
> > [!warning] 鸡生蛋陷阱
> > 加载项要从商店安装，而商店拉镜像正是本章要解决的 ghcr 瓶颈。**不要**指望先装加载项再改源；改系统文件优先用控制台 `login` 或 22222。
>
> > [!tip] 一句话流程（VMware 最省事）
> > 烧录 → 开机 → **VM 控制台 `login`** 直接改文件；想远程就按 ① 的 CONFIG 公钥法。首次引导卡"拉 700MB 组件"就先按 4.5 预置时间源。

## 4.1 三层换源的区别：为什么缺一不可

HAOS 的下载/更新分三层，各自独立，**互不替代**：

| 维度          | Docker 换源                  | Supervisor 换源                         | OTA 换源                      |
| ----------- | -------------------------- | ------------------------------------- | --------------------------- |
| 管什么         | 容器镜像（Core、Add-on 的运行镜像）    | Supervisor 及其拉取的所有 ghcr.io 镜像         | 整个操作系统的固件升级                 |
| 下载源         | docker.io（Docker Hub）      | ghcr.io（GitHub Container Registry）    | GitHub Releases（`.raucb` 包） |
| 配置文件        | `/etc/docker/daemon.json`  | `/usr/share/hassio/docker.json`       | 无（Supervisor 内置写死）          |
| 生效命令        | `systemctl restart docker` | `systemctl restart hassio-supervisor` | `rauc install` / 自动 OTA     |
| 官方 HAOS 可改？ | ❌ 根只读                      | ✅ 主路                                  | ❌ 需手动 `rauc` 或换发行版          |
| 更新频率        | 按需拉取                       | 随版本检查                                 | 每月自动检查                      |

三个常见误区，必须分清：

> [!warning] 误区一：`registry-mirrors` 只对 docker.io 生效
> `daemon.json` 里的 `registry-mirrors`（数组）只改写 **docker.io** 的拉取地址，对 **ghcr.io 无效**。而 HA 的核心镜像和 Add-on 镜像恰恰托管在 ghcr.io——这部分必须走 Supervisor 层。

> [!warning] 误区二：`registries_mirror` 是仓库级映射
> `docker.json` 里的 `registries_mirror`（对象）是 Supervisor 拉镜像时的**仓库重定向**（`"ghcr.io": "ghcr.nju.edu.cn"`），管的是「把 ghcr.io 的请求改道」。它和 Docker 引擎的 `registry-mirrors` 是两套机制，别混。

> [!warning] 误区三：OTA 地址写死，配置文件改不了
> 系统升级的下载地址在 Supervisor 内部写死、指向 GitHub 官方 Releases，**没有配置文件入口**。官方原版上 OTA 无法像镜像那样配国内源——要么手动 `rauc install`，要么换内置重定向的 [[05_HAOS-CN极速版|HAOS-CN]]。

## 4.2 Docker 换源：容器镜像层（普通 Linux + Docker / Supervised）

国内直连 Docker Hub（docker.io）拉镜像普遍慢或超时，根因是官方 Registry 节点没有覆盖大陆网络。Docker daemon 提供 `registry-mirrors` 配置：拉取 docker.io 镜像时自动改走镜像站，镜像站会回源缓存，命中缓存的镜像几乎秒下。

> [!warning] 本节不适用于官方 HAOS
> 官方 HAOS 根文件系统**只读**，`/etc/docker/daemon.json` 改了也无效；官方 HAOS 走 **4.3** 改 `/usr/share/hassio/docker.json`。本节只适用于**普通 Linux + Docker 或 Supervised 安装**。

**详细过程：**

1. 确认文件不存在是正常的，先创建目录：
   ```bash
   mkdir -p /etc/docker
   ```
2. 写入配置（`/etc/docker/daemon.json`，多配几个做故障转移）：
   ```json
   {
     "registry-mirrors": [
       "https://docker.1ms.run",
       "https://docker.xuanyuan.me",
       "https://docker.m.daocloud.io",
       "https://docker.mirrors.ustc.edu.cn"
     ]
   }
   ```
3. 重启 Docker 并验证：
   ```bash
   systemctl restart docker
   docker info | grep -A5 "Registry Mirrors"
   ```
4. 实测拉一个小镜像：
   ```bash
   docker pull hello-world
   ```

**2026 年实测可用的镜像源（采集 2026-08）：**

| 镜像源 | 地址 | 说明 |
|--------|------|------|
| 毫秒镜像 | `docker.1ms.run` | 商业源较稳定，支持 `ghcr.1ms.run`、`mcr.1ms.run` 等替换前缀 |
| 轩辕镜像 | `docker.xuanyuan.me` | 公益源，仅加速 Docker Hub，有限流 |
| DaoCloud | `docker.m.daocloud.io` | 老牌公益源 |
| 中科大 | `docker.mirrors.ustc.edu.cn` | 教育网有优势 |
| 阿里云加速器 | `<你的ID>.mirror.aliyuncs.com` | 需注册申请专属地址 |

> [!note] 毫秒镜像的多仓库替换前缀
> `docker.1ms.run` 这类商业源常提供**多仓库替换入口**：`ghcr.1ms.run`（ghcr.io）、`mcr.1ms.run`（MS Container Registry）、`k8s.1ms.run`（registry.k8s.io）。Supervisor 换源（4.3）里把 `ghcr.io` 指向 `ghcr.1ms.run` 也是可行方案。

> [!warning] 曾经方案：udev 覆盖 daemon.json（已失效）
> 官方 HAOS 根只读，社区曾用 udev bind-mount 把自定义 `daemon.json` 覆盖到 `/etc/docker/daemon.json`。**该方案自 2026.2.1 起失效**，新版照抄会 boot loop，只作原理理解，不再作为主线。

> [!warning] 坑：`registry-mirrors` 只对 docker.io 生效
> 它只改写 docker.io 的拉取地址，对 **ghcr.io 无效**。HA 核心与 Add-on 镜像在 ghcr.io——需要走 4.3 的 Supervisor 层配置，两条路径互补，缺一不可。

> [!tip] 实操建议
> 公益镜像站隔天失效很常见，"多配几个 + 故障转移"比"只信某一个"更重要。发现拉不动先 `docker pull` 单测，再替换清单里的失效项；配好后把拉取命令存成脚本，每月巡检一次（第 8 章有周期性清单）。

## 4.3 Supervisor 换源：HA 组件层（官方 HAOS 主线）

这是官方原版解决 ghcr.io 的核心路径，也是本章最值钱的一节。原理：HA 架构里 Supervisor 是"调度中枢"，Core 和所有 Add-on 的容器镜像都由它负责拉取，而这些镜像全部托管在 ghcr.io。国内直连经常超时，表现就是 Add-on 装不上、Core 更新拉不动、系统卡在启动转圈界面。

配置分两个文件，各管一件事（**官方 HAOS 只改文件二**）：

**文件一：`/etc/hassio.json`** —— 改 Supervisor 自身的镜像地址：

> [!warning] 官方 HAOS 没有这个文件，跳过文件一
> `/etc/hassio.json` 只在 **Supervised 安装**下存在且可改。官方 HAOS 的 `/etc` 位于只读根文件系统，**该文件不存在也不可编辑**。官方 HAOS 上只需改下面的**文件二**。

```bash
# /etc/hassio.json：改 supervisor 自身镜像（仅 Supervised 安装）
#   "supervisor": "ghcr.nju.edu.cn/xjboss/{arch}-hassio-supervisor"
#   {arch} = amd64（x86_64）或 aarch64（ARM 派）
```

**文件二：`/usr/share/hassio/docker.json`** —— 加 `registries_mirror`，把 ghcr.io 和 docker.io 的拉取整体映射到国内镜像：

**详细过程：**

1. 编辑配置文件（不存在则 `vi` 新建，`/usr/share/hassio/` 指向可写持久分区）：
   ```bash
   vi /usr/share/hassio/docker.json
   ```
2. 写入 `registries_mirror` 映射：
   ```json
   {
     "registries": {},
     "registries_mirror": { "ghcr.io": "ghcr.nju.edu.cn", "docker.io": "docker.nju.edu.cn" }
   }
   ```
   > 每个仓库配一个镜像，可换成任意可用源；公益源随时可能失效，配前先用下面的检测法验证。

**可选镜像源（2026-08 采集，公益源随时可能失效）：**

| 仓库        | 可选镜像                                                             | 说明                  |
| --------- | ---------------------------------------------------------------- | ------------------- |
| ghcr.io   | `ghcr.nju.edu.cn`                                                | 南京大学，2026-07 状态监测在线 |
| ghcr.io   | `ghcr.m.daocloud.io`                                             | DaoCloud 前缀替换       |
| ghcr.io   | `ghcr.1ms.run`                                                   | 毫秒镜像，2026-08 实测通过   |
| docker.io | `docker.nju.edu.cn`                                              | 南京大学                |
| docker.io | `docker.1ms.run` / `docker.xuanyuan.me` / `docker.m.daocloud.io` | 见 4.2 清单            |
|           |                                                                  |                     |

**如何检测镜像可用：**

用 curl 打 registry 的 `/v2/` 端点，返回 **`200` 或 `401`** 即可用，`404` / `503` / 超时即失效：

```bash
# 单测一个
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" --max-time 5 https://ghcr.nju.edu.cn/v2/

# 批量测一组，挑出能用的
for m in ghcr.nju.edu.cn ghcr.m.daocloud.io ghcr.1ms.run docker.nju.edu.cn; do
  code=$(curl -s -o /dev/null -w "%{http_code}" --max-time 5 "https://$m/v2/")
  echo "$m -> $code"
done
```

更可靠的是**真实拉取测试**（测 ghcr 源请用真实存在的镜像名；标签不存在返回 404 不代表源挂）：

```bash
# docker.io 源
docker pull docker.1ms.run/library/hello-world
# ghcr 源（版本号换成实际存在的）
docker pull ghcr.nju.edu.cn/home-assistant/amd64-hassio-supervisor:<版本号>
```

> [!note] 与 `registry-mirrors`（4.2）的差异
> `registries_mirror` 是**按仓库一对一映射**（每个仓库一个镜像地址），不是 `daemon.json` 的 `registry-mirrors` 那种故障转移数组。某镜像失效时，用检测法找出可用源，编辑 `docker.json` 换掉再重启 Supervisor。

3. 重启 Supervisor 生效：
   ```bash
   systemctl restart hassio-supervisor
   ```
4. 验证：去 Add-on 商店安装一个之前装不上的加载项，速度应明显改善；或看 Supervisor 日志确认走的是国内源。

> [!tip] 没有宿主 shell？用 docker 直接改
> 如果进不去宿主 shell，但加载项有 docker 权限，可以用 4.6 方案 A 从容器里改同一个文件（`/data/docker.json` = 宿主的 `/usr/share/hassio/docker.json`）。

> [!warning] 易错点：升级会重置，必须先备份
> HAOS 系统升级时 `/usr/share/hassio/docker.json` 很可能被重置为默认值，加速悄悄失效。备份并在升级后对比恢复：
> ```bash
> cp /usr/share/hassio/docker.json /usr/share/hassio/docker.json.bak
> ```

> [!note] 能力边界
> `registries_mirror` 只解决**镜像拉取**，不解决 GitHub 源码下载和 OTA 升级。Add-on 仓库从 GitHub 拉源码、系统更新走官方 OTA，这些仍需 4.5 的国内仓库和 4.4 的方案。

## 4.4 OTA 换源：系统固件层

OTA 是操作系统层面的整体升级：HAOS 用 **RAUC** 的 A/B 双槽位机制，下载 `.raucb` 固件包（约 100MB–1GB），签名校验后写入非活动槽位，重启切换，失败自动回滚。

**为什么官方原版配不了国内 OTA 源？** 四个障碍：

> [!note] 常见思路：把官方 OTA 包搬到 Gitee，让 HA 从我的仓库更新
> 思路方向正确（国内 OTA 镜像正是 [[05_HAOS-CN极速版|HAOS-CN]] 的核心卖点），但**官方原版上做不通**：
> 1. **没有配置入口**：OS 更新下载地址在 Supervisor 内部写死，指向 GitHub 官方 Releases，不是 4.3 的 `docker.json` 能改的；
> 2. **根文件系统只读**：squashfs/EROFS 只读，改不了内置端点——这正是 HAOS-CN 必须在构建时硬编码重定向的原因；
> 3. **要重定向两个端点**：版本检查（`version.home-assistant.io`）和下载端点都要改，只搬 .raucb 到 Gitee，HA 根本不知道去哪找；
> 4. **Gitee 放不下**：官方 .raucb 约 500MB–1GB，Gitee 免费仓库单文件一般限 100MB。
>
> 好的一面：RAUC 更新包有官方签名，搬运官方包签名校验能过——卡住你的不是签名，是上面 1–4。

**方案一：手动 `rauc install`（官方原版，保留签名 + A/B 回滚）**

在任意有网的机器上下载官方 OTA 包，传到 HAOS 持久分区再本地安装：

```bash
# 1) 在任意有网的机器上，从 GitHub 拉官方 OTA 包（gh-proxy 加速）
wget -c https://gh-proxy.org/https://github.com/home-assistant/operating-system/releases/download/12.5/haos_generic-x86-64-12.5.raucb
# 2) 传到 HAOS 持久分区（/mnt/data 可写）
scp haos_generic-x86-64-12.5.raucb root@<IP>:/mnt/data/
# 3) 宿主 shell 里本地安装（保留 RAUC 签名校验 + A/B 槽位 + 失败自动回滚）
ssh root@<IP> -p 22222
cd /mnt/data
rauc install haos_generic-x86-64-12.5.raucb
systemctl reboot     # 树莓派 5 必须用 systemctl reboot，普通 reboot 可能不切槽位
```

- 板型名：VMware/PVE/实体机 x86-64 是 `generic-x86-64`，树莓派是 `rpi4-64` 等；
- 安装前先按第 7 章做一次备份；
- 版本号 `12.5` 仅为示例，以官方 Releases 实际版本为准。

**方案二：切换 HAOS-CN（全自动国内 OTA）**

[[05_HAOS-CN极速版|HAOS-CN]] 把版本检查 + OTA 下载都重定向到国内腾讯 BGP 节点，保留 RAUC 签名 + A/B 原子更新，官方版一键转过去：

```bash
login
curl -fsSL https://ota.hasscn.top/upgrade.sh | bash
```

代价是第 5 章的信任模型（非官方、校验和缺口、硬依赖中国 IP）。

**补充命令（RAUC / 启动槽位）：**

```bash
rauc status        # 查看当前启动槽位与状态
ha os info         # 查看 OS 信息
ha os boot-slot    # 切换启动槽位（回滚用）
```

| 方案 | 效果 | 代价 |
|------|------|------|
| 官方 OTA（默认） | 国内慢/易失败 | 零改动 |
| 手动 `rauc install` | 升级速度自己掌控，官方签名保真 | 每次手动下载 + scp + 安装 |
| [[05_HAOS-CN极速版\|HAOS-CN]] | 全自动国内 OTA | 信任模型 + 无校验和 |

## 4.5 其他国内化：Add-on 商店 + NTP 时间

**Add-on 商店国内仓库与镜像映射**

Add-on 商店默认仓库大多指向 github.com / ghcr.io，国内加载经常失败。双管齐下：加一个 Gitee 国内仓库作安装源，再用映射表替换拉取地址。

> [!example] 添加仓库
> 设置 → 加载项商店 → 右上角三个点 → 仓库 → 粘贴添加：
> ```text
> https://gitee.com/desmond_GT/hassio-addons
> ```

| 原地址 | 国内镜像 | 用途 |
|--------|---------|------|
| ghcr.io | `ghcr.nju.edu.cn` | Add-on 容器镜像（核心加速项） |
| docker.io / lscr.io | `docker.1ms.run` | Docker Hub 与 LinuxServer 镜像 |
| github.com | `gh-proxy.org` | GitHub 仓库源码 / 更新 |

机制：每个 Add-on 的 manifest 声明 `image` 字段，Supervisor 按映射改写镜像地址，和 4.3 的 `registries_mirror` 一套思路的两种实现。配置后**无需翻墙**，翻墙反而可能因代理链路失败；国内镜像首次安装偶发失败，**重试一次即可**。

**NTP 时间同步国内化**

时间不同步是隐蔽"稳定性杀手"：HTTPS 证书校验、自动化定时、更新检查都依赖准确时间。通过宿主 SSH 编辑：

```ini
# /etc/systemd/timesyncd.conf
[Time]
NTP=ntp1.aliyun.com ntp2.aliyun.com ntp3.aliyun.com
FallbackNTP=ntp.tencent.com cn.pool.ntp.org
```

```bash
systemctl restart systemd-timesyncd.service
timedatectl   # 看到 System clock synchronized: yes 即成功
```

> [!tip] 首次启动前预置（强烈建议）
> 烧录后把同样配置放进 `hassio-boot` 分区的 `CONFIG/timesyncd.conf`（权限 644），首次启动 10 秒内完成时间同步，避免首次联网拉取 700MB 组件时证书校验失败。

> [!warning] 时间异常判别法
> - 差**整 8 小时**：时区未设（Asia/Shanghai），不是 NTP 问题；
> - 差**几分钟且持续增大**：NTP 同步失败，回看 `timedatectl` 同步状态。

## 4.6 宿主 shell 前置与替代路线

前面 4.2–4.5 都要改**系统级文件**，通常前提是能进宿主 shell。如果你连 22222 都进不去（没配公钥、又不想动控制台），先看这节——**有 docker 权限时，4.3 的 `docker.json` 可以不用宿主 shell 直接改**（方案 A）。

> [!warning] 容器识别速查：你不在宿主 shell
> 「Terminal & SSH」加载项跑在**容器**里，不是宿主系统，在里面改系统文件、跑 `systemctl` 都会失败：
> - 提示符形如 `[ad19d24a-ssh hassio]$`（`xxx-ssh hassio`）→ **容器**
> - 执行 `systemctl` 报 `command not found` → **容器**
> - 宿主 shell 里 `systemctl` 一定可用，提示符通常为 `root@homeassistant:~#`

**方案 A（有 docker 权限时最快）：直接用 docker 改 `docker.json`，不进宿主 shell**

比如addon插件：Advanced SSH & Web Terminal，关闭安全模式就可以使用了。

适用：加载项有 docker 权限、只想配 ghcr 镜像加速、不想进宿主 shell。原理：`hassio_supervisor` 容器把宿主的 `/usr/share/hassio` 挂载为自己的 `/data`，所以**容器里的 `/data/docker.json` 就是宿主的 `/usr/share/hassio/docker.json`**。

```bash
# 1) 确认能看到 supervisor 容器，且 /data 对应宿主 /usr/share/hassio
docker ps | grep hassio_supervisor
docker exec hassio_supervisor ls -la /data/

# 2) 写入 /data/docker.json（= 宿主的 /usr/share/hassio/docker.json）
cat <<'EOF' | docker exec -i hassio_supervisor sh -c 'cat > /data/docker.json'
{
  "registries": {},
  "registries_mirror": { "ghcr.io": "ghcr.nju.edu.cn", "docker.io": "docker.nju.edu.cn" }
}
EOF

# 3) 验证 + 重启 Supervisor 生效（等价宿主 systemctl restart hassio-supervisor）
docker exec hassio_supervisor cat /data/docker.json
ha supervisor restart

# 4) 备份（HAOS 升级可能重置该文件）
docker exec hassio_supervisor sh -c 'cp /data/docker.json /data/docker.json.bak'
```

> [!warning] 注意
> JSON 必须合法，否则 Supervisor 可能起不来 Docker，写完先 `cat` 确认。这只解决 4.3 的镜像加速；要改 4.5 的 NTP 等系统文件，仍需进宿主 shell（见方案 B/C/D）。

下面的方案 B–E 是「进宿主 shell」的替代路线，按省事程度排序：

**方案 B（推荐，零配置）：VM 控制台 `login`**

适用：最快进宿主 shell 的方式，适合一次性把系统文件改完。核心理解：**VM 控制台 = 这台虚拟机的「屏幕窗口」**——就像给机器接了一台显示器，在窗口里操作与网络、SSH、浏览器都无关，是机器本体的调试入口。它和加载项终端（容器）是完全不同的两个东西。

VMware Workstation / Player 步骤：

1. 左侧库列表找到 HAOS 虚拟机，**双击打开它的窗口**（即显示虚拟机屏幕的大窗口；VMware 主界面本身不是控制台）。
2. 等启动日志滚完，停在 `Home Assistant OS login:`（或 `homeassistant login:`）提示符。
3. 输入 `login` 回车——这是 **HAOS 的开发者调试命令，不是用户名**，会免密码直接进 root shell，提示符变为 `root@homeassistant:~#`。
4. 验证进对了：`systemctl --version` 能输出版本号即宿主系统（加载项容器里会 `command not found`）；`hostname` 应显示 `homeassistant`。
5. 然后正常执行 4.3 / 4.5 的命令（如 `vi /usr/share/hassio/docker.json`、`systemctl restart hassio-supervisor`）。

> [!tip] 操作技巧
> 在 VM 窗口内点击后，鼠标键盘会被虚拟机捕获；按 **Ctrl+Alt** 释放鼠标回 Windows。PVE 用户在虚拟机列表点该机 → 右上角「Console」（noVNC 网页控制台），同样输入 `login`。

**方案 C：CONFIG U 盘解锁宿主 SSH 22222（官方方法，可远程）**

适用：不依赖加载项、想长期从 Windows 远程管理宿主。准备一个 U 盘/分区，卷标命名 `CONFIG`（全大写），根目录放 `authorized_keys`（无扩展名、LF 换行、ASCII，内容为 SSH 公钥），插上重启自动导入（或 `ha os import`）。之后 `ssh root@<IP> -p 22222`。VM 场景就是把虚拟 U 盘挂给虚拟机。

**方案 D：从加载项一行命令解锁宿主 SSH 22222（社区方法，需 Docker 权限）**

适用：已有 docker 权限、想顺手把宿主 SSH 长期打开。原理：利用加载项容器的 Docker 权限，把自己的公钥写进 HAOS 的 CONFIG 分区。前置检查：

```bash
which docker        # 有输出 = 加载项有 Docker 权限；没有则先开加载项配置里的 Docker 访问
lsblk               # 确认引导分区：VMware 通常 /dev/sda1，NVMe /dev/nvme0n1p1，树莓派 /dev/mmcblk0p1
```

然后在加载项终端执行（把 `/dev/sda1` 换成你看到的引导分区）：

```bash
(BOOT_PART=/dev/sda1; cat /data/.ssh/authorized_keys | sudo docker exec -i homeassistant bash -c "mkdir -p /mnt/temp && mount $BOOT_PART /mnt/temp && mkdir -p /mnt/temp/CONFIG && cat >| /mnt/temp/CONFIG/authorized_keys && umount /mnt/temp && rmdir /mnt/temp")
```

> [!warning] 注意
> - 加载项若用密码登录（没有密钥文件），把 `cat /data/.ssh/authorized_keys` 换成 `echo '你的 SSH 公钥'`。
> - 执行完 `reboot`，重启后 `ssh root@<IP> -p 22222` 即可进宿主。
> - 这是社区方法，操作前用 `lsblk` 确认引导分区别选错；方法源自 HAOS 官方开发者文档的调试思路。

**方案 E：直接换 [[05_HAOS-CN极速版|HAOS-CN]]（第 5 章，连宿主都不用进）**

适用：不想碰任何系统文件、接受非官方信任模型。内置全套国内加速（ghcr 重定向 + 12 源故障转移 + 国内 OTA），在加载项里一行切换：

```bash
login
curl -fsSL https://ota.hasscn.top/upgrade.sh | bash
```

代价是信任模型（非官方 + 校验和缺口 + 硬依赖中国 IP），详见第 5 章。

> [!tip] 一句话建议
> 只想配镜像加速：方案 A（docker 直接改）。一次性完整配置：方案 B（控制台 `login`）。长期远程管理：方案 C 或 D 解锁 22222。不想碰系统文件：方案 E 换 HAOS-CN。
