# 第六章：升级与运维流程

> [!summary] 本章讲什么
> 本章把前面各章命令串成运维 SOP：标准升级顺序（备份 → supervisor → core → os）、版本指定与多版本落后的分批升级、配置修改生效链路（options → rebuild → restart）、日常运维速查清单，以及用 `SUPERVISOR_ENDPOINT` / `SUPERVISOR_API_TOKEN` 远程调用 `ha`。

前几章把命令组一个个拆开讲。这一章把它们串成完整的**运维流程**：标准的升级顺序是什么、怎么指定版本、改配置后如何正确让改动生效、日常要敲哪些命令，以及如何从外部机器远程调用 `ha`。读完这章，你就有了一套可以直接照着执行的运维 SOP。

## 标准升级顺序

Home Assistant 系统分三层：Supervisor、Core、OS。升级顺序有讲究，**乱了会出兼容问题**。官方推荐顺序：

1. **先做完整备份**，并存到设备外；顺带查一下两个版本之间的 Breaking Changes。
2. **升级 Supervisor**（必须先升它，它管理一切）。
3. **升级 Core**（升级前自动备份）。
4. **最后升级 OS**（OS 更新不自动备份，出错可以回滚）。

完整命令序列：

```bash
# 0. 升级前备份
ha backups new --name "before-upgrade"

# 1. 先升 Supervisor
ha supervisor update

# 2. 再升 Core（--backup 会在升级前自动备份）
ha core update --backup

# 3. 最后升 OS
ha os update
```

### 为什么 Core 先于 OS

OS 升级走的是 A/B 双槽机制（第三章讲过），启动失败会自动回退；而 Core 升级是直接改配置，**不会自动备份到可回滚的状态**。所以把 Core 放在 OS 前面，确保 Core 这层稳定了再动 OS。

### 版本指定与多版本落后

某些时候你不想升到最新，或系统落后太多，需要指定版本：

```bash
# 升级 Core 到指定版本
ha core update --version 2024.8.0

# 升级 OS 到指定版本
ha os update --version 15.2

# 降级 Core（update 支持 downgrade 别名）
ha core update --version 2024.7.4
```

> [!tip] 落后多版本要分批升
> **落后超过 6 个版本时**，不要一次跨十几个版本升：用 `ha core update --version` 每次升 6 个版本，确认系统正常后再继续下一批。每到一个可用版本，立即再做一次备份作为回滚检查点。

```bash
# 落后多版本时的分批升级示例（2024.6.0 → 2024.12.0）
ha core update --version 2024.6.0   # 升到中间版本
ha core update --version 2024.12.0  # 确认正常后再继续
```

升级完成后，检查 Persistent Notifications 和日志，确认没有新问题：

```bash
ha core logs --lines 50
ha supervisor logs --lines 50
```

## 配置修改生效链路

改 Core 运行选项（`ha core options`）之后，有些改动**不会立即生效**，需要按正确顺序走完整链路。经典场景是开启 duplicate-log-file（把日志同时写到文件）：

```bash
# 1. 设置运行选项
ha core options --duplicate-log-file=true

# 2. 重建 Core 容器镜像（让选项生效）
ha core rebuild

# 3. 重启 Core
ha core restart
```

> [!warning] 三步缺一不可
> 只做第一步、跳过 rebuild，日志不会出现——这是最常见的"改了没生效"坑。这条链路的通用规则是：**`ha core options` → `ha core rebuild` → `ha core restart`**，三步缺一不可。

## 日常运维速查清单

把日常要做的操作集中成一张清单：

| 场景 | 命令 |
|------|------|
| 查整体状态 | `ha info` |
| 查 Core / Supervisor 状态 | `ha core info`、`ha supervisor info` |
| 看日志 | `ha core logs -f`、`ha supervisor logs -f`、`ha addons logs <slug> -f` |
| 排障重启 | `ha core restart --safe-mode`（安全模式禁问题集成） |
| 改配置前验证 | `ha core check` |
| 改配置生效 | `ha core options ...` → `ha core rebuild` → `ha core restart` |
| 配静态 IP | `ha network update eth0 --ipv4-method static ...` → `ha network info` |
| 升级 addon | `ha addons update <slug>` |
| 指定版本 | `ha core update --version x.y.z`、`ha os update --version x.y.z` |

这套清单覆盖了 90% 的日常运维。剩下的低频操作，翻第八章速查表。

## 远程调用 ha 命令

`ha` 不一定要在设备本机上敲。通过全局环境变量，可以从任意一台机器远程调用：

```bash
# 1. 设置端点（设备 IP + 8123 端口）
export SUPERVISOR_ENDPOINT=http://192.168.1.100:8123

# 2. 设置 API token（Web UI → 左下角用户 → 安全 → 长期访问令牌）
export SUPERVISOR_API_TOKEN=your-long-lived-token

# 3. 远程执行命令
ha core info
ha supervisor logs -f
```

等价于每次命令带 flags：

```bash
ha --endpoint http://192.168.1.100:8123 --api-token your-token core info
```

> [!warning] 远程执行高风险命令要小心
> 远程调用适合巡检和脚本集成，但要小心：远程执行 `ha host reboot` / `ha os datadisk wipe` 这类高风险命令时，要确认 IP 没写错、设备没认错。

配合脚本可以做定时巡检，比如每天检查是否有可用更新：

```bash
#!/bin/bash
export SUPERVISOR_ENDPOINT=http://192.168.1.100:8123
export SUPERVISOR_API_TOKEN=your-token

echo "=== Core 版本 ==="
ha core info | grep -E "version|update_available"
echo "=== 可用更新 ==="
ha supervisor available_updates
```

## 本章小结

- 标准升级顺序：**备份 → `ha supervisor update` → `ha core update --backup` → `ha os update`**，Core 先于 OS。
- 版本指定用 `--version`；落后超 6 个版本分批升，每 6 版一确认，每到一版立刻备份作检查点。
- 配置生效链路是 `ha core options` → `ha core rebuild` → `ha core restart`，三步缺一不可。
- 日常运维清单一张表覆盖查状态、看日志、排障、配 IP、升级 addon。
- 远程调用靠 `SUPERVISOR_ENDPOINT` + `SUPERVISOR_API_TOKEN` 两个环境变量，适合巡检脚本，但高风险命令要格外小心。
