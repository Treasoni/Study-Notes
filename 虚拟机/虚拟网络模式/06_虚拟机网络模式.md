# 第六章：虚拟机网络模式

> [!note] 笔记信息
> **笔记类型**：概念笔记 | **阅读时间**：30 分钟
> **前置要求**：理解网络命名空间与 veth（第五章）、[[NAT]] 基本概念

## 开篇

第五章我们深入了 Linux 网络命名空间和 veth pair — 这是**容器网络**的基石。但容器并不是唯一的虚拟化形式。虚拟机（VM）的虚拟网络有着完全不同的一套模式：[[VMware]] 有桥接、[[NAT]]、仅主机三种经典模式；[[KVM]] 则提供了 Masquerade、[[Bridge模式|Bridge]]、Routed、Isolated 四种选择。

而且，现实环境中**虚拟机 + 容器混合部署**越来越常见 — 比如在 KVM 虚拟机里跑 [[Docker]]，或者在同一台物理机上同时运行 VM 和容器。这时网络模式的选择就变得复杂了：如何避免两层 NAT 的叠加性能损耗？macvlan/ipvlan 能解决什么问题？

本章从 VMware 和 KVM 出发，讲清虚拟机网络模式的原理和选型，最后给出 VM + Docker 混合部署的推荐方案。

---

## 1. VMware 三种网络模式

VMware Workstation / Fusion 提供了三种经典的虚拟机网络模式。理解这三种模式，也就理解了虚拟机网络的核心设计空间。

### 1.1 桥接模式（Bridged）

#### 原理

桥接模式是 VMware 中**最接近物理机**的网络模式。

```
┌─────────────────────────────────────────────────────┐
│                    宿主机                             │
│                                                      │
│  ┌────────────┐     ┌──────────────┐                │
│  │  虚拟机 A   │     │  虚拟机 B    │                │
│  │ 192.168.1.101  │  │ 192.168.1.102│                │
│  └──────┬─────┘     └──────┬───────┘                │
│         │                  │                         │
│         └────────┬─────────┘                         │
│                  │                                   │
│             ┌────▼────┐                              │
│             │ VMnet0  │  ← VMware 虚拟交换机         │
│             │ (网桥)   │                              │
│             └────┬────┘                              │
│                  │                                   │
│             ┌────▼────┐                              │
│             │  物理网卡 │  ← 混杂模式                 │
│             │ (eth0)  │                              │
│             └────┬────┘                              │
└──────────────────┼──────────────────────────────────┘
                   │
              ┌────▼────┐
              │ 物理交换机 │
              │ 192.168.1.0/24 │
              └─────────┘
```

**运作方式**：
1. VMware 创建一个虚拟交换机 **VMnet0**
2. 虚拟机的虚拟网卡连接到 VMnet0
3. VMnet0 通过**网桥**连接到宿主机的物理网卡
4. 物理网卡进入**混杂模式**（promiscuous mode）— 这样宿主机网卡会接收所有 MAC 地址的数据包，不只收自己的
5. 虚拟机获得与宿主机**同一网段**的独立 IP 地址

#### 关键特性

| 维度 | 说明 |
|------|------|
| IP 地址 | 与宿主机同网段的独立 IP（如宿主机 `192.168.1.100`，VM 可以拿 `192.168.1.101`） |
| 外部访问 | **可以直接访问虚拟机** — 其他机器只需知道 VM 的 IP 即可 |
| DHCP | VMware 内置 DHCP 服务，也可用手动静态 IP |
| 性能损耗 | **< 5%** — 近乎原生性能 |
| 对 WiFi 的适应性 | **较低** — 公共 WiFi、酒店网络等可能限制 MAC 地址数量或启用端口隔离 |

#### 适用场景

- **需要对外提供服务的服务器**：Web 服务器、API 服务器、游戏服务器
- **网络仿真实验**：GNS3、EVE-NG 等网络模拟平台建议使用桥接
- **需要与局域网设备直接通信**：如测试 NAS、打印机等局域网设备

#### 配置要点

在 VMware Workstation 中设置桥接模式时，需要注意：

1. **选择正确的物理网卡**：如果宿主机有多个网卡（有线 + WiFi），需要指定桥接到哪一个
2. **自动桥接 vs 指定桥接**：VMware 默认自动选择网卡，但有时会选错，建议手动指定
3. **IP 冲突**：由于 VM 和宿主机同网段，如果局域网上其他设备已经占用了该 IP，会产生冲突

```bash
# VMware 命令行指定网桥（vmnet-cfg 工具）
# 将 VMnet0 桥接到 eth0（有线）而非 wlan0（WiFi）
sudo vmnet-cfg bridge --dev eth0 vmnet0
```

> [!tip] 实践建议
> 如果宿主机使用 WiFi 上网，桥接模式可能不稳定（公共 WiFi 通常开启**客户端隔离**，阻止同一 AP 下的设备互相通信）。这时应改用 [[NAT]] 模式。

### 1.2 NAT 模式

#### 原理

NAT 模式是 VMware 的**默认模式**。它在宿主机内部创建一个私有虚拟网络，虚拟机在这个私有网络中拥有 IP，通过宿主机做 NAT（网络地址转换）访问外网。

```
┌─────────────────────────────────────────────────────────┐
│                        宿主机                             │
│                                                          │
│  ┌────────────┐      ┌──────────────┐                   │
│  │  虚拟机 A   │      │  虚拟机 B    │                   │
│  │ 192.168.81.101  │  │ 192.168.81.102│                  │
│  └──────┬─────┘      └──────┬───────┘                   │
│         │                   │                            │
│         └────────┬──────────┘                            │
│                  │                                       │
│             ┌────▼────┐                                  │
│             │ VMnet8  │   ← 虚拟交换机                   │
│             └────┬────┘                                  │
│                  │                                       │
│          ┌───────┴────────┐                              │
│          │  NAT 设备      │  ← 关键组件                  │
│          │ (SNAT/DNAT)    │                              │
│          └───────┬────────┘                              │
│                  │                                       │
│          ┌───────┴────────┐                              │
│          │  DHCP 服务器    │  ← 自动分配 192.168.81.0/24 │
│          └───────┬────────┘                              │
│                  │                                       │
│             ┌────▼────┐                                  │
│             │  物理网卡 │                                  │
│             │ (eth0)  │                                  │
│             └────┬────┘                                  │
└──────────────────┼──────────────────────────────────────┘
                   │
              ┌────▼────┐
              │ 外部网络  │
              └─────────┘
```

**关键组件**：

| 组件 | 作用 |
|------|------|
| **VMnet8** | 虚拟交换机，连接同一 NAT 网络内的所有虚拟机 |
| [[NAT|NAT 设备]] | 负责 IP 地址转换和端口映射 — 它是宿主机上的一个用户态进程 |
| **DHCP 服务器** | 自动分配 `192.168.81.0/24` 网段的 IP（网段可配置） |
| **虚拟网卡（宿主机侧）** | 宿主机上生成一个虚拟网卡 `vmnet8`，IP 为 `192.168.81.1`，作为虚拟机的网关 |

#### 通信流程

**VM 访问外网（出站）**：
1. VM A（`192.168.81.101`）发送数据包到 `8.8.8.8`
2. 数据包到达 VMnet8，根据路由被送到 NAT 设备
3. NAT 设备执行 SNAT：将源 IP 从 `192.168.81.101` 替换为宿主机的物理网卡 IP（如 `192.168.1.100`）
4. NAT 设备记录这个连接的五元组映射，存入 conntrack 表
5. 数据包从物理网卡发出到外部网络
6. 回包到达宿主机时，NAT 设备查 conntrack 表，将目的 IP 还原为 `192.168.81.101`
7. 数据包通过 VMnet8 送达 VM

**外网访问 VM（入站）**：
1. 外部无法直接访问 `192.168.81.101`（这是一个私有地址）
2. 需要在 NAT 设备上配置**端口转发**规则
3. 例如：宿主机 IP `192.168.1.100:8080` → 转发到 VM `192.168.81.101:80`

```bash
# VMware 的端口转发配置（在虚拟网络编辑器中设置）
# 将宿主机的 8080 端口转发到 VM 的 80 端口
# 这等价于 iptables DNAT 规则
```

#### 关键特性

| 维度 | 说明 |
|------|------|
| IP 地址 | 私有子网（默认 `192.168.81.0/24`） |
| 外部访问 VM | 需手动配置端口转发 |
| 性能损耗 | **~15%** — NAT 转换和处理有 CPU 开销 |
| 隔离性 | **高** — 外部无法探测到内部虚拟机 |
| WiFi 适应性 | **极高** — 宿主机只要有网络连接即可 |

#### 适用场景

- **日常开发测试**（最推荐）— 开箱即用，无需关心局域网配置
- **在公共 WiFi / 公司网络中使用虚拟机** — 不需要 IT 部门开放网段
- **同时运行多个 VM，需要它们共享同一 IP 上网** — 多台 VM 共享宿主机 IP

> [!note] 关于性能损耗
> NAT 的 ~15% 损耗不是 VMware 的问题，而是 NAT 本身的固有开销 — 每收发一个数据包都需要查 conntrack 表、改写 IP 头、计算校验和。在文件传输、视频流等大流量场景下，这个影响较为明显。

### 1.3 仅主机模式（Host-Only）

#### 原理

仅主机模式创建一个**完全封闭**的虚拟网络 — 虚拟机只能和宿主机及同网络内的其他 VM 通信，无法访问外部网络。

```
┌─────────────────────────────────────────────┐
│                   宿主机                      │
│                                              │
│  ┌────────────┐     ┌──────────────┐         │
│  │  虚拟机 A   │     │  虚拟机 B    │         │
│  │ 192.168.94.101 │  │ 192.168.94.102│        │
│  └──────┬─────┘     └──────┬───────┘         │
│         │                  │                  │
│         └────────┬─────────┘                  │
│                  │                            │
│             ┌────▼────┐                       │
│             │ VMnet1  │  ← 虚拟交换机         │
│             └────┬────┘                       │
│                  │                            │
│          ┌───────┴────────┐                   │
│          │  虚拟网卡       │                   │
│          │  vmnet1        │  ← 宿主机访问用   │
│          │  192.168.94.1  │                   │
│          └────────────────┘                   │
│                                              │
│         ┌──────────────────────────┐          │
│         │    物理网卡 (eth0)       │          │
│         │    --- 完全隔离 ---      │          │
│         └──────────────────────────┘          │
└─────────────────────────────────────────────┘
```

**和 NAT 模式的关键区别**：仅主机模式没有 NAT 设备，所以数据包无法穿越到外部网络。

#### 关键特性

| 维度 | 说明 |
|------|------|
| 外网访问 | **不可用** |
| 宿主机 ↔ VM | 可以通信（通过 `vmnet1` 虚拟网卡） |
| VM ↔ VM | 可以通信（通过 VMnet1 交换机） |
| 安全性 | **极高** |
| 性能损耗 | 近乎无（没有 NAT 开销） |

#### 适用场景

- **恶意软件分析** — 隔离性最高，病毒无法通过 VM 感染外部网络
- **安全研究** — 测试漏洞利用、网络攻防实验
- **封闭开发环境** — 不需要联网的开发/测试场景
- **只想在宿主机和 VM 之间传文件或调试**

---

### 1.4 三种模式快速对比

| 维度      | 桥接（[[Bridge模式 | Bridged]]）               | [[NAT]]                  |
| ------- | ------------- | ------------------------ | ------------------------ |
| 虚拟交换机   | VMnet0        | VMnet8                   | VMnet1                   |
| IP 来源   | 同局域网 DHCP 或手动 | 内置 DHCP（192.168.81.0/24） | 内置 DHCP（192.168.94.0/24） |
| VM → 外网 | 直接可达          | 经宿主机 NAT                 | 不可达                      |
| 外网 → VM | 直接可达          | 需端口转发                    | 不可达                      |
| 性能损耗    | < 5%          | ~15%                     | < 5%                     |
| 配置难度    | 较高（需关注局域网兼容性） | 低（默认可用）                  | 低                        |
| 隔离性     | 无             | 中                        | 高                        |
| 推荐场景    | 对外服务          | 日常开发（默认）                 | 安全研究                     |

## 2. KVM 四种网络模式

[[KVM]]（Kernel-based Virtual Machine）是 Linux 上的原生虚拟化方案。与 VMware 集成了一套完整虚拟网络系统不同，KVM 的网络管理更加"Linux 原生" — 它依赖 **libvirt** 作为虚拟化管理层，底层网络实现基于 Linux bridge、[[iptables]]、dnsmasq 等标准组件。

### 2.1 Masquerade（NAT）模式

#### 原理

Masquerade 是 KVM 的**默认网络模式**。它的工作机制和 VMware 的 [[NAT]] 模式相似，但实现方式更"Linux 原生"。

```
┌─────────────────────────────────────────────────┐
│                     宿主机                        │
│                                                   │
│  ┌──────────┐      ┌──────────┐                  │
│  │   VM A    │      │   VM B   │                  │
│  │ 192.168.122.101 │ 192.168.122.102 │            │
│  └─────┬────┘      └─────┬────┘                  │
│        │                 │                        │
│        └────────┬────────┘                        │
│                 │                                 │
│            ┌────▼────┐                            │
│            │  virbr0  │  ← Linux bridge           │
│            └────┬────┘                            │
│                 │                                 │
│     ┌───────────┴───────────┐                     │
│     │                       │                     │
│  ┌──▼──┐               ┌───▼────┐                │
│  │NAT  │               │dnsmasq │                 │
│  │(SNAT)│               │(DHCP)  │                 │
│  └──┬──┘               └────────┘                 │
│     │                                             │
│     │  iptables: POSTROUTING MASQUERADE           │
│     │                                             │
│     ▼                                             │
│  ┌──────┐                                         │
│  │ eth0 │  ← 物理网卡                             │
│  └──┬───┘                                         │
└─────┼───────────────────────────────────────────┘
      │
      ▼
   外部网络
```

**核心组件**：

| 组件 | 来源 | 职责 |
|------|------|------|
| **virbr0** | libvirt 自动创建 | 虚拟网桥，作为 VM 的二层交换机 |
| **dnsmasq** | libvirt 自动启动 | DHCP（默认 `192.168.122.0/24`）+ DNS |
| **iptables SNAT** | libvirt 自动添加 | 源地址转换，实现 VM 访问外网 |
| **ip_forward** | libvirt 自动开启 | 内核 IP 转发 |

当 libvirt 启动时，它自动执行了这些命令：

```bash
# libvirt 自动帮你做的事情（等价于）：
sudo ip link add virbr0 type bridge
sudo ip link set virbr0 up
sudo ip addr add 192.168.122.1/24 dev virbr0

# 启动 dnsmasq 提供 DHCP/DNS
sudo dnsmasq --interface=virbr0 \
  --dhcp-range=192.168.122.2,192.168.122.254,255.255.255.0 \
  --dhcp-option=3,192.168.122.1  # 网关设为 virbr0 的 IP

# 添加 iptables 规则实现 NAT
sudo iptables -t nat -A POSTROUTING -s 192.168.122.0/24 \
  ! -o virbr0 -j MASQUERADE

# 开启转发
sudo sysctl -w net.ipv4.ip_forward=1
```

#### 配置查看

```bash
# 查看 libvirt 的网络列表
sudo virsh net-list

# 查看默认网络的详细信息
sudo virsh net-dumpxml default
```

输出示例：
```xml
<network>
  <name>default</name>
  <uuid>...</uuid>
  <forward mode='nat'/>
  <bridge name='virbr0' stp='on' delay='0'/>
  <mac address='52:54:00:...'/>
  <ip address='192.168.122.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='192.168.122.2' end='192.168.122.254'/>
    </dhcp>
  </ip>
</network>
```

#### 查看底层 iptables 规则

```bash
# 查看 KVM 自动添加的 NAT 规则
sudo iptables -t nat -L -n -v | head -15
```

输出示例：
```
Chain POSTROUTING (policy ACCEPT 0 packets, 0 bytes)
pkts bytes target     prot opt in     out     source        destination
1234  567K MASQUERADE  all  --  *      !virbr0  192.168.122.0/24  0.0.0.0/0
```

这条规则的含义：源地址为 `192.168.122.0/24` 且**不是**从 `virbr0` 出去的包（也就是发往外部网络的包），做 MASQUERADE。

### 2.2 桥接模式（Bridge）

桥接模式让 VM 的虚拟网卡直接连接到宿主机所在的物理网络。

#### 创建桥接网络

与 VMware 的桥接不同，KVM 的桥接需要在宿主机上**手动创建**一个 bridge，将物理网卡加入 bridge，然后 VM 接入这个 bridge。

```bash
#!/bin/bash
# 手动创建桥接网络

# 确保安装了需要的工具
sudo apt install bridge-utils  # Ubuntu/Debian
# 或 sudo yum install bridge-utils  # CentOS/RHEL

# 步骤 1：创建一个 bridge
sudo ip link add br0 type bridge

# 步骤 2：将物理网卡（如 eth0）加入 bridge
# 先把 eth0 的 IP 迁移到 br0
sudo ip addr del 192.168.1.100/24 dev eth0
sudo ip link set eth0 master br0

# 步骤 3：给 bridge 配 IP（替代原来 eth0 的 IP）
sudo ip addr add 192.168.1.100/24 dev br0
sudo ip link set br0 up

# 步骤 4：设置默认路由（指向网关 192.168.1.1）
sudo ip route add default via 192.168.1.1 dev br0

# 步骤 5：物理网卡不需要 IP 了，但仍需 up
sudo ip link set eth0 up
```

#### 永久配置（/etc/network/interfaces，Ubuntu）

```
# 在 /etc/network/interfaces 中添加：
auto br0
iface br0 inet static
    address 192.168.1.100
    netmask 255.255.255.0
    gateway 192.168.1.1
    bridge_ports eth0
    bridge_stp off
    bridge_fd 0
```

#### 网卡混杂模式

桥接模式要求物理网卡进入**混杂模式**：

```bash
# 检查物理网卡的混杂模式状态
ip link show eth0

# 输出中的 PROMISC 标志表示混杂模式已开启：
# eth0: <BROADCAST,MULTICAST,PROMISC,UP,LOWER_UP> ...
```

混杂模式确保物理网卡会接收**所有**经过它的数据包（不只是自己的 MAC 地址的包），这样才能把属于 VM 的包也收上来，通过 bridge 转发给 VM。

#### 关键特性

| 维度 | 说明 |
|------|------|
| 性能 | **< 5% 损耗** — 近乎原生 |
| 配置 | 需要手动创建 bridge（相比 VMware 的自动配置更复杂） |
| IP | VM 直接从局域网 DHCP 获取或手动配 |
| 对物理网卡的影响 | 暂时断网 — 在迁移 IP 到 br0 的瞬间网络会中断 |

> [!warning] 实践建议
> 如果远程连接服务器做桥接配置，务必小心！`ip addr del` 删除 IP 的瞬间 SSH 连接会断开。建议通过 IPMI/iDRAC 带外管理，或先写一个脚本来避免意外断开。

### 2.3 路由模式（Routed）

路由模式是桥接和 NAT 之间的折中方案。

#### 原理

```
┌─────────────────────────────────────────┐
│             宿主机                        │
│                                          │
│  ┌──────────┐  ┌──────────┐              │
│  │  VM A    │  │  VM B    │              │
│  │ 10.0.1.2 │  │ 10.0.1.3 │              │
│  └────┬─────┘  └────┬─────┘              │
│       │             │                    │
│       └──────┬──────┘                    │
│              │                           │
│         ┌────▼────┐                      │
│         │ virbr0  │   ← 虚拟交换机      │
│         │ 10.0.1.1  │                    │
│         └────┬────┘                      │
│              │                           │
│         ┌────▼────┐                      │
│         │ 路由决策  │  ← NETMAP / 路由   │
│         └────┬────┘                      │
│              │                           │
│         ┌────▼────┐                      │
│         │  eth0   │                      │
│         │ 192.168.1.100                  │
│         └────┬────┘                      │
└──────────────┼──────────────────────────┘
               │
          ┌────▼────┐
          │ 物理路由器 │
          │ 需配置到    │
          │ 10.0.1.0/24 │
          │ 的静态路由   │
          └─────────┘
```

**路由模式 vs 桥接模式**：
- 桥接模式：VM 和宿主机在同一子网（L2 连通）
- 路由模式：VM 在独立子网（L3 连通），需要物理路由器配置到 VM 子网的路由

**路由模式 vs NAT 模式**：
- NAT 模式：VM 访问外网时源 IP 被替换，外网无法直接访问 VM
- 路由模式：VM 使用自己的 IP 直接通信，外网可以直达 VM（只要路由可达）

#### 配置方法

```bash
# 在 libvirt 中创建路由网络
sudo virsh net-define /tmp/routed-network.xml
sudo virsh net-start routed-net
```

`/tmp/routed-network.xml`:
```xml
<network>
  <name>routed-net</name>
  <forward mode='route'/>
  <bridge name='virbr1' stp='on' delay='0'/>
  <ip address='10.0.1.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='10.0.1.10' end='10.0.1.100'/>
    </dhcp>
  </ip>
</network>
```

然后在物理路由器上添加静态路由：
```
# 在路由器上配置
ip route add 10.0.1.0/24 via 192.168.1.100
# 告诉路由器：去 10.0.1.0/24 的包发给宿主机 192.168.1.100
```

#### 关键特性

| 维度 | 说明 |
|------|------|
| 性能 | < 5% 损耗 |
| 隔离性 | 中（通过独立子网隔离） |
| 配置复杂度 | 高（需要协调外部网络团队配置路由表） |
| 适用场景 | 多租户环境、需要独立 IP 空间的场景 |

---

### 2.4 隔离模式（Isolated）

隔离模式等价于 VMware 的仅主机模式。VM 之间可以通信、VM 和宿主机可以通信，但没有任何出口到外部网络。

```xml
<network>
  <name>isolated-net</name>
  <bridge name='virbr2' stp='on' delay='0'/>
  <!-- 没有 <forward> 元素 — 不转发到外部 -->
  <ip address='172.16.0.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='172.16.0.10' end='172.16.0.100'/>
    </dhcp>
  </ip>
</network>
```

**关键**：配置中没有 `<forward>` 标签，这就告诉 libvirt 这个网络是完全隔离的，不做任何转发。

---

### 2.5 KVM 四种模式对比

| 模式 | 实现方式 | VM→外网 | 外网→VM | 性能损耗 | 配置复杂度 |
|------|---------|---------|---------|---------|-----------|
| **Masquerade (NAT)** | virbr0 + iptables SNAT | 可（NAT） | 需端口转发 | ~15% | 低（默认） |
| **[[Bridge模式|Bridge]]** | br0 + 物理网卡混杂 | 直接 | 直接 | < 5% | 高（需手动创建） |
| **Routed** | L3 路由 + 外部路由表 | 直接 | 直接 | < 5% | 极高（需外部路由） |
| **Isolated** | 私有 bridge，无转发 | 不可 | 不可 | 无 | 低 |

## 3. Docker + VM 混合部署场景

### 3.1 问题场景

现在越来越多的部署采用**混合架构**：

```
        同一台物理机
    ┌─────────────────────┐
    │                     │
    │  KVM Hypervisor     │
    │  ┌──────────────┐   │
    │  │   VM 1       │   │
    │  │  ┌─────────┐ │   │
    │  │  │ Docker  │ │   │
    │  │  │ 容器 A   │ │   │
    │  │  │ 容器 B   │ │   │
    │  │  └─────────┘ │   │
    │  └──────────────┘   │
    │                     │
    │  ┌──────────────┐   │
    │  │   VM 2       │   │
    │  │  (无 Docker)  │   │
    │  └──────────────┘   │
    └─────────────────────┘
```

典型场景：
- **开发环境**：在 KVM 虚拟机中运行 Docker 进行开发和测试
- **混合集群**：部分服务在 VM 中运行（如数据库），部分在容器中运行（如 Web 应用）
- **迁移过渡**：传统 VM 架构逐步向容器化迁移，中间阶段两者共存

### 3.2 问题：两层 NAT 的性能灾难

如果 VM 使用 KVM 的默认 Masquerade 模式，而 VM 内的 Docker 也使用默认 bridge 模式，就会出现**两层 NAT**：

```
容器 (172.17.0.2) → Docker bridge (172.17.0.1)
  → Docker iptables MASQUERADE → VM (192.168.122.101)
    → KVM virbr0 + iptables SNAT → 宿主机 (192.168.1.100)
      → 外部网络
```

**性能影响**：

| 层级 | 操作 | 额外开销 |
|------|------|---------|
| Docker 层 | iptables MASQUERADE | ~5-10% |
| KVM 层 | iptables SNAT | ~5-10% |
| 两层 conntrack | 双倍连接追踪 | 内存 + CPU |
| **合计** | | **~15-20% 额外损耗** |

除了性能，两层 NAT 还带来：

1. **外部无法直接访问容器** — 需要同时配置 KVM 的端口转发和 Docker 的端口映射
2. **调试困难** — `tcpdump` 抓到的 IP 地址经过两次改写，难以追踪真实来源
3. **MTU 问题翻倍** — 每一层 NAT 都可能因为封装导致 MTU 不一致

### 3.3 推荐方案：macvlan / ipvlan

`macvlan` 和 `ipvlan` 是 Linux 内核提供的网络驱动，可以让容器**跳过** Docker bridge，直接使用物理网卡（或 VM 的虚拟网卡）。

#### macvlan 原理

```
┌─────────────────────────────────────────┐
│               KVM 虚拟机                  │
│                                          │
│  ┌────────────┐  ┌────────────┐          │
│  │  容器 A    │  │  容器 B    │          │
│  │  MAC: AA:AA │  │ MAC: BB:BB │          │
│  │  IP: 10.0.0.2 │  │ IP: 10.0.0.3│        │
│  └──────┬─────┘  └──────┬─────┘          │
│         │               │                 │
│    ┌────┴───────────────┴┐                │
│    │   eth0 (物理网卡)    │                │
│    │   MAC: CC:CC        │                │
│    │   IP: 10.0.0.1      │                │
│    └────────┬─────────────┘               │
└─────────────┼─────────────────────────────┘
              │
         ┌────▼────┐
         │ 物理交换机 │
         └─────────┘
```

**关键特点**：
- **每个容器获得独立的 MAC 地址** — 从物理网络角度看，每个容器就是一个独立的"设备"
- **容器直接出现在物理网络的广播域中** — 和 VM 在同一个子网
- **性能近乎原生** — 没有 NAT、没有 bridge 转发，只有内核级的二层交换

```bash
# 在 Docker 中创建 macvlan 网络
docker network create -d macvlan \
  --subnet=10.0.0.0/24 \
  --gateway=10.0.0.1 \
  -o parent=eth0 \
  macnet

# 使用 macvlan 网络启动容器
docker run --network=macnet --ip=10.0.0.10 -d nginx
```

#### macvlan 的局限性

| 局限性 | 说明 | 解决方法 |
|--------|------|---------|
| **容器与宿主机不能直通** | 容器拥有独立的 MAC，宿主机使用不同的 MAC，二层上宿主机和容器无法直接通信 | 创建子接口 `eth0.10` 给 macvlan，宿主机走 `eth0` |
| **仅限 Linux** | Docker 的 macvlan 驱动只支持 Linux 主机 | Windows 场景不可用 |
| **云平台不支持** | AWS、Azure、GCP 等云平台直接屏蔽非授权 MAC 地址 | 在云上改用 overlay 或 host 模式 |
| **MAC 地址数量限制** | ESXi 默认限制每端口 8 个 MAC，vSwitch 限制 64 个 | 调整 ESXi 参数或改用 ipvlan |

#### ipvlan 作为替代方案

ipvlan 和 macvlan 的核心区别：**所有容器共享父接口的 MAC 地址**，靠 IP 来区分彼此。

```bash
# L2 模式 — 同子网通信
docker network create -d ipvlan \
  --subnet=10.0.0.0/24 \
  --gateway=10.0.0.1 \
  -o parent=eth0 \
  -o ipvlan_mode=l2 \
  ipvlan-net-l2

# L3 模式 — 路由隔离，不同容器在独立子网
docker network create -d ipvlan \
  --subnet=10.0.1.0/24 \
  --subnet=10.0.2.0/24 \
  -o parent=eth0 \
  -o ipvlan_mode=l3 \
  ipvlan-net-l3
```

**ipvlan 的优势**：
- 不消耗额外的 MAC 地址 — 克服了 macvlan 在虚拟化平台上的最大痛点
- L3 模式提供天然网络隔离
- 内核 4.2+ 支持，已有广泛兼容性

### 3.4 混合部署最佳实践

```
┌────────────────────────────────────────────────────┐
│                   物理网络                          │
│              192.168.1.0/24                        │
│                                                      │
│  ┌────────┐  ┌────────┐  ┌────────┐  ┌───────────┐ │
│  │ 数据库  │  │  Web   │  │  Redis  │  │ 反向代理   │ │
│  │  VM    │  │  容器   │  │  容器   │  │  (haproxy) │ │
│  │192.168.1.10│192.168.1.11│192.168.1.12│ 192.168.1.2 │ │
│  └────────┘  └────────┘  └────────┘  └─────┬─────┘ │
│       │           │          │              │       │
│       └───────────┴──────────┴──────────────┘       │
│                   同一子网，直接通信                    │
└──────────────────────────────────────────────────────┘
```

**推荐架构**：

1. **VM 网络**：KVM 使用桥接模式（不要默认的 Masquerade）
2. **容器网络**：Docker 使用 macvlan 或 ipvlan（不要默认的 bridge）
3. **对外服务**：通过集中反向代理（haproxy/nginx）统一暴露服务
4. **访问控制**：结合 iptables 或 eBPF 做跨边界访问控制

**Why?**
- 所有 VM 和容器都在同一子网，彼此可以直接用 IP 通信
- 没有 NAT 性能开销
- 集中代理统一管理外部访问入口
- 简化了故障排查（IP 不会被改写）

## 4. VMware vs KVM 网络模式对照

| VMware 模式 | KVM 对应模式 | 原理类比 |
|-------------|-------------|---------|
| 桥接 (VMnet0) | Bridge (br0) | 虚拟机直连物理网络 |
| NAT (VMnet8) | Masquerade (virbr0) | 私有网络 + NAT 访问外网 |
| 仅主机 (VMnet1) | Isolated | 完全封闭的内部网络 |
| — | Routed | KVM 特有，需要外部路由支持 |

## 本章小结

- **VMware 三种模式**的核心区别在于虚拟机和外部网络的关系：桥接让 VM 直接接入 LAN（<5% 损耗），NAT 通过宿主机中转（~15% 损耗），仅主机完全隔离。
- **KVM 的默认 Masquerade 模式**基于 Linux bridge（virbr0）+ dnsmasq + iptables SNAT，是 libvirt 自动搭建的 NAT 网络。桥接模式需要手动创建 br0 并将物理网卡加入。
- **[[Docker]] + VM 混合部署**时，默认的"两层 NAT"（KVM Masquerade + Docker bridge）会导致性能损耗叠加和调试困难。推荐将两者都改为直连模式：KVM 用桥接，Docker 用 [[Macvlan|macvlan]]/[[Ipvlan|ipvlan]]。
- **macvlan** 给每个容器独立的 MAC 地址，性能近乎原生，但受限于云平台和 MAC 数量配额。**ipvlan** 共享 MAC 地址，在虚拟化平台上兼容性更好，L3 模式还能提供路由隔离。
