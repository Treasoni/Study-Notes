我们可以从大模型的底层计费和运行机制，来拆解为什么这种极其密集的网页抓取工作流会成为 "Token 碎钞机"。

### 一、 为什么这种 WebFetch 轰炸是 Token 灾难？

**1. 网页正文的"体积膨胀"**

大模型去抓取像 LangChain、CrewAI 官方文档或者各类技术博客（如 Lilian Weng 的博客）时，哪怕经过了初步的 HTML 清洗，整篇文档的字数也极其惊人。

- 官方文档通常包含大量的代码示例、侧边栏导航、无用页眉页脚。
- 随便抓取一个长篇的技术概念（比如截图里的 concepts/memory），解包出来的纯文本可能就高达 几千甚至上万 Token。
- 你这里并行或串行抓取了 20 多个网页，光是原始数据量就已经拉满了。

**2. 工具链调用（Tool Call）的"疯狂套娃"**

这是多 Agent 工作流最隐蔽的扣费点。如果你的 Subagent 是串行（一个接一个）执行这些 WebFetch 的：

- 第 1 步：抓取网页 A ➔ 大模型读了网页 A ➔ 决定去抓网页 B。
- 第 2 步：大模型带着【网页 A 的全部内容 + 之前的思考】去抓取网页 B ➔ 大模型同时读了 A 和 B ➔ 决定去抓网页 C。
- 第 3 步：大模型带着【网页 A + 网页 B + 思考历史】去抓网页 C……

后果：这种滚雪球式的多轮对话，会导致前面的网页内容被反复、叠加地作为输入投喂给大模型。如果不做特殊处理，Token 消耗呈几何级数（指数级）暴涨。

**3. 红叉（Failed 报错）彻底击穿缓存（Cache Miss）**

截图中出现了好几个红叉（如 Pinecone、Anthropic、OpenAI 的域名请求失败）。

- 网络超时或被反爬虫拦截返回的 403/504 Error 报错信息，属于完全不可预测的动态字符串。
- 这些报错信息一旦插进 Context 中，会直接污染并彻底击穿大模型的 Prompt Cache（提示词缓存），导致大模型不得不以全额原价去重新读取之前已经缓存过的那几十万 Token 的历史。

### 二、 应该如何优化这个"资料搜集"阶段？

既然这个 Subagent 的核心任务是"收集网上的学习资料"，我们不能因噎废食不让它抓取，但必须重构它的抓取策略：

**1. 将"抓取"与"思考"彻底剥离（走外部中间件）**

千万不要让主力大模型直接去当爬虫的调度器。

- 优化方案：在 Subagent 外部（用本地 Python 脚本，或者专门的 MCP 爬虫服务器）把这一长串 URL 一次性全部下载到本地。
- 使用类似 Jina Reader API 或 Firecrawl 这类专门的脱水工具，在外部就把网页转化为极简的、剔除了所有垃圾代码的 Markdown 纯文本，然后再一次性喂给大模型。

**2. 引入"流式单向摘要"机制（斩断上下文累积）**

不要让 Agent 带着全量网页内容进入下一轮。

- 做法：让一个廉价的小模型（如 DeepSeek-V3 或 GPT-4o-mini）专门负责干体力活：每下载完一个网页，立刻原地对它进行单向脱水摘要（比如把 1 万字的文档精简为 500 字的核心提纲和代码片段）。
- 最终，搜集 Agent 只需要把这 20 个网页的精简摘要合集交付给后面的笔记整理 Agent。全量网页正文在完成摘要后立刻从内存中销毁，绝不带入下一轮对话。

**3. 限制单次任务的抓取上限与并发度**

在 Agent 的 SOP 中增加强约束，例如："单次主题搜集允许的最大 WebFetch 次数不得超过 5 次，超出部分需提示用户确认"。

避免大模型因为某些关键词触发了"强迫症"，沿着文档链接无限抓取下去，导致 Token 彻底失控。
