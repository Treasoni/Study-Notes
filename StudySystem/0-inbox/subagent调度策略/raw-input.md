# Subagent 调度策略 —— Skill 强制编排 vs AI 动态拉起

## 1. 核心结论

在决定如何调用 Subagent 时，没有绝对的唯一解。核心原则是：

- 核心的、高频的常规工作流 → 写在 Skills 里强制执行（正规军模式）
- 突发的、探索性的任务 → 交给主 Agent 动态决定（游击战模式）

## 2. 模式对比与深度解析

### 方案 A：在 Skills 中强制编排（"正规军"模式）

将 Subagent 的调用逻辑和上下文传递硬编码到 Skill（SOP）中，构建稳定流水线。

**核心优势：**

- 消除信息衰减与幻觉：避免主 Agent 派发任务时"缺斤少两"。可以强制规定上下文传递格式（例如："调用测试 Agent 时，必须带上完整的 pytest 报错日志"）
- 绝对的权限与安全掌控：结合 `.claude/agents/` 下的固化配置，实现物理级权限隔离（例如强制 Review 环节的 Subagent 只有 [Read] 权限）
- 高度模块化：长篇 Prompt 被拆解为独立的步骤，像搭积木一样，易于后期维护

**适用场景（特征：3 步以上 + 逻辑固定）：**

- 代码提交前检查：主 Agent 编码 → linter-agent 查规范 → test-agent 跑测试
- 全局架构解析：让主 Agent 派发多个只读 Subagent 去不同目录收集信息，再汇总输出

### 方案 B：让主 Agent 自由发挥（"游击战"模式）

不写死在 SOP 中，依赖大模型（如 Sonnet）自身的判断力，遇到障碍时自行召唤"临时工"。

**核心优势：**

- 应对突发状况：开发中经常遇到预料之外的巨型日志或奇怪报错，临时拉起 Subagent 处理最灵活
- 探索性试错：面对完全陌生的 API 或环境时，主 Agent 可以动态决定拉起几个沙盒去分头探路

**适用场景：**

- 死胡同排错：主 Agent 连续修复失败后，开子进程去查文档或写测试脚本
- 复杂环境折腾：配置 PVE、Docker 网络等容易出现千奇百怪报错的场景

## 3. 最佳实践：混合调度架构 (Hybrid Strategy)

在实际开发中，最强大的系统应当是"主干稳定，分支灵活"的混合模式。

| 调度场景 | 执行策略 | 典型示例 |
|----------|----------|----------|
| 标准化工作流 | Skill 强制调度 | 重构代码后，必须经过专属 Reviewer 检查并出具报告 |
| 预期的异常处理 | Skill 分支触发 | "如果测试报错，请调用 test-runner 尝试修复，最多重试 3 次。" |
| 未知的突发阻碍 | 主 Agent 自由发挥 | 遇到看不懂的千行内核日志，主 Agent 随手拉个临时工去看，看完只拿总结 |

## 一句话总结

把摸透规律的、结构化的防错机制用 Skills 固化下来；把未知的、需要试错的精力留给主 Agent 去动态拉起。这样既有流水线的稳定，又有专家的灵活。
