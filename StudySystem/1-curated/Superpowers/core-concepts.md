# Superpowers - Core Concepts

## 1. Skill 系统架构

### Skill 是什么

Skill = 可复用的技术/模式/工具的参考指南。**不是**叙事性故事，而是结构化的操作指南。

### Skill 类型

| 类型 | 说明 | 示例 |
|------|------|------|
| Technique | 具体步骤和方法 | condition-based-waiting, root-cause-tracing |
| Pattern | 问题思考方式 | flatten-with-flags, test-invariants |
| Reference | API 文档/语法指南 | office 文档参考 |

### Skill 发现机制（CSO - Claude Search Optimization）

1. **Description 字段**：只写触发条件（"Use when..."），**不**写技能做了什么
   - 原因：如果 description 总结了流程，代理会直接按 description 执行，跳过完整 Skill 内容
2. **关键词覆盖**：包含错误信息、症状、工具名等可搜索词
3. **描述性命名**：动词开头（creating-skills 而非 skill-creation）

### 指令优先级

```
用户显式指令（CLAUDE.md） > Superpowers Skills > 默认系统提示
```

### 调用规则

```
即使只有 1% 的可能性某个 Skill 适用 → 也必须调用它
这不是可选的。不能合理化跳过。
```

## 2. Brainstorming（头脑风暴）

### 核心流程

```
探索项目上下文 → 提供可视化伴侣 → 逐个提问澄清 → 提出 2-3 种方案 → 分段展示设计 → 用户批准 → 写设计文档 → Spec 自审 → 用户审阅 → 转入 writing-plans
```

### 关键规则

- **HARD-GATE**：设计未批准前，禁止写代码、搭建项目、做任何实施动作
- **每次只问一个问题**，优先用选择题
- **YAGNI 无情砍**：从设计中删除不必要的功能
- **Anti-Pattern**："这个太简单不需要设计" → 错。所有项目都要走这个流程
- **Visual Companion**：可选的浏览器伴侣，用于展示原型和图表

### 设计文档

保存到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`

## 3. Writing Plans（编写计划）

### 核心原则

- 假设执行者**零代码库上下文**、品味堪忧
- 每个步骤 2-5 分钟，包含完整代码、精确文件路径、验证命令
- **零占位符**：不允许 TBD、TODO、"类似 Task N"

### 任务粒度示例

```
Step 1: 写失败测试 → Step 2: 运行验证失败 → Step 3: 写最小实现 → Step 4: 运行验证通过 → Step 5: 提交
```

### 计划文档头

```markdown
# [Feature] Implementation Plan
> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
**Goal:** 一句话描述
**Architecture:** 2-3 句描述
**Tech Stack:** 关键技术
```

## 4. Subagent-Driven Development（子代理驱动开发）

### 核心机制

**每任务新子代理 + 双重审查（规范合规 → 代码质量）**

### 流程

```
提取所有任务 → 逐任务执行：
  1. 派发实现子代理（附完整任务文本+上下文）
  2. 子代理提问？→ 回答 → 继续
  3. 子代理实现、测试、提交、自审
  4. 派发规范审查子代理 → 不通过则修复 → 重新审查
  5. 派发代码质量审查子代理 → 不通过则修复 → 重新审查
  6. 标记完成
→ 全部完成后：最终代码审查 → finishing-branch
```

### 模型选择策略

| 任务类型 | 推荐模型 |
|----------|----------|
| 机械实现（1-2 文件、明确 spec） | 快速廉价模型 |
| 集成和判断（多文件协调） | 标准模型 |
| 架构/设计/审查 | 最强模型 |

### 子代理状态处理

| 状态 | 处理 |
|------|------|
| DONE | 进入规范审查 |
| DONE_WITH_CONCERNS | 评估关切，再决定 |
| NEEDS_CONTEXT | 提供缺失上下文，重新派发 |
| BLOCKED | 评估阻塞原因：上下文问题/能力不足/任务过大/计划本身有误 |

### 连续执行原则

不要在任务间停下来问用户"要继续吗？"。只在以下情况停止：无法解决的 BLOCKED、阻碍进展的歧义、所有任务完成。

## 5. TDD（测试驱动开发）

### 铁律

```
没有失败测试就不能写生产代码
先写了代码再写测试？删除。重来。
```

### RED-GREEN-REFACTOR

```
RED:    写一个最小的失败测试
        ↓ 验证：测试失败（不是报错）
GREEN:  写最简单的代码让测试通过
        ↓ 验证：测试通过，其他测试也通过
REFACTOR: 清理（去重复、改名、提取辅助）
        ↓ 保持绿色
循环...
```

### 反合理化表（核心亮点）

| 借口 | 现实 |
|------|------|
| "太简单不需要测试" | 简单代码也会出 bug。测试只需 30 秒 |
| "我之后再测" | 之后写的测试立即通过，什么也证明不了 |
| "后写测试能达到同样目的" | 后写 = "这代码做什么？" 先写 = "这代码应该做什么？" |
| "已经手动测过了" | 临时测试 ≠ 系统测试。无记录、无法重跑 |
| "删掉 X 小时的工作太浪费" | 沉没成本谬误。保留未验证的代码才是技术债 |
| "TDD 太教条了" | TDD 才是务实的：更快发现 bug、防止回归、支持重构 |

## 6. Systematic Debugging（系统化调试）

### 铁律

```
没有根因调查就不能尝试修复
```

### 四阶段

| 阶段 | 关键活动 |
|------|----------|
| 1. 根因调查 | 读错误信息、复现、检查变更、收集证据、追踪数据流 |
| 2. 模式分析 | 找工作示例、对比参考实现、识别差异 |
| 3. 假设与测试 | 形成单一假设、最小变更测试、验证 |
| 4. 实施修复 | 创建失败测试、实现单一修复、验证 |

### 架构质疑规则

**3 次修复失败 → 停止修复 → 质疑架构**

模式：每次修复揭示新的耦合/状态问题，修复需要"大规模重构"，修复在其他地方产生新症状。

## 7. Writing Skills（元技能：如何编写 Skills）

### 核心映射

**编写 Skills = 将 TDD 应用于过程文档**

| TDD 概念 | Skill 创建 |
|----------|-----------|
| 测试用例 | 压力场景 + 子代理 |
| 生产代码 | Skill 文档 (SKILL.md) |
| 测试失败 (RED) | 代理在没有 Skill 时违反规则（基线行为） |
| 测试通过 (GREEN) | 代理在有 Skill 时遵守规则 |
| 重构 | 发现新的合理化借口 → 堵住 → 重新验证 |

### 铁律

```
没有失败测试就不能写 Skill
写了 Skill 没测试？删除。重来。
```

### SKILL.md 结构

```yaml
---
name: skill-name-with-hyphens
description: Use when [specific triggering conditions]
---
```

关键：**description 只写触发条件，不写流程**。因为测试发现，如果 description 总结了流程，Claude 会按 description 执行而跳过完整 Skill 内容。

### 反合理化机制

每个纪律性 Skill 都需要：
1. **封闭每个漏洞**：明确禁止具体的工作绕行方式
2. **理性化表**：从基线测试中收集的所有借口
3. **红旗列表**：代理自我检查用
4. **"精神 vs 字面"封堵**："违反字面规则就是违反精神规则"
