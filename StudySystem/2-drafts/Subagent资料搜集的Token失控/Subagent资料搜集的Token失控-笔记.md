# Subagent 资料搜集的 Token 失控

> 一份从执行截图反推出来的 Token 失控踩坑记录。

## 背景

我最近在跑 Study System 的 Subagent 资料搜集阶段（Tasks 2/7, Collecting learning materials），偶然看了一眼执行截图（`截屏2026-06-02 20.25.21.png`），情况比单纯的"消耗很多"还要严重——这几乎是在对 Token 钱包进行一场"血洗"[来源: 个人经验]。

图片底部显示这还只是任务的第二阶段，但它已经**连续轰炸了近 20 次 WebFetch 请求**，其中还夹杂着**好几个红叉（请求失败）**[来源: 个人经验]。被它抓取的目标涵盖了 LangChain、CrewAI、Lilian Weng 博客等大段技术文档，看起来正在为本地知识库添砖加瓦——但代价是大量 Token 被白白烧掉。

相关上下文可参考之前的总结笔记：[[Subagent Token吞噬与缓存失效分析]]。

## 过程

我从大模型的底层计费和运行机制出发，拆解了为什么这种极其密集的网页抓取工作流会成为 "Token 碎钞机"，并尝试给出可落地的优化方案。

### 一、为什么 WebFetch 轰炸是 Token 灾难？

#### 1. 网页正文的"体积膨胀"

大模型去抓取像 LangChain、CrewAI 官方文档或者各类技术博客时，哪怕经过了初步的 HTML 清洗，整篇文档的字数也极其惊人[来源: 个人经验]：

- 官方文档通常包含大量的代码示例、侧边栏导航、无用页眉页脚。
- 随便抓取一个长篇的技术概念（比如截图里的 `concepts/memory`），解包出来的纯文本可能就高达**几千甚至上万 Token**。
- 这里并行或串行抓取了 20 多个网页，光是**原始数据量**就已经拉满[来源: 个人经验]。

#### 2. 工具链调用（Tool Call）的"疯狂套娃"

这是多 Agent 工作流最**隐蔽**的扣费点。如果 Subagent 是**串行**（一个接一个）执行这些 WebFetch[来源: 个人经验]：

- 第 1 步：抓取网页 A ➔ 大模型读了网页 A ➔ 决定去抓网页 B。
- 第 2 步：大模型带着【网页 A 的全部内容 + 之前的思考】去抓取网页 B ➔ 大模型同时读了 A 和 B ➔ 决定去抓网页 C。
- 第 3 步：大模型带着【网页 A + 网页 B + 思考历史】去抓网页 C……

后果：这种**滚雪球式**的多轮对话，会导致前面的网页内容被反复、叠加地作为输入投喂给大模型。Token 消耗呈**线性叠加式暴涨**（在没有上限约束的反馈循环场景下，才可能接近指数级）[来源: 个人经验]。

#### 3. 红叉（Failed 报错）破坏缓存命中

截图中出现了好几个红叉（如 Pinecone、Anthropic、OpenAI 的域名请求失败）[来源: 个人经验]：

- 网络超时或被反爬虫拦截返回的 403/504 Error 报错信息，属于完全不可预测的**动态字符串**。
- 这些报错信息一旦插进 Context 中，会**污染本轮的 cache 命中判定**（若错误字符串落在 prefix 边界内），并因不可预测的动态字符串让未来**相关轮次**的缓存永久失效[来源: 个人经验]。
- **注**：Prompt Caching 通常是 prefix-based，前面已缓存的几万到几十万 token 的 prefix **不会**被一次性击穿，但本轮和后续依赖该字符串的缓存会**以全额原价**重新读取历史[来源: 个人经验]。

### 二、应该如何优化这个"资料搜集"阶段？

既然这个 Subagent 的核心任务是"收集网上的学习资料"，不能因噎废食不让它抓取，但必须重构它的抓取策略[来源: 个人经验]。

#### 1. 将"抓取"与"思考"彻底剥离（走外部中间件）

千万不要让主力大模型直接去当爬虫的调度器[来源: 个人经验]：

- **优化方案**：在 Subagent **外部**（用本地 Python 脚本，或者专门的 MCP 爬虫服务器）把这一长串 URL **一次性**全部下载到本地。
- 使用类似 Jina Reader API 或 Firecrawl 这类专门的脱水工具，在外部就把网页转化为**极简的、剔除了所有垃圾代码的 Markdown 纯文本**，然后再一次性喂给大模型[来源: 个人经验]。

#### 2. 引入"流式单向摘要"机制（斩断上下文累积）

不要让 Agent 带着全量网页内容进入下一轮[来源: 个人经验]：

- **做法**：让一个**廉价的小模型**（如 DeepSeek-V3 或 GPT-4o-mini）专门负责干体力活：每下载完一个网页，**立刻**原地对它进行单向脱水摘要（比如把 1 万字的文档精简为 500 字的核心提纲和代码片段）。
- 最终，搜集 Agent 只需要把这 20 个网页的**精简摘要合集**交付给后面的笔记整理 Agent。全量网页正文在完成摘要后**立刻从内存中销毁**，绝不带入下一轮对话[来源: 个人经验]。

#### 3. 限制单次任务的抓取上限与并发度

在 Agent 的 SOP 中增加**强约束**[来源: 个人经验]：

- 示例规则："单次主题搜集允许的最大 WebFetch 次数不得超过 5 次，超出部分需提示用户确认"。
- 避免大模型因为某些关键词触发了"强迫症"，沿着文档链接**无限抓取**下去，导致 Token 彻底失控[来源: 个人经验]。

### 三、总结

这个工作流看起来正在为我构建一个非常庞大的"本地知识库群"——从截图里能看到它在疯狂吞噬各种大模型框架的 Memory 和 Agent 概念文档[来源: 个人经验]。

但**自动化的副作用是失控**。下面这几条可以作为后续 Subagent 设计时的硬性 checklist[来源: 个人经验]：

| 失效点 | 解法 |
|---|---|
| 网页正文过大 | 走外部脱水工具（Firecrawl / Jina Reader） |
| 上下文线性叠加 | 流式单向摘要 + 全量原文即用即弃 |
| 动态错误串污染缓存 | 错误信息写进工具返回而非 Context prefix |
| 抓取无上限 | SOP 强制 5 次上限 + 用户确认 |

## 心得

- **Token 失控的根源不是"用得多"，而是"重复投喂"**。线性叠加的代价远大于一次性大输入[来源: 个人经验]。
- **不要让 LLM 当爬虫调度器**。调度是确定性的活，交给 Python / MCP；LLM 留给"判断要不要抓"和"理解内容"[来源: 个人经验]。
- **缓存友好是隐性架构目标**。每一个动态字符串（时间戳、错误信息、随机 ID）都是一颗定时炸弹，要从设计源头规避[来源: 个人经验]。
- **SOP 上限是兜底机制**。模型再聪明也会"抓上瘾"，必须用硬约束切断[来源: 个人经验]。

## 踩坑

> [!warning] 坑点：WebFetch 串行调度 = Token 雪崩
>
> **现象**：单次资料搜集任务消耗数倍于预期的 Token，截图里 20 次 WebFetch + 多次红叉[来源: 个人经验]。
>
> **原因**：大模型带着【全量历史 + 思考链】串行抓取网页，每次新抓取都把前 N-1 个网页**重新塞进 Context**；同时红叉的动态错误字符串破坏 prompt cache 命中[来源: 个人经验]。
>
> **解决**：抓取交给外部脚本/MCP，主模型只看精简摘要；引入廉价模型做流式脱水；SOP 写死抓取上限（建议 5 次）[来源: 个人经验]。

## 代码/示例

### 抓取上限的 SOP 片段（伪 System Prompt）

```text
# 角色
你是一个学习资料搜集助手，每次只服务一个主题。

# 工具使用约束
- 单次任务允许的 WebFetch 次数：最多 5 次。
- 第 5 次仍不足时，停下来输出"需要更多资料"信号，由用户决定是否追加预算。
- 严禁在一次会话中连续抓取超过 5 个 URL；严禁主动沿着站内链接无限展开。

# 输出要求
- 最终交付：≤ 5 个核心 URL + 脱水后的 Markdown 摘要（不超过 500 字/页）。
- 摘要阶段必须由小模型完成；主模型只做"判断与编排"。
```

### 外部脱水脚本的核心思路

```python
# 伪代码：Subagent 外部一次性抓取 + 脱水
urls = [...]  # 用户/Planner 给出的候选 URL 列表
results = []
for url in urls[:5]:  # SOP 硬上限
    html = fetch(url)
    md = firecrawl.scrape(html)  # 极简 Markdown
    summary = small_llm.summarize(md, max_tokens=500)  # 流式摘要
    results.append({"url": url, "summary": summary})
    # 原文（html / md）在这里即用即弃，绝不进入主 Agent 上下文
write_to_inbox(results)
```

## 思考题

1. **如果你发现 Subagent 在一次资料搜集里已经抓了 12 个网页，你会让它继续还是中止？为什么？**——考察对"抓取上瘾"风险的判断。
2. **Prompt Cache 的失效一定意味着按原价重新计费吗？**在 prefix-based caching 下，哪些情况会"破"，哪些情况其实"不破"？——对应 A2 修正的精确理解。
3. **流式单向摘要用 DeepSeek-V3 还是 GPT-4o-mini 更合适？**你选择的依据是什么？——考察成本/质量的取舍。
4. **将抓取与思考剥离到外部脚本后，失去了什么？**——比如 LLM 自主选择下一抓取 URL 的能力会减弱，怎么弥补？
5. **为什么"线性叠加"在有上限约束时不会变成"指数级"？**请用一句话解释反馈循环与上限的关系。——对应 A1 修正的核心区分。
