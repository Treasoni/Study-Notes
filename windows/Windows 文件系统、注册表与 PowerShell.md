## 第零章 导读：文件系统、注册表、PowerShell 是什么关系

装系统、修电脑、写脚本时，你迟早会同时遇到这三个词。它们看起来像三个互不相干的软件，实际上是一套系统的三个层次。这一章不讲命令，只帮你把三者的位置摆正——位置摆正了，后面三章的内容才不会互相打架。

### 0.1 三句话定位：各管一件事

**文件系统**管"数据放在哪"。官方定义里，Windows 支持的所有文件系统共用三个存储组件：**卷**是"目录和文件的集合"，**目录**是"目录和文件的分层集合"，**文件**是"相关数据的逻辑分组" [A1]。你平时双击进文件夹、复制粘贴、看 C 盘还剩多少空间，都是在和文件系统打交道。

> [!tip] 大白话
> 把文件系统想成一个仓库：卷是一整栋库房，目录是一排排货架，文件是货架上的箱子。它只回答"东西在哪个位置、怎么找到"。

**注册表**管"系统和程序怎么配置自己"。它是一个分层数据库，数据以树状组织，树上的每个节点叫**键**，键里可以放**子项**和**值**；官方把这种"键、子项和值"的逻辑组称为**配置单元**，英文 hive [S2]。系统的启动设置、程序的偏好、文件类型的关联方式，都记在这里。

> [!tip] 大白话
> 把注册表想成整台电脑的"后台登记本"：开机要看哪几页、某个程序要什么参数，翻这本本子就能查到。它不存你的照片和文档，只存"怎么设置"。

**PowerShell** 管"怎么用命令批量操作前两者"。它有一套叫**提供程序（Provider）**的机制，把不同的数据存储都以**驱动器**的形式暴露出来，路径与使用方式跟硬盘一样；于是同一批命令可以直接作用在文件上，也能作用在注册表键上 [C-5]。

> [!tip] 大白话
> PowerShell 像一只万能遥控器：不管对面是文件系统这台"电视"，还是注册表这台"空调"，都用同一套按键去操作。

### 0.2 两个交叉点：注册表长在文件系统上

第一个交叉点是**注册表存在硬盘文件里**。官方把配置单元（hive）描述为"一组在操作系统启动时或用户登录时加载到内存中的支持文件"；这些支持文件**大部分**位于 `%SystemRoot%\System32\Config` 目录中，当前用户的配置单元则是 `Ntuser.dat` [S2]。所以注册表和文件系统是"内容"与"存放位置"的关系。

> [!warning] 最容易混淆的一点
> 三者不是三个并列的软件，而是 **存储层（文件系统）/ 配置层（注册表）/ 操作层（PowerShell）** 的关系。读者最常搞错的，就是"注册表也是存在硬盘上的文件"这件事——很多人以为注册表是系统内部某种"内存里的设置"，其实它有实实在在的磁盘文件，只是平时不让你直接编辑。

第二个交叉点是**PowerShell 用同一套命令操作两者**。因为 Provider 把注册表也变成了"盘符"，你在文件系统上用惯的命令，换个注册表路径就能读、能建 [C-5]。这就是本笔记把 PowerShell 排在两个主题章之后的原因：它是把前面的内容串起来的那根线。

### 0.3 本笔记的两个阅读约定

**约定一：每个命令块都带"环境 / 版本 / 权限"三元组。**

- **环境**：这条命令在哪里敲——`cmd`（命令提示符）/ `PowerShell` / `regedit`（注册表编辑器界面）/ `diskpart`（交互式子环境）
- **版本**：`5.1`（`powershell.exe`）/ `7`（`pwsh.exe`）/ `5.1 & 7`；非 PowerShell 命令标"全版本适用"
- **权限**：是否需要管理员

**约定二：官方没写的，一律标"官方未说明"，不替你推断。**

最后一条尤其要注意。比如创建符号链接是否需要提升权限，官方页面根本没提，我们只会如实写"可能需要提升权限，官方文档未明确说明"，而不会编一个"必须用管理员"的结论。

### 0.4 动手前的安全纪律

1. **先在小范围试。** 任何命令先在测试目录、测试键上跑通，再放到正式位置。
2. **改注册表前先导出 `.reg`。** 官方在 reg 命令页用 Caution 级警告写明：注册表编辑器"绕过标准安全措施，允许降低性能、损坏系统甚至要求重新安装 Windows 的设置"，并明确要求"如果必须直接编辑注册表，请先备份它" [S8]。导出备份与导入还原的完整步骤，第 2 章会逐步给出。

### 本章小结

> [!summary] 小结
> - 文件系统管"数据放在哪"，核心结构是卷 / 目录 / 文件三层 [A1]
> - 注册表管"系统和程序怎么配置自己"，由键、子项、值组成 [S2]
> - PowerShell 管"怎么用命令批量操作前两者"，靠 Provider 把一切统一成"盘符" [C-5]
> - 注册表也长在硬盘上：配置单元的支持文件存放在 `%SystemRoot%\System32\Config` [S2]
> - 命令一律标注"环境 / 版本 / 权限"；官方未说明的权限要求写成"官方未说明"
> - 改注册表前先导出 `.reg` 备份，官方对此有 Caution 级警告 [S8]

下一章从最底层讲起：卷、目录、文件这三层是怎么定义的，路径为什么会写错，以及 C 盘里那些奇怪的文件夹各自是干什么的。

## 第一章 Windows 文件系统——数据到底放在哪

导读里我们把文件系统比作"仓库"：卷是库房，目录是货架，文件是箱子。这一章要把这个比喻落到能动手的程度——先看清仓库的三层命名规则，再摸清 C 盘里那些眼熟的文件夹各自是什么，最后学会几条真正能用的命令。学完这一章，你应该能回答三个问题：为什么有的路径会写错？C 盘里的 `WinSxS`、`AppData`、`ProgramData` 到底是什么？为什么复制文件时"看起来成功了"其实可能出过错？

本章的写法统一按一个套路：先用中文人话讲直觉，再给官方术语，最后说清"它到底指什么"。

### 1.1 三个基本名词：卷、目录、文件

#### 1.1.1 官方定义

Windows 支持的所有文件系统共用三个存储组件，官方给的定义是：**卷**是"目录和文件的集合"，**目录**是"目录和文件的分层集合"，**文件**是"相关数据的逻辑分组"；组织层级中最高的一级是卷，文件系统"驻留在卷上" [A1]。

翻译成人话：**卷**是一整块可以存放东西的区域（平时你叫它"C 盘""D 盘"）；**目录**是卷里的分层货架，货架还能挂货架，这就是"分层"；**文件**是最后放在货架上的箱子，存的是"相关数据"。你双击进文件夹、复制粘贴、看 C 盘还剩多少空间，全都是在跟这三层打交道。

#### 1.1.2 一个反直觉点：目录本身也是"文件"

很多人以为"目录"和"文件"是两种完全不同的东西。但在文件系统层面，**目录本身就是一种"具有特殊属性的文件"**，所以"必须像常规文件一样遵循所有命名规则" [A1][A2]。

这句话的后果很实际：下一节讲的"文件名不能包含哪些字符""不能叫 `NUL`""不能以句点结尾"，**对目录名同样生效**。你要是以为目录可以随便起名，就会在 1.2 节踩坑。

#### 1.1.3 NTFS 是什么，为什么新版 Windows 默认用它

**NTFS** 是 Windows 的一种文件系统格式，也是新版 Windows 的默认选择，它提供"安全描述符、加密、磁盘配额和支持丰富的元数据" [A14]。用中文说：它除了存数据，还额外记住"谁能访问这个文件"（安全描述符）、"怎么把内容加密"（加密）、"每个用户能占多少空间"（磁盘配额），以及一堆额外的说明信息（元数据）。

> [!tip] 大白话
> 把文件系统想成仓库的"货架制度"。FAT32 是最老的那套制度，只记"哪箱东西放在哪格"；NTFS 是新制度，除了位置，还记每箱的**钥匙权限、封条编号、占用额度**。所以同样一栋库房，换成 NTFS 这套制度后就能管权限、管加密、管配额。

> [!note] 这里不需要知道的事
> 官方文档在讲文件系统时，会写到"文件系统由一个或多个驱动程序和动态链接库组成"，还会出现 `CreateFile`、I/O 系统这类开发接口名 [A1]。这些是写给写驱动的程序员看的。对你来说，只需要记住一句话：**Windows 靠一组后台程序 + 系统文件来读写硬盘，你不需要知道它们在哪、叫什么名字。**

### 1.2 命名规则与路径规则（全章第一坑区）

这一节是整章最容易出错的地方。坑不在命令难，而在"你想当然的写法，和 Windows 实际的理解不一样"。

#### 1.2.1 九个保留字符 + NUL

文件（以及目录）名里**不能出现**这九个字符：`< > : " / \ | ? *`，外加整数值 0，也就是 NUL 字符 [A2]。其中**反斜杠 `\`** 的身份最特殊：它的作用是"把名称分隔成组件的保留字符" [A2]——也就是说，它不是名字的一部分，而是名字之间的分隔符。所以 `C:\a\b.txt` 里的两个 `\` 划出了 `C:`、`a`、`b.txt` 三个组件。

#### 1.2.2 保留设备名：`NUL.txt` 等于 `NUL`

有一批名字属于"操作系统自己要用"的，**不能拿来当文件名**：`CON`、`PRN`、`AUX`、`NUL`、`COM1`–`COM9`、`LPT1`–`LPT9` [A2]。这些名字来自早年 DOS 时代的设备概念。

坑在于官方还补了一句："另请避免这些名称紧跟扩展名" [A2]。也就是说，**`NUL.txt` 和 `NUL` 是等效的**，你并不会得到一个叫"NUL.txt"的普通文件。顺带一个冷门但有用的事实：字符码 **1–31 在备用数据流中允许使用**——流的命名规则和文件不一样（1.5 节会讲什么是流）[A2]。

> [!warning] `NUL.txt` 不是普通文件；8.3 短名也不能假设存在
> 文件名一旦撞上保留设备名（哪怕加了扩展名），行为就不是"创建了一个文件"那么简单 [A2]。另外，和短名相关的假设也要小心：8.3 短名**可以被禁用**，所以**不要假设某个文件一定有 `T97B4~1.TXT` 这样的短名** [A2]。

#### 1.2.3 别用空格或句点结尾；大小写不敏感

文件或目录名**不要以空格或句点结尾**，因为"Windows Shell 和用户界面不支持" [A2]。你也许能用底层接口造出这样的名字，但资源管理器不会好好显示它。

另一条：Windows 文件名**大小写不敏感**。官方原话是把名称 `OSCAR`、`Oscar` 和 `oscar` 视为相同；驱动器号同理，`D:\` 与 `d:\` 指的是同一个卷 [A2]。这对用惯了 Linux 的人是个反向冲击——在 Linux 上这是三个不同文件，在 Windows 上它们是同一个。

#### 1.2.4 8.3 短名：`T97B4~1.TXT`

为了兼容老程序，Windows 会给长文件名另外生成一个 "8.3 短名"，形如 `T97B4~1.TXT` [A2]。但官方给了一句关键提醒：**不要假设磁盘上已经存在 8.3 别名**——它可能被禁用 [A2]。

这个"不一定存在"的性质，会在 1.8 节变成一个真实风险：`dir` 的星号通配符**始终使用短文件名映射**，如果短名被启用，`dir t97\*` 会同时匹配到 `t97.txt` 和 `t.txt2` [A12]。这个坑留到 1.8 节展开。

#### 1.2.5 绝对路径、相对路径、UNC——以及 `C:tmp.txt` 这个陷阱

官方对路径的解释方式是这样的："如果文件名不以下列项之一开头，则其与当前目录相对应"，而 UNC 路径、`C:\` 这种带盘符加反斜杠的、以及单独一个 `\` 开头的，都是例外 [A2]。

| 写法 | 官方含义 | 你的直觉对不对 |
|---|---|---|
| `tmp.txt` | 当前目录下的文件 | 对 |
| `C:\tmp.txt` | C 盘**根目录**下的文件 | 对 |
| `C:tmp.txt` | **C 盘当前目录**下的文件 | **错——很多人以为等于 `C:\tmp.txt`** |
| `\tmp.txt` | 当前盘根目录下 | 对 |
| `\\server\share\x.txt` | UNC 路径（网络共享） | 对 |

第三行是全章第一坑。官方明说：`C:tmp.txt` 指"驱动器 C 上当前目录中"的文件，**与 `C:\tmp.txt` 不同** [A2]。差别在于：`C:\` 带反斜杠，是"根目录"；`C:` 不带反斜杠，是"C 盘**当前的**目录"，会跟着你在 C 盘里 `cd` 到哪而改变。另外 `.` 表示当前目录、`..` 表示父目录 [A2]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：无需管理员

```cmd
# 假设当前目录是 C:\Users\Public
type C:tmp.txt    # 实际打开的是 C:\Users\Public\tmp.txt（C 盘的“当前目录”）
type C:\tmp.txt   # 打开 C 盘根目录下的 tmp.txt —— 完全是另一个文件
```

> [!warning] 把 `C:tmp.txt` 当成 `C:\tmp.txt`，会打开（或覆盖）另一个文件
> 这两个写法在资源管理器里看不出区别，在脚本里却指向不同位置。写路径时**盘符后面一律补上反斜杠**，能避开绝大多数"明明文件在，程序却说找不到"的问题 [A2]。

#### 1.2.6 路径开头的两个字符，决定 Windows 用哪套规则

官方把 `\\?\` 描述为：告诉 Windows API "禁用所有字符串分析，并将其后面的字符串直接发送到文件系统"；把 `\\.\` 描述为进入 Win32 设备命名空间，是"直接访问物理磁盘和卷的方式，而无需通过文件系统" [A2]。

用中文人话说：

- `\\?\C:\很长的路径\...`——这是给程序用的**"别自作聪明"开关**。平时 Windows 会对你的路径字符串做各种处理（补全、解析 `.` 和 `..`、判断长度），加上这个前缀就一律跳过，原样交给文件系统。
- `\\.\C:`——这是**直接对着设备说话**的入口，绕过文件系统这一层。日常基本用不到。

官方还提到，在更底层的 NT 命名空间里，Win32 看到的 `C:` 其实只是"指向 `HarddiskVolume1` 的符号链接" [A2]。这层属于写驱动的人关心的内容，**本章不展开**——你只要记住"**路径开头的两个字符决定了 Windows 用哪套规则理解它**"这一个直觉就够了。

#### 1.2.7 MAX_PATH = 260 与"扩展长度路径"

传统的路径长度上限是 **MAX_PATH = 260 个字符**，它的构成是"驱动器号、冒号、反斜杠、用反斜杠分隔的名称组件和终止 null 字符" [A3]。也就是说，这 260 里还包含了 `C:\` 和一个看不见的结尾字符，**实际能用的字符比 260 少**。

加上 `\\?\` 前缀后，可以使用"扩展长度路径，最大约 32,767 个字符"（UNC 路径要写成 `\\?\UNC\` 的形式）；官方明确说这个数字是**近似值** [A3]。但 `\\?\` 有代价：**不能用正斜杠 `/` 作分隔符，不能用 `.` 表示当前目录，也不能用 `..` 表示父目录** [A3]。另外两条细节：相对路径的总字符数始终不能超过 MAX_PATH；用 API 创建目录时，**目录名不能超过 MAX_PATH 减 12**（要留出 8.3 短名的空间）[A3]。

还有一个容易被忽略的分界：**Shell（资源管理器）和文件系统不是一套标准**。官方原话是"可以使用 Shell 用户界面无法正确解释的 Windows API 来创建路径" [A3]——换句话说，**资源管理器打不开的路径，在文件系统里可能真的存在**。

#### 1.2.8 长路径开关：一个注册表值 + 程序自己声明

从 Windows 10 版本 1607 起，许多 Win32 文件/目录函数移除了 MAX_PATH 限制，但**应用必须显式选择支持**。要同时满足两个条件 [A3]：

1. 注册表 `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem` 下的 `LongPathsEnabled` 值为 `1`；
2. 应用程序的清单里包含 `longPathAware` 声明。

**二者缺一不可。** 官方还提到这个值"按进程缓存"，因此"可能需要重新启动" [A3]。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：需要提升的特权（管理员）

```powershell
# 打开“长路径支持”这个开关（写入 HKLM，所以需要管理员权限）
New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem" `
  -Name "LongPathsEnabled" -Value 1 -PropertyType DWORD -Force
```

> [!tip] 大白话
> 把这个开关想成**仓库新装的一扇加宽门**：门装好了，不代表所有送货的人都会走它。**老程序不一定认这个开关**——它必须自己在清单里声明"我支持长路径"，才会走那道宽门。所以改完注册表还会遇到"某些老工具照样报路径太长"，这不是你没改对，而是它没表态。

> [!note] 留个心眼：本章的两个空白点
> 官方素材本轮**没有覆盖**两个问题：一是文件/目录三种时间戳（创建、访问、修改）的完整官方说明；二是 ReFS 与 NTFS 的区别。这两处本章不写结论，需要时另行查证。

### 1.3 盘符、卷、装入点与分区

#### 1.3.1 盘符和卷不是一回事

你平时说"C 盘"，说的是**盘符**（一个字母）。但盘符只是卷的一个"外号"——卷本身有自己的名字。官方给出的卷名语法是 `\\?\volume\{GUID}\`，其中**花括号不能省** [A11]。

#### 1.3.2 卷装入点：不给盘符也能挂载

**卷装入点**允许"链接卷，而无需驱动器号"，但它必须建立在"现有 NTFS 目录"上 [A11]。好处官方说得很直白：可以用"单个驱动器号（如 `C:`）访问所有本地卷"，"无需记住哪个卷对应于哪个驱动器号" [A11]。

> [!tip] 大白话
> 盘符像**给仓库单独开一扇大门并挂上字母门牌**（C、D、E……）。装入点则是**在已有走廊里开一道内门**：你不用新门牌，走 `C:\sysmount` 这扇内门，就进了另一间库房。字母只有 26 个，内门却可以随便开。

#### 1.3.3 `mountvol` 常用参数

`mountvol` 是管理卷装入点的命令行工具，常用参数有 `/l`、`/d`、`/p`、`/n`、`/e`、`/s` [A11]。其中 `/p` 的行为要特别知道：它会"卸载基本卷，使基本卷脱机，使其不可装载"，而且"**如果其他进程正在使用该卷，则 mountvol 会在卸载卷之前关闭所有打开的句柄**" [A11]。

> [!note] "关闭句柄"是什么意思
> 官方用"句柄"来描述"某个程序正开着这个卷"。翻译成人话：**别人正在用这个卷时，强卸载会先断开他们的连接**——正在往里写数据的程序可能因此报错。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```cmd
# 不带参数：列出当前卷与卷名（卷名里的花括号不能省）
mountvol

# 把一个卷挂到已存在的空目录 \sysmount（免盘符访问）
mountvol \sysmount \\?\volume{2eca078d-5cbc-43d3-aff8-7e8511f60d0e}\

# /d 删除装入点；/p 卸载卷并使其脱机（会先断开正在使用它的程序）
mountvol \sysmount /d
mountvol X: /p
```

#### 1.3.4 `diskpart` 的焦点模型

`diskpart` 是分区管理工具，官方明确要求："您必须在本地**管理员**组或具有类似权限的组中才能运行 diskpart。"[A15]

它的核心心智模型是**焦点（focus）**：官方说"必须先列出一个对象，然后选择一个对象以使其处于焦点状态。对象具有焦点后，键入的任何 diskpart 命令都将对该对象执行操作"，而且焦点会**自动转移**——"创建新分区时，焦点会自动切换到新分区" [A15]。

> [!warning] diskpart 最容易出错的地方：你以为在改 A，其实改的是 B
> 因为焦点是"隐式记住"的，连着敲命令时很容易忘记当前焦点停在哪。**每做一步破坏性操作前，先 `list` 一次确认对象**，是最省事的自保方式 [A15]。

> 环境：cmd（进入 diskpart 交互子环境）｜ 版本：全版本适用 ｜ 权限：必须属于本地管理员组

```cmd
# 进入 diskpart 交互子环境（需要管理员）
diskpart

# 以下命令在 diskpart> 提示符下输入
list disk                    # 先列出对象
select disk 1                # 选中后，它成为“焦点”
create partition primary     # 焦点会自动转移到新建的分区
format fs=ntfs label=Backup quick   # 快速格式化为 NTFS，卷标 Backup
```

#### 1.3.5 冷知识：NTFS 卷能有多大

NTFS 卷的上限**不是固定值，而取决于"群集大小"这个设置** [A14]。在本章的入门阶段你只需要记住一个直觉：**群集大小越大，单个卷能支持的容量越大**。具体数字放到这个冷知识框里：

| 群集大小 | 卷上限（官方数据） |
|---|---|
| 4 KB（默认） | 16 TB |
| 64 KB | 256 TB |
| 2048 KB（最大） | 8 PB |

另外官方补了一条：使用依赖卷影复制服务（VSS）快照的"以前版本"功能或备份程序时，**最大支持的卷大小为 64 TB** [A14]。（装载了超过上限的群集大小的卷时，系统会报 `STATUS_UNRECOGNIZED_VOLUME`，也就是"认不出这个卷" [A14]。）

### 1.4 系统目录地图：C:\Windows、Program Files、Users、ProgramData、AppData

这一节回答"我 C 盘里那些文件夹到底是干什么的"。先看一张全景图：

```text
C:\
├─ Windows\              ← %windir%
│  ├─ System32\
│  ├─ SysWOW64\          ← 仅 64 位系统上有
│  └─ WinSxS\            ← 本章只说明它存在
├─ Program Files\        ← %ProgramFiles%
├─ Program Files (x86)\  ← 仅 64 位系统上有
├─ ProgramData\          ← %ALLUSERSPROFILE%
└─ Users\
   ├─ <用户名>\          ← %USERPROFILE%
   │  └─ AppData\
   │     ├─ Roaming\     ← %APPDATA%
   │     ├─ Local\       ← %LOCALAPPDATA%
   │     └─ LocalLow\
   └─ Public\            ← %PUBLIC%
```

#### 1.4.1 `AppData` 三兄弟

用户配置文件目录 `%USERPROFILE%` 等于 `%SystemDrive%\Users\%USERNAME%`；它下面的 **`AppData` 分成三个子目录** [A6]：

- **`Roaming`**（`%APPDATA%`）——官方定义是"用作应用程序特定数据的通用存储库" [A6]。它叫"漫游"，意思是可以跟着账户配置一起同步。
- **`Local`**（`%LOCALAPPDATA%`）——官方定义是"充当本地非漫游应用程序的数据存储库" [A6]。也就是"只属于这台机器，不跟着走"。
- **`LocalLow`**——路径是 `%USERPROFILE%\AppData\LocalLow`，官方只给出路径和一句"**没有 CSIDL 等效项**" [A6]。

这三个文件夹的类型都是 **PERUSER**，也就是"**每个用户各有一份**" [A6][A7]。

> [!warning] `AppData\LocalLow` 的用途，官方未说明
> 素材里能查到的只有它的**路径**和"无 CSIDL 等效项"这一句 [A6]。网上常见的"低完整性级别进程使用"这类说法，本轮**没有任何官方来源支撑**，因此本节不写用途，只写它存在 [A6]。

#### 1.4.2 全机器共用的两个目录

- **`ProgramData`**（`%ALLUSERSPROFILE%`，典型路径 `C:\ProgramData`）——官方定义是"包含所有用户的应用程序数据的文件系统目录"；XP 时代的旧路径是 `%ALLUSERSPROFILE%\Application Data` [A6][A7]。
- **`Public`**（`%PUBLIC%`，典型路径 `C:\Users\Public`）——官方标注它是"Windows Vista 新增功能"，同样"无 CSIDL 等效项"；下面按类型分成 `Documents`、`Desktop`、`Music`、`Pictures`、`Videos`、`Favorites` [A6][A7]。

这两个目录的类型是 **FIXED**，也就是"**全机器共用一份**" [A6]。

> [!tip] 大白话
> 把 `AppData` 和 `ProgramData` 的区别想成**员工抽屉和公共储物柜**：`Roaming` 是你可以带走的抽屉，`Local` 是锁在这间办公室的抽屉，`LocalLow` 是一只官方没贴标签的抽屉；而 `ProgramData` 和 `Users\Public` 是走廊里的公共储物柜，全机器共用一份 [A6][A7]。

#### 1.4.3 `C:\Windows` 与 `System32`、`SysWOW64`

`C:\Windows` 由 `%windir%` 指向；`System32` 位于 `%windir%\system32`。关键的一点是：**在 64 位系统上，`FOLDERID_SystemX86` 解析到的其实是 `%windir%\syswow64`** [A6][A7]。

> [!warning] 关于 `System32` / `WinSxS`：本章只说明它们存在
> 网上常说这些目录"不可手动删除"。本轮素材**没有找到这个说法的官方依据**，所以本节**只描述它们存在**，不写"不可删"这类断言。要动这些目录前，请先自己查权威来源。

#### 1.4.4 `Program Files` 与 `Program Files (x86)`

`Program Files` 对应 `%ProgramFiles%`，典型路径 `%SystemDrive%\Program Files` [A6]。而 `Program Files (x86)` 有一条必须记住的规则：**它只存在于 64 位系统** [A6]。官方给出的对照是：

| 系统位数 | `FOLDERID_ProgramFiles` | `FOLDERID_ProgramFilesX86` |
|---|---|---|
| 32 位 | `Program Files` | `Program Files`（**同一个**） |
| 64 位 | `Program Files` | `Program Files (x86)` |

所以，**32 位系统上两个常量指向同一路径**，"`Program Files (x86)` 一定存在"是错误直觉 [A6]。另外两条附带规则：在 64 位系统上运行 **32 位**应用时，`FOLDERID_ProgramFiles` 也会被解析到 `Program Files (x86)`；而 `FOLDERID_ProgramFilesX64` 在"任一情况下使用都会导致错误" [A6]。

> [!warning] "`Program Files (x86)` 一定存在"是错误直觉
> 32 位系统上根本没有这个目录。写脚本时**不要假设它存在**，先判断系统位数或先检查目录是否存在 [A6]。（官方同一页面上对 `ProgramFilesX86` 默认路径的表述存在前后不一致，本节只采用"64 位系统上为 `Program Files (x86)`"这一结论 [A6]。）

### 1.5 NTFS 的四个特色功能：备用数据流、压缩、加密、稀疏文件

这四个功能都是"NTFS 有、老的 FAT32 没有"的能力。它们不是日常必用，但经常出现在"为什么这个文件删不干净""为什么复制后大小对不上"这类问题里。

#### 1.5.1 备用数据流（ADS）：文件身上的"隐藏附加文件"

**备用数据流**（官方的叫法是"流"）是这么定义的：NTFS 中"流包含写入文件的数据，并提供有关文件的详细信息，而不是属性"（例如搜索关键字、创建者身份）[A8]。

关键在于：**每个流有自己的分配大小、实际大小，并"维护自己的压缩、加密和稀疏状态"**；而且**流没有自己的文件时间**——"更新文件中的任何流时，文件的文件时间将更新" [A8]。

> [!tip] 大白话
> 把文件想成一个**文件夹**：平时你只看到里面那份"主文件"，但 NTFS 允许它**再挂几个隐藏的附件**。这些附件有自己的大小、自己的压缩/加密状态，却**没有自己的时间戳**——你动附件，文件的修改时间照样会变。想知道一个文件身上挂了几份附件，用 `dir /r`。

#### 1.5.2 观察 ADS 的入口：`dir /r`

流的命令行全名格式是"`文件名:流名称:流类型`"（例如 `myfile.dat:stream1:$DATA`）；默认数据流是未命名的，所以 `文件名::$DATA` 等价于 `文件名` [A8]。

几条命名规则要知道：流名称只能用文件名的合法字符（**含空格**）；**用户无法创建新的流类型**；流类型"始终以美元符号（$）符号开头" [A8]。另外，单字符文件名必须写成全限定路径或加 `.\`，因为"Windows 将单个字符文件名视为驱动器号" [A8]。

> [!note] 进阶附录：额外流类型
> 官方还给出了一组"目录本身也是流"的等价写法（如 `DirName::$INDEX_ALLOCATION`），以及 EFS 使用 `$EFS`、事务性 NTFS 使用 `$TXF_DATA` 这类流类型 [A8]。它们属于进阶内容，本章不展开。

#### 1.5.3 NTFS 压缩：`compact`

`compact` 是"NTFS 文件系统压缩功能的命令行版本" [A13]。有一个非常容易误解的点：**目录的压缩状态表示的是"将文件添加到目录时是否自动压缩"，而"设置目录的压缩状态不一定更改目录中已存在文件的压缩状态"** [A13]。也就是说，你把一个目录标成"压缩"，里面**已经存在**的文件不会自动变小。

另外**不能压缩 FAT 或 FAT32 分区** [A13]。（`/EXE` 参数下的 `XPRESS4K`、`XPRESS8K`、`XPRESS16K`、`LZX` 等算法名属于进阶内容，本章不展开 [A13]。）

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```cmd
# 压缩整个卷（需在卷根目录执行）；/i 表示遇到错误继续处理
compact /c /i /s:\

# 只压缩指定扩展名，不改目录本身的压缩属性
compact /c /s:\tmp *.bmp

# 查询 / 设置系统级“紧凑 OS”状态
compact /CompactOs:query
compact /CompactOs:always
```

#### 1.5.4 EFS 加密：`cipher`

EFS"使用公钥系统为 NTFS 文件系统卷上的单个文件提供加密保护" [A21]。`cipher` 是最常用的查看/设置工具，输出里 **`E` 表示已加密、`U` 表示未加密** [A16]。

官方留下了一个经典坑，原文是："**如果未加密父目录，则修改文件时，加密文件可能会解密。因此，加密文件时，还应加密父目录。**" [A16]

> [!warning] 加密了单个文件，改一次就可能自动变回明文
> 只加密文件本身、不管父目录，会出现"改一下就解密"的情况。**加密时把父目录一起加密**，是官方明确给出的做法 [A16]。`cipher /w:<directory>` 则用于"从整个卷上可用未使用的磁盘空间中删除数据" [A16]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```cmd
# 查看当前目录下每个文件的加密状态：E=已加密，U=未加密
cipher

# 加密一个目录（务必连同它的父目录一起加密，见上方警告）
cipher /e C:\Users\Public\Secret

# 擦除卷上“已删除文件”留下的残留数据
cipher /w:C:\

# 导出 EFS 证书与密钥 —— 加密后一定要备份，丢了就打不开
cipher /x C:\Users\Public\Secret\a.txt
```

#### 1.5.5 EFS 与压缩：只验证了单向

官方明确列出 EFS **无法加密**的对象：**压缩文件**、系统文件、系统目录、根目录、交易 [A21]。但紧接着又说明：**可以加密稀疏文件** [A21]。

> [!warning] 只说一个方向：无法加密"已压缩"的文件
> 已有的官方证据是"**无法加密已压缩的文件**"这一条 [A21]。**反向结论（"加密后能否再压缩"）本轮没有验证**，所以本章**不写成"两者互斥"**，只写这一个方向 [A21]。

#### 1.5.6 稀疏文件：看起来占空间，其实没占

稀疏文件的原理是：程序"将这些未分配的区域视为包含值为零的字节，但没有使用磁盘空间来表示这些零" [A17]。也就是"内容全是零的部分不占地方，但读起来仍然是零"。

有两条限制要知道：应用必须**显式声明**文件为稀疏（对应一个叫 `FSCTL_SET_SPARSE` 的控制码），并"由应用程序负责"维持稀疏性；此外"**只有压缩文件或稀疏文件才能具有操作系统已知的清零范围**" [A17][A20]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：**必须以管理员或管理员组成员身份登录** [A18]

```cmd
# 把文件标记为稀疏文件
fsutil sparse setflag C:\temp\sample.txt

# 查询是否已标记为稀疏
fsutil sparse queryflag C:\temp\sample.txt

# 扫描文件里哪些区间是非零数据
fsutil sparse queryrange C:\temp\sample.txt

# 用零填充一段区间：从偏移 0 开始、长度 1048576 字节
fsutil sparse setrange C:\temp\sample.txt 0 1048576
```

> [!warning] `fsutil` 主页有信息缺口
> 素材显示 `fsutil` 主页面的**部分子命令描述在抓取结果中为空**，因此涉及 `fsutil fsinfo`、`fsutil volume` 的子命令本章**不展开** [A18]。

> [!warning] `compact` / `cipher` 要不要管理员？官方未说明
> 本轮官方页面**完全没有提到** `compact`、`cipher`、`mountvol`、`robocopy` 是否需要管理员权限 [A13][A16][A11][A10]。本节一律标注"官方未说明"，不替你推断。**唯一的例外是 `fsutil`**，它的官方页面明确写了"必须以管理员或管理员组成员身份登录" [A18]。

### 1.6 链接三兄弟：硬链接、符号链接、交接点

官方原话是："NTFS 文件系统支持三种类型的文件链接：硬链接、交接点和符号链接。" [A19]

| 类型 | 指向什么 | 能否跨卷 | 能否指目录 | `mklink` 参数 |
|---|---|---|---|---|
| **硬链接** | 同一卷上的**同一个文件** | **否** | **否** | `/h` |
| **符号链接** | 文件或目录（默认是文件） | 是 | 是（用 `/d`） | 默认 / `/d` |
| **交接点** | 一个**单独的目录** | 只限同一台机器的不同本地卷 | 是（只能是目录） | `/j` |

具体一点：硬链接是"文件的文件系统表示形式，其中多个路径引用同一卷中的单个文件"，它**不能引用目录，也不能引用不同卷上的文件** [A19]。交接点"引用的存储对象是单独的目录"，"还可以链接位于同一计算机上的不同本地卷上的目录"，它靠**重分析点**实现 [A19]。

> [!tip] 大白话
> 把链接想成 Windows 里的一种**"指针文件"**：硬链接是**给同一个箱子贴了第二个标签**（箱子还是一个）；符号链接和交接点更像**一张写着"东西在那边"的纸条**。最重要的一句话：**删链接 ≠ 删原文件**——你撕掉纸条，箱子还在原地。

#### 1.6.1 反直觉细节与删除语义

官方提到一个很容易看懵的细节：硬链接的"目录条目大小和文件属性信息**仅在进行更改的链接处**明显更新"——在一个链接上清掉只读标志，**其他链接仍显示只读** [A19]。

删除语义则是另一条关键规则：每个文件"可视为至少有一个硬链接"，"**只有在删除了指向某一文件的所有链接之后，才会从文件系统中删除该文件**" [A18]。

#### 1.6.2 `mklink` 的四种形态

`mklink` 默认创建**文件符号链接**，`/d` 创建目录符号链接，`/h` 创建硬链接，`/j` 创建**目录交接点**；删除链接用普通命令即可——`rd` 删目录符号链接、`del` 删硬链接 [A5]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：**官方未说明**

```cmd
# 目录符号链接（/d）—— 像快捷方式，但发生在文件系统层
mklink /d \MyFolder \Users\User1\Documents

# 硬链接（/h）—— 同一卷内，两个名字指向同一个文件
mklink /h \MyFile.file \Users\User1\Documents\example.file

# 目录交接点（/j）—— 官方叫“目录联接”，只能指向目录
mklink /j C:\LinkToData D:\Data
```

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：无需管理员

```cmd
# 删除链接用普通命令；删掉的只是“这个名字”，原文件仍在
rd C:\LinkToData
del C:\MyFile.file
```

> [!warning] `/j` 是"目录联接"，不是"目录硬链接"
> 社区里常把 `mklink /j` 叫成"目录硬链接"，但官方参数表的定义是"**目录联接**"（英文 junction）[A5]。以官方参数表为准 [A19]。硬链接**根本不能指向目录**，所以"目录硬链接"这个说法在概念上就站不住。

> [!warning] `mklink /F` 这个参数不存在
> 官方参数表里只有 `/d`、`/h`、`/j`、`/?` 四种 [A5]。网上流传的 `mklink /F` 是错误信息，敲下去只会得到"参数无效"。

> [!warning] `mklink /d` 要不要管理员？官方文档未明确说明
> 创建符号链接**可能需要提升权限，但官方文档没有明确说明这一点** [A5]。如果你执行时遇到"拒绝访问"，最务实的做法是以管理员身份重试一次——但请注意，这是操作建议，不是官方结论。

### 1.7 查看与修改元数据：文件属性（attrib）与权限（icacls）

#### 1.7.1 文件属性：`attrib`

`attrib` 可设置的属性字母包括：`r` 只读、`a` 存档、`s` 系统、`h` 隐藏、`o` 脱机、`i` 非内容索引、`x` 清理、`p` 固定、`u` 未固定、`b` SMR Blob [A9]。常用的三个开关是：`/s` 递归子目录、`/d` 作用于目录、`/l` 作用于符号链接**本身**而不是它指向的目标 [A9]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：无需管理员

```cmd
# 查看单个文件的属性
attrib news86

# 加上 / 去掉只读属性
attrib +r report.txt
attrib -r b:\public\*.* /s
```

> [!warning] `attrib` 有一条操作顺序说法，仅有一条官方来源、未实测
> 官方写到：文件若设了**系统属性或隐藏属性**，"必须清除该属性，然后才能更改文件的任何其他属性" [A9]。本轮**只有这一条来源，且未实际验证**，所以你按这个顺序操作**可能得不到预期结果**。遇到"改了没反应"时，先把 `s` / `h` 清掉再改一次试试。

#### 1.7.2 `icacls`：看权限和改权限

`icacls` 的作用是"显示或修改指定文件中的任意访问控制列表（DACL）"，并取代已弃用的 `cacls` [A4]。这里有两个新名词：

- **DACL**：可以理解成"**这张通行名单**"——谁被允许、谁被拒绝，都在里面。
- **SID**：账户的**内部编号**，形如 `S-1-5-21-...`，**不是用户名** [A4]。

官方还说明，ACE（名单里的每一条）有**固定的规范顺序**：显式拒绝 → 显式授予 → 继承的拒绝 → 继承的授予 [A4]。

简单权限字母不用加括号：`N` 无法访问、`F` 完全访问、`M` 修改、`RX` 读取和执行、`R` 只读、`W` 只写、`D` 删除 [A4]。而**高级权限和继承标志必须写在括号里**：例如 `(DE)` 删除、`(WDAC)` 更改权限、`(WO)` 获取所有权、`(RD)` 读取数据/列出目录、`(X)` 执行/遍历；继承标志有 `(I)` 继承、`(OI)` 对象继承（仅目录）、`(CI)` 容器继承（仅目录）、`(IO)` 仅继承、`(NP)` 不传播继承 [A4]。

一条极易忽略的区别：`/grant:r` 是"权限**替换**以前授予的显式权限"，不带 `:r` 则是"**添加**到任何先前授予的显式权限中" [A4]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：无需管理员（改系统目录等位置需要相应权限）

```cmd
# 查看一个路径的权限（列出的就是 DACL 里的各条 ACE）
icacls C:\Users\Public\demo.txt
```

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：无需管理员（视目标位置而定）

```cmd
# 给用户 User1 授予“删除 + 更改权限”
icacls test1 /grant User1:(d,wdac)

# 用数字 SID 时前面要加星号（*）—— S-1-1-0 是 Everyone
icacls test1 /grant *S-1-1-0:(d,wdac)

# 权限改坏了：/reset 替换为所有匹配文件的“默认继承 ACL”
icacls C:\Users\Public\demo.txt /reset

# 批量备份 / 还原 ACL（/t 递归）
icacls c:\windows\* /save aclfile /t
icacls c:\windows\ /restore aclfile
```

（继承行为还可以用 `/inheritancelevel:e|d|r` 控制：`e` 启用、`d` 禁用、`r` 移除继承的权限 [A4]。）

### 1.8 列目录与看隐藏内容：`dir` 的三个开关与星号坑

#### 1.8.1 三个开关

`dir` 的默认行为是**不显示隐藏文件和系统文件**。官方的说明是：加 `/a` 但不指定具体属性时，才会"显示所有文件的名称，包括隐藏文件和系统文件" [A12]。另外两个开关：`/r` 可以"显示文件的备用数据流"，`/x` 显示 8.3 短名 [A12]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：无需管理员

```cmd
# 默认：隐藏 / 系统文件不出现
dir C:\Users\Public

# /a 不带属性值 = 显示全部（含隐藏、系统文件）
dir /a C:\Users\Public

# /r = 显示备用数据流（1.5 节讲的 ADS）
dir /r C:\Users\Public

# /x = 显示 8.3 短名
dir /x C:\Users\Public
```

#### 1.8.2 星号通配符的坑：它走的是短名映射

官方 Remarks 里写着：星号"始终使用短文件名映射" [A12]。后果是：`dir t97\*` 会**同时返回** `t97.txt` 和 `t.txt2`（后者的短名是 `T97B4~1.TXT`）；而 `del t97\*` 会**把两个文件都删掉** [A12]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：无需管理员

```cmd
# 危险演示：星号会走“短名映射”，匹配范围比你想的宽
dir t97\*     # 同时列出 t97.txt 和 t.txt2
del t97\*     # 会把两个文件都删掉
```

> [!warning] 星号通配符 + 短名映射 = 误删风险
> 你以为 `t97\*` 只匹配"以 t97 开头的文件"，实际它会**通过短名匹配到更多文件** [A12]。搭配 `del` 使用时尤其危险。**批量删除前，先用 `dir` 看一遍匹配结果**，这是最省事的一道保险。

### 1.9 复制与备份：`robocopy` 的默认值有多危险

`robocopy` 的语法是 `robocopy <source> <destination> [<file>] [<options>]`，不指定文件时默认处理 `*.*` [A10]。

#### 1.9.1 `/s` 与 `/e` 的区别

`/s` 复制子目录但"自动排除空目录"，`/e` 则"自动包括空目录" [A10]。想做完整备份，用 `/e`。

#### 1.9.2 `/mir` 是最危险的参数

官方明确：**`/mir` 相当于 `/e` 加 `/purge`**，也就是镜像整个目录树，并**删除目标端源中已不存在的文件和目录** [A10]。

> [!warning] `/mir` 会删除目标端的文件，执行前必须先演练
> 这不是"多复制一份"，而是"让目标端变得和源端一模一样"——**目标端多出来的东西会被删掉** [A10]。执行前先加 `/L` 演练（只列出计划、不实际复制），确认清单无误再真正执行。

#### 1.9.3 默认重试极其激进

官方的默认值是：`/r` 重试 **1,000,000** 次、`/w` 等待 **30** 秒 [A10]。这两个默认值意味着：**网络路径失效时，robocopy 会长时间假死**。官方自己的示例普遍写成 `/R:2 /W:5` [A10]——跟着官方示例加这两个参数，是性价比最高的一条习惯。

> [!warning] 默认 `/r:1000000 /w:30` 会让失效的网络路径长时间假死
> 目标不存在或网络断了时，robocopy 会按默认值反复重试，看起来就像"卡死了" [A10]。**每次都用 `/R:2 /W:5`（或类似的小值）**，能让你在几秒内拿到明确结果，而不是干等。

#### 1.9.4 退出码语义反直觉

`0` 表示"未复制任何文件"（没有失败），`1` 表示"已成功复制所有文件"，而"任何等于或大于 **8** 的值都表示在复制作期间至少发生一次故障" [A10]。

> [!tip] 大白话
> 记住一句话就够：**0 和 1 都算正常，≥8 才是出错。** 别看到 `0` 就以为"出大事了"——它只是说"源和目标完全一样，没什么可复制的" [A10]。

#### 1.9.5 `/copy` 与日志

`/copy` 的默认值是 `DAT`（数据、属性、时间戳）；`/sec` 相当于 `/copy:DATS`；`/copyall` 相当于 `/copy:DATSOU` [A10]。官方"强烈建议"每次运行都加上 `/log:` [A10]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：**官方未说明**

```cmd
# 安全复制：/E 含空目录、/ZB 失败时改用备份模式重试、必带日志
robocopy C:\Users\Admin\Records D:\Backup /E /ZB /LOG:C:\Logs\Backup.log

# 镜像（= /E + /PURGE）：会删除目标端多余文件，破坏性最强
robocopy C:\Users\Admin\Records D:\Backup /MIR /R:2 /W:5 /LOG:C:\Logs\Backup.log

# 多线程复制（/MT:16），适合大量小文件
robocopy C:\Users\Admin\Records D:\Backup /S /E /COPY:DAT /MT:16 /LOG:C:\Logs\Backup.log
```

#### 1.9.6 两个隐藏行为

- **默认会跟随交接点**。官方注明 robocopy 默认包含交接点，要主动用 `/xj`（全部排除）、`/xjd`（排除目录交接点）、`/xjf`（排除文件符号链接）来排除 [A10]。
- **从设备根目录复制时，目标目录会获得"隐藏"和"系统"属性** [A10]。这是官方 Important 级提示，很多人复制完发现目标目录"不见了"，就是这条造成的。

另外：`/sparse` 控制是否保留稀疏状态，不选时默认为 **yes**；`/mt:<n>` 的 `n` 必须为 1–128（默认 8），且"不能与 `/ipg` 和 `/efsraw` 参数一起使用" [A10]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```cmd
# 演练优先：/L 只列出要做什么，不真的复制
robocopy C:\Users\Admin\Records D:\Backup /MIR /L /LOG:C:\Logs\Plan.log

# 限速 1 MB/s、显示预计完成时间
robocopy C:\Users\Admin\Records D:\Backup /E /iorate:1m /ETA

# 排除交接点（robocopy 默认会跟随它）
robocopy C:\Users\Admin\Records D:\Backup /E /xj
```

### 本章小结

> [!summary] 小结
> - 文件系统分三层：**卷**是"目录和文件的集合"，**目录**是"分层集合"，**文件**是"相关数据的逻辑分组"；**目录本身也是一种"特殊属性的文件"**，所以目录名同样受文件名规则约束 [A1][A2]
> - **命名第一坑**：`C:tmp.txt` 指"C 盘当前目录"，**不等于** `C:\tmp.txt`；保留字符是 `< > : " / \ | ? *` 加 NUL；`NUL.txt` 等同于 `NUL`；8.3 短名**不保证存在** [A2]
> - **路径长度**：传统上限 MAX_PATH = 260；`\\?\` 前缀可用约 32767 字符，但不能用 `/`、`.`、`..`；长路径开关需要"注册表值 + 应用自己声明"两者齐备 [A3]
> - **系统目录**：`%USERPROFILE%\AppData` 分 `Roaming` / `Local` / `LocalLow` 三个（每个用户各一份）；`ProgramData` 和 `Users\Public` 全机器共用；`Program Files (x86)` **只存在于 64 位系统** [A6][A7]
> - **NTFS 四特色**：流（`dir /r` 看）、压缩（`compact`）、加密（`cipher`，加密文件时**要一起加密父目录**；**无法加密已压缩文件**）、稀疏文件（`fsutil sparse setflag`）[A8][A13][A16][A21]
> - **链接三兄弟**：硬链接（不能指目录、不能跨卷）、符号链接（`/d` 可指目录）、交接点（`/j`，官方叫"**目录联接**"）；**删链接 ≠ 删原文件** [A19][A5]
> - **元数据**：`attrib` 看/改属性（`s`/`h` 的操作顺序说法**仅一条来源、未实测**）；`icacls` 看/改/重置权限，`/reset` 是权限改坏后的兜底 [A9][A4]
> - **复制备份**：`robocopy` 的 `/mir` **会删除目标端文件**；默认 `/r:1000000 /w:30` 会让失效网络路径长时间假死；退出码 **0 和 1 都正常，≥8 才是出错** [A10]
> - **官方未说明的位置**（本章一律不推断）：`mklink /d` 的提权要求、`compact` / `cipher` / `mountvol` / `robocopy` 的管理员要求、`AppData\LocalLow` 的用途 [A5][A10][A11][A13][A16][A6]

## 第二章 Windows 注册表——系统和程序的配置中心

导读里我们把注册表比作整台电脑的"后台登记本"。这一章把本子摊开：它长什么样（树 / 键 / 子项 / 值）、顶层五个"总目录"各管什么、它存放在硬盘上的哪个文件里、值有哪几种类型、64 位系统上为什么会有"两套"注册表。

排版顺序是刻意的：**先把备份和回滚讲透（2.7），再讲怎么查、怎么改、怎么删（2.8、2.9）**。官方的警告不是客套话——错误地修改注册表，"可能需要重新安装操作系统才能解决" [S6]。请务必按顺序读。写法沿用第一章：先中文人话讲直觉，再给官方术语，最后说清"它到底指什么"。

### 2.1 注册表是什么：树、键、子项、值

#### 2.1.1 四个基本词：树、键、子项、值

官方的定义是：注册表是一个**分层数据库**，数据以**树**的格式组织；树中每一个节点称为**键**，每个键可以**同时**包含**子项**和称为**值**的数据条目，而且一个键可以有任意数量的值 [S1]。

把这句话拆成四个词：

| 词 | 官方术语 | 它到底指什么 |
|---|---|---|
| 树 | 分层数据库 | 整个注册表是一棵倒过来的树，从顶层往下不断分叉 |
| 键 | key | 树上的一个节点，作用相当于"文件夹" |
| 子项 | subkey | 键下面再分出来的键，相当于"子文件夹" |
| 值 | value | 挂在键上的"数据条目"，相当于贴在文件夹上的标签 |

> [!note] 键能装东西，也能被装东西
> 这是注册表最容易记混的一点：**一个键既是"文件夹"，又挂着"标签"**。你在 regedit 里点开一个键，看到的往往是"左边一串子文件夹 + 右边一串标签"，两者并列，不是二选一 [S1]。

> [!tip] 大白话
> 把注册表想成一栋**倒着长的文件柜**：顶层是五个大抽屉，抽屉里是文件夹，文件夹里还有文件夹；每个文件夹的封面上都贴满写着一行小字的便利贴。**文件夹**就是"键"和"子项"，**便利贴**就是"值"。系统开机做的事，就是按索引翻到某几个文件夹，看一眼上面写了什么。

#### 2.1.2 命名规则：谁不能带反斜杠

键名的规则比"值"严格，官方给了四条 [S1]：

- 键名**不区分大小写**（`Software` 和 `software` 是同一个键）；
- 键名**不能包含反斜杠 `\`**；
- 而**值的名称和数据可以**包含反斜杠；
- 键名**不做本地化**，值**可以被本地化**。

后两条需要解释一下。"本地化"就是"翻译成当地语言"：**键名不做翻译**，所以不管你用中文版还是英文版 Windows，键路径都是 `Software\Microsoft\Windows\CurrentVersion` 这种固定英文形式，网上找到的路径可以直接照抄；而**值可以被翻译**，同一个键下不同语言系统可以放不同语言内容的值。

反斜杠在键名里的角色和第一章的文件路径一样，**是分隔符，不是名字的一部分**：`Software\Microsoft\MyApp` 里的两个 `\` 划出三层，正因如此键名里不能再出现它；但值是"贴上去的标签"，不受这个限制。

#### 2.1.3 树的深度：512 层与 32 层

两个关于深度的数字 [S1]：

- 注册表树**最深可达 512 层**；
- 通过**单次注册表 API 调用**，一次最多创建 **32 层**。

对零基础读者，这两个数字只需一个直觉：**注册表可以很深，但日常几乎碰不到极限**。真正要记住的是"它是分层结构"——找一个键就像沿路径一层层往下点，少一节都到不了。

#### 2.1.4 五个顶层"总目录"的意义

应用程序必须先**打开一个键**，才能往注册表里添加数据。系统为此定义了一批**始终打开**的键作为入口，称为**预定义键**；官方的要求是：添加数据的应用**应始终在预定义键的框架内工作**，这样管理工具才能找到并使用新数据。预定义项的名称最大长度为 **255 个字符** [S4][S6]。

> [!tip] 大白话
> 把预定义键想成图书馆里划好的**五大分类区**。官方要求程序"必须把书写进分类区里"，不是它管得宽，而是——如果每本书都随手塞进自己的抽屉，图书管理员就再也找不到任何东西了。注册表也一样：regedit 和各类管理工具，只认这五个入口往里查。

> [!note] 给开发者的补充（可跳过）
> 官方在讲这一节时会用"预定义项""句柄"`RegOpenKeyEx` 这类说法 [S1][S4]。这些是写给写程序的人看的。对你来说只需要记住：**注册表有 5 个顶层文件夹**，往下全是分叉。

### 2.2 五个根键各管什么

顶层那 5 个文件夹（**根键**）全名都很长，平时一律用缩写。先看总览，再逐个说：

| 缩写 | 全名 | 管什么 |
|---|---|---|
| HKLM | HKEY_LOCAL_MACHINE | 整台计算机 |
| HKCU | HKEY_CURRENT_USER | 当前登录的这个用户 |
| HKCR | HKEY_CLASSES_ROOT | 文件类型与右键菜单（合并视图） |
| HKU | HKEY_USERS | 所有用户的配置文件 |
| HKCC | HKEY_CURRENT_CONFIG | 当前硬件配置（只是一个别名） |

#### 2.2.1 HKLM：这台机器的"物理状态"

`HKEY_LOCAL_MACHINE`（HKLM）保存计算机**物理状态**的数据：总线类型、系统内存、已安装的软硬件，以及即插即用信息。官方特别指出，其中的 `Enum` 分支记录了"系统上出现过的全部硬件" [S4]。

翻译成人话：**只要是"这台机器本身"的属性，都在 HKLM**——换个人登录，看到的东西基本一样。

#### 2.2.2 HKCU：当前这个用户的偏好

`HKEY_CURRENT_USER`（HKCU）保存**当前用户**的偏好：环境变量设置、程序组、颜色、打印机、网络连接和应用偏好 [S4]。

它的机制值得单说一句，因为这是 HKU 与 HKCU 关系的关键：**HKCU 映射到 `HKEY_USERS` 中当前用户的那一个分支**，而且这个映射是**按进程**建立的，依据是"第一个引用它的线程的安全上下文"；如果那套安全上下文在 `HKEY_USERS` 下**没有已加载的 hive**，就映射到 `HKEY_USERS\.Default` [S4]。

> [!tip] 大白话
> 把 `HKU` 想成一栋**员工宿舍楼**，每个住户（每个用户）一间房，房里放着这个人的个人设置。`HKCU` 不是第 6 栋楼，而是**前台发给你的门牌**：你今天以谁的身份登录，牌子就指向谁的房间；每个程序各自领一块牌子，所以不同程序看到的 `HKCU` 内容可能不同——这就叫"按进程建立"。`HKU\.Default` 则是"没人认领时的默认房间" [S4]。

#### 2.2.3 HKCR：不是真实位置，是一张"合并视图"

`HKEY_CLASSES_ROOT`（HKCR）最反直觉：**它不是一个真实存储位置**，而是两个真实位置的**合并视图**——`HKLM\Software\Classes`（本机所有用户的默认设置）和 `HKCU\Software\Classes`（仅当前交互用户的覆盖设置）。你往 HKCR 里写东西，系统会把它**重定向**到这两个位置之一 [S6]。

所以 HKCR 更像"投影"，不像"房间"：你在上面看到的内容，实际来自另外两个地方。

> [!warning] 不要直接往 HKCR 里写
> 官方明确要求：**要更改"当前交互用户的设置"，必须在 `HKEY_CURRENT_USER\Software\Classes` 下修改；要更改"默认设置"，必须在 `HKEY_LOCAL_MACHINE\Software\Classes` 下修改**，而不是在 `HKEY_CLASSES_ROOT` 下修改 [S6]。这条规则在第 2.9 节会有一个很实际的好处：写在 HKCU 那边的自定义右键菜单项，**不需要提升权限** [S25]。

#### 2.2.4 HKCC 只是别名，性能数据根本不在注册表里

`HKEY_CURRENT_CONFIG`（HKCC）只是 `HKLM\System\CurrentControlSet\Hardware Profiles\Current` 的**别名**，描述当前硬件配置与标准配置之间的差异 [S4]。换句话说，你在 HKCC 里看到的东西，本体在 `HKLM\System\CurrentControlSet\Hardware Profiles\Current`——它没有自己的存储空间。

另一件事：`HKEY_PERFORMANCE_DATA` 这个根键里的数据**并不真的存在注册表里**，而是由注册表函数**触发系统从数据源实时收集**[S4]。它和别的根键性质完全不同，本章不展开，遇到时知道"它不是存储位置"就够了。

### 2.3 Hive：注册表在磁盘上的真实文件

导读里说过一句关键的话：注册表也长在硬盘上。这一节把它落实——注册表**不是内存里的抽象设置**，它有实实在在的磁盘文件。

#### 2.3.1 "配置单元"和它的支持文件

官方的定义是：**配置单元（hive）**是注册表中键、子项和值的**逻辑组**，它带有一组"在操作系统启动时或用户登录时加载到内存中的支持文件" [S2]。

这句话有点绕，拆成三点：

- "配置单元"就是注册表的**数据库文件**（官方术语叫 hive，中文译作"配置单元"）；
- 它**在磁盘上真实存在**，是一组文件，不是虚构概念；
- 加载时机很明确：**开机时**（系统级）或**用户登录时**（用户级）被读进内存——这也解释了为什么注册表"平时看不到文件、却感觉一直在"。

后文为了好读，一律用"**注册表文件**"或直接给文件名。

#### 2.3.2 每次新用户登录，就多一个用户配置文件配置单元

官方说明：**每次新用户登录**，系统都会为该用户创建一个新的配置单元，称为**用户配置文件配置单元**，位于 `HKEY_USERS` 键下，内容包括该用户的应用程序设置、桌面、环境、网络连接和打印机 [S2]。

这就解释了 2.2.2 里 HKCU 为什么能"跟人走"：每个用户各有一个自己的配置单元，挂在 `HKEY_USERS` 下面 [S2]。

#### 2.3.3 支持文件对照表

注册表的**大部分**支持文件位于 `%SystemRoot%\System32\Config` 目录中（每次用户登录时更新）。官方的对照关系如下 [S2]：

| 注册表配置单元 | 磁盘上的支持文件 |
|---|---|
| HKEY_CURRENT_CONFIG | System、System.alt、System.log、System.sav |
| HKEY_CURRENT_USER | Ntuser.dat、Ntuser.dat.log |
| HKEY_LOCAL_MACHINE\SAM | Sam、Sam.log、Sam.sav |
| HKEY_LOCAL_MACHINE\Security | Security、Security.log、Security.sav |
| HKEY_LOCAL_MACHINE\Software | Software、Software.log、Software.sav |
| HKEY_LOCAL_MACHINE\System | System、System.alt、System.log、System.sav |
| HKEY_USERS\.DEFAULT | Default、Default.log、Default.sav |

注意表里的两种情况：**大部分**机器级 hive 的支持文件在 `%SystemRoot%\System32\Config` 里；而**用户级**那一个（HKEY_CURRENT_USER）对应的文件是 `Ntuser.dat` 及其日志 [S2]。

#### 2.3.4 用户级 hive 的磁盘承载文件

用户级 hive 的磁盘承载文件是 **`NTUSER.DAT`**（以及它的日志 `NTUSER.DAT.LOG`）；它属于**用户配置文件** hive，随用户登录被加载 [S2][S6]。

> [!warning] 用户级 hive 的磁盘位置，两份官方文档说法不一致
> 一处官方资料（Win32「注册表 Hives」）说"Hives 的**大部分**支持文件位于 `%SystemRoot%\System32\Config`"，但没有为 `Ntuser.dat` 指明目录 [S2]；另一处（KB256986）则写"HKEY_CURRENT_USER 的支持文件位于 `%SystemRoot%\Profiles\Username` 文件夹中" [S6]。
>
> 这两处说法**并不一致**，而且**都没有给出符合现代 Windows 布局的用户级 hive 磁盘路径**。因此本章的处理口径是：**只说 `NTUSER.DAT` / `NTUSER.DAT.LOG` 属于"用户配置文件 hive"，磁盘位置用"用户配置文件目录"来表述，不写死任何路径**。需要提醒的是，部分官方资料仍沿用旧版布局（`%SystemRoot%\Profiles\...`）描述，内容是经典 KB，个别路径描述偏旧 [S2][S6]。

#### 2.3.5 扩展名含义：这些是系统自己用的，不要动

同一批文件有几种扩展名，含义不一样 [S2]：

- **无扩展名**（如 `Software`）= 配置单元数据的**完整副本**；
- **`.alt`** = 备份副本，**只有 `HKLM\System` 才有**（官方原话是"只有系统密钥具有 .alt 文件"）；
- **`.log`** = 键和值更改的**事务日志**；
- **`.sav`** = 配置单元的**备份副本**。

> [!warning] 这些文件是系统自己用的，不要删也不要改
> `.log` / `.alt` / `.sav` 不是给你清理的"垃圾文件"，而是系统用来保证注册表完整性的日志和副本 [S2]。讲它们的目的只有一个：**它们出现在你眼前时，你知道"不要动它们"。**

#### 2.3.6 格式演进：两种格式，四个 hive 例外

注册表文件只有**标准格式**和**最新格式**两种。Windows 2000 只支持标准格式；**从 Windows XP 起**支持最新格式 [S2]。

但即使在支持最新格式的系统上，仍有四个 hive **继续使用标准格式**：`HKEY_CURRENT_USER`、`HKLM\SAM`、`HKLM\Security`、`HKEY_USERS\.DEFAULT`；其余 hive 使用最新格式 [S2]。

这条对你没有操作上的影响，但能解释一件怪事：为什么有些老式的注册表工具在部分键上行为不一样。

#### 2.3.7 临时挂载：把一块注册表当文件加载进来

应用程序可以把注册表的一部分保存成文件再加载回来，适用于"数据量大、条目过多或数据是临时的"场景；`RegLoadKey` 把文件数据加载到 `HKEY_USERS` 或 `HKEY_LOCAL_MACHINE` 下的指定子项，之后可以用 `RegUnLoadKey` 还原到以前的状态 [S3]。

命令行工具里对应的是 `reg load` 和 `reg unload`，本意是"临时挂载做排查"，具体命令见 2.7.4。

### 2.4 值类型：一套类型的三副面孔

同一个东西，官方文档里叫 `REG_SZ`，注册表编辑器里显示"字符串值"，PowerShell 里写 `-Type String`——**这是同一套类型的三副面孔**。这一节把三副面孔对上号。

#### 2.4.1 常用类型

注册表值可以存储多种格式的数据，这些类型定义在 `winnt.h` 头文件中 [S5]：

- **`REG_SZ`**：以 null 结尾的字符串；
- **`REG_BINARY`**：任何形式的二进制数据；
- **`REG_DWORD`**：**32 位数字**；
- **`REG_QWORD`**：**64 位数字**；
- **`REG_NONE`**：没有定义的值类型。

先给读者一个心智锚点：**`REG_SZ` 是"文字"，`REG_DWORD` 是"32 位的数字"，`REG_QWORD` 是"64 位的数字"**，这三条覆盖了日常绝大多数情况。

> [!note] 关于"小端"，一句话就够
> 官方还定义了 `REG_DWORD_LITTLE_ENDIAN` 和 `REG_DWORD_BIG_ENDIAN`。前者的定义是：在 Windows 头文件里，它**就等同于 `REG_DWORD`**（因为 Windows 被设计为运行在小端架构上）；后者是供某些 UNIX 大端系统使用的 [S5]。所以你**不需要理解"字节序"**，在 Windows 上看到 `REG_DWORD_LITTLE_ENDIAN` 就当作 `REG_DWORD` 处理即可。

#### 2.4.2 REG_EXPAND_SZ：带着 `%变量%` 的字符串

`REG_EXPAND_SZ` 是"**包含对环境变量的未扩展引用**"的字符串，例如 `%PATH%` 或 `%systemroot%`；要用的时候，得调用 `ExpandEnvironmentStrings` 把它展开 [S5]。

"未扩展"的意思是：**值里存的是 `%systemroot%` 这串字符本身，不是展开后的 `C:\Windows`**；只有用到它并且显式要求展开时，系统才会替换成真实路径。这就是同一个值在不同机器上能给出不同结果的原因。

#### 2.4.3 REG_MULTI_SZ：一个值装多行

`REG_MULTI_SZ` 是**以长度为 0 的字符串结尾的字符串序列**，官方示例长这样：`String1\0String2\0String3\0LastString\0\0` [S5]。

这里有两条硬规则 [S5]：

- 它需要**两个**终止 null 字符（示例末尾的 `\0\0`）；
- 它**不能包含零长度字符串**（官方定义的"空序列"写成单个 `\0`）。

> [!tip] 大白话
> `\0` 是**字符串末尾的隐藏结束符**，你看不见它。`REG_MULTI_SZ` 就是"一个值里装一个列表"，每项之间用隐藏结束符隔开，列表**结尾要连用两个**表示"到此为止"。既然"空的一项"和"列表结束"用的是同一个符号，这个类型自然就**不能有空行** [S5]。

#### 2.4.4 三列对照表：同一套类型的三副面孔

| 官方类型名（文档 / `reg` 的 `/t`） | regedit 里显示为 | PowerShell 的 `-Type` | 什么时候用它 |
|---|---|---|---|
| `REG_SZ` | 字符串值 | `String` | 普通文字，如程序名、路径（不含 `%变量%`） |
| `REG_EXPAND_SZ` | 可扩充字符串值 | `ExpandString` | 含 `%变量%` 的路径，如 `%SystemRoot%\...` |
| `REG_BINARY` | 二进制值 | `Binary` | 原始字节，如硬件信息、加密数据 |
| `REG_DWORD` | DWORD (32 位) 值 | `DWord` | 开关、状态码、端口号这类整数 |
| `REG_QWORD` | QWORD (64 位) 值 | `QWord` | 超出 32 位范围的大整数 |
| `REG_MULTI_SZ` | 多字符串值 | `MultiString` | 一个值里存一个列表 |

表格的依据：类型定义来自 [S5]，regedit 中的显示形式与 `REG_QWORD` 的呈现方式来自 [S6]，PowerShell 一侧的 `-Type` 取值（含"`String` 是默认值"）来自 [S21][S22]。

> [!example] 把三副面孔对上号
> 假设要在自建键 `HKCU\Software\Demo` 下写一个 32 位数字 `1`，三条路写出来的是**同一个类型的同一个值**，只是入口不同：
>
> - **regedit 里**：新建 →「DWORD (32 位) 值」，值填 `1`；
> - **`reg` 命令行**：`reg add "HKCU\Software\Demo" /v Flag /t REG_DWORD /d 1 /f`；
> - **PowerShell**：`Set-ItemProperty -Path "HKCU:\Software\Demo" -Name Flag -Value 1 -Type DWord`。
>
> 记住这张对照，你在任何一份教程里看到 `REG_DWORD`、"DWORD 值"、`-Type DWord` 这三种写法，就知道说的是同一件事。

#### 2.4.5 字符串终止符：读写注册表最常见的陷阱

官方明确指出，**字符串的终止符是读写注册表最常见的陷阱** [S5]：

- **写入时**，必须把终止 null 计入长度——官方给的做法是用 `strlen(string) + 1`，而不是 `strlen`；
- **读取时**，字符串**可能未正确终止**，你必须自行确保终止，否则可能覆盖缓冲区。

对零基础读者，这条的价值不在于让你自己写代码，而在于理解"**为什么有的注册表工具会把字符串写坏**"：多算了留垃圾、少算了溢出，这是一个真实存在的坑 [S5]。

#### 2.4.6 在 regedit 里，同一种类型的显示方式不同

在注册表编辑器里，**DWORD 值可以按二进制、十六进制或十进制三种格式显示**——看到 `0x1` 和看到 `1` 可能是同一个值。另一条：`REG_QWORD`（Windows 2000 引入）在注册表编辑器中**以"二进制值"的形式显示** [S6]——明明是个 64 位数字，却显示得像二进制数据，这不代表类型错了 [S6]。

#### 2.4.7 尺寸限制：为什么会遇到"值写不进去"

有四个数字容易记混，做成一张小表 [S6][S19]：

| 限制 | 数值 | 什么时候会遇到 |
|---|---|---|
| 值名称的最大长度 | 16,383 个字符 | 名字起得极长时 |
| 单个值的数据大小 | 超过 **2,048 字节** 必须改存为文件 | 想把一大段数据塞进一个值时；此时注册表里只存文件名 |
| 一个项的所有值加起来 | **64 K** 上限 | 往同一个键里塞太多值时 |
| `Run` 键里的命令行 | **不超过 260 个字符** | 写开机自启命令时（见 2.9） |

官方解释为什么要限制：超过 2,048 字节的长值"必须存储为文件，只在注册表中存文件名"，这样"有助于注册表高效执行" [S6]。

> [!warning] 遇到"写不进去"时，先想这四条
> 值名称太长、单个值太大（>2048 字节）、一个键里所有值加起来超过 64 K、自启命令行超过 260 字符——**表现可能都是"写不进去"或"被截断"**，但原因完全不同 [S6][S19]。排查时按这张表逐个对，不要靠猜。

### 2.5 64 位系统上的两套注册表：WOW6432Node

#### 2.5.1 默认行为：谁看谁那一套

官方规定：在 WOW64（即 64 位 Windows 运行 32 位程序的环境）上，**32 位应用程序默认访问 32 位注册表视图，64 位应用程序默认访问 64 位注册表视图** [S20]。

用中文说清楚"两套注册表"：

> [!tip] 大白话
> 把注册表想成一个**装了两种高度书架的档案室**：64 位程序习惯用高架子，32 位程序习惯用矮架子。**同一个路径**（比如 `HKLM\Software`），64 位程序看到的是高架子上的东西，32 位程序看到的是矮架子上的东西——**这不是"文件被搬走了"，也不是"有个假的副本"**，而是同一套注册表按"来的人是 32 位还是 64 位"显示不同内容。矮架子那一批，在 64 位程序眼里就挂在 `WOW6432Node` 下面 [S20][S6]。

官方还给了两个可切换视图的标志：`KEY_WOW64_64KEY`（值 `0x0100`）让任一应用访问 64 位键，`KEY_WOW64_32KEY`（值 `0x0200`）让任一应用访问 32 位键；这两个标志**对共享注册表键无效**，而且**同时指定会失败**，返回 `ERROR_INVALID_PARAMETER` [S20]。

#### 2.5.2 WOW6432Node 是保留键，不要直接改

官方明确：`Wow6432Node` 与 `WowAA32Node` 键是**保留的**，"为了兼容性，应用程序**不应直接使用**这些键" [S20]。配套最佳实践是：应用一旦用某个视图标志访问了备用视图，之后对该视图下**所有子键**的创建、删除、打开都必须显式使用**同一个标志**；要准确枚举两个视图中的所有键，必须**分两遍**枚举（各用一个标志） [S20]。

#### 2.5.3 你实际会遇到的只是两个开关

上面那些掩码数字是写给开发者的。**读者实际只会遇到两个开关**：`reg query` / `reg add` / `reg import` 等命令提供的 `/reg:32` 与 `/reg:64`，用来指定操作哪一套视图 [S9][S10][S14]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 同一个路径，分别从 32 位视图和 64 位视图看（只读，安全）
reg query "HKLM\Software\MyApp" /reg:32
reg query "HKLM\Software\MyApp" /reg:64
```

另外，**64 位 Windows 自带的 64 位注册表编辑器，会在 `HKEY_LOCAL_MACHINE\Software\WOW6432Node` 节点下显示 32 位项** [S6]。这就是"明明数据在，却找不到"的常见原因。

> [!warning] 找不到键时的第一步：怀疑视图
> 在 64 位系统上找一个键却怎么都找不到，**先怀疑"是不是看错了视图"**，再怀疑别的 [S20][S6]。同时记住：**不要直接去改 `WOW6432Node`**——它是保留键 [S20]。

### 2.6 权限与所有者

#### 2.6.1 每个键都带一张权限清单，默认从父键继承

Windows 的安全模型允许你控制对注册表项的访问。调用 `RegCreateKeyEx` 或 `RegSetKeySecurity` 时，可以为键指定**安全描述符**；如果指定为 `NULL`，键会获得**默认安全描述符**——而默认安全描述符中的权限清单，**继承自它的直接父键** [S7]。

翻译成对读者有用的那句：**注册表键也有权限**；你没特意设过权限的键，它用的就是"爸爸键"的权限清单 [S7]。

#### 2.6.2 想干不同的事，需要不同的权限

注册表项支持的访问权限里，有几条与日常操作直接对应 [S7]：

| 你想做的事 | 需要的权限 |
|---|---|
| 查询值 | `KEY_QUERY_VALUE` |
| 创建、删除或设置值 | `KEY_SET_VALUE` |
| 创建子项 | `KEY_CREATE_SUB_KEY` |
| 枚举子项 | `KEY_ENUMERATE_SUB_KEYS` |
| 请求更改通知 | `KEY_NOTIFY` |

两条边界：注册表键**不支持 `SYNCHRONIZE`**；`KEY_CREATE_LINK`（值 `0x0020`）**保留供系统使用**。另外，打开键时系统会按安全描述符检查你请求的权限，**权限不足则打开失败** [S7]。

#### 2.6.3 权限不足时，官方给出的唯一解法

官方的原话是：如果管理员需要访问某个键，解决方案是**启用 `SE_TAKE_OWNERSHIP_NAME` 特权，并以 `WRITE_OWNER` 访问权限打开该键** [S7]。

零基础读者请这样记：**"取得所有权"**是那个特权要做的事，"以**所有者身份写入**的权限打开"是那个访问权限要做的事。落到能操作的动作上就是：**在权限对话框里把所有者改成自己，再给自己赋"完全控制"** [S7]。

#### 2.6.4 两个核对权限的入口

1. **注册表编辑器**：定位到目标键 →「编辑」菜单 →「权限」 [S7]。
2. **PowerShell**：`Get-Acl` 读取、`Set-Acl` 写入（官方示例用 `RegistryAccessRule` 给指定用户加 `FullControl`） [S7][S21]。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 只读：查看某个键的权限清单（不会改动任何东西）
Get-Acl -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion"
```

> [!tip] 改之前先看一眼权限，比出事之后再救便宜
> 官方的建议顺序是"先看现有权限，再决定要不要动" [S7]。本章 2.7.7 的风险 checklist 里也会再出现这一条。

### 2.7 备份与回滚（本章强制主线）

**这一节必须完整读完，再往下看修改命令。** 官方的警告不是吓唬人，它把"错误修改注册表"的后果写成了"可能需要重新安装操作系统"。

#### 2.7.1 官方的两条警告原文

**Caution 级**（来自 `reg` 命令页）：「除非没有替代项，否则不要直接编辑注册表。注册表编辑器绕过标准安全措施，允许降低性能、损坏系统甚至要求重新安装 Windows 的设置。……**如果必须直接编辑注册表，请先备份它。**」 [S8]

**Warning 级**（来自 KB256986）：错误地修改注册表"**可能需要重新安装操作系统才能解决。Microsoft 不能保证可以解决这些问题**" [S6]。

同时也要记下官方的另一半态度：**编辑注册表有时"可能是解决产品问题的最佳方法"** [S6]。所以本章的口径不是"永远别碰"，而是"**没备份就别碰**"。

> [!warning] 两页警告的语气强度不一样，不要合成一个版本
> `reg` 命令页用 Caution 级，KB256986 用 Warning 级并明确承认"有时必须改" [S8][S6]。两段都是官方原文，**强度不同是事实本身**，不要改写成更强或更弱的版本。

#### 2.7.2 官方推荐的修改顺序

官方的建议是：**使用 Windows 用户界面更改系统设置，而不是手动编辑注册表**；如果 Microsoft 知识库针对你的问题给出了分步说明文章，则「建议完全按照这些说明操作」 [S6]。

翻译一下这条顺序：**能用设置界面（控制面板 / 设置 / 组策略 / MMC）改的，就别动注册表。** 只有当设置界面里根本没有这个选项时，才轮到手动编辑 [S6]。

#### 2.7.3 主路径：导出 `.reg` → 需要时导入还原

这是官方覆盖范围最广的一条路（该页面适用于 Windows 11 / Windows 10 / Windows 8.1）[S18]。

**方式一 · regedit 界面**（官方给出步骤最完整的一条）[S18]：

1. 「开始」→ 搜索 `regedit.exe` → 回车。**若有管理员密码或确认提示，需提供**（官方原文即含此提示）；
2. 在注册表编辑器中找到并单击要备份的项或子项；
3. 「文件」>「导出」；
4. 在"导出注册表文件"对话框中，选择保存位置并输入备份文件名；
5. 「保存」。

还原时：「文件」>「导入」→ 选择备份文件 →「打开」 [S18]。

> 环境：regedit（注册表编辑器界面）｜ 版本：全版本适用 ｜ 权限：官方明写会有管理员密码或确认提示，即导出与导入都按提权处理 [S18]

**方式二 · 命令行 `reg.exe`** [S13][S14]：

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 备份：把某个键（含其下所有子项和值）导出为 .reg 文件
reg export "HKLM\SOFTWARE\MyApp" AppBkUp.reg /y

:: 还原：把这个 .reg 文件导入回注册表
reg import AppBkUp.reg
```

几条必须知道的边界 [S13][S14]：

- `reg export` 的文件名**必须带 `.reg` 扩展名**；`/y` 表示覆盖同名文件时不提示；**仅适用于本地计算机**；键名含空格必须加引号；
- `reg import` 的文件**必须由 `reg export` 提前创建**，同样仅适用于本地计算机；
- 返回值 **0 = 成功 / 1 = 失败**，可以用于脚本判断。

> [!warning] `reg export / import` 是否需要管理员，官方未说明
> 上面那张表里，只有 **regedit 界面**的导出/导入有官方明确的"会有管理员密码或确认提示" [S18]。而 **`reg export` / `reg import` 是否需要管理员权限，官方页面全未明示**——本章**不做推断**，一律标注"官方未说明" [S13][S14]。这一条对 `reg save` / `reg restore` / `reg load` / `reg unload` 同样成立（见 2.7.4）。

#### 2.7.4 进阶路径：整键快照 → 写回（`.hiv`）

除了导出文本格式的 `.reg`，还有一条更"原始"的路径：把整个键原样快照成一个二进制文件（`.hiv`），需要时写回。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 编辑前先做整键快照（官方指定的"编辑前必做"动作）
reg save "HKLM\Software\MyApp" AppBkUp.hiv /y

:: 编辑失败时写回原始子项（会覆盖该键的现有内容）
reg restore "HKLM\Software\MyApp" AppBkUp.hiv

:: 只做临时加载排查，用完必须卸载
reg load   HKLM\TempHive TempHive.hiv
reg unload HKLM\TempHive
```

官方在 `reg save` 的备注里直接把"备份"写成了必做动作：

> 「在编辑任何注册表项之前，**必须**使用 `reg save` 命令保存父项和子项。如果编辑失败，则可以使用 `reg restore` 还原原始子项。」 [S15][S16]

几条边界 [S15][S16][S17][S8]：

- `reg restore` 会**覆盖**目标键的现有内容；
- `reg restore` 用的文件**必须由 `reg save` 创建**，且**必须是 `.hiv` 扩展名**；
- `reg load` 的定位是"**故障排除或编辑注册表项的临时文件**"式操作；`reg unload` 的定义就是"删除使用 `reg load` 加载的注册表部分"——所以 **load 之后必须 unload**，否则那块内容会一直挂在 `HKLM` 下。

#### 2.7.5 整机级兜底：备份"系统状态"

如果要备份的是**整个注册表**，官方给的办法不是"导出某个键"，而是用**备份工具备份"系统状态"**——官方说明"系统状态包括注册表、COM+ 类注册数据库和启动文件"；还原时走"**从备份还原系统状态**"。备份系统状态还会在 `%SystemRoot%\Repair` 文件夹中生成注册表文件的更新副本 [S6]。

> [!warning] "备份整个注册表"这句话，含义并不统一
> 一份官方资料把"备份整个注册表"指向**备份系统状态**（整机快照）[S6]；另一份面向普通用户的资料（覆盖 Win11）则只教 **regedit 的「导出 / 导入」**，而那是**按键导出** [S18]。两者不冲突，但覆盖面完全不同。
>
> 所以务必分清：**按键级备份** = 导出 `.reg`（只保住了你导出的那一个键）；**整机级备份** = 备份系统状态（保住整台机器）。**把"导出 `HKLM\Software` 下的某一个键"当成"备份了整个注册表"，是一个非常常见也非常危险的误解** [S6][S18]。

#### 2.7.6 系统还原：只作附注，不是回滚主路径

还有一条整机级的回滚路径是**系统还原**（还原点）。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方明确要求"以管理员身份运行" [S26]

```powershell
# 在 C: 上启用系统还原功能
Enable-ComputerRestore -Drive "C:\"
```

官方的几条限制 [S26]：

- 在 Windows Vista 及更高版本上，**必须用"以管理员身份运行"打开 Windows PowerShell** 才能运行该 cmdlet；
- **要在任何驱动器上启用系统还原，必须先在系统驱动器上同时启用**；
- **不能用于外部驱动器或远程网络驱动器**；
- 可以用 `Rstrui.exe` 查看每个驱动器的还原状态。

> [!warning] 不要把系统还原写成注册表回滚的"主路径"
> 官方关于系统还原的那一页，正文称"系统还原点和 ComputerRestore cmdlet **仅在 Windows 7、Windows Vista 和 Windows XP 等客户端操作系统上受支持**"，但同一页的"适用于"和该 cmdlet 在 Windows 10 / 11 的 PowerShell 5.1 里仍然存在——**文档的版本声明明显滞后** [S26]。与此同时，另一份覆盖 Windows 11 的官方页面（2.7.3 的主路径来源）**通篇没有提到系统还原**，只给 regedit 导出 / 导入两条路径 [S18]。
>
> 因此本章口径是：**回滚主路径 = 导出 `.reg` → 需要时导入还原**；系统还原**只作整机级兜底的一条附注**，并注明官方版本声明存疑 [S18][S26]。

#### 2.7.7 编辑前的官方风险 checklist

以下是官方在"修改注册表之前"要求你确认的事项，原样落地 [S8][S6][S7]：

> [!warning] 除非没有替代项，否则不要直接编辑注册表
> （Caution 级，官方原文）注册表编辑器"绕过标准安全措施，允许降低性能、损坏系统甚至要求重新安装 Windows 的设置"。**能用控制面板的程序或 MMC 安全地改的设置，就不要手动改注册表** [S8]。

> [!warning] 改错了，Microsoft 不能保证能修好
> （Warning 级，官方原文）"如果使用注册表编辑器或使用其他方法错误地修改了注册表，则可能会发生严重问题。这些问题可能需要重新安装操作系统才能解决。Microsoft 不能保证可以解决这些问题。" [S6]

> [!warning] 遇到权限不足的键：先取得所有权
> 官方给出的唯一解法是：启用 `SE_TAKE_OWNERSHIP_NAME` 特权，并以 `WRITE_OWNER` 权限打开该键 [S7]，即"把所有者改成自己，再赋完全控制"（见 2.6.3）。

> [!tip] 改之前的两件事
> 一是**备份并分清级别**：主路径导出 `.reg`（按键级）、进阶 `reg save` 出 `.hiv`（整键快照）、整机级是备份系统状态 [S18][S15][S6]；二是**先核对现有权限**：注册表编辑器 → 定位到键 →「编辑」>「权限」 [S7]。

### 2.8 查询、修改、删除：reg.exe 与 PowerShell 对照

前面把"为什么"和"怎么保命"讲完了，这一节才是命令清单。**所有修改类命令请在自建的键上练习**，不要拿系统关键键做实验。

下列 `reg` 命令块的权限标注统一为"官方未说明"（依据见 2.7.3 的 [!warning]）。顺带说明一条常被问到的：**修改 `HKEY_LOCAL_MACHINE` 下的键是否必须管理员权限，官方文档同样没有明示**，本章不推断——你在实际操作中如果被拒绝访问，请按 2.6.3 的"取得所有权"思路处理 [S7]。

#### 2.8.1 `reg query`：先看清楚，再动手

这是本章你**最应该熟练**的一条命令——它只读，不改任何东西。完整语法如下 [S9]：

```bat
reg query <keyname> [{/v <valuename> | /ve}] [/s] [/se <separator>] [/f <data>]
          [{/k | /d}] [/c] [/e] [/t <Type>] [/z]
```

各参数的含义 [S9]：

| 参数 | 作用 |
|---|---|
| `/s` | 递归查询所有子项和值 |
| `/f <data>` | 指定要搜索的数据或模式 |
| `/k` | 仅搜索**键名**——**必须与 `/f` 同时使用** |
| `/d` | 仅搜索**数据** |
| `/c` | 区分大小写 |
| `/e` | 仅返回**完全匹配**的结果 |
| `/t <Type>` | 限定类型，可选 `REG_SZ`、`REG_MULTI_SZ`、`REG_EXPAND_SZ`、`REG_DWORD`、`REG_BINARY`、`REG_NONE` |
| `/z` | 附带显示该类型的等效数字 |

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 查一个具体的值
reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion" /v ProgramFilesDir

:: 递归搜索：/k 表示只搜键名，必须与 /f 一起用
reg query "HKLM\SOFTWARE\Microsoft" /s /f asp.net /k

:: /ve 表示查询"没有值名称"的那个默认条目
reg query "HKLM\SOFTWARE" /ve
```

#### 2.8.2 `reg add`：新增值（但不能凭空造一棵子树）

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 新增一个二进制值（/f 免确认）
reg add "HKLM\Software\MyCo" /v Data /t REG_BINARY /d fe340ead /f

:: 新增一个多字符串值（\0 分隔各项）
reg add "HKLM\Software\MyCo" /v MRU /t REG_MULTI_SZ /d fax\0mail\0

:: 新增一个可扩充字符串值 —— 注意百分号要用 ^ 转义
reg add "HKLM\Software\MyCo" /v Path /t REG_EXPAND_SZ /d ^%systemroot^%
```

两条关键提示 [S10]：

- **`reg add` 无法通过此操作添加子树**——它能在已有路径下加值，但**不能一次性造出一整串新键**；
- **`REG_EXPAND_SZ` 类型的数据里，百分号 `%` 必须用插入符号 `^` 转义**，写成 `^%systemroot^%`。

`/t` 可选的类型清单：`REG_SZ`、`REG_MULTI_SZ`、`REG_DWORD`、`REG_DWORD_BIG_ENDIAN`、`REG_DWORD_LITTLE_ENDIAN`、`REG_BINARY`、`REG_LINK`、`REG_FULL_RESOURCE_DESCRIPTOR`、`REG_EXPAND_SZ` [S10]。

#### 2.8.3 `reg delete`：删值不是删键

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 危险操作 —— 动手前务必先 reg export 备份
reg delete "HKLM\Software\MyCo\MyApp\Timeout" /f
reg delete "HKLM\Software\MyCo" /v MTU /f
```

参数含义 [S11]：

- **`/va`**：删除指定键中的**所有值**，**但不会删除其中的子项**；
- **`/v <name>`**：删除特定的值；
- **`/ve`**：只删除"没有值名称"的那个默认条目；
- **`/f`**：免确认。

#### 2.8.4 `reg copy`：复制键

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: /s 表示连同该项下所有子项和值一起复制
reg copy "HKLM\Software\MyCo\MyApp" "HKLM\Software\MyCo\SaveMyApp" /s
```

两条行为 [S12]：**只有指定 `/s` 才会连同所有子项和条目一起复制**；而且**复制子项时此命令不要求确认**（不会弹提示）。

> [!tip] `reg copy` 页面有一处官方笔误
> `reg copy` 页面文末残留了"`reg 比较`作的返回值"字样（那是 `reg compare` 的文案没清理干净），与命令本体不对应，属官方页面笔误 [S12]。**引用返回值语义时以页面正文为准：0 = Success / 1 = Failure。**

#### 2.8.5 PowerShell 的等价写法与差异

同一批操作，PowerShell 侧用"Item / ItemProperty"这一组 cmdlet 完成 [S21]：

| 想做的事 | 用哪个 cmdlet |
|---|---|
| 设置值 | `Set-ItemProperty` |
| 新建值 | `New-ItemProperty` |
| 复制值 | `Copy-ItemProperty` |
| 移动值 | `Move-ItemProperty` |
| 重命名值 | `Rename-ItemProperty` |
| 删除值 | `Remove-ItemProperty` |
| 删除键 | `Remove-Item`（**项包含子项时默认弹确认**，加 `-Recurse` 免提示） |
| 清空整个键的所有值（保留键本身） | `Clear-Item` |

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 只读：看一个值（不会改动任何东西）
Get-ItemProperty -Path HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion -Name "ProgramFilesDir"

# 写值：必须显式给出 -Type，否则默认写成 String
Set-ItemProperty -Path "HKCU:\Software\Demo" -Name "NoOfEmployees" -Value 823 -Type DWord

# 只删值，不删键
Remove-ItemProperty -Path "HKCU:\Software\Demo" -Name "NoOfEmployees"
```

两个最容易出错的差异：

> [!warning] `Set-ItemProperty` 的 `-Type` 默认是 `String`，不是自动判断
> `Set-ItemProperty` 的动态参数 `-Type` **默认为 `String`（也就是 `REG_SZ`）** [S21]。所以**写数字型的值时必须显式指定 `DWord` / `QWord`**，否则类型会被写成字符串——表面上看"值写进去了"，但类型错了，程序读到的就不是数字。可选值包括 `ExpandString`、`Binary`、`DWord`、`MultiString`、`QWord`、`Unknown`（`Unknown` 表示不受支持的类型，如 `REG_RESOURCE_LIST`） [S21]。

> [!warning] `Remove-Item` 和 `Clear-Item` 不是一回事
> **`Remove-ItemProperty` 只删值**；**`Remove-Item` 删的是键本身**，而且**当这个键里还有子项时，它默认会弹确认框**，只有加 `-Recurse` 才不提示 [S21]。另外 **`Clear-Item` 是把一个键的所有值清空，但保留键本身** [S21]。删错一个词，后果完全不同。

#### 2.8.6 官方提醒：能用管理接口就别直接改注册表

官方在讲注册表提供程序时给了一个很好的示范：把某个服务的启动类型从 Automatic 改成 Manual，**既可以**用 `Set-ItemProperty -Path $path -Name Start -Value 3` 直接写注册表值，**也可以**用 `Set-Service -Name Spooler -StartupType Automatic` 通过专用命令改回去 [S21]。

官方的意思很明确：**能通过管理接口改的，就别去动注册表值本身。**

#### 2.8.7 `reg` 的根键规则

`reg` 命令的 `keyname` **必须包含一个有效根键**。本地有效的根键有五个：`HKLM`、`HKCU`、`HKCR`、`HKU`、`HKCC`；而**指定远程计算机时，只有 `HKLM` 和 `HKU` 有效** [S9][S8]。

### 2.9 实用路径速查与开机自启

#### 2.9.1 开机自启一共四个键

`Run` 和 `RunOnce` 各有 HKLM 与 HKCU 两个版本，**共四个**，都在 `Software\Microsoft\Windows\CurrentVersion\` 下 [S19]：

| 用途 | 完整路径 |
|---|---|
| 所有用户，每次登录运行 | `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` |
| 所有用户，仅运行一次 | `HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce` |
| 当前用户，每次登录运行 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` |
| 当前用户，仅运行一次 | `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce` |

行为差异是这一节的核心 [S19]：

- `Run` 键让程序在**每次**用户登录时运行；
- `RunOnce` 键让程序运行**一次，然后删除该键**；
- 这些键的数据值是一条**不超过 260 个字符**的命令行，形式为 `说明-字符串 = 命令行`；
- **如果在同一个键下注册了多个程序，这些程序的运行顺序是不确定的**。

> [!note] 这些键是靠"登录事件"触发的
> 官方口径是：用 `Run` / `RunOnce` 注册表项**使程序在用户登录时运行**——`Run` 键是"每次用户登录时运行"，`RunOnce` 是"运行一次，然后删除该键" [S19]。所以"往 Run 里写东西"和"程序会运行"之间，中间那一步是**登录事件**——这也解释了为什么改完自启项，通常要重新登录甚至重启才看得到效果。

#### 2.9.2 `RunOnce` 的三个行为细节（与 `!`、`*` 前缀）

`RunOnce` 藏了三个容易记反的细节 [S19]：

1. **`HKLM\...\RunOnce` 仅在重新启动后、管理员组的成员登录时才执行**；
2. **删除值的时机**：`RunOnce` 默认在命令行**运行之前**删除值；如果**在值名称前加感叹号 `!`**，删除就会被**延迟到命令运行之后**。官方解释了原因：没有 `!` 前缀时，一旦这次运行失败，下次开机就不会再让关联程序运行了；
3. **安全模式**：默认情况下，**计算机以安全模式启动时会忽略这些键**；如果**在值名称前加星号 `*`**，就能**强制该程序在安全模式下也运行**。

> [!warning] `!` 和 `*` 是最容易记反的两个前缀
> 记法：**`!` 管"什么时候删"**（加了它 → 先运行后删；不加 → 先删后运行）；**`*` 管"安全模式跑不跑"**（加了它 → 安全模式也跑）[S19]。另外别忘最易忽略的那条：**`HKLM\...\RunOnce` 只在管理员组成员登录时才执行**——标准用户登录时它根本不会跑 [S19]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 四个自启键分别看一眼（只读，安全）
reg query "HKLM\Software\Microsoft\Windows\CurrentVersion\Run"
reg query "HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce"
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run"
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce"
```

#### 2.9.3 文件关联三要素：verb、命令字符串、ProgID

右键菜单和文件关联之所以容易看晕，是因为三个词都要先解释 [S23][S24]：

- **verb（谓词）**：指右键菜单里的**一条命令项**。它对应的命令字符串形如 `"My Program.exe" "%1"`——**任何可能包含空格的元素都必须加引号**（这就是为什么程序路径外面要包一层引号） [S23]；
- **ProgID**：文件类型的**登记名**，标准格式是 `厂商或应用.组件.版本`，例如 `Word.Document.6` [S24]；
- **键位置**：`HKEY_CLASSES_ROOT\<ProgID>\shell\<verb>\command`，其中 `(Default)` 条目就是那条命令行 [S23]。

#### 2.9.4 一个免提权技巧

因为 HKCR 是 `HKCU\Software\Classes` 与 `HKLM\Software\Classes` 的组合（见 2.2.3），**可以把自定义的 verb 注册在 `HKEY_CURRENT_USER\Software\Classes` 下**——官方点明了这么做"**主要好处是不需要提升权限**" [S25]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：不需要提升权限（官方说明写在这个位置的主要好处就是免提权）[S25]

```bat
:: 示意：把一个自定义 verb 注册在当前用户名下（路径依据 S25，命令行形式依据 S23；非官方示例）
reg add "HKCU\Software\Classes\MyApp.Document\shell\MyVerb\command" /ve ^
  /d "\"My Program.exe\" \"%1\"" /f
```

> [!tip] 这条技巧为什么值得记住
> 它把 2.2.3 那条"不要直接写 HKCR"的规则变成了好处：写在 HKCU 那边，既符合官方要求，又**不需要管理员权限** [S25][S6]——这是本章里少数几条有官方明确权限说法的路径之一。

#### 2.9.5 实用路径速查表

下面只收录有官方来源的路径：

| 用途 | 路径 | 来源 |
|---|---|---|
| 开机自启（四键） | 见 2.9.1 的表 | [S19] |
| 文件右键菜单命令（verb） | `HKCR\<ProgID>\shell\<verb>\command` | [S23] |
| 某程序处理任意文件类型的默认过程 | `HKCR\Applications\<MyProgram.exe>\shell\...` | [S23] |
| 类级右键菜单（官方真实示例） | `HKEY_CLASSES_ROOT\DesktopBackground\Shell` | [S25] |
| 无需提权注册自定义 verb | `HKEY_CURRENT_USER\Software\Classes` | [S25] |
| 32 位程序在 64 位系统上的视图 | `HKEY_LOCAL_MACHINE\Software\WOW6432Node`（**保留键，不应直接使用**） | [S6][S20] |
| 硬件 / 即插即用历史 | `HKLM\HARDWARE`（含 `DESCRIPTION`、`DEVICEMAP`、`RESOURCEMAP`、`ACPI`、`UEFI`） | [S21][S1] |
| 用户配置文件 hive 的键位置 | `HKEY_USERS` 下，每个登录用户一个 | [S2] |
| 硬件配置文件信息 | `HKLM\System\CurrentControlSet\Hardware Profiles\Current`（即 `HKEY_CURRENT_CONFIG`） | [S4] |
| 系统信息的版本类路径 | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion` | [S22] |

> [!warning] 本章不写的一些"网上常见说法"
> 通配 verb 形态 `HKCR\*\shell`、以及"用某个键给**所有文件**加右键菜单"这类写法，**官方来源中没有出现**，本章**不写**，也不做推断 [S23][S25]。如果你想给某类文件加菜单项，请按 2.9.3 讲的 **ProgID 级** verb 来写。

> [!tip] 看到 `@%SystemRoot%\shell32.dll,-154` 这种值，别手动改
> 文件关联区里会出现形如 `@%SystemRoot%\shell32.dll,-154` 的"间接字符串"，看着像乱码 [S24]。**把它当成一条警告就够了：这类值由系统间接指向资源，不要去手动编辑它**——本章不解释它的语法。

### 本章小结

> [!summary] 小结
> - **四个基本词**：注册表是分层数据库（树），节点叫**键**，键下可同时有**子项**和**值**；键名不能含反斜杠、不本地化，值名称和数据可以含反斜杠 [S1]
> - **五个根键**：HKLM 管整机物理状态、HKCU 管当前用户（映射到 HKU 中该用户的分支，按进程建立）、HKCR **不是真实位置而是合并视图**、HKCC 只是别名、`HKEY_PERFORMANCE_DATA` 的数据并不真的在注册表里 [S4][S6]
> - **Hive 与磁盘文件**：机器级支持文件**大部分**在 `%SystemRoot%\System32\Config`；用户级 hive 的承载文件是 `NTUSER.DAT` / `NTUSER.DAT.LOG`，**其磁盘位置两份官方资料说法不一致、都没提现代路径**，故本章只用"用户配置文件目录"表述、不写死路径；`.log` / `.alt` / `.sav` **不要删** [S2][S6]
> - **值类型是三副面孔**：`REG_SZ` ↔ "字符串值" ↔ `-Type String`；`REG_DWORD` 是 32 位、`REG_QWORD` 是 64 位；`REG_MULTI_SZ` 结尾要**两个**隐藏结束符且**不能有空项**；字符串终止符是读写注册表最常见的陷阱 [S5][S6][S21]
> - **尺寸上限**：值名称 ≤16,383 字符；值数据 >2,048 字节要改存文件；一个键所有值合计 ≤64 K；`Run` 键命令行 ≤260 字符 [S6][S19]
> - **两套视图**：32 位与 64 位程序默认各看一套，32 位那套在 64 位程序眼里挂在 `WOW6432Node` 下（**保留键，不应直接使用**）；实际会用的只有 `/reg:32` 与 `/reg:64` [S20][S9][S6]
> - **备份与回滚（本章主线）**：主路径 = **导出 `.reg` → 需要时导入还原**（覆盖 Win11）[S18][S13][S14]；进阶 = `reg save` → `reg restore`（`.hiv`，官方明写"编辑前必须 reg save"）[S15][S16]；整机级 = 备份"系统状态" [S6]；**系统还原只作附注，不是回滚主路径**（官方版本声明存疑）[S26]
> - **两类备份别混**：**按键级**是导出 `.reg`（只保住导出的那个键）；**整机级**才是备份系统状态 [S6][S18]
> - **命令边界**：`reg add` **不能添加子树**；`reg delete /va` **只删值不删子项**；`Set-ItemProperty` 的 `-Type` **默认是 `String`**，写数字必须显式指定 [S10][S11][S21]
> - **自启四键**：`Run` 每次登录运行，`RunOnce` 一次后**删除该键**；`HKLM\...\RunOnce` **仅管理员组成员登录时执行**；值名前 `!` 把删除推迟到运行之后，`*` 强制在安全模式运行；**触发时机是"用户登录"，改完通常要重新登录或重启才生效** [S19]
> - **官方未说明的位置**（本章一律不推断）：`reg export / import / save / restore / load / unload` 以及 `reg query / add / delete / copy` 的管理员权限要求 [S13]–[S17]

## 第三章 Windows PowerShell——用命令操作前两者

第二章结尾留了两个悬念：为什么 PowerShell 管道里流动的是**对象**而不是文本，以及**执行策略**为什么"防的是手滑，不是防坏人"。这一章就来回答这两个问题，顺便把另外两个新手最常撞上的墙一起拆掉：打开 PowerShell 就报"在此系统上禁止运行脚本"，以及中文显示成一片乱码。

本章内容偏概念，但每一节最后都能落到"你能敲的命令"上。如果你此刻最急迫的问题就是上面那两类报错，可以先跳到 3.6 和 3.7，读懂之后回头再补 3.1–3.5。

### 3.1 对象而不是文本：PowerShell 与 cmd 的根本差别

#### 3.1.1 先看一个场景，再看官方的那句话

假设你想知道"现在哪个进程占内存最多"。在 cmd（命令提示符）里，`tasklist` 会吐给你这么一片东西：

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：无需管理员

```text
映像名称                       PID 会话名              会话#       内存使用
========================= ======== ================ =========== ============
notepad.exe                   1234 Console                    1     12,345 K
explorer.exe                  5678 Console                    1     98,765 K
```

它是**一屏文字**。你说"我只要第 5 列"，cmd 帮不了你——它不知道"第 5 列"是什么，它只知道"这是一串字符"，你得自己按空格把每行切开、数到第 5 段、再去比大小。列宽一变、程序名里多一个空格，你数位置的办法就全废了。

PowerShell 不一样。官方的说法是：PowerShell 与其他 shell 的根本区别，是**接受并返回 .NET 对象而不是文本**，因此管道连接更省事 [C-2]。

这句话里的"**对象**"是本章第一个必须讲透的词。按本笔记一直用的三步走：

| 三步 | 内容 |
|---|---|
| 中文人话 | 命令返回的不是"一段文字"，而是**一排带名字的格子** |
| 官方术语 | .NET 对象（object） |
| 它到底指什么 | 每个结果项（比如一个进程）自带若干**属性**，每个属性都有名字，如 `Name`、`Id`、`Handles` [C-2]；除了"格子里装什么"，它还带一些可以执行的动作 |

关键差别在"**名字**"这两个字。文本管道里的东西没有名字，只有位置（第 1 列、第 2 列）；对象管道里的东西有名字（`Name`、`Id`），你想取哪一项，说的是**名字**，不是位置。

> [!tip] 大白话
> 把 **cmd 的管道想成一沓打印好的表格纸**：信息都在上面，但你要拿"第 5 列"，只能靠眼睛数，列一歪就数错。
> 把 **PowerShell 的管道想成一个带表头的 Excel 表**：每一列顶上写着 `Name`、`Id`、`Handles`，你要"内存那一列"，报的是表头的名字，不用管它排在第几位、中间有没有空格。
> 所以差别不在"谁更漂亮"，而在**后面的命令能不能靠名字直接拿到数据**——这正是下一节要讲的事。

#### 3.1.2 把好处说得再具体一点：文本要切，对象可以直接点

把两种做法并排看，差别就清楚了：

| | 文本管道（cmd / Bash 那一套） | 对象管道（PowerShell） |
|---|---|---|
| 管道里流动的 | 一行一行的**字符串** | 一个一个有结构的**对象** |
| 想取"某个字段" | 自己按分隔符切开、数第几段，还要处理列宽变化 | 直接按**属性名**取用 [C-2] |
| 想"筛掉不符合条件的" | 对字符串做匹配，容易误伤（比如名字里恰好含同样字符） | 按属性的值判断，判断的是数据本身 |

官方举的例子很能说明问题：因为管道里传的是**进程对象**，所以 `Get-Process notepad | Stop-Process` 这句里，后一条命令 `Stop-Process` **根本不需要你再告诉它进程的名字或编号**——上一个命令送过来的对象已经自带这些信息了 [C-1]。

> [!note] 一个提醒：不要再按"文本处理"的思路使唤 PowerShell
> 很多人从 cmd / Bash 过来，习惯先想办法"把输出切成文本再处理"。在 PowerShell 里这通常是绕远路：先`Get-Member`看看对象有哪些带名字的格子（3.3 会讲这条命令），比琢磨怎么切字符串省事得多。

### 3.2 管道怎么工作：一次一个对象

#### 3.2.1 `|` 到底做了什么

管道是由管道操作符 `|`（ASCII 码 124，键盘上就是那个竖线）连接起来的一串命令；**每个运算符把上一条命令的结果发给下一条命令**，整串按**从左到右**的顺序处理 [C-1]。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：取决于目标进程（官方未说明）

```powershell
# 找到记事本进程，把它结束掉
# 注意：后面这条命令没有写 -Name，也没有写 -ID
Get-Process notepad | Stop-Process
```

#### 3.2.2 为什么接收端不用重新"点名"

承接 3.1 的结论：因为管道里流动的是**进程对象**，对象本身就带着名字和编号，`Stop-Process` 直接拿就行，所以它不需要 `-Name`、也不需要 `-ID` [C-1]。这一点刚开始会很不习惯——在 cmd 里，你几乎总要重复一遍"要操作谁"；在 PowerShell 里，**"要操作谁"是跟着对象一起流过去的**。

#### 3.2.3 成功流、错误流，以及一个"没有接进来"的东西

PowerShell 也有类似"标准输出 / 标准错误"的两条通道，官方称为**成功流**和**错误流**，作用确实跟 stdout / stderr 类似 [C-1]。但有一处反直觉：**标准输入（stdin）并没有接入 PowerShell 的管道** [C-1]。

也就是说，管道的主要作用是把"上一条命令产出的对象"送给下一条命令，而不是"把外部程序的输入接进来"。所以当你看到某个来自 Linux 世界的用法在 PowerShell 里怎么都不对时，先想想它是不是依赖了 stdin。

#### 3.2.4 接收端得"肯接"才行

不是随便什么命令都能接住上一个命令丢过来的东西。只有**带"接受管道输入"参数**的命令才能接 [C-1]。

那怎么知道某个命令肯不肯接、又该由哪个参数来接？官方给的办法是用帮助系统去查 [C-1]：`Get-Help <命令> -Full`，或者 `-Parameter *` 把参数列表全列出来。帮助里会写清两件事：**是哪个参数在接**、**按什么方式接**。

#### 3.2.5 两种"接住"的方式：按值，还是按属性名

这是本章第二个硬骨头。官方把接收方式分成两种 [C-1]：

| 接法 | 官方术语 | 中文人话 | 什么时候能接上 |
|---|---|---|---|
| 按值 | ByValue | 看**东西本身**能不能用 | 送来的对象的类型，正好是目标参数要的类型，或者能转换过去 |
| 按属性名 | ByPropertyName | 看**名字**对不对得上 | 送来的对象身上，有一个属性名正好等于目标参数的名字 |

比如上一个命令丢过来一个对象，它身上有 `Destination` 这个属性；而下游命令恰好有个叫 `-Destination` 的参数——这就是"按属性名"接上了。

官方还给了**绑定成功必须同时满足的三个条件**（注意是"同时"）[C-1]：

1. 目标参数**确实接受管道输入**；
2. **类型匹配**（按值）或**属性名对得上**（按属性名）；
3. 这个参数**没有在命令里被显式写出来**——官方明确说，**无法建议或强制 PowerShell 绑定到某个特定参数**，绑不上这条命令就直接失败 [C-1]。

第 3 条最容易被忽略：**你一旦手写了某个参数，就等于把这个参数"占"了，管道就不会再往它上面绑了。**

#### 3.2.6 关键区别：一次送一个，还是整包一起送

这是本节最重要的一个细节，官方原话是——**"这种细微差异具有重大后果"** [C-1]。

- **走管道**时，PowerShell **一次发送一个对象**：上游有多少个进程，下游就被调用多少次（概念上如此），每次只看见一个。
- **改用 `-InputObject` 参数**时，整个集合是当作**一整个数组对象**送过去的 [C-1]。

落到能看见的差别上，就是这一对对照 [C-1]：

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：无需管理员

```powershell
# 第一种：走管道。一次一个对象，所以 Get-Member 看到的是"单个进程"的类型
Get-Process | Get-Member
# 输出里 TypeName: 一行显示
#   System.Diagnostics.Process

# 第二种：用 -InputObject。整个集合被当成一个数组对象送过去
Get-Member -InputObject (Get-Process)
# 输出里 TypeName: 一行显示
#   System.Object[]
```

一个告诉你"我看到的是一台进程"，另一个告诉你"我看到的是一整包东西"。**后者不是"更详细的进程信息"，而是完全换了一个观察对象**——这就是"重大后果"的含义。官方之所以要专门点出这条，正是因为写脚本时踩这个坑会得到莫名其妙的结果。

> [!tip] 大白话
> **管道像"一个一个递苹果"**：每递一个，对方都能把这个苹果的品种、大小看个清楚。
> **`-InputObject` 像"把整筐苹果一起递过去"**：对方一低头，看到的是"一筐"，至于筐里每个苹果什么样，它是看不见的。
> 所以 `Get-Member` 在两处的回答不是"一个详细一个简略"，而是**它盯着看的东西根本换了**。

#### 3.2.7 数组会被拆开，字符串和哈希表不会

还有一个反直觉的规则。官方说：管道执行时会自动把实现了 `IEnumerable` 的那类东西**逐个展开**，但有例外——**哈希表需要调用 `GetEnumerator()`**，而 **`System.String` 虽然也实现了这个接口，却不会被展开** [C-1]。

按本笔记的降维口径，这句话翻译成：

- **数组（以及一批结果）会被拆成一个个元素**，逐个往后传；
- **字符串不会被拆开**——它是一整个，不是"一串字符挨个往下传"；
- **哈希表也不会被拆开**，想逐个看，得先 `GetEnumerator()`。

用 `Get-Member` 去看"对方到底看见了什么"，一眼就能分辨：

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：无需管理员

```powershell
# 数组：被拆成一个元素逐个送过去，所以看到的是单个整数
1, 2, 3 | Get-Member
# 输出里 TypeName: 一行显示
#   System.Int32

# 字符串：不会被拆开，看到的是"整个字符串"
"abc" | Get-Member
# 输出里 TypeName: 一行显示
#   System.String

# 哈希表：不会被拆开，看到的是"整个哈希表"
@{a = 1} | Get-Member
# 输出里 TypeName: 一行显示
#   System.Collections.Hashtable

# 想逐个看哈希表里的元素，得先显式展开
@{a = 1}.GetEnumerator() | Get-Member
```

> [!warning] 绑定失败时的官方排查三步
> 如果你写下一条管道，报"输入对象无法绑定到任何参数"之类的错误，官方给的排查手段是这个顺序 [C-1]：
> 1. `Get-Help <下游命令> -Parameter <目标参数>` —— 看这个参数**是否接受管道输入**，以及它**按值还是按属性名**接；
> 2. `<上游命令> | Get-Member` —— 看上游送来的对象身上**有没有名字对得上的属性**；
> 3. `Trace-Command -Name ParameterBinding` —— 打开参数绑定的跟踪，看它到底试了哪些绑定、为什么失败。
>
> 下面这段是官方示例的结构（路径是假设的，不要照抄执行）：
>
> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：取决于目标键（示例为假设的键）
>
> ```powershell
> # 打开参数绑定跟踪，看这次管道到底怎么绑的
> Trace-Command -Name ParameterBinding -PSHost -Expression {
>   Get-Item -Path HKLM:\Software\MyCompany\sales |
>     Move-ItemProperty -Path HKLM:\Software\MyCompany\design -Name product
> }
>
> # 看 Destination 参数是否按属性名接收管道输入
> Get-Help Move-ItemProperty -Parameter Destination
>
> # 看上游对象身上有没有 Destination 属性
> Get-Item -Path HKLM:\Software\MyCompany\sales | Get-Member
> ```

### 3.3 命令长什么样：Verb-Noun 与四个自举命令

#### 3.3.1 命令名是"动词-名词"

PowerShell 的命令正式名称叫 **cmdlet**（读作"命令莱特"），名字由 **Verb-Noun**（动词-名词）两部分组成，例如 `Get-Process`；动词部分应当取自 `Get-Verb` 返回的那张标准动词表 [C-2]。

> [!tip] 大白话
> 把命令名想成快递单上的"**动作 + 对象**"：`Get-Process` 是"取-进程"，`Stop-Process` 是"停-进程"，`Set-ItemProperty` 是"设置-项的属性"。
> 好处是**你没学过的命令也能猜个八九不离十**：看到 `Get-` 就知道是"读"，看到 `Set-` 就知道是"写"，后面的名词告诉你"对谁干"。

#### 3.3.2 四个自举命令，回答四个不同的问题

新手最常问的是"我怎么知道有这条命令、它怎么用"。官方给的答案是：这四个命令足够发现几乎所有内容 [C-2]：

| 命令 | 它回答的问题 | 有用的过滤参数 |
|---|---|---|
| `Get-Verb` | 有哪些**合法的动词** | —— |
| `Get-Command` | 这台机器上**装了哪些命令** | `-Name` / `-Verb` / `-Noun` / `-ParameterType` [C-2] |
| `Get-Member` | 这个**对象身上有什么**属性、方法 | —— |
| `Get-Help` | 这条命令**怎么用**、参数是什么 | 见 3.4 [C-6] |

注意这四个是**四个不同的问题**，不是四个可以互相替代的命令 [C-2][C-6]。新手最常见的错位是：想"查命令怎么用"，却去敲 `Get-Command`——它只告诉你"有这么条命令"，不会告诉你怎么用。

#### 3.3.3 官方推荐的"找命令"顺序

官方的推荐顺序是：**`Get-Command`（有哪些命令）→ `Get-Help`（怎么用）→ `Get-Member`（返回的对象有什么）** [C-2][C-6]。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：无需管理员

```powershell
# 0. 先确认自己在哪个版本里（5.1 与 7 的行为有差异，见 3.8）
$PSVersionTable

# 1. 有哪些命令：找"动词是 Get、名词以 U 开头"的命令
Get-Command -Verb Get -Noun U*

# 1b. 合法的动词表长什么样
Get-Verb

# 2. 这条命令怎么用
Get-Help Get-ChildItem

# 3. 这条命令返回的对象有什么属性和方法
Get-Process notepad | Get-Member
```

### 3.4 让 PowerShell 自己教你怎么用：Get-Help 与 Update-Help

#### 3.4.1 一个反直觉的前提：帮助文件不是天生就在的

`Get-Help` 是从**本机的帮助文件**里取内容的；**如果没有帮助文件，它只显示基本信息**（大概就是语法那一小段）。关键在于：**从 PowerShell 3.0 起，Windows 自带的模块不再包含帮助文件**，要用 `Update-Help` 下载，或者改用 `-Online` 去看网页版 [C-6]。

所以"`Get-Help` 查不到东西"通常不是命令坏了，而是**帮助文件还没装**。

#### 3.4.2 哪些参数要有帮助文件才管用

`-Detailed` / `-Full` / `-Examples` / `-Parameter` 这几个参数，**只有在计算机装了帮助文件时才有效**；而且它们**对 `about_` 开头的概念文章无效** [C-6]。

另外 `-Online` 是去浏览器里打开网页版帮助，它**不能在远程会话中使用** [C-6]。

#### 3.4.3 概念文章的名字必须用英语

`about_` 开头的概念文章（比如 `about_Execution_Policies`）**必须以英语输入，即使你用的是非英语版 PowerShell** [C-6]。想看全部概念文章，敲 `Get-Help about_*` 就会列出来 [C-6]。

> [!tip] 大白话
> 帮助系统像一个**随软件的说明书柜**：柜子是空的（3.0 之后不自带说明书），你得先跑一趟 `Update-Help` 把说明书搬回来。搬回来之前，除了封面上那几行"用法"，别的都翻不到。
> 而概念文章的**文件名是固定的英文**——就像图书馆的索书号，不管馆里放的是中文书还是英文书，索书号都长一个样。

#### 3.4.4 `Update-Help` 的两条硬限制

这两条在中文社区的文章里几乎从不提，但官方写得很明确 [C-7]：

1. **不加 `-Force` 时，`Update-Help` 每 24 小时只运行一次**；
2. **每个模块的下载上限是 1 GB 未压缩内容**。

官方还特意解释了为什么限制"每天一次"：**正是为了让用户能放心地把它写进配置文件**（这样每次开 PowerShell 尝试更新一次，也不会变成持续占用带宽的操作）[C-7]。

#### 3.4.5 `Update-Help` 的权限按版本不同（这是本章要盯住的一处 5.1 / 7 差异）

- **PowerShell 6.0 及更低版本**（含本章说的 5.1）：`Update-Help` **需要管理员权限**；
- **6.1 及更高版本**（含 7）：`-Scope` 的**默认值是 `CurrentUser`**，也就是默认只给当前用户装；但**如果更新的是 `$PSHOME\Modules` 里的模块，仍然需要"以管理员身份运行"** [C-7]。

按本笔记的降维口径翻译：**只有装在系统目录里的那部分帮助需要管理员；你自己装的模块，普通账户就能更新** [C-7]。

#### 3.4.6 下载失败：系统语言不受支持

`en-US` 的帮助文件**始终会发布**。如果你的系统区域是 en-GB 这类不受支持的语言，可能报 `The specified culture is not supported`，这时要**显式指定**语言 [C-7]。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：5.1 需管理员；7 默认只装当前用户（更新系统目录中的模块仍需管理员）

```powershell
# 首次：下载本机帮助文件（PowerShell 6.1+ 默认只装当前用户）
Update-Help -Verbose

# 系统区域不是 en-US 而下载失败（报 The specified culture is not supported）时
Update-Help -UICulture en-US -Force

# 查命令怎么用
Get-Help Get-ChildItem
Get-Help Get-ChildItem -Examples              # 只看示例（要有帮助文件）
Get-Help Get-ChildItem -Parameter Path        # 只看某个参数
Get-Help Get-ChildItem -Online                # 浏览器版；不能在远程会话中用
Get-ChildItem -?                              # 等价于 Get-Help，但只对 cmdlet 有效

# 查概念文章（名字必须用英语），以及列出全部概念文章
Get-Help about_Execution_Policies
Get-Help about_*

# 查某个"提供程序"的专属帮助（见 3.5）
Get-Help Registry
Get-Help Certificate
```

> [!warning] 中文社区常见建议漏掉了什么
> 你大概会看到"把 `Update-Help` 写进 `$PROFILE`，每次开机自动更新"这类建议。它本身是可行的（官方也确实这么解释"每天一次"的设计），但社区文章普遍不提两条硬限制：**每 24 小时只运行一次** 和 **每模块 1 GB 上限** [C-7]。不知道这两条，你会以为"我写了自动更新但它没生效，是不是坏了"。

### 3.5 Provider 与 PSDrive：把一切变成"盘"

#### 3.5.1 八个内置的"盘"

Provider（提供程序）的作用是**把专用的数据存储，以"驱动器"的形式暴露出来**，路径的写法和使用方式跟硬盘一样 [C-5]。PowerShell 内置 8 个 [C-5]：

| Provider | 它把什么变成了"盘" | 平台 |
|---|---|---|
| FileSystem | 磁盘上的文件与目录 | 全平台 |
| Registry | 注册表 | **仅 Windows** |
| Certificate | 证书存储 | **仅 Windows** |
| WSMan | WS-Management 配置 | **仅 Windows** |
| Alias | 别名（命令的短名字） | 全平台 |
| Environment | 环境变量 | 全平台 |
| Function | 已定义的函数 | 全平台 |
| Variable | 变量 | 全平台 |

有 3 个是**仅 Windows 平台可用**：Certificate、Registry、WSMan [C-5]。

#### 3.5.2 同一批命令，可以作用在任何"盘"上

这是 Provider 模型最漂亮的地方：**同一批 cmdlet 可以作用于任何 Provider 的数据**。官方举的例子是 `New-Item`——在 `C:` 上是建文件，在注册表上是建键，在 `Alias:` 上是建别名，**用法完全一样** [C-5][C-15]。

分层数据的导航方式也和硬盘一致：用 `drive:\location\child-location` 这种写法；**路径里含空格就必须加双引号**；`.` 和 `..` 分别表示当前层和上一层 [C-5][C-15]。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：写系统位置（HKLM、系统目录）需要管理员；其余官方未说明

```powershell
# 看看这台机器上有哪些"盘"（含 Provider 驱动器）
Get-PSDrive
Get-PSProvider

# 同一个 New-Item：在文件系统里建目录
New-Item -Path "C:\" -Name "Logfiles" -ItemType "Directory"

# 同一个 New-Item：在注册表里建键（写入位置决定要不要管理员）
New-Item -Path "HKLM:\Software\ContosoCompany"

# 同一个 New-Item：在 Alias 盘里建别名
New-Item -Path "Alias:np" -Value "notepad.exe"

# 切换位置：可以切到任何 Provider 的路径
Set-Location HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion

# 路径含空格时要加双引号；. 和 .. 分别表示当前层与上一层
Set-Location "C:\Program Files"
Set-Location ..
```

> [!tip] 大白话
> 把 Provider 想成**给不同仓库统一装上了同一种门牌系统**：文件仓库、注册表仓库、证书仓库，本来各有各的找法；装上之后，**都用 `C:`、`HKLM:`、`Cert:` 这样的"盘符"进门，都用同一套 `dir` / `cd` / `New-Item` 逛**。
> 你不需要记住"注册表有别的一套命令"，只要记住"换个盘符，命令照旧"。

#### 3.5.3 只有文件系统这一种"盘"有"家目录"

FileSystem 是**唯一有默认 Home 的 Provider**（值等于 `$HOME`），所以 `~` 表示 Home 目录；**没有 Home 的 Provider，用 `~` 会报错** [C-5]。

#### 3.5.4 有些参数，只在特定的"盘"里出现

官方管这叫**动态参数**：只在配合特定 Provider 时才出现。典型例子是在 `Cert:` 盘里，`Get-ChildItem` 会多出一个 `-CodeSigningCert` 参数 [C-5]。

想知道某个 Provider 有哪些动态参数，官方给的办法是 `Get-Help <provider-name>`（例如 `Get-Help Certificate`）[C-5]——这也正好接上 3.4.6 命令清单里的最后两条。

> [!tip] 大白话
> 动态参数像**只有在特定仓库里才会递到你手上的专用工具**：你在普通仓库里翻遍工具箱都找不到它，一走进证书仓库，门口就多摆了一个"只看签名证书"的筛子。所以"这个参数我昨天怎么没见过"很正常——**换盘再看**。

#### 3.5.5 这些"盘"，别的地方看不见

`Get-PSDrive` 能看到 `New-PSDrive` 创建的**会话级驱动器**；而 `net use`、`[System.IO.DriveInfo]::GetDrives()`、`Get-CimInstance` **都看不到它们** [C-13]。

换句话说，PowerShell 里的"盘"有一部分是**PowerShell 自己造的**，出了 PowerShell 就没了。

#### 3.5.6 预告一下：这些命令，第 4 章要正式排队上场

> [!note] 本章只管"有这些命令"，用法留给第 4 章
> 你已经在 3.5.2 见过 `New-Item` 了。文件系统与注册表的常用 cmdlet 主体（`Get-ChildItem`、`Get-Item`、`Get-ItemProperty`、`Get-ItemPropertyValue`、`Set-ItemProperty`、`Remove-Item`、`Remove-ItemProperty`、`Clear-Item`、`Set-Location` 等）**全部放在第 4 章**，因为它们正好是把前两章内容串起来的那批命令。本章只先记住一件事：**它们能用同一套写法，同时作用在文件系统和注册表上** [C-5][C-9][C-11][C-12][C-15]。

### 3.6 执行策略：它防的是手滑，不是防坏人

#### 3.6.1 官方明说：它不是安全边界

这是本章最需要纠正的一个流行误解。官方对执行策略的定位说得非常直白：**执行策略不是安全边界**，它是一种"深层防御"——因为**当用户无法运行脚本时，直接在命令行里把脚本内容粘贴进去就能绕过它** [C-3]。

> [!warning] 执行策略是"防误运行的便利机制"，不是安全方案
> 中文社区普遍把它当成一种"安全设置"来讲，甚至建议换成最严的档位来"提高安全性"。**官方口径不是这样**：它明确说执行策略不是安全边界，防的是"随手运行来路不明脚本"这类**手滑**，不是防有意绕过的人 [C-3]。
>
> 落到行动上就是两句话：**别为了"看起来安全"把它调到最严**（那只会让你天天被自己的脚本挡住）；也**别因为它"不是安全"就随手关掉**——它确实帮你挡了一次误运行。

#### 3.6.2 `Restricted` 拦的是什么

`Restricted` 是"允许单个命令、但**阻止所有脚本文件**"的档位。注意"所有脚本文件"包括 `.ps1`、`.ps1xml`、`.psm1`，以及 **PowerShell 的配置文件** [C-3]——这一点很重要，因为新手遇到的第一个报错往往就是配置文件被拦。

#### 3.6.3 从网上下载的脚本，会被贴一张标签

从 Internet 下载的脚本会被标记为"**来自 Internet**"。在 `RemoteSigned` 下，**未签名的这类文件不会被运行**；要放行，可以用 `Unblock-File` 解除标记 [C-3]。

有一条容易踩的细节：**并不是所有下载方式都会带上这张标签**。官方明确说，用 `curl.exe`、`Invoke-RestMethod`、`Invoke-WebRequest` 下载的文件**不会**带这个标记 [C-3]。所以"我明明是从网上下的，怎么没被拦"和"我这个明明是本地生成的，怎么被拦了"两种情况都可能出现。

#### 3.6.4 默认值到底是什么

官方给出的默认是：策略 `Default` **在客户端和服务器上都是 `RemoteSigned`**；而如果所有作用域都是 `Undefined`，那么**客户端**的有效策略是 **`Restricted`**、**服务器**是 **`RemoteSigned`** [C-3]。

> [!warning] 默认与推荐都是 `RemoteSigned`，不是 `AllSigned`
> 社区文章常把 `AllSigned` 列为"建议"、把 `RemoteSigned` 说成"折中方案"；**官方默认是 `RemoteSigned`** [C-3]。本笔记按官方口径写：**默认与推荐都用 `RemoteSigned`**，`AllSigned` 只作为一种"可选更严档位"在这里提一句——你只有在确实需要"所有脚本都必须签名"的场景（比如统一的受控环境）才需要考虑它。
>
> 同一件事还有第二层：**`Undefined` 不等于"没有限制"**。如果各级作用域都还是 `Undefined`，客户端上的实际效果是 `Restricted`（也就是"禁止运行脚本"）[C-3]——这正是 3.6.2 那个报错的来源之一。

#### 3.6.5 作用域：先只记一条 `CurrentUser`

执行策略有多个"作用域"（scope），不同作用域存在不同地方、优先级也不同。官方给的优先级是：`Process`（最高）> `CurrentUser` > `LocalMachine`，并且**组策略的设置覆盖所有作用域** [C-3]。

对零基础读者，**先只记 `CurrentUser` 这一条就够了**：

- **`CurrentUser` 只影响你自己**，而且 **`Set-ExecutionPolicy -Scope CurrentUser` 不需要管理员权限** [C-3]。

另外有一个好用的档位是 `Process`：它只对**当前这个会话**生效，而且**不写注册表**——它改的是环境变量 `$Env:PSExecutionPolicyPreference` [C-3]。适合"我只想让这个窗口能跑脚本，关掉窗口就恢复原样"的场景。

至于 `LocalMachine` 和组策略，先放着，等 3.6.7 那个"改了不生效"的场景再回来看。**`LocalMachine` 需要管理员**，这一点官方是明确写了的 [C-3]。

#### 3.6.6 命令清单

> 环境：PowerShell ｜ 版本：5.1 & 7（5.1 用 `powershell.exe`，7 用 `pwsh.exe`）｜ 权限：`CurrentUser` / `Process` 无需管理员；`LocalMachine` 需要管理员 [C-3]

```powershell
# 只看不写：当前生效策略，以及各作用域的实际取值
Get-ExecutionPolicy
Get-ExecutionPolicy -List

# 官方推荐的最小改动：只影响当前用户，不需要管理员
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

# 只对当前会话生效，不落盘（改的是 $Env:PSExecutionPolicyPreference）
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope Process

# 起一个"只这一次"的会话（7 用 pwsh.exe；5.1 换成 powershell.exe）
pwsh.exe -ExecutionPolicy RemoteSigned

# 解除"来自 Internet"标记（下载的脚本被 RemoteSigned 拦下时）
Unblock-File -Path .\downloaded.ps1

# 恢复默认：删掉当前用户的设置，回到系统默认值
Set-ExecutionPolicy -ExecutionPolicy Undefined -Scope CurrentUser
```

> [!example] 你可能见过的那个报错
> 现象：一打开 PowerShell 就弹出一行红字，大意是"**无法加载文件 …\profile.ps1，因为在此系统上禁止运行脚本**"，后面还跟着 `CategoryInfo: SecurityError … PSSecurityException` [C-17]（现象）。
>
> 原理在官方文档里：`Restricted` 会**阻止 `.ps1` 配置文件**；而在所有作用域都是 `Undefined` 时，客户端的有效策略就是 `Restricted` [C-3]（原理）。
>
> 所以这不是"你的电脑中毒了"，也不是"PowerShell 装坏了"，而是**配置文件被执行策略挡住了**。要在理解 3.6.1 的前提下处理：如果你确实要用配置文件，按 3.6.6 把 `CurrentUser` 作用域设成 `RemoteSigned`。

> [!note] 两条我们不写进结论的情形
> 一是 **UNC 路径在 `RemoteSigned` 下的限制**：官方原文的限定语是"在无法将 UNC 路径与 Internet 路径区分开来的系统上"，**它对平台有依赖，本章不写成通用结论** [C-3]。二是 **Server Core 上的 `AuthorizationManager check failed`**：那是依赖 `explorer.exe` 提供区域检查 API 的场景，对零基础读者属极边缘，本章刻意剔除 [C-3]。

#### 3.6.7 改了不生效怎么办（排错小节）

如果在一台**公司统一管理的电脑**上，你按 3.6.6 把 `CurrentUser` 设成了 `RemoteSigned`，`Get-ExecutionPolicy` 却还显示别的值，或者你设完又被改回去——那大概率不是你没敲对，而是**更高优先级的作用域在压着它**。

按优先级从高到低看 [C-3]：

| 优先级 | 作用域 | 存在哪 | 特点 |
|---|---|---|---|
| 最高 | `Process` | 环境变量 `$Env:PSExecutionPolicyPreference` | **不写注册表**，只影响当前会话 [C-3] |
| 中 | `CurrentUser` | 用户的 `powershell.config.json` | **不需要管理员**，只影响你自己 [C-3] |
| 低 | `LocalMachine` | `$PSHOME/powershell.config.json` | **需要管理员**，影响全机 [C-3] |
| 覆盖一切 | 组策略 | 由域策略下发 | **组策略设置覆盖所有作用域** [C-3] |

排查顺序建议是：

1. `Get-ExecutionPolicy -List` 把各作用域的实际取值列出来，**先看清到底是谁在生效**；
2. 如果你要的档位被 `Process` 压着，看看是不是启动命令里带了 `-ExecutionPolicy`，或者当前会话的环境变量被设过；
3. 如果是**组策略**在压着，那 `Set-ExecutionPolicy` 改哪个作用域都没用——官方明说组策略覆盖所有作用域 [C-3]。这时正确的动作是**找管理员**，而不是反复重试命令。

### 3.7 编码与中文乱码：三条独立通道

这一节要解决"中文乱码"。但必须先把一个错误期待掐掉：**不存在"改一个设置就好"的万能开关**。官方在同一页里就先说了"通常 Windows PowerShell 默认使用 Unicode UTF-16LE 编码"，紧接着又说"**Windows PowerShell 中 cmdlet 使用的默认编码不一致**" [C-8]——所以本章的写法是：**把编码拆成三条互不相干的通道，哪条出问题就修哪条**。

#### 3.7.1 前提

Windows 既支持 Unicode 也支持传统字符集；PowerShell **默认使用 Unicode**，并且**多个 cmdlet 都带 `-Encoding` 参数**，可以指定成别的字符集 [C-8]。

#### 3.7.2 通道一：脚本源码本身是什么编码

这一条管的是"**你写的那份 `.ps1` 文件，本身用什么编码存**"。

- 在 **Windows PowerShell（5.1）** 里，**除 `UTF7` 以外，任何 Unicode 编码总是会创建 BOM** [C-8]；
- 在 **PowerShell（v6 及以上，含 7）** 里，**默认对所有文本输出使用 `utf8NoBOM`** [C-8]。

> [!tip] 大白话：什么是 BOM
> BOM 是**文件开头多出来的 3 个看不见的字节**，作用是告诉读它的程序："我是 UTF-8"。
> 你打开文件看不到它们，但程序第一眼看到的就是它们。5.1 存脚本时**默认会加上这 3 个字节**；7 默认**不加**。这就是为什么同一份中文脚本在 5.1 里正常、在 7 里也正常，但换一种存法就可能变乱码。

#### 3.7.3 通道二：`-Encoding` 参数与各 cmdlet 的默认值（5.1 最坑的一块）

这一条管的是"**命令把内容写进文件时用什么编码**"。注意：**在 5.1 里没有"统一的默认编码"这回事**，必须**按 cmdlet 分别判断** [C-8]：

| 写法 | 5.1 的默认编码 | 7 的默认编码 |
|---|---|---|
| `Out-File`，以及重定向 `>` / `>>` | **UTF-16LE** | `utf8NoBOM` |
| `Export-Csv` | **ASCII** | `utf8NoBOM` |
| `New-Item -Type File -Value` | **不带 BOM 的 UTF-8** | `utf8NoBOM` |
| `Add-Content` / `Set-Content`（目标文件为空或不存在时） | `Default`（系统 ANSI 旧代码页） | `utf8NoBOM` |

后三行和第一行放在一起看，你就明白为什么"5.1 默认是 XX 编码"这句话是错的：同一个版本里，**不同 cmdlet 出来的文件编码各不相同** [C-8]。5.1 上写中文文件，最稳妥的办法是**每次都显式写 `-Encoding`**。

#### 3.7.4 通道三：控制台，以及"对外部程序说话"用的编码

这一条管的是"**你在窗口里看到的字符，和 PowerShell 传给外部程序的东西，用什么编码**"。

官方的关键说明是：自动变量 `$OutputEncoding` **只影响 PowerShell 与外部程序通信时的编码，不影响重定向运算符，也不影响 cmdlet 写文件时的编码** [C-8]。

换句话说，**通道三和通道二互不覆盖**：

- `$OutputEncoding` 管"**和外部程序说话**"；
- `-Encoding` 参数，以及 `$PSDefaultParameterValues` 管"**存到文件**" [C-8]。

还有一条把两边搭上桥的事实：**从 5.1 起，`>` 和 `>>` 内部是调用 `Out-File` 来实现的**，所以设置 `$PSDefaultParameterValues['Out-File:Encoding'] = 'utf8'` 可以**同时**管住"写文件"和"重定向"这两种写法 [C-8]。

> [!tip] 大白话
> 把三条通道想成**三根独立的水管**：一根进水（脚本源码存成什么编码）、一根出水到文件（`-Encoding`）、一根接到外部程序（`$OutputEncoding` / 控制台）。
> 只拧一根，另外两根不会跟着变。所以"乱码"要**先判断是哪根漏的**：是文件打开就乱，还是只在某个外部程序输出里乱？

#### 3.7.5 BOM 到底加不加：按文件类型分开

官方的建议看起来是"两个相反方向"，其实是**针对两类不同文件**，必须分开表述 [C-8]：

| 文件类型 | 建议 | 依据 |
|---|---|---|
| **脚本源码**（尤其是 5.1 的 `$PROFILE`） | **用带 BOM 的 UTF-8** | 含非 ASCII 字符的脚本在 5.1 下**需要 BOM**，否则会被误读为"过时的 ANSI 代码页"，中文就乱了 [C-8] |
| **纯数据文件** | **用不带 BOM 的 UTF-8** | 为获得最佳整体兼容性，官方建议避免在 UTF-8 文件中使用 BOM（跨平台工具链通常不认它）[C-8] |

> [!warning] BOM 的两条建议是"分工"，不是"打架"
> 你如果把"避免 BOM"和"必须用 BOM"两条建议放在一起看，会得出互相矛盾的结论。**正确的读法是按文件类型分工**：**脚本源码（5.1 的 `$PROFILE`）用 BOM；纯数据文件不用 BOM** [C-8]。
>
> 中文社区的文章通常只讲后一半（脚本要 BOM），照着做之后再拿这个文件去喂 Linux 上的工具，又会被 BOM 坑到 [C-18]（现象）。

#### 3.7.6 诊断与落盘的命令清单

**第一步永远是诊断**：先把"当前三根管子的状态"看清楚，再决定改哪根 [C-8]。

> 环境：PowerShell ｜ 版本：5.1 & 7（默认编码行为不同）｜ 权限：无需管理员

```powershell
# —— 第一步：诊断。看当前代码页与三条编码通道 —— 5.1 & 7
chcp                        # 当前控制台代码页
[Console]::OutputEncoding   # 控制台"输出"用什么编码
[Console]::InputEncoding    # 控制台"输入"用什么编码
$OutputEncoding             # 与外部程序通信用什么编码

# —— 第二步：写文件时显式指定编码（最不容易错）—— 5.1 & 7
'你好' | Out-File -FilePath .\a.txt -Encoding utf8
'你好' | Set-Content -Path .\a.txt -Encoding utf8

# —— 会话级默认：让 cmdlet 的 -Encoding 都走 utf8 —— 5.1 & 7
# （从 5.1 起 > 和 >> 内部调用 Out-File，所以这一行也管住了重定向）
$PSDefaultParameterValues['Out-File:Encoding'] = 'utf8'
$PSDefaultParameterValues['*:Encoding'] = 'utf8'

# —— 会话级：控制台与对外部程序的编码（临场救急用）—— 5.1 & 7
# 注意：$OutputEncoding 只影响与外部程序通信，不影响写文件
chcp 65001 | Out-Null
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
[Console]::InputEncoding  = [System.Text.Encoding]::UTF8
$OutputEncoding           = [System.Text.Encoding]::UTF8

# —— 第三步：把设置落盘到配置文件（永久生效）—— 5.1 & 7
Test-Path $PROFILE
New-Item -Path $PROFILE -ItemType File -Force   # 不存在时先创建
notepad $PROFILE                                # 用记事本打开编辑
```

> [!warning] 不要在 `$PROFILE` 里只写 `chcp 65001`
> 中文社区最常见的方案是"把代码页改成 65001（UTF-8）"，理由是"代码页 936 与 UTF-8 不一致" [C-18]（现象）。
>
> 对应到官方原理上，这类方案**只能覆盖通道三的一部分**：它管的是控制台与外部程序那一头，**管不到 cmdlet 写文件时用的编码**（那是通道二，要靠 `-Encoding` 或 `$PSDefaultParameterValues`）[C-8]（原理）。
>
> 所以会出现一个典型的失败场景：**"写出来的文件正常了，但调用某个外部程序时输出还是乱码"**——这不是方案错了，而是它**只修了三条通道里的一条** [C-8]。

> [!example] 你可能见过的乱码长什么样
> 现象：正常的中文被显示成 `UTF-8 缂栫爜宸查厤缃畬鎴愶紒` 这一类谁也看不懂的字符，社区把它归因于"控制台代码页 936（GBK）与脚本文件 UTF-8 不一致" [C-18]（现象）。
>
> 原理要回到官方：5.1 的 `Out-File` / `>` / `>>` 默认写 **UTF-16LE**，而 `Export-Csv` 默认写 **ASCII**，再加上 `$OutputEncoding` 只管对外部程序——是**这几条通道各自为政**造成的 [C-8]（原理）。
>
> 明白这一点，你就知道为什么"换一个文本编辑器打开文件"有时看起来是好的：**编辑器按自己的猜测解码了**，文件本身并没有变对。

> [!warning] 中文目录里第三方程序报 `Error 3`：只能说成"某些第三方程序的已知限制"
> 有一条现象值得知道：**在中文目录下，某些第三方 native 组件会报 `Error 3: The system cannot find the path specified.`，而同一路径在资源管理器里明明看得见** [C-19]（现象）。
>
> **这一条只有 C 级的第三方 issue，没有 A 级的官方原理**，所以本章**只把它写成"某些第三方程序的已知限制"，绝不解释成 PowerShell 的原理**。遇到它时，可用的做法是换个纯英文路径试试——这是绕过，不是修复。

> [!note] 本章刻意留下的空白
> 本轮素材里有两条与"中文环境"相关的疑点，都因为**没有可用的来源**而**本章不写**：
> 1. 有一条与"**用户名/路径含非 ASCII 字符时的模块搜索路径**"有关的疑点，三个来源尝试全部抓取失败，**既无现象来源也无原理来源**，按 P2 决策，正文里**不写现象、不写原理、也不做推断** [C-14]；
> 2. 中文路径下 `Error 3` 的**原理**（现象已在上面提及，但原理没有 A 级支撑）[C-19]。
>
> 这两处请不要当成结论使用。可用的相邻 A 级事实只有一条：**Documents 的位置会被文件夹重定向和 OneDrive 改变**，官方给的验证命令是 `[Environment]::GetFolderPath('MyDocuments')` [C-14]。

### 3.8 PowerShell 5.1 与 7：两个版本可以一起装

#### 3.8.1 两套并存，各有各的名字和路径

这两个版本**并行安装、并行运行**，各有**独立的安装路径、可执行文件名、`PSModulePath`、配置文件和事件日志** [C-4]：

| | Windows PowerShell 5.1 | PowerShell 7 |
|---|---|---|
| 可执行文件 | `powershell.exe` | `pwsh.exe` |
| 安装位置 | `$Env:windir\System32\WindowsPowerShell\v1.0` | `$Env:ProgramFiles\PowerShell\7` |

> [!tip] 大白话
> 把它想成**同一栋楼里住着两位同名不同姓的管家**：一位叫 `powershell.exe`，一位叫 `pwsh.exe`，各管各的房间、各用各的记事本。
> 所以"我明明装了 7，怎么还是旧行为"这种问题，十有八九是**你打开的是 5.1 那位管家**——看窗口标题、或者敲 `$PSVersionTable` 就能分辨。

#### 3.8.2 模块搜索路径 `PSModulePath` 的差别

`PSModulePath` 是 PowerShell 找模块时依次去看的目录清单。两版本的差别是 [C-4][C-14]：

- **PowerShell 7** 的 `$Env:PSModulePath` **额外包含 Windows PowerShell 的路径**，这是为了支持模块自动加载；
- **5.1** 的默认模块路径是 `$HOME\Documents\WindowsPowerShell\Modules` 与 `$Env:ProgramFiles\WindowsPowerShell\Modules` [C-14]。

#### 3.8.3 配置文件改了位置

| | 配置文件位置 |
|---|---|
| 5.1 | `$HOME\Documents\WindowsPowerShell` |
| 7 | `$HOME\Documents\PowerShell` |

路径变了，所以**你在 5.1 里写的那份配置，7 不会自动读**。想知道当前这位管家实际用的是哪一份，用这条命令看 [C-4]：

> 环境：PowerShell ｜ 版本：5.1 & 7（输出路径不同）｜ 权限：无需管理员

```powershell
# 查看当前会话实际使用的配置文件路径
$PROFILE | Select-Object *Host* | Format-List

# 确认自己在哪个版本里
$PSVersionTable

# 看本版本的模块搜索路径（7 会额外包含 5.1 的路径）
$Env:PSModulePath
```

#### 3.8.4 地基不同：.NET 版本与 ISE

- PowerShell **7.4 基于 .NET 8.0**，**5.1 基于 .NET Framework 4.x**；版本差异**可能改变脚本行为**（尤其是脚本里直接调用 .NET 方法的时候）[C-4]。
- **ISE（集成脚本环境）仅支持 5.1，且没有更新计划**；官方推荐改用 VS Code 的 PowerShell 扩展 [C-4]。

按本笔记的降维口径，版本号这一条不用记，只记**后果**：**如果你要跑一个只支持 5.1 的老模块，见 3.8.5。**

#### 3.8.5 老模块怎么办：兼容开关

PowerShell 7 提供了兼容开关 `Import-Module -UseWindowsPowerShell`，用来跑那些只支持 5.1 的模块 [C-4]。

> 环境：PowerShell ｜ 版本：7（5.1 无此需求）｜ 权限：官方未说明

```powershell
# 用兼容层导入一个只支持 Windows PowerShell 5.1 的老模块
Import-Module -UseWindowsPowerShell <模块名>
```

> [!warning] 全程要盯住的四项版本差异
> 这两个版本在**四个行为上不同**，是本章乃至全书最容易出错的地方，本章全程都做了 `5.1` / `7` 标注 [C-4][C-7][C-8]：
> 1. **默认编码**（3.7.3：5.1 各 cmdlet 不一致，7 统一 `utf8NoBOM`）
> 2. **配置文件路径**（3.8.3：`WindowsPowerShell` vs `PowerShell`）
> 3. **`PSModulePath`**（3.8.2：7 额外包含 5.1 的路径）
> 4. **`Update-Help` 权限**（3.4.5：5.1 需要管理员，7 默认只装当前用户）
>
> 另外多记一条**只在 7 上存在**的功能：**位置历史 `cd -` / `cd +`**（PowerShell 6.2 起可用，5.1 不能用），第 4 章会正式用到它 [C-10]。

> [!warning] "迁移简单、快速且安全"这句话，要降级来读
> 官方在迁移页开头称迁移"简单、快速且安全"，但同一页也说明：**ISE 不再更新、部分模块需要 `Import-Module -UseWindowsPowerShell` 兼容层、.NET 版本差异可能改变脚本行为** [C-4]（矛盾）。
>
> 对零基础读者，本章把这句话降级为：**"5.1 与 7 可以共存，所以可以慢慢迁"**——你不需要"先卸掉 5.1 再装 7"，两者互不干扰 [C-4]。

> [!note] 一个问题，本章不给结论
> "**新手该默认用 7 吗？**"——本轮素材中**没有官方倾向来源**（官方只说明两者可以并行、迁移简单，没有给出"新手就用哪个"的推荐）[C-4]。所以本章**不给"就用 7"的结论**，请你按自己的场景决定。另外两处时效性留白也一并说明：本轮抓取的 **8 张 cmdlet 参考页没有 `Last updated` 字段**（时效不可考）[C-6][C-7][C-9]–[C-13][C-15]；**PowerShell 7 的当前稳定版本号未确认**，所以全篇版本标注统一写 `7`，不写具体小版本 [C-4]。

#### 3.9.1 十个维度逐项对照

| 维度 | PowerShell 5.1（`powershell.exe`） | PowerShell 7（`pwsh.exe`） | cmd.exe | Bash |
|---|---|---|---|---|
| 管道传的东西 | 对象 | 对象 | 文本 | 文本 |
| 命令名风格 | Verb-Noun（`Get-ChildItem`）+ 别名（`dir` / `ls`） | 同 5.1 | 独立小工具（`dir`） | 独立小工具（`ls`） |

| 盘符 | `C:`，另有 Provider 盘符 `HKLM:`、`Cert:`、`Env:` | 同 5.1 | `C:` | 无（挂载点） |
| 变量语法 | `$name`；环境变量 `$Env:NAME` | 同 5.1 | `%NAME%` | `$name` / `${name}` |
| 脚本扩展名 | `.ps1`（另有模块 `.psm1`、清单 `.psd1`） | `.ps1` | `.bat` / `.cmd` | `.sh`（常无扩展名） |
| 脚本执行前提 | 受执行策略约束（默认 `RemoteSigned`） | 受执行策略约束 | 不受执行策略约束 | 需 `chmod +x` |

### 本章小结

> [!summary] 小结
> - **对象而不是文本**：PowerShell 接收并返回**对象**而不是文本，所以管道连接更省事；文本管道只能传字符串、取字段要自己切，对象管道里的每个项自带 `Name`、`Id`、`Handles` 这类**带名字的格子** [C-2]
> - **管道一次一个对象**：`|` 从左到右把上一条的结果发给下一条；因为传的是对象，`Get-Process notepad | Stop-Process` 不必再写 `-Name` / `-ID`；stdin **没有**接入 PowerShell 管道 [C-1]
> - **参数绑定**：接收端必须有"接受管道输入"的参数，接法分**按值**（ByValue）和**按属性名**（ByPropertyName）；绑上要同时满足三条，且**无法强制绑定到特定参数** [C-1]
> - **`-InputObject` 的坑**：管道一次送**一个**对象，`-InputObject` 把集合当**一整个数组**送——官方称"这种细微差异具有重大后果"：`Get-Process | Get-Member` 显示 `System.Diagnostics.Process`，而 `Get-Member -InputObject (Get-Process)` 显示 `System.Object[]` [C-1]
> - **数组会拆、字符串和哈希表不拆**：自动枚举有例外——哈希表要 `GetEnumerator()`，`System.String` 不会被枚举 [C-1]
> - **四个自举命令**：`Get-Verb`（合法动词）、`Get-Command`（有哪些命令）、`Get-Member`（对象有什么）、`Get-Help`（怎么用）；官方推荐顺序是 `Get-Command` → `Get-Help` → `Get-Member` [C-2][C-6]
> - **帮助系统**：3.0 起 Windows 自带模块**不含帮助文件**，要 `Update-Help` 下载或用 `-Online`；`Update-Help` **每 24 小时只运行一次**、**每模块上限 1 GB**；权限按版本不同（5.1 需管理员，7 默认只装当前用户）[C-6][C-7]
> - **Provider 把一切变成"盘"**：内置 8 个（Certificate / Registry / WSMan **仅 Windows 可用**）；同一批 cmdlet 可作用于任何 Provider；FileSystem 是唯一有默认 Home 的；动态参数只在特定盘里出现 [C-5][C-13]
> - **执行策略不是安全边界**：它是**防误运行的便利机制**，粘贴脚本内容即可绕过；**默认与推荐都是 `RemoteSigned`**（不是 `AllSigned`）；**`CurrentUser` 不需要管理员**，`LocalMachine` 需要，**组策略覆盖所有作用域** [C-3]
> - **编码是三条独立通道**：① 脚本源码编码（5.1 除 `UTF7` 外总是创建 BOM；7 默认 `utf8NoBOM`）② `-Encoding` 参数与各 cmdlet 默认值（5.1 **按 cmdlet 分别判断**：`Out-File` / `>` / `>>` = UTF-16LE，`Export-Csv` = ASCII，`New-Item -Type File -Value` = 无 BOM 的 UTF-8，空文件的 `Add-Content` / `Set-Content` = 系统 ANSI）③ 控制台与对外部程序编码（`$OutputEncoding`，**不管写文件**）[C-8]
> - **BOM 按文件类型分工**：**脚本源码（尤其 5.1 的 `$PROFILE`）用带 BOM 的 UTF-8；纯数据文件用不带 BOM 的 UTF-8** [C-8]
> - **5.1 与 7 可以共存**：各有独立路径、可执行名、`PSModulePath`、配置文件、事件日志；四项行为差异要全程盯住（默认编码、配置文件路径、`PSModulePath`、`Update-Help` 权限）；`cd -` **仅 7 可用** [C-4][C-10]
> - **官方未说明的位置**`（本章一律不推断）`：`Unblock-File`、`Import-Module -UseWindowsPowerShell`、`Set-ItemProperty` 写注册表值、`New-Item` 建文件/键、`Trace-Command`、`chcp` 与 `[Console]::*Encoding` 修改的**管理员权限要求**均**官方未说明**
> - **本章刻意留白**：与"用户名/路径含非 ASCII 字符时的模块搜索路径"相关的疑点**零可用来源，不写**；中文路径下 `Error 3` **只有 C 级现象、无 A 级原理**，只作"某些第三方程序的已知限制"提及 [C-19][C-14]

## 第四章 串联——用 PowerShell 同时操作文件系统与注册表

前三章各管一块：文件系统回答"数据放在哪"，注册表回答"系统和程序怎么配置自己"，PowerShell 回答"怎么用命令批量操作前两者"。这一章的任务不是再讲一遍它们，而是把三块拼起来——用**同一个窗口、同一套命令**，先逛文件系统，再逛注册表，最后完整走一遍"备份 → 改值 → 复核 → 回滚"。本章约八成篇幅是命令清单，概念只回答一个问题：为什么这两件看起来毫不相干的事，能用同一批命令做？

### 4.1 为什么两件事能变成一件事

#### 4.1.1 回顾：两个"盘"

第三章 3.5 已经把底牌交代过了：Provider（提供程序）把专用的数据存储**以"驱动器"的形式**暴露出来，路径的写法和使用方式跟硬盘一样 [C-5]。文件系统是其中一个 Provider（FileSystem），注册表是另一个（Registry）——两个都只在 Windows 平台可用 [C-5]。

于是到了命令行这一层，"逛 C 盘"和"逛注册表"真的变成了同一件事：换的只是盘符，命令照旧。第三章 3.5.2 见过的那条 `New-Item` 就是最好的例子——在 `C:` 上建目录、在 `HKLM:` 上建键、在 `Alias:` 上建别名，用法完全一样 [C-5][C-15]。

#### 4.1.2 关键区别：一边是"项"，一边是"值"

如果只有上面那一句，你会以为两边完全对称。但对到命令上就会发现一处**根本性的不对称**，它是本章后面所有命令差异的根源。

> [!note] 两边的"东西"不是同一类东西
> - 文件系统里，你能看到的东西是**项**（item）：文件、目录；
> - 注册表里，你能看到的东西分两种：**键**（相当于文件夹）和挂在键上的**值**；
> - 而在 PowerShell 眼里，**"值"不是"项"，它是键的"属性"（property）** [C-11][C-12]。
>
> 差别的后果很直接：`Get-ChildItem` / `Get-Item` 这一对"看项"的命令，在注册表里**只能看见键，看不见值**；要读值、写值，得换成 `Get-ItemProperty` / `Set-ItemProperty` 这一族 [C-11][C-12][S21]。

把两边的概念摆在一起对一遍，这张表要记住：

| 你眼里的东西 | 文件系统里它是 | 注册表里它是 | 用哪族命令 |
|---|---|---|---|
| "文件夹" | 目录（**项**） | 键（**项**） | `Get-ChildItem` / `Get-Item` / `New-Item` [C-5][C-15] |
| "文件" | 文件（**项**） | ——（注册表里没有对应物） | 同上 |
| "数据本身" | 文件内容（**项**） | **值（属性）** | `Get-ItemProperty` / `Set-ItemProperty` [C-11][C-12][S21] |

第三行是整章的分水岭。在文件系统里，你要的数据就是"项"本身（文件）；在注册表里，你要的数据**不是项，是挂在项上的属性**。所以"同一个路径，为什么换成注册表就要改命令"这个问题，答案只在这一行。

> [!tip] 大白话
> 把注册表的键想成**文件夹**，把值想成**贴在文件夹封面上的标签页**。文件夹本身是一个"东西"（项），标签不是——**标签是文件夹的一个属性**。
> 所以你在资源管理器里找文件夹用的那套办法（进目录、翻下一层），放在注册表上只能找到"文件夹"，找不到"标签"。要看标签，得专门说一句"我要看这个文件夹的属性"——这就是 `Get-ItemProperty` 干的事。

#### 4.1.3 三种路径写法

同一个位置可以有不同写法。本章会一直用到这三种 [C-5][C-11]：

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：切换位置本身不改动数据；官方未说明

```powershell
# 写法一：文件系统盘符（第一章的内容）
Set-Location C:\Test

# 写法二：注册表盘符。HKLM: 映射 HKEY_LOCAL_MACHINE，HKCU: 映射 HKEY_CURRENT_USER
Set-Location HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion

# 写法三（备用）：不依赖 HKLM: 驱动器的等价写法
Get-ItemProperty -Path Registry::HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion
```

第三种写法本章**只作为"备用写法"列在这里**，它的提供一个程序全名语法不展开——你只要知道"`HKLM:` 那种写法还有一条不用盘符的等价写法"就够了 [C-11]。用得上的位置是 4.3.6。

### 4.2 文件系统常用操作清单

这一节把第一章那些 cmd 命令，换成 PowerShell 语境下的写法。凡是两版行为不同的，命令块会写明版本。

#### 4.2.1 列目录：`Get-ChildItem` 与 `-Force`

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：无需管理员

```powershell
# 列一个目录（别名 dir / gci，敲 dir 也行）
Get-ChildItem -Path C:\Test

# 含隐藏项与系统项：默认不显示，要加 -Force
Get-ChildItem -Path C:\Test -Force
```

对应第一章 1.8 那条 `dir /a`。[C-9] 里有一条容易误解的提醒：`-Force` 只是让 PowerShell **把隐藏/系统项也列出来**，它**不会替代安全限制**——没权限看到的东西，加上 `-Force` 也不会变成看得到 [C-9]。

#### 4.2.2 递归：官方推荐的那条写法

第一章 1.8 讲过 `dir` 的星号通配符会走短名映射，是误删风险的来源 [A2][A12]。在 PowerShell 里换个命令，但同类风险换了个形式出现。

> [!warning] 不要用 `-Path` 搭配 `-Recurse`（官方不建议）
> 官方明确说：**不建议把 `-Path` 与 `-Recurse` 一起用**。官方给出的安全写法是——用 `-LiteralPath` 指定目标目录，再用 `-Filter`（或 `-Include`）指定匹配模式 [C-9]。
>
> 官方在这一页**没有解释**这条建议的内部机制，本章也不展开（按第三章 3.5 的降维口径：内部机制不解释，直接给结论 + 一条安全写法）。你要做的只有一件事：**把 `-Path` 换成 `-LiteralPath`，把匹配范围交给 `-Filter`。**

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：无需管理员

```powershell
# 官方不建议的写法：-Path 与 -Recurse 一起用
Get-ChildItem -Path C:\Test -Recurse

# 官方推荐的写法：-LiteralPath 指定目录，-Filter 指定模式
Get-ChildItem -LiteralPath C:\Test -Recurse -Filter *.log
```

#### 4.2.3 切换位置：`Set-Location`

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 切到文件系统目录（别名 cd / chdir）
Set-Location C:\Test

# 切到任何 Provider 的路径：注册表、证书、环境变量都行
Set-Location HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion
Set-Location Cert:\
Set-Location Env:\

# 驱动器名不带反斜杠（C:）= 恢复到该盘“当前目录”，不是根目录
Set-Location C:
```

最后一行要单独说一句，因为它正是第一章 1.2.5 那个坑的 PowerShell 版：官方说明，驱动器名**不带反斜杠**时（如 `C:`）表示"恢复到该驱动器的**当前目录**" [C-10]。也就是说，`C:` 和 `C:\` 在 PowerShell 里同样不是一回事——`C:\` 是根目录，`C:` 是"C 盘上次停在哪"。第一章那个"`C:tmp.txt` ≠ `C:\tmp.txt`"的直觉，在这里原样适用 [A2]。

还有一条官方说明值得知道：PowerShell 的"当前目录"是**每个 runspace 独立**的，与 `[System.Environment]::CurrentDirectory` 不是同一个东西 [C-10]。按本笔记的降维口径压缩成一句话：**在 PowerShell 里 `cd` 只影响 PowerShell 自己，不影响你在脚本里调用的程序**。

#### 4.2.4 位置历史：`cd -` 与 `cd +`

来回在两个目录之间跳，每次都敲全路径很烦。PowerShell 有一条捷径，但它有版本门槛。

> [!note] `cd -` / `cd +` 仅 PowerShell 6.2+（含 7）可用，5.1 会报错
> 官方说明：从 **PowerShell 6.2** 起，`Set-Location -Path -` 与 `Set-Location -Path +`（最短写法就是 `cd -` / `cd +`）可以在**最近 20 个位置**的历史中前后导航 [C-10]。
>
> 请务必盯住版本：**这是 6.2 及以上版本（本章标注里的 `7`）才有的功能，5.1 上执行会报错**。这和第三章 3.8 那四项版本差异是同一类问题——写法本身没错，是版本不够。搞不清自己在哪个版本里，先敲 `$PSVersionTable`。

> 环境：PowerShell ｜ 版本：7（5.1 不可用）｜ 权限：官方未说明

```powershell
# 在最近 20 个位置的历史中前后导航（仅 PowerShell 6.2+/7）
cd -
cd +
```

#### 4.2.5 新建目录：`New-Item`

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 建目录（-ItemType 要写明是 Directory）
New-Item -Path "C:\" -Name "Logfiles" -ItemType "Directory"

# 同一个 New-Item，换成注册表盘符就是建键（4.3.4 展开）
New-Item -Path "HKCU:\Software\DemoApp"
```

`-ItemType` 要写明是 `Directory`，是因为**同一条 `New-Item` 还能建文件、建注册表键、建别名**——不写清楚它不知道你要建哪一种 [C-5][C-15]。第二行那个"换成盘符就换了个世界"的写法，是 4.3.4 的主角。

#### 4.2.6 看看有哪些"盘"：`Get-PSDrive`

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：无需管理员

```powershell
# 列出 PowerShell 认识的所有驱动器，包含 Provider 驱动器
Get-PSDrive
```

第三章 3.5.5 已经说明过它的特殊性：`Get-PSDrive` 能看到 `New-PSDrive` 创建的**会话级驱动器**，而 `net use`、`[System.IO.DriveInfo]::GetDrives()`、`Get-CimInstance` **都看不到它们** [C-13]。所以排查"这个盘怎么突然不见了"时，先分清你问的是哪一个"盘"。

### 4.3 注册表常用操作清单

**动手之前请把第二章 2.7 读完。** 本节涉及修改的示例全部落在**自建键**上，请照着做。

#### 4.3.1 读值：`Get-ItemProperty` 与 `Get-ItemPropertyValue`

> 环境：PowerShell ｜ 版本：5.1 & 7（`Get-ItemPropertyValue` 需 **PowerShell 5.0 起**）｜ 权限：官方未说明

```powershell
# 读一个指定名称的值
Get-ItemProperty -Path HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion -Name ProgramFilesDir

# 只把指定属性的值取出来（PowerShell 5.0 起）
Get-ItemPropertyValue -Path HKLM:\SOFTWARE\Microsoft\Wbem -Name BUILD

# 看子项，并排除以 D 开头的那几个
Get-ChildItem -Path HKLM:\HARDWARE -Exclude D*
```

第一条是官方的成例，它依赖映射到 `HKLM` 的 `HKLM:` 驱动器，官方同时说明也可以改用 4.3.6 的备用写法 [S22]；后两条出自注册表提供程序的说明页 [S21]。

两条命令的差别就在名字里：**`Get-ItemProperty` 给你一整个"带属性的对象"**（你要从里面把想要的那格点出来），**`Get-ItemPropertyValue` 直接把那一格的值丢给你** [S21]。只看一个值的时候，后者更省事。

#### 4.3.2 四个看命令的分工（这一节要背下来）

读注册表时有四条命令长得非常像，用途却完全不同 [S21][S22]：

| 命令 | 它看的是 | 在注册表里能看到什么 |
|---|---|---|
| `Get-ChildItem` | **子项**（下一层） | 这个键下面的**键**；**不显示父键自身的属性** |
| `Get-Item` | **键本身及其属性** | 这个键自己的信息，**仍然不是它的值** |
| `Get-ItemProperty` | **值** | 键上挂着的值 |
| `Get-ItemPropertyValue` | **值中指定的那一个** | 只把你要的那个值取出来 |

> [!warning] 注册表的"值"，用 `Get-Item` 或 `Get-ChildItem` 看不到
> 这是 4.1.2 那句话的直接后果：**值不是项，而是键的属性** [C-11][C-12]。所以在 PowerShell 里"看不到某个值"，十有八九不是它不存在，而是**你用了看"项"的命令**。换成 `Get-ItemProperty` 立刻就能看到 [C-11][C-12][S21]。
>
> 第二章 2.5 讲过"找不到键时先怀疑视图"（32 位 / 64 位）[S20]；这里补上第二种"找不到"：**键找到了、值却说没有**，先怀疑命令用错了族。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 四条命令指向同一个键，看出来的东西不一样
Get-ChildItem -Path HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion
# 只看下一层的子项（键）
Get-Item -Path HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion
# 看这个键本身，仍然看不到它的值
Get-ItemProperty -Path HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion -Name ProgramFilesDir
# 看值（这里指定了一个）
Get-ItemPropertyValue -Path HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion -Name ProgramFilesDir
# 只要这个值
```

> [!tip] 大白话
> 把这四条命令想成四种问法，问的是**同一个地址**：
> - `Get-ChildItem` = "**这层楼还有哪些房间？**"（只看下一层）
> - `Get-Item` = "**这个房间本身是什么样？**"（看门牌信息，不看房里贴了什么）
> - `Get-ItemProperty` = "**这个房间门上贴的标签都有哪些？**"（看值）
> - `Get-ItemPropertyValue` = "**只念'营业时间'那张标签给我听。**"（只要一个值）
> 问错问法，得到的当然不是你想听的东西。

#### 4.3.3 写值：`Set-ItemProperty` 与那个必须显式写的 `-Type`

> [!warning] `-Type` 默认是 `String`（REG_SZ），写数字型值必须显式指定
> `Set-ItemProperty` 的动态参数 `-Type` 决定数据类型，**默认值为 `String`（也就是 `REG_SZ`）** [S21]。所以**写数字型的值时，必须显式写出 `DWord` / `QWord`**，否则值会被写成字符串——表面上看"值写进去了"，但类型错了，程序读到的就不是数字 [S21][C-12]。
>
> 可选值有：`ExpandString`、`Binary`、`DWord`、`MultiString`、`QWord`、`Unknown`（表示不受支持的类型，如 `REG_RESOURCE_LIST`）[S21]。回看第二章 2.4.4 那张"同一套类型的三副面孔"表：这里的 `DWord` 就是 `REG_DWORD`、就是 regedit 里的"DWORD (32 位) 值" [S5][S6]——**三副面孔，同一个类型**。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 官方示例（写在 HKLM 下的自建键路径）：不写 -Type
Set-ItemProperty -Path "HKLM:\Software\ContosoCompany" -Name "NoOfEmployees" -Value 823

# 想写一个 32 位数字值，必须显式指定 -Type DWord
Set-ItemProperty -Path "HKCU:\Software\Demo" -Name "NoOfEmployees" -Value 823 -Type DWord
```

第一行是官方的示例原文 [S21]。但请看上面那条警告：它没写 `-Type`，而 `-Type` 默认为 `String`——**照抄这一行，你得到的是一个字符串值，不是数字值**。所以本章统一写成第二行那种形式：**只要是数字，就显式写 `-Type DWord`（或 `QWord`）** [S21][C-12]。另外，练习时把路径换成 `HKCU:` 下的自建键，别照着往 `HKLM:\Software` 下写。

#### 4.3.4 新建键：还是 `New-Item`

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 在注册表里建键：用法和 4.2.5 建目录完全一样
New-Item -Path "HKCU:\Software\DemoApp"
```

这就是 4.1.1 那句话最直观的样子：同一条 `New-Item`，`C:` 上是建目录，`HKCU:` 上是建键 [C-5][C-15]。

#### 4.3.5 删值、删键、清空：三条命令三种范围

> [!warning] 三条命令，三种范围，别搞混
> - **`Remove-ItemProperty`**：**只删值**，键还在 [S21]；
> - **`Remove-Item`**：删的是**键本身**（相当于把"文件夹"一起删）；**当这个键里还有子项时，它默认会弹确认框**，只有加 `-Recurse` 才不提示 [S21]；
> - **`Clear-Item`**：把这个键的**所有值清空**，但**保留键本身** [S21]。
>
> 对回第二章 2.8.3 的 `reg delete`：`/va` 是"删除指定键中的所有值但不删除其中的子项"，和这里的 `Clear-Item` 是同一件事的两个入口 [S11][S21]。删错一个词，后果完全不同。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 只删一个值，键还在
Remove-ItemProperty -Path "HKCU:\Software\Demo" -Name "NoOfEmployees"

# 清空这个键的所有值，但保留键本身
Clear-Item -Path "HKCU:\Software\Demo"

# 删掉键本身；键里还有子项时必须加 -Recurse 才不弹确认
Remove-Item -Path "HKCU:\Software\DemoApp" -Recurse
```

#### 4.3.6 备用写法：`Registry::`

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 不依赖 HKLM: 驱动器的等价写法
Get-ItemProperty -Path Registry::HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion
```

官方在注册表提供程序的说明里给出了这个等价形式：注册表的驱动器是 `HKLM:`（映射 `HKEY_LOCAL_MACHINE`）与 `HKCU:`（映射 `HKEY_CURRENT_USER`），也可以用上面这种提供程序全名语法 [S21][C-11]。本章只把它作为**备用写法**列在这里——正如 4.1.3 说的，提供程序全名语法的细节本章不展开。

#### 4.3.7 用 PowerShell 改注册表的安全流程

把第二章 2.7 的主路径和本节命令拼起来，就是本章要你形成条件反射的一套动作 [S18][S13][S14]：

1. **先备份**：用 `reg export` 把要改的键导出成 `.reg`（第二章 2.7.3 的主路径）；
2. **读现状**：`Get-ItemProperty` 确认它现在是什么值；
3. **改值**：`Set-ItemProperty`，数字记得带 `-Type DWord` / `QWord`；
4. **复核**：再用 `Get-ItemProperty` 读一次，确认改对了；
5. **需要时回滚**：`reg import` 把第 1 步的 `.reg` 导回去。

请注意这套流程里的一个"分工"：**PowerShell 负责"改"，`reg.exe` 负责"保命"**。这不是随手选的——本轮素材里，PowerShell 侧**没有**官方文档化的"导出注册表"cmdlet，而 `reg export` / `reg import` 的用法、`.reg` 扩展名要求、返回值语义（0 = 成功 / 1 = 失败）都是官方写明的 [S13][S14]，regedit 界面的导出/导入步骤也是官方给得最完整的一条 [S18]。所以在 PowerShell 里改注册表时，备份这一步直接调 `reg export`。完整演练见 4.5。

### 4.4 三种执行方式对照与选型：regedit / reg.exe / PowerShell

#### 4.4.1 官方列举过的那些手段

官方在讲"如何修改注册表"时，列出的手段有：注册表编辑器（Regedit.exe 或 Regedt32.exe）、组策略、系统策略、注册表（`.reg`）文件、Windows Script Host 脚本、WMI（含 Wmic.exe），以及控制台注册表工具 Reg.exe [S6]。

本章只对照其中日常最常用的三个：**regedit（界面）、reg.exe（命令）、PowerShell**。它们不是三种不同的注册表，而是**同一份注册表的三个入口**。

#### 4.4.2 三者各自的强项

- **regedit** 的强项是"**看得见再改**"：官方步骤最完整的那条备份路径就在它的「文件」>「导出 / 导入」里 [S18]；
- **reg.exe** 的强项是"**命令本身就是记录**"：可复制、可贴进批处理、可留档 [S9]；
- **PowerShell** 的强项是"**脚本化**"：用 `HKLM:` / `HKCU:` 驱动器，和文件系统共用同一套命令，天然适合跟 4.2 那些操作写进同一段脚本 [C-5][S21]。

#### 4.4.3 选型表

| | regedit（界面） | reg.exe（命令） | PowerShell |
|---|---|---|---|
| 是否可视化 | **是**（树 + 键值列表） | 否 | 否 |
| 是否可脚本化 | 否（界面操作） | **是** | **是** |
| 备份方式 | 「文件」>「导出」成 `.reg`；还原「文件」>「导入」[S18] | `reg export` / `reg save` 出备份，还原用 `reg import` / `reg restore` [S13][S14][S15][S16] | 借用同一台机器上的 `reg export` / `reg save`（PowerShell 本身没有官方文档化的"导出注册表"cmdlet，本轮素材未命中） |
| 提权要求 | 官方明写导出与导入**会有管理员密码或确认提示** [S18] | **官方未说明** [S13]–[S16] | **官方未说明**（写注册表值的提权要求本轮素材未命中） |

表格按大纲要求处理：**"提权要求"这一列只填官方明确写出的**，其余一律写"官方未说明"，不替你推断 [S13]–[S16]。

表外还有一条官方明确写出的免提权路径，第二章 2.9.4 讲过：因为 HKCR 是 `HKCU\Software\Classes` 与 `HKLM\Software\Classes` 的组合，**可以把自定义的 verb 注册在 `HKEY_CURRENT_USER\Software\Classes` 下**，官方点明这么做"**主要好处是不需要提升权限**" [S25]。

> [!tip] 大白话：三个门，同一间房
> 把注册表想成**一间上了锁的档案室**：`regedit` 是**带玻璃的推拉门**（你能隔窗看清楚再进去动手），`reg.exe` 是**投递口**（塞纸条进去，动作可复制、可留底），PowerShell 是**和隔壁仓库共用的那条传送带**（同一套规则，能从文件那边一路推过来）。
> 三扇门通向的是**同一间房**，不是三间一样的房——你在 regedit 里改的，`reg query` 和 `Get-ItemProperty` 立刻就能查到。

#### 4.4.4 官方在这件事上的统一态度

不管用哪个入口，官方的态度是一致的：**优先用 Windows 用户界面或组策略更改系统设置**，直接编辑注册表是**最后手段** [S6][S8]。

第二章 2.7 已经把两条官方原文和它们的语气强度写全了，这里只重复关键的两点，不合成一个新版本：`reg` 命令页用的是 **Caution 级**警告，"除非没有替代项，否则不要直接编辑注册表" [S8]；KB256986 用的是 **Warning 级**，说错误修改"可能需要重新安装操作系统才能解决。Microsoft 不能保证可以解决这些问题"，**同时承认"编辑注册表有时可能是解决产品问题的最佳方法"** [S6]。

所以本章的结论不是"三种方式都别用"，而是那两句一直没变的话：**能用设置界面或组策略改的，就别绕到注册表来**；**真要改，先备份** [S6][S8]。

### 4.5 一条端到端示例：改一个值 → 验证 → 回滚

#### 4.5.1 场景

假设你为自己的小工具建了一个配置键 `HKCU\Software\DemoApp`，里面有一个 32 位数字值 `RetryCount`（重试次数）。现在要把它从 `3` 改成 `5`，而且**改完要能验证、能回滚**。

> [!warning] 示例只用自建键，绝不使用系统关键键
> 本章出现的注册表**修改**示例（4.3.3 的 `HKCU:\Software\Demo`、4.5 的 `HKCU:\Software\DemoApp`）**全部落在你自己建的键上**，这是刻意的安排。
>
> 练习时请同样对待：**一律用自建键，绝不拿系统关键键做实验**。这里的"系统关键键"包括但不限于 `HKLM\SYSTEM`、`HKLM\SAM`、`HKLM\SOFTWARE\Microsoft` 下的各类路径，以及四个开机自启键 [S19]。第二章 2.7.1 引的那句官方警告——错误修改"可能需要重新安装操作系统才能解决" [S6]——不是客套话。

#### 4.5.2 完整七步

顺序是刻意的：**先备份，再读，再改，再复核，然后才谈回滚**。前四步在下面第一个命令块，后三步在第二个。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明（`reg export` 的管理员要求见第二章 2.7.3）

```powershell
# —— 第 0 步（准备）：建一个专供练习的自建键，并放入初始值 3
New-Item -Path "HKCU:\Software\DemoApp"          # 键已存在时会报错，忽略即可
New-ItemProperty -Path "HKCU:\Software\DemoApp" -Name "RetryCount" -PropertyType DWORD -Value 3
# 新建值用 New-ItemProperty（见第二章 2.8.5 的对照表），-PropertyType 的写法同第一章 1.2.8

# —— 第 1 步：备份。用第二章 2.7.3 的主路径，先导出成 .reg
# 这是 reg.exe 的命令，在 PowerShell 窗口里可以直接敲
reg export "HKCU\Software\DemoApp" DemoAppBkUp.reg /y
# 返回值语义：0 = 成功 / 1 = 失败

# —— 第 2 步：读现状。先确认它现在是什么
Get-ItemProperty -Path "HKCU:\Software\DemoApp" -Name "RetryCount"
# 输出里能看到：RetryCount : 3

# —— 第 3 步：改值。数字型值必须显式写 -Type DWord
Set-ItemProperty -Path "HKCU:\Software\DemoApp" -Name "RetryCount" -Value 5 -Type DWord

# —— 第 4 步：复核。再读一次，确认真的改成 5 了
Get-ItemProperty -Path "HKCU:\Software\DemoApp" -Name "RetryCount"
# 输出里能看到：RetryCount : 5
```

**第 5 步：改错了怎么办？** 分两种情况：

- **只是值写错了，键结构没动**：按第 6 步把备份导回去，一切复原——这正是第 1 步先导出 `.reg` 的意义 [S18][S14]。
- **连键都删了、或者改了不止一个地方**：`.reg` 导入会把导出时记录的内容写回去；如果改动范围超出了当初导出的那个键，请按第二章 2.7 的层级判断——**按键级备份**只能救回你导出的那个键，**整机级**才谈得上"备份了整个注册表" [S6][S18]。所以正确的做法是：**动哪个键，就先导出哪个键**。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# —— 第 6 步：回滚。把第 1 步导出的 .reg 导入回去
reg import DemoAppBkUp.reg

# 导入完再读一次，确认已经变回 3
Get-ItemProperty -Path "HKCU:\Software\DemoApp" -Name "RetryCount"

# —— 第 7 步：清理演示键（键里若有子项，必须加 -Recurse 才不弹确认）
Remove-Item -Path "HKCU:\Software\DemoApp" -Recurse
```

第 7 步用的是 4.3.5 讲过的 `Remove-Item` 语义：**它在键里还有子项时默认会弹确认框，加 `-Recurse` 才免提示** [S21]。演示键干净了，练习才算收尾。

#### 4.5.3 同一场景的 regedit 版与 reg.exe 版

上面那件事，换另外两个入口做是同一个结果。这正好回答本章开头那个问题：三个入口，一件事。

**regedit 版（界面）** [S18]：

> 环境：regedit（注册表编辑器界面）｜ 版本：全版本适用 ｜ 权限：官方明写会有管理员密码或确认提示 [S18]

1. 「开始」→ 搜索 `regedit.exe` → 回车；**若有管理员密码或确认提示，需提供**；
2. 在左侧树里定位到 `HKEY_CURRENT_USER\Software\DemoApp`；
3. **备份**：「文件」>「导出」→ 选择保存位置、输入文件名 →「保存」；
4. **改值**：双击右边的 `RetryCount` → 把 `3` 改成 `5` →「确定」；
5. **回滚**：「文件」>「导入」→ 选中刚才那个 `.reg` →「打开」。

**reg.exe 版（命令行）** [S9][S10][S11][S13][S14]：

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 备份（第 1 步）
reg export "HKCU\Software\DemoApp" DemoAppBkUp.reg /y

:: 改值（第 3 步）—— 类型显式写成 REG_DWORD
reg add "HKCU\Software\DemoApp" /v RetryCount /t REG_DWORD /d 5 /f

:: 复核（第 4 步）
reg query "HKCU\Software\DemoApp" /v RetryCount

:: 回滚（第 6 步）
reg import DemoAppBkUp.reg

:: 清理（第 7 步）
reg delete "HKCU\Software\DemoApp" /f
```

三种写法对照成一张表，差别就一目了然：

| 同一个动作 | regedit | reg.exe | PowerShell |
|---|---|---|---|
| 备份 | 「文件」>「导出」[S18] | `reg export` [S13] | 在 PowerShell 里调 `reg export` |
| 读值 | 双击打开看 | `reg query /v` [S9] | `Get-ItemProperty` [C-11][S22] |
| 改值 | 双击修改 | `reg add /t REG_DWORD` [S10] | `Set-ItemProperty ... -Type DWord` [C-12][S21] |
| 删键 | 右键删除 | `reg delete` [S11] | `Remove-Item -Recurse` [S21] |
| 回滚 | 「文件」>「导入」[S18] | `reg import` [S14] | 在 PowerShell 里调 `reg import` |

三条路改的是**同一份注册表**：你在 regedit 里双击改完，回到 PowerShell 敲一次 `Get-ItemProperty`，看到的立刻是新值 [C-11][S22]。

### 本章小结

> [!summary] 小结
> - **为什么能"一件两事"**：FileSystem 与 Registry 是同一套 Provider 模型下的两个"盘"，同一批 cmdlet 作用在任何盘上 [C-5]；`New-Item` 在 `C:` 上建目录、在 `HKCU:` 上建键，用法相同 [C-5][C-15]
> - **根源性的不对称**：文件系统里的是**项**（文件 / 目录），注册表里的是**值**，而"值"在 PowerShell 里是**键的属性**——所以看"项"的 `Get-Item` / `Get-ChildItem` **看不到值**，必须用 `Get-ItemProperty` / `Set-ItemProperty` 这一族 [C-11][C-12][S21]
> - **文件系统侧**：`Get-ChildItem` 默认不显示隐藏项、要加 `-Force`（但 `-Force` 不替代安全限制）[C-9]；递归要用 `-LiteralPath` + `-Filter`，**官方不建议 `-Path` 配 `-Recurse`** [C-9]；`Set-Location` 可切任何 Provider 路径，`C:`（不带反斜杠）表示该盘当前目录 [C-10]；**`cd -` / `cd +` 仅 6.2+（含 7）可用，5.1 报错** [C-10]；`Get-PSDrive` 是唯一能看到会话级驱动器的一条 [C-13]
> - **注册表侧**：四条命令分工是"看子项 / 看键本身 / 看值 / 只取一个值" [S21][S22]；`Set-ItemProperty` 的 **`-Type` 默认是 `String`（REG_SZ）**，数字必须显式写 `DWord` / `QWord` [S21][C-12]；`Remove-ItemProperty` 只删值、`Remove-Item` 删键（含子项时默认弹确认，`-Recurse` 免提示）、`Clear-Item` 清空值但保留键 [S21]
> - **三个入口**：regedit / reg.exe / PowerShell 是同一份注册表的三个门；三者都改同一份数据 [S6][S9][S21]；**提权要求这一列只有 regedit 的导出/导入与 `HKCU\Software\Classes` 免提权有官方依据，其余官方未说明** [S18][S25]
> - **官方统一态度**：优先用 Windows 用户界面或组策略改系统设置，直接改注册表是最后手段 [S6][S8]
> - **安全流程**：改注册表 = **先 `reg export` 备份 → 读现状 → 改（显式 `-Type`）→ 复核 → 需要时 `reg import` 回滚**；在 PowerShell 里改注册表，备份这一步交给 `reg.exe` [S13][S14][S18]
> - **官方未说明的位置**（本章一律不推断）：`Set-Location`、`New-Item`（建目录 / 建键）、`Get-ItemProperty` / `Get-ItemPropertyValue` / `Get-ChildItem`（注册表侧）、`Set-ItemProperty`、`Remove-Item`、`Remove-ItemProperty`、`Clear-Item` 的**管理员权限要求**，以及 `reg export / import / save / restore` 的提权要求，均**官方未说明** [S13]–[S16]

### 5.2 九个跨方向易错点回顾

这九条是素材在三个方向之间对比时发现的**口径冲突**：社区流传的说法和官方原文不一致，或者两份官方资料本身就不一致。它们不是"冷知识"，而是**照着错的做会出事**的地方。

| # | 易错点（常见错误认知） | 正确口径 | 详见 |
|---|---|---|---|
| 5.2.1 | 以为**系统还原**是注册表回滚的标准做法 | 回滚**主路径 = 导出 `.reg` → 需要时导入还原**（官方覆盖 Win11）；系统还原**只作整机级兜底**，且官方那页的版本声明明显滞后（正文说仅 Win7/Vista/XP 受支持，另一页覆盖 Win11 却完全不提它） | 第 2 章 2.7.6 |
| 5.2.2 | 把"导出 `HKLM\Software` 下的一个键"当成"**备份了整个注册表**" | **按键级备份** = 导出 `.reg`（只保住导出的那个键）；**整机级备份** = 备份"系统状态"（保住整台机器）。**动哪个键，就先导出哪个键** | 第 2 章 2.7.5 |
| 5.2.3 | 以为 `NTUSER.DAT` 有一个可以照抄的**磁盘路径** | 两份官方资料给的路径**不一致**（`%SystemRoot%\System32\Config` vs `%SystemRoot%\Profiles\Username`），而且**都没提现代布局**。本笔记只用"用户配置文件目录"表述，**不写死路径** | 第 2 章 2.3.4 |
| 5.2.4 | 以为 **`Program Files (x86)` 一定存在** | 它**只存在于 64 位系统**；32 位系统上 `FOLDERID_ProgramFiles` 与 `FOLDERID_ProgramFilesX86` 指向**同一个路径**。官方同页对该默认路径的表述前后不一致，本笔记只采用"64 位系统上为 `Program Files (x86)`"这一结论 | 第 1 章 1.4.4 |
| 5.2.5 | 把 `mklink /j` 叫成"**目录硬链接**" | 官方参数表的定义是"**目录联接**"（junction）。硬链接**根本不能指向目录**，所以"目录硬链接"这个说法在概念上就站不住 | 第 1 章 1.6.2 |
| 5.2.6 | 以为有 `mklink /F` 这个参数 | 官方参数表里只有 `/d`、`/h`、`/j`、`/?` 四种。`/F` 是网上的错误信息，敲下去只会得到"参数无效" | 第 1 章 1.6.2 |
| 5.2.7 | 把**执行策略**当成一种"安全设置"，甚至为了"更安全"调到最严 | 官方明说**它不是安全边界**，而是**防误运行的便利机制**——直接在命令行粘贴脚本内容就能绕过。所以：别为了"看起来安全"调到最严，也别因为它"不是安全"就随手关掉 | 第 3 章 3.6.1 |
| 5.2.8 | 想找一个"**改一个设置就好**"的编码开关 | **不存在"5.1 的默认编码"这句话**。编码是**三条独立通道**：① 脚本源码编码 ② `-Encoding` 参数与各 cmdlet 默认值 ③ 控制台与对外部程序编码。哪条漏了修哪条——5.1 里同一个版本不同 cmdlet 写出的编码本身就各不相同 | 第 3 章 3.7.3 |
| 5.2.9 | 以为"安全的做法"是 `AllSigned`，`RemoteSigned` 只是折中 | **默认与推荐都是 `RemoteSigned`**；`AllSigned` 只作为一种"可选更严档位"。另外 **`Undefined` 不等于"没有限制"**——各级作用域都是 `Undefined` 时，客户端上的实际效果是 `Restricted` | 第 3 章 3.6.4 |

> [!tip] 大白话：这九条为什么值得单独一页
> 把它们想成**九块"看起来是路、其实是墙"的牌子**。前四章一路写下来，每块牌子都立在它该在的位置上；但真动手时你不会重读全书，只会在某一处想起"好像是这么做的"——这一页就是把那九块牌子搬到门口，出门前看一眼。
> 判断标准很简单：**只要你的做法和"正确口径"那一列相反，就停下来翻一下"详见"**。

### 5.4 接着往下练的建议

这张笔记里的命令，看完不等于会。剩下三件事，按顺序做一遍，基本就稳了。

#### 5.4.1 在自建目录与自建键上练，不碰系统关键键

- **文件系统侧**：在 `C:\Test` 这类自己建的目录里练 `dir` / `attrib` / `icacls` / `robocopy`，不要拿 `C:\Windows`、`Program Files` 做实验（1.4.3、1.9.2）。
- **注册表侧**：所有**修改**类示例都应落在你自己建的键上——本笔记用的是 `HKCU:\Software\Demo` 和 `HKCU:\Software\DemoApp`（4.3.3、4.5.1）。"系统关键键"包括但不限于 `HKLM\SYSTEM`、`HKLM\SAM`、`HKLM\SOFTWARE\Microsoft` 下的各类路径，以及四个开机自启键 [S19]。
- 第二章 2.7.1 引的那句官方警告——错误修改"**可能需要重新安装操作系统才能解决。Microsoft 不能保证可以解决这些问题**" [S6]——是这段纪律的全部理由。

#### 5.4.2 改注册表前先导出 `.reg`，练成条件反射

这一条要在**动手之前就完成**，而不是出事之后再想：

1. 先 `reg export "<要改的键>" <文件名>.reg /y`（或走 regedit「文件」>「导出」）——这是官方覆盖范围最广的一条主路径，覆盖 Windows 11 [S18]；
2. 再 `Get-ItemProperty` 读一次现状；
3. 才动手改（写数字时显式 `-Type DWord` / `QWord`）；
4. 改完 `Get-ItemProperty` 复核一次；
5. 需要回滚时 `reg import <文件名>.reg`。

这套流程的完整版在 4.3.7 与 4.5.2，三个入口（regedit / reg.exe / PowerShell）的对照在 4.5.3。**记住那个分工：PowerShell 负责"改"，`reg.exe` 负责"保命"**——PowerShell 侧没有官方文档化的"导出注册表"cmdlet [S13][S14]。

#### 5.4.3 用 `Get-Help` / `Get-Command` / `Get-Member` 自己探索，不依赖记忆

本笔记只能覆盖到你最可能用到的那一批命令；剩下的靠这三个命令自己挖出来，顺序是官方的推荐顺序 [C-2][C-6]：

1. **`Get-Command`** —— "有没有这条命令？"（配 `-Verb` / `-Noun` 过滤更快）；
2. **`Get-Help`** —— "它怎么用、参数是什么？"（帮助文件没装时先 `Update-Help`，注意 3.4.4 的两条硬限制）；
3. **`Get-Member`** —— "它返回的东西有哪些属性和方法？"（这是对象管道最省事的地方，3.1）。

再加一条：不记得自己在哪个版本里，先敲 `$PSVersionTable`（3.3.3）——本笔记的四项版本差异（默认编码、配置文件路径、`PSModulePath`、`Update-Help` 权限）和 `cd -` / `cd +`，全都拴在 5.1 与 7 的差别上（3.8.5）。

### 本章小结

> [!summary] 小结
> - **三张速查表**：文件系统命令表保留"环境 / 版本 / 权限"三元组 [A5]–[A21]；注册表命令表按 **regedit / reg.exe / PowerShell 三列对照** [S9]–[S21]；PowerShell 命令表分**探索 / 帮助 / 执行策略 / 编码**四组 [C-1]–[C-15]。**表内命令全部来自前四章，无新增**
> - **九个跨方向易错点**：系统还原不是回滚主路径、按键级 ≠ 整机级备份、HKCU 磁盘位置官方两说、`Program Files (x86)` 只存在于 64 位、`mklink /j` 是"目录联接"、`mklink /F` 不存在、执行策略不是安全边界、编码是三条独立通道、默认是 `RemoteSigned` 而非 `AllSigned`
> - **绝大多数"要不要管理员"官方都没写**：全笔记里只有 `diskpart` [A15]、`fsutil` [A18]、regedit 导出/导入 [S18] 三处有明说的提权要求，加 `HKCU\Software\Classes` [S25] 与 `-Scope CurrentUser` [C-3] 两处免提权依据；其余一律"官方未说明"
> - **两类留白要分清**：**"官方未说明"**（官方没写，不等于不用）与**"素材未覆盖所以本笔记不写"**（连现象都没有，如中文用户名 `PSModulePath`、`USRCLASS.DAT`、`RegBack`、`HKCR\*\shell`）；这两类都**不要当成结论使用**
> - **动手三纪律**：在自建目录与自建键上练、改注册表前先导出 `.reg`、用 `Get-Command` → `Get-Help` → `Get-Member` 自己探索

从"数据放在哪"，到"系统和程序怎么配置自己"，再到"怎么用命令批量操作前两者"——这份笔记想留下的不是那几百条命令，而是三样东西：**一套看路径和看键的眼光、一套"先备份再动手"的肌肉记忆、以及一条"这条说法有没有官方依据"的检查习惯**。前面那些表格和清单，都是为这三样东西服务的。

祝你在自己的机器上玩得安心。
