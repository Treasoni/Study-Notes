# Note Updater

用于更新已有笔记，而不是从零生成新笔记。

## 口径核对（先于改写）

- 用户就笔记内容提澄清问题（「有没有 X」「能不能 Y」）时，**回一手来源（`sources/` / 官方原文）与用户的实际场景作答**，不要复述或外推**既有笔记里的既有结论**——你要更新的这篇笔记，本身可能就是待修正对象；你上一轮的结论也可能是错的。
- 对「有没有 / 能不能 / 是不是 / 只有…才…」这类定性结论，落笔前先查证一手来源，并把**作用范围写进句子本身**：说「**本体库**不能转夸克」，不要图省事写成「小雅不能转夸克」（抹掉作用范围的绝对否定，是本类错误的典型形态）。
- 没有来源支撑的数字 / 比例（如「覆盖 85%~90%」）**不写进笔记**；写「以实机为准」，或另立来源件后再回写。

## 配方类内容：只写「文档逐字给出」或「实测得到」的取值

env / config / command 这类**可执行配方**，取值只有两个合法来源：① 官方文档**逐字给出**；② 你自己**实测**得到。两者都没有时，**不要用常识或记忆补一个像样的值**——标「待核」，或回原始载体（源码 / 官方示例 / 容器内实跑输出）取。

- 典型翻车：官方文档只写了字段名、没给示例值，就「想当然」补一个哈希/默认值（曾把文档里的 `scrypt$…` 字段写成 bcrypt `$2b$12$`）。**字段名 ≠ 取值**，缺值宁可留空待核。
- 把文档**转写成派生产物**（docker-compose 片段、示例配置、命令拼接）时，落笔前先做一次**最小实测**（如 `docker compose config`）。**「读文档」不等于「跑得通」**：文档给你字段名，不保证你拼出来的产物能跑；实测不过就改写法，不要拿「文档就是这么写的」当免责。
- 已知高危点（实测确认）：Compose 会把 `$`+字母/下划线当变量插值（`$`+数字反而安全），scrypt 之类含 `$` 的哈希写进 compose 必须逐段写成 `$$`；YAML 引号 / `env_file` / `.env` 都挡不住，只有 `$$` 有效。
- **字段 / 模板旁的自带注释是线索，不是权威取值**：注释常把两个概念混写。曾据 monlor `env` 的 `# webdav用户名为dav，设置密码。默认用户密码：guest/guest_Api789` 的**前半句**，把 WebDAV 的挂载**路径** `/dav` 当成用户名写进笔记，还把独立来源一致给出的正确值 `guest` 反标成「错的」（并配同向 `[!warning]`），直到用户实战反证才纠正。**注释自相矛盾、或与多个独立来源 / 实测冲突时，以后者为准**；注释原文**逐字留档**（不静默删），在旁边解释它为何易误读；**落笔前把整条注释读完**，不取半句。
- **引 `:行号` 前先定位一次**：出处行号会随文件变动漂移，不凭上一轮转录誊抄（曾把注释所在的 `:31` 一律引成字段行 `:32`）；用 `rg -n` 当场取行号再落笔。
- **配置骨架以官方「完整示例文件」逐字段核对，不只抄教程某一节的讲解段**：教程按主题分节，本就不会在一节里把字段给全。曾据官方博客「媒体服务器类型」一节只写 `server.type: FNTV`，漏掉 `port` 与 `server.addr`，读者照配起不来，还以为是自己「不会用」。落笔前拿 `raw` 的 `*.example` / 默认配置本体**逐字段过一遍**，并自问「照这份配能不能跑起来」；**多文件配方里每个代码块必须标注所属文件**（`docker-compose.yml` vs `config.yaml`），不标读者会把两份抄成一个文件。

## Inputs

必须先确认：

- `existing_note_path`: 旧笔记路径，可以在项目工作区或用户指定的 Obsidian vault 中。
- `update_goal`: 更新原因，如版本变化、概念过时、补充案例、修正错误。
- `destination_mode`: `patch-in-place`、`copy-updated` 或 `project-output-only`。
- `moc_path`: 可选，更新后同步 MOC。

## Workflow

1. **先判形态，再读最小上下文**
   - `existing_note_path` 若是**拆分笔记集合**（总览 + 分章文件，工作区可能另有 `chapters/`、`output/` 同名副本），**先一次列齐集合全部成员**（`ls` / `Glob`），通读总览与各章标题 / 小结，得出**本次受影响文件集**，再开始逐文件最小读取与改写。
   - 口径类改动（术语、定性、凭据、结论）**天然横跨多章**：不要「边改边发现还有文件没看」。改动落定后，对集合内**未修改**的成员明说「为什么没动」（如「其措辞不因此口径而错」），对集合外相关笔记（如上游 `chapters/` 与下游 `output/`、vault 副本）登记同步范围。
   - 单文件笔记才只读 frontmatter、目录、疑似过时段落；若用户指定具体段落，只处理该段落。
2. **生成 stale map**
   - 列出：保留、需要更新、需要删除、需要新增。
   - 不直接重写全文。
3. **最小资料收集**
   - 只搜索/读取与 stale map 对应的资料。
   - 每条资料保存 URL、日期、100-200 字摘要。
4. **局部更新**
   - 保留用户原有结构和写作风格。
   - 更新 `updated` frontmatter。
   - 追加 `## 更新记录`，记录日期和变更摘要。
5. **Obsidian 同步**
   - 如果目标在 vault 内，检查双链、标签、MOC。
   - 如提供 `moc_path`，调用 `moc-organizer` 同步索引。
6. **摸底并登记 vault / workspace 漂移**
   - **改拆分子集里的任一章之前**，先跑一次**全量副本比对**（如 `publish_copies.py --check`），摸清**全部**漂移章——漂移是历史累积的，与本次改哪章无关；只查当前章会漏掉其它同名副本（曾只为第 5 章补内容，却一次暴露第 3、4、5 章都在漂移）。
   - 本次改动落在 vault 内时，检查该项目工作区是否留有同名副本（`${WORKSPACE_PATH:-./workspace}/{project_slug}/chapters/`、`output/`）：本次只更新了 vault 一侧，两边**必然**长期漂移。
   - 若该 run 已是 `current_phase: done`，workspace 副本不会再被任何流程更新，而两边文件名相同，极易被误当权威稿。
   - 在 `update_report.md` 里登记「vault 已于 <日期> 更新，workspace 副本停留在 <日期>」，不要把漂移留在沉默里。
   - 不要默认回写 workspace，也不要默认「以 vault 为准」就收工：**先与用户确认同步方向**（vault → workspace，还是反向），方向未定不要动手；再让用户二选一——重跑 note-assembler 同步 workspace，或明确弃用 workspace 副本。
   - 若需把 vault 正文**回灌** workspace（反向同步，项目发布器通常只做单向），落盘前用**未漂移 / 已知正确**的样本做 **byte-exact 往返自证**（提取 → 正向重建 → 与发布件比对），通过后再对漂移章使用；定位「正文尾部」边界用**章末导航块 / 最后一个匹配项**，不要用 `[-k:]` 这类从文件尾数的索引（曾越过章末导航块并踩尾部空白 off-by-one）。

## 写作风格

改写内容时遵循 `.claude/rules/obsidian/note-style.md`（入门优先 + 参考类豁免）：

- 目标是把内容「说得更清楚」，保留原文结构与深度，不做降级改写。
- 原文未解释的关键术语，趁更新补一句大白话；原文是新手向笔记时，新增段落也维持白话风格。
- 若原文是参考 / 速查类笔记，保持精简，不强行加白话铺垫。

## Output Files

默认在同目录生成：

- `update_plan.md`：过时点和更新计划
- `updated_note.md` 或直接 patch 原笔记
- `update_report.md`：更新摘要、来源、未处理风险

## Token Rules

- 不把整篇旧笔记复制进上下文，除非文件很短。
- 不重写未过时段落。
- 搜索结果只保留结构化摘要，不保存网页全文。
