# 小结与下一步

> [!summary] 本章导读
> 前面 04-09 章从两条入口（脚手架改造 / 从零手写）合流成一条渐进路径，把插件「写 → 配 → 验证 → 打包 → 装」整条链路走通了。这一章没有新代码、没有新命令，只做一次完整复盘：收拢全文件增量、命令链、自查清单和下一步方向——卡在哪一步，就翻回哪一章。最后用一个「换工具」清单告诉你：`git_log` 只是第一间房，钥匙（A→C 链路）已经在你手里。

## 1. 全文件清单回顾：从 2 文件到完整工程的每一次增量

整条路线只有 6 次增量，手写文件从 2 个长到 6 个，构建后再产出 `dist/`，终点共 8 个文件[^1][^3]：

| 阶段 | 章节 | 新增/修改 | 文件 |
| --- | --- | --- | --- |
| ① 最小跑通 | 第 05 章 | 新增 2 个 | `src/index.ts` + `dev-cordis.patch.yml` |
| ② 加工具 | 第 06 章 | 新增 1 个 | `src/tools/git-log.ts`；`src/index.ts` 升级为注册中心 |
| ③ 加配置 | 第 07 章 | 不新增 | `src/index.ts` 加 `Config` schema；两份 patch 加 `config` 块 |
| ④ 验证 | 第 08 章 | 不新增 | 验证命令链（web / dump / headless） |
| ⑤ 工程化 | 第 09 章 | 新增 3 个 | `package.json` + `tsconfig.json` + `cordis.patch.yml`；build 产出 `dist/` |
| ⑥ 打包安装 | 第 09 章 | 不新增 | `pnpm pack` → `pnpm dsh plugin add` |

起点是最小 2 文件骨架[^1]。第 ⑤ 步定型双 patch：`dev-cordis.patch.yml`（开发期绝对路径）与 `cordis.patch.yml`（bundle，`name = dsh-git-log-plugin`）。文件归属沿用 [[01-插件开发核心-从apply到system-prompt|插件开发核心]]：工具进 `src/tools/`，`src/index.ts` 做注册中心。

## 2. 一条命令链串起来：`pnpm dsh web --patch` → `--dump-config` → headless → `pnpm pack` → `pnpm dsh plugin add`

从开发到交付，五条命令按顺序就是整条流水线[^3]：

| 顺序 | 命令 | 作用 | 章节 |
| --- | --- | --- | --- |
| 1 | `pnpm dsh web --patch ./git-log-plugin/dev-cordis.patch.yml` | 开发期加载，看 `[git-log-plugin] plugin loaded!` | 第 05 章 |
| 2 | `pnpm dsh --profile demo --dump-config` | 分层打印合并后配置 | 第 08 章 |
| 3 | `pnpm dsh --profile headless "<task>"` | 一次性任务端到端（退出码 0/1） | 第 08 章 |
| 4 | `pnpm pack` | 打成 tarball | 第 09 章 |
| 5 | `pnpm dsh plugin --profile demo add <tarball>` | 装进 profile 并对账 | 第 09 章 |

`pnpm dsh ...` 命令（第 1/2/3/5 条）在 dsh 源码仓库根目录执行，只有第 4 条 `pnpm pack` 在插件工程目录执行；打包安装机制来自官方 bundle/profile 文档。

> [!tip] 大白话
> 把全篇压成一张「从零到装好」的路线图：先 2 个文件把插件点亮（第 05 章），再长出手脚（工具）、装上旋钮（配置）、验过合格（第 08 章）、搭好流水线（第 09 章）、装箱送货（第 09 章）。卡在哪一步，就翻回哪一章——§1 的表格就是索引。

> [!note] 这在 Claude Code 里相当于
> 一篇插件的「从模板 starter 到 npm 发布」完整 SOP 回顾：入口初始化（apply）→ 注册工具 → 配置校验（schema）→ 本地验证 → 工程化打包 → 发布安装，每一步都有 Claude Code 插件开发现实可对照。

## 3. 自查清单（改别人工具 / 重写前对着过一遍）

动手改写前，三处最容易翻车的点各就各位[^2]：

- **第 05 章｜绝对路径**：dev patch 的 `name` 必须是指向 `src/index.ts` 的**绝对路径**，相对路径静默失效。
- **第 06 章｜四处名字**：`export const name`（诊断）/ package.json `name`（包名）/ patch `id`（实例）/ defineTool `name`（模型可见），别混。
- **第 09 章｜打包三件套**：`prepare` 脚本 + pnpm≥10 的 `allowBuilds` 放行 + git 安装用 `#sha` 钉 commit；bundle patch `name` == package.json `name`。

## 4. 下一步：换成你自己的工具

按「补全当前插件 → 走向真实发布」排四个方向[^3]：

1. **更多工具**：按第 06 章 defineTool 五件套继续加，一个插件可注册多个工具。
2. **配置实战**：按第 07 章扩展 Schema 类型，把参数做成可配，对照 [[03-配置实战-接入skills-hooks-mcp-rules|配置实战]]。
3. **发布到 npm registry**：第 09 章只演示 `pnpm pack`，改走 `npm publish`，任何 profile 即可 `pnpm dsh plugin add dsh-git-log-plugin` 安装。
4. **官方模板 `dsh-plugin-*`**：现在回头看脚手架能读懂每个文件为何存在——从零练理解，模板提速度。

任何「agent 能帮你做、但需要执行外部命令/查数据」的事，都能包成 dsh 工具[^2]——改 `defineTool` 的 name/description/parameters 告诉模型它是什么、要什么参数，再换 `execute` 里的命令/调用：

| 工具想法 | defineTool 要改哪 | execute 换成什么 | 要不要加配置项 |
| --- | --- | --- | --- |
| API 封装（天气 / 股票 / 汇率） | name + description + parameters | `fetch('https://api...')` + 解析结果 | 建议：endpoint、key 做成 config |
| 笔记检索（在 vault 里搜） | name + description + parameters | `rg` 扫 vault 目录 + 组装结果 | 建议：vault 路径做成 config |
| 目录统计（各目录文件数） | name + description + parameters | `find <dir> -type f` + 汇总 | 可选：目录路径做成 config |
| 构建脚本（跑测试 / 编译） | name + description + parameters | `pnpm run build` / `tsc` | 视情况：目标路径做成 config |

> [!tip] 大白话
> 改造脚手架 = 拿到模板房钥匙后，自己决定每间房用来做什么。`git_log` 是改好的第一间；下一个工具只是给 `execute` 摆上不同的家具，钥匙（A→C 链路）已经在你手里。

> [!note] 这在 Claude Code 里相当于
> 「换成你自己的工具」≈ 在 Claude Code 里持续往工具包里加自定义 tool / MCP——一样是「一次声明（name + description + parameters）、到处调用」，攒多了就是你的工具箱。

## 5. 双起点收口：改造与从零在终点汇合

04-10 章把原《插件实战》（脚手架改造）与《从零写插件》（空目录手写）合并成**同一条渐进路径**：两条入口在第 04 章选路后汇流，共用同一套一致性基线——同一 `git_log` / 同一四名分离 / 同一 `maxCommits=5`，因此终点严格一致，任意一步都能逐文件对照，不会出现「名字对不上」的困惑[^2][^3]。

- **已有脚手架基础**：跳过第 04 章选路对照，从第 05 章直接上手；每一步都能与 `example-plugin` 成品对号入座。
- **从零读者**：以 05-10 章为主线，读到 defineTool、Config schema、bundle 概念时，回翻 [[01-插件开发核心-从apply到system-prompt|插件开发核心]] 与 [[02-配置体系-补丁树Profile与bundle|配置体系]] 做对照验证，两条线互相印证。

## 本章小结

- 从零到装好共 6 次增量，手写文件 2 → 6 个，加 `dist/` 产物共 8 个文件。
- 一条命令链覆盖开发到交付：`web --patch` → `--dump-config` → headless → `pnpm pack` → `pnpm dsh plugin add`。
- 自查清单三处：dev patch 绝对路径、四处名字别混、打包三件套（`prepare` / `allowBuilds` / `#sha`）。
- 下一步四条路：更多工具、配置实战、npm 发布、官方模板 `dsh-plugin-*`。
- 两条入口（改造 / 从零）在共同基线上收口，任意一步可逐文件对照。
- 至此你能脱离脚手架，从空目录独立造出带 `git_log` 工具与 `maxCommits` 配置的 dsh 插件——把它换成你自己的工具，就正式出师。
