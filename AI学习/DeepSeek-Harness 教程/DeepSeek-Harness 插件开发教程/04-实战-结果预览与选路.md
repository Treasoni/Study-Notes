# 实战：结果预览与选路

> [!summary] 本章导读
> 前面两章讲完了概念（[[01-插件开发核心-从apply到system-prompt|插件开发核心]]）与配置理论（[[02-配置体系-补丁树Profile与bundle|配置体系]]），可让你亲手写一个插件还是不知道从哪下手？从本章起进入**实战**：原《插件实战》（脚手架改造）与《从零写插件》（空目录手写）两篇实战分册合并成同一条渐进路径，即第 04-10 章。这一章不写代码，先把「终点长什么样」「两条路怎么选」「全篇一致性基线」钉清楚——你看得见靶子，后面 05-10 章才射得准。

## 1. 先看结果——你要做出什么

你将在 05-10 章亲手做出一个**真正能给模型干活**的 dsh 插件。终点交付两样东西[^1]：

- **① 一个新工具 `git_log`**——用 `defineTool` 声明，会出现在 Web UI 里、模型随时能调用；
- **② 一个可安装的 bundle**——打包好的插件包，装进 profile 就能复用。

示范工具选 `git_log`（最近提交概览）：它与系列脚手架 `example-plugin` 的 `repo_status` 同为 git 家族，改动最小、最容易照做。你的真实工具可以是任何 `defineTool` 能表达的东西（笔记检索、目录统计、API 封装）。

> [!tip] 大白话
> 你要动手做的不是毛坯房——是把「从零手写」和「脚手架改造」两条路合在一起的样板间。先看清楚样板间长什么样，再选从哪扇门进去。

改造完成后，模型在 Web UI 里调用 `git_log` 的样子大致如下——`execute` 跑 `git log --oneline -n <max>`，`render` 把结果转成模型能读的文本[^1]：

```text
# 模型调用 git_log（参数 max=5）后，模型看到的输出：
最近 5 条提交：
db5f25c vault backup: 2026-08-15 18:17:40
99aa24a vault backup: 2026-08-15 18:16:37
d02e904 vault backup: 2026-08-15 18:15:13
c0da45b vault backup: 2026-08-15 18:11:16
4ced37b vault backup: 2026-08-15 18:08:53
```

## 2. 你要走完的 8 步（先混个眼熟）

整条链路压成 8 步，后面 05-10 章逐章拆开[^1]：

```bash
# ① 前提：源码环境已就绪（clone → pnpm install → pnpm run build），在 dsh 仓库根目录
#    —— 这一步得到：一个能跑 dsh 的本地源码仓库

# ② 两个入口任选其一（05 章）：
#    从零：mkdir git-log-plugin（空目录手写）
#    改造：cp -r example-plugin ./example-plugin（拷贝脚手架）
#    —— 这一步得到：一份可以随便改、不碰原件的插件骨架

# ③ 写工具：注册中心 src/index.ts + 工具本体 src/tools/git-log.ts（06 章）
#    —— 这一步得到：一个能注册 git_log 工具的插件

# ④ 配参数：Config schema 加 maxCommits + 两份 patch 的 config 块传值（07 章）

# ⑤ 启动加载：pnpm dsh web --patch ./git-log-plugin/dev-cordis.patch.yml
#    —— 预期输出：[git-log-plugin] plugin loaded!（08 章）

# ⑥ 验证：--dump-config / --dump-default-config / headless 命令链（08 章）

# ⑦ 打包：pnpm install && pnpm run build → dist/；pnpm pack 打 tarball（09 章）

# ⑧ 安装：pnpm dsh plugin --profile demo add <tarball>；带 profile 启动验证（09 章）
```

## 3. 双起点选路：改造 vs 从零

同一个 `git_log`，两条路都能到终点——动手前先选好走哪条[^2]：

| 维度 | 改造路线（原《插件实战》） | 从零路线（原《从零写插件》） |
| --- | --- | --- |
| 起点 | `example-plugin` 脚手架 | 空目录 |
| 第一步 | 复制脚手架、删改自带文件 | 手写 `src/index.ts` + 最小 patch |
| 终点 | 同一插件：工具 `git_log` + 配置 `maxCommits` | 同一插件：工具 `git_log` + 配置 `maxCommits` |
| 收获 | 脚手架里每个文件是干什么的 | 每个文件为什么必须存在 |

> [!tip] 大白话
> 两条路像同一道菜的「半成品加工版」与「全流程生做版」——菜一样，一个省事、一个练基本功。想快速吃到嘴，走改造；想学会从备菜到出锅的全过程，走从零。05-10 章会同时给出两个入口，你按选好的路线走就行。

**本篇刻意不教 / 不重复的**[^3]：

- **脚手架自带文件**：eslint 配置、tsconfig 的细化选项、dev/bundle 双 patch 之外的约定文件——这些属于改造路线的讲解范围，从零路线按需才引入；
- **monorepo 内建包规范**：`lib/types` 目录、extends 根 tsconfig、references、constraints——这是 deepseek-harness 仓库**内部建包**的规范，**不含** `dsh.bundle.patch`；独立插件只按 V1 规范走（`src/` + `tsc` + `dist/` + `dsh.bundle.patch`），两套规范不要混用。

## 4. 全篇一致性基线

两篇实战共用同一套基线，因此终点严格一致——任一章节，都能把两路文件逐文件对照，不会出现「名字对不上」的困惑[^1][^2]：

| 基线 | 固定值 |
| --- | --- |
| 模型可见工具名 | `git_log`（defineTool `name`） |
| 诊断名 | `export const name = 'git-log-plugin'` |
| 包名 | `dsh-git-log-plugin`（package.json `name`） |
| patch 实例 id | `git-log` |
| 配置默认值 | `maxCommits: Schema.number().default(5)` |

其中最核心、也是全篇最高频的坑是**四名分离**——同一件事有四个名字，各管各的，改错会怎样一并对齐：

| 名字 | 值 | 改在哪 | 改错了会怎样 |
| --- | --- | --- | --- |
| 诊断名 `export const name` | `git-log-plugin` | `src/index.ts` 顶部 | 只出现在日志/加载消息；错了仅日志难看，不影响功能 |
| 包名 `package.json` name | `dsh-git-log-plugin` | `package.json` | 打包后 bundle 层的 patch `name` 必须引用它（09 章），不一致加载失败 |
| 实例 id patch `id` | `git-log` | `dev-cordis.patch.yml` / `cordis.patch.yml` | 合成配置里插件实例的标识；08 章 `--dump-config` 靠它辨认 |
| 模型可见工具名 defineTool `name` | `git_log` | `src/tools/git-log.ts` | Web UI 里模型真正调用的名字；改错模型根本找不到这个工具 |

记住一句话：**`git-log-plugin` ≠ `dsh-git-log-plugin` ≠ `git-log` ≠ `git_log`**。前三个连字符命名各管各的（日志 / 包 / 补丁实例），只有 `git_log` 是下划线命名且直接暴露给模型——它是模型和你的代码之间的协议，一旦发布再改，所有依赖它的对话历史都会失效，所以从 06 章起就是冻结值。

## 本章小结

- 终点 = 一个 `git_log` 工具 + 一个可安装的 bundle；整条链路 8 步，05-10 章逐章拆解。
- 双起点：改造（脚手架）省事、从零（空目录）练基本功，终点一致、可互相参照；独立插件规范与 monorepo 内建包规范不可混用。
- 一致性基线把两条路钉在同一个终点：同一 `git_log` / 同一四名分离 / 同一 `maxCommits=5`。
