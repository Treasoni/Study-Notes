# 部署进阶：Docker、多后端与安全基线

前几章 Hermes 跑在本地 CLI 里，属于"随开随用"。本章是部署的**决策层**：想让它 7×24 常驻，选哪种形态？命令执行想隔离，有哪些后端可选？安全基线哪条不能妥协？

照抄命令、排障、配 Compose 的**操作细节不在这里重复**，统一指向 [[Hermes Docker 部署指南/README|Hermes Docker 部署指南]] 分册（下称 Docker 分册）。本章只保留"怎么选"，以及 Docker 分册没覆盖的两块：**多后端全景**与 **Docker 当 terminal 沙箱**。

## 本地 CLI 的边界：什么时候需要"部署进阶"

前几章都在本机跑 `hermes` CLI：进程退出就停、没有开机自启、命令直接跑在宿主机、也没有对外接口。出现下面任一诉求时，才需要考虑本章：

- **常驻**：希望 Hermes 7×24 在线，崩溃自动拉起、开机自启；
- **接入消息平台**：Telegram / Discord / 微信 / 飞书 / QQ 等需要 gateway 长连接；
- **暴露 API**：让其他程序或 Open WebUI 这类 OpenAI 兼容客户端调用；
- **隔离命令执行**：不希望 agent 直接在宿主机上跑任意命令。

> [!tip] 大白话
> 本地 CLI 像"想用才开的个人工作台"，部署是"24 小时营业的门店"。先确认你要不要开店、开哪种店，再看下面。

## 两种 Docker 用途：先分清你要哪种

Docker 里跑 Hermes 有两种诉求完全不同，别混为一谈：

1. **跑 Hermes 本体**：把整个 agent 装进容器，作为常驻服务对外提供 Gateway / API——这是 Docker 分册 01~02 章的主线。
2. **只当 terminal 后端**：Hermes 本身仍在宿主机跑，但所有命令执行丢进一个**单常驻沙箱容器**，隔离文件系统与依赖——延续 07 章 execute_code / terminal 的隔离思路。

> [!tip] 大白话
> 把 Docker 想成两种租房：整租是 agent 全家搬进容器过日子；厨房外包是 agent 住外边，只在专用厨房做饭（执行命令）。先想清楚要哪种，再写 docker run。

## 三种部署形态速览

| 形态 | 一句话 | 适合场景 | 详版 |
|------|--------|----------|------|
| 本地 CLI | `hermes` 直接跑在宿主，随开随用 | 学习、调试、短期个人使用 | 本系列 02 章 |
| Docker 跑本体 | 容器常驻 gateway，状态全在 `~/.hermes` | 7×24 服务、接平台、暴露 API | Docker 分册 01 + 02 |
| 远程 / 沙箱后端 | 命令执行进隔离容器或云端 serverless | 不想让 agent 直接动宿主 | 本章下方两节 |

- **Docker 跑本体**的具体操作（镜像 / 数据卷 / setup / Compose / 升级 / 排障）见 [[Hermes Docker 部署指南/01-镜像数据卷与首次setup|01-镜像数据卷与首次setup]]、[[Hermes Docker 部署指南/02-Gateway常驻与Compose编排|02-Gateway常驻与Compose编排]]。
- 资源建议随 Compose 一起落地：内存 1GB 起、2~4GB 推荐（Playwright 浏览器自动化最耗内存），数据卷 500MB 起、建议预留 2GB——Docker 分册 02 的 compose 示例已内置 `memory: 4G`。

## 多后端清单与版本漂移

README 宣称支持 **7 种终端后端**：`local` / `Docker` / `SSH` / `Singularity` / `Modal` / `Daytona` / `Vercel Sandbox`。其中 Modal / Daytona 提供 serverless 持久化——空闲休眠、按需唤醒，适合不想常驻 VPS 的场景。

但这份清单**会漂移**：v0.15.0 曾移除 Vercel Sandbox 后又回归，`terminal-backends` 文档页也已 404。所有涉及后端数量、Vercel 的内容一律**以 v0.20.x 文档为准**。

> [!warning] 远程后端的凭据泄露面
> 把后端同步到远程（Docker / SSH / Modal / Daytona）时，`~/.hermes` 同时含 `.env` 密钥与 `auth.json` OAuth token，必须配置 ignore 排除，否则凭据进入不受控基础设施。

## Docker 作为 terminal 后端：沙箱配置

Hermes 本身留在宿主机，命令执行丢进 Docker 沙箱。配置示例：

```yaml
# ~/.hermes/config.yaml —— 让命令执行进 Docker 沙箱
terminal:
  backend: docker
  docker_image: hermes-agent:latest
  docker_volumes:
    - /path/to/work:/work
  docker_run_as_host_user: true
  docker_persist_across_processes: true
  docker_orphan_reaper: true
```

要点（配合 03 章"配置与密钥分离、凭据只放 `~/.hermes/.env`"的基线一起用）：

- `skills/` 目录与凭据文件会被自动**只读 bind-mount** 进沙箱，避免容器内 agent 篡改；
- `docker_persist_across_processes`：容器是否跨 Hermes 进程存活（关闭则每条命令结束即回收）；
- `docker_orphan_reaper`：回收孤儿进程，防止僵尸进程堆积。

这样沙箱既隔离、又不丢状态。

## bind mount：让容器访问宿主机目录

容器默认看不到宿主机其他目录。需要在 Compose 的 `volumes` 下追加一条：

```yaml
volumes:
  - ${HOME}/.hermes:/opt/data
  - /path/to/your/project:/work:ro   # 只读优先；确需读写再改 :rw
```

- `:rw` 允许 agent 修改甚至删除宿主机文件——只需要分析内容时**优先 `:ro`**，不要把整个 Home 或 `/` 挂进去。
- 挂载后让 Hermes 用容器内路径（`/work/...`），不要用宿主机原始路径。
- macOS Docker Desktop 需先在 **Settings → Resources → File Sharing** 允许该目录。

## 安全基线：一句话原则

> [!warning] 部署安全第一原则
> **凡是暴露到非 loopback 的入口，要么有认证，要么 fail-closed 拒绝启动**——宁可不服务，也不裸奔。

落到配置上：

- **API Server 三件套**缺一不可：`API_SERVER_ENABLED=true` + `API_SERVER_HOST=0.0.0.0` + `API_SERVER_KEY` ≥8 位（`openssl rand -hex 32` 生成）。`0.0.0.0` 意味着暴露公网，没密钥等于裸奔。
- **dashboard**（`HERMES_DASHBOARD=1`，端口 9119）同理：非环回绑定必须配认证（basic auth / Nous Portal OAuth / 自建 OIDC），否则 fail-closed 拒绝启动；旧的 `HERMES_DASHBOARD_INSECURE=1` 已废弃为 no-op。
- 这不是危言耸听——2026-06 就曾发生未认证仪表盘被扫描器发现、植入 SSH 后门的事件。

> [!note] 安全详版
> 完整展开（API 三件套、密钥落盘泄露面、UID 10000 权限最小化、平台侧 allowlist 清单）见 [[Hermes Docker 部署指南/10-安全基线|Docker 分册 10-安全基线]]。

## 本章小结

- 部署进阶服务四类诉求：**常驻 / 接消息平台 / 暴露 API / 隔离命令执行**；纯本地使用不需要。
- Docker 两种用途别混：**跑本体**（→ Docker 分册 01~02）vs **只当 terminal 后端**（本章沙箱配置）。
- 多后端有 7 种：local / Docker / SSH / Singularity / Modal / Daytona / Vercel Sandbox；**清单会漂移，以 v0.20.x 文档为准**。
- Docker 当 terminal 后端：`terminal.backend: docker` + 凭据 / skills 只读挂载，`persist_across_processes` 控存活、`orphan_reaper` 收孤儿进程。
- 安全一句话：**非 loopback 入口要么有认证要么 fail-closed**；API Server 三件套缺一不可。
