# 多平台接入与定时任务：从"你找它"到"它找你"

前五章里，都是你主动打开终端去找 Hermes 聊天。本章把交互模式反过来：接入 Gateway 网关后，agent 常驻在 Telegram、Discord、Home Assistant 等平台上"等你来找它"；配上 cron 定时任务后，它甚至到点主动干活、把结果推给你——从"你找它"变成"它找你"。两件事都能在对话里用自然语言配置，是 Hermes 相比 Claude Code / OpenClaw 顺手的地方（来源 S6、S7）。

## 6.1 Gateway 多平台接入

### 接入：一个进程连 20+ 平台

跑 `hermes gateway setup` 交互式配置，向导引导你选定平台并生成凭证。配置完成后，一个 gateway 进程同时连接 20+ 平台：Telegram、Discord、Slack、WhatsApp、Signal、Email 等（来源 S6）。配好之后你就不用再守着终端——agent 常驻在云端或本地，掏出手机在任何接入平台发消息就能对话。bot 要真正干活需要两样东西：**model provider**（模型入口）+ **tool provider**（工具网关）。如果用 Nous Portal，OAuth 一次捆绑两者，省去分开配置（来源 S6）。

> [!tip] 大白话
> 把 gateway 想成总机接线员：一根电话线接 20 多个分机（平台），你在任意一个平台发消息，总机都转到同一个 agent。绑定 Nous Portal 等于一次性办好了"话费套餐"——模型和工具一起开通，不用跑两趟。

### 授权：默认拒绝 + DM 配对

Gateway 是默认 deny 白名单：任何平台上的陌生消息一概不理，只有你主动授权过的账号能对话。授权方式是先在 CLI 会话里跑配对命令，把平台发来的配对码审批通过：

```bash
hermes gateway setup                    # 交互式配置平台接入
hermes pairing approve telegram <code>  # 审批 Telegram 配对请求
```

> [!tip] 大白话
> 把配对想成小区门禁：默认访客全拦下，只有你到物业（CLI）确认过的车牌才放行。所以你在 Telegram 上给 bot 发消息不会立刻有反应——得先在终端里批准它。

### 常驻与自愈边界

Gateway 设计为常驻服务，官方建议用 systemd（Linux）或 launchd（macOS）托管；日志在 `~/.hermes/logs/gateway.log`。无头 VM 上以 user service 方式跑，并执行 `loginctl enable-linger`，让用户会话在无人登录时也保持运行（来源 S6）：

```ini
# systemd user service 骨架（示意；实际 Unit 名与 ExecStart 以 `hermes gateway install` 生成为准）
[Unit]
Description=Hermes Gateway
After=network-online.target

[Service]
Restart=on-failure

[Install]
WantedBy=default.target
```

macOS 端还有个小坑：装完新工具后要重跑 `hermes gateway install` 固化 PATH，否则重启后的 gateway 可能找不到新装的命令（来源 S6）。

一个必须记住的坑：每个平台适配器都有**熔断器**，连续失败会熔断该平台；熔断后**不会自动恢复**，必须手动在会话里执行 `/platform resume` 重新接通（来源 S6）。所以 gateway 挂了一晚上没响应，先查 `gateway.log` 再看是否熔断。

> [!tip] 大白话
> 熔断器想成烧断的保险丝：短路时它主动断开保护设备，但保险丝不会自己长回去。平台反复报错被熔断后，你得手动换一根（`/platform resume`），别干等。

### 常用平台接入教程

所有平台都走同一条路径：`hermes gateway setup` 向导选平台 → 填凭证 → `hermes gateway` 启动 → 陌生账号用 DM 配对码授权（见上「授权」）。下面是 10 个常用平台的最小变量集与最常踩的坑，手动配直接写进 `~/.hermes/.env`（来源 S21）：

| 平台 | 上手难度 | 要不要公网 | 典型用途 |
|------|---------|-----------|---------|
| Telegram | ⭐ 最易 | 否（默认轮询） | 个人主力 IM |
| Discord | 易 | 否 | 群组 / 服务器 |
| Slack | 中 | 否 | 团队协作 |
| WhatsApp Cloud | 中 | 要（webhook） | 客服 / 海外 |
| Signal | 中 | 否 | 隐私优先 |
| Email | 易 | 否 | cron 推送 / 兜底 |
| 钉钉 / 飞书 / 企业微信 | 中 | 否（长连接） | 国内办公 IM |
| 微信（个人，iLink Bot） | 中 | 否（长轮询） | 个人微信消息 |

**Telegram** — 最快上手，5 分钟：@BotFather 建 bot 拿 token，@userinfobot 查你的数字 ID。

```bash
TELEGRAM_BOT_TOKEN=123456789:ABCdef...   # @BotFather 建 bot 后给的 token
TELEGRAM_ALLOWED_USERS=123456789         # @userinfobot 查到的数字 ID
```

- 坑：bot 默认开隐私模式，群里只响应 @提及；去 BotFather → Bot Settings → Group Privacy 关闭，且关掉后要把 bot 移出群再拉回。
- 云端部署想收消息用 `TELEGRAM_WEBHOOK_URL`（公网 HTTPS），本地跑默认轮询即可。

**Discord** — 变量最少，但有两个开关必须开：

```bash
DISCORD_BOT_TOKEN=your-bot-token
DISCORD_ALLOWED_USERS=284102345871466496   # 设置 → 开发者模式 → 右键复制用户 ID
```

- 坑①：开发者后台必须开 **Message Content Intent**，否则 bot 收到事件但消息正文是空的——"收到却不应答"的头号原因。
- 坑②：**Server Members Intent** 也要开。邀请链接：`https://discord.com/oauth2/authorize?client_id=<APP_ID>&scope=bot+applications.commands&permissions=274878286912`。
- 群里默认 @提及才响应，`DISCORD_REQUIRE_MENTION=false` 可去掉。

**Slack** — 先跑 `hermes slack manifest --agent-view --write` 生成 manifest，去 api.slack.com 用 manifest 建 app，一次性声明 scope 和 Socket Mode：

```bash
SLACK_BOT_TOKEN=xoxb-...   # Bot User OAuth Token（安装后拿）
SLACK_APP_TOKEN=xapp-...   # Socket Mode 的 App-Level Token（connections:write）
SLACK_ALLOWED_USERS=U01ABC2DEF3
```

- 坑：Socket Mode 要单独开并生成 `xapp-` 的 App-Level Token；事件订阅至少要 `message.im` / `message.channels` / `app_mention`，漏了就是"bot 收不到消息"的头号原因。
- 装完要在频道里 `/invite @Hermes Agent`，bot 不会自动加入。

**WhatsApp（Cloud API）** — 官方生产级路线，但要公网回调；先跑 `hermes whatsapp-cloud` 向导逐项校验凭证比手填稳：

```bash
WHATSAPP_CLOUD_PHONE_NUMBER_ID=...   # Meta 后台的号码 ID，不是手机号！头号填错点
WHATSAPP_CLOUD_ACCESS_TOKEN=EAA...   # 临时 token 24h 过期，生产换 System User 永久 token
WHATSAPP_CLOUD_APP_SECRET=...        # 32 位十六进制，webhook 签名校验
WHATSAPP_CLOUD_VERIFY_TOKEN=...      # 自己生成的随机串
WHATSAPP_CLOUD_ALLOWED_USERS=15551234567
```

- 要公网 HTTPS：`cloudflared tunnel --url http://localhost:8090`，再把回调 `https://<tunnel>/whatsapp/webhook` 配到 Meta 后台。
- 只支持私聊、不支持群；群聊要用非官方 Baileys 版（`hermes whatsapp`，有封号风险）。

**Signal** — 依赖独立 signal-cli 守护进程：

```bash
SIGNAL_HTTP_URL=http://127.0.0.1:8080   # signal-cli daemon 的 HTTP 端点
SIGNAL_ACCOUNT=+1234567890             # bot 号码（E.164 格式）
SIGNAL_ALLOWED_USERS=+15551234567
```

- 先 `signal-cli link -n "HermesAgent"` 扫码把 bot 配成你的第二台设备，再 `signal-cli --account +1234567890 daemon --http 127.0.0.1:8080` 常驻。
- 群消息默认全忽略，要监控群得设 `SIGNAL_GROUP_ALLOWED_USERS`。

**Email** — 唯一不用额外开账号的平台，用你自己的邮箱：

```bash
EMAIL_ADDRESS=me@example.com
EMAIL_PASSWORD=app-password          # Gmail/Outlook 开 2FA 后生成"应用专用密码"
EMAIL_IMAP_HOST=imap.gmail.com       # Outlook 用 outlook.office365.com
EMAIL_SMTP_HOST=smtp.gmail.com
EMAIL_ALLOWED_USERS=friend@example.com
```

- 默认轮询收 UNSEEN 邮件、只处理白名单发件人；未知发件人默认忽略（配对需显式开启）。适合给 cron 结果当推送终点。

**钉钉（DingTalk）** — 走 Stream 模式，无需公网 IP：

```bash
DINGTALK_CLIENT_ID=appkey
DINGTALK_CLIENT_SECRET=appsecret
DINGTALK_ALLOWED_USERS=user-id-1
```

- 后台建 H5 微应用 → 添加机器人 → 消息接收方式选 **Stream 模式**（长连接，穿透 NAT）。
- `hermes gateway setup` 选钉钉可直接扫码，自动把凭据写进 `.env`。

**飞书（Feishu/Lark）** — 推荐 WebSocket 连接模式：

```bash
FEISHU_APP_ID=cli_xxx
FEISHU_APP_SECRET=secret_xxx
FEISHU_DOMAIN=feishu                # 海外用 lark
FEISHU_CONNECTION_MODE=websocket    # 无需公网；webhook 模式要配加密
FEISHU_ALLOWED_USERS=ou_xxx
```

- 权限要加 `im:message` / `im:message:send_as_bot` / `im:chat` 等，并订阅 `im.message.receive_v1`；改权限后要在版本管理发布才生效。

**企业微信（WeCom）** — 扫码自动建 bot 最省事：

```bash
WECOM_BOT_ID=...
WECOM_SECRET=...
WECOM_ALLOWED_USERS=...
```

- `hermes gateway setup` 选企业微信扫码，自动创建带正确权限的 AI bot 应用并写入凭据。
- 走 WebSocket，无需公网端点；群策略 `WECOM_GROUP_POLICY` 可设 `open` / `allowlist` / `disabled`。

**微信（Weixin，个人号）** — 和上面企业微信是两码事：这里管的是**个人微信**，走腾讯 **iLink Bot API**，没有 AppID/AppSecret，全程靠扫码登录生成一个 iLink bot 身份（形如 `a5ace6fd482e@im.bot`）：

```bash
hermes gateway setup     # 选 Weixin → 终端显示二维码 → 微信 App 扫码 → 凭据自动存盘
WEIXIN_ACCOUNT_ID=your-account-id   # 扫码成功后自动写入 ~/.hermes/.env
WEIXIN_DM_POLICY=open               # open / allowlist / disabled / pairing
WEIXIN_ALLOWED_USERS=               # 私聊白名单：别人先发消息，从 gateway 日志捞 user ID 填进来
```

- 依赖 `pip install aiohttp cryptography`；启动走 35 秒长轮询 `getupdates`，无需公网 / webhook / WebSocket。
- 坑①：iLink bot **一般拉不进普通微信群**，群功能大概率不可用——`WEIXIN_GROUP_POLICY` 默认 `disabled`，硬开会在日志打警告。
- 坑②：扫二维码的是你的个人微信号，别人 @你的微信 ≠ @ iLink bot，别混。
- 坑③：token 单实例锁；session 过期（`errcode=-14`）要重跑 `hermes gateway setup`。

> [!tip] 大白话
> 想成给 agent 办各聊天软件的"工牌"：到物业（`hermes gateway setup`）统一登记，每个平台一张门禁卡（bot token），不认识的访客一律拦在门外（白名单）。Telegram 是最好办的那张；WhatsApp 得先给家里装个可视门铃（公网 webhook）才有人按门铃。

### Home Assistant：智能家居双向接入

接入 Home Assistant（HA）把"多平台"从消息渠道扩展到**智能家居**：一条 WebSocket 通道把设备状态变化实时推给 agent（事件进来），四个 `ha_*` 工具让 agent 直接调服务控制设备（控制出去）。它和 Telegram 那种纯聊天平台不同——不是多一个说话的地方，而是给 agent 装上"感官"和"手脚"（来源 S20）。

**一个 Token 两条通道：** HA 有两条通道但只需一个 **Long-Lived Access Token** 同时激活——设置 `HASS_TOKEN` 后，Gateway 平台（事件）与 `homeassistant` 工具集（控制）一起生效。先生成令牌：Home Assistant 个人资料（Profile）→ 长期访问令牌（Long-Lived Access Tokens）→ 创建令牌；再写进 `~/.hermes/.env`：

```bash
HASS_TOKEN=your-long-lived-access-token   # 必需：HA 长期访问令牌
HASS_URL=http://192.168.1.100:8123        # 可选，默认 http://homeassistant.local:8123
```

验证令牌有效后重启 gateway（环境变量只在进程启动时读取）：

```bash
curl -H "Authorization: Bearer <token>" http://<HA地址>:8123/api/
# 应返回 {"message": "API running."}
```

**四个智能家居工具：** `HASS_TOKEN` 就位后，agent 自动获得四个 LLM 可调用的工具（来源 S20）：

| 工具 | 作用 |
|------|------|
| `ha_list_entities` | 列出实体，可按 domain（light / climate / switch…）或 area 过滤 |
| `ha_get_state` | 获取单个实体完整状态与属性（亮度、温度设定点、传感器读数…） |
| `ha_list_services` | 列出某 domain 下可用的服务（动作） |
| `ha_call_service` | 调用服务控制设备 |

```python
ha_call_service(domain="light", service="turn_on", entity_id="light.living_room")   # 开客厅灯
ha_call_service(domain="climate", service="set_temperature",
                entity_id="climate.thermostat",
                data={"temperature": 22, "hvac_mode": "heat"})                      # 恒温器 22°C 制热
```

**事件转发：默认全关，白名单过滤：** 实时状态事件默认**一条都不转发**——必须在 `~/.hermes/config.yaml` 的 `platforms.homeassistant.extra` 里至少配 `watch_domains` / `watch_entities` / `watch_all` 之一，否则启动时打警告然后静默丢弃（来源 S20）：

```yaml
platforms:
  homeassistant:
    enabled: true
    extra:
      watch_domains:
        - climate
        - binary_sensor
        - alarm_control_panel
        - light
      watch_entities:
        - sensor.front_door_battery
      ignore_entities:
        - sensor.uptime
        - sensor.cpu_usage
        - sensor.memory_usage
      cooldown_seconds: 30
```

`cooldown_seconds` 限制同一实体两次事件的最小间隔（默认 30 秒），压掉高频噪音；`ignore_entities` 先于 domain/entity 过滤生效。官方建议起步盯 `climate` / `binary_sensor` / `alarm_control_panel` 这几个域，别贪多。agent 的出站消息以标题 **"Hermes Agent"** 的 persistent notification 出现在 HA 通知面板。

> [!tip] 大白话
> 接入 HA 等于给 agent 发了一张"智能家居总钥匙卡"：`ha_*` 工具是遥控器（想开灯就按键），Gateway 事件通道是门磁感应器（门一开它自己就知道）。一张卡把遥控器和感应器同时办好。

**安全边界与连接管理：** 为防在 HA 主机上执行任意代码或 SSRF，`shell_command`、`command_line`、`python_script`、`pyscript`、`hassio`、`rest_command` 等服务域被硬拦截；`entity_id` 按 `^[a-z_][a-z0-9_]*\.[a-z0-9_]+$` 校验防注入。连接上，WebSocket 带 30 秒心跳，断线按 5s → 10s → 30s → 60s 指数退避自动重连；出站通知走独立 REST 会话，避免与事件 WebSocket 冲突。HA 事件由 `HASS_TOKEN` 认证，无需像 Telegram 那样走 DM 配对白名单（来源 S20）。

## 6.2 cron 定时任务

### 自然语言定义调度

cron 能力通过统一的 `cronjob` 工具暴露，在对话里用自然语言建/停/改/删，不用碰 crontab 语法（来源 S7）。调度支持四种格式：

| 格式 | 示例 | 含义 |
|------|------|------|
| 相对延迟 | `30m` / `2h` | 从现在起 30 分钟 / 2 小时后跑一次 |
| 间隔 | `every 2h` | 每 2 小时循环一次 |
| cron 表达式 | `0 9 * * *` | 标准 crontab 写法，如每天 9 点 |
| ISO 时间戳 | `2026-09-01T08:00:00` | 指定某一时刻 |

### 结果自动投递

任务结果自动投递到绑定的 20+ 平台（origin / local / telegram / slack / whatsapp / email / dingtalk / feishu / wecom 等），**agent 不自己发消息**（来源 S7）。`context_from` 把上一任务输出作为下一任务的输入，链成流水线；`continuity=true` 时注入自己上次的输出，防止对同一事件重复报告（来源 S7）。

> [!tip] 大白话
> 想成设好闹钟的自动取件机器人：到点出门、取完快递、把东西放回你常看的门口（平台），全程不用你守着。`context_from` 是"把上次取到的单子带给下一次"，`continuity=true` 是"上回说过的事这回复述一遍"。

### 模型解析与 fails closed

每次运行前要决定"让哪个模型干活"，解析顺序：任务 pin → `cron.model` → 全局默认。关键安全语义：未 pin 的任务在创建时**快照**全局默认模型，之后你改了默认模型，会让任务 fails closed——跳过运行、零推理消耗，而不是悄悄用新模型跑（来源 S7），从根上避免配置漂移引发的意外行为。任务派发前还会做配置校验：校验失败的任务被标记为 `blocked_config`，只发一条告警、零 LLM 调用，不会反复空跑烧 token（来源 S7）。

> [!tip] 大白话
> 想成保险单：创建任务时按当时价格"锁定"了模型，之后你改价（换默认模型）不会自动生效，任务宁可停跑也不偷偷换。省下的 token 是真金白银，行为可预期更重要。

### no_agent 脚本模式与 wakeAgent 门

很多定时任务根本不需要 LLM。`no_agent` 模式按计划直接跑脚本，**零 LLM 调用**：脚本 stdout 原文投递到平台，空输出 = 静默 tick（不打扰），非零退出才告警（来源 S7）。更省的是 `wakeAgent` 预检门：先跑一段轻量检查，若脚本输出如下 JSON，则跳过本轮 LLM，适合高频轮询的零成本门控：

```json
{"wakeAgent":false}
```

> [!tip] 大白话
> 把 no_agent 想成自动售货机：到点就吐货（跑脚本），不需要店员（LLM）在场。`wakeAgent` 是售货机门口的感应器：感应到没人（false）就不启动，省电（token）。

### 运行机制与实现细节

任务清单存在 `~/.hermes/cron/jobs.json`，执行历史进 `executions.db`；gateway 每 60 秒 tick 一次检查到期任务，最小调度粒度约为一分钟。cron 会话默认不能再建 cron（防递归）；带 `workdir` 的任务在指定目录**串行**执行，并自动注入该目录的 AGENTS.md / CLAUDE.md，让脚本吃到项目上下文（来源 S7）。

## 本章小结

- Gateway 一个进程连 20+ 平台，`hermes gateway setup` 配置；Nous Portal 一次捆绑 model + tool provider。
- 默认 deny：陌生消息一律不理，用 `hermes pairing approve telegram <code>` 审批配对。
- Gateway 用 systemd / launchd 托管，日志在 `~/.hermes/logs/gateway.log`；无头 VM 记得 `loginctl enable-linger`。
- 平台适配器熔断不自动恢复，需手动 `/platform resume`。
- `cronjob` 工具自然语言管理定时任务，四种调度格式；结果自动投递、agent 不自发消息。
- 模型解析 fails closed：默认模型变更后任务跳过运行、零推理；`no_agent` 模式零 LLM，`wakeAgent` 预检门把高频轮询成本压到近乎零。
- 常用平台走 `hermes gateway setup` 向导：Telegram 最易；Discord 记得开 Message Content Intent；Slack 用 manifest + Socket Mode；WhatsApp 需公网 webhook；Signal 靠 signal-cli 守护进程；Email 用应用专用密码；钉钉 / 飞书 / 企业微信走长连接免公网；个人微信走 iLink Bot 扫码（群聊大概率不可用）。
- Home Assistant 接入：一个 Long-Lived Access Token 同时开两条通道——`ha_*` 工具（LLM 遥控器）+ Gateway 事件（默认全关，`watch_domains` / `watch_entities` 白名单过滤）；出站消息走 persistent notification。
- HA 安全边界：`shell_command` / `python_script` 等域硬拦截、entity_id 正则校验；WebSocket 30s 心跳 + 指数退避重连。
