# 多平台运维：日志、升级与日常管理

微信、飞书、QQ 都接入后，Hermes 从「跑一次试试」变成了常驻服务，真正的问题也从「怎么接」变成了「怎么日常照看」。这一章给运维最小集：出故障去哪看日志、版本怎么安全升级与回滚、多实例怎么不打架、资源给多少。全章是实操命令，可直接照抄到宿主机执行。

## 9.1 日志四来源：同一个事件，四个机位

Hermes 的 gateway 会把日志同时写到四个地方（D1 §日志），定位问题时按「就近」原则挑入口：

| # | 来源 | 入口 | 典型用途 |
|---|------|------|----------|
| 1 | `docker logs` | 容器 stdout，实时跟随 | 首选入口，看最近的报错 |
| 2 | dashboard 日志 | Web UI（Compose 里 9119 端口） | 浏览器里翻历史、查图表 |
| 3 | `container-boot.log` | 启动阶段引导日志 | 容器起不来的第一现场 |
| 4 | `hermes logs --follow` | CLI 实时跟随 | 想在终端里过滤某类日志 |

> [!tip] 大白话
> 把日志想成一场戏的四个机位：`docker logs` 是正对舞台的主摄（stdout 全记录），gateway 会 tee 一份同样的录像归档到 `~/.hermes` 的日志柜；dashboard 是导演监视屏；`container-boot.log` 是开演前的彩排录像；`hermes logs --follow` 是拿对讲机实时盯某段。同一个事件四个地方都能看到，就近挑顺手的看就行。

关键命令如下：

```bash
# 日志定位：按时间就近原则选入口

# 入口1：容器 stdout，实时跟随（最常用）
docker logs -f hermes --tail 200

# 入口1：只看最近 10 分钟的日志
docker logs hermes --since 10m

# 入口4：CLI 实时跟随。
# 注意：镜像内没有 hermes 可执行文件，不能用 docker exec，
# 必须 run 一个临时容器挂同一个数据卷来跑 CLI（D1 §故障排查）
docker run -it --rm -v ~/.hermes:/opt/data \
  nousresearch/hermes-agent logs --follow

# 入口3：启动阶段日志，与 docker logs 的 tee 副本同目录
tail -f ~/.hermes/logs/gateways/<profile>/container-boot.log

# 入口3 的兄弟：docker logs 的落盘副本
tail -f ~/.hermes/logs/gateways/<profile>/current
```

> [!warning] 常见坑
> `docker exec hermes logs` 会报 PATH 找不到二进制——镜像里根本没有 `hermes` 这个可执行文件。跑 CLI（setup / logs / gateway）一律走「临时容器 + 挂同卷」，不要试图进容器里敲命令。

## 9.2 升级与回滚：数据卷不动，先备份再动

升级的本质是「换镜像、重建容器」，数据卷 `~/.hermes` 保持原样（D1 §升级）。核心纪律是**动手前先写时间戳备份**，翻车了能一键还原。

> [!tip] 大白话
> 把数据卷想成房子，镜像是房子里的装修。升级 = 重新装修（换镜像），房子本身（`~/.hermes`）不动。时间戳备份 = 动工前先给房子拍一套全景照，装修翻车了能照着原样还原，而不是重新攒家具。

```bash
# ~/.hermes/upgrade-hermes.sh  升级流程（宿主机执行）
TS=$(date +%Y%m%d-%H%M%S)             # 生成时间戳，如 20260828-210500

# 1) 先备份：数据卷是唯一状态源，备份 = 拷贝整个目录
cp -a ~/.hermes ~/.hermes.bak.$TS

# 2) 拉新镜像（Compose 场景会按 compose 里的 image 拉取）
docker compose pull

# 3) 重建容器：volumes 映射不变，状态不丢
docker compose up -d --force-recreate

# 4) 确认启动正常
docker compose ps
```

**回滚**只需两步：把 `docker-compose.yaml` 里的 `image` 指回旧 tag，再重复上面的 2-3 步。`~/.hermes.bak.$TS` 留着别急着删，等新版本跑稳一两天再清理；确认没问题后可用 `rm -rf ~/.hermes.bak.$TS` 释放空间。

## 9.3 多平台并存：两个「排他」红线

同时接多个平台不代表能随意起多个实例，有两条硬约束：

1. **禁止两个 gateway 共享同一个数据目录**（D1 §故障排查）。gateway 启动会对 `~/.hermes` 加排他锁，第二个进程起不来。
2. **同 app_id 只能一个实例**（F1 §Troubleshooting）。这是平台侧的约束，飞书文档明确记录：同一 app_id 只认一条长连接，再起一个实例会被顶掉。

> [!tip] 大白话
> 一个档案柜只配一把主钥匙。两个 gateway 共用一个 `~/.hermes`，就像两个门卫同时开同一个档案柜——日志互相覆盖、状态互相抢写，所以 Hermes 用排他锁直接拒绝第二个人。同 app_id 同理：平台侧一个 app 只认一条长连接，多开的那个是「假钥匙」，一开就被顶掉。

## 9.4 资源建议：memory 4G / cpus 2.0

`02` 章 Compose 示例里的资源限制是官方推荐的起步值（D1 §Compose）：**memory 4G、cpus 2.0**。原因是镜像内置 Playwright + Chromium（浏览器工具）和 Python + Node 两套运行时，本地开发机内存低于 4G 时，浏览器工具容易崩。可按平台裁剪：纯聊天平台（只接微信/QQ、不跑浏览器工具）可适当调低。

```yaml
# docker-compose.yaml 片段：资源限制
services:
  hermes:
    deploy:
      resources:
        limits:
          memory: 4G
          cpus: "2.0"
```

## 9.5 需实测项

> [!note] 需实测
> - **健康端点具体 HTTP 路径**：官方文档未明说 gateway 的健康检查 URL 长什么样，部署后需自己探（可用 `curl -v localhost:8642/<path>` 试 `/health`、`/healthz` 等常见路径）。
> - **官方镜像 tag pin 策略**：官方示例默认用 `:latest`（D1 §快速开始），而实际发布用日期式 tag（如 `v2026.8.27`，当前版本 0.20.6，F2）。生产环境建议 pin 到日期 tag 再升级，避免 `:latest` 漂移；具体保留策略需实测确认。

## 本章小结

- 日志有四来源：`docker logs`（tee 到 `~/.hermes/logs/gateways/<profile>/current`）、dashboard、`container-boot.log`、`hermes logs --follow`，就近挑入口。
- 升级 = 备份（时间戳）→ pull 新镜像 → 重建容器，数据卷不动；回滚 = 指回旧 tag 重来。
- 多实例两条红线：数据目录排他锁、同 app_id 单实例。
- 资源起步值 memory 4G / cpus 2.0（Compose 示例，可裁剪）。
- 健康端点路径与 tag pin 策略列入需实测。
