# 第 4 章 自定义工具开发与注册

内置工具体系（第 2 章）、Tool Gateway（第 3 章）再加上 MCP（第 5 章），已经覆盖了绝大多数"借能力"的场景。但总有边界情形：需要专属 API 认证、必须精确执行二进制处理、或要处理流式数据。这时你就得动手写一个自定义工具。动手之前，本章先逼你回答一个更重要的前置问题：**这真的需要做成工具吗？** 多数情况下答案是否定的——写个 skill 就够了。

> 版本锚定：Hermes v0.20.x。本章所有函数签名、文件路径均照抄官方源码与贡献指南；配置以 `hermes doctor` 输出为准。

## 4.1 先决策：skill 还是 tool？

"这个问题是所有新贡献者问得最多的，答案几乎永远是 skill。"（来源 S6）这条原则同样适用于你自己——不只是给 Hermes 提 PR，也包括给自家项目加能力。

先回顾第 1 章建立的边界：tool 是**可执行能力**（"能干什么"），skill 是**程序性知识文档**（"怎么干"）。判断标准不是"想不想写代码"，而是"这个能力能不能用指令 + 现有工具表达"。

> [!tip] 大白话
> 把 skill 想成"带步骤的说明书"，把 tool 想成"一台专用机床"。说明书能指挥人手（或 Agent）用仓库里的现成工具把活干完；专用机床是只有它才能干、而且每次都必须干得一模一样的精密活。多数日常需求，一份好说明书就够了，不必专门造机床。

### 优先做成 skill 的场景

- 能力可以用「指令 + shell 命令 + 现有工具」表达；
- 只是包装一个外部 CLI 或 API，Agent 通过 `terminal` 或 `web_extract` 就能调用；
- 不需要在 Agent 里内置自定义 Python 集成或 API key 管理；
- 典型例子：arXiv 检索、git 工作流、Docker 管理、PDF 处理、用 CLI 工具发邮件（来源 S6）。

### 必须做成 tool 的场景

- 需要**端到端**打通 API key、认证流程或多组件配置，并且要由 Agent 框架统一管理；
- 需要自定义处理逻辑，每次都必须**精确执行**，不能靠 LLM "尽力理解"（best effort）；
- 处理**二进制 / 流式 / 实时事件**数据，terminal 根本传不过去；
- 典型例子：浏览器自动化（Browserbase 的会话管理）、TTS（音频编码 + 平台投递）、视觉分析（base64 图像处理）（来源 S6）。

动手前先过一遍"三连问"：

1. 能不能用 `terminal` 跑一条命令解决？能 → 倾向 skill；
2. 是不是每次都必须输出完全一致的二进制 / 结构化结果？是 → 倾向 tool；
3. 是不是要框架帮你管 key、管会话、管授权？是 → 倾向 tool。

> [!warning] 别急着造轮子
> 贡献指南把"新工具"排在贡献优先级第 6，明确说新工具 **rarely needed**。每往核心加一个工具，就多一份长期维护负担。你只是自用、且能力能用 shell + 现有工具表达时，先写 skill；只有 skill 确实表达不了，才动手写 tool。

## 4.2 注册五要素：registry.register 的五个参数

写工具之前，先看清三个文件的分工（来源 S6）：

- `tools/registry.py`：**中心注册表**。所有工具的 schema、handler、dispatch（派发）汇聚于此，是"工具总台账"。
- `toolsets.py`：**分组与预设**。把工具分进 `web`、`terminal`、`file`、`browser` 等 toolset，并定义各平台 presets 默认开哪些组。
- `model_tools.py`：**编排**。加载时触发自动发现，把注册好的工具组装成发给 LLM 的 tools 列表。

数据流一句话：`registry.py`（登记）→ `toolsets.py`（编组）→ `model_tools.py`（上呈给模型）。

任何自定义工具的入口都是这一行调用（来源 S6）：

```python
registry.register(
    name="my_tool",
    toolset="my_toolset",
    schema=MY_TOOL_SCHEMA,
    handler=lambda args, **kw: my_tool(**args, **kw),
    check_fn=_check_requirements,
)
```

五个参数逐一拆解：

- **`name`**：工具在注册表里的唯一 ID，LLM 调用时靠它定位。命名要短、小写、下划线分隔。
- **`toolset`**：工具归属的分组。决定它在 `hermes tools` 里归哪一类、随哪个 toolset 一起开关（呼应第 1 章的 toolset 机制）。
- **`schema`**：OpenAI function 格式的 JSON，描述工具叫什么、干什么、参数长什么样。这是给 LLM 看的"使用说明书"。
- **`handler`**：真正干活的函数。注意注册表传给 handler 的是一个参数字典（`args`）加 kwargs，所以标准写法是 `lambda args, **kw: my_tool(**args, **kw)`，把字典展开成具名参数再调用。
- **`check_fn`**：依赖可用性探针，返回 `bool`。比如工具依赖某个 Python 库，就在这里 import 试试：成功返回 `True`，失败返回 `False`。框架据此决定是否把该工具上呈给模型。

> [!tip] 大白话
> `registry.register` 就像公司前台登记新员工：`name` 是工牌上的名字，`toolset` 是部门，`schema` 是贴在工位上的岗位说明书（给 Agent/同事看的），`handler` 是本尊——真到干活时找的就是他，`check_fn` 是入职体检——体检不过，连工牌都不发，更不会让 LLM 看到你。

## 4.3 handler 与 schema：返回 JSON 字符串、OpenAI function 格式

### handler：返回 JSON 字符串的纯函数

handler 签名统一为 `def my_tool(param1: str, param2: int = 10, **kwargs) -> str`，返回值是**字符串**，通常是 JSON（来源 S6）。为什么必须是字符串？因为工具结果要拼回对话上下文、进 LLM 的 message，所以结构化对象得先 `json.dumps()` 序列化。handler 应当是一个纯函数：接收具名参数、算出结果、序列化返回，不碰全局状态。

### schema：OpenAI function 格式

schema 是给 LLM 看的参数契约，两层结构：

```python
MY_TOOL_SCHEMA = {
    "type": "function",
    "function": {
        "name": "my_tool",
        "description": "What this tool does and when the agent should use it.",
        "parameters": {
            "type": "object",
            "properties": {
                "param1": {"type": "string", "description": "What param1 is"},
                "param2": {"type": "integer", "description": "What param2 is", "default": 10},
            },
            "required": ["param1"],
        },
    },
}
```

要点：

- `description` 要写清"做什么 + 什么时候用"，这是 LLM 决定是否调用它的依据——写得准，模型才选得准；
- `properties` 声明每个参数的类型、描述与默认值，`required` 列出必填参数；
- 默认值同时写在 schema（`"default": 10`）和 handler 签名里，双保险。

> [!tip] 大白话
> schema 就是给 LLM 看的"点餐菜单"。菜单上写清楚"这道菜叫什么、什么口味、要不要辣（参数）"，LLM 才会照着下单（构造正确的 tool_call）。描述含糊，模型要么不点这道菜，要么点错配菜。

### check_fn：依赖可用性探针

`check_fn` 返回 `bool`。除了"依赖库是否装好"，也可以做更聪明的判断——比如联网工具检查 API key 是否已配置。框架发现 `check_fn` 返回 `False`，就会把这个工具从 LLM 可见列表里摘掉，避免模型反复调用一个必然失败的工具，浪费迭代次数（呼应第 2 章的 `HERMES_MAX_ITERATIONS` 上限）。

## 4.4 自动发现机制：discover_builtin_tools() 与 tools/*.py

内置工具**自注册**，无需手动维护导入清单（来源 S6）：

- 任何 `tools/*.py` 文件，只要**顶层**包含 `registry.register(...)` 调用，就会被 `discover_builtin_tools()`（位于 `tools/registry.py`）在 `model_tools` 加载时自动 import；
- `model_tools.py` 里**没有**一份手动维护的 import 清单——你新建一个 `tools/xxx.py` 并在顶层注册，框架下次启动就自动接上。

> [!tip] 大白话
> 自动发现就像前台的门禁系统：你入职登记（顶层调用 `register()`）的瞬间，系统就自动把你的工牌信息录进数据库，不需要人事再手动加一行。你只需要"登记"这一下，剩下的事门禁系统自己会扫到。

但这带来一个必须警惕的反面问题——**登记 ≠ 暴露**，见下一节。

## 4.5 关键一步：把 toolset 加进 toolsets.py，否则「注册但不暴露」

这是官方文档里最醒目、也最容易被新手踩中的坑：

> "你必须把工具名加进 `toolsets.py` 里对应的列表（例如 `_HERMES_CORE_TOOLS` 或一个专门的 toolset）；否则工具注册了，但永远不会暴露给 Agent。如果你引入了一个新 toolset，就在 `toolsets.py` 里加上它，并接进相关平台 presets。"（来源 S6）

也就是说，`registry.register` 只完成"登记"，`toolsets.py` 决定"上不上台"，两步缺一不可：

```
tools/xxx.py 顶层 register()   →  登记成功（注册表里有记录）
toolsets.py 列表里没有它       →  LLM 永远看不到、永远调不到
```

```python
# toolsets.py（示意）
_HERMES_CORE_TOOLS = [
    # ... 已有工具
    "my_tool",   # 不加这一行，上面 register() 等于白做
]
```

> [!warning] 最大坑：「注册但不暴露」
> 你写好了工具、测试也过了、`register()` 也调用了，但 Agent 就是调不到。十有八九是忘了把工具名加进 `toolsets.py`。排查时先查这一条，再查 toolset 是否在平台预设里启用。

**新 toolset 接平台 presets**：如果你用的是新分组（而不是塞进 `_HERMES_CORE_TOOLS`），还需要把它接进相关平台 presets——即第 1 章讲的平台预设 toolset（如 `hermes-cli`、`hermes-telegram`）。否则用户即使在 `hermes tools` 里想开这个组，也找不到它。新组必须出现在这些预设里，才会被默认或可选启用。

## 4.6 实操：从零注册一个自定义工具

### 代码：tools/my_tool.py 最小模板

下面这个最小模板整体照抄自官方 CONTRIBUTING.md（来源 S6 344–386 行），新建 `tools/my_tool.py` 填入即可跑通：

```python
"""my_tool — Brief description of what this tool does."""

import json
from tools.registry import registry


def my_tool(param1: str, param2: int = 10, **kwargs) -> str:
    """Handler. Returns a string result (often JSON)."""
    result = do_work(param1, param2)
    return json.dumps(result)


MY_TOOL_SCHEMA = {
    "type": "function",
    "function": {
        "name": "my_tool",
        "description": "What this tool does and when the agent should use it.",
        "parameters": {
            "type": "object",
            "properties": {
                "param1": {"type": "string", "description": "What param1 is"},
                "param2": {"type": "integer", "description": "What param2 is", "default": 10},
            },
            "required": ["param1"],
        },
    },
}


def _check_requirements() -> bool:
    """Return True if this tool's dependencies are available."""
    return True


registry.register(
    name="my_tool",
    toolset="my_toolset",
    schema=MY_TOOL_SCHEMA,
    handler=lambda args, **kw: my_tool(**args, **kw),
    check_fn=_check_requirements,
)
```

逐行拆讲：

1. **模块 docstring**：一句话说明工具干什么。项目代码风格要求"只在解释非显然意图时写注释"，不要流水账。
2. **导入**：`import json`（序列化返回值）+ `from tools.registry import registry`（拿中心注册表）。
3. **handler** `my_tool(...)`：纯函数。`param1` 必填、`param2` 有默认值、`**kwargs` 兜底。返回 `json.dumps(result)` 序列化后的字符串。
4. **`MY_TOOL_SCHEMA`**：OpenAI function 格式，注意是 `{"type": "function", "function": {...}}` 双层结构。
5. **`_check_requirements()`**：依赖探针，这里恒返回 `True`（无外部依赖）。真实场景替换成 import 探测或 key 检测。
6. **`registry.register(...)`**：登记。`handler=lambda args, **kw: my_tool(**args, **kw)` 把注册表传入的参数字典展开成具名参数。
7. **别忘了回到 4.5**：把 `my_tool` 加进 `toolsets.py` 的列表，并把 `my_toolset` 接进平台 presets，否则"注册但不暴露"。

> 模板里的 `do_work(param1, param2)` 是占位，换成你的真实逻辑即可；结果若是 dict/list，记得先 `json.dumps()`。

> [!example] 一个真实改法思路
> 假设要给 Agent 加一个"查询本机磁盘剩余空间"的工具：handler 里用 `shutil.disk_usage()` 拿到 `(total, used, free)`，`return json.dumps({"free_gb": free // 2**30})`；schema 里没有必填参数（`required: []`）；`_check_requirements` 里 `import shutil` 成功返回 `True`。然后加进 `toolsets.py`，重启会话即可被模型调用。

### 测试：tests/skills/test_<skill>_skill.py

工具与 skill 的测试统一约定（来源 S6）：

- 测试文件放 `tests/skills/test_<skill>_skill.py`；
- 只用 stdlib + pytest + `unittest.mock`，**不做任何真实网络调用**；
- 涉及环境变量或文件系统的依赖，用 `monkeypatch` 和 `tmp_path`；
- 运行：`scripts/run_tests.sh tests/skills/test_<skill>_skill.py -q`。`scripts/run_tests.sh` 等同 CI，必须在无密钥泄漏的 hermetic 环境里通过。

安全层由 `tools/approval.py` 承担：用正则做危险命令检测，配合用户逐次审批流（来源 S6）。你写 handler 时遵守同一条铁律——**凡是把用户输入拼进 shell 命令的地方，一律 `shlex.quote()`**，防 shell 注入（这也呼应第 3 章的 approvals 体系）。

### shell 映射：skill 引用工具的硬约束

如果你写的是 skill 而不是 tool（多数情况），SKILL.md 正文里引用工具时有两道硬约束（来源 S6）：

1. **引用的工具必须是原生 Hermes 工具或该 skill 显式期望的 MCP server**，用反引号点名，例如 `` `terminal` ``、`` `web_extract` ``、`` `read_file` ``、`` `search_files` ``、`` `patch` ``；
2. **不要点名 Agent 已经包好的 shell 命令**。想用某个能力时，用对应的原生工具，而不是教模型裸跑 shell：

| 不要写 | 要写 |
|---|---|
| `grep`, `rg` | `search_files` |
| `cat`, `head`, `tail` | `read_file` |
| `sed`, `awk` | `patch` |
| `find`, `ls` | `search_files`（`target='files'`） |
| `curl`（抓内容） | `web_extract` |
| `echo > file`, `cat <<EOF` | `write_file` |

理由：原生工具自带参数校验、审批、截断、结果结构化等框架能力；裸 shell 命令绕过了这一切。若 skill 依赖 MCP server，在 `## Prerequisites` 里写明 server 名和 setup 步骤；第三方 CLI（`ffmpeg`、`gh`、某个 SDK）可以放进 skill 的 `scripts/` 里被脚本调用，但正文要表述为"通过 `terminal` 工具调用"，而不是一段手工 shell 会话。

## 4.7 插件路径：ctx.register_tool / ctx.register_cli_command（不改核心）

不想改核心代码，又想加工具或命令？走插件路径（来源 S6）：

- 插件通过 **`ctx.register_tool`** 注册工具、**`ctx.register_cli_command`** 注册 CLI 子命令，还可以挂生命周期钩子（`pre_tool_call`、`post_tool_call`、`pre_llm_call`、`post_llm_call`、`on_session_start`、`on_session_end`）；
- **第三方产品集成**（观测后端、SaaS 连接器、付费服务接入等）一律作为**独立插件仓库**发布，落到 `~/.hermes/plugins/`（或 pip entry point），不进 Hermes 核心树——这是维护成本决策，不是质量裁决；
- 如果插件需要框架没暴露的能力，那是"扩大通用插件面"的 feature request，而不是在核心里给某个插件开特例。

> [!tip] 大白话
> 核心代码就像小区物业的围墙，`ctx` 是围墙上的统一门禁。你要加新业务，走门禁登记（`ctx.register_tool`）就行，物业不会因为你一家给墙开洞。若门禁确实不满足你，正当诉求是"加一种通用门禁"，而不是"给我家单独开洞"。

## 本章小结

- 新能力**先问是不是 skill**：能用指令 + shell + 现有工具表达，就做成 skill（arXiv / git / Docker / PDF / email CLI）；只有要端到端 auth、精确执行、或处理二进制/流式数据才做 tool（浏览器自动化 / TTS / 视觉分析）。
- 架构路径是 `tools/registry.py`（登记）→ `toolsets.py`（编组）→ `model_tools.py`（上呈），三层各司其职。
- `registry.register` 五要素：`name`、`toolset`、`schema`（OpenAI function 格式）、`handler`（返回 JSON 字符串的纯函数）、`check_fn`（依赖可用性 `bool`）。
- 自动发现：`tools/*.py` 顶层含 `register()` 即被 `discover_builtin_tools()` 自动 import，`model_tools.py` 无手动清单。
- **最大坑**：只 `register()` 不加进 `toolsets.py` = "注册但不暴露"；新 toolset 还要接平台 presets。
- 测试用 `tests/skills/test_<skill>_skill.py`（stdlib + pytest + mock、无网络），`scripts/run_tests.sh` 运行；skill 引用工具必须点名原生工具或显式 MCP server，shell 命令映射到 `search_files` / `read_file` / `patch` / `web_extract`；插件走 `ctx.register_tool` / `ctx.register_cli_command`，不改核心。

下一章，我们把视角从"项目内造轮子"切换到"生态里借轮子"——MCP 接入与排错：把任意外部能力通过 `mcp_servers` 接进普通工具注册表，并学会排查"工具不显示"。
