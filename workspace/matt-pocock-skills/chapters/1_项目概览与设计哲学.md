## 1.1 仓库背景

Matt Pocock 是 TypeScript 社区最知名的教育者之一，以 `@mattpocock` 的身份在 YouTube 上制作了大量 TypeScript 深度教程，也是 Total TypeScript 的创始人。2025 年底，他开源了 `mattpocock/skills` 仓库——一个"Skills for Real Engineers"的项目，迅速获得了 184K+ stars，成为 GitHub 上最热门的 AI Agent 项目之一。

这个仓库的本质是一组**可组合的、轻量的指令集（skills）**，供 Claude Code 和 Codex 等 AI 编码 Agent 使用。每个 skill 是一个 `< 100 行的 SKILL.md` 文件，编码了一项工程实践——从盘问需求到 TDD、从代码审查到架构改进。Matt 把这些称为"straight from my .agents directory"，是他日常工作中真实使用的技能集合。

仓库迅速增长的原因不是技术复杂度，而是它解决了一个普遍存在的痛点：**AI 编码 Agent 很好用，但你如何让它一直做好用？** 大多数用户发现，虽然 Agent 在单次对话中表现出色，但缺乏纪律性——做错事、说废话、写坏代码、越写越烂。Matt 的 skills 正是针对这四类问题的系统化方案。

## 1.2 四大问题域与对应方案

Matt 在 README 中明确列出了 AI 编码 Agent 的四种典型失败模式，以及每个模式的对应 skill 方案：

### 问题 1：对齐失败（Misalignment）

Agent 做了错误的事情。你让它写一个订单系统，它先写了一个完整的前端 UI。

**方案：Grilling 体系**
- `/grill-me`：无状态盘问，适合没有代码库的场景
- `/grill-with-docs`：有状态盘问，生成 CONTEXT.md 和 ADR
- 两者都依赖同一个核心原语 `/grilling`：一次问一个问题，带推荐答案，走决策树

### 问题 2：冗余啰嗦（Verbosity）

Agent 缺乏项目的共享行话，每次对话都要重新解释一遍上下文，浪费大量 token。

**方案：CONTEXT.md + 领域模型**
- 建立一个项目的通用语言（Ubiquitous Language）
- 把术语、定义、关系写到 `CONTEXT.md`
- 所有 skill 共享这个词汇表，避免同义反复

### 问题 3：代码不工作（Broken Code）

Agent 在没有反馈的情况下飞写代码，写出一堆看似合理但实际不工作的代码。

**方案：TDD + 调试 discipline**
- `/tdd`：严格的 red-green-refactor 循环
- `/diagnosing-bugs`：先建反馈回路再生产假设
- `/code-review`：双轴审查（规范 + 规格）

### 问题 4：架构衰退（Architecture Decay）

代码库随时间变成"代码泥球"（ball of mud）——到处是透传层、缺乏清晰边界、越来越难改。

**方案：定期的架构改进**
- `/improve-codebase-architecture`：扫描代码库，发现深挖机会
- `/codebase-design`：深模块设计词汇表（受 John Ousterhout 影响）
- "删除测试"：想象删掉一个模块，复杂度消失还是转移？

> 核心论断："AI 辅助开发质量的上限由工程纪律设定，而非模型基准。"— 来自社区深度分析 [E1]

## 1.3 设计哲学总览

### Small, Adaptable, Composable

这是仓库的三个关键词：

- **Small**：每个 skill 做一件事，SKILL.md 控制在 100 行以内。最小的 skill（grill-me）只有 3 行正文。
- **Adaptable**：skill 是指令集，不是插件。不依赖特定平台特性，Claude Code 和 Codex 都能用。
- **Composable**：skill 之间通过散文式引用组合（"Run the `/grilling` skill"），而不是硬编码的依赖链。

### 两种设计哲学的对决

有一篇社区文章 [E3] 将 Matt 的 skills 与另一个项目 **superpowers** 进行了精彩对比：

| 维度 | mattpocock/skills | superpowers |
|------|-------------------|-------------|
| 核心假设 | "模型大多做对的事" | "模型会走捷径" |
| 策略 | 提供最小锚点 | 掌控完整流程 |
| Skill 大小 | 12 行（grilling） | 689 行 |
| 复杂度 | 松散、独立、可组合 | 一体化、流程化 |
| 依赖关系 | 散文式引用 | 显式依赖注入 |

Matt 的方法论核心是：**信任模型的能力，只在必要的地方设置护栏。** 不是教模型怎么做事，而是引出模型已有的能力。这就是为什么 12 行的 grilling skill 能生效——"grill" 一词在模型的预训练中已经携带了盘问、追问、探求的含义。

### 与"本项目"的对比

| 对比维度 | 本项目 | mattpocock/skills |
|---------|--------|-------------------|
| 设计哲学 | 工作流编排（planner → orchestrator → 模板） | 松散可组合的指令集 |
| 核心流程 | 单线程研究笔记生产 | 通用 AI 编码 idea-to-ship |
| 状态管理 | workflow state file + 断点恢复 | 无统一状态管理，依赖上下文窗口 |
| 上下文管理 | 逐章处理 + token 优化规则 | Smart Zone + /handoff 分叉 |

两者并不矛盾：本项目面向的是**确定性产出**（学习笔记），Matt 的 skills 面向的是**高质量过程**（软件工程）。这正是本书要探讨的核心——如何把 Matt 的设计哲学和模式应用到更有确定性的项目框架中。

## 1.4 核心概念速览

在深入各章之前，先建立全书通用的概念地图：

### Bucket 目录体系
Skills 按用途分组到不同目录：
- `engineering/`（已推广）— 日常编码工作
- `productivity/`（已推广）— 日常非编码工作
- `misc/`（未推广）— 保留不推广
- `personal/`（未推广）— 个人绑定
- `in-progress/`（未推广）— 草稿
- `deprecated/`（未推广）— 废弃

### User-invoked vs Model-invoked
这是贯穿全书的最核心的二分法：
- **User-invoked**：仅人类可调用，零上下文负载，付认知负载
- **Model-invoked**：Agent 可自主发现并调用，付上下文负载，零认知负载

### Skill 即指令集
Skill ≠ Plugin。Skill 不安装二进制、不注册钩子、不增加功能。它就是一段精心编写的 Markdown 指令，告诉 Agent 怎么做一件事。

### Context Load vs Cognitive Load
- **上下文负载**：description 每轮占用窗口的消耗
- **认知负载**：人类必须记住 skill 存在的消耗
- 两者是跷跷板关系：一个减少，另一个增加

## 本章要点

1. Matt Pocock Skills 是一组轻量、可组合的 Agent 指令集，解决 AI 编码中的四类典型问题
2. 设计哲学根植于"信任模型能力，提供最小锚点"，与 superpowers 的"掌控流程"形成对比
3. Bucket 目录体系、User/Model-invoked 二分法、Context/Cognitive Load 权衡，是全书的基础框架
4. 本项目（学习笔记生产）和 Matt Skills（通用编码）虽然场景不同，但设计模式可以迁移
