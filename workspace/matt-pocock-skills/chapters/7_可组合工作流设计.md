# 第 7 章：可组合工作流设计

> 素材引用: [R12], [R13], [R14], [E1]

---

前 6 章分别拆解了不同的设计模式。这一章把它们串联起来，看它们如何组成一个完整的工作流系统——以及你可以如何借鉴这些组合模式。

## 7.1 ask-matt 路由器 — 工作流的"全息图"

ask-matt 是整个 skill 系统的中央路由器。它的 SKILL.md 开头说：

> "You don't remember every skill, so ask."

这是 router skill 的核心理念——你不需要记住所有 skill，只需要记住 `/ask-matt`。

### 功能地图

ask-matt 定义的完整功能地图如下：

```
主流程 (Main Flow): idea → ship
  1. /grill-with-docs → 盘问对齐
  2. 分支: 需要原型? → handoff → /prototype → handoff 回来
  3. 分支: 多会话构建?
     ├── 是 → /to-spec → /to-tickets → 每 ticket /implement
     └── 否 → 直接 /implement
  4. 每个 /implement 内部链: /tdd → typecheck → test → /code-review → commit

入口 (On-Ramps):
  ├── 涌入的 Issue → /triage
  ├── 出了 Bug → /diagnosing-bugs
  └── 模糊大项目 → /wayfinder

词汇底层 (Vocabulary Underneath):
  ├── /domain-modeling → 领域词汇
  └── /codebase-design → 模块设计

跨会话 (Crossing Sessions):
  ├── /handoff → 分叉到新会话
  └── /compact → 同会话继续

独立使用 (Standalone):
  ├── /grill-me → 无代码库时盘问
  ├── /prototype → 验证性代码
  ├── /research → 背景资料调查
  └── /teach → 多会话学习
```

### Router 的设计原则

1. **User-invoked** — ask-matt 自己就是 user-invoked，不占 context load
2. **不执行，只指路** — router 告诉你去哪个 skill，但不帮你调用它（因为 user-invoked skills 互相不可见）
3. **条件分支** — "是否需要原型？"、"是否多会话？"这些判断条件嵌入在 router 的描述中
4. **上下文纪律** — router 明确写了"前 3 步同窗口，每 implement 新会话"

### 什么时候需要 Router

前面第 3.5 节提到过，这里提供一个更具体的判断标准：

- **不需要 Router**：<5 个 user-invoked skills，你能清楚记得每个的用途
- **考虑 Router**：5-10 个，偶尔会犹豫该用哪个
- **必须 Router**：>10 个，经常需要查找

Matt 在播客中提到：大多数用户只需要 4 个核心 skill（grill-with-docs、to-spec、implement、code-review）就能覆盖 80% 的工作流。Router 是当 skill 数量超出记忆上限时的解决方案，不是默认配置。

## 7.2 Implement 管线 — 执行的终点

Implement 是"从想法到代码"的最终执行者。它用户触发的 user-invoked skill，内部委托给 model-invoked skills 构成一条管线：

```
/implement (user-invoked)
  ├── 使用 → /tdd (model-invoked)
  │     └── red-green-refactor 循环
  ├── 类型检查 → 单测 → 全量测试
  ├── 使用 → /code-review (model-invoked)
  └── commit
```

### Pre-agreed Seams（预约定边界）

Implement 最核心的设计概念是 **pre-agreed seams**：

> "The idea implement runs on is the seam — the stable interface a feature is tested at, chosen before any code is written."

这意味着在进入 implement 之前，已经通过盘问和规格确定了两件事：
1. **测试边界**：这条功能在哪层接口上测试
2. **交付顺序**：tickets 的依赖顺序已解决

Implement 不做决策，只执行。它是"手，不是头"——头已经在 grilling + to-spec 阶段完成了思考。

### 任务维度

Implement 每次处理一个 ticket，在开始下一个之前清除上下文：

```
/implement ticket-1  ← 新会话
  → /tdd → typecheck → test → /code-review → commit
  → 清除上下文

/implement ticket-2  ← 新会话
  → /tdd → typecheck → test → /code-review → commit
  → 清除上下文
```

这和第 6 章的上下文卫生规则一致——每个实现任务独立，避免 token 污染。

### 对你项目的映射

你的学习笔记项目中，"implement" 对应的是"逐章写作"：

```
/implement (逐章写作)
  ├── 预约定 seam: 大纲定义了章节范围和深度
  ├── 输入: 03_outline.md (类似 spec)
  ├── 执行: 每章新会话 (类似 implement per ticket)
  └── 完成标准: 章节内容覆盖了大纲中定义的范围
```

## 7.3 词汇表即架构 — codebase-design

codebase-design 是一个特殊的 skill——它不包含步骤（steps），全部是参考（reference）。它是其他 skill（如 tdd、improve-codebase-architecture）的共享词汇表。

### 统一术语表

| 术语 | 定义 | 禁止词 |
|------|------|--------|
| Module | 有 interface 和 implementation 的任何东西 | unit, component, service |
| Interface | 调用者必须知道的所有信息 | API, signature |
| Depth | 每单位 interface 能调用的行为量 | — |
| Seam | 可改变行为而无需在那里编辑的地方 | boundary |
| Adapter | 在 seam 处满足 interface 的具体实现 | — |
| Leverage | 调用者从 depth 获得的收益 | — |
| Locality | 维护者从 depth 获得的收益 | — |

### 为什么"统一术语表即架构"？

因为**语言决定了思考方式**。如果团队有人用"component"、有人用"module"、有人用"service"，同一个概念有多种称呼，Agent 就无法精确理解。

codebase-design 的作者（受 John Ousterhout《A Philosophy of Software Design》影响）认为：**interface 是所有调用者必须知道的总和**——不仅仅是类型签名，还包括约束、错误模式、排序要求、性能特征。这个定义比狭义的 "API" 或 "type signature" 更精确，也更有用。

### 删除测试（Deletion Test）

这是 codebase-design 提供的最实用的判断工具：

> "Imagine deleting the module. If complexity vanishes, it was a pass-through. If complexity reappears across N callers, it was earning its keep."

简单说：
- **浅模块**：删掉后复杂度消失（说明它只是在传数据）
- **深模块**：删掉后复杂度出现在 N 个调用方（说明它在封装复杂逻辑）

### 设计两次（Design It Twice）

DESIGN-IT-TWICE.md 描述了并行子代理模式：

```
派发 3+ 子代理
  ├── 子代理 1: 最小化 interface
  ├── 子代理 2: 最大化灵活性
  └── 子代理 3: 优化常见调用方
  每个子代理输出:
    - Interface
    - 使用示例
    - 实现隐藏了什么
    - 依赖策略
    - 权衡
```

这是 Matt 体系中最复杂的并行模式——不是一个 Agent 设计一个接口，而是多个 Agent 从不同角度设计，然后比较。

## 7.4 三种组合模式

从 Matt 的体系中可以提炼出三种技能组合模式：

### 模式 1：链式委托（Chained Delegation）

User-invoked → Model-invoked 的单向调用。

```
grill-me (user-invoked) → grilling (model-invoked)
implement (user-invoked) → tdd (model-invoked) → code-review (model-invoked)
```

**特点**：
- 上游是 entry point，下游是执行者
- 只有一种调用方向（user → model）
- 上下游可以独立测试

**适用场景**：工作流的主干路径。

### 模式 2：状态组合（Stateful Composition）

相同行为核心 + 不同状态策略。

```
grill-me (user-invoked, 无状态) → grilling (核心)
grill-with-docs (user-invoked, 有状态) → grilling + domain-modeling (核心 + 持久化)
```

**特点**：
- 共享同一套核心行为逻辑
- 外层封装决定是否有持久化
- 通过组合获得两种行为模式，而非复制代码

**适用场景**：同一行为有时需要保存有时不需要。

### 模式 3：并行子代理（Parallel Sub-Agents）

多 Agent 从不同角度同时工作。

```
code-review:
  ├── 子代理 1: 代码规范（Standards）
  └── 子代理 2: 规格一致性（Spec）

design-it-twice:
  ├── 子代理 1: 最小 interface
  ├── 子代理 2: 最大灵活性
  └── 子代理 3: 优化调用方
```

**特点**：
- 子代理独立运行，互不干扰
- 结果在主上下文聚合
- 适合"多角度审查"或"多方案探索"

**适用场景**：需要从不同维度评估同一件事。

### 模式选择速查

| 你的需求 | 用什么模式 | 示例 |
|---------|----------|------|
| 入口 skill 调用内部逻辑 | 链式委托 | grill-me → grilling |
| 同一行为有/无持久化 | 状态组合 | grill-me vs grill-with-docs |
| 多角度评审 | 并行子代理 | code-review, design-it-twice |
| 多个入口共享同一逻辑 | 链式委托 + 状态组合 | 结合使用 |

## 7.5 你的项目可以借鉴的工作流设计

### 建议 1：设计 Router

你的项目目前已经有多个 skills：research-planner、research-collector、outline-generator、chapter-writer、note-assembler、note-beautifier、moc-organizer。如果需要，可以创建一个 router skill 来整合它们。

对照 ask-matt 的模式：

```markdown
# ask-study-system
你不知道该用哪个 skill，所以问。

## 主流程：从想法到笔记
1. /research-planner → 澄清学习意图
2. /research-collector → 收集资料
3. 大纲 → 写作 → 组装（按流程推进）

## 独立使用
- /moc-organizer → 更新 MOC 目录
- /note-beautifier → 美化笔记格式
```

### 建议 2：规划调用边界

对照 Matt 的 model/user-invoked 划分：

| 当前 Skill | 建议调用类型 | 原因 |
|-----------|------------|------|
| research-planner | User-invoked | 入口 skill，需要人类主动启动 |
| research-collector | Model-invoked | 被 planner 或后续步骤调用 |
| outline-generator | Model-invoked | 被工作流编排调用 |
| chapter-writer | Model-invoked | 被工作流编排调用 |
| note-assembler | Model-invoked | 被工作流编排调用 |
| note-beautifier | User-invoked | 需要人类指定输出位置 |
| moc-organizer | User-invoked | 手动同步 |

### 建议 3：引入并行子代理模式

你的项目中可以在以下场景使用并行子代理：

- **资料收集阶段**：多个 subagent 同时搜索不同方向（已在 research-collector 中实现）
- **内容审查阶段**：一个子代理查技术准确性，一个查格式一致性
- **大纲评审**：一个子代理评估完整性，一个评估深度

### 建议 4：词汇表 + ADR

你的项目也需要自己的 CONTEXT.md 和 ADR 模式：

```markdown
# CONTEXT.md（你的项目）
- Workflow: 从意图到发布的状态机路径
- Todo.md: 阶段状态的单一真相源
- Phase Gate: 阶段间需要用户确认的检查点
- ...
```

即使只有 5-10 个术语也值得建立——防止 "todo list"、"state file"、"workflow run" 等术语在团队中产生歧义。

## 本章要点

1. **Router skill**（ask-matt）是认知负载的解药——一个 skill 记住所有 skill
2. **Implement 管线**将"思考"（盘问+规格）与"执行"（实现）分离——你的项目也遵循同样的分离（规划 vs 写作）
3. **词汇表即架构**——codebase-design 示范了 model-invoked 的纯参考 skill 如何成为多个 skill 的共享基座
4. **三种组合模式**：链式委托（主干路径）、状态组合（有/无持久化）、并行子代理（多角度）
5. **可迁移设计**：router 整合入口、调用边界规划、并行收集、词汇表统一
