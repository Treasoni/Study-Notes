## 2.1 Bucketed Curation 模式

mattpocock/skills 的目录结构不是随意组织的——它本身就体现了一种成熟的**发布管理哲学**。所有 skills 被分为六个 bucket 目录，每个 bucket 有明确的角色和推广状态：

```
skills/
├── engineering/      # 已推广 — 日常编码工作，出现在 README 和 Plugin 中
├── productivity/     # 已推广 — 日常非编码工作，出现在 README 和 Plugin 中
├── misc/             # 未推广 — 保留但很少使用
├── personal/         # 未推广 — 绑定到个人工作流
├── in-progress/      # 未推广 — 草稿阶段，尚未准备好发布
└── deprecated/       # 未推广 — 不再使用
```

### Promotion Gates（推广门禁）

这个体系的精妙之处在于**推广门禁（promotion gates）**——不是所有 skill 都平等。只有两个 bucket（`engineering/` 和 `productivity/`）被"推广"，它们必须同时满足三个条件：

1. 出现在顶层 `README.md` 中
2. 出现在 `.claude-plugin/plugin.json` 的 `skills` 数组中
3. 有对应的对外文档页 `docs/<bucket>/<skill-name>.md`

非推广 bucket 则**禁止**出现在以上任何位置。这是 CLAUDE.md 中明确规定的硬规则：

> "Skills in `misc/`, `personal/`, `in-progress/`, and `deprecated/` must not appear in either."

为什么要这样设计？因为**不是每个 skill 都面向公众消费**。你可能有个正在调试的草稿（in-progress），有个只为你自己工作流服务的工具（personal），有个试过但放弃的方案（deprecated）。它们对你有用，但不应该出现在公共文档中混淆视听。

### 生命周期视角

这个体系实际上覆盖了一个 skill 的完整生命周期：

1. **构思** → 创建在 `in-progress/` 中
2. **完善** → 测试、迭代、积累信心
3. **推广** → 移到 `engineering/` 或 `productivity/`，加入 README 和 Plugin
4. **维护** → 持续修剪、更新、删除过时内容
5. **废弃** → 移到 `deprecated/`（保留但不推广，供历史参考）

> **对你自建框架的启示**：你也需要一个"发布管道"。不是每个实验性的 skill 都要推向用户。用目录结构天然实现发布管理，比用配置文件更直观、更不易出错。

## 2.2 CLAUDE.md / AGENTS.md 双文件契约

仓库中有一个有趣的现象：`CLAUDE.md`（面向 Claude Code）和 `AGENTS.md`（面向 Codex）的**内容完全相同**。

这不是意外，而是一个刻意的架构决策——**跨系统的契约**。两个不同的 AI 编码平台各自读取自己的配置文件，但得到的规则完全相同。这样保证了：

- 仓库结构规则在两个平台上一致执行
- 新增 skill 时只需更新一处（实际是两处相同内容）
- 没有 "Claude 上能用、Codex 上不能用" 的认知负担

CLAUDE.md 中定义的具体规则包括：

```
- Skills 按 bucket 组织，推广 bucket 必须出现在 README 和 plugin.json
- 非推广 bucket 不得出现在上述位置
- 每个 promoted skill 有对外文档页
- ask-matt 是中央路由器，随技能变更同步更新
- scripts/link-skills.sh 用于本地 symlink 安装
```

这些规则构成了仓库的**宪法**——不写在代码里，而写在 Agent 的配置文件中，让 AI Agent 在每次交互时都知道并遵守这些规则。

## 2.3 CONTEXT.md — 领域词汇表

如果说 CLAUDE.md 是仓库的宪法，`CONTEXT.md` 就是国家的词典。它定义了整个 skill 系统中使用的**通用语言（Ubiquitous Language）**，这是从 Domain-Driven Design（Eric Evans）借来的概念。

### 词汇表结构

每个术语包含三个部分：定义、禁止词（`_Avoid_`）、关系模型。

```markdown
**Issue tracker**:
The tool that hosts a repo's issues — GitHub Issues, Linear, ...
_Avoid_: backlog manager, backlog backend, issue host

**Issue**:
A single tracked unit of work inside an Issue tracker.
_Avoid_: ticket (use only when quoting external systems)

**Decision ticket**:
A wayfinder unit — a child Issue of a wayfinder:map.
```

### 为什么需要 `_Avoid_` 指令？

因为同义词是 token 杀手。如果团队中有人说"ticket"、有人说"issue"、有人说"task"、有人说"item"，每个 skill 都需要覆盖所有这些词，否则 Agent 会困惑。通过 `_Avoid_` 指令，系统强制使用一套术语，既节省 token，又消除歧义。

### Flagged Ambiguities（已标记歧义）

这个设计极其精妙——`CONTEXT.md` 不仅记录"正确用法"，还记录**已经解决过的歧义**：

```
Flagged ambiguities:
- "backlog" was previously used to mean both the tool and the body of work
  — resolved: the tool is Issue tracker; "backlog" is no longer used as a domain term
```

为什么需要记录已解决的歧义？因为同一个团队可能在几个月后又用回旧的术语。记录解决历史就是"防止重犯同样的错误"。

### 关系模型

词汇表还形式化了实体之间的关系：

```
- Issue tracker holds many Issues
- Issue carries one Triage role at a time
- Decision ticket is an Issue (child of wayfinder:map)
```

这实际上是一个轻量级的领域模型——不画 UML 图，不用 ORM，就是用简单的句子表达实体间的约束。

> **对你自建框架的启示**：你可能不需要 50 个术语的词汇表。但即使只有 5-10 个核心术语，建立 CONTEXT.md 并严格执行 `_Avoid_` 指令，就能显著减少 Agent 的混淆和 token 浪费。

## 2.4 ADR 机制 — 架构决策记录

`.agents/adr/` 目录存放了架构决策记录（Architecture Decision Records）。仓库中有两份 ADR，但每一个都值得深入分析，因为它们示范了 **ADR 的正确写法**。

### ADR-0001: 硬/软依赖分离

> 结论：仅对硬依赖（to-tickets, to-spec, triage）添加 `/setup-matt-pocock-skills` 指针；软依赖仅引用领域词汇表，无 setup 指针。

**这个决策解决了什么问题？**

如果不加区分地在每个 skill 的描述中添加"请确保已运行 setup"，会浪费大量 token。更关键的是，Agent 可能会在不需要时也检查 setup，产生误报。

Matt 的洞察是：依赖有两类——
- **硬依赖**：没有 setup 输出就是错的（to-tickets 需要知道 issue tracker 是哪个）
- **软依赖**：没有 setup 只是输出不够尖锐（tdd 仍然能工作，只是不引用领域词汇）

前者需要显式安全网，后者优雅降级即可。

### ADR-0002: 平台特定分发

> 结论：先发 Claude Code Plugin，推迟 Codex Plugin。

**这个决策解决了什么问题？**

Claude Code 的 `plugin.json` 接受 skills 为路径数组，可以精确挑选 promoted bucket 中的子集。Codex 只接受单个路径字符串，无法表达"从 engineering 和 productivity 中挑出这些 skill"。

**被拒方案记录：**
1. 重构目录结构（影响面大，所有文件路径改变）
2. 提交重复副本到扁平目录（同步负担，第二真相源）

### ADR 编写要点

从这两个 ADR 中可以提炼出好的 ADR 模式：

- **记录被拒方案**（好：列出 2 个被拒方案并说明原因）
- **记录约束条件**（好：Codex 只接受单路径字符串）
- **记录技术原因**（好：symlinks 在 install 时不存活）
- **记录后续待办**（好："Revisit when Codex supports..."）
- **形成检查清单**（好："Invariants this creates" 列出必须维护的规则）

> **对你自建框架的启示**：即使只有 2-3 个架构决策也值得写 ADR。被拒方案 + 技术原因 这两项是最有价值的部分——几个月后你不会记得"为什么没选方案 B"。

## 2.5 双分发机制

仓库提供了两种安装方式：

### skills.sh 安装器

```bash
npx skills@latest add mattpocock/skills
```

- 将文件**复制**到项目目录
- **可编辑** — 你可以 fork 和修改
- 适用于 Claude Code、Codex、Cursor 等所有平台
- 每次 `git pull` 后需重新运行以获取更新

### Claude Code Plugin

- 在 Claude Code Plugin 市场中安装
- **只读** — 不可编辑，但自动更新
- 适用于不想维护 fork 的用户
- 通过 `.claude-plugin/marketplace.json` 注册

### 为什么需要两种方式？

因为不同的用户有不同的需求。想深度定制的开发者需要 skills.sh 的可编辑性；想要"开箱即用、永远最新"的用户需要 Plugin 的自动更新。两种方式的并存不是功能膨胀，而是对用户需求的务实响应。

> **对你自建框架的启示**：在项目早期，只需要 skills.sh 或本地目录方式就够了。Plugin 分发是推广阶段才需要考虑的事。

## 2.6 代码示例：典型目录结构

以下是仓库的完整目录结构示意（省略非关键文件）：

```
mattpocock/skills/
├── CLAUDE.md                  # 宪法（Claude Code 规则）
├── AGENTS.md                  # 同内容（Codex 规则）
├── CONTEXT.md                 # 词典（通用语言）
├── README.md                  # 对外文档首页（含 skill 列表）
│
├── skills/
│   ├── engineering/           # [已推广] 编码技能
│   │   ├── ask-matt/SKILL.md
│   │   ├── grill-with-docs/SKILL.md
│   │   ├── implement/SKILL.md
│   │   ├── tdd/SKILL.md
│   │   ├── code-review/SKILL.md
│   │   ├── triage/SKILL.md
│   │   ├── wayfinder/SKILL.md
│   │   ├── codebase-design/
│   │   │   ├── SKILL.md
│   │   │   ├── DEEPENING.md
│   │   │   └── DESIGN-IT-TWICE.md
│   │   └── ...
│   │
│   ├── productivity/          # [已推广] 非编码技能
│   │   ├── grill-me/SKILL.md
│   │   ├── grilling/SKILL.md
│   │   ├── handoff/SKILL.md
│   │   ├── writing-great-skills/
│   │   │   ├── SKILL.md
│   │   │   └── GLOSSARY.md
│   │   └── ...
│   │
│   ├── in-progress/           # [草稿] 不推广
│   ├── misc/                  # [保留] 不推广
│   ├── personal/              # [个人] 不推广
│   └── deprecated/            # [废弃] 不推广
│
├── docs/
│   ├── engineering/           # 推广技能的对外文档
│   └── productivity/
│
├── .agents/
│   ├── adr/
│   │   ├── 0001-*.md
│   │   └── 0002-*.md
│   └── invocation.md
│
└── .claude-plugin/
    ├── plugin.json
    └── marketplace.json
```

### 结构中的架构模式

1. **目录即配置**：推广状态不写在 YAML/JSON 中，而是由目录位置决定。减少了配置文件的维护。
2. **单文件技能**：每个 skill 以 `SKILL.md` 为核心，扩展文件（GLOSSARY.md、DEEPENING.md）放在同目录下，遵循 co-location 原则。
3. **文档镜像**：`docs/` 目录的结构是 `skills/` 的镜像，但只包含推广技能——不重复创建，但保持结构一致。
4. **跨平台契约**：`CLAUDE.md` 和 `AGENTS.md` 内容相同，保证两个平台上规则一致。

## 本章要点

1. **Bucket 目录**：用目录位置实现推广状态管理，覆盖 skill 的完整生命周期
2. **双文件契约**：CLAUDE.md / AGENTS.md 作为跨平台宪法，让两个 Agent 系统遵守同一套规则
3. **CONTEXT.md**：明确术语定义 + `_Avoid_` 指令 + Flagged ambiguities，防止词汇漂移
4. **ADR 机制**：记录架构决策、被拒方案、约束条件——好的 ADR 是团队的集体记忆
5. **双分发**：skills.sh 可编辑 vs Plugin 只读自动更新，满足不同用户需求
6. **目录即架构**：目录结构和文件组织方式本身就是架构声明，比 YAML 配置更直观

> **对你自建框架的启示**：从第一天就建立好目录规范——推广 bucket、CONTEXT.md、ADR 目录。这些基础设施成本极低，但一旦 skill 数量增长，重构目录的代价远高于一开始就做好。
