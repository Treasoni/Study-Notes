# 第 3 章：调用模型深度解析

> 素材引用: [R3], [R6], [R7], [E3]

---

## 3.1 为什么 Invocation 是核心轴

在 Matt Pocock 的设计体系中，整个 skill 分类只有一个轴：**调用方式（Invocation）**。

不是按功能分（"这个是编码的，那个是沟通的"）、不是按复杂度分（"这个简单，那个难"）、不是按使用频率分。只有**谁可以调用它**这一个问题。

这个单一轴的设计选择本身就是重要的架构决策。为什么只需要一个轴？

### 因为其他维度都不是独立的

- 功能分类 → 由目录 bucket 解决（engineering vs productivity）
- 复杂度 → 由 SKILL.md 的行数限制控制（<100 行）
- 使用频率 → 由 router skill 解决（ask-matt 帮你记住所有 skill）

剩下的、真正需要形式化的只有：**这个 skill 应该由人类手动触发，还是 Agent 可以自主发现并调用？**

### 核心概念：两种负载

这个问题的答案取决于一个根本权衡：

```text
上下文负载 (Context Load)  ↔  认知负载 (Cognitive Load)
    模型付出                          人类付出
```

- **Context Load**: Model-invoked skill 的 description 每轮对话都存在于上下文中，消耗 token 和注意力
- **Cognitive Load**: User-invoked skill 必须由人类记住并手动触发，消耗脑力

它们是跷跷板：你减少一个，另一个就会增加。

## 3.2 User-Invoked 模式

User-invoked skill 的特征非常简单：去掉 description，让 Agent 不知道它的存在。

### 技术实现

```yaml
# 在 SKILL.md 的 frontmatter 中：
---
name: grill-me
description: A relentless interview to sharpen a plan or design.
disable-model-invocation: true
---
```

关键点：
- `disable-model-invocation: true` → Agent 看不到这个 skill
- description 面向**人类**（一行摘要，没有触发词列表）
- 其他 skill **无法**调用它（因为看不到 description）

### 代价

**认知负载** —— 你得记住它存在。这是 User-invoked 的代价。当 user-invoked skills 增加到超过你记忆上限时，就需要一个 **router skill**（见 3.5 节）来帮助记忆。

### 优势

**零上下文负载** —— 因为 description 不存在，它不占用每轮对话的 token。对于一个你每周只用一次但每次都用很久的 skill，零上下文负载是最优选择。

### 什么时候选择 User-Invoked

- 你**只在需要时手动触发**它
- Agent **不需要**自主决定调用它
- 其他 skill **不需要**引用它
- 你愿意承受记住它存在的认知负担

---

## 3.3 Model-Invoked 模式

Model-invoked skill 是默认状态——保留 description，让 Agent 能看见并理解它的用途。

### 技术实现

```yaml
# 省略 disable-model-invocation → 默认 model-invoked
---
name: grilling
description: Grill the user relentlessly about a plan, decision, or idea.
  Use when the user wants to stress-test their thinking, or uses any
  'grill' trigger phrases.
---
```

关键点：
- 省略 `disable-model-invocation` → Agent 可见
- description 面向**模型**：包含触发词（"Use when...", "mentions...", "trigger phrases"）
- 其他 skill 可以通过名称调用它（"Run the `/grilling` skill"）

### 代价

**上下文负载** —— description 每轮对话都在上下文中。Matt 的建议是：一个 model-invoked skill 的 description 应该**比正文更需要修剪**，因为它每轮都在消耗 token。

### 额外的角色：共享参考

Model-invoked 还有一个特殊用途：当一个 skill 的内容全部是参考（reference）而非步骤（steps）时，它可以作为**多个其他 skill 的共享词汇库**。其他 skill 在运行时调用它来获取共同的术语定义。这是 codebase-design 的定位——它被 tdd 和 improve-codebase-architecture 调用。

### 什么时候选择 Model-Invoked

- Agent 需要**自主决定调用**它
- 其他 skill 需要**引用**它
- 它作为**共享参考**存在
- 你愿意承受 description 持续的 token 消耗

---

## 3.4 选择决策树

基于以上分析，可以整理出清晰的决策路径。以下是你可以直接用在项目中的决策树：

```
这个 skill 应该让 Agent 知道吗？
├── 需要 Agent 自主触发吗？
│   ├── 是 → Model-Invoked（付 context load）
│   └── 否 → 往下看
│
├── 其他 skill 需要调用它吗？
│   ├── 是 → Model-Invoked（付 context load）
│   └── 否 → 往下看
│
├── 它是多个 skill 的共享参考吗？
│   ├── 是 → Model-Invoked（付 context load）
│   └── 否 → User-Invoked（付 cognitive load）
```

### 实际项目中的选择

Matt 的仓库有 ~22 个活跃 skill，其中只有 6 个是 model-invoked：

| User-Invoked (16) | Model-Invoked (6) |
|---|---|
| ask-matt, grill-me, grill-with-docs | grilling |
| implement, triage, wayfinder | tdd, diagnosing-bugs |
| to-spec, to-tickets | codebase-design |
| handoff, teach | domain-modeling |
| writing-great-skills | code-review |
| prototype, research | resolving-merge-conflicts |

比例大约 **3:1**（user-invoked 占多数）。这印证了 Matt 的哲学：**只在必要时让 Agent 自主调用**，否则保持 user-invoked 以节省 context load。

## 3.5 Router Skill 模式

当 user-invoked skills 增加到超过你的记忆上限时（对大多数人来说大概是 5-7 个），**认知负载**就变成了问题。Matt 的解决方案是 **router skill**。

### ask-matt 的设计

```markdown
# Ask Matt
You don't remember every skill, so ask.

A flow is a path through the skills. Most paths run along one main flow...
```

Router skill 是 user-invoked（它自己不占 context load），但它是一个目录，告诉你其他 user-invoked skills 在哪儿、什么时候该用哪个。

### Router 能做什么（和不能做什么）

- **能**：命名其他 skill，说明触发条件，描述工作流
- **不能**：直接调用其他 user-invoked skills（因为它们没有 description，router 也看不见）
- **能**：描述 model-invoked skills 的用途（通过 prose 引用）

router 本质上是一个**带记忆功能的索引**：你只需要记住 `/ask-matt`，其他的交给它。

### 什么时候需要 Router

这是一个实用的判断标准：如果你发现自己经常在"该用哪个 skill"上犹豫，或者你需要脑内列出技能清单，就需要一个 router。你可以从 2-3 个 skill 开始，等增加到 7-8 个时再引入 router。

> **对你自建框架的启示**：在项目早期（<5 个 skills），不需要 router。但设计目录时预留一个 `router.md` 的位置，做好将来扩展的准备。

## 3.6 核心规则：调用边界

这是 Matt 体系中最容易被忽视但最关键的设计规则：

> **User-invoked skill 可以调用 model-invoked skill，但绝不调用另一个 user-invoked skill。**

为什么？因为 user-invoked skill 对 Agent 是不可见的。如果 `skill-A`（user-invoked）尝试调用 `skill-B`（也是 user-invoked），Agent 会看到 `skill-A` 的指令 "Run `/skill-B`" 但找不到 `skill-B`——它在上下文中不可见。

这个规则的实际效果是**调用方向永远是从上到下**：

```
User (人类)
  │
  ▼
User-Invoked Skills (可见于人类)
  │
  ▼
Model-Invoked Skills (可见于 Agent 和人类)
  │
  ▼
共享参考 (codebase-design, domain-modeling 等)
```

这一层层的调用边界相当于代码中的访问控制——public / internal / private。User-invoked 是 public interface，model-invoked 是 internal API，共享参考是 private 模块。

### 这个规则对你项目的影响

当你设计自己的 Agent 框架时，遵循这个规则意味着：

1. **入口 skill**（用户直接输入的）统一为 user-invoked
2. **内部 skill**（被入口调用的）统一为 model-invoked
3. **共享词汇**（被多个内部 skill 引用的）也是 model-invoked，但内容全部是 reference
4. **禁止** user-invoked 相互调用——如果你发现有两个 user-invoked 需要互相引用，说明该合并或引入 router 了

---

## 本章要点

1. **单一分类轴**：Invocation 是唯一需要形式化的维度——其他维度由目录、行数限制和 router 解决
2. **Context Load vs Cognitive Load**：model-invoked 付 token 代价，user-invoked 付记忆代价——两者权衡决定了你的 skill 设计
3. **3:1 比例**：实际项目中 user-invoked 占多数，只在必要时才让 Agent 自主发现
4. **Router Skill**：认知负载的解药——当一个 skill 记住其他所有 skill
5. **调用边界规则**：User-invoked → Model-invoked → 共享参考，不可逆向，不可跨级

> **对你自建框架的启示**：从第一天就规划好调用边界。把入口操作设为 user-invoked，把可复用逻辑设为 model-invoked，建立你自己的 CONTEXT.md 作为共享参考。这个基础架构的投入产出比极高。
