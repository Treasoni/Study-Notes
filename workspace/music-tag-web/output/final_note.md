## 第一章 项目定位与能力边界

装软件之前先想清楚它替谁干活，能省掉后面返工。这一章回答四个问题：它解决什么，它说的「元数据」「刮削」是什么意思，V1 和 V2 该选哪个，以及它明确不做什么。

### 1.1 一句话定位：它替谁解决什么问题

官方给 V1 的定位是「可以编辑歌曲的标题，专辑，艺术家，歌词，封面等信息的应用程序」[D6](https://xiers-organization.gitbook.io/music-tag-web/xiang-mu-jie-shao.md)。痛点则在同页说破：

> 在使用 Navidrome 时，我存储音乐文件放在远程服务器上或 NAS 中，本地的 Musictag 和 mp3tag 并不能完全满足我的需求，我需要直接在 NAS 上去需改存储的音乐文件标签。

（原文引用，「去需改」为原文自带笔误。）

Musictag、mp3tag 这类桌面工具只能操作本机磁盘；音乐放 NAS 上就得拖回本地改完再传回去。Music Tag Web 让编辑器跑在服务器上，你在浏览器里操作，文件始终待在原地。

仓库 README 自述它是「Navidrome / Jellyfin 配套边车工具，替代本地 MP3Tag、MusicBrainz Picard」（项目自述，README 有 SEO 改写痕迹，仅作参考）。有媒体服务器它是补充，没有也不影响使用——V1 手册页面树里全是标签操作 [T17](https://xiers-organization.gitbook.io/music-tag-web/llms.txt)。

> [!tip] 大白话
> 「自托管」就像自家厨房：菜（音乐文件）在自己家，锅（软件）也架在自己家，没人经手你的菜。不像用别人家的外卖平台——那得先把菜送出去。

### 1.2 两个先要懂的词

官方对元数据的定义：

> 元数据通常是指我们在音乐流媒体平台看到的与歌曲息息相关的信息，包括歌曲名称、演唱者、作词、作曲、唱片公司、发行公司等等，一般内嵌于音乐文件中，与音乐共同存在。[D5](https://xiers-organization.gitbook.io/music-tag-web-v2/ming-ci-jie-shi.md)

README 里换了个叫法「ID3 标签」，指的是同一批信息。

> [!tip] 大白话
> 音乐文件像快递包裹：音频是箱里的货，元数据是箱外的面单——歌名、歌手、专辑、封面、歌词都写在这张单子上。播放器通常不拆箱子只读单子，所以面单写错，音箱、车机、手机会一起认错。

官方对刮削的定义：

> 刮削是音频播放软件及音乐管理软件的一项功能，它可以自动识别音乐文件，并在线获取相应的专辑封面、歌曲名称、艺术家、专辑信息、流派和发行日期等数据，使得管理和播放本地音乐文件变得更加便捷。[D5](https://xiers-organization.gitbook.io/music-tag-web-v2/ming-ci-jie-shi.md)

> [!tip] 大白话
> 刮削 = 给一箱没写面单的包裹补面单：先「认货」（识别这是什么歌），再上网查回资料，最后抄到文件上。它是「联网查资料 + 写回本地文件」，不是下载音乐（准确性另见 1.6）。

V2 名词解释把相关动作拆成三个近义词。下表**逐字**照录该页原文；三行原文均以「本项目中的功能，」起头，为省版面提到表前：

> V2 名词解释页三个词条的开头一律是：「本项目中的功能，」

| 术语 | 官方定义（V2 名词解释页，逐字） |
| --- | --- |
| 手动刮削 | 选择需要修改文件或文件目录，可自定义修改音乐元数据中的内容。 |
| 自动刮削 | 选择需要修改文件或文件目录，可自动从音乐流媒体平台搜索元数据实行刮削操作 |
| 后台刮削 | 固定的文件目录下，可自动从音乐流媒体平台搜索元数据、整理文件夹、重命名等一系列操作 |

差别在「谁选文件、谁查资料」：手动是自己填，自动是软件替你查，后台则是你只把新歌丢进一个目录，剩下它全包。用法见第四章。

### 1.3 支持的音频格式

V1 项目介绍首段列出的清单是 FLAC、APE、WAV、AIFF、WV、TTA、MP3、MP4、M4A、OGG、MPC、OPUS、WMA、DSF、DFF 等音频格式 [D6](https://xiers-organization.gitbook.io/music-tag-web/xiang-mu-jie-shao.md)；仓库 README 的清单顺序略有不同（MP4 排在最后），但集合一致，都是这 15 种。

这份清单说的是「能读写标签」；个别功能对格式另有要求（第五章举例）。

### 1.4 V1 与 V2：定位差别

README 把两套部署说明并排放在同一个文件里，端口却不一样，这是最容易踩的第一个坑。

| 维度 | V1（「音乐标签」Web 版） | V2（Music Tag Web V2） |
| --- | --- | --- |
| 官方定位 | 「可以编辑歌曲的标题，专辑，艺术家，歌词，封面等信息的应用程序」[D6](https://xiers-organization.gitbook.io/music-tag-web/xiang-mu-jie-shao.md) | 「集合音乐标签刮削和音乐播放一体的个人音乐库解决方案」[D1](https://xiers-organization.gitbook.io/music-tag-web-v2/xiang-mu-jie-shao.md) |
| 功能范围 | 标签刮削与编辑 | 官方称具有 V1 版本的所有功能，另有新增 [D1](https://xiers-organization.gitbook.io/music-tag-web-v2/xiang-mu-jie-shao.md) |

V2 新增功能里与后文相关的是「插件模块」与「元数据版本管理」两条，官方对后者的描述是「自动记录每次元数据修改历史，支持版本查看、差异对比与一键回退」[D1](https://xiers-organization.gitbook.io/music-tag-web-v2/xiang-mu-jie-shao.md)。另有一条非技术差别：V2 需要激活，激活信息落在 `/app/data`，属于第三章。

> [!warning] 官方称 V2 包含 V1 全部功能，但 V2 手册未为这三项提供独立页面，实际入口需在界面中确认
> V2 项目介绍页写明「V2 版本具有 V1 版本的所有功能」，但 V2 手册页面树中检索不到「切割音轨」「拆分文件名称」「简繁体转换」的独立页面。本笔记的推断是它们被并入了其他功能（仅为推断）。本笔记不把这三项当作 V2 已确认的独立功能；你在第五章看到对应小节时，请以界面里实际是否存在为准。

### 1.5 能力边界：它不做什么

README 免责声明里被加粗的那句，就是整个项目的边界声明：

> 本自托管项目仅编辑本地已有音乐文件元数据，不提供下载音乐本体！

两层意思：一是**只编辑已有的文件**——不帮你找歌、不下载音频，刮削拿回来的是封面、歌名、艺术家这类描述信息，不是音频本体；二是**不碰你不给它的东西**——README 自述「所有曲库文件本地存储不上传第三方」。

还有一件文档没写、但必须有预期的事：它改的是你的文件本身，第四章会讲清「写入元数据」与「写入数据库」两种模式的后果差异。**本笔记建议**动手前先备份 `/app/data` 与音乐文件本身。官方文档在升级页只写到「确保所有重要数据都已正确挂载到持久化存储上，防止数据丢失」[F4](https://xiers-organization.gitbook.io/music-tag-web-v2/jiao-cheng-wen-zhang/zen-me-geng-xin-sheng-ji-ban-ben-ne.md)，并未给出具体的备份步骤（升级相关细节见附录 B）。

平台支持上有一处口径要分辨：仓库 README 自述「适配群晖、威联通、Linux 小主机 Docker 部署」，但官方手册的部署页里**未见威联通专页**（V2 手册部署页只覆盖群晖、1Panel、绿联、飞牛云 fnOS、极空间）。所以官方**没有**给出威联通部署步骤，本笔记也不为它编内容——请以第二章的通用 Docker Compose 写法为准。

它还对外**开放 API**：官方举例 info 接口供 homepage 展示信息，lyrics 接口供音流 app 展示歌词，health 接口供 Docker 健康检查心跳检测 [D5](https://xiers-organization.gitbook.io/music-tag-web-v2/ming-ci-jie-shi.md)。

## 第二章 部署（以 Docker Compose 为主）

上一章交代了它是什么、能做什么；这一章解决「让它真正跑起来」。部署是整个流程里最容易"手一抖就白忙"的一环：卷挂载写错，程序照样启动，但你打开界面看到的是一片空曲库；`/app/data` 忘了挂，容器重启一次，配置和激活状态全丢。所以本章不直接甩一份 compose 让你抄，而是先把容器里那几条**固定路径**讲透，再动手。本章以通用 Docker Compose 为主线，NAS 的平台差异收在 2.6。

### 2.1 部署前必须知道的容器路径与挂载概念

#### 一句话定位：什么是「目录挂载」

官方名词解释里把绑定挂载（Bind Mounts）定义为容器与宿主机之间共享文件或目录的方式，原文是：「绑定挂载（Bind Mounts）是 Docker 容器与宿主机之间共享文件或目录的一种方式。它允许你将宿主机上的任意路径直接映射到容器内的指定路径。」[^c2-d5]

拆开看，一次挂载要写两个路径[^c2-d5]：

- **宿主机地址（Host Path）**：你的 NAS 或服务器上的真实目录，你想让容器用到的那份数据所在的地方。这个由你决定。
- **容器内地址（Container Path）**：数据在容器内部"出现"的位置。官方补了一句关键的话：「容器内的地址一般是开发者定义的路径位置，不可修改了。」[^c2-d5]

#### 具体产物：这个项目定义了三个容器内路径

对 Music Tag Web 来说，右边那一列（容器内路径）是作者定死的，你只能换左边：

```text
宿主机（你的 NAS / 服务器）                容器内部（music-tag-web）
/你的音乐目录        ──── 挂载 ────►      /app/media      # 曲库
/你的配置目录        ──── 挂载 ────►      /app/data       # 配置与数据库
/你的下载目录        ──── 挂载 ────►      /app/download   # 后台刮削监控目录
```

三个路径各自的用途，官方 Compose 部署页给的说明是：`/path/to/your/music` 换成「你的 NAS 上音乐文件夹的绝对路径」，`/path/to/your/config` 换成「你新建的一个目录路径，用于存放应用程序的配置文件」，而 `/path/to/your/download` 换成「你新下载音乐的目录，不与媒体库重复和重合，用于后台刮削监控目录」[^c2-d4]。

#### 带具体值的可代入例子

假设你的曲库在 `/volume1/music`，想给容器配置单独建一个 `/volume1/docker/mtw`，下载目录是 `/volume1/downloads`，那么三条挂载就写成：

```text
/volume1/music      : /app/media
/volume1/docker/mtw : /app/data
/volume1/downloads  : /app/download
```

反过来说：如果你把宿主机路径写成 `/volume1/music`，却在容器里期待 `/app/media` 指向别处，那是做不到的——右边不可改。

#### 对照表：左右两边谁说了算

| 位置 | 写法示例 | 谁决定 | 能否改 | 改错的后果 |
| --- | --- | --- | --- | --- |
| 宿主机路径（冒号左边） | `/volume1/music` | 你 | 随便改，指向你自己的目录即可 | 指到空目录 → 界面里曲库为空 |
| 容器内路径（冒号右边） | `/app/media` | 项目作者 | **不可改** | 改成别的 → 程序找不到数据，等于没挂 |
| 宿主机端口（`-p` 左边） | `8002` | 你 | 可改，冲突时换一个 | 记错端口 → 浏览器打不开 |
| 容器内端口（`-p` 右边） | `8002` | 项目作者 | **不可改**（V2 为 8002） | 改成 8001 → 连不上服务 |

> [!tip] 大白话
> 把容器想成一套**已经装修好的出租屋**：屋里的三个柜子——`/app/media`（放唱片）、`/app/data`（放钥匙和账本）、`/app/download`（收快递的暂存区）——位置是房东装死的，你不能挪。你能做的是在屋外挑三个真实房间，用一根管子接过去，让屋里那个柜子"通"到你指定的房间。管子接错房间，柜子本身还在，只是永远是空的。

> [!tip] 实践建议：先建目录，再写 compose
> 动手前先在宿主机上把目录准备好：曲库目录（已有就跳过）和配置目录（新建一个）。配置目录建议放在专门留给 Docker 的位置，例如 `/volume1/docker/mtw`，将来整体备份、迁移都只动这一个文件夹。之所以强调"先建"，是因为 Docker 遇到不存在的宿主机路径时通常不会报错——它会替你建一个空目录，于是你得到一个"挂上了、但是空的"曲库，比直接报错更难排查。

> [!note] 核心概念：容器与宿主机的边界
> 容器有自己独立的文件系统，默认**看不见**宿主机上的任何目录。挂载就是在这道边界上凿一个洞：左边是边界外的真实目录，右边是边界内的固定挂载点。所以"容器里能不能看到我的音乐"，完全取决于你有没有挂、挂对没挂对，而不是取决于文件是否存在于你的机器上。

> [!warning] 易错点
> 挂载路径的冒号左右**不能写反**。`-v /app/media:/volume1/music` 这种写法不会报错，但你会得到一个空的曲库，而且极难一眼看出问题。

### 2.3 Compose 部署（三卷、端口映射、重启策略）

#### 官方原始 compose

Docker Compose 部署页给出的完整配置如下（逐字照录）[^c2-d4]：

```yaml
version: '3'

services:
  music-tag:
    image: xhongc/music_tag_web:latest
    container_name: music-tag-web
    ports:
      - "8002:8002"
    volumes:
      - /path/to/your/music:/app/media
      - /path/to/your/config:/app/data
      - /path/to/your/download:/app/download
    restart: always
```

把三处 `/path/to/your/...` 换成你自己的路径即可运行。这就是官方推荐的部署形态：**三个卷**。

#### 逐行拆解

- `ports: - "8002:8002"`：冒号左边是宿主机端口，右边是容器内端口。
- `volumes` 三行：分别对应 2.1 讲过的 `/app/media`、`/app/data`、`/app/download`。
- `restart: always`：容器退出后自动拉起（下一段会说明这里我们改用 `unless-stopped`）。

> [!note] 核心概念：端口映射
> 容器是一个隔离的网络环境，容器内部监听 8002，宿主机上的 8002 默认并不会自动转发给它。`-p 8002:8002`（compose 里就是 `ports` 那一行）就是做这件事：**把宿主机的 8002 接到容器的 8002**。和挂载一样，右边（容器内）是项目定死的，左边（宿主机）由你决定。

> [!tip] 大白话
> 端口映射像**公司总机转分机**：外面的人只知道公司总机号（宿主机端口），打进来之后总机帮你转到某个分机上（容器端口）。分机号是内部分配的、不能自己乱改（8002 就是 8002）；总机号对外公示，冲突了可以换一个。所以"我改端口"永远只改左边。

#### 三个卷：为什么推荐照单全收

| 卷 | 挂载点 | 装什么 | 不挂会怎样 |
| --- | --- | --- | --- |
| 第一 | `/app/media` | 你的音乐库 | 界面里看不到任何歌曲 |
| 第二 | `/app/data` | 配置与数据库（含 V2 激活信息） | 重建容器后配置、激活状态丢失 |
| 第三 | `/app/download` | 后台刮削的监控目录 | 官方 Compose 页给出的第三个卷，用于「后台刮削监控目录」[^c2-d4] |

第三卷按官方说明是「你新下载音乐的目录，不与媒体库重复和重合，用于后台刮削监控目录」[^c2-d4]。

> [!warning] 关于第三卷的口径，请照官方，不要照本笔记
> 官方 `docker run` 示例只挂了两个卷（不含 `/app/download`），Compose 示例挂了三个，官方**没有说明两者等价或如何取舍**[^c2-d3][^c2-d4]。
> 本笔记的推荐是：**以 Compose 的三卷为准**。至于"不用后台刮削就可以省掉第三卷"，这是**本笔记的推断**，不是官方说法；`/app/download` 是否必需、缺失时后台刮削是否仍可用，本轮收集中 `未取到`。稳妥做法是三个都挂上。

#### 重启策略：三种写法，统一用 `unless-stopped`

同一个项目里出现过三种重启写法[^c2-d3][^c2-d4][^c2-d7]：

| 出处 | 写法 | 含义 |
| --- | --- | --- |
| V2 Docker 部署页 | `--restart=unless-stopped` | 崩溃或重启后自动拉起；但**你手动停止过**的容器不会自动再起 |
| V2 Compose 页 | `restart: always` | 无论什么原因退出都自动拉起，包括你手动停掉的 |
| V1 快速开始页 | `--restart=always` | 同 `always` |

**本笔记统一采用 `unless-stopped`**：它既有"挂了自动拉起"的可靠性，又尊重你手动停容器的意图——你想停它做维护时，它不会立刻自己爬起来。

> [!warning] 两个 compose 层面的常见坑
> - **宿主机目录先建好**：路径不存在时 Docker 常会自己造一个空目录，表现为"挂上了但里面什么都没有"。
> - **端口冲突**：宿主机 8002 已被别的服务占用时，`docker compose up -d` 会直接失败。把 `ports` 左边改成别的端口即可，例如 `"18002:8002"`——右边 8002 保持不动，因为那是容器内的固定值。改完记得访问地址也跟着换成新端口。

#### 改好的可运行版本

把路径和重启策略换成我们推荐的形式：

```yaml
version: '3'

services:
  music-tag:
    image: xhongc/music_tag_web:latest
    container_name: music-tag-web
    ports:
      - "8002:8002"           # 宿主机:容器内；右边 8002 不可改，左边冲突时可换
    volumes:
      - /volume1/music:/app/media           # 曲库，右边不可改
      - /volume1/docker/mtw:/app/data       # 配置与数据库，右边不可改
      - /volume1/downloads:/app/download    # 后台刮削监控目录，不与曲库重合
    restart: unless-stopped
```

保存为 `docker-compose.yml`，在它所在目录执行：

```bash
docker compose up -d      # 后台启动；首次会自动拉镜像
docker compose logs -f    # 观察启动日志，Ctrl+C 退出查看
```

> [!tip] 实践建议
> 这份 compose 是"最小可用"版本。如果你后续想启用容器内一键自动更新等进阶能力，它们对挂载有额外要求。相关做法集中在附录 B，本处不展开——先把最小可用版跑通，再回附录按需加。

### 2.4 `docker run` 对照写法

不想用 compose 也能跑。官方 Docker 部署页给的是一条 `docker run`（原文为一行，下面为提高可读性折行）[^c2-d3]：

```bash
docker run -d \
  -p 8002:8002 \
  -v /path/to/your/music:/app/media \
  -v /path/to/your/config:/app/data \
  --name=music-tag-web \
  --restart=unless-stopped \
  xhongc/music_tag_web:latest
```

官方对参数的说明是：把 `/path/to/your/music` 换成「你的 NAS 上音乐文件夹的绝对路径」，把 `/path/to/your/config` 换成「你新建的一个目录路径，用于存放应用程序的配置文件」[^c2-d3]。绿联部署页给的命令与此一致，只是前面多了 SSH 登录步骤[^c2-n3]。

#### 与 Compose 的差异（这是本章必须盯住的一处）

| 对比项 | Compose（2.3） | `docker run`（官方 D3 示例） |
| --- | --- | --- |
| 卷的数量 | **3 个**（含 `/app/download`） | **2 个**（不含 `/app/download`） |
| 重启策略 | `restart: always` | `--restart=unless-stopped` |
| 容器名 | `container_name: music-tag-web` | `--name=music-tag-web` |
| 端口 | `"8002:8002"` | `-p 8002:8002` |

> [!warning] 用 `docker run` 起步的人，最容易漏掉第三个卷
> 官方 `docker run` 示例只有两个 `-v`，而 Compose 示例有三个，官方未说明二者等价或如何取舍[^c2-d3][^c2-d4]。如果你打算使用后台刮削，按 2.3 的说明补上第三个 `-v`：
> `-v /volume1/downloads:/app/download`。

#### V1 的写法（供对照，别照抄到 V2）

V1 快速开始页的四步如下[^c2-d7]：

```bash
# 1. 拉镜像
docker pull xhongc/music_tag_web:latest

# 2. docker run 启动（注意端口是 8001）
docker run -d -p 8001:8001 -v /path/to/your/music:/app/media -v /path/to/your/config:/app/data --restart=always xhongc/music_tag_web:latest
```

V1 还给了 Portainer stacks 的等价写法（原文以单行呈现，此处按 YAML 排版）[^c2-d7]：

```yaml
version: '3'
services:
  music-tag:
    image: xhongc/music_tag_web:latest
    container_name: music-tag-web
    ports:
      - "8001:8001"
    volumes:
      - /path/to/your/music:/app/media:rw
      - /path/to/your/config:/app/data
    command: /start
    restart: always
```

对照可见两处关键差别：V1 端口是 **8001**，且多一行 `command: /start`。快速开始页把这一点写得很直白——V2「容器内的端口是 8002，和不需要 command /start 命令」[^c2-d2]。**如果你复制的是 V1 的片段却期望跑 V2，端口和启动命令都会对不上。**

> [!warning] 注意 `:rw` 后缀
> V1 的 Portainer 示例中 `/app/media` 写了 `:rw` 后缀（读写），而 V2 Compose 示例的三个卷都没写[^c2-d7][^c2-d4]。不写后缀默认就是读写，所以这不是必须项，但看到别人配置里多一个 `:rw` 不必惊讶。

### 2.5 访问地址、默认凭据与后台入口

#### 访问地址

V2 安装完成后，官方 Docker 部署页的原文是：「在网页浏览器中输入 `http://127.0.0.1:8002` 或者绿联设备的实际 IP 地址加上端口 8002」[^c2-d3]。

从别的机器访问时，把 `127.0.0.1` 换成部署机器的实际 IP。绿联页的原文是「安装完成后，在网页浏览器中输入绿联设备的IP地址后跟端口号8002（例如 `http://greenlink_ip:8002`），即可访问 Music Tag Web 的登录界面。」——该页的尖括号自动链接把「，即可访问 Music」一段转义吞掉了，这里按可读方式还原（原文如此，不是本笔记改写）——并把 `greenlink_ip` 换成实际地址[^c2-n3]。

> [!warning] V2 手册提到"绿联设备"疑似串页
> V2 的通用 Docker 部署页里出现了"绿联设备"字样，而该站另有独立的绿联部署页[^c2-d3]。**本笔记推断**这是从绿联页复制过来的残留表述，不影响你按 IP:8002 访问这件事。[推断]

#### 默认凭据与后台入口

官方 Docker 部署页写明：「登录后，默认账号密码为 `admin/admin`。」[^c2-d3] 首次登录后应立即修改默认密码。

后台入口 `[/admin]` 的写法：

| 版本 | 官方给出的地址 | 来源 |
| --- | --- | --- |
| V1 | `127.0.0.1:8001/admin` | V1 快速开始页原文「访问在 `127.0.0.1:8001/admin` 默认账号密码 *admin/admin*」[^c2-d7] |
| V2 | 只给了 `http://127.0.0.1:8002`，**未说明是否仍需 `/admin` 后缀** | V2 Docker 部署页[^c2-d3] |

> [!warning] 访问路径写法不一致
> V1 手册明确带 `/admin`，V2 手册只给根地址、未说明后缀[^c2-d3][^c2-d7]。**本笔记的建议写法**是：先访问 `http://<你的IP>:8002`，后台入口为 `/admin`，即 `http://<你的IP>:8002/admin`。请注意 V2 手册**未明确**这一点，实际以界面为准。

#### 三个容易踩的细节

1. **反向代理报 csrf 错误**：官方原文「如果你反向代理页面进去报错 csrf 错误，请用局域网地址进入。」[^c2-d3] 也就是说，先用内网地址把初始化做完。
2. **Subsonic 密码**：官方说「如果需要修改 Subsonic 的默认账号密码，也请在登录后进行操作」，并提醒修改后可能需要重新登录、页面没刷出来就刷新[^c2-d3]。凭据位置与客户端清单属播放侧内容，见附录 A。
3. **V2 必须激活**：官方第 6 步是「登录后，点击 V1 标签，按照提示输入 V2 激活码以完成激活。」[^c2-d3] 这一步是 V2 的强制门槛，登录后的完整流程（改密、激活码获取、6 次上限）见第三章。

#### 部署完成后的自检清单

按下面五项逐条核对，任何一条不过，都不要急着往下走：

1. **容器在跑**：终端里 `docker ps` 能看到 `music-tag-web`，状态是 Up。
2. **端口能通**：浏览器打开 `http://<你的IP>:8002`，看到登录页而不是"无法访问"。
3. **曲库挂上了**：登录后界面里能看到你的音乐内容，而不是一片空白。空的基本只有一个原因——`/app/media` 那行左边指错了目录。
4. **配置挂上了**：确认 `/app/data` 对应的宿主机目录里已经生成了文件（数据库与配置文件）。这一步是防"重建容器后配置、激活全丢"的关键。
5. **第三个卷在位**：若你打算使用后台刮削，确认 `/app/download` 也挂了，并且它和曲库目录不重合。

后三项都可以用一条命令查实际挂载：

```bash
docker ps                                                      # 容器是否在跑，端口映射对不对
docker inspect music-tag-web --format "{{json .Mounts}}"       # 实际挂了哪几个卷、左边对应哪
```

**本节已知空白**：官方部署页**没有出现任何环境变量清单**（如 PUID/PGID/TZ 之类），fnOS 页全部截图里也没有环境变量输入区与网络模式字段[^c2-d3][^c2-o1]——本节因此不列任何环境变量示例（`未取到`）。

### 2.6 NAS 差异小节

通用的 Compose 写法在所有支持 Docker 的 NAS 上都成立，差别只在"从哪里点进去"。本节以飞牛 fnOS 为主——它的官方部署页整页几乎没有文字，步骤全部承载在 11 张截图里。

#### 飞牛 fnOS（以截图为准）

> [!warning] 该页的版本号含义未确认

**路线一：容器部署（界面表单）**[^c2-o1]

1. 左侧进 **Docker 应用**（不是应用商店，该页全程没有出现应用商店），在「镜像仓库」页搜索 `xhongc/music_tag_web`。搜索结果有 3 条，官方那条是第一条 `xhongc/music_tag_web`（下载量 `100K+`、收藏 `35`、带描述行 `Music Tag 音乐标签web版`），另外两条是同名个人镜像（`w497273/...`、`0x152a/...`）。页面没有文字提示该选哪条。[截图读取]
2. 点下载后弹「选择标签」，字段 `镜像标签` 填 `latest`。[截图读取]
3. 下载完成后进「创建容器」第 1 步：`选择镜像*` = `xhongc/music_tag_web:latest`，`容器名称*` = `music_tag_web`（**下划线**）；「资源限制」不勾，「开机自动开启」不勾。[截图读取]
4. 第 2 步「高级设置」：`端口设置` 一行填 本地端口 `8002` → 容器端口 `8002`，协议 `TCP`；`存储位置` 填两条 —— 本地 `/vol1/1000/music` → 装载 `/app/media`（读写），本地 `/vol1/1000/mtw_config` → 装载 `/app/data`（读写）。[截图读取]
5. 第 3 步「确认信息」：核对后勾选「创建后启动容器」，点「创建」。[截图读取]

**路线二：Compose 部署**[^c2-o1]

1. 左侧 `Compose` → 项目管理 → `+ 新增项目`。
2. 「创建项目」弹窗里选来源 `创建docker-compose.yml`，路径填 `vol1/1000/mtw_config`，勾「创建项目后立即启动」。
3. 内嵌编辑器里粘贴下面这段 YAML（**逐字照录自截图，此 YAML 不在页面正文里**）[^c2-o1]：

```yaml
version: '3'

services:
  music-tag:
    image: xhongc/music_tag_web:latest
    container_name: music-tag-web
    ports:
      - "8002:8002"
    volumes:
      - /vol1/1000/music:/app/media:rw
      - /vol1/1000/mtw_config:/app/data
    restart: unless-stopped
```

部署完成后，页面正文的说明是「成功部署访问8002端口，默认账号密码 都为 admin，左上角V1标签点击激活V2版本」[^c2-n4]。

> [!warning] fnOS 截图自身有缺陷，照容器路线走必须自查
> **「高级设置」里配了 2 条卷映射（`/app/media` 与 `/app/data`），但紧接着的「确认信息」汇总页只剩 1 条**——`/app/data` 那一行不见了。这是截图本身的差异，不是阅读误差；对比之下 Compose 路线的 YAML 明确带 2 条卷。[截图读取][^c2-o1]
> 后果是实打实的：V2 的配置与数据库落在 `/app/data`，**这个卷没挂上，重建容器就等于丢配置、丢激活**。所以照容器路线走完第 3 步「确认信息」时，请务必回头确认 `/app/data` 那一条真的在列表里；不在就点「上一步」重加。
> 另外两条路线生成的容器名不同：容器部署是 `music_tag_web`（下划线），Compose 部署是 `music-tag-web`（连字符）[^c2-o1]。后续写命令（例如检查日志）时不要混用。
> 还有一处小的不一致：Compose 的「路径」字段截图里填的是 `vol1/1000/mtw_config`（无前导斜杠），而同一页 YAML 卷里写的是 `/vol1/1000/mtw_config`（有前导斜杠）[^c2-o1]。按 YAML 里的带斜杠写法即可。

> [!tip] 大白话
> 这一步就像**在租房 App 里下单，最后一步的确认清单比前面的勾选项少了一行**。你前面明明勾了"配置柜"，确认页却没列出来——如果不回头核对，你以为都装好了，实际搬进去才发现没有衣柜。fnOS 这份官方截图就处于这个状态。

> [!summary] 本章小结
> - **三条挂载，右边不可改**：`/app/media`（曲库）、`/app/data`（配置与数据库）、`/app/download`（后台刮削监控目录）。左边宿主机路径由你决定。
> - **推荐 Compose 三卷配置**；官方 `docker run` 示例只挂两卷、少了 `/app/download`，"不用后台刮削可省"是**本笔记推断**，不是官方说法。
> - **重启策略统一用 `unless-stopped`**：官方三种写法并存，它兼顾自动拉起与"手动停就别再自己爬起"。
> - **端口只改左边**：V2 容器内固定 8002，V1 是 8001 且多一行 `command: /start`。
> - **镜像认准 `xhongc/music_tag_web`**；写成 `xhong/music_tag_web`（少个 c）拉不到镜像。
> - **访问 `http://<IP>:8002`，后台入口为 `/admin`**（V2 手册未明确 `/admin` 后缀）；默认凭据 `admin/admin`，登录后立即改密。
> - **NAS 上以飞牛 fnOS 为主**；其容器路线截图有卷映射缺陷，务必自查 `/app/data` 是否真的挂上。威联通无官方专页。

下一章我们接着登录之后的动作往下走：改掉默认密码、拿到并填入 V2 激活码，以及为什么这串激活码有 6 次上限、跨设备激活会顶掉前一台——做好这几件事，V2 才算真正可用。

## 第三章 首次登录、改密与 V2 激活

容器跑起来了，浏览器能打开 8002，只说明服务活着。对这一版的 Music Tag Web 来说，还有一道绕不开的门——激活。本章只处理从登录到真正可用之间的这一小段：默认凭据与后台入口、密码要不要改、Subsonic 密码为什么必须动一次、激活入口在哪、激活码怎么来，以及激活没反应时官方把原因归到哪。

### 3.1 打开界面：地址、默认凭据与后台入口

#### 访问地址

V2 官方 Docker 部署页给的访问地址是根地址，不带路径：

```text
http://127.0.0.1:8002
```

同页也说明可用设备实际 IP 加端口 8002 访问（该句举例写的是「绿联设备」，而这一页并非绿联专题页，属原文如此）。换机器访问时把 `127.0.0.1` 换成宿主机局域网 IP。[^c3-d3]

#### 默认凭据

默认账号密码都是 `admin`。官方 Docker 部署页写「登录后，默认账号密码为 `admin/admin`」，飞牛 fnOS 页末段复述「默认账号密码 都为 admin」；而项目介绍、FAQ、激活专页、1Panel 页这几处官方页面都没有给出默认凭据。[^c3-d3] [^c3-n4]

> [!warning] 易错点
> `admin/admin` 是公开印在官方文档里的固定值。只要容器能被局域网外访问到，这就等于一扇没锁的门。

#### 后台入口是 /admin：V2 手册没有写明的一处

这是第二章遗留的一处含糊点：V1 手册明确给出带路径的登录地址，V2 部署页只给根地址、没提 `/admin`；但同一站点的 FAQ 第 9 条恰恰以「/admin 进不去后台，报 403 无法访问」提问，反证 `/admin` 是 V2 的后台入口。[^c3-d3] [^c3-f1]

| 来源 | 层级 | 关于访问路径的口径 |
| --- | --- | --- |
| V2 Docker 部署 第 3 步 | 官方 | 只给 `http://127.0.0.1:8002` 或设备 IP + 8002，未提 `/admin` |
| FAQ 第 9 条 | 官方 | 以「/admin 进不去后台，报 403」提问，反证 `/admin` 是后台入口 |
| Issue #360 用户评论 | 用户实测（社区） | 称可「NAS_IP:8002/admin 登录后台管理」，而 `NAS_IP:8002` 进的是普通界面 |

本笔记因此按「访问 `http://<ip>:8002` 是主界面，后台入口为 `/admin`」来写，并如实标注：**V2 手册未明确这一点**，第三行来自社区实测，不是官方陈述。[^c3-i360]

> [!tip] 大白话
> 把 8002 想成楼栋门牌，`/admin` 就是楼里那间后勤办公室。门牌让你进楼，办公室才是你干活的地方——找不到办公室不等于楼不对，只是还没走到那个房间。

### 3.2 第一件事：改掉默认密码

官方第 4 步的标题是「修改默认密码（可选）」，即官方口径里这一步不是必做项。但默认凭据公开印在文档上，**本笔记建议**可能被局域网外访问到的实例都改掉——这是本笔记的建议，不是官方要求。[^c3-d3]

改密发生在登录后的管理界面里：用默认账号密码登录，进入管理界面即可修改。

#### 反向代理下的两种拦路表现

如果通过反向代理访问，可能碰上两种情况，官方在两处分别记录过：[^c3-d3] [^c3-f1]

| 现象 | 出处 | 官方处置 |
| --- | --- | --- |
| 反向代理进去报 csrf 错误 | V2 Docker 部署 第 4 步附注 | 「请用局域网地址进入」 |
| `/admin` 报 403 无法访问 | FAQ 第 9 条 | 「受限制框架安全机制，反代的地址无法进入，局域网地址可以」 |

两处归因不同（csrf / 框架安全机制），动作一致：**改用局域网地址访问**。

#### 连密码都进不去怎么办

若默认密码试不进去，或之后忘了密码，官方另有一条改密路径——需要在容器内执行命令重设。那属于排错范畴，本笔记放在附录 C，这里只留指路。

### 3.3 Subsonic 密码：先设一次，否则音乐收藏会一直转圈

Subsonic 密码和你的登录密码是两套东西。官方 Docker 部署页把它列为第 5 步（同样标「可选」），写「如果需要修改 Subsonic 的默认账号密码，也请在登录后进行操作」，并提示「修改后可能需要重新登录，并且如果页面没有正确加载，请尝试刷新页面」。[^c3-d3]

FAQ 第 6 条把后果写得更直白——问的是「为什么音乐收藏一直在 loading 中」，答「更改过或未设置 subsonic 的密码需要设置一次，需要重新再登录一次，后再刷新音乐收藏页面」。也就是说：**只要这个密码处于未设置或改动过的状态，音乐收藏就会一直转圈**，设置一次、重新登录、刷新页面才会恢复。[^c3-f1]

密码位置在官方「音乐收藏与播放」页有交代：在 `admin`/后台的 subsonic 用户中，「修改 api token 即是密码」，改完需重新登录后刷新页面。[^c3-p1]

> [!note] 核心概念
> 要建立的心理模型是：**管理员密码管「你进不进得来后台」，Subsonic 密码管「音乐收藏和播放服务跑不跑得起来」**。两者互不相通，改了一个不等于改另一个。

本节只覆盖「要设一次、去哪儿设」这一层。Subsonic 服务端的登录地址、客户端清单与播放生态联动属于播放侧内容，集中放在附录 A。

> [!tip] 大白话
> 管理员密码像家大门的钥匙，Subsonic 密码像楼下信箱的钥匙。大门钥匙在手，信箱没配钥匙，里面的信（音乐收藏）照样一份都取不出来——转圈不是坏了，是还没给它配钥匙。

### 3.4 V2 激活：不是可选升级，而是必过门槛

#### 不激活会看到什么

官方 FAQ 把「怎么进来还是V1啊？」单列成一条问答，答案只有一句：「点击 V1 按钮输入激活码激活。」这就是未激活状态的真实表现：**能登录、能进界面，但界面停在 V1**。[^c3-f1]

> [!note] 核心概念
> 对 V2 来说，激活不是「想升级再考虑」的选项，而是部署流程里固定的第 6 步。本笔记因此把它写成**必过门槛**：不跨过它，你拿到的其实是一个 V1。

#### 激活入口在哪

官方各页对入口的描述一致指向同一个东西——登录后，点界面上的「V1」标签（按钮），按提示输入激活码：[^c3-d3] [^c3-f1] [^c3-n2] [^c3-n4]

| 来源 | 层级 | 原文措辞 |
| --- | --- | --- |
| V2 Docker 部署 第 6 步 | 官方 | 「登录后，点击 V1 标签，按照提示输入 V2 激活码以完成激活。」 |
| FAQ 第 2 条 | 官方 | 「点击 V1 按钮输入激活码激活。」 |
| 1Panel 部署 正文末段 | 官方 | 「在登录后 点击V1 标签，输入 V2 激活 即可完成激活。」 |
| 飞牛 fnOS 部署 末段 | 官方 | 「左上角V1标签点击激活V2版本」 |

飞牛页那句补上了方位：这个标签在界面**左上角**。另一个反直觉之处：入口叫「V1 标签」，作用却是**激活 V2**——看见「V1」字样别以为走错了地方。

> [!warning] 易错点
> 官方文档没有为这个激活入口提供任何截图或弹窗示意图，只能靠上面的文字定位。界面上具体长什么样，需要你自己到界面里确认。

#### 激活码怎么拿

官方「项目介绍」页有一个独立的「激活方式」小节，给两条路径：[^c3-d1]

1. **通过赞助项目获取**：经爱发电（`https://ifdian.net/a/music-tag-web`）赞助获得激活码；
2. **直接联系开发者**：若无法访问上述网站，可直接联系开发者微信号（`charlesnowed`）获取激活码。

FAQ 第 3 条写得更具体：「爱发电中……发电后，会私信发你激活码。当爱发电进不去时，可添加作者微信（charlesnowed）购买激活码。」[^c3-f1]

> [!warning] 缺口提示（不要凭想象补）
> 官方页面只写了「发电」「购买」这样的字眼，**激活码的价格、发电档位与最低金额，本次核对中未取到**。本笔记不给出任何金额或档位数字。

> [!tip] 大白话
> 那道「V1 标签」其实是一道闸机，激活码是你手里的卡。闸机在你必经的路上，不是旁边那条「想升级再走」的岔路——没卡，你就停在 V1 那一边。

### 3.5 6 次上限与「换台机器」：先把预期立对

最需要提前管理预期的是两件事：**重新激活有次数上限**，以及**换一台机器激活会把上一台顶下线**。两条同出 FAQ 第 10 条，原文列了三段：[^c3-f1]

> - 「/app/data 配置没删除，重新部署自动生效 ，/app/data 删除 ， 可以用激活码重新激活」
> - 「重新激活有 6 次上限，为了限制频繁激活。（可联系作者清空激活信息）」
> - 「另一台机器激活后，上一台机器就会失效下线了」

拆成场景，预期就清楚了：

| 你做了什么 | 激活状态 | 依据 |
| --- | --- | --- |
| 重新部署或换机部署，但 `/app/data` 没删 | 自动生效，无需重新激活 | FAQ 第 10 条 |
| 删掉 `/app/data` 后重新部署 | 需用激活码重新激活，消耗一次重新激活额度 | FAQ 第 10 条 |
| 在第二台机器用同一激活码激活 | 上一台机器失效下线 | FAQ 第 10 条 |

关键变量就是第二章讲过的持久化卷 `/app/data`——激活信息落在它里面，所以「重装掉激活」通常不是激活码坏了，而是这个卷没保住。

若已看到「激活码已被激活」的报错，官方在激活专页「情况 3」写得很直接：原因是「重复多次激活，超限 6 次」，解法是「描述清楚当前问题后，找开发者进行重置次数」。[^c3-f2]

> [!warning] 缺口提示（不要凭想象补）
> 以下三项在此次核对的官方页面中**未取到**，本笔记不写成陈述句：重置 6 次上限是否收费、需要什么凭证、处理多久；激活码与机器的绑定粒度（绑定硬件、绑定 IP，还是只记录最后一次激活）。

> [!tip] 大白话
> 把激活信息想成记在 `/app/data` 里的一份「居住登记」。房子（容器）拆了重建不要紧，只要登记本还在，拎包就能住回去；登记本一撕，就得去社区重新登记一次——而社区只允许重登记 6 次，超了要找管理员手工改记录。至于「两台机器同时住」，登记本上只认一个地址，写新的，旧的自动销号。

### 3.6 激活没反应时，官方怎么归因

激活失败的官方归因集中在两处：官方「激活码激活失败、无响应」专页按现象分了三种情况，FAQ 里另有两条问答与之呼应。逐条对照：[^c3-f2] [^c3-f1]

| 现象 | 官方归因 | 官方给出的动作 |
| --- | --- | --- |
| 激活后无提示、无响应 | 「激活时需向激活服务器发送认证验证，容器内网络不通导致无响应」 | 把网络模式改为 host（「需要占用 8001、8002、9001 端口，启动失败查看端口占用情况」），或让 bridge 能访问外部网络 |
| 提示「请矫正服务时间，验证超时！」 | 时间与北京时间偏差过大 | 校正服务器/容器内时间，「误差不要超过 1 分钟」 |
| 提示「激活码已被激活」 | 「重复多次激活，超限 6 次」 | 「描述清楚当前问题后，找开发者进行重置次数」 |

两处口径可以对照着看：网络这条，FAQ 第 4 条问「输入激活码没有反应」，答「确保容器里能访问到外部的网络，能访问到激活服务器，可以修改网络模式为 host 试试」，与专页「情况 1」同向；时间这条在三处出现，分别写作「服务器（NAS）上的时间」、「容器内的时间」与 Docker 部署页第 7 步的「服务器时间」——两种说法在官方文档中并存，宿主机与容器内的时间都值得各看一眼。[^c3-f1] [^c3-d3]

#### 官方 host 建议 vs 社区实测相反

网络这条建议需要显式提示读者。官方在激活专页与 FAQ 里都推荐改用 **host** 网络模式；但同一仓库的 Issue #360 中，有用户留下过相反的实测经历：

> 「我用host网络也是一样，默认账号密码无法登陆，换成bridge网络没问题」

作者对该条的回应只有「可能有端口冲突」一句，并未撤回 host 建议。这条属于**用户实测（社区来源）**，不是官方结论。[^c3-i360]

**处置建议**：按官方口径优先尝试 host；若 host 下问题依旧，可再反向尝试让 bridge 正常访问外网——官方在专页「情况 1」里本就写了「或者让 bridge 能访问外部网络」作为并列方案。网络模式的完整排错放在附录 C。

> [!tip] 大白话
> 激活时容器要给「激活服务器」打个电话报身份。官方推荐把网络模式换成 host，理由是「容器内网络不通」会导致无响应；但社区里有用户实测恰恰相反——host 下照样登不进去，换回 bridge 反而正常。两条路都值得试，官方自己也在同一页写了「或者让 bridge 能访问外部网络」作为并列方案。

> [!summary] 本章小结
> - 默认凭据 `admin/admin`；主界面在 `http://<ip>:8002`，后台入口为 `/admin`——但 V2 手册未明确 `/admin`。
> - 改密在登录后的管理界面，官方标注「可选」；反向代理进不去（csrf 或 403）时，官方两条口径都指向改用局域网地址。
> - Subsonic 密码与管理员密码是两套东西；未设置或改动过它会让音乐收藏一直 loading。位置在后台 subsonic 用户，改 api token 即改密码。
> - 激活是 V2 的必过门槛：不激活，界面停在 V1。入口是登录后左上角的「V1」标签，激活码经爱发电或作者微信获取（价格未取到）。
> - 激活信息落在 `/app/data`：保住该卷则重新部署自动生效，删了则需重新激活且有 6 次上限；另一台机器激活会让上一台失效下线。

登录、改密、激活都过了，界面才真正属于你。但此时它还是一座空库房——接下来第四章进入本笔记的核心：把已有音乐挂进来、刮削匹配、批量改标签，也就是「数据到底是怎么进到你的文件里去的」这一整套主线。

## 第四章 刮削与标签编辑主线

前面几章你已经把容器跑起来、登录进 V2、也激活过了。现在进入这套工具真正的正题：把曲库里那些元数据残缺、封面丢失、文件名乱码的音乐，一次刮干净、改整齐。这一章是整本笔记的核心，它回答的是「点哪个按钮、按什么顺序点、点下去之后文件到底发生了什么」。而在动手之前，你必须先弄明白一件事：这个项目有两种截然不同的写入目标，选错了就会出现「我明明改好了，为什么别的播放器里看不到」这类最经典的困惑。

### 4.1 先分清：你改的是音乐文件，还是 mtw 的数据库

V2 的「基本设置」页面把写入目标拆成两组：**本地音乐写入位置**与 **webdav 音乐写入位置**，每组都可以在「写入元数据」和「写入数据库」之间二选一[^c4-t11]。官方在这个页面上只给了两行说明文字，但这两行决定了你后续所有操作的可见范围，值得逐字读。

第一行针对本地音乐：「写入元数据会影响做种，写入数据库必须有 mtw 提供的 subsonic 服务端播放才能显示。」[^c4-t11] 第二行针对网盘挂载进来的音乐：「网盘挂载在本地的目录，写入元数据会下载音乐后修改再上传回网盘，有较为频繁的操作，写入数据库，只会读取音乐文件的一部分内容就能读到元数据，然后存入 mtw 的数据库，使用提供的 subsonic 服务端播放才能显示。」[^c4-t11]

把这两句话拆成一张对照表：

| 音乐来源 | 写入位置 | 官方描述的行为 | 你能看到的后果 |
| --- | --- | --- | --- |
| 本地音乐 | 写入元数据 | 「会影响做种」 | 文件本体被改动，任何播放器/工具都能读到新标签；正在做种的资源会受影响 |
| 本地音乐 | 写入数据库 | 「必须有 mtw 提供的 subsonic 服务端播放才能显示」 | 原文件不动，标签只存在于 mtw 数据库，换播放器看不到 |
| webdav 音乐 | 写入元数据 | 「会下载音乐后修改再上传回网盘，有较为频繁的操作」 | 每次保存都要走一遍下载—改写—回传，网盘读写压力大 |
| webdav 音乐 | 写入数据库 | 「只会读取音乐文件的一部分内容就能读到元数据，然后存入 mtw 的数据库」 | 省流量、不动网盘文件，同样只有 mtw 的 Subsonic 端能显示 |

> [!tip] 大白话
> 把「写入元数据」想成**直接在书的正文上做批注**——书本身被改掉了，谁拿到这本书都看得见你的批注；把「写入数据库」想成**只在图书馆的借阅系统里加了一条备注**——书还是原样，只有用这套系统查书的电脑才看得到。所以选「写入数据库」时，你在 Navidrome、Jellyfin、foobar2000 里是看不到这次修改的，只有登录 mtw 自带的 Subsonic 服务端（细节见附录 A）才显示。

关于「写入元数据具体怎么改文件」，这里必须诚实标注一个文档缺口：官方所有标签操作页都没有出现「原地」「副本」「覆盖」这类词，也**没有任何一处说明是否会生成文件的副本**。基于「写入元数据会影响做种」这一句，本笔记**推断**其行为是在原文件上改写（原地修改），但这是推断，不是官方口径。请按「会动到原文件」来准备，动手前自行备份音乐目录。这里补一句更准确的话：本次收集的 11 个**标签操作页面**里确实没有「请先备份」这类建议，也没有「操作不可逆」的告警；但**官方并非全无备份口径**——《容器自动更新》页的「最佳实践」写着「**保持备份**：重要数据定期备份，避免意外情况」，升级页也提示过「防止数据丢失」[^c4-f8]。所以「动手前先备份」是本笔记的建议加上官方口径的支撑，不是凭空加的。

最后补一句关于撤销：V1 没有任何回退说明；V2 项目介绍提到「元数据版本管理」会「自动记录每次元数据修改历史，支持版本查看、差异对比与一键回退」[^c4-t19]，这是唯一一处接近「操作可撤销」的官方表述，但它覆盖哪些操作、有没有时间限制，官方没写，不要把「一键回退」当成万能后悔药。

### 4.2 V2 的三种刮削：先把术语对齐

V2 名词解释给出的定义如下，原文照录[^c4-t13]：

- **手动刮削**：「本项目中的功能，选择需要修改文件或文件目录，可自定义修改音乐**元数据中的内容。**」
- **自动刮削**：「本项目中的功能，选择需要修改文件或文件目录，可自动从音乐流媒体平台搜索**元数据**实行**刮削**操作」
- **后台刮削**：「本项目中的功能，固定的文件目录下，可自动从音乐流媒体平台搜索**元数据、整理文件夹、重命名**等一系列操作」

同一页还定义了「刮削」本身，说明这个词借自影视领域：「刮削是音频播放软件及音乐管理软件的一项功能，它可以自动识别音乐文件，并在线获取相应的专辑封面、歌曲名称、艺术家、专辑信息、流派和发行日期等数据」；并定义「元数据」为「一般内嵌于音乐文件中，与音乐共同存在」的那些歌曲信息[^c4-t13]。

| 术语 | 谁来触发 | 是否联网搜索标签源 | 作用范围 |
| --- | --- | --- | --- |
| 手动刮削 | 你手工选中文件/目录 | 由你选定标签源后由你决定应用哪些字段 | 个别文件或指定目录，可完全自定义 |
| 自动刮削 | 你手工选中文件/目录 | 是，自动匹配后保存 | 批量，但需要你发起一次 |
| 后台刮削 | 系统定时器 | 是，自动匹配并继续整理、重命名 | 固定的监控目录，无人值守 |

> [!warning] 文档空缺：V2 的两个功能页是空的
> V2 手册里确实存在「手动刮削」和「自动刮削」两个页面，但抓取回来的正文**只有一级标题**：一个页面是 `# 手动刮削`，另一个是 `# 自动刮削`，标题之下再无一个字、也没有任何截图[^c4-t8][^c4-t9]。这已经排除了抓取失败的可能（同批抓取的其他页都完整），是页面本身没有内容。所以上面表格里的「是否联网搜索」等语义，只能由名词解释页[^c4-t13]和教程文章[^c4-t14]**侧证**，不是功能页自己写的。V2 界面上这两个入口究竟长什么样，需要你部署后在界面里自己确认。

> [!tip] 大白话
> 把三种刮削想成三种「整理相册」的方式：**手动刮削**是你自己一页页翻、亲手写标题；**自动刮削**是你把一叠照片交给识别软件、它帮你填标题（你按一次按钮）；**后台刮削**是你在玄关放了一个「待整理」的箱子，只要往箱子里丢新照片，系统每隔几分钟就自己拿去识别、命名、归档。区别不在「智能程度」，而在**谁决定开始、以及要不要人守着**。

关于术语还有一处版本间的不一致，写作时如实保留：V1 的「批量修改」页面把批量操作定义为「手动填写」共有元数据[^c4-t2]，而 V2 名词解释把「批量」能力归给了自动刮削[^c4-t13]，两版手册没有统一这个用词。读到「批量」二字时，请结合上下文判断它指的是「批量手填」还是「批量自动匹配」。

还有一处必须先交代的文档空白：官方两版手册都只使用「标签源」「音乐流媒体平台」这类泛称，**从未点名任何具体的提供方**。本笔记在写作时对两版手册做了全文关键词检索，网易、QQ 音乐、酷狗、酷我、MusicBrainz、AcoustID、Spotify、Deezer、iTunes、Last.fm 等常见名称的命中数均为 0；据此**推断**是文档确实未公开这份名单，而不是检索遗漏[^c4-t13]。所以「它到底支持哪些标签源」这个问题，本笔记给不出答案，只能等你在界面里的标签源下拉框中自行确认。

### 4.3 手动修改标签：六步走完一次刮削

V1 手册的「手动修改标签」页把整个流程拆成编号 1–6 的六步，页首一句话概括它的用途：「手动刮削，针对个别的音乐文件进行修改」[^c4-t1]。这六步是理解这套工具交互方式的骨架，V2 的手动刮削是同一套思路的延伸。

1. **配置说明**。原文两条：「选中一个标签源，用于后续的刮削」「选中展示字段，字段选中的顺序会影响页面的显示。」[^c4-t1]
2. **查询音乐标签信息**。对选中文件发起一次查询，把标签源返回的候选数据显示出来[^c4-t1]。
3. **选中应用的标签元数据**。这是决定「改哪些字段」的一步，见下方三种粒度[^c4-t1]。
4. **歌词翻译**。页面这一步只写「机翻歌词」四个字[^c4-t1]。
5. **歌词操作**。「打开导出 lrc 开关，会将音乐元数据中歌词导出为 ${filename}.lrc 的歌词文件」；「导入 lrc 开关」则把同目录下的 `${filename}.lrc` 歌词文件嵌入音乐元数据中[^c4-t1]。
6. **保存信息**。原文只有一句「完成一次音乐刮削」[^c4-t1]。

> [!note] 核心概念：三种应用粒度
> 第 3 步给出了三档精细度，你不需要每次都全量覆盖[^c4-t1]：
> - 「应用栏-箭头按钮 应用全部元数据」——一次性把查询到的全部字段写进去；
> - 「点击 各个标签下的数据，独自应用数据」——只应用你点的那一个字段，其余保持不变；
> - 「歌词栏-加载歌词-异步在加载歌词数据」——歌词单独异步加载，不阻塞其他字段。
>
> 这三档是从「全都要」到「只要这一条」的连续光谱，也是手动刮削比自动刮削更可控的地方。

> [!example] 手动刮削的能力清单
> V2 教程文章把手动刮削能做的事列成一张清单，并明确「下面功能均支持批量操作」[^c4-t14]：重命名文件名称；手动补充艺术家、专辑等元数据；导出歌词为 lrc 文件；lrc 歌词嵌入的音乐中；导出专辑封面；导入专辑封面。六个条目里，只有「补充元数据」需要联网标签源，其余都可离线完成——这也是它被官方描述为「选择需要修改文件或文件目录，可自定义修改音乐元数据中的内容」[^c4-t14]的原因。

**一条必须标注的缺口**：第 6 步「保存信息」最终把数据落到哪里——是写回音乐文件，还是写进 mtw 数据库——这一页**没有说明**[^c4-t1]。请回头按 4.1 的「基本设置」里你选定的写入位置来预期，不要在文档层面把「保存」等同于「写进文件」。

顺带记住一条界面行为：「字段选中的顺序会影响页面的显示」[^c4-t1]，也就是说你在第 1 步勾选展示字段的先后次序，会直接决定后面各字段在页面上的排列，想按自己的习惯读表就按想要的顺序勾。

### 4.4 批量修改（V1）：手动填写共有元数据

V1 的「批量修改」定义得非常克制：「勾选多个文件或文件夹进行批量修改文件中相同的元数据（注意是手动填写）」[^c4-t2]。括号里那四个字是重点——它修改的是**所有选中文件共有的、由你亲手填写的**那部分数据，不是联网匹配来的结果。这与 4.2 里提到的 V2 用词差异直接相关：V1 的「批量修改」并不智能，它只是「一次写给很多个文件」。

官方给了两个「例如」来示意[^c4-t2]：

- 「你想要批量把音乐的风格修改为 流行乐」——即给一批文件统一填同一个流派值；
- 「你想批量把音乐的文件名称改为 艺术家+专辑的格式」——这一条原文附带一句「ps.这里使用到变量的用法」，说明它要靠变量拼接。

同页的「变量的使用」小节交代了 V1 最实用的一个小技巧：「鼠标悬浮在标题的label上可以查看变量的名称，点击就会复制变量。（其他同理）」[^c4-t2]。页面用一首歌举例说明替换效果：「《我想》的 ${title}="我想" ，${album}="东海岸"」[^c4-t2]。

**这里有一个必须写明的缺口**：V1 只说可以悬浮查看并复制变量名，**从未列出完整的变量清单**[^c4-t2]。V2 手册里确实有一份完整的变量表（见 4.7），但那是 V2 的能力，不能回填到 V1——不要拿 V2 的清单去假设 V1 也支持同名变量。

### 4.5 自动批量修改（V1）：宽松模式与严格模式

V1「自动批量修改」一句话定义它的行为：「自动从你选定的标签源中匹配并保存到音乐文件中」[^c4-t3]。与 4.4 的批量修改刚好互补——一个靠你手填，一个靠标签源匹配。

它提供两种匹配模式[^c4-t3]：

| 模式 | 官方原文 | 已知风险（官方自述） |
| --- | --- | --- |
| 宽松模式 | 「只根据标题匹配元数据, 可能存在同名或翻唱歌曲。」 | 同名曲、翻唱会被误配 |
| 严格模式 | 「根据标题和歌手或标题和专辑匹配元数据, 准确性更高。」 | 官方补充：「（也会出现错误判断的情况，建议少量批量修改，手动辅助修正。）」 |

第二行那句补充值得单独强调：这是官方文档里少见的准确性免责表述，也就是说官方自己也不保证严格模式不出错，并建议**少量分批 + 人工复核**。把它当成操作纪律而不是客套话——批量刮削越猛，误配的返工成本越高。

**这个页面同样有缺口**：除上述两种模式的文字说明外，T3 页面其余内容都是截图，**完整的界面操作步骤未在文档中取到**[^c4-t3]。你在界面上会看到哪些勾选项、点哪个按钮开始匹配，需要自己对照界面确认。

### 4.6 后台刮削：两个监控目录与音乐预处理

后台刮削是三种刮削里唯一「无人值守」的：官方定义它的行为是「自动对新添加进文件夹的音乐自动刮削后整理归档到目录中」，并给出调度频率——「**开启后台刮削**，后台会每3分钟检查 目标目录 进行自动刮削。」[^c4-t10]

它监听两个固定目录[^c4-t10]：

- `/app/download`：「该目录需要自在部署docker应用时额外再映射一个目录到/app/download，这个目录做为新增文件的下载目录可以是自定义的任意目录」；
- `/app/media/download`：「该目录不需要再次映射，因为/app/media 不出意外你在部署时已经映射过了，只需要在/app/media创建一个download 目录即可」。

> [!warning] 与第二章的挂载矛盾直接相关
> `/app/download` 正是第二章 2.3 与 2.4 那处「挂载卷集合不一致」的落点：Compose 示例挂了三个卷（含 `/app/download`），而 `docker run` 一步到位的示例只挂了两个卷。结论在这里补全——**想用后台刮削，就必须在部署时多挂一个目录到 `/app/download`（或在已挂载的 `/app/media` 下建一个 `download` 子目录）**；反过来，如果你确定不用后台刮削，可以省掉这个卷，但这一点是本笔记**推断**（依据是官方只把 `/app/download` 描述为后台刮削的监控目录），官方没有明说二者是可选的因果关系。

**音乐预处理**是后台刮削流水线的前置环节，官方列出三项：「支持声纹识别、乱码修复、繁体转简体」[^c4-t10]。教程文章把三项各自展开[^c4-t15]：

1. **声纹识别**：「对于缺少艺术家或专辑元数据的音乐文件，系统会使用声纹识别技术尝试找到匹配的信息。」
2. **乱码修复**：「系统会自动检测并修复文件名、艺术家、专辑名中的乱码问题。」
3. **繁体转简体**：「所有繁体中文会被转换成简体中文，保持一致性。」

这三项也解释了一处版本间的形态差异：V1 有一页独立的「简繁体转换」，但正文只有一张截图、没有任何文字步骤；到了 V2，繁体转简体被收进后台刮削的预处理项里，没有独立页面[^c4-t10]。如果你要做繁简统一，V2 里优先走后台刮削这条路径。

**整理与转移文件在后台刮削里是必选项**。教程文章在「音乐文件整理（必选）」一节写道：「**整理文件**：确保所有文件按照规定的格式存放。」「**转移文件**：根据处理结果（成功或失败），将文件转移到相应的 `completed` 或 `failed` 目录中。」[^c4-t15] 也就是说，监控目录里的文件在刮削完成后**会被移动到别处**，这不是可关的附属功能。FAQ 里用户问得更直接：「后台刮削中转移文件/整理文件可不可不选择，都是必选的吗？」官方回答：「是的，必须要选择，不然每次监控就不是增量数据，数据会越积累越多，这个目录的目的是为了新增音乐的自动刮削，如果因此不满足你的需求，我们从长计议。」[^c4-f1]

> [!tip] 大白话
> 把后台刮削的监控目录想成**家里的「待处理文件筐」**。你只管往筐里丢新下载的音乐，系统每 3 分钟来看一次；处理完了它就把文件从筐里拿走、按结果分别放进「已完成」和「失败」两个柜子。所以这个筐**必须被清空**——如果处理完的文件还留在筐里，下次它会把老文件再算一遍，筐会越堆越满。这就是官方在 FAQ 第 11 条回答「是的，必须要选择」的朴素理由。

### 4.7 变量与正则：一次学会这套模板语言

变量是贯穿「批量修改文件名」「重命名」「批量重命名」的通用能力，值得单独学一次。V2 的规则很明确：「当前项目基于 Mako 实现，**仅解析 `${...}` 表达式**，不支持完整 Mako 块语法。」[^c4-t12] 官方对变量的定义是：「变量本质是**占位符**，在输入框编写 `${变量名}`，系统保存标签/重命名文件时，会自动替换为歌曲对应的真实信息。」[^c4-t12]

最常见的变量如下（V2 手册与名词解释页口径一致）[^c4-t12][^c4-t13]：

| 变量 | 说明 |
| --- | --- |
| `${title}` | 歌曲标题 |
| `${artist}` | 歌手 |
| `${first_artist}` | 第一个歌手 |
| `${first_artist_letter}` | 第一个歌手首字母 |
| `${album}` / `${albumartist}` | 专辑名称 / 专辑艺术家 |
| `${discnumber}` / `${tracknumber}` | CD 号 / 音轨号 |
| `${filename}` / `${file_song_name}` / `${file_suffix}` | 完整文件名 / 不含扩展名的文件名 / 文件扩展名 |
| `${parent_path}` / `${parent_parent_path}` | 父目录名 / 上上级目录名 |
| `${lyrics}` / `${comment}` | 歌词 / 注释 |
| `${year}` / `${genre}` | 发行年份 / 流派 |
| `${composer}` / `${lyricist}` | 作曲 / 作词 |
| `${language}` / `${guess_language}` | 语言 / 自动识别语言 |
| `${counter}` | 计数器 |
| `${null}` | 空值，用于把某个元数据置空 |

**空值兜底**是这套语法里最实用的写法，两种写法等价[^c4-t12]：

```text
${title if title else "未知标题"}
${title or "未知标题"}
```

官方给的输出示意是：模板 `${title or "未知标题"} - ${artist or "未知歌手"}`，在只有歌手有值时输出 `未知标题 - 刘德华`[^c4-t12]。它还可以多级兜底，例如 `${artist or albumartist or "未知歌手"}`[^c4-t12]。

**音轨号补零**要注意官方给的一条坑：不要在 `${}` 里写复杂的 Python 格式化。原文提示「不建议在 `${}` 内使用复杂格式化写法，正则解析会兼容异常。」并给出推荐写法[^c4-t12]：

```text
❌ 不推荐：${"{:02d}".format(int(tracknumber))}
✅ 推荐：  ${tracknumber.zfill(2) if tracknumber else ""}
```

官方把后者称为「高兼容写法（适配 `1/12` 这类特殊格式，避免 `int` 报错）」——因为音轨号有时会写成「1/12」这种「第几首/共几首」的形式，用 `int()` 强转会直接报错[^c4-t12]。

**明确不支持的两类写法**[^c4-t12]：Mako 块语法（`% if tracknumber:` … `% endif`）与 foobar2000 风格语法（`$if(${discnumber},$num(${discnumber},2),)`）。官方给的替代写法是 Python 表达式风格：`${discnumber.zfill(2) + "_" if discnumber else ""}`[^c4-t12]。

变量之外还有一条**正则命名组**的路子，用于处理「元数据不可靠、只有文件名里有信息」的场景。V2 教程给出场景 1：文件名 `01.夜曲.flac`，用正则 `(?P<tracknumber>\d+)\.(?P<title>\w+)` 解析出音轨号与标题；教程同时提醒这个表达式「不会直接更改文件名」，要真正去掉音轨号，得把它改成 `(?P<tracknumber>\d+)\.(?P<filename>\w+)`——换个命名组，就换了输出里留下什么[^c4-t16]。

场景 2 是「以 艺术家-音乐名 格式重命名」，教程的步骤写得很直白：「首先确认您的文件元数据中已经包含了正确的艺术家信息。」然后在文件名字段用 `${artist}-${title}` 这样的变量构建新名字。这里还有一句省心的说明：「文件扩展名会继续填充源文件的扩展名，所以你无需额外输入文件扩展名。」[^c4-t16]

> [!tip] 大白话
> 变量就像**快递面单上的填空位**：你写下 `${artist}`，系统在打包时会照着这首歌的信息把空填上，不同歌曲填出不同结果。`${title or "未知标题"}` 则像**面单上的兜底栏**——「有名字就写名字，没名字就写『未知』」，避免收件人一栏空着。正则命名组则是反过来的用法：不去「填空」，而是**拿一把带刻度的尺子去量文件名**，量出哪一段是音轨号、哪一段是标题，量准了才决定留下哪一段。

### 4.8 本章小结与下一章

> [!summary] 本章要点
> - **写入位置是本项目最容易踩的隐形坑**：本地音乐与 webdav 音乐各自可在「写入元数据（改文件本体、影响做种）」和「写入数据库（只有 mtw 的 Subsonic 端可见）」之间二选一[^c4-t11]。
> - **V2 有三种刮削**：手动（自定义改）、自动（选目录后由标签源批量匹配）、后台（固定目录、每 3 分钟自动跑），语义只能由名词解释与教程文章侧证，因为 T8/T9 两个功能页正文为空[^c4-t8][^c4-t9][^c4-t13]。
> - **手动修改标签是六步流程**，核心是第 3 步的三种应用粒度：全部应用、按字段独自应用、歌词异步加载[^c4-t1]；字段的勾选顺序还会影响页面显示顺序。
> - **V1 的「批量修改」是手填共有值，「自动批量修改」才联网匹配**，后者有宽松 / 严格两种模式，官方自述严格模式仍可能误判，建议少量分批 + 人工复核[^c4-t2][^c4-t3]。
> - **后台刮削监控两个目录**（`/app/download` 与 `/app/media/download`），带声纹识别、乱码修复、繁体转简体三项预处理，且整理/转移文件为必选项，否则监控目录会不断堆积[^c4-t10][^c4-t15][^c4-f1]。
> - **变量引擎基于 Mako 但只解析 `${...}`**，支持空值兜底与 `zfill()` 补零，不支持 Mako 块语法与 foobar2000 写法；文件名还可走正则命名组方案[^c4-t12][^c4-t16]。

到这里，标签已经刮好、改齐了，但文件本身还散乱在曲库里——目录层级、命名格式、繁简用字都还没统一。下一章就接着这一步往下走：先用「整理文件夹」按元数据把文件归位，再用「拆分文件名称」「批量重命名」「简繁体转换」「切割音轨」把文件名和音轨结构收拾干净，让整个曲库变成一台播放器能直接扫出正确结构的形态。

## 第五章 整理与批处理

前四章把标签本身改对了——标题、艺术家、专辑、封面、歌词都进了元数据。但文件在硬盘上还是买来时的样子：一堆散落在同一个目录里的 `01.我想.mp3`，繁体简体混杂，整轨 CD 没切开，文件名毫无规律。本章解决的就是最后一公里：**把文件本体的摆放也摆整齐**。这里每一项操作都会真的移动、改名或新建文件，和第四章"改标签"一样属于会落盘的动作，所以顺序上放在刮削之后最合适。

本章的小节顺序不是随手排的，而是照 V1 官方手册的页面顺序来的：整理文件夹 → 简繁体转换 → 拆分文件名称 → 切割音轨，最后补上 V2 教程里的批量重命名[^c5-t17]。先看一张总览，知道每项操作动的是什么：

| 本章操作 | 处理的输入 → 输出 | V1 手册页面 | V2 手册页面 |
| --- | --- | --- | --- |
| 整理文件夹 | 元数据 → 目录结构 | 有独立页 | 未设独立页 |

> 本章涉及的操作会移动、改名甚至生成新文件。本次收集的 11 个标签操作页面里，**没有一页给出"请先备份音乐文件"的建议，也没有"操作不可逆"的告警**——这是"文档未说明"这一事实本身，不是我在转述官方口径。因此"先备份一份完整曲库再动手"属于**本笔记建议**，不是官方要求。另外，V2 有"元数据版本管理"支持一键回退，但官方未说明它覆盖哪些操作、有无时间限制，回退能力边界 `未取到`[^c5-t19]。更细的备份与恢复讨论集中在附录 C。

### 5.1 整理文件夹：按元数据的值把文件分到目录里

**它是什么。** 整理文件夹做的是一件"把文件摆放对齐标签内容"的事。页面首段的定位句是：「将音乐文件，以元数据中的值进行分组到文件夹中」[^c5-t4]。也就是说，它读的是**标签里已有的值**，按这个值把文件搬进对应目录——它不联网、不刮削、不新增信息，纯粹是一次基于既有元数据的归位。

**具体产物长什么样。** 页面点名了三个界面要素，加上一个独立小节：

- **多级目录（可选）**——勾上之后目录会有层级，而不只是一层。
- **整理后的根目录**——它是整理结果的落点，页面原话是：「整理后的根目录：意味着整理后文件会存放在这个目录下。」[^c5-t4]
- **删除空文件夹**——见下一小节。

> [!warning] 两处官方文档的缺口
> **第一，分组键字段名 `未取到`。** 页面只说"以元数据中的值"，全文没有点明到底按标题、专辑还是艺术家分组，也没有给出默认分组规则。所以你在界面上看到的第一个下拉框是什么，请以实际界面为准，本笔记不替官方指定字段。
> **第二，同名文件的冲突策略 `未取到`。** 整理时如果两个文件会落到同一个目标路径，是覆盖、自动改名还是跳过，页面全文没有任何说明。这一条建议你在**自己的测试目录上先跑一次**再对正式曲库动手。

页面上描述多级目录的那句话里有个笔误，照录如下：「选择多级目录，会更加音乐的元数据进行整理分组文件。」[^c5-t4]（**原文如此**，按上下文此处应为"会根据"）。我保留原样，不替官方"顺手改字"后当成结论，但它不影响理解：勾上多级目录后，整理分组会参考元数据来做层级划分；至于按哪个字段分层，仍属上面说的 `未取到`。

#### 删除空文件夹：只删一层，不级联

页面把这条单独列为一节，定义得很清楚：

> 删除文件夹下*无任何文件*的文件夹。
> 例如 A/B/C 都为空， 会优先将 C 目录删除，不会将 A/B/C 级联删除，（如果想级联删除，再执行两次）[^c5-t4]

用官方自己的 A/B/C 例子画出来就是这样：

```text
音乐库根目录/
└── A/
    └── B/
        └── C/        ← 三层都为空时，第一次执行只删掉这一层
```

再执行一次，B 变成最内层的空目录，被删；第三次才轮到 A。所以"清掉一整条空目录链"要执行三次，而不是一次。

> [!tip] 大白话：整理文件夹和"只删一层"
> **整理文件夹**，把元数据想成书脊上的标签，整理文件夹就是那个"按标签把书插回对应书架格"的动作。你没给它新的标签，它只是照着你已经贴好的标签归位；标签写得越规范，归位结果越整齐。
> **删除空文件夹**，像剥洋葱——它一次只剥掉最外面那一层空壳（C），不会连着里面一起拔（A、B 还在）。想剥到底，就多剥两次。

### 5.2 简繁体转换：V1 有页面，但正文只有一张截图

这一节先说一个必须坦白的事实：**V1 手册确实有「简繁体转换」这个独立页面，但页面上除了一个一级标题，只有一张截图，没有任何文字步骤**[^c5-t5]。也就是说，**V1 里这个功能具体怎么操作，`未取到`**——我不会靠猜去补一段"先点 A 再点 B"。

V2 这边的形态不一样。V2 **没有**为简繁体转换单设页面，而是把它作为**后台刮削的"音乐预处理"环节之一**：教程页写的是「繁体转简体：所有繁体中文会被转换成简体中文，保持一致性。」[^c5-t15]。换句话说，在 V2 里它不是你要专门去找的一个按钮，而是后台流水线自动做掉的一步。

> [!warning] 三项操作在 V2 的位置，官方口径与手册实际不一致
> 官方在 V2 项目介绍里写：「V2 版本具有 V1 版本的所有功能」[^c5-t19]。但把 V2 手册的页面树拉出来逐条核对，**找不到「切割音轨」「拆分文件名称」「简繁体转换」对应的独立页面**[^c5-t18]。所以本笔记的写法是：官方称 V2 包含 V1 全部功能，但 V2 手册未为这三项提供独立页面，**实际入口需要你在界面里自行确认**。本节、5.3 节、5.4 节都适用这条提醒。

> [!tip] 大白话：简繁体转换
> 把它想成"把整箱书里竖排繁体的书名，统一改写成简体横排"。V1 里它是一台摆在台面上的独立机器（有页面，但说明书只拍了一张照片、没写怎么开）；V2 里它被搬进流水线，成了后台刮削在入库前顺手做掉的一道工序，你基本感觉不到它单独存在。

### 5.3 拆分文件名称：从文件名倒推标签

**它是什么。** 整理文件夹是"标签 → 目录"，拆分文件名称是**反方向**的一次操作：从文件名里把信息抠出来，写进元数据。页面给出的适用前提很具体：「你收集的音乐文件中，只有文件名称存在歌曲基本信息，元数据中没有的情况，可以快速的将文件名称中的基本信息嵌入到音乐元数据中。」[^c5-t6]

**规则怎么定。** 页面明确两点：

1. 「支持定义两个标题规则，成功命中规则的文件会被修改。」——也就是**最多两条规则**，而且只有**命中**规则的文件才会被改，没命中的原样不动[^c5-t6]。
2. 规则用变量模板书写，官方给的示例是 `${tracknumber}.${title}`。

**带具体值的例子。** 官方把一条完整推演写在了页面上，照录如下：

> 例如： `${tracknumber}.${title}`
> 我的文件名称为：01. 我想.mp3
> `${tracknumber}`= 01, `${title}` = 我想
> 命中规则，会将tracknumber， title 嵌入音乐元数据。[^c5-t6]

读法是这样的：模板 `${tracknumber}.${title}` 描述的是"一个数字、一个点、一段标题"这种文件名形状；`01. 我想.mp3` 正好长成这个形状，于是被命中，`01` 填进音轨号、`我想` 填进标题。如果某个文件叫 `夜曲.mp3`，它不匹配"数字.点.标题"的形状，就不会被这条规则动到。

| 维度 | 整理文件夹（5.1） | 拆分文件名称（5.3） |
| --- | --- | --- |
| 数据流向 | 元数据 → 目录结构 | 文件名 → 元数据 |
| 前提条件 | 元数据里已经有正确的值 | 文件名里有信息、元数据里没有 |
| 匹配方式 | 以元数据中的值分组（字段名 `未取到`） | 最多两条标题规则，命中才改 |
| 结果 | 文件被移动进新目录 | 元数据被写入，文件名不变 |

> [!tip] 大白话：拆分文件名称
> 文件名像快递面单——收件人、电话、地址其实都印在上面了，只是没录进系统。拆分文件名称就是照着面单的**固定版式**（数字、点、名字）把内容抄进系统字段里。版式对不上的（比如面单上没写字号），它就跳过，不会乱抄。

### 5.4 切割音轨：先自己把 ffmpeg 放进去

**它是什么。** 页面副标题一句话说清了输入和输出：「使用CUE专辑标记文件无损切割整轨CD音轨」[^c5-t7]。所谓整轨，就是一张 CD 被完整抓成一个音频文件；CUE 文件则是这张 CD 的"分轨清单"，记录每首歌从第几分几秒开始。切割音轨就是按这份清单把整轨切回一首首单曲。

**前置条件：先自备 ffmpeg。** 这是本节唯一有完整文字步骤的部分，官方写成三步[^c5-t7]：

1. 到 [ffmpeg](https://johnvansickle.com/ffmpeg/) 官网下载，**按你自己电脑的系统架构选版本**；可执行文件要放到挂载出来的 `/app/data/bin/` 目录下（页面提示 `/app/data/` 就是部署时挂载的配置文件路径）。
2. 解压缩后，把其中的 **ffmpeg 单个可执行文件**（页面备注大小为 `20Mb` 左右）移动到 `/app/data/bin` 目录下。
3. 「最终路径是 /app/data/bin/ffmpeg」。

放好之后还有两条「注意点」，第二条是权限相关的命令[^c5-t7]：

```bash
chmod +x /app/data/bin/ffmpeg
```

这两条注意点照录如下：

> 注意点： 1. ffmpeg 不支持 ape 音乐的操作，如需要切分 ape 音乐，可先将 ape 转换为其他格式。
> 2. 需要有 ffmpeg 的执行权限 chmod +x /app/data/bin/ffmpeg[^c5-t7]

第二点说白了就是：文件放过去还不够，还得给它"可执行"的身份，否则程序调不动它。

> [!warning] 本节的三处缺口
> **第一，界面级完整步骤 `未取到`。** 页面只讲 ffmpeg 怎么装，**没写**切割时在界面上选什么、CUE 和音频文件怎么配对、输出目录落在哪。
> **第二，整轨原文件是否保留 `未取到`。** 切完之后原来那个大文件是留着还是删掉，页面未提及。动手前请自行确认或先备份——这正好呼应本章开头的备份建议。
> **第三，V2 有一篇配套的 ffmpeg 安装教程。** V2 手册里另有《ffmpeg安装教程》一页，讲的是同一件事的另一侧：它是从**宿主机**视角出发的，举例说明 `/app/data` 对应宿主机的挂载目录（**原文该处把 `/app/data` 误打成 `/aap/data`**，按上下文应为 `/app/data`，此处按可读方式还原；页面示例目录为 `/volume/music_tag_web/data`），让你在该目录下新建 `bin`，把 ffmpeg 放进去，最终宿主机路径形如 `/volume/music_tag_web/data/bin/ffmpeg`，并在该目录下执行 `chmod +x ffmpeg`[^c5-v2ffmpeg]。它和 T7 并不冲突：**容器内路径固定是 `/app/data/bin/ffmpeg`，宿主机路径则取决于你部署时把 `/app/data` 挂到了哪里**。注意这页只解决"ffmpeg 怎么装"，V2 仍然**没有**切割音轨的操作页。

> [!tip] 大白话：切割音轨与 ffmpeg
> CUE 文件就是这张 CD 的**目录页**，写着"第 1 首 0:00 起、第 2 首 3:42 起"。整轨音频是一整条没有断点的录音带。切割音轨 = 拿着目录页，用一把刀把录音带剪成一首首。
> **ffmpeg 就是那把刀**，而且它不在容器里，得你自己买来放进工具箱。刀放进去还得"开刃"——`chmod +x` 就是给文件加上"可以执行"的身份；少了这一步，工具在盒子里躺着，程序拿不起来。

### 5.5 批量重命名文件名称：一条正则、一条变量

V2 教程页给了两个场景，正好对应批量改名的两条技术路线[^c5-t16]。

#### 场景 1：用正则命名组去掉文件名里的音轨号

需求是"文件名里的音轨号我不喜欢，想批量去掉"。官方拿 `01.夜曲.flac` 举例，先用这条正则解析：

```text
(?P<tracknumber>\d+)\.(?P<title>\w+)
```

`(?P<名字>...)` 这种写法叫**正则命名组**：括号圈住的那段内容会被单独抓出来，并且挂上你指定的名字（这里是 `tracknumber`、`title`）。页面解释这条表达式的含义是「匹配数字（即音轨号）后面跟着一个点和随后的单词字符（即歌曲标题）」[^c5-t16]。

关键在下一步。官方指出：「虽然上述表达式能够正确地解析这些信息，但不会直接更改文件名。」[^c5-t16] 只解析不改名。要实现"去掉音轨号、只留《夜曲》"，**只需把正则里的名字换一个**：

```text
(?P<tracknumber>\d+)\.(?P<filename>\w+)
```

把原本叫 `title` 的那一段改名为 `filename`，等于告诉程序"这段是要拼成最终文件名的部分"；而 `tracknumber` 没有被任何输出模板引用，自然就被丢掉了[^c5-t16]。

> [!note] 为什么改名就能"去掉"音轨号
> 正则负责**切分**，命名组负责**给切出来的片段贴标签**，而最终文件名只由被引用的那些标签拼成。`tracknumber` 切出来但没人引用，它就不参与结果——音轨号就这样"被忽略掉"，而不是被删除。理解这一点，你就能用同一招保住任何想要、丢弃任何不想要的片段。

#### 场景 2：用变量拼出「艺术家-音乐名」

第二条路线不碰正则，改用**变量模板**。官方步骤写得很直接：

1. 「确保元数据完整: 首先确认您的文件元数据中已经包含了正确的艺术家信息。」[^c5-t16]
2. 打开手动刮削功能 → 勾选需要重命名的文件 → 在**「文件名」字段**里用变量拼出新格式。

模板示例是 `${artist}-${title}`，即"艺术家-音乐名"。这里有一条很省事的官方说明：「文件扩展名会继续填充源文件的扩展名，所以你无需额外输入文件扩展名。」[^c5-t16] 也就是你写模板时**不要**带 `.flac`、`.mp3` 这类后缀，程序会自动沿用源文件的扩展名。

| 对比项 | 场景 1：正则命名组 | 场景 2：变量模板 |
| --- | --- | --- |
| 依据的数据 | 当前**文件名**里已有的字符 | 元数据字段（如 `${artist}`、`${title}`） |
| 书写形态 | 正则表达式 + 命名组，如 `(?P<filename>\w+)` | 变量占位符，如 `${artist}-${title}` |
| 前置条件 | 文件名本身有规律可循 | 元数据里已有正确的艺术家等信息 |
| 扩展名 | 由正则保留在文件名结果中 | 自动沿用源文件扩展名，模板里不用写 |
| 适合场景 | 想删掉/重排文件名中已有的片段 | 想按标签内容重新组织文件名 |

> [!tip] 大白话：正则和变量这两条路
> **变量模板**像填报销单：`${artist}-${title}` 是表格里的两个空格，值从**标签**里取，标签填得对，名字就出得来。
> **正则命名组**像拿荧光笔在旧名字上划线分区，再给每一段贴便利贴起名。`(?P<filename>...)` 那张便利贴意味着"这段保留下来当文件名"，没贴便利贴的片段（`tracknumber`）就落选了。所以"去掉音轨号"不是拿橡皮擦，而是**不给它贴便利贴**。

### 5.6 在后台刮削里，「整理 / 转移文件」是必选项

本章最后回到整理这件事——但换到 V2 的自动化视角。V2 教程把「音乐文件整理（必选）」明确标为**必选**，它的内容是两项[^c5-t15]：

- **整理文件**：「确保所有文件按照规定的格式存放。」
- **转移文件**：「根据处理结果（成功或失败），将文件转移到相应的 `completed` 或 `failed` 目录中。」

注意后半句：**原文件的位置会被移动**——处理成功的进 `completed`，失败的进 `failed`。这是本章里最容易被忽略的一次"文件搬家"，因为它是后台自动发生的。

为什么必须选？官方 FAQ 的回答是：

> A：是的，必须要选择，不然每次监控就不是增量数据，数据会越积累越多，这个目录的目的是为了新增音乐的自动刮削，如果因此不满足你的需求，我们从长计议。[^c5-f1]

也就是：这个"整理 + 转移"是把处理过的文件挪走，好让监控目录里只剩**新增**的待处理文件，从而保证后台每次扫描都是增量。

> [!warning] 关于 FAQ 第 6 条的一处来源核对结果
> 本章的素材清单里列有「常见问题 第 6 条」。回源核对后：**FAQ 第 6 条问的是"音乐收藏一直在 loading"，答案是 subsonic 密码需设置后重新登录刷新**，与本章的整理/批处理无关[^c5-f1]。而"转移/整理是否必选"实际落在 **FAQ 第 11 条**，上面引用的就是它。因此本节引用的是第 11 条，第 6 条的内容归入登录与播放相关的章节。

> [!note] 与第四章的衔接
> 后台刮削怎么开启、监控目录 `/app/download` 与 `/app/media/download` 怎么选、音乐预处理包含哪几项，属于第四章的范围，这里不展开——你只需要先记住一件事：**后台刮削一旦开起来，它会自动帮你做本章 5.1 的"整理"和一次文件转移**。

> - 整理文件夹的**分组键字段**与**同名冲突策略**官方均未写明（`未取到`），建议先在测试目录跑一遍。
> - 「删除空文件夹」**只删当前一层、不级联**：A/B/C 全空时要执行三次才清完。
> - 简繁体转换在 V1 是只有截图的独立页（操作方式 `未取到`），在 V2 被并入后台刮削的"音乐预处理"。
> - 切割音轨必须先自备 ffmpeg 放到 `/app/data/bin/`，并用 `chmod +x /app/data/bin/ffmpeg` 赋执行权限；`ape` 需先转格式，整轨原文件是否保留 `未取到`。
> - 批量重命名两条路：正则命名组决定"保留哪些片段"，变量模板从元数据拼名，且扩展名自动沿用、无需手写。
> - 本次收集的 11 个**标签操作页面**均无备份建议与不可逆告警；但官方《容器自动更新》页「最佳实践」写有「保持备份：重要数据定期备份，避免意外情况」。动手前自行备份仍属本笔记建议。

## 附录 A 播放侧与生态（可跳读）

> [!note] 这一节可跳读，不影响主线
> 正文主线到「整理与批处理」就收束了。本附录只装播放侧的零散能力：Subsonic 服务端与客户端清单、音乐收藏、Navidrome 联动、小爱音箱、网盘音乐、智能歌单与去重。你暂时没有 Navidrome / Jellyfin，所以「边车」定位不展开；每小节可单独跳读。

### A.1 服务端：V2 自己就是一台音乐服务器

V2 的播放服务端是自带的，不必再装一个 Navidrome 之类的服务端。「音乐收藏与播放」页开头写：「Open Subsonic 协议的播放服务器。登录的 host 是站点 ip:8002, 账号密码在后台管理里subsonic 用户中查看并修改。」[^cA-p1]「Subsonic客户端」页说得更直接：「Music Tag Web 提供音乐服务器，就不需要其他的服务端了，可以直接用下列中的客户端连接听歌了」。[^cA-p6]

同页第 4、5 条补了两点：

1. 第 4 条写「支持所有 subsonic 的客户端。 基于 Open Subsonic 协议音乐播放接口。」[^cA-p1]，所以客户端不限于官方列出的那几款。
2. 密码不在「修改密码」页改。第 5 条写：「admin/后台中 subsonic 用户中，修改 api token 即是密码。」改完「需要重新登录后刷新页面」。[^cA-p1]

> [!warning] 默认凭据是文档空白，别照猜
> Subsonic 用户的**默认用户名与默认密码具体值**，官方页面没给，本笔记同样没取到，也不会替你编一个。登录不上时，直接去后台看 subsonic 用户的当前配置。

> [!tip] 大白话
> 把 V2 想成一台自带点歌台的音箱柜：柜子（服务端）随柜附带，不用另买功放。8002 是门牌号，各种 Subsonic 客户端只是不同样式的遥控器。关键不是「再装一个服务端」，而是「把门牌号告诉遥控器」。

同一套官方手册里，「跨平台」一行列的客户端不一致：

| 平台 | 「音乐收藏与播放」页 | 「Subsonic客户端」页 |
| --- | --- | --- |
| 跨平台 | 音流 | 箭头音乐、音流 |
| Android | Symfonium、DSub、Tempo、substreamer、Subtracks、Ultrasonic | 与左列相同 |
| iOS | play:Sub、substreamer、Amperfy、iSub | 与左列相同 |
| Web | Thunderdrome、Airsonic Refix、Subplayer、Aurial、Subfire、Jamstash | 与左列相同 |
| 桌面 | Supersonic、Sublime Music、Submariner、Sonixd | 与左列相同 |

差异只在「跨平台」一行：前者写「音流」[^cA-p1]，后者写「箭头音乐、音流」[^cA-p6]，其余四类两页一致。

> [!note] 怎么理解这一处不一致

### A.3 音乐收藏：先导入，才有得播

播放侧的一切都建立在「音乐收藏」这个中间层上，它和「操作台里能看到文件」不是一回事。第 1 条写：「在操作台中，勾选想要导入的目录，导入收藏，等待导入后可在音乐收藏中展示。」[^cA-p1] 顺序是勾选目录 → 导入收藏 → 等跑完。

第 6 条讲反过来的清理：「已经导入收藏的音乐，后续在文件管理中删除了，收藏中还存在可在其他设置-删除不存在收藏中同步删除，或着直接通过 操作台中的删除文件夹功能删除文件。该功能会同时删除音乐收藏中的音乐。」[^cA-p1]

> [!warning] 删文件会连带删收藏
> 「该功能会同时删除音乐收藏中的音乐」，指用操作台「删除文件夹」删文件时，收藏记录会被一起清掉。想只清记录不动文件，走「其他设置-删除不存在收藏」。

> [!tip] 大白话
> 把音乐收藏想成图书馆的**索书卡**，操作台里的文件是**书架**。往书架塞新书，索书卡不会自动出现——必须手动「导入收藏」建卡；书被抽走，卡片还留在盒子里（所以有「删除不存在收藏」补卡）。而操作台的「删除文件夹」是连书带卡一起扔。

### A.4 Navidrome 联动：`artist.jpg` 和 `cover.jpg` 是两类文件

**官方教程讲艺术家图。**前提条件写得很明确：「确保您的音乐已导入到音乐收藏中。」[^cA-p7] 即 A.3 没做完就不必往下看。流程三步：

1. 「系统设置」→「其他设置」→「刮削艺术家」，点击按钮；完成后到「操作记录」看刮削详情。
2. 若目录结构形如 `/app/media/music/王以太/演.说.家/人间天堂.flac`，那么「则系统将在 `/王以太/` 目录下自动生成 `artist.jpg` 文件。」
3. 「`artist.jpg` 文件将被 NaviDrome 自动识别并用于艺术家页面的展示。」[^cA-p7]

「总结」把目录结构写成硬约束：`/艺术家/` → `/专辑/` → `音乐文件`，原话是「为了确保艺术家封面能被正确显示，请务必按照以下目录结构组织您的音乐文件」[^cA-p7]；页首也自称「本实验演示在music tag web 中批量刮削艺术家封面，并成功被 navidrome 识别到」[^cA-p7]。

**社区经验讲专辑图。** 飞牛论坛帖里，有用户给出打开「导出图片」开关的做法：「我发现navidrome显示的专辑封面是取得歌曲文件夹里面的cover.jpg，用music-tag刮削后，要把“导出图片”这个设置为开，保存音乐信息就会自动生成一张cover.jpg。」[^cA-p8] 这是**社区经验，非官方口径**；同帖后续有人回「成功了，感谢」。

| 维度 | `artist.jpg` | `cover.jpg` |
| --- | --- | --- |
| 来源层级 | 官方教程（P7） | 社区经验（P8） |
| 对应界面 | 「刮削艺术家」 | 「导出图片」开关设为开 |
| 生成位置 | `/艺术家名/` 目录下 | 歌曲所在文件夹内 |
| 服务对象 | Navidrome 艺术家页展示 | Navidrome 专辑封面展示 |

**关于「部分识别不出」。** 楼主说的是：「music-tag 刮削过后 navidrome 部分有些还是识别不出来 手动和自动刮削都试过了」[^cA-p8]。这**不构成对官方成功结论的反驳**——官方实验针对 `artist.jpg`，该帖讨论的主要是专辑封面一侧。

同帖另有用户给出体积与分辨率经验值：「有情提示 图片别大于80K 不信你可以试一下」「补充下 分辨 800-550 左右合适 高了有时候不识别」[^cA-p8]。这是**社区经验值**：官方没给封面体积或分辨率限制，请当作排错方向，别当硬阈值。

> [!tip] 大白话
> 把音乐文件想成一份份**塑封专辑**：`cover.jpg` 是**专辑盒面**上的图，`artist.jpg` 是**歌手货架**上的头像。Navidrome 逛货架先看头像，翻专辑先看盒面。所以「头像贴好了但盒面空着」，看起来就是「部分识别不出」——不是方法失效，是你贴错了位置。

### A.5 社区 compose 样例：两容器共用一个音乐目录

> [!warning] 这是社区做法，不是官方推荐配置
> 下面整段来自博客园一篇个人文章[^cA-p9]，属**社区实践层级**。其中端口等数值**不能当官方事实**：官方 P1–P7 从未提及 Navidrome 默认端口。

该文作者把 Navidrome 与 MTW 放进同一份 compose，两容器挂**同一个音乐目录**：Navidrome 挂 `/music`，MTW 挂 `/app/media`，改完标签两边读的是同一批文件。

```yaml
version: "3"
services:
  navidrome:
    image: deluan/navidrome:latest
    container_name: navidrome
    ports:
      - "4533:4533"
    environment:
      - ND_LOGLEVEL=info
      - ND_MUSICFOLDER=/music
      - ND_DATAFOLDER=/data
      - ND_ENABLEDOWNLOADS=true
    volumes:
      - /vol1/1001/06_Music:/music  # 你的音乐目录，和NAS路径对应
      - ./navidrome:/data  # Navidrome 数据持久化
    restart: always
    networks:
      - music-network

  musictagweb:
    image: xhongc/music_tag_web:latest
    container_name: musictagweb
    ports:
      - "8002:8002"  # 前端访问端口，可自行修改
    volumes:
      - /vol1/1001/06_Music:/app/media  # 挂载和Navidrome相同的音乐目录，直接编辑标签
      - ./musictagweb/data:/app/data  # 挂载数据存储目录
    restart: unless-stopped
    networks:
      - music-network

networks:
  music-network:
    driver: bridge
```

两处可留意：MTW 只挂 `/app/media` 与 `/app/data`，没有 `/app/download`（该作者不需要后台刮削）；MTW 用 `restart: unless-stopped`，作者解释是「在MusicTagWeb上面，启动模式是 unless-stopped ，也就是可以随时手动停止」，需要加歌时再打开容器，属低性能 NAS 的省资源取舍[^cA-p9]。`8002:8002` 与官方 V2 端口一致。

### A.6 小爱音箱：用语音点局域网里的歌

功能定位是「使用小爱音箱播放局域网内的音乐，支持歌曲和播放列表点歌。」[^cA-p2] 配置项按官方顺序填：

1. **设备型号、名称、小米账号。** 型号看音箱底部标签（例如 LX06）；账号「为小米 ID ，非手机号码」；名称填账号下这台音箱的名字，改过名填改后的。
2. **关键字**：识别「要播放局域网音乐」的需求。
3. **内网地址和端口**：「内网地址是本项目的内网地址，端口是部署命令的端口。」[^cA-p2]
4. **测试连接**：成功会发出语音；没声音先核对配置与账号密码，都正确还没声音，可能是「该型号的音箱不支持这个功能」。
5. **轮询时间**：查询间隔，单位秒。
6. **是否启用**：唤醒说「小爱同学 关键词 歌曲名」，操作日志可看是否检索到（官方连写三遍「不需要说歌手！」）。

官方列的兼容性口径是：「测试通过的型号 LX06，L16A，LX5A ，L17A，S12。」另有「只能播放mp3 格式的型号：L05B」。[^cA-p2]

> [!warning] 型号清单不是白名单
> 官方只给了「测试通过」和「只能播 mp3」各一条，并提示其他型号「可能是该型号的音箱不支持这个功能」。**清单之外的机型行为如何，官方没有完整兼容列表**——本笔记也没有，别反推「不在列表里就一定不行」。

### A.7 网盘音乐：直连与本地挂载，先分清再选

这页给出两条路径，差别不在配置细节，而在**刮削会不会动到网盘上的原始文件**。

**直连模式**官方定义是「直接连接 alist api，对网盘音乐进行刮削和入库。」[^cA-p3] 要填 Alist Url、根目录地址、alist 用户名与账号密码，另有「显示条数」「清除缓存」；根目录地址映射到容器内 `/app/webdav/`，配好后去「操作台」看该目录是否出现网盘文件。关键是那句提示：「注意：刮削操作不会修改网盘音乐文件的元数据。」[^cA-p3]

**本地挂载**的官方说明是「通过挂载工具将网盘挂载本地/app/weddav 目录，可当做本地文件使用」[^cA-p3]。四步：

1. 部署时额外增加映射卷，官方示例写 `/path/to/your/webdavmusic:/app/webdav:rw`；挂载地址要与 alist 里的一致，alist 才能正确解析。
2. 「系统设置」→「基本设置」→「webdav写入位置」→ 勾选「数据库」。
3. 导入收藏。
4. 「系统设置」→「网盘音乐」→ 配置 alist 地址。

> [!note] 原文拼写不一致，按 `webdav` 理解
> 本地挂载那段正文把路径写成 `/app/weddav`（多一个 d），同页映射示例写的是 `/app/webdav`。这是页面内的笔误，**原文如此，保留原样不做「顺手修正」**；实操按映射示例的 `/app/webdav` 来。

| 维度 | 直连模式 | 本地挂载 |
| --- | --- | --- |
| 前置 | alist 可访问 + 账号密码 | alist 可访问 + 额外映射一卷 |
| 刮削是否改网盘原文件 | 官方明示：不会修改 | 当作本地文件使用 |
| 额外步骤 | 无 | 勾选 webdav 写入位置为「数据库」→ 导入收藏 |
| 适合谁 | 只想在 MTW 里管理、不愿动云上文件 | 想把网盘当本地曲库处理 |

> [!tip] 大白话
> 把网盘想成**别人家的仓库**。直连是「隔着窗户看货、在自家账本上登记」，货不动；本地挂载是「把货搬进自己院子」。后者自由度高，但记得勾「webdav 写入位置-数据库」，否则你会对着一个不更新的收藏列表发呆。

**网盘类型是文档空白**：该页只说明经 alist 接入，**未列举支持哪些具体网盘**，本笔记同样没取到。

### A.8 智能歌单与音乐去重

两个都是轻量工具，不需要账号或插件，门槛只是「音乐库里有东西」。

**智能歌单**入口是「音乐收藏-智能歌单」，作用一句话：「根据满足条件快速从音乐库中创建歌单列表」[^cA-p4]。但该页只有标题、一张截图和这一句，**没有列出「条件」支持哪些字段或操作符**——这是未取到的内容，本笔记不补写条件清单。

**音乐去重**入口是「操作台-勾选目录-重复文件检查」。页首那句最要紧：「查找出重复的文件 不会自动删除您的文件，可以到操作记录中查看重复文件进一步删除操作。」[^cA-p5] 执行成功后到「操作记录」看结果，详情罗列检查到的重复文件，由你挑要删哪些。

> [!tip] 大白话
> 音乐去重像**超市盘点时拉一张「疑似同款」清单**：它只把重复的挑出来摆在你面前，一支笔都不替你划。真正的删除永远在「操作记录」里由你手动完成。看到检查跑完别以为文件已经清掉了——那只是一张待办清单。

### 附录 A 小结

- **服务端自带**：连站点 IP 加 8002；密码在后台 subsonic 用户里，改「api token」即是改密码，改完重新登录刷新；**默认凭据官方未给出**。
- **客户端清单取两页并集**：跨平台「音流 / 箭头音乐」，其余四类两页一致。
- **音乐收藏是中间层**：必须手动「导入收藏」；清记录走「删除不存在收藏」，而「删除文件夹」会连收藏一起删。

### B.1 切换到 MySQL（解决 `sqlite database is locked`）

MySQL 页开篇原文：「本项目默认采用Sqlite数据库，sqlite 在并发写入时容易出现sqlite database is locked，因此支持提供替换成为 msyql 数据库」（末词 "msyql" 为原文拼写）[^cB-n6]。该页每个 `MYSQL_*` 变量都注明「（没有可以不填，默认使用 sqlite）」——它是**替换项**，不是必需项。

> [!tip] 大白话
> Sqlite 像**只有一支笔的账本**：同一时刻只能一个人写，第二个来写就得等，等不到就报 "database is locked"；MySQL 像**银行柜台**，多人各写各的。只有多任务同时写（后台刮削撞上手动编辑）时，才值得换。

#### 方法一（推荐）：一个 yaml 起两个容器

原文：「在一个 yaml 文件中部署 MySQL 和 Music Tag Web 两个容器。」[^cB-n6] 这份可直接跑，替换三处（密码、音乐目录、配置目录）即可。

```yaml
version: '3'

services:
  db:
    image: mysql:latest
    container_name: mysql
    restart: always
    command:
      --character-set-server=utf8mb4
      --collation-server=utf8mb4_unicode_ci
    environment:
      MYSQL_ROOT_PASSWORD: your_root_password  # ← 改成你自己的强密码
      MYSQL_DATABASE: music_tag  # 数据库名
    volumes:
      - ./mysql-data:/var/lib/mysql

  music-tag:
    image: xhongc/music_tag_web:latest
    container_name: music-tag-web
    ports:
      - "8002:8002"  # 主机端口:容器端口
    volumes:
      - /path/to/your/music:/app/media  # ← 改成你的音乐文件目录
      - /path/to/your/config:/app/data  # ← 改成你的配置文件目录
    environment:
      - MYSQL_HOST=db  # 数据库主机名（服务名）
      - MYSQL_PASSWORD=your_root_password  # 与上面一致
      - MYSQL_DB_NAME=music_tag  # 数据库名
      - MYSQL_USER=root
      - MYSQL_PORT=3306
      - WORKER_NUM=8  # 后台任务线程数
    restart: always
    depends_on:
      - db
```

启动用 `docker-compose up -d`，验证是「打开浏览器，访问 `http://你的服务器IP:8002`」；原文另提示首次部署「建议**不额外修改任何默认配置**」[^cB-n6]。注意 `MYSQL_HOST=db` 填的是 **MySQL 的服务名**而非 IP。

#### 方法二：分开部署

原文写的是「分开部署 mysql 和 music tag web 容器」[^cB-n6]。先单独起 MySQL：

```bash
docker run -p 3306:3306 --name mysql \
  -v /your/mysql/data:/var/lib/mysql \
  --restart=always \
  -e MYSQL_ROOT_PASSWORD=your_root_password \
  -e MYSQL_DATABASE=music_tag \
  -d mysql:latest
```

再停掉原有容器、加上 `MYSQL_*` 变量重启它（页内称 `/app/media`、`/app/data` 目录无需删除），变量说明为：`MYSQL_HOST` 填 MySQL 的局域网 IP，`MYSQL_PASSWORD` 填上文配置的密码，`MYSQL_DB_NAME` 填数据库名，`MYSQL_USER` 默认 root，`MYSQL_PORT` 默认 3306[^cB-n6]。

> [!warning] 同一变量在页内有两种叫法
> `MYSQL_DB_NAME` 在方法一注释里叫「数据库名称，无需修改」，方法二注释里却叫「数据表名称（没有可以不填，默认使用 sqlite）」[^cB-n6]，二者并不等价。按它与 `MYSQL_DATABASE: music_tag` 的对应关系，理解成**数据库名**、值保持 `music_tag`。

#### 配完打不开？官方 5 条自查

原页「配置完成后打不开 music tag web？」给出 5 条[^cB-n6]：MySQL 端口是否暴露；music tag web 能否访问到 mysql；原先已有 mysql 时是否建了 `music_tag` 数据库；配置是否拼写错误；mysql 版本太新可用 `mysql:5.7`。

> [!note] 本节空白
> 从 Sqlite 切到 MySQL 后**原有数据如何迁移，N6 全页未说明**（`未取到`）；动手前先整体备份 `/app/data`。

### B.2 接外置 Redis

外置 Redis 页首段：「容器本身就会启动一个 redis，如果你不需要**外置**的 redis，可以不进行此项的配置。」[^cB-n7] 即**不配置是默认状态**，只有服务器上已有 Redis 想复用时才需要往下看。

> [!tip] 大白话
> Redis 像**前台那块便签板**：常用信息抄在板上，取用快，断电就没了，真正的账本在数据库里。容器自带一块够用，已有自己的板子就让容器指向它。

**方法一（复用已有 Redis）**：原文要求在环境变量添加 `REDIS_HOST`；改用其他端口时需同时设置 `REDIS_PORT`。`REDIS_HOST` 可填局域网 IP 或容器网络里的连接地址；若 Redis 设了密码，还需 `REDIS_PASSWORD`[^cB-n7]。

**方法二（一起写进 compose）**：原文是「在一个yaml 文件中一起部署 redis 和 music tag web」[^cB-n7]：

```yaml
version: '3'

services:
  redis:
    image: redis:latest
    container_name: redis
    restart: always
    ports:
      - "6379:6379"  # 主机端口:容器端口
    command: redis-server --requirepass yourpassword  # 设置密码

  music-tag:
    image: xhongc/music_tag_web:latest
    container_name: music-tag-web
    ports:
      - "8002:8002"
    volumes:
      - /path/to/your/music:/app/media  # ← 改成你的音乐文件目录
      - /path/to/your/config:/app/data  # ← 改成你的配置文件目录
    environment:
      - REDIS_HOST=redis  # 服务名
      - REDIS_PASSWORD=yourpassword  # 与上面一致
      - REDIS_PORT=6379
    restart: always
    depends_on:
      - redis
```

`REDIS_HOST=redis` 同样是**服务名**；密码在 Redis 侧由 `command: redis-server --requirepass yourpassword` 设定，再用 `REDIS_PASSWORD` 传给 Music Tag Web，两处必须一致[^cB-n7]。

> [!warning] `REDIS_PORT` 的默认值，文档给了两个
> 自定义端口页（N8）表格中 `REDIS_PORT` 既写默认「6379」，又备注「选填，v2.6.0 及以上版本默认 6380」[^cB-n8]；外置 Redis 页（N7）正文则写「其默认端口为 6379」[^cB-n7]。两说并存，**取哪个取决于版本是否 ≥ v2.6.0**，本笔记无法确认你手上镜像的实际默认值；稳妥做法是显式写出 `REDIS_PORT`。

> [!note] 本节空白
> 切到外置 Redis 后原有缓存/数据是否重建，N7 全页未说明（`未取到`）。

### B.3 自定义服务端口（host / bridge 两种改法）

自定义端口页首句：「如果你使用网络模式host，出现端口冲突，可以进行自定义端口号」[^cB-n8]——host 模式下容器直接占用宿主机的 8001 / 8002 / 9001，被占就起不来。

「二、核心环境变量说明（容器内端口）」的表[^cB-n8]：

| 环境变量 | 作用说明 | 默认值 | 特殊说明 |
| --- | --- | --- | --- |
| `GUNICORN_PORT` | 后端服务端口 | 8001 | 选填 |
| `NGINX_PORT` | Nginx 代理后的后端服务端口 | 8002 | 选填 |
| `SUPERVISOR_PORT` | Supervisor 进程管理端口 | 9001 | 选填 |
| `REDIS_PORT` | Redis 服务端口 | 6379 | 选填，v2.6.0 及以上版本默认 6380 |

原文：这些变量「仅影响容器内部，不直接映射到主机」[^cB-n8]。

**host 模式（原文标为"推荐修改方式"）**：「直接在 `environment` 中添加需自定义的端口变量，无需修改 `ports` 配置。」[^cB-n8]

**bridge 模式（原文标为"特殊情况修改"）**：「一般无需修改容器内端口，仅需在 `ports` 中映射主机端口即可」；若确要改容器内端口，两个条件必须同时满足——改 `environment` 里对应变量（如 `GUNICORN_PORT`），并在 `ports` 中同步映射新的容器内端口（如 `"8006:8006"`）[^cB-n8]。**少改任意一处都接不上。**

> [!tip] 大白话
> 端口像**门牌号**：host 模式是"门牌直接挂在街上"，号被占就得换；bridge 模式是"你在小区里，大门另有对外门牌"——外面换号不影响屋里，**屋里换号则内外两块牌子必须同时换**，否则快递（请求）送不到门口。

原页「四、完整配置示例」把主机与容器内端口改成 8006、另设 `GUNICORN_PORT=8003`，并注明 `ports` 的容器内端口要「与NGINX_PORT保持一致」：

```yaml
music-tag:
    image: xhongc/music_tag_web:latest
    container_name: music-tag-web
    ports:
      - "8006:8006"  # 主机端口:容器内端口（与NGINX_PORT保持一致）
    volumes:
      - /path/to/your/music:/app/media
      - ./config:/app/data
    environment:
      - WORKER_NUM=8
      - GUNICORN_PORT=8003  # 自定义后端服务端口
      - NGINX_PORT=8006  # 与 ports 映射的容器内端口一致
      - SUPERVISOR_PORT=9001  # 默认值
    restart: always
    depends_on:
      - db  # 依赖MySQL服务，确保先启动数据库
```

该示例原文没有顶层 `version:` / `services:` 包裹，服务名直接写 `music-tag`，并带 `depends_on: db`——它本是 MySQL 方案的一部分，单独抄用需补回外层结构并删掉 `depends_on`。

> [!note] 本节空白
> 三个端口变量**是否必须保持特定关系，N8 未说明**（`未取到`）；能确认的只有：`NGINX_PORT` 与 `ports` 的容器内端口取同一值。

### B.4 自动更新、定时更新与三种升级方式

#### B.4.1 一键更新与 Docker Socket 前提

自动更新页声明其可自动完成：「下载最新版本的程序 / 停止旧版本容器 / 启动新版本容器 / 清理旧版本镜像，释放磁盘空间 / 保留你的所有数据和配置」[^cB-n9]。入口是登录后左侧菜单「系统设置」→「系统信息」→「系统版本」点「检查更新」，再确认容器名称（通常为 `music-tag-web`）[^cB-n9]。

前提原文加重语气：「**如果你想使用自动更新功能，在首次部署时必须挂载 Docker Socket。**」[^cB-n9] 对应一行挂载：

```yaml
      - /var/run/docker.sock:/var/run/docker.sock
```

未挂载时原页列出的表现有「Docker客户端初始化失败」「无法连接到 Docker daemon」「更新按钮点击后没有反应」[^cB-n9]。检查是否挂上，原文给两法：

```bash
# 方法 1：看容器配置里的挂载项
docker inspect music-tag-web | grep docker.sock
# 期望看到："Source": "/var/run/docker.sock", "Destination": "/var/run/docker.sock"

# 方法 2：进容器查看
docker exec -it music-tag-web bash
ls -l /var/run/docker.sock
# 期望看到：srw-rw---- 1 root docker 0 Dec  2 10:00 /var/run/docker.sock
```

> [!tip] 大白话
> Docker Socket 像**整栋楼的总电闸钥匙**：容器本只能用自己屋里的插座；挂上 socket 等于把总闸钥匙交给它，它才能开关别的容器、拉删镜像——自动更新靠的正是这个"越权"。代价是能进容器的人就握有宿主机 Docker 的控制权。

#### B.4.2 定时更新：两种 Watchtower 用法

方法 1，系统 crontab（示例为每天凌晨 3 点跑一次）[^cB-n9]：

```bash
crontab -e
0 3 * * * docker run --rm -v /var/run/docker.sock:/var/run/docker.sock containrrr/watchtower --cleanup --run-once music-tag-web
```

方法 2，常驻 Watchtower（`--interval 86400` 表示每 24 小时检查一次，`--cleanup` 表示自动清理旧镜像）[^cB-n9]：

```bash
docker run -d \
  --name watchtower \
  --restart unless-stopped \
  -v /var/run/docker.sock:/var/run/docker.sock \
  containrrr/watchtower \
  --cleanup \
  --interval 86400 \
  music-tag-web
```

两条命令末尾的 `music-tag-web` 都是**要监控的容器名**；网络受限时官方给替代镜像 `registry.cn-hangzhou.aliyuncs.com/xhongc/watchtower:latest`[^cB-n9]。

> [!warning] 容器名对不上，Watchtower 就白跑
> 更新页与 `docker run` 场景用 `music-tag-web`[^cB-n9]，升级页的 Watchtower 示例末尾却写 `music_tag_web`（下划线）[^cB-f4]。**命令末尾必须换成你机器上真实的容器名**（用 `docker ps` 的 `NAMES` 列确认）；名字写错时它不报错、也不更新，最难发现。

#### B.4.3 三种升级方式（含 `down -v` 警告）

升级页开头写「提供3种方式进行更新」：docker pull、Docker Compose、watchtower[^cB-f4]。

**方式一 `docker pull` 后重建**：先拉新镜像，再「停止正在运行的旧版容器，并将其删除」，最后按「快速开始」的命令用新镜像重新部署[^cB-f4]：

```bash
docker stop my-music-tag-web   # ← 换成你的容器名
docker rm my-music-tag-web
```

**方式二 Docker Compose**：原文说 Compose「可以自动处理容器的停止、删除和重新创建」，步骤为「拉取新镜像：`docker-compose pull`」+「更新并重启服务：`docker-compose up -d`」[^cB-f4]。

> [!warning] `docker-compose down -v` 会连卷一起删
> 原页区分两条命令：`docker-compose down` 只清理「容器、网络但不包括卷（数据持久化存储）」；「若要连同卷一起删除，请添加 -v 选项：`docker-compose down -v`」。紧接的提醒是「确保所有重要数据都已正确挂载到持久化存储上，防止数据丢失。」[^cB-f4] 除非你确定数据都挂在宿主机目录且另有备份，**不要用 `-v`**：卷一删，`/app/data` 里的配置与数据库一并没了。

**方式三 watchtower 一次性更新**：「`docker run --rm -v /var/run/docker.sock:/var/run/docker.sock containrrr/watchtower --cleanup --run-once music_tag_web`」，末尾换成你自己的容器名[^cB-f4]。

> [!warning] 升级示例里的镜像名少了个 `c`
> 升级页示例写 `docker pull xhong/music_tag_web:2.0.1`[^cB-f4]，正确的仓库名是 `xhongc/music_tag_web`[^cB-n6][^cB-n7][^cB-n9]，照抄会**拉不到镜像**；`2.0.1` 只是「假设我们想要更新到版本 2.0.1」的举例[^cB-f4]，**当前最新版本号本笔记无法确认**（`未取到`）。

#### B.4.4 服务名不一致：抄哪份 yaml 就按哪份的服务名

| 出处 | 服务名 | `container_name` |
| --- | --- | --- |
| MySQL 页 方法一 / 方法二 | `music-tag` | `music-tag-web` |
| 外置 Redis 页 方法二 | `music-tag` | `music-tag-web` |
| 自定义端口页 示例 | `music-tag` | `music-tag-web` |
| 自动更新页 首段 yaml | `music-tag-web` | `music-tag-web` |
| 自动更新页「确保数据持久化」片段 | `web` | （未写） |

**服务名在官方各页之间不统一，同一页内也会变**[^cB-n6][^cB-n7][^cB-n8][^cB-n9]。`depends_on` 与 `docker-compose up <name>` 里的名字，必须和自己 yaml 的服务名逐字一致。

#### B.4.5 更新耗时与中断

原页「更新需要多长时间？」写「**通常 1-5 分钟**」；同页「步骤 2：执行更新」写的是「等待更新完成（通常需要 1-3 分钟）」[^cB-n9]。

> [!note] 两个数字并列，不合并
> 同一页给出「1-3 分钟」与「1-5 分钟」两种耗时，官方未说明适用条件差异，本笔记**并列保留两个说法**。

### B.5 多目录独立挂载

原页定位：「将多个音乐库目录添加到容器中，实现灵活管理且避免路径冲突」，适合音乐分散在多处的用户[^cB-f6]。做法是在 `docker-compose.yml` 的 `volumes` 段按分类逐行添加：

```yaml
volumes:
  # 流行音乐库
  - /path/to/your/pop_music:/app/media/Pop
  # 摇滚音乐库
  - /path/to/your/rock_music:/app/media/Rock
  # 古典音乐库
  - /path/to/your/classical_music:/app/media/Classical
  # - /path/to/another_music:/music/AnotherCategory
```

原页解释：左侧「是你本地计算机上的实际音乐文件夹路径」，右侧「是容器内的路径，按音乐类别进行分类」[^cB-f6]；改完执行 `docker-compose down` 再 `docker-compose up -d` 生效[^cB-f6]。

> [!tip] 大白话
> 默认是把整个曲库**一个书架**搬进容器；音乐按类型散在几处时，硬合成一个目录既费事又易乱。多目录挂载相当于**在容器里摆几个贴着标签的格子**，每个宿主机文件夹各接一格，将来挪哪个只动哪一根线。

> [!warning] 同一页的容器内路径有两版，对不上
> 配置段的映射写 `/app/media/Pop`，同页「容器内访问」一节却列出「`/music/Pop`：对应本地流行音乐库」[^cB-f6]，两组路径互斥。**本笔记按配置段（`/app/media/<分类>`）理解**——它可执行，也与第二章「`/app/media` 是曲库根目录」一致；原文两版并存。

原页四条注意事项中最关键的两条[^cB-f6]：1）「确保挂载路径的正确性，错误的路径会导致容器无法访问音乐文件」；2）「新增或移除音乐库后，需要重启容器才能生效」。

### B.6 升级前检查清单

> [!warning] 本节依据社区反馈，不是官方口径
> 下列现象来自项目 issue **#546**（用户报告 + 作者回复），属**社区层级**；清单是本笔记建议。官方自动更新页的声明是「保留你的所有数据和配置」[^cB-n9]，与 #546 现象并不一致，两者并列，不替任一方下结论。

**社区现象（#546）**：用户报告「就是升级了2.66版本，没有做任何命令改变。升级完成再打开音乐收藏图片全部不显示，专辑艺术家都无法显示」；作者追问附件目录是否被删，用户答复只删了旧镜像、拉了新镜像，设置都在，唯独封面丢失，且附件目录里图片仍在。到本笔记可复核到的公开评论为止**未见根因结论**[^cB-f14]。

**升级前检查清单（本笔记建议，非官方口径）**：

1. **先备份 `/app/data`**：整目录打包到容器外另存一份。
2. **确认卷映射未变**：核对 `/app/media`、`/app/data`、`/app/download` 三条挂载仍在、左侧值未改。
3. **升级后立刻验证封面**：#546 的现象正是升级后才暴露。
4. **保留旧镜像**：自动更新会「清理旧版本镜像」[^cB-n9]，留一份旧 tag 便于回退。
5. **避开低峰时段**：更新期间服务会短暂中断[^cB-n9]。

> [!note] 本附录的已知空白
> 下列四项本次复核均未找到官方说明，均为 `未取到`，本笔记不作陈述：Sqlite→MySQL 的数据迁移方式；切外置 Redis 后原有缓存/数据的处理；当前最新版本号；三个端口变量（`GUNICORN_PORT`/`NGINX_PORT`/`SUPERVISOR_PORT`）是否必须保持特定关系。

> [!summary] 本附录小结
> - **MySQL 与 Redis 都是替换项**：默认 Sqlite、容器自带 redis；`MYSQL_HOST` 填服务名，`REDIS_PORT` 默认值有 6379 与「≥ v2.6.0 时 6380」两说。
> - **改端口分网络模式**：host 只改 `environment`；bridge 改容器内端口须 `environment` 与 `ports` 同改。
> - **自动更新的前提是挂上 `docker.sock`**，容器名用 `docker ps` 核对。
> - **升级三法**：`docker pull` 重建、`docker-compose pull` + `up -d`、watchtower；`down -v` 会连卷删除。
> - **升级前先备份 `/app/data`**——本笔记建议，依据社区 #546。

只想稳定使用的话，B.1–B.3 大多可以不动；真正值得现在就做的是 B.6 第 1 项。遇到具体故障，再翻附录 C 的排错 FAQ。

## 附录 C 排错 FAQ 与已知文档缺陷（可跳读）

> [!note] 这篇什么时候看
> 正文五章讲的是「顺利用下去」，本附录讲「卡住了怎么办」。前半按故障簇排（登录 → 改密 → 升级 → 数据库 → Redis → 文件名 → FLAC → Subsonic → 刮削），后半是 FAQ 精选、**官方没写清的**、以及**官方文档自身的缺陷清单**。带「未取到」说明的条目只到标题/正文层级，**不要当成已确认的解法**。

排错时最容易犯的一个错，是把 issue 里的一句话当成官方结论。先花一分钟把下面这件事分清楚，后面会一直用到。

### C.1 先分清三种「说法」

这个项目的故障信息有三个来源，权威性完全不同：

| 说法 | 谁说的 | 可信度 | 本附录怎么标 |
| --- | --- | --- | --- |
| 官方文档口径 | 官方手册页面 | 最高，但可能过时，或与实测冲突 | 「官方文档」 |
| 官方回复 | 作者 xhongc 在 issue 里答复 | 高，但**常在同一个帖里自相矛盾** | 「官方回复」 |
| 用户实测 | 其他用户在 issue 里的报告 | 仅供参考，可能是猜测 | 「用户实测」 |

> [!warning] 一条硬规则
> 官方回复 ≠ 官方文档。作者在 issue 里说「可以试试」，不是产品承诺；同一个帖里他可能先给一套排查清单、再换一套、最后又换一套（`#360` 就是典型）。看到「作者说」三个字，先问是哪一种。

### C.2 登录 / 鉴权进不去

#### 症状

后台登录页输入用户名密码后，右上角会弹两个 alert，标题为「查询失败！」，内容为「身份认证信息未提供」[^cC-f14]。这是全仓评论数最高的一类故障：`#81`（38 条评论，全仓第一）、`#360`（20 条）、`#351`（13 条）。

> [!warning] 最常见的误解：以为存在「默认密码」
> 很多人第一反应是问默认账号密码是多少。但 FAQ 14 条里**没有**这条问答；官方唯一与密码相关的页面是《忘记登录密码怎么办？》，讲的是**忘记之后怎么改**，不是初次登录该用什么[^cC-f1][^cC-f3]。所以别在官方文档里找默认密码——找不到是正常的，不是你没翻到。

#### 官方回复给的排查顺序

作者在 `#360` 里给过一份四条清单[^cC-f14]：

1. 查看日志里是否有进程**一直在重启**；
2. 检查 **redis** 配置与连接是否正常；
3. 检查**内存**分配是否足够；
4. （host 模式下）检查是否**端口冲突**。

而这四条之外，同一帖里他又先后追加过两种不同的口径：把 `/app/data` 里的数据库**删掉**再重启；以及**换浏览器 / 升级浏览器版本**。

> [!warning] 这个帖没有闭环
> 用户按「删库重启」操作后反馈「WebUI登录依旧是这错误」，之后再无结论。**所以「删数据库」不是官方定论**——它是作者的一次尝试性建议，代价却是你丢掉整个配置库（激活信息、数据库、封面索引都在里面）。

#### 社区反向个案：host 不一定更好

FAQ 第 4、8 条都建议改 host 网络模式来解决「激活无响应」「刮削不到信息」[^cC-f1]，官方《激活码激活失败、无响应》页也把无响应归因于「容器内网络不通导致无响应」，同样建议 host[^cC-f2]。但 `#360` 里有用户实测相反[^cC-f14]：

> 「我用host网络也是一样，默认账号密码无法登陆，换成bridge网络没问题」

作者只回了一句「可能有端口冲突」，**没有撤回 host 建议**。另外官方自己也承认 host 模式要占用 8001、8002、9001 三个端口[^cC-f2]。**结论：host 与 bridge 两向都值得试一次，不要认定只有 host 对。**

#### 本笔记建议的动作顺序

1. 先看 `docker logs` 有没有进程反复重启——这是最快的分诊；
2. 再确认 `/app/data` **已挂载**（「启动不起来」类故障里，未挂载 `/app/data` 是反复出现的真根因，见 C.12 的 `#198`）；
3. 再查 redis（容器内自带的那个是否起来了，见 C.6）；
4. 网络模式 host / bridge 各试一次；
5. **删数据库放到最后**，且动手前先备份 `/app/data`（理由见 C.14）。

```bash
# 分诊三连：看日志、看挂载、看端口
docker logs --tail 100 music-tag-web
docker inspect music-tag-web --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
docker ps -a --filter name=music-tag-web
```

第一行看有没有反复重启的堆栈；第二行确认 `/app/data`、`/app/media`、`/app/download` 三个卷都在；第三行确认容器没在不停 Restarting。

### C.3 忘记密码怎么办（这一条官方给得很明确）

与登录失败相反，**「忘记密码」是本附录里少数能直接照做的一条**。官方《忘记登录密码怎么办？》只给了三步，全部在容器内完成[^cC-f3]：

1. 进入项目的 Docker 容器内；
2. 在容器中打开终端，执行下面的命令；
3. 按提示输入并确认新密码。

```bash
python manage.py changepassword admin
```

官方特别注明：这里的 `admin` 指你要改的**用户账号名**，「如果您要为不同的用户更改密码，请将`admin`替换为目标用户的用户名」[^cC-f3]。

> [!warning] 三件官方没说的
> ① 官方**没有网页端「忘记密码」自助重置入口**，流程必须进容器执行命令；
> ② 这条只覆盖**管理员登录密码**，FAQ 第 6 条提到的 **Subsonic 密码**是另一个密码，两者关系官方未说明；
> ③ 进容器前先确认容器的实际名字（用上面的 `docker ps -a` 查），名字写错会报 「No such container」。

### C.4 升级之后：容器重启风暴与封面全丢

升级是本项目故障最集中的动作，两件事都发生在「拉新镜像、重建容器」之后。

#### `#377`：升级后容器反复重启、CPU 飙升（23 条评论）

作者的处理轨迹是三步[^cC-f14]：

> 「不是，先用 2.3.8 版本，我在看看」→「已经修复了，重新拉一下新版本吧」→「2.4.2 修复了」

也就是说，这是一次**跨版本的回归缺陷**，最终落在 2.4.2 修复。帖里还有多位用户报告同类复现，现象一致：「一样的问题，更新完就gg了，CPU占用率飙升而且打不开」。

> [!tip] 大白话
> 这不是你配置错了，是**那一版的镜像本身坏了**。遇到「升级完就打不开」，先去官方 issue 里搜同版本反馈，再考虑回退到上一个能用的 tag——而不是反复折腾自己的 compose 文件。

#### `#546`：升级后专辑与艺术家封面全部 404（23 条评论）

现象很具体：页面图片裂开，浏览器 F12 里 `/rest/getCoverArt/` 接口返回 **404 Not Found**，**而映射目录里图片文件明明还在**[^cC-f14]。

作者的排查链与最终答复（原文逐字）[^cC-f14]：

> 「检查是否删除 attaments 目录」→（用户逐项核对：目录在、图片在、8002 端口能播、后台封面地址可达、F12 显示接口 404）→「这个啊，算了，你重新导入收藏」

帖末用户追问「是所有的不是就这一个专辑」，**此后没有回复**。

> [!warning] 这一条要如实看
> ① 官方**没有定位根因**；
> ② 官方给的动作是「重新导入收藏」，属于**绕过**而非修复；
> ③ 该帖**未闭环**。
>
> 另外，官方《容器自动更新》页明确声明自动更新会「保留你的所有数据和配置」「这样更新后你的数据不会丢失」[^cC-f8]。**声明与这条实测之间存在缺口**——这不是说官方声明造假，而是提醒你：声明覆盖的是数据卷，不保证升级后封面索引一定还认得出。

#### 升级前检查清单（本笔记建议）

> [!tip] 动手前花五分钟
> 1. 备份 `/app/data` 整个目录（配置、数据库、封面索引都在里面）；
> 2. 记下当前镜像的版本 tag，便于回退；
> 3. 别用 `docker-compose down -v`——官方文档自己警告过 `-v` **会连同卷一起删除**[^cC-f4]；
> 4. 升完先看 `docker logs` 有没有重启风暴，再去看封面。

### C.5 Database is locked（数据库繁忙）

**这是官方给了明确答案的一个**，也是本附录里少数能直接照做的一条。FAQ 第 14 条原文[^cC-f1]：

> 「Sqlite 数据库并发读写**独占锁**机制，会锁定整个数据库，可以切换到 mysql 数据库有更好体验。」

> [!tip] 大白话
> Sqlite 像**只有一支笔的账本**：同一时刻只允许一个人写，第二个来写就得等，等不到就报 「database is locked」。什么时候会撞上？后台刮削正在写库，你同时在页面上手动改标签，两个写操作撞在一起。MySQL 则像**银行柜台**，多人各写各的，不会互相堵死。

切换方法见附录 B.1：官方《Mysql 部署》页给了可直接跑的 compose，且每个 `MYSQL_*` 变量都注明「（没有可以不填，默认使用 sqlite）」，说明它是**替换项**而非必需项[^cC-f9]。

> [!warning] 已经锁死了怎么办？官方没说
> 官方只给了「切 MySQL」这个长期方案，**没有给「现在就卡住了」的应急恢复步骤**。这类应急步骤在本笔记里属于未取到——不要自行想象一个「官方推荐做法」，也别照抄网上来路不明的删锁命令。

### C.6 Redis 连不上

先明确一件事：**外置 Redis 不是必需项**。官方原文[^cC-f10]：

> 「容器本身就会启动一个 redis，如果你不需要**外置**的 redis，可以不进行此项的配置。」

所以只有在你**主动接了外置 Redis**（或用了 MySQL 方案里带 redis 的 compose）之后，「Redis 连不上」才构成问题。

`#397`（15 条评论）是一条独立故障簇：用户说配置好 Redis 但始终连不上，后台日志一直报错，而**在容器里能 telnet 通**对应的 Redis 服务[^cC-f13]。**该帖评论区内容在收集时未取到**（GitHub API 速率限制），所以本笔记只到标题/正文层级，**不写解决结论**。

> [!warning] 一个已知的文档坑：REDIS_PORT 默认值自相矛盾
> 官方《自定义服务端口》页的变量表里，同一个单元格既写默认 **6379**，又写「v2.6.0 及以上版本默认 **6380**」；而《外置Redis服务》页正文写「其默认端口为 6379」[^cC-n8][^cC-f10]。**两处不一致，且没说哪个版本起改了。** 接外置 Redis 时以你自己 Redis 实例的实际端口为准，不要照抄任一处默认值。

排查方向（**本笔记建议，非官方口径**）：既然容器内能 telnet 通，问题多半不在网络层，而在配置有没有传对。逐项核对 `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` 三个变量，并确认外置 Redis 与容器在同一个 docker 网络里[^cC-f10]。

### C.7 文件名乱码（`#33`，28 条评论）

现象是文件名乱码导致无法打开、重命名报错。作者前期判定为文件名编码问题；最终**由用户自行解决**[^cC-f14]：

> 「windows文件名称编码默认是GB2312，linux默认是UTF-8，通过convmv即可进行修改。」

> [!tip] 大白话
> 同一串中文，Windows 存成 GB2312 的字节，Linux 按 UTF-8 去读，读出来就是乱码——**不是文件坏了，是两边的「字典」不一样**。`convmv` 就是那本翻译词典。

同一帖里作者还澄清过一类**操作方式误解**（不算缺陷）[^cC-f14]：

> 「勾选的时候是 批量操作 ，你要操作单个文件的话 点选名称就可以进去 编辑页面修改」

也就是说，「改了没生效」有时是你勾了一堆文件在批量改，而不是改的那一个。

### C.8 FLAC 元数据异常（`#263` + `#551`）

`#263`（13 条评论）报「加载文件失败, 请检查文件的元数据是否损坏」，`#551`（8 条评论）报浮点参数转换失败[^cC-f13]。两条构成 **FLAC 元数据兼容簇**。

**这两条的评论区内容在收集时未取到**，因此本笔记：

- 只提示此簇的**存在**与**症状**；
- **不写「官方怎么修」**，也不推断「升级到某版本即可」。

> [!tip] 一个能自己做的判断
> 报错文本本身就是「元数据是否损坏」——先排除文件侧问题（用别的工具能不能读出这张 FLAC 的标签），再怀疑程序兼容性。若只有个别文件如此、其他 FLAC 正常，那是文件的问题，不是部署的问题。

### C.9 Subsonic 接口覆盖不全（`#510`，18 条评论）

用户点名该项目**不支持** `getIndexes`、`getStarred`、`getLyricsBySongId` 三个 Subsonic API[^cC-f12]，导致部分第三方客户端的功能异常（如索引浏览打不开、歌词拉不到）。

**评论区内容未取到**，所以不能写「作者承诺补哪些接口」。可确认的只有一点：这是**功能覆盖范围**问题，不是你的配置问题——换客户端通常比等更新更快。

### C.10 刮削不准（`#40` / `#339` / `#415`）

表现为刮削匹配到别的专辑、指定专辑名仍匹配到别的作品、宽松模式匹配偏差[^cC-f13]。这三条**多为功能请求而非缺陷**（用户希望增加更精确的匹配手段），**评论区未取到**。

> [!tip] 能自己做的
> 刮削不准时，优先在**手动刮削**里逐张专辑确认再写入，而不是让后台批量刮完再回头修。手工确认的入口与能力见正文第四章。

### C.11 FAQ 精选（14 条里最该记住的）

官方 FAQ 共 14 条，正文各章已散引了一部分；这里把**排错向**的几条集中列一遍，按「卡在哪」排序[^cC-f1]。

#### 进不去 / 看不到东西

| 现象 | 官方回答要点 |
| --- | --- |
| 首页歌曲数是 0 | 在操作台勾选歌曲目录 → 「导入收藏」，等后台导入 |
| 音乐收藏一直 loading | **subsonic 密码**未设置或改过：重设一次、重新登录、再刷新收藏页 |
| `/admin` 报 403 | 框架安全机制限制反代地址，**用局域网地址可以进** |
| 输入激活码没反应 | 确认容器能访问外网与激活服务器，可改 host 网络模式 |

> [!warning] 关于「音乐收藏 loading」这条（FAQ 第 6 条）
> 网上有些转载把这条写成了别的内容。**第 6 条的真实问答是**：Q「为什么音乐收藏一直在 loading 中？」A「更改过或未设置subsonic 的密码需要设置一次，需要重新再登录一次，后再刷新音乐收藏页面。」[^cC-f1] 它的根因在 **Subsonic 密码**，与数据库、与封面都无关——恢复时别往错的方向查。

#### 刮削 / 任务不动

- 后台刮削不生效、删除不存在的音乐收藏不生效 → 「其他设置」→ **停止所有后台任务**，等它重新执行（第 7 条）；
- 搜索刮削提示「暂无歌曲信息」 → 确认容器可访问网络，可改 host（第 8 条）。

#### 激活类

- 激活失败 / 验证超时 → 把**容器内时间校正为北京时间**，误差不超过 1 分钟（第 13 条）；
- 提示「激活码已被激活」 → 重复激活**超过 6 次上限**，需联系开发者重置次数（《激活码激活失败》情况 3）[^cC-f2]；
- 重新部署会不会失效 → `/app/data` 没删就自动生效；删了要用激活码重新激活。另一个上限是**同一激活码换机器激活后，上一台会失效下线**（第 10 条）。

#### 数据库

- `Database is locked` → 见 C.5。

### C.13 官方文档自身的缺陷清单（别照抄）

> [!warning] 这些是官方文档的错，不是你的错
> 官方手册里有若干处笔误与自相矛盾。**照抄会踩坑**，所以逐条列出——本笔记**不「顺手改正」后当事实用**，只如实标注。

| 位置 | 缺陷 |
| --- | --- |
| 升级页示例 | 镜像名写成 `xhong/music_tag_web`，与快速开始页的 `xhongc/music_tag_web` 不一致——**照抄升级页命令会拉不到镜像**[^cC-f4] |
| 多目录挂载页 | 配置段写容器内路径 `/app/media/Pop`，同页「容器内访问」段却写 `/music/Pop`，两组互斥[^cC-f6] |
| MySQL 页 | 同一页也出现 `/app/media/Pop` 与 `/music/Pop` 两版路径；且同一个变量被注释成「数据库名称」与「数据表名称」两种语义[^cC-f9] |
| 自定义服务端口页 | `REDIS_PORT` 同一单元格里同时写默认 6379 与 6380（见 C.6）[^cC-n8] |
| 整理文件夹页 | 措辞笔误「会更加音乐的元数据」（应为「会根据」），且**分组键字段名未取到**[^cC-t4] |
| 绿联部署页 | 正文有错位，如「（例如 `<http://greenlink_ip:8002），即可访问Music> Tag Web的登录界面。`」——括号与链接标签错插，属抓取到的原样[^cC-n3] |
| 极空间部署页 | 页面自述是**转载第三方**，不可与官方自述步骤混引[^cC-n5] |

> [!tip] 用文档时的一条准则
> 官方文档**没有 changelog、没有环境变量总表、没有各 NAS 平台版本号**，很多「应该有的」信息它就是不提供。**遇到文档内部冲突，以能跑通的那一处为准**，而不是以「哪句写得更像官方」为准。

### C.14 备份建议（本笔记建议）

> [!warning] 先把口径说清楚
> **官方对备份并非全无口径**，但它**不落在操作页上**：
>
> - 《容器自动更新》页的「最佳实践」写着「**保持备份**：重要数据定期备份，避免意外情况」[^cC-f8]；
> - 《怎么更新/升级版本呢？》页写着「确保所有重要数据都已正确挂载到持久化存储上，**防止数据丢失**」[^cC-f4]。
>
> 但本次收集的 **11 个标签操作页面**里，确实**没有**任何「请先备份」的建议，也没有「操作不可逆」的告警。所以「动手前先备份」是**本笔记的建议**（有官方口径支撑，但不是官方在操作页上提出的要求）——不伪装成官方口径。

要备份什么、什么时候备份：

| 时机 | 备份对象 | 为什么 |
| --- | --- | --- |
| 任何写标签操作前 | **音乐文件本身** | 标签是写回元数据的，改的是原文件（写元数据与写数据库的区别参见正文第四章） |
| 升级 / 重建容器前 | `/app/data` 整个目录 | 配置、数据库、封面索引都在这里；`#546` 升级丢封面就发生在这 |
| 切数据库前 | `/app/data` | 从 sqlite 切 MySQL 失败时能回退 |
| 整理 / 切轨前 | 涉及的音乐目录 | 切割音轨时整轨原文件是否保留，官方未说明 |

> [!tip] 一句话总结本附录
> 出问题先问三件事：**这条说法是官方文档、官方回复、还是用户实测？** 是「用户实测」就当线索、别当结论；是「官方回复」就注意它可能前后矛盾；是「官方文档」也要防着 C.13 里那几处笔误。然后——**动手之前先备份**。
