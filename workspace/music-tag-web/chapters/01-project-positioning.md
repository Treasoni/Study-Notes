# 第一章 项目定位与能力边界

装软件之前先想清楚它替谁干活，能省掉后面返工。这一章回答四个问题：它解决什么，它说的「元数据」「刮削」是什么意思，V1 和 V2 该选哪个，以及它明确不做什么。

## 1.1 一句话定位：它替谁解决什么问题

官方给 V1 的定位是「可以编辑歌曲的标题，专辑，艺术家，歌词，封面等信息的应用程序」[D6](https://xiers-organization.gitbook.io/music-tag-web/xiang-mu-jie-shao.md)。痛点则在同页说破：

> 在使用 Navidrome 时，我存储音乐文件放在远程服务器上或 NAS 中，本地的 Musictag 和 mp3tag 并不能完全满足我的需求，我需要直接在 NAS 上去需改存储的音乐文件标签。

（原文引用，「去需改」为原文自带笔误。）

Musictag、mp3tag 这类桌面工具只能操作本机磁盘；音乐放 NAS 上就得拖回本地改完再传回去。Music Tag Web 让编辑器跑在服务器上，你在浏览器里操作，文件始终待在原地。

仓库 README 自述它是「Navidrome / Jellyfin 配套边车工具，替代本地 MP3Tag、MusicBrainz Picard」（项目自述，README 有 SEO 改写痕迹，仅作参考）。有媒体服务器它是补充，没有也不影响使用——V1 手册页面树里全是标签操作 [T17](https://xiers-organization.gitbook.io/music-tag-web/llms.txt)。

> [!tip] 大白话
> 「自托管」就像自家厨房：菜（音乐文件）在自己家，锅（软件）也架在自己家，没人经手你的菜。不像用别人家的外卖平台——那得先把菜送出去。

## 1.2 两个先要懂的词

官方对元数据的定义：

> 元数据通常是指我们在音乐流媒体平台看到的与歌曲息息相关的信息，包括歌曲名称、演唱者、作词、作曲、唱片公司、发行公司等等，一般内嵌于音乐文件中，与音乐共同存在。[D5](https://xiers-organization.gitbook.io/music-tag-web-v2/ming-ci-jie-shi.md)

README 里换了个叫法「ID3 标签」，指的是同一批信息。

> [!tip] 大白话
> 音乐文件像快递包裹：音频是箱里的货，元数据是箱外的面单——歌名、歌手、专辑、封面、歌词都写在这张单子上。播放器通常不拆箱子只读单子，所以面单写错，音箱、车机、手机会一起认错。

官方对刮削的定义：

> 刮削是音频播放软件及音乐管理软件的一项功能，它可以自动识别音乐文件，并在线获取相应的专辑封面、歌曲名称、艺术家、专辑信息、流派和发行日期等数据，使得管理和播放本地音乐文件变得更加便捷。[D5](https://xiers-organization.gitbook.io/music-tag-web-v2/ming-ci-jie-shi.md)

> [!tip] 大白话
> 刮削 = 给一箱没写面单的包裹补面单：先「认货」（识别这是什么歌），再上网查回资料，最后抄到文件上。它是「联网查资料 + 写回本地文件」，不是下载音乐（准确性另见 1.6）。

V2 名词解释把相关动作拆成三个近义词。下表**逐字**照录该页原文；三行原文均以「本项目中的功能，」起头，为省版面提到表前：

> V2 名词解释页三个词条的开头一律是：「本项目中的功能，」

| 术语 | 官方定义（V2 名词解释页，逐字） |
| --- | --- |
| 手动刮削 | 选择需要修改文件或文件目录，可自定义修改音乐元数据中的内容。 |
| 自动刮削 | 选择需要修改文件或文件目录，可自动从音乐流媒体平台搜索元数据实行刮削操作 |
| 后台刮削 | 固定的文件目录下，可自动从音乐流媒体平台搜索元数据、整理文件夹、重命名等一系列操作 |

差别在「谁选文件、谁查资料」：手动是自己填，自动是软件替你查，后台则是你只把新歌丢进一个目录，剩下它全包。用法见第四章。

## 1.3 支持的音频格式

V1 项目介绍首段列出的清单是 FLAC、APE、WAV、AIFF、WV、TTA、MP3、MP4、M4A、OGG、MPC、OPUS、WMA、DSF、DFF 等音频格式 [D6](https://xiers-organization.gitbook.io/music-tag-web/xiang-mu-jie-shao.md)；仓库 README 的清单顺序略有不同（MP4 排在最后），但集合一致，都是这 15 种。

这份清单说的是「能读写标签」；个别功能对格式另有要求（第五章举例）。

## 1.4 V1 与 V2：定位差别

README 把两套部署说明并排放在同一个文件里，端口却不一样，这是最容易踩的第一个坑。

| 维度 | V1（「音乐标签」Web 版） | V2（Music Tag Web V2） |
| --- | --- | --- |
| 官方定位 | 「可以编辑歌曲的标题，专辑，艺术家，歌词，封面等信息的应用程序」[D6](https://xiers-organization.gitbook.io/music-tag-web/xiang-mu-jie-shao.md) | 「集合音乐标签刮削和音乐播放一体的个人音乐库解决方案」[D1](https://xiers-organization.gitbook.io/music-tag-web-v2/xiang-mu-jie-shao.md) |
| 功能范围 | 标签刮削与编辑 | 官方称具有 V1 版本的所有功能，另有新增 [D1](https://xiers-organization.gitbook.io/music-tag-web-v2/xiang-mu-jie-shao.md) |
| 容器内端口 | 8001 | 8002，且不再需要 `command: /start` [T18](https://xiers-organization.gitbook.io/music-tag-web-v2/llms.txt) |
| 激活 | V1 手册页面树中无激活相关条目 [T17](https://xiers-organization.gitbook.io/music-tag-web/llms.txt) | 需激活码：爱发电赞助获取，或联系开发者微信 charlesnowed [D1](https://xiers-organization.gitbook.io/music-tag-web-v2/xiang-mu-jie-shao.md) |

端口配置放第二章；这里只记结论：两者是不同形态。

V2 新增功能里与后文相关的是「插件模块」与「元数据版本管理」两条，官方对后者的描述是「自动记录每次元数据修改历史，支持版本查看、差异对比与一键回退」[D1](https://xiers-organization.gitbook.io/music-tag-web-v2/xiang-mu-jie-shao.md)。另有一条非技术差别：V2 需要激活，激活信息落在 `/app/data`，属于第三章。

> [!warning] 官方称 V2 包含 V1 全部功能，但 V2 手册未为这三项提供独立页面，实际入口需在界面中确认
> V2 项目介绍页写明「V2 版本具有 V1 版本的所有功能」，但 V2 手册页面树中检索不到「切割音轨」「拆分文件名称」「简繁体转换」的独立页面。本笔记的推断是它们被并入了其他功能（仅为推断）。本笔记不把这三项当作 V2 已确认的独立功能；你在第五章看到对应小节时，请以界面里实际是否存在为准。

## 1.5 能力边界：它不做什么

README 免责声明里被加粗的那句，就是整个项目的边界声明：

> 本自托管项目仅编辑本地已有音乐文件元数据，不提供下载音乐本体！

两层意思：一是**只编辑已有的文件**——不帮你找歌、不下载音频，刮削拿回来的是封面、歌名、艺术家这类描述信息，不是音频本体；二是**不碰你不给它的东西**——README 自述「所有曲库文件本地存储不上传第三方」。

还有一件文档没写、但必须有预期的事：它改的是你的文件本身，第四章会讲清「写入元数据」与「写入数据库」两种模式的后果差异。**本笔记建议**动手前先备份 `/app/data` 与音乐文件本身。官方文档在升级页只写到「确保所有重要数据都已正确挂载到持久化存储上，防止数据丢失」[F4](https://xiers-organization.gitbook.io/music-tag-web-v2/jiao-cheng-wen-zhang/zen-me-geng-xin-sheng-ji-ban-ben-ne.md)，并未给出具体的备份步骤（升级相关细节见附录 B）。

平台支持上有一处口径要分辨：仓库 README 自述「适配群晖、威联通、Linux 小主机 Docker 部署」，但官方手册的部署页里**未见威联通专页**（V2 手册部署页只覆盖群晖、1Panel、绿联、飞牛云 fnOS、极空间）。所以官方**没有**给出威联通部署步骤，本笔记也不为它编内容——请以第二章的通用 Docker Compose 写法为准。

它还对外**开放 API**：官方举例 info 接口供 homepage 展示信息，lyrics 接口供音流 app 展示歌词，health 接口供 Docker 健康检查心跳检测 [D5](https://xiers-organization.gitbook.io/music-tag-web-v2/ming-ci-jie-shi.md)。

## 1.6 许可证与免责声明要点

以下要点均出自 README 原文：

- **许可证**：基于 GPL V3.0 发行，并附有补充协议，冲突时以补充协议为准。
- **禁止商业用途**：原文为「禁止任何形式的商业用途，包括但不仅限于售卖/打赏/获利」。
- **版权数据 24 小时规则**：过程中可能产生版权数据（图像、音频、名字、歌词等），使用者「务必在 24 小时内清除」——刮回来的封面、歌词正属此类。
- **准确性**：数据从各官方音乐平台的公开服务器拉取、筛选合并后展示，「本项目不对数据的准确性负责」。
- **合规**：禁止在违反当地法律法规的情况下使用本项目。

> [!warning] 三条不能忽略的红线
> 1. 不要商用——包括打赏、售卖、获利等任何形式。
> 2. 刮削产生的封面、歌词等版权数据，用完 24 小时内清除。
> 3. 别把它当成「数据一定正确」的工具——官方声明不对准确性负责。

## 1.7 标签源与插件的公开口径

官方手册的口径是**泛称、不点名**：名词解释页用「音乐流媒体平台」，功能页用「标签源」；V2 项目介绍里唯一的机制性说法是「插件模块：内置多种标签源插件，并支持用户上传自定义插件」[D1](https://xiers-organization.gitbook.io/music-tag-web-v2/xiang-mu-jie-shao.md)——仍未列出任何源名。本笔记核对过两套手册的页面树 [T17](https://xiers-organization.gitbook.io/music-tag-web/llms.txt) [T18](https://xiers-organization.gitbook.io/music-tag-web-v2/llms.txt)，其中确实不存在标签源名单。**具体支持哪些平台属于本次收集未取到的信息**，请勿接受任何二手名单。

有一条原文要单独说明：它不是功能清单，而是免责声明里的词语约定。README 定义「官方音乐平台」时这样写：

> 「官方音乐平台」指对本项目内置的包括酷我、网易云、QQ音乐、咪咕、酷狗音乐、酷我音乐等音乐源的官方平台统称

这只是免责声明为划清责任所做的举例式统称，**不能当作官方公布的刮削源清单**。要确认实际可用的源，只能以你部署后界面里的插件 / 标签源列表为准。

## 1.8 本章的已知信息缺口

最容易犯的错，是把文档没写的地方当成写过了。本章范围内有三处**空白**：

| 缺口 | 状态 |
| --- | --- |
| 当前最新版本号 | 未取到。官方文档没有给出「当前版本是几」 |
| 变更日志 / release notes | V2 手册页面树中不存在该页面 [T18](https://xiers-organization.gitbook.io/music-tag-web-v2/llms.txt) |
| 标签源 / 插件具体名单 | 未取到（见 1.7） |

> [!summary] 小结
> - 它是自托管的 Web 版音乐元数据编辑器：文件留在 NAS / 远程服务器上，你在浏览器里改。
> - 核心动作叫「刮削」——联网查资料再写回本地文件，**不下载音乐本体**。
> - V2 是超集定位（官方称包含 V1 全部功能），容器端口 8002 且无需 `command: /start`，且**必须激活**；V1 端口为 8001。
> - V2 手册未为「切割音轨」「拆分文件名称」「简繁体转换」提供独立页面，实际入口需在界面中确认。
> - 许可证为 GPL-3.0 加补充协议：禁止商用、版权数据 24 小时内清除、不对准确性负责。
