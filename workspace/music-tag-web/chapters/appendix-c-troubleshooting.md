# 附录 C 排错 FAQ 与已知文档缺陷（可跳读）

> [!note] 这篇什么时候看
> 正文五章讲的是「顺利用下去」，本附录讲「卡住了怎么办」。前半按故障簇排（登录 → 改密 → 升级 → 数据库 → Redis → 文件名 → FLAC → Subsonic → 刮削），后半是 FAQ 精选、**官方没写清的**、以及**官方文档自身的缺陷清单**。带「未取到」说明的条目只到标题/正文层级，**不要当成已确认的解法**。

排错时最容易犯的一个错，是把 issue 里的一句话当成官方结论。先花一分钟把下面这件事分清楚，后面会一直用到。

## C.1 先分清三种「说法」

这个项目的故障信息有三个来源，权威性完全不同：

| 说法 | 谁说的 | 可信度 | 本附录怎么标 |
| --- | --- | --- | --- |
| 官方文档口径 | 官方手册页面 | 最高，但可能过时，或与实测冲突 | 「官方文档」 |
| 官方回复 | 作者 xhongc 在 issue 里答复 | 高，但**常在同一个帖里自相矛盾** | 「官方回复」 |
| 用户实测 | 其他用户在 issue 里的报告 | 仅供参考，可能是猜测 | 「用户实测」 |

> [!warning] 一条硬规则
> 官方回复 ≠ 官方文档。作者在 issue 里说「可以试试」，不是产品承诺；同一个帖里他可能先给一套排查清单、再换一套、最后又换一套（`#360` 就是典型）。看到「作者说」三个字，先问是哪一种。

## C.2 登录 / 鉴权进不去

### 症状

后台登录页输入用户名密码后，右上角会弹两个 alert，标题为「查询失败！」，内容为「身份认证信息未提供」[^cC-f14]。这是全仓评论数最高的一类故障：`#81`（38 条评论，全仓第一）、`#360`（20 条）、`#351`（13 条）。

> [!warning] 最常见的误解：以为存在「默认密码」
> 很多人第一反应是问默认账号密码是多少。但 FAQ 14 条里**没有**这条问答；官方唯一与密码相关的页面是《忘记登录密码怎么办？》，讲的是**忘记之后怎么改**，不是初次登录该用什么[^cC-f1][^cC-f3]。所以别在官方文档里找默认密码——找不到是正常的，不是你没翻到。

### 官方回复给的排查顺序

作者在 `#360` 里给过一份四条清单[^cC-f14]：

1. 查看日志里是否有进程**一直在重启**；
2. 检查 **redis** 配置与连接是否正常；
3. 检查**内存**分配是否足够；
4. （host 模式下）检查是否**端口冲突**。

而这四条之外，同一帖里他又先后追加过两种不同的口径：把 `/app/data` 里的数据库**删掉**再重启；以及**换浏览器 / 升级浏览器版本**。

> [!warning] 这个帖没有闭环
> 用户按「删库重启」操作后反馈「WebUI登录依旧是这错误」，之后再无结论。**所以「删数据库」不是官方定论**——它是作者的一次尝试性建议，代价却是你丢掉整个配置库（激活信息、数据库、封面索引都在里面）。

### 社区反向个案：host 不一定更好

FAQ 第 4、8 条都建议改 host 网络模式来解决「激活无响应」「刮削不到信息」[^cC-f1]，官方《激活码激活失败、无响应》页也把无响应归因于「容器内网络不通导致无响应」，同样建议 host[^cC-f2]。但 `#360` 里有用户实测相反[^cC-f14]：

> 「我用host网络也是一样，默认账号密码无法登陆，换成bridge网络没问题」

作者只回了一句「可能有端口冲突」，**没有撤回 host 建议**。另外官方自己也承认 host 模式要占用 8001、8002、9001 三个端口[^cC-f2]。**结论：host 与 bridge 两向都值得试一次，不要认定只有 host 对。**

### 本笔记建议的动作顺序

1. 先看 `docker logs` 有没有进程反复重启——这是最快的分诊；
2. 再确认 `/app/data` **已挂载**（「启动不起来」类故障里，未挂载 `/app/data` 是反复出现的真根因，见 C.12 的 `#198`）；
3. 再查 redis（容器内自带的那个是否起来了，见 C.6）；
4. 网络模式 host / bridge 各试一次；
5. **删数据库放到最后**，且动手前先备份 `/app/data`（理由见 C.14）。

```bash
# 分诊三连：看日志、看挂载、看端口
docker logs --tail 100 music-tag-web
docker inspect music-tag-web --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
docker ps -a --filter name=music-tag-web
```

第一行看有没有反复重启的堆栈；第二行确认 `/app/data`、`/app/media`、`/app/download` 三个卷都在；第三行确认容器没在不停 Restarting。

## C.3 忘记密码怎么办（这一条官方给得很明确）

与登录失败相反，**「忘记密码」是本附录里少数能直接照做的一条**。官方《忘记登录密码怎么办？》只给了三步，全部在容器内完成[^cC-f3]：

1. 进入项目的 Docker 容器内；
2. 在容器中打开终端，执行下面的命令；
3. 按提示输入并确认新密码。

```bash
python manage.py changepassword admin
```

官方特别注明：这里的 `admin` 指你要改的**用户账号名**，「如果您要为不同的用户更改密码，请将`admin`替换为目标用户的用户名」[^cC-f3]。

> [!warning] 三件官方没说的
> ① 官方**没有网页端「忘记密码」自助重置入口**，流程必须进容器执行命令；
> ② 这条只覆盖**管理员登录密码**，FAQ 第 6 条提到的 **Subsonic 密码**是另一个密码，两者关系官方未说明；
> ③ 进容器前先确认容器的实际名字（用上面的 `docker ps -a` 查），名字写错会报 「No such container」。

## C.4 升级之后：容器重启风暴与封面全丢

升级是本项目故障最集中的动作，两件事都发生在「拉新镜像、重建容器」之后。

### `#377`：升级后容器反复重启、CPU 飙升（23 条评论）

作者的处理轨迹是三步[^cC-f14]：

> 「不是，先用 2.3.8 版本，我在看看」→「已经修复了，重新拉一下新版本吧」→「2.4.2 修复了」

也就是说，这是一次**跨版本的回归缺陷**，最终落在 2.4.2 修复。帖里还有多位用户报告同类复现，现象一致：「一样的问题，更新完就gg了，CPU占用率飙升而且打不开」。

> [!tip] 大白话
> 这不是你配置错了，是**那一版的镜像本身坏了**。遇到「升级完就打不开」，先去官方 issue 里搜同版本反馈，再考虑回退到上一个能用的 tag——而不是反复折腾自己的 compose 文件。

### `#546`：升级后专辑与艺术家封面全部 404（23 条评论）

现象很具体：页面图片裂开，浏览器 F12 里 `/rest/getCoverArt/` 接口返回 **404 Not Found**，**而映射目录里图片文件明明还在**[^cC-f14]。

作者的排查链与最终答复（原文逐字）[^cC-f14]：

> 「检查是否删除 attaments 目录」→（用户逐项核对：目录在、图片在、8002 端口能播、后台封面地址可达、F12 显示接口 404）→「这个啊，算了，你重新导入收藏」

帖末用户追问「是所有的不是就这一个专辑」，**此后没有回复**。

> [!warning] 这一条要如实看
> ① 官方**没有定位根因**；
> ② 官方给的动作是「重新导入收藏」，属于**绕过**而非修复；
> ③ 该帖**未闭环**。
>
> 另外，官方《容器自动更新》页明确声明自动更新会「保留你的所有数据和配置」「这样更新后你的数据不会丢失」[^cC-f8]。**声明与这条实测之间存在缺口**——这不是说官方声明造假，而是提醒你：声明覆盖的是数据卷，不保证升级后封面索引一定还认得出。

### 升级前检查清单（本笔记建议）

> [!tip] 动手前花五分钟
> 1. 备份 `/app/data` 整个目录（配置、数据库、封面索引都在里面）；
> 2. 记下当前镜像的版本 tag，便于回退；
> 3. 别用 `docker-compose down -v`——官方文档自己警告过 `-v` **会连同卷一起删除**[^cC-f4]；
> 4. 升完先看 `docker logs` 有没有重启风暴，再去看封面。

## C.5 Database is locked（数据库繁忙）

**这是官方给了明确答案的一个**，也是本附录里少数能直接照做的一条。FAQ 第 14 条原文[^cC-f1]：

> 「Sqlite 数据库并发读写**独占锁**机制，会锁定整个数据库，可以切换到 mysql 数据库有更好体验。」

> [!tip] 大白话
> Sqlite 像**只有一支笔的账本**：同一时刻只允许一个人写，第二个来写就得等，等不到就报 「database is locked」。什么时候会撞上？后台刮削正在写库，你同时在页面上手动改标签，两个写操作撞在一起。MySQL 则像**银行柜台**，多人各写各的，不会互相堵死。

切换方法见附录 B.1：官方《Mysql 部署》页给了可直接跑的 compose，且每个 `MYSQL_*` 变量都注明「（没有可以不填，默认使用 sqlite）」，说明它是**替换项**而非必需项[^cC-f9]。

> [!warning] 已经锁死了怎么办？官方没说
> 官方只给了「切 MySQL」这个长期方案，**没有给「现在就卡住了」的应急恢复步骤**。这类应急步骤在本笔记里属于未取到——不要自行想象一个「官方推荐做法」，也别照抄网上来路不明的删锁命令。

## C.6 Redis 连不上

先明确一件事：**外置 Redis 不是必需项**。官方原文[^cC-f10]：

> 「容器本身就会启动一个 redis，如果你不需要**外置**的 redis，可以不进行此项的配置。」

所以只有在你**主动接了外置 Redis**（或用了 MySQL 方案里带 redis 的 compose）之后，「Redis 连不上」才构成问题。

`#397`（15 条评论）是一条独立故障簇：用户说配置好 Redis 但始终连不上，后台日志一直报错，而**在容器里能 telnet 通**对应的 Redis 服务[^cC-f13]。**该帖评论区内容在收集时未取到**（GitHub API 速率限制），所以本笔记只到标题/正文层级，**不写解决结论**。

> [!warning] 一个已知的文档坑：REDIS_PORT 默认值自相矛盾
> 官方《自定义服务端口》页的变量表里，同一个单元格既写默认 **6379**，又写「v2.6.0 及以上版本默认 **6380**」；而《外置Redis服务》页正文写「其默认端口为 6379」[^cC-n8][^cC-f10]。**两处不一致，且没说哪个版本起改了。** 接外置 Redis 时以你自己 Redis 实例的实际端口为准，不要照抄任一处默认值。

排查方向（**本笔记建议，非官方口径**）：既然容器内能 telnet 通，问题多半不在网络层，而在配置有没有传对。逐项核对 `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` 三个变量，并确认外置 Redis 与容器在同一个 docker 网络里[^cC-f10]。

## C.7 文件名乱码（`#33`，28 条评论）

现象是文件名乱码导致无法打开、重命名报错。作者前期判定为文件名编码问题；最终**由用户自行解决**[^cC-f14]：

> 「windows文件名称编码默认是GB2312，linux默认是UTF-8，通过convmv即可进行修改。」

> [!tip] 大白话
> 同一串中文，Windows 存成 GB2312 的字节，Linux 按 UTF-8 去读，读出来就是乱码——**不是文件坏了，是两边的「字典」不一样**。`convmv` 就是那本翻译词典。

同一帖里作者还澄清过一类**操作方式误解**（不算缺陷）[^cC-f14]：

> 「勾选的时候是 批量操作 ，你要操作单个文件的话 点选名称就可以进去 编辑页面修改」

也就是说，「改了没生效」有时是你勾了一堆文件在批量改，而不是改的那一个。

## C.8 FLAC 元数据异常（`#263` + `#551`）

`#263`（13 条评论）报「加载文件失败, 请检查文件的元数据是否损坏」，`#551`（8 条评论）报浮点参数转换失败[^cC-f13]。两条构成 **FLAC 元数据兼容簇**。

**这两条的评论区内容在收集时未取到**，因此本笔记：

- 只提示此簇的**存在**与**症状**；
- **不写「官方怎么修」**，也不推断「升级到某版本即可」。

> [!tip] 一个能自己做的判断
> 报错文本本身就是「元数据是否损坏」——先排除文件侧问题（用别的工具能不能读出这张 FLAC 的标签），再怀疑程序兼容性。若只有个别文件如此、其他 FLAC 正常，那是文件的问题，不是部署的问题。

## C.9 Subsonic 接口覆盖不全（`#510`，18 条评论）

用户点名该项目**不支持** `getIndexes`、`getStarred`、`getLyricsBySongId` 三个 Subsonic API[^cC-f12]，导致部分第三方客户端的功能异常（如索引浏览打不开、歌词拉不到）。

**评论区内容未取到**，所以不能写「作者承诺补哪些接口」。可确认的只有一点：这是**功能覆盖范围**问题，不是你的配置问题——换客户端通常比等更新更快。

## C.10 刮削不准（`#40` / `#339` / `#415`）

表现为刮削匹配到别的专辑、指定专辑名仍匹配到别的作品、宽松模式匹配偏差[^cC-f13]。这三条**多为功能请求而非缺陷**（用户希望增加更精确的匹配手段），**评论区未取到**。

> [!tip] 能自己做的
> 刮削不准时，优先在**手动刮削**里逐张专辑确认再写入，而不是让后台批量刮完再回头修。手工确认的入口与能力见正文第四章。

## C.11 FAQ 精选（14 条里最该记住的）

官方 FAQ 共 14 条，正文各章已散引了一部分；这里把**排错向**的几条集中列一遍，按「卡在哪」排序[^cC-f1]。

### 进不去 / 看不到东西

| 现象 | 官方回答要点 |
| --- | --- |
| 首页歌曲数是 0 | 在操作台勾选歌曲目录 → 「导入收藏」，等后台导入 |
| 音乐收藏一直 loading | **subsonic 密码**未设置或改过：重设一次、重新登录、再刷新收藏页 |
| `/admin` 报 403 | 框架安全机制限制反代地址，**用局域网地址可以进** |
| 输入激活码没反应 | 确认容器能访问外网与激活服务器，可改 host 网络模式 |

> [!warning] 关于「音乐收藏 loading」这条（FAQ 第 6 条）
> 网上有些转载把这条写成了别的内容。**第 6 条的真实问答是**：Q「为什么音乐收藏一直在 loading 中？」A「更改过或未设置subsonic 的密码需要设置一次，需要重新再登录一次，后再刷新音乐收藏页面。」[^cC-f1] 它的根因在 **Subsonic 密码**，与数据库、与封面都无关——恢复时别往错的方向查。

### 刮削 / 任务不动

- 后台刮削不生效、删除不存在的音乐收藏不生效 → 「其他设置」→ **停止所有后台任务**，等它重新执行（第 7 条）；
- 搜索刮削提示「暂无歌曲信息」 → 确认容器可访问网络，可改 host（第 8 条）。

### 激活类

- 激活失败 / 验证超时 → 把**容器内时间校正为北京时间**，误差不超过 1 分钟（第 13 条）；
- 提示「激活码已被激活」 → 重复激活**超过 6 次上限**，需联系开发者重置次数（《激活码激活失败》情况 3）[^cC-f2]；
- 重新部署会不会失效 → `/app/data` 没删就自动生效；删了要用激活码重新激活。另一个上限是**同一激活码换机器激活后，上一台会失效下线**（第 10 条）。

### 数据库

- `Database is locked` → 见 C.5。

## C.12 官方没说、issue 也没结论的事

下面这些是**真空区**，本笔记不替你编答案：

- **没有官方 changelog。** GitBook 站点树里根本没有版本变更记录页，所以哪个版本修了哪个 bug 无法官方核对——`#377` 那句「2.4.2 修复了」只存在于 issue 回复里[^cC-f14]。
- **`#198` 的真实教训（官方回复是错的）：** 作者原话是「更多的内存试试，v2 要占用 600 多」，但真根因是**用户自己发现 `/app/data` 没挂载**——「挂载上app/data 之后可以正常启动了」[^cC-f14]。**「内存不够」这条官方回复是错的。** 部署后起不来，先检查卷挂载，再考虑加内存。
- **`#397` / `#24` / `#637` 评论区未取到**（API 速率限制），只到标题/正文层级，无解决状态。
- **`#479` / `#510` / `#559` / `#257` / `#145` / `#263` / `#551` / `#40` / `#339` / `#415` / `#34` / `#30` / `#631` 的评论区未取到**，无法区分官方回复与用户猜测，故不写结论。
- **已锁死状态下的应急恢复步骤**：未取到。
- **激活码价格 / 发电档位、重置 6 次上限的成本与耗时、激活码的绑定粒度**：三处官方页面均无金额，也未说明绑定硬件、IP 还是仅绑定最后一次激活记录。

## C.13 官方文档自身的缺陷清单（别照抄）

> [!warning] 这些是官方文档的错，不是你的错
> 官方手册里有若干处笔误与自相矛盾。**照抄会踩坑**，所以逐条列出——本笔记**不「顺手改正」后当事实用**，只如实标注。

| 位置 | 缺陷 |
| --- | --- |
| 升级页示例 | 镜像名写成 `xhong/music_tag_web`，与快速开始页的 `xhongc/music_tag_web` 不一致——**照抄升级页命令会拉不到镜像**[^cC-f4] |
| 多目录挂载页 | 配置段写容器内路径 `/app/media/Pop`，同页「容器内访问」段却写 `/music/Pop`，两组互斥[^cC-f6] |
| MySQL 页 | 同一页也出现 `/app/media/Pop` 与 `/music/Pop` 两版路径；且同一个变量被注释成「数据库名称」与「数据表名称」两种语义[^cC-f9] |
| 自定义服务端口页 | `REDIS_PORT` 同一单元格里同时写默认 6379 与 6380（见 C.6）[^cC-n8] |
| 整理文件夹页 | 措辞笔误「会更加音乐的元数据」（应为「会根据」），且**分组键字段名未取到**[^cC-t4] |
| 绿联部署页 | 正文有错位，如「（例如 `<http://greenlink_ip:8002），即可访问Music> Tag Web的登录界面。`」——括号与链接标签错插，属抓取到的原样[^cC-n3] |
| 极空间部署页 | 页面自述是**转载第三方**，不可与官方自述步骤混引[^cC-n5] |

> [!tip] 用文档时的一条准则
> 官方文档**没有 changelog、没有环境变量总表、没有各 NAS 平台版本号**，很多「应该有的」信息它就是不提供。**遇到文档内部冲突，以能跑通的那一处为准**，而不是以「哪句写得更像官方」为准。

## C.14 备份建议（本笔记建议）

> [!warning] 先把口径说清楚
> **官方对备份并非全无口径**，但它**不落在操作页上**：
>
> - 《容器自动更新》页的「最佳实践」写着「**保持备份**：重要数据定期备份，避免意外情况」[^cC-f8]；
> - 《怎么更新/升级版本呢？》页写着「确保所有重要数据都已正确挂载到持久化存储上，**防止数据丢失**」[^cC-f4]。
>
> 但本次收集的 **11 个标签操作页面**里，确实**没有**任何「请先备份」的建议，也没有「操作不可逆」的告警。所以「动手前先备份」是**本笔记的建议**（有官方口径支撑，但不是官方在操作页上提出的要求）——不伪装成官方口径。

要备份什么、什么时候备份：

| 时机 | 备份对象 | 为什么 |
| --- | --- | --- |
| 任何写标签操作前 | **音乐文件本身** | 标签是写回元数据的，改的是原文件（写元数据与写数据库的区别参见正文第四章） |
| 升级 / 重建容器前 | `/app/data` 整个目录 | 配置、数据库、封面索引都在这里；`#546` 升级丢封面就发生在这 |
| 切数据库前 | `/app/data` | 从 sqlite 切 MySQL 失败时能回退 |
| 整理 / 切轨前 | 涉及的音乐目录 | 切割音轨时整轨原文件是否保留，官方未说明 |

> [!tip] 一句话总结本附录
> 出问题先问三件事：**这条说法是官方文档、官方回复、还是用户实测？** 是「用户实测」就当线索、别当结论；是「官方回复」就注意它可能前后矛盾；是「官方文档」也要防着 C.13 里那几处笔误。然后——**动手之前先备份**。
