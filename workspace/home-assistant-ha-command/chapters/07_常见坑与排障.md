# 第七章：常见坑与排障

这一章是全书最"救命"的一章。`ha` 命令本身不复杂，但使用者踩的坑高度集中在 11 条上。我把它们逐个拆开，每条给出报错现场、原因、解决路径。遇到问题时按图索骥即可，平时也可以当 checklist 扫一遍。

## 坑 1：`ha: command not found`

这是出现频率最高的坑，原因也很简单：**当前环境里根本没有 `ha` 命令**。

| 场景 | 解决办法 |
|------|---------|
| 用的是 Docker Container / Core 直装 | 没有 Supervisor，就没有 `ha`；改用 Supervisor REST API 或 `hassio.*` 服务 |
| 用的是 HA Supervised | 宿主 shell 里没有，进 CLI 容器：`docker exec -it hassio_cli bash` |
| HAOS 系统控制台在 `HA>` 提示符 | 先输入 `login` 进入 root shell 再敲 `ha` |

应急命令：

```bash
# HA Supervised 宿主上进入 CLI 容器
docker exec -it hassio_cli bash
```

## 坑 2：`Another job is running for job group home_assistant_core`

执行 `ha core` 相关命令时被拒绝，因为有一个任务卡住、占用了 `home_assistant_core` 这个任务组。

处理路径：

```bash
# 1. 看卡住的任务
ha jobs info

# 2. 重置任务队列
ha jobs reset

# 3. 还不行就安全模式重启
ha core stop
ha core restart --safe-mode
```

排查方向：某些集成（如 Entso-e）长时间占用任务会导致这个问题；实在解不开，最后手段是重启宿主机（`ha host reboot`）。

## 坑 3：`ha core options --duplicate-log-file=true` 后日志没出现

开了 duplicate-log-file 但日志文件就是不出来。原因：**只改了选项，没重建容器**。这个选项需要重建镜像才生效。

正确三步：

```bash
ha core options --duplicate-log-file=true
ha core rebuild
ha core restart
```

## 坑 4：`ha addons update` 无更新时退出码 1

脚本里跑 `ha addons update <slug>`，明明没报错，退出码却是 1，脚本判失败。原因：**addon 已是最新版时，update 返回退出码 1 表示"无更新可升"**，这是正常行为不是错误。

解决：脚本里忽略退出码 1，只把其他退出码当失败：

```bash
ha addons update core_ssh
if [ $? -eq 1 ]; then
  echo "已经是新版，无需升级"
fi
```

## 坑 5：restore 报 `only a partial backup`

恢复备份时报 `only a partial backup`。原因：这是一个 partial（部分）备份，**restore 必须显式指定要恢复的内容**。

解决：

```bash
# partial 备份恢复必须指定内容
ha backups restore <slug> --folders homeassistant --app core_mosquitto
```

要避免这个问题，日常全量备份请用自动化 `hassio.backup_full`（第五章讲过），而不是命令行 `ha backups new`。

## 坑 6：restore 输登录密码被拒

恢复加密备份时 `--password` 一直报错。原因：**`--password` 是备份加密密钥**（Web UI 里配置的那个），不是用户登录密码。

解决：去 Settings > System > Backups 里找加密密钥，或者 emergency kit 里的密钥。换过密钥的旧备份要拿旧密钥解密。

## 坑 7：`ha jobs info` 输出巨大、内存高

`ha jobs info` 一次输出巨量数据，甚至内存暴涨。原因：**已知 bug**，备份子任务未被清理，导致 `done: null` 的任务越积越多。

解决：

```bash
ha jobs reset
# 或重启 Supervisor
ha supervisor restart
```

## 坑 8：改静态 IP 不生效

`ha network update` 改了 IP，`ha network info` 一看还是老样子。常见原因：没重载网络配置、或网关配置在了多个接口上。

解决：

```bash
# 1. 重载网络配置
ha network reload

# 2. 确认网关只设在一个主接口
ha network info
```

多网卡设备尤其注意：网关不要重复配置在多个接口上。

## 坑 9：按旧文档敲 `ha host update` 报错

`ha host update` 在旧文档里出现过，但**新版源码已移除该子命令**。

解决：以 `ha <组> --help` 为准；OS 升级统一走 `ha os update`：

```bash
ha os update
```

通用技巧：任何命令不确定时，`ha <组> --help` 列出当前版本真实存在的子命令，永远以它为准。

## 坑 10：`ha os datadisk wipe` 后数据仍在

执行抹除后数据还在，怀疑没删干净。原因：多半是**坏盘**（抹除写不进），需要更换存储介质；部分硬件需要按实体按钮配合（Yellow+CM4 是红钮，Green 是黑钮），否则抹除流程不会真正完成。

处理：更换存储介质，按硬件手册操作实体按钮后再执行 wipe。

## 坑 11：shell_command 自动化调不到 `ha`

在 `shell_command` 里写 `ha core restart`，执行报 command not found。原因：**`shell_command` 集成运行在 Core 容器内**，那里没有 `ha` 命令。

解决：改用 `hassio.*` 服务（如 `hassio.host_reboot`、`hassio.backup_full`）或直接调 Supervisor REST API，不要指望 shell_command 里能敲 `ha`。

## 排障判断路径

遇到 `ha` 相关报错，按这条路径判断，能少走一半弯路：

```bash
# 1. 先确认是"环境问题"还是"命令问题"
#    command not found → 看坑 1（环境/入口）
#    命令报错 → 继续下面

# 2. 先校验配置（很多重启类问题源于配置错误）
ha core check

# 3. 看是不是任务卡住
ha jobs info

# 4. 看 Supervisor 健康检查
ha resolution info

# 5. 看日志定位
ha core logs -f | grep -i error
ha supervisor logs -f | grep -i error

# 6. 确认环境无虞后，才考虑安全模式重启
ha core restart --safe-mode
```

原则：**先 `ha core check` 排除配置问题，再动重启**。改配置必 check，重启是最后手段。

## 本章小结

- 11 条坑高度集中在四类：环境不对（坑 1/11）、任务卡住（坑 2/7）、备份恢复误操作（坑 5/6）、命令文档过时（坑 9）。
- `command not found` 先判断部署方式；Supervised 用 `docker exec -it hassio_cli bash`。
- 备份 `--password` 是加密密钥不是登录密码；partial 恢复必须指定 `--folders/--app`。
- 配置改动生效要走 `options → rebuild → restart` 三步。
- 排障路径：`core check` → `jobs info` → `resolution info` → 看日志 → 安全模式重启。
