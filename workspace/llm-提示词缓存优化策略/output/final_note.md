# LLM 提示词缓存优化策略

## 核心思路

缓存不是"少传 token"就会命中，而是让高频请求拥有尽可能长、尽可能稳定的前缀。减少总输入量只是 Token 优化的目标，缓存优化追求的是**重复输入的前缀一致性**——即使总 token 不多，每次动态拼接不同内容也会让缓存收益很低。

---

## 1. 区分两类成本

| 维度 | Token 优化 | 缓存优化 |
|------|-----------|---------|
| 目标 | 减少总输入输出量 | 复用已处理的上下文 |
| 手段 | 精简提示词、缩短输出 | 保持重复输入前缀一致 |
| 关系 | 两者最好同时做 | 但"少"不等于"稳定" |

> 缓存优化的本质不是做减法，而是做**结构化**——把变化的部分隔离到末尾，让不变的部分形成稳定的前缀。

---

## 2. 找出高频且变化小的内容

以下内容应进入稳定前缀：

- **系统规则**：项目级约束、安全策略、行为指南
- **角色说明**：Agent 身份、职责边界、行为模式
- **输出格式**：JSON Schema、Markdown 模板、代码格式化要求
- **固定工作流**：阶段定义、检查项、状态流转规则
- **工具使用约束**：可用工具列表、调用限制、参数规范
- **示例**：少量固定范例，不应频繁更换

---

## 3. 固定提示词结构

始终按同一顺序组织提示词：

```
[固定系统/项目规则]
[固定角色职责]
[固定输出格式与限制]
[固定示例或少量范例]

[动态参数]
- 用户请求
- 当前文件路径或局部片段
- 时间、ID、进度、git 状态
```

**关键规则**：动态内容一定放后面。不要在请求开头插入时间戳、随机 ID、实时状态、完整待办列表。前缀的任何"抖动"都会导致缓存 miss。

---

## 4. 将"大而少用"的内容延迟加载

把完整案例、参考资料、长篇规则拆成**入口文件**和**按需引用文件**。每次只加载当前任务需要的章节、锚点或检索结果，而不是把整个仓库、所有技能说明都塞进上下文。

```markdown
# ❌ 错误做法
加载所有模板 → 所有规则 → 所有历史 → 再执行任务

# ✅ 正确做法
加载当前任务模板 → 按需引用规则文件 → 只读相关片段
```

---

## 5. 子代理使用固定模板

子代理最容易因为每次 prompt 改写而失去缓存。固定职责、边界、输出格式，最后再注入参数：

```markdown
你是资料收集助手。
只返回结构化摘要。
每条包含：标题、链接、摘要、可信度。
禁止返回网页正文和无关导航。

参数：
- 主题: {topic}
- 关键词: {keywords}
- 信源限制: {sources}
```

模板本身形成稳定的前缀缓存，只有末尾的参数部分变化。

---

## 6. 减少无意义的上下文波动

- 不要默认读取镜像目录、构建产物、重复配置
- 避免每轮自动生成状态文件、自动提交
- 避免把变化后的 git diff 自动注入提示词
- 状态应写在文件中，只有任务需要时才读取

**原则**：每一次上下文变化都应有明确的目的，变化的内容应尽可能集中在末尾。

---

## 7. 建立可观测性

为请求记录以下指标：

| 指标 | 用途 |
|------|------|
| 输入 token | 基础用量 |
| 缓存读取 token | 复用了多少缓存 |
| 缓存写入 token | 新创建了多少缓存 |
| 缓存命中率 | 提示词稳定性的直接反映 |
| 请求类型 | 区分不同模板的缓存表现 |

按"命中率低且调用频繁"的提示模板优先治理。缓存规则通常依赖：

- 相同模型
- 相同工具定义
- 足够一致的前缀

具体阈值以所用平台为准。

---

## 8. 一句话总结

> 把规则和模板做成稳定的"壳"，把用户输入、文件片段和实时状态做成末尾可替换的"参数"。这样既减少上下文，也更容易获得实际的缓存命中。

---

- [ ] 子代理 prompt 模板是否固定，仅参数部分变化？
- [ ] 大块参考资料是否做了延迟加载设计？
- [ ] 是否有监控缓存命中率的可观测性方案？
