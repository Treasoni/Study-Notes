# DeepSeek-Reasonix 沙箱与安全

> [!info] 文档定位
> 本文是 DeepSeek-Reasonix 的安全章（04-高级功能篇第 14 章）：讲清沙箱的层级模型（配置层 → OS 层 → 凭据层）、各平台的实现机制、凭据保护模型、白名单与配置示例，以及常见的安全坑。面向已掌握 Reasonix 配置、准备在真实环境（或无人值守场景）运行的用户。命令字段与行为均取自官方 `reasonix.example.toml`、`docs/GUIDE.zh-CN.md` 与 CLI 参考；实时权威始终是应用内 `/help`。关联：[[reasonix.toml 配置详解]]、[[DeepSeek-Reasonix 权限模式指南]]、[[DeepSeek-Reasonix 自动化与 CI]]。

本文回答的核心问题：**把 Reasonix 放开手脚干活时，它会不会「越界」？** 我们从「沙箱分几层」讲到「凭据怎么保护」再到「白名单怎么配」，给你一套能落地到生产的隔离心智模型。

## 一、安全心智模型：沙箱是三层，不是一层

Reasonix 的隔离设计分**三个层级**，各防各的，别只盯着一层看：

| 层级 | 机制 | 防什么 |
|------|------|--------|
| **配置层** | `[permissions]` 白名单/黑名单（allow/deny/ask）+ 只读工具目录白名单 | 决定「哪些命令/工具**允许被考虑**执行」 |
| **OS 层** | 系统级沙箱（macOS Seatbelt / Linux bubblewrap / Firecracker 微虚拟机） | 决定「即使执行了，能不能碰工作区外的文件/网络」 |
| **凭据层** | 凭据保护模型（只读/受管/严格三类） | 决定「agent 手里的密钥，能读几个、能被谁读」 |

一句话：**配置层管「能不能做」，OS 层管「做了会不会出圈」，凭据层管「密钥在谁手里」**。三层层层递进，任何一层失守都不至于全盘暴露。

> [!tip] 大白话
> 把三层想成「实验室安全」：**准入制度**（配置层）规定哪些试剂能领、领多少；**物理隔离**（OS 层）把高危实验放在负压房，爆炸也炸不到走廊；**保险柜**（凭据层）把钥匙分成三把，只有三个人各拿一把才能开。少任何一层，出事就不是「小事故」而是「大事故」。

## 二、配置层：`[permissions]` 白名单/黑名单

第一道闸是**配置层的权限规则**，决定哪些命令/工具「允许被考虑」。核心结构与 Claude Code 的 permission rules 对齐：

```toml
[permissions]
allow = [        # 白名单：允许执行
  "Bash(npm run build)",
  "Write(src/**)",
]
deny = [         # 黑名单：禁止执行（优先于 allow）
  "Bash(git push)",
]
ask = [          # 需要审批
  "Write(.env*)",
]
additionalDirectories = [   # 只读工具（Read/Glob/Grep）可访问的工作区外目录
  "../shared",
]
```

要点：

- `allow` / `deny` / `ask` 是规则列表，deny **优先于** allow——这条和 Claude Code 一致，别配了 `allow` 就以为能绕过 `deny`。
- `additionalDirectories`：只读工具默认只能读工作区，要读工作区外的共享目录必须在这里白名单化。
- 规则支持 Bash / Edit / Write / Read 等工具类型，可用 `工具名(模式)` 的写法做精细控制。

> [!warning] deny 永远赢
> 规则优先级是 **deny > allow**。即使某条命令在 `allow` 里，只要命中 `deny` 就绝不执行。安全审计时先看 deny 列表，再看 allow——别把 allow 当免死金牌。

## 三、OS 层：系统级沙箱与平台实现

第二道闸是**OS 级沙箱**。`[sandbox]` 配置里用 `bash` 字段控制系统级 Bash 沙箱：

```toml
[sandbox]
bash = "enforce"    # 可选：off / enforce（默认 off）
```

各平台的实现机制不同，隔离强度也不同：

| 平台 | 实现 | 特点 |
|------|------|------|
| macOS | **Seatbelt** | 系统级强制访问控制，限制文件/网络访问 |
| Linux | **bubblewrap** | 轻量用户命名空间沙箱 |
| Linux（可选） | **Firecracker** | 微虚拟机，最强隔离（可选开启） |
| Windows | **无 OS 级 Bash 沙箱** | `bash = "enforce"` 在 Windows 上解析为 **off** |

- `bash = "enforce"` 开启系统级 Bash 沙箱；macOS/Linux 有实现，**Windows 不提供 OS 级 Bash 沙箱**，enforce 会被降级为 off。
- 微虚拟机（Firecracker）是更强隔离的可选项；是否可配置以官方 GUIDE.zh-CN.md 为准。

> [!tip] 大白话
> 把沙箱想成「每个临时工一个独立工位」：macOS 的 Seatbelt 是工位隔板、Linux 的 bubblewrap 是活动隔间、Firecracker 是把人关进独立办公室（隔离最强）。Windows 上暂时没隔板——所以 Windows 用户要隔离，就得整间房（容器）来关。

## 四、凭据层：凭据保护模型（Credential Protection）

第三道闸，也是最能体现 Reasonix 安全设计的地方：**凭据保护模型**。它解决的是「agent 手里的密钥，能不能被外部工具偷走」的问题。

Reasonix 提供三类凭据保护模式（来自官方 GUIDE.zh-CN.md）：

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| **只读（read-only）** | 凭据可被模型与工具读取 | 常规开发，信任 agent |
| **受管（managed）** | 工具不可直接读取凭据内容，只能「引用」 | 更严格，防止凭据被工具外泄 |
| **严格（strict）** | 凭据不可用、不可访问 | 最高等级，禁止任何凭据访问 |

> [!note] 凭据保护与 ACP 的关系
> 需要更严格的隔离时，Reasonix 支持在 ACP 会话里声明「最小权限凭据」与「扩展工作区根」——凭据按需最小化，工作区根按需扩展。编辑器/IDE 集成方接入时的凭据边界，见[[DeepSeek-Reasonix ACP 协议指南]]。

> [!tip] 大白话
> 把三类凭据模式想成「钥匙保管」：**只读**是把钥匙挂在墙上，人人能拿；**受管**是钥匙锁在保险柜里，保安（agent）能带你去用，但不把钥匙给你；**严格**是金库直接封死，谁也别想开。越敏感的环境，钥匙越该往里收。

## 五、综合配置示例

把三层闸串成一个可落地的生产配置：

```toml
[permissions]
allow = [
  "Bash(npm run build)",
  "Bash(npm test)",
  "Write(src/**)",
]
deny = [
  "Bash(git push)",
  "Bash(rm -rf /)",
]
ask = [
  "Write(.env*)",
]
additionalDirectories = [
  "../shared",
]

[sandbox]
bash = "enforce"

# 凭据保护：strict 或 managed，按环境敏感度选
```

配置优先级：flag > `./reasonix.toml` > 全局 `~/.reasonix/config.toml` > 内置默认（详见[[reasonix.toml 配置详解]]）。改完配置用 `/reload` 重载。

## 六、与权限模式、CI 的关系

- **权限模式 vs 沙箱是两维**：权限模式（`ask`/`auto`/`manual`/`yolo`，见[[DeepSeek-Reasonix 权限模式指南]]）决定「要不要审批」；沙箱（`[sandbox] bash`）决定「执行时有没有物理隔离」。`yolo` 跳的是权限审批，**不跳沙箱**——即使 `--yolo`，仍遵守 deny 规则、沙箱与需人工审批的工具。
- **CI 无人值守双保险**：fail-closed 权限 + 沙箱。CI 里别为省事全开 `--yolo`，最小权限始终更稳；Windows runner 上无 OS 级沙箱，需要隔离时用容器（详见[[DeepSeek-Reasonix 自动化与 CI]]）。
- **凭据保护与 CI**：无人值守任务建议把凭据模式收紧（managed/strict），避免 agent 把密钥写进日志或传给外部工具。

> [!warning] `--yolo` 不等于「无沙箱」
> `--yolo` 只跳过**权限审批**，但 deny 规则、沙箱与「需人工审批的工具」仍然生效。把 `--yolo` 当成「关掉所有安全」是危险的误解——它关的只是「是否逐条问你要不要放行」这一层。

## 七、常见坑

1. **以为 allow 能压过 deny**。规则优先级 deny > allow，deny 是硬边界。
2. **Windows 上开了 enforce 却没隔离**。Reasonix 不在 Windows 提供 OS 级 Bash 沙箱，`bash = "enforce"` 在 Windows 解析为 off。需要隔离就在容器里跑。
3. **把凭据写进项目 `.env`**。项目 `.env` 只作 `${VAR}` 展开来源、不导入 provider key；凭据放全局 `<Reasonix home>/.env`，并配合凭据保护模式控制读取边界。
4. **只读工具访问工作区外目录失败**。Read/Glob/Grep 默认只读工作区，要访问外部共享目录必须在 `additionalDirectories` 白名单。
5. **`--yolo` 当万能钥匙**。`--yolo` 不关沙箱、不破 deny、不碰「需人工审批的工具」；它是「跳过逐条审批」，不是「关闭安全」。
6. **配置优先级没排查**。「安全规则不生效」按 flag > `./reasonix.toml` > 全局配置 > 内置默认的顺序查覆盖者。

---

一句话收束：Reasonix 的安全是「三层递进」——配置层白名单决定能不能做，OS 层沙箱决定做了会不会出圈，凭据层决定密钥在谁手里；`--yolo` 只跳审批不破沙箱，Windows 没有 OS 级沙箱，安全配置永远优先看 deny 和凭据模式。

## 常见问题

**Q: Reasonix 的沙箱到底有哪几层？**
A: 三层：配置层（`[permissions]` allow/deny/ask 白名单）、OS 层（Seatbelt / bubblewrap / Firecracker 系统级沙箱）、凭据层（只读/受管/严格三类凭据保护）。

**Q: Windows 上能开系统级沙箱吗？**
A: 不能。Reasonix 不在 Windows 提供 OS 级 Bash 沙箱，`[sandbox] bash = "enforce"` 在 Windows 上解析为 off。需要隔离时应在容器中运行。

**Q: `--yolo` 是不是等于关掉所有安全？**
A: 不是。`--yolo` 只跳过权限审批，但 deny 规则、沙箱与需人工审批的工具仍然生效。

**Q: 凭据保护三种模式怎么选？**
A: 常规开发用「只读」；对工具可能外泄凭据的敏感场景用「受管」（工具不能直接读，只能引用）；最高等级用「严格」（禁止任何凭据访问）。

**Q: 只读工具读不了工作区外的目录怎么办？**
A: 在 `[permissions]` 的 `additionalDirectories` 里把外部共享目录加进白名单。
