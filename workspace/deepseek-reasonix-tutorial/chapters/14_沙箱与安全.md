# DeepSeek-Reasonix 沙箱与安全

> [!info] 文档定位
> 这是高级功能篇第 14 章，也是「沙箱与凭据保护」的唯一权威章节：工作区沙箱的 `[sandbox]` 字段、macOS Seatbelt / Linux bubblewrap / Windows 无 OS 级 Bash 沙箱的实现差异、API Key 的凭据保护模型，以及威胁模型下的加固建议。权限模式的语义见 [[DeepSeek-Reasonix 权限模式指南]]，`[sandbox]` 字段的书写位置见 [[reasonix.toml 配置详解]]，无人值守 CI 里的权限与沙箱组合见 [[DeepSeek-Reasonix 自动化与 CI]]。

本章回答的核心问题：**当 agent 可以一直开着跑、没人盯着时，凭什么相信它不会乱写文件、乱跑命令、把密钥读走？** 答案不是某一道锁，而是权限、沙箱、凭据保护三层机制叠起来，再配一个「可撤销」的长时自治模型。

## 一、安全模型三层

Reasonix 的定位是「可以一直开着跑的编码 Agent」。长时自治意味着模型会在你不在场时持续读写文件、执行命令、访问网络。它的安全不靠单一机制，而是三层叠加：

| 层 | 机制 | 回答的问题 | 权威章节 |
|----|------|-----------|---------|
| 权限 | `[permissions]` + 6 种权限模式 | 这个工具调用**能不能做**？ | 第 6 章 |
| 工作区沙箱 | `[sandbox]` + OS 级隔离 | 做了会不会**波及工作区之外**？ | 本章 |
| 凭据保护 | config 只存变量名 + 全局 `.env` | 密钥会不会**被模型或子进程读走**？ | 本章 |

三层的协作关系：权限是第一道闸，决定放行与否；沙箱是第二道闸，把已放行的动作限制在工作区边界内；凭据保护贯穿全程，保证即使模型被诱导，也拿不到真实密钥。任何一层单独失效，另外两层仍在兜底。

> [!tip] 大白话
> 把三层安全想成「办公楼的三道防线」：权限是**门卫查工牌**（能不能进），沙箱是**楼层围墙**（进去后只能在指定楼层活动），凭据保护是**保险柜**（就算进了办公室，也撬不开放钥匙的抽屉）。三道防线各管一段，拆掉任何一道，另外两道还挡着。

## 二、工作区沙箱：把 agent 关进一个房间

### `[sandbox]` 字段

`reasonix.toml` 的 `[sandbox]` 节控制工作区沙箱（字段书写位置见 [[reasonix.toml 配置详解]]）：

```toml
[sandbox]
workspace_root = ""               # 工作区根目录，界定沙箱活动范围
allow_write = ["/tmp"]            # 可写目录白名单，之外写操作被拒
forbid_read = ["${HOME}/.ssh"]    # 禁读目录，保护敏感路径
bash = "enforce"                  # enforce|off；Windows 强制 off
network = true                    # 沙箱网络开关
```

- `workspace_root`：工作区根目录，界定沙箱的「房间」范围。
- `allow_write`：可写白名单。只有列出的路径允许写，白名单之外的写操作被拒——这是「默认拒绝」思路在文件系统上的体现。
- `forbid_read`：禁读黑名单。保护 `${HOME}/.ssh`、`.aws`、`*.pem` 等敏感路径，即使模型「想读」也读不到。
- `bash`：OS 级 Bash 沙箱开关，`enforce`（强制执行）或 `off`。
- `network`：沙箱网络开关，可关闭以构建完全离线的沙箱。

### 三种操作系统的实现差异

`bash = "enforce"` 的底层实现按平台不同：

- **macOS**：用 **Seatbelt**（macOS 的 OS 级沙箱机制）隔离 Bash 执行。
- **Linux**：用 **bubblewrap**（非特权用户命名空间沙箱）隔离 Bash 执行。
- **Windows**：**不提供 OS 级 Bash 沙箱**。即使配置写 `bash = "enforce"`，也会被解析为 `off`——不是报错，是静默降级。

> [!warning] 坑点：无沙箱环境下 `enforce` 会拒绝执行
> `enforce` 的意思是「必须放进 OS 级沙箱执行」。如果当前环境没有可用的沙箱实现（比如缺少 bubblewrap、或平台不支持），Reasonix 会**直接拒绝执行 bash 命令**，而不是降级成无沙箱执行。这是 fail-closed 思路在沙箱上的延伸：隔离不了，就不执行。

> [!tip] 大白话
> 把沙箱想成「装修工地的围墙」：`allow_write` 是「只允许在工地内堆放材料」（白名单），`forbid_read` 是「工地隔壁的金库禁止靠近」（黑名单），`bash = "enforce"` 是「施工必须站在围栏里」。没有围墙（无沙箱环境）却要求 enforce，Reasonix 的态度是「没围墙就**直接停工**」，而不是在露天施工。

## 三、凭据保护：密钥不落地在配置文件

API Key 是安全链条里最脆弱的一环。Reasonix 遵循「声明与凭据分离」的模型：

1. **config 只存变量名**：`reasonix.toml` 里写 `api_key_env = "DEEPSEEK_API_KEY"`，这是环境变量名，不是密钥本身。
2. **真实值只在全局 `.env`**：密钥放在全局 `<Reasonix home>/.env`（macOS/Linux `~/.reasonix/`，Windows `%AppData%\reasonix\`），由 `reasonix setup` 统一管理。
3. **项目 `.env` 不导入 provider key**：项目根目录的 `.env` 只作为 MCP/plugin 的 `${VAR}` 展开来源，Reasonix **不会**从项目 `.env` 导入 provider 密钥。
4. **运行时从工具子进程移除已保存凭据**：Reasonix 会从它启动的工具子进程中移除已保存的凭据，避免子进程读走密钥。

这样设计的收益：`reasonix.toml` 和项目 `.env` 都可以安全提交到仓库，因为里面根本没有真实密钥；泄露面被压缩到全局那一个文件，且由 `setup` 工具集中管理。

> [!tip] 大白话
> 把 `api_key_env` 想成「保险箱上贴的标签，只写着钥匙放在哪只抽屉」，真实密钥放在全局 `.env` 的保险箱里，项目文件里只有「标签」。所以即使模型被诱导去翻项目里的文件，也找不到密钥——它只存在于那个全局保险箱里，而且连工具子进程都被「没收了钥匙」（运行时移除）。

## 四、权限兜底与沙箱协同

沙箱与权限是两道独立的闸，协同规则（权限语义见 [[DeepSeek-Reasonix 权限模式指南]]）：

- **fail-closed 默认拒绝**：非交互的 `ask/manual` 下，需要显式 Ask 的决定与普通写操作默认被拒绝（关门不放行）。无人值守任务必须 `--auto` / `-y` / `--permission-mode auto` 显式放行。
- **`deny` 黑名单永远压过 `allow` / `--allowed-tools`**：配置里的 `deny` 是权限里优先级最高的一层，命令行临时放行也绕不过。
- **`bypassPermissions`（YOLO）也有底线**：跳过的是「权限模式」这一层，但仍遵守 `deny` 规则、工作区沙箱，以及需要人工审批的工具。换句话说，YOLO 能让你不用按审批键，但不能拆掉沙箱的围墙、不能绕过黑名单。

> [!tip] 大白话
> 把沙箱和权限想成「工地的两道门禁」：权限是**保安查工牌**（能不能进），沙箱是**围墙**（进去后只能在工地范围活动）。`--yolo` 只是跟保安打了招呼免检，围墙还在——你不会因为打了招呼就能穿墙到工地外的银行金库（`.ssh`）。fail-closed 则是「没人值班的工地默认锁门」，而不是默认放行。

## 五、威胁模型与边界

理解安全设计的边界，才知道什么时候该信任、什么时候不该。

**信任模型**：Reasonix 默认信任配置作者与工作区内容，但不信任「模型的行为」——它通过权限审批 + 工作区沙箱 + 逐轮 checkpoint，把模型的不可预测行为关在可撤销的笼子里。它保护的对象是：工作区外的敏感路径、真实凭据、以及失控循环造成的破坏。

**长时自治可撤销**：设计哲学是用计划模式、权限、工作区沙箱与**逐轮 checkpoint** 保证长时自治运行**可读、可撤销**。每一轮工具调用前后都有检查点，出问题可以回看、回退，而不是让一个跑了一整晚的 agent 留下不可逆的破坏。

**边界**：沙箱不是万能隔离。`network = true` 时模型仍可访问网络；`forbid_read` 只防「模型主动读」，不防用户自己把敏感文件放进工作区。威胁模型是「防模型越权」，不是「防恶意代码主动外传」——沙箱隔离的是行为，不是对抗性代码。

> [!note] 与 Claude Code 对齐
> Reasonix 的 `[sandbox]` 与 Claude Code 的工作区沙箱概念同源（PR #6431 对齐了权限与交互），差异在实现细节：Reasonix 明确区分 macOS Seatbelt / Linux bubblewrap / Windows off 三档 OS 实现，并把 `bash = "enforce"` 设计成「无沙箱即拒绝」的 fail-closed 语义。

## 六、加固建议

1. **`forbid_read` 保护敏感路径**：至少加 `${HOME}/.ssh`、`${HOME}/.aws`、`*.pem` 等，防止模型在无意识下读取或引用私钥内容。
2. **`allow_write` 白名单收口**：把可写目录限制到工作区 + 必要的临时目录（如 `/tmp`），减少失控写扩散。
3. **Windows 用容器/CI 隔离替代**：Windows 无 OS 级 Bash 沙箱，需要隔离时把任务放进容器（Docker）或推到带 bubblewrap 的 Linux runner 上跑（编排见 [[DeepSeek-Reasonix 自动化与 CI]]）。
4. **CI 用最小权限**：无人值守任务用 `reasonix run --auto` + 明确的 `deny` 规则，而不是全开 `--yolo`；需要时配合 `--budget` 兜底成本。
5. **禁止 `--yolo` 滥用**：YOLO 只适合完全可信的一次性本地实验；任何涉及生产环境、真实密钥、共享机器的场景都别用。
6. **密钥零落地**：`reasonix.toml` 只写 `api_key_env` 变量名，密钥只放全局 `.env`；不要把项目 `.env` 当成 provider key 的存放处。

> [!warning] 坑点：Windows 上的隔离不能靠 `bash = "enforce"`
> Windows 用户如果把 `bash = "enforce"` 写进配置，不会报错，但实际被当成 `off`。真正的隔离要靠「换地方跑」——容器、远程 Linux runner 或 CI 环境，而不是指望本地配置提供 OS 级沙箱。

## 七、常见坑

1. **Windows 上 `bash = "enforce"` 被忽略**：不报错，但被解析为 `off`，别指望它提供与 macOS/Linux 同等的 OS 级隔离。
2. **无沙箱环境下 `enforce` 直接拒绝 bash 执行**：不是降级，是拒绝。排障时先确认环境是否具备 Seatbelt / bubblewrap。
3. **`deny` 永远压过 CLI allow**：`--allowed-tools` 放行也绕不过配置里的 `deny` 黑名单。
4. **`--yolo` 不拆沙箱**：YOLO 跳过权限审批，但仍遵守 deny、沙箱与需人工审批的工具。
5. **项目 `.env` 放 provider key 不生效**：项目 `.env` 只作 MCP/plugin 的 `${VAR}` 展开，不导入 provider 密钥；连接测试失败先查全局 `.env` 有没有对应变量。

## 常见问题

**Q：Windows 上怎么获得沙箱隔离？**
A：Reasonix 不在 Windows 提供 OS 级 Bash 沙箱，`bash = "enforce"` 会被解析为 `off`。需要隔离时把任务放进容器（Docker）或推到 Linux/macOS runner 上运行。

**Q：`bash = "enforce"` 在无沙箱环境会怎样？**
A：直接拒绝执行 bash 命令，而不是降级成无沙箱执行。这是 fail-closed 语义：隔离不了，就不执行。

**Q：API Key 到底该放在哪？**
A：config 里只写 `api_key_env = "变量名"`；真实密钥放在全局 `<Reasonix home>/.env`（由 `reasonix setup` 管理）。项目 `.env` 只作 MCP/plugin 的 `${VAR}` 展开，不会导入 provider key。

**Q：`--yolo` 能绕过沙箱吗？**
A：不能。`bypassPermissions` 跳过的是权限审批这一层，但仍遵守 `deny` 规则、工作区沙箱，以及需要人工审批的工具。
