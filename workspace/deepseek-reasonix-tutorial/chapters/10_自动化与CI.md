# DeepSeek-Reasonix 自动化与 CI

> [!info] 文档定位
> 把无头执行、结构化输出、事件遥测接进 CI 流水线的实战手册：从 `reasonix run` 到 GitHub Actions，讲清「怎么让 agent 在没人盯着时干活，干完怎么把结果交给机器判断」。命令全量定义见 [[DeepSeek-Reasonix CLI 完整参考]]，权限语义见 [[DeepSeek-Reasonix 权限模式指南]]，成本数据见 [[DeepSeek-Reasonix 前缀缓存与成本优化]]。

本章面向已熟悉 Claude Code 的用户：`claude -p` 你已经很熟，Reasonix 的 `reasonix run` 就是对应物，但它在权限（fail-closed）、结构化输出（`--output-format json`）与遥测（`--events-jsonl`）上有一套自己的约定，CI 里接错会踩不少坑。我们把「无头跑任务 → 拿机器可读结果 → 接进流水线」这条链路一次讲清。

## 一、无头模式：让 agent 一次跑完就退出

无头（headless）模式是自动化与 CI 的入口——不打开 TUI、不等待按键，`reasonix run` 执行完一个任务就退出，天然适合脚本与流水线。

```bash
# 直接给任务
reasonix run "把 main.go 的 TODO 实现掉"

# -p / --print：只输出最终答案，方便接管道
reasonix run -p "修复这个函数的 bug"

# 管道输入：从 stdin 读任务
echo "帮我生成项目的 README" | reasonix run
```

无人值守的**关键在权限**。headless 一次性路径的审批超时默认 **infinite**（无限等待）——这意味着任务需要人工审批时不会超时报错，而是干等，CI 任务会直接卡死。所以 CI 里必须显式放行权限：

```bash
# 三种等价写法，任选其一
reasonix run --auto "批量重命名所有测试文件"
reasonix run -y "批量重命名所有测试文件"
reasonix run --permission-mode auto "批量重命名所有测试文件"
```

> [!warning] fail-closed：默认拒绝，别指望 CI 里有人帮你按「允许」
> 无头模式默认 fail-closed：在非交互的 `ask/manual` 权限下，需要显式 Ask 的决定与普通写操作都会被**拒绝**（fallback 到拒绝），而不是等你审批。带写操作的任务若不开 `--auto`，会在第一个需要授权的动作上失败。
> 另注意 `--auto` 本身就是 `--permission-mode auto` 的别名，**不能与显式 `--permission-mode` 组合**；`--yolo`（bypassPermissions 别名）是更激进的「跳过所有权限」，但仍遵守 deny 规则、沙箱与需人工审批的工具。

> [!tip] 大白话：fail-closed 像夜间无人的办公楼
> 把无人值守的 agent 想成**晚上加班的临时工**：没有门禁卡（`--auto`），他连会议室都进不去——不是保安不让进，而是根本没人能给他刷卡。所以要么发张自动放行卡，要么他只能干点只读的活，一碰写操作就被拒。

## 二、结构化输出：把结果交给机器

`--output-format` 三选一：

| 格式 | 形态 | 适用场景 |
|------|------|---------|
| `text` | 纯文本 | 直接给人类看 |
| `json` | 一次性 result 对象，跑完整体输出 | 跑完再判断整体结果（CI 成功/失败） |
| `stream-json` | 流式事件，边跑边输出 | 实时看进度、尽早发现异常 |

```bash
reasonix run --output-format json "统计 src/ 下的 Go 文件数"
```

result 对象字段（节选自官方 CLI 参考）：

| 字段 | 含义 |
|------|------|
| `type` | 消息类型，结果为 `"result"` |
| `subtype` | 结果子类型 |
| `is_error` | 是否错误结果 |
| `duration_ms` | 耗时（毫秒） |
| `num_turns` | 完成所用轮数 |
| `result` | 最终答案文本 |
| `session_id` | 本次会话 ID |
| `total_cost` | 会话总成本 |
| `currency` | 货币（ISO 代码） |
| `total_cost_usd` | 美元计成本（同值，不换算） |
| `usage` | token 用量：`input` / `output` / `cache_read_input` / `cache_creation_input` |

```json
{
  "type": "result",
  "subtype": "text",
  "is_error": false,
  "duration_ms": 48210,
  "num_turns": 7,
  "result": "共找到 23 个 Go 文件",
  "session_id": "sess_01abcd...",
  "total_cost": 0.042,
  "currency": "CNY",
  "total_cost_usd": 0.042,
  "usage": {
    "input": 128000,
    "output": 2400,
    "cache_read_input": 110000,
    "cache_creation_input": 18000
  }
}
```

> 上例为示意，字段名以官方 CLI 参考为准；其中 `total_cost_usd` 按文档为**同值不换算**。CI 里最常用的消费方式是 `--output-format json`：跑完把整个 result 对象写进文件，再按 `is_error` / `exit code` 决定流水线走向。

> [!tip] 大白话：json 像交班报告写表格
> `--output-format json` 像**让临时工把交班报告写成表格**而不是口头汇报：耗时、轮数、成本、token 用量各占一格，机器直接读表，不用人肉解析一段自然语言。`cache_read_input` 那一格尤其重要——缓存读得越多，成本越低。

## 三、事件流与遥测：看清 agent 到底干了啥

结果对象回答「跑得怎么样」，事件流回答「它这轮经历了什么」。三个参数分工：

| 参数 | 输出 | 用途 |
|------|------|------|
| `--events-jsonl PATH` | 脱敏的生命周期遥测（NDJSON 逐行写文件） | 观测 agent 完整生命周期，脱敏后适合长期留档 |
| `--trajectory PATH` | 事件流输出 | 复现/分析运行轨迹 |
| `--metrics PATH` | 指标输出 | 汇总运行指标 |

```bash
reasonix run --auto --events-jsonl ./events.jsonl "实现登录功能"
reasonix run --trajectory ./trace.jsonl --metrics ./metrics.json "跑一遍测试"
```

> [!warning] `--events-jsonl` 与 `--output-format` 互斥
> 两者都试图接管输出通道，**不能同时使用**。要结构化结果就用 `--output-format json`，要生命周期遥测就用 `--events-jsonl`，二选一。

> [!tip] 大白话：events-jsonl 像行车记录仪
> `--output-format json` 给你一张**罚单式的结论**；`--events-jsonl` 则是一路**行车记录仪**——每个关键节点（初始化、工具调用、权限申请）都记了一笔，出了事故能倒带回放。代价是它占用了「记录仪」这条通道，不能再同时输出结构化结论。

## 四、CI 集成：跑在流水线里

### 只读接口与退出码

Reasonix 提供一组 CI 友好的只读接口，支持 `--json`：`session list/show/status/recovery`、`task list/show`、`task monitor ...`、`hook list/status`。用于在流水线中查询会话状态、恢复会话、监控任务进度。

无头模式用退出码区分失败类型（对齐 [[DeepSeek-Reasonix CLI 完整参考]]）：

| 退出码 | 含义 | 脚本处理 |
|--------|------|---------|
| `0` | 成功 | 继续 |
| `1` | 状态/查询错误 | 查运行状态、会话 |
| `2` | 参数错误 | 查命令用法 |

### GitHub Actions 示例

一个最小流水线：安装 → 无头跑任务 → 按退出码分流 → 成功后提交变更。

```yaml
name: reasonix-ci
on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  reasonix-task:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 安装 reasonix
        run: npm install -g reasonix

      - name: 无头执行任务（结果写入 result.json，不因失败中断步骤）
        id: run
        run: |
          set +e
          reasonix run --auto --output-format json \
            "修复 src/ 下失败的测试" > result.json
          code=$?
          set -e
          echo "exit=$code" >> "$GITHUB_OUTPUT"

      - name: 参数错误（退出码 2）→ 打印结果并失败
        if: steps.run.outputs.exit == '2'
        run: |
          echo "reasonix 参数错误（退出码 2），请检查命令用法"
          cat result.json
          exit 2

      - name: 状态/查询错误（退出码 1）→ 打印结果并失败
        if: steps.run.outputs.exit == '1'
        run: |
          echo "reasonix 状态/查询错误（退出码 1）"
          cat result.json
          exit 1

      - name: 成功后提交变更
        if: steps.run.outputs.exit == '0'
        run: |
          reasonix commit   # git add + commit，提交信息由 LLM 生成
          reasonix index    # 刷新本地语义索引
```

> [!note] 配套命令：commit / index
> `reasonix commit` 执行 `git add + commit`（提交信息由 LLM 写），`reasonix index` 刷新本地语义索引。两者都是写操作，在 CI 里同样需要权限放行（`--auto` 或在配置 `[permissions]` 中用 `allow` 规则明确放行）；生产环境建议只对明确允许的仓库路径放行，别一把梭 `--yolo`。

## 五、CI 中的成本与状态

无人值守任务最容易「跑飞」，三道闸控制成本与状态：

```bash
# 1. 成本上限：花到 80% 警告、100% 拒绝（该参数为 v1 文档收录）
reasonix run --auto --budget 1.0 --output-format json "重构模块 A"

# 2. 跑完看成本/缓存分解
reasonix stats

# 3. 定期清理历史会话，防止 CI 积攒大量会话文件
reasonix prune-sessions --days 7
```

- `--budget <usd>`：会话成本上限，80% 警告 / 100% 拒绝，给无人值守任务兜底。
- `reasonix stats [transcript]`：一次性 cost/cache 分解，跑完看一眼命中率与花费。
- `prune-sessions --days N`：会话保留策略，CI 高频跑会快速累积会话，按天清理。

> [!tip] 大白话：--budget 像每日材料预算
> 把 `--budget` 想成**工地每日材料预算**：花到 80% 有人提醒你，花到 100% 直接停工。无人值守的 CI 任务尤其需要这道闸，防止一次失控调用烧掉太多钱。缓存命中率与成本优化细节见 [[DeepSeek-Reasonix 前缀缓存与成本优化]]。

## 六、常见坑

1. **无人值守忘开 `--auto` → 任务卡死或失败**。headless 审批超时默认 infinite，非交互下默认 fail-closed 拒绝写操作。CI 里要么 `--auto` / `-y` / `--permission-mode auto`，要么带写操作的任务会停在第一个审批上。
2. **`--auto` 与显式 `--permission-mode` 互斥**。`--auto` 就是 `permission-mode auto` 的别名，再写一个 `--permission-mode` 属于重复指定。
3. **`--events-jsonl` 与 `--output-format` 互斥**。都要接管输出通道，只能用一个。
4. **`--copy` 的提示走 stderr**。用 `--copy` 时提示信息写到 stderr，保证 stdout 是纯 machine-readable 输出——解析 stdout 时不要混入提示文本。
5. **Windows 沙箱 off**。Reasonix 不在 Windows 提供 OS 级 Bash 沙箱，`bash="enforce"` 会解析为 off。CI 里若用 Windows runner，需要隔离时应在容器中运行（或用 ubuntu/macOS runner）。
6. **退出码分流别偷懒**。参数错误 `2`、状态/查询错误 `1` 是两类不同问题，脚本里分开处理，排障时才能一眼定位是「写错命令」还是「运行状态异常」。

> [!warning] 权限 + 沙箱双保险
> fail-closed 权限（默认拒绝）+ 沙箱（OS 级隔离）是无人值守的两道保险：权限决定「能不能做」，沙箱决定「做了会不会波及工作区外」。CI 中别为省事全开 `--yolo`——它虽仍遵守 deny、沙箱与需人工审批的工具，但保留最小权限始终更稳。沙箱与凭据保护详见第 14 章。

---

一句话收束：`reasonix run` 是入口，`--auto` 是无人值守的钥匙，`--output-format json` 是交接班表格，`--events-jsonl` 是行车记录仪，退出码是流水线的红绿灯——把这几样串起来，Reasonix 就能作为一个「会干活的 runner」跑在你的 CI 里。

## 常见问题

**Q: 无头任务在 CI 里卡住不动，可能是什么原因？**
A: 大概率是审批等待——headless 审批超时默认 infinite，任务需要授权时没人按「允许」就无限等。给 `reasonix run` 加 `--auto` / `-y` / `--permission-mode auto`。

**Q: `--output-format json` 和 `--events-jsonl` 能一起用吗？**
A: 不能，二者互斥。要结构化结果用 `--output-format json`，要生命周期遥测用 `--events-jsonl`。

**Q: 怎么在脚本里区分「命令写错」和「运行出错」？**
A: 看退出码：参数错误 `2`，状态/查询错误 `1`。

**Q: 想给无人值守任务设成本上限，用哪个参数？**
A: `--budget <usd>`（80% 警告 / 100% 拒绝），该参数为 v1 文档收录，main-v2 下以应用内 `/help` 为准。
