## 第二章 Windows 注册表——系统和程序的配置中心

导读里我们把注册表比作整台电脑的"后台登记本"。这一章把本子摊开：它长什么样（树 / 键 / 子项 / 值）、顶层五个"总目录"各管什么、它存放在硬盘上的哪个文件里、值有哪几种类型、64 位系统上为什么会有"两套"注册表。

排版顺序是刻意的：**先把备份和回滚讲透（2.7），再讲怎么查、怎么改、怎么删（2.8、2.9）**。官方的警告不是客套话——错误地修改注册表，"可能需要重新安装操作系统才能解决" [S6]。请务必按顺序读。写法沿用第一章：先中文人话讲直觉，再给官方术语，最后说清"它到底指什么"。

### 2.1 注册表是什么：树、键、子项、值

#### 2.1.1 四个基本词：树、键、子项、值

官方的定义是：注册表是一个**分层数据库**，数据以**树**的格式组织；树中每一个节点称为**键**，每个键可以**同时**包含**子项**和称为**值**的数据条目，而且一个键可以有任意数量的值 [S1]。

把这句话拆成四个词：

| 词 | 官方术语 | 它到底指什么 |
|---|---|---|
| 树 | 分层数据库 | 整个注册表是一棵倒过来的树，从顶层往下不断分叉 |
| 键 | key | 树上的一个节点，作用相当于"文件夹" |
| 子项 | subkey | 键下面再分出来的键，相当于"子文件夹" |
| 值 | value | 挂在键上的"数据条目"，相当于贴在文件夹上的标签 |

> [!note] 键能装东西，也能被装东西
> 这是注册表最容易记混的一点：**一个键既是"文件夹"，又挂着"标签"**。你在 regedit 里点开一个键，看到的往往是"左边一串子文件夹 + 右边一串标签"，两者并列，不是二选一 [S1]。

> [!tip] 大白话
> 把注册表想成一栋**倒着长的文件柜**：顶层是五个大抽屉，抽屉里是文件夹，文件夹里还有文件夹；每个文件夹的封面上都贴满写着一行小字的便利贴。**文件夹**就是"键"和"子项"，**便利贴**就是"值"。系统开机做的事，就是按索引翻到某几个文件夹，看一眼上面写了什么。

#### 2.1.2 命名规则：谁不能带反斜杠

键名的规则比"值"严格，官方给了四条 [S1]：

- 键名**不区分大小写**（`Software` 和 `software` 是同一个键）；
- 键名**不能包含反斜杠 `\`**；
- 而**值的名称和数据可以**包含反斜杠；
- 键名**不做本地化**，值**可以被本地化**。

后两条需要解释一下。"本地化"就是"翻译成当地语言"：**键名不做翻译**，所以不管你用中文版还是英文版 Windows，键路径都是 `Software\Microsoft\Windows\CurrentVersion` 这种固定英文形式，网上找到的路径可以直接照抄；而**值可以被翻译**，同一个键下不同语言系统可以放不同语言内容的值。

反斜杠在键名里的角色和第一章的文件路径一样，**是分隔符，不是名字的一部分**：`Software\Microsoft\MyApp` 里的两个 `\` 划出三层，正因如此键名里不能再出现它；但值是"贴上去的标签"，不受这个限制。

#### 2.1.3 树的深度：512 层与 32 层

两个关于深度的数字 [S1]：

- 注册表树**最深可达 512 层**；
- 通过**单次注册表 API 调用**，一次最多创建 **32 层**。

对零基础读者，这两个数字只需一个直觉：**注册表可以很深，但日常几乎碰不到极限**。真正要记住的是"它是分层结构"——找一个键就像沿路径一层层往下点，少一节都到不了。

#### 2.1.4 五个顶层"总目录"的意义

应用程序必须先**打开一个键**，才能往注册表里添加数据。系统为此定义了一批**始终打开**的键作为入口，称为**预定义键**；官方的要求是：添加数据的应用**应始终在预定义键的框架内工作**，这样管理工具才能找到并使用新数据。预定义项的名称最大长度为 **255 个字符** [S4][S6]。

> [!tip] 大白话
> 把预定义键想成图书馆里划好的**五大分类区**。官方要求程序"必须把书写进分类区里"，不是它管得宽，而是——如果每本书都随手塞进自己的抽屉，图书管理员就再也找不到任何东西了。注册表也一样：regedit 和各类管理工具，只认这五个入口往里查。

> [!note] 给开发者的补充（可跳过）
> 官方在讲这一节时会用"预定义项""句柄"`RegOpenKeyEx` 这类说法 [S1][S4]。这些是写给写程序的人看的。对你来说只需要记住：**注册表有 5 个顶层文件夹**，往下全是分叉。

### 2.2 五个根键各管什么

顶层那 5 个文件夹（**根键**）全名都很长，平时一律用缩写。先看总览，再逐个说：

| 缩写 | 全名 | 管什么 |
|---|---|---|
| HKLM | HKEY_LOCAL_MACHINE | 整台计算机 |
| HKCU | HKEY_CURRENT_USER | 当前登录的这个用户 |
| HKCR | HKEY_CLASSES_ROOT | 文件类型与右键菜单（合并视图） |
| HKU | HKEY_USERS | 所有用户的配置文件 |
| HKCC | HKEY_CURRENT_CONFIG | 当前硬件配置（只是一个别名） |

#### 2.2.1 HKLM：这台机器的"物理状态"

`HKEY_LOCAL_MACHINE`（HKLM）保存计算机**物理状态**的数据：总线类型、系统内存、已安装的软硬件，以及即插即用信息。官方特别指出，其中的 `Enum` 分支记录了"系统上出现过的全部硬件" [S4]。

翻译成人话：**只要是"这台机器本身"的属性，都在 HKLM**——换个人登录，看到的东西基本一样。

#### 2.2.2 HKCU：当前这个用户的偏好

`HKEY_CURRENT_USER`（HKCU）保存**当前用户**的偏好：环境变量设置、程序组、颜色、打印机、网络连接和应用偏好 [S4]。

它的机制值得单说一句，因为这是 HKU 与 HKCU 关系的关键：**HKCU 映射到 `HKEY_USERS` 中当前用户的那一个分支**，而且这个映射是**按进程**建立的，依据是"第一个引用它的线程的安全上下文"；如果那套安全上下文在 `HKEY_USERS` 下**没有已加载的 hive**，就映射到 `HKEY_USERS\.Default` [S4]。

> [!tip] 大白话
> 把 `HKU` 想成一栋**员工宿舍楼**，每个住户（每个用户）一间房，房里放着这个人的个人设置。`HKCU` 不是第 6 栋楼，而是**前台发给你的门牌**：你今天以谁的身份登录，牌子就指向谁的房间；每个程序各自领一块牌子，所以不同程序看到的 `HKCU` 内容可能不同——这就叫"按进程建立"。`HKU\.Default` 则是"没人认领时的默认房间" [S4]。

#### 2.2.3 HKCR：不是真实位置，是一张"合并视图"

`HKEY_CLASSES_ROOT`（HKCR）最反直觉：**它不是一个真实存储位置**，而是两个真实位置的**合并视图**——`HKLM\Software\Classes`（本机所有用户的默认设置）和 `HKCU\Software\Classes`（仅当前交互用户的覆盖设置）。你往 HKCR 里写东西，系统会把它**重定向**到这两个位置之一 [S6]。

所以 HKCR 更像"投影"，不像"房间"：你在上面看到的内容，实际来自另外两个地方。

> [!warning] 不要直接往 HKCR 里写
> 官方明确要求：**要更改"当前交互用户的设置"，必须在 `HKEY_CURRENT_USER\Software\Classes` 下修改；要更改"默认设置"，必须在 `HKEY_LOCAL_MACHINE\Software\Classes` 下修改**，而不是在 `HKEY_CLASSES_ROOT` 下修改 [S6]。这条规则在第 2.9 节会有一个很实际的好处：写在 HKCU 那边的自定义右键菜单项，**不需要提升权限** [S25]。

#### 2.2.4 HKCC 只是别名，性能数据根本不在注册表里

`HKEY_CURRENT_CONFIG`（HKCC）只是 `HKLM\System\CurrentControlSet\Hardware Profiles\Current` 的**别名**，描述当前硬件配置与标准配置之间的差异 [S4]。换句话说，你在 HKCC 里看到的东西，本体在 `HKLM\System\CurrentControlSet\Hardware Profiles\Current`——它没有自己的存储空间。

另一件事：`HKEY_PERFORMANCE_DATA` 这个根键里的数据**并不真的存在注册表里**，而是由注册表函数**触发系统从数据源实时收集**[S4]。它和别的根键性质完全不同，本章不展开，遇到时知道"它不是存储位置"就够了。

### 2.3 Hive：注册表在磁盘上的真实文件

导读里说过一句关键的话：注册表也长在硬盘上。这一节把它落实——注册表**不是内存里的抽象设置**，它有实实在在的磁盘文件。

#### 2.3.1 "配置单元"和它的支持文件

官方的定义是：**配置单元（hive）**是注册表中键、子项和值的**逻辑组**，它带有一组"在操作系统启动时或用户登录时加载到内存中的支持文件" [S2]。

这句话有点绕，拆成三点：

- "配置单元"就是注册表的**数据库文件**（官方术语叫 hive，中文译作"配置单元"）；
- 它**在磁盘上真实存在**，是一组文件，不是虚构概念；
- 加载时机很明确：**开机时**（系统级）或**用户登录时**（用户级）被读进内存——这也解释了为什么注册表"平时看不到文件、却感觉一直在"。

后文为了好读，一律用"**注册表文件**"或直接给文件名。

#### 2.3.2 每次新用户登录，就多一个用户配置文件配置单元

官方说明：**每次新用户登录**，系统都会为该用户创建一个新的配置单元，称为**用户配置文件配置单元**，位于 `HKEY_USERS` 键下，内容包括该用户的应用程序设置、桌面、环境、网络连接和打印机 [S2]。

这就解释了 2.2.2 里 HKCU 为什么能"跟人走"：每个用户各有一个自己的配置单元，挂在 `HKEY_USERS` 下面 [S2]。

#### 2.3.3 支持文件对照表

注册表的**大部分**支持文件位于 `%SystemRoot%\System32\Config` 目录中（每次用户登录时更新）。官方的对照关系如下 [S2]：

| 注册表配置单元 | 磁盘上的支持文件 |
|---|---|
| HKEY_CURRENT_CONFIG | System、System.alt、System.log、System.sav |
| HKEY_CURRENT_USER | Ntuser.dat、Ntuser.dat.log |
| HKEY_LOCAL_MACHINE\SAM | Sam、Sam.log、Sam.sav |
| HKEY_LOCAL_MACHINE\Security | Security、Security.log、Security.sav |
| HKEY_LOCAL_MACHINE\Software | Software、Software.log、Software.sav |
| HKEY_LOCAL_MACHINE\System | System、System.alt、System.log、System.sav |
| HKEY_USERS\.DEFAULT | Default、Default.log、Default.sav |

注意表里的两种情况：**大部分**机器级 hive 的支持文件在 `%SystemRoot%\System32\Config` 里；而**用户级**那一个（HKEY_CURRENT_USER）对应的文件是 `Ntuser.dat` 及其日志 [S2]。

#### 2.3.4 用户级 hive 的磁盘承载文件

用户级 hive 的磁盘承载文件是 **`NTUSER.DAT`**（以及它的日志 `NTUSER.DAT.LOG`）；它属于**用户配置文件** hive，随用户登录被加载 [S2][S6]。

> [!warning] 用户级 hive 的磁盘位置，两份官方文档说法不一致
> 一处官方资料（Win32「注册表 Hives」）说"Hives 的**大部分**支持文件位于 `%SystemRoot%\System32\Config`"，但没有为 `Ntuser.dat` 指明目录 [S2]；另一处（KB256986）则写"HKEY_CURRENT_USER 的支持文件位于 `%SystemRoot%\Profiles\Username` 文件夹中" [S6]。
>
> 这两处说法**并不一致**，而且**都没有给出符合现代 Windows 布局的用户级 hive 磁盘路径**。因此本章的处理口径是：**只说 `NTUSER.DAT` / `NTUSER.DAT.LOG` 属于"用户配置文件 hive"，磁盘位置用"用户配置文件目录"来表述，不写死任何路径**。需要提醒的是，部分官方资料仍沿用旧版布局（`%SystemRoot%\Profiles\...`）描述，内容是经典 KB，个别路径描述偏旧 [S2][S6]。

#### 2.3.5 扩展名含义：这些是系统自己用的，不要动

同一批文件有几种扩展名，含义不一样 [S2]：

- **无扩展名**（如 `Software`）= 配置单元数据的**完整副本**；
- **`.alt`** = 备份副本，**只有 `HKLM\System` 才有**（官方原话是"只有系统密钥具有 .alt 文件"）；
- **`.log`** = 键和值更改的**事务日志**；
- **`.sav`** = 配置单元的**备份副本**。

> [!warning] 这些文件是系统自己用的，不要删也不要改
> `.log` / `.alt` / `.sav` 不是给你清理的"垃圾文件"，而是系统用来保证注册表完整性的日志和副本 [S2]。讲它们的目的只有一个：**它们出现在你眼前时，你知道"不要动它们"。**

#### 2.3.6 格式演进：两种格式，四个 hive 例外

注册表文件只有**标准格式**和**最新格式**两种。Windows 2000 只支持标准格式；**从 Windows XP 起**支持最新格式 [S2]。

但即使在支持最新格式的系统上，仍有四个 hive **继续使用标准格式**：`HKEY_CURRENT_USER`、`HKLM\SAM`、`HKLM\Security`、`HKEY_USERS\.DEFAULT`；其余 hive 使用最新格式 [S2]。

这条对你没有操作上的影响，但能解释一件怪事：为什么有些老式的注册表工具在部分键上行为不一样。

#### 2.3.7 临时挂载：把一块注册表当文件加载进来

应用程序可以把注册表的一部分保存成文件再加载回来，适用于"数据量大、条目过多或数据是临时的"场景；`RegLoadKey` 把文件数据加载到 `HKEY_USERS` 或 `HKEY_LOCAL_MACHINE` 下的指定子项，之后可以用 `RegUnLoadKey` 还原到以前的状态 [S3]。

命令行工具里对应的是 `reg load` 和 `reg unload`，本意是"临时挂载做排查"，具体命令见 2.7.4。

### 2.4 值类型：一套类型的三副面孔

同一个东西，官方文档里叫 `REG_SZ`，注册表编辑器里显示"字符串值"，PowerShell 里写 `-Type String`——**这是同一套类型的三副面孔**。这一节把三副面孔对上号。

#### 2.4.1 常用类型

注册表值可以存储多种格式的数据，这些类型定义在 `winnt.h` 头文件中 [S5]：

- **`REG_SZ`**：以 null 结尾的字符串；
- **`REG_BINARY`**：任何形式的二进制数据；
- **`REG_DWORD`**：**32 位数字**；
- **`REG_QWORD`**：**64 位数字**；
- **`REG_NONE`**：没有定义的值类型。

先给读者一个心智锚点：**`REG_SZ` 是"文字"，`REG_DWORD` 是"32 位的数字"，`REG_QWORD` 是"64 位的数字"**，这三条覆盖了日常绝大多数情况。

> [!note] 关于"小端"，一句话就够
> 官方还定义了 `REG_DWORD_LITTLE_ENDIAN` 和 `REG_DWORD_BIG_ENDIAN`。前者的定义是：在 Windows 头文件里，它**就等同于 `REG_DWORD`**（因为 Windows 被设计为运行在小端架构上）；后者是供某些 UNIX 大端系统使用的 [S5]。所以你**不需要理解"字节序"**，在 Windows 上看到 `REG_DWORD_LITTLE_ENDIAN` 就当作 `REG_DWORD` 处理即可。

#### 2.4.2 REG_EXPAND_SZ：带着 `%变量%` 的字符串

`REG_EXPAND_SZ` 是"**包含对环境变量的未扩展引用**"的字符串，例如 `%PATH%` 或 `%systemroot%`；要用的时候，得调用 `ExpandEnvironmentStrings` 把它展开 [S5]。

"未扩展"的意思是：**值里存的是 `%systemroot%` 这串字符本身，不是展开后的 `C:\Windows`**；只有用到它并且显式要求展开时，系统才会替换成真实路径。这就是同一个值在不同机器上能给出不同结果的原因。

#### 2.4.3 REG_MULTI_SZ：一个值装多行

`REG_MULTI_SZ` 是**以长度为 0 的字符串结尾的字符串序列**，官方示例长这样：`String1\0String2\0String3\0LastString\0\0` [S5]。

这里有两条硬规则 [S5]：

- 它需要**两个**终止 null 字符（示例末尾的 `\0\0`）；
- 它**不能包含零长度字符串**（官方定义的"空序列"写成单个 `\0`）。

> [!tip] 大白话
> `\0` 是**字符串末尾的隐藏结束符**，你看不见它。`REG_MULTI_SZ` 就是"一个值里装一个列表"，每项之间用隐藏结束符隔开，列表**结尾要连用两个**表示"到此为止"。既然"空的一项"和"列表结束"用的是同一个符号，这个类型自然就**不能有空行** [S5]。

#### 2.4.4 三列对照表：同一套类型的三副面孔

| 官方类型名（文档 / `reg` 的 `/t`） | regedit 里显示为 | PowerShell 的 `-Type` | 什么时候用它 |
|---|---|---|---|
| `REG_SZ` | 字符串值 | `String` | 普通文字，如程序名、路径（不含 `%变量%`） |
| `REG_EXPAND_SZ` | 可扩充字符串值 | `ExpandString` | 含 `%变量%` 的路径，如 `%SystemRoot%\...` |
| `REG_BINARY` | 二进制值 | `Binary` | 原始字节，如硬件信息、加密数据 |
| `REG_DWORD` | DWORD (32 位) 值 | `DWord` | 开关、状态码、端口号这类整数 |
| `REG_QWORD` | QWORD (64 位) 值 | `QWord` | 超出 32 位范围的大整数 |
| `REG_MULTI_SZ` | 多字符串值 | `MultiString` | 一个值里存一个列表 |

表格的依据：类型定义来自 [S5]，regedit 中的显示形式与 `REG_QWORD` 的呈现方式来自 [S6]，PowerShell 一侧的 `-Type` 取值（含"`String` 是默认值"）来自 [S21][S22]。

> [!example] 把三副面孔对上号
> 假设要在自建键 `HKCU\Software\Demo` 下写一个 32 位数字 `1`，三条路写出来的是**同一个类型的同一个值**，只是入口不同：
>
> - **regedit 里**：新建 →「DWORD (32 位) 值」，值填 `1`；
> - **`reg` 命令行**：`reg add "HKCU\Software\Demo" /v Flag /t REG_DWORD /d 1 /f`；
> - **PowerShell**：`Set-ItemProperty -Path "HKCU:\Software\Demo" -Name Flag -Value 1 -Type DWord`。
>
> 记住这张对照，你在任何一份教程里看到 `REG_DWORD`、"DWORD 值"、`-Type DWord` 这三种写法，就知道说的是同一件事。

#### 2.4.5 字符串终止符：读写注册表最常见的陷阱

官方明确指出，**字符串的终止符是读写注册表最常见的陷阱** [S5]：

- **写入时**，必须把终止 null 计入长度——官方给的做法是用 `strlen(string) + 1`，而不是 `strlen`；
- **读取时**，字符串**可能未正确终止**，你必须自行确保终止，否则可能覆盖缓冲区。

对零基础读者，这条的价值不在于让你自己写代码，而在于理解"**为什么有的注册表工具会把字符串写坏**"：多算了留垃圾、少算了溢出，这是一个真实存在的坑 [S5]。

#### 2.4.6 在 regedit 里，同一种类型的显示方式不同

在注册表编辑器里，**DWORD 值可以按二进制、十六进制或十进制三种格式显示**——看到 `0x1` 和看到 `1` 可能是同一个值。另一条：`REG_QWORD`（Windows 2000 引入）在注册表编辑器中**以"二进制值"的形式显示** [S6]——明明是个 64 位数字，却显示得像二进制数据，这不代表类型错了 [S6]。

#### 2.4.7 尺寸限制：为什么会遇到"值写不进去"

有四个数字容易记混，做成一张小表 [S6][S19]：

| 限制 | 数值 | 什么时候会遇到 |
|---|---|---|
| 值名称的最大长度 | 16,383 个字符 | 名字起得极长时 |
| 单个值的数据大小 | 超过 **2,048 字节** 必须改存为文件 | 想把一大段数据塞进一个值时；此时注册表里只存文件名 |
| 一个项的所有值加起来 | **64 K** 上限 | 往同一个键里塞太多值时 |
| `Run` 键里的命令行 | **不超过 260 个字符** | 写开机自启命令时（见 2.9） |

官方解释为什么要限制：超过 2,048 字节的长值"必须存储为文件，只在注册表中存文件名"，这样"有助于注册表高效执行" [S6]。

> [!warning] 遇到"写不进去"时，先想这四条
> 值名称太长、单个值太大（>2048 字节）、一个键里所有值加起来超过 64 K、自启命令行超过 260 字符——**表现可能都是"写不进去"或"被截断"**，但原因完全不同 [S6][S19]。排查时按这张表逐个对，不要靠猜。

### 2.5 64 位系统上的两套注册表：WOW6432Node

#### 2.5.1 默认行为：谁看谁那一套

官方规定：在 WOW64（即 64 位 Windows 运行 32 位程序的环境）上，**32 位应用程序默认访问 32 位注册表视图，64 位应用程序默认访问 64 位注册表视图** [S20]。

用中文说清楚"两套注册表"：

> [!tip] 大白话
> 把注册表想成一个**装了两种高度书架的档案室**：64 位程序习惯用高架子，32 位程序习惯用矮架子。**同一个路径**（比如 `HKLM\Software`），64 位程序看到的是高架子上的东西，32 位程序看到的是矮架子上的东西——**这不是"文件被搬走了"，也不是"有个假的副本"**，而是同一套注册表按"来的人是 32 位还是 64 位"显示不同内容。矮架子那一批，在 64 位程序眼里就挂在 `WOW6432Node` 下面 [S20][S6]。

官方还给了两个可切换视图的标志：`KEY_WOW64_64KEY`（值 `0x0100`）让任一应用访问 64 位键，`KEY_WOW64_32KEY`（值 `0x0200`）让任一应用访问 32 位键；这两个标志**对共享注册表键无效**，而且**同时指定会失败**，返回 `ERROR_INVALID_PARAMETER` [S20]。

#### 2.5.2 WOW6432Node 是保留键，不要直接改

官方明确：`Wow6432Node` 与 `WowAA32Node` 键是**保留的**，"为了兼容性，应用程序**不应直接使用**这些键" [S20]。配套最佳实践是：应用一旦用某个视图标志访问了备用视图，之后对该视图下**所有子键**的创建、删除、打开都必须显式使用**同一个标志**；要准确枚举两个视图中的所有键，必须**分两遍**枚举（各用一个标志） [S20]。

#### 2.5.3 你实际会遇到的只是两个开关

上面那些掩码数字是写给开发者的。**读者实际只会遇到两个开关**：`reg query` / `reg add` / `reg import` 等命令提供的 `/reg:32` 与 `/reg:64`，用来指定操作哪一套视图 [S9][S10][S14]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 同一个路径，分别从 32 位视图和 64 位视图看（只读，安全）
reg query "HKLM\Software\MyApp" /reg:32
reg query "HKLM\Software\MyApp" /reg:64
```

另外，**64 位 Windows 自带的 64 位注册表编辑器，会在 `HKEY_LOCAL_MACHINE\Software\WOW6432Node` 节点下显示 32 位项** [S6]。这就是"明明数据在，却找不到"的常见原因。

> [!warning] 找不到键时的第一步：怀疑视图
> 在 64 位系统上找一个键却怎么都找不到，**先怀疑"是不是看错了视图"**，再怀疑别的 [S20][S6]。同时记住：**不要直接去改 `WOW6432Node`**——它是保留键 [S20]。

### 2.6 权限与所有者

#### 2.6.1 每个键都带一张权限清单，默认从父键继承

Windows 的安全模型允许你控制对注册表项的访问。调用 `RegCreateKeyEx` 或 `RegSetKeySecurity` 时，可以为键指定**安全描述符**；如果指定为 `NULL`，键会获得**默认安全描述符**——而默认安全描述符中的权限清单，**继承自它的直接父键** [S7]。

翻译成对读者有用的那句：**注册表键也有权限**；你没特意设过权限的键，它用的就是"爸爸键"的权限清单 [S7]。

#### 2.6.2 想干不同的事，需要不同的权限

注册表项支持的访问权限里，有几条与日常操作直接对应 [S7]：

| 你想做的事 | 需要的权限 |
|---|---|
| 查询值 | `KEY_QUERY_VALUE` |
| 创建、删除或设置值 | `KEY_SET_VALUE` |
| 创建子项 | `KEY_CREATE_SUB_KEY` |
| 枚举子项 | `KEY_ENUMERATE_SUB_KEYS` |
| 请求更改通知 | `KEY_NOTIFY` |

两条边界：注册表键**不支持 `SYNCHRONIZE`**；`KEY_CREATE_LINK`（值 `0x0020`）**保留供系统使用**。另外，打开键时系统会按安全描述符检查你请求的权限，**权限不足则打开失败** [S7]。

#### 2.6.3 权限不足时，官方给出的唯一解法

官方的原话是：如果管理员需要访问某个键，解决方案是**启用 `SE_TAKE_OWNERSHIP_NAME` 特权，并以 `WRITE_OWNER` 访问权限打开该键** [S7]。

零基础读者请这样记：**"取得所有权"**是那个特权要做的事，"以**所有者身份写入**的权限打开"是那个访问权限要做的事。落到能操作的动作上就是：**在权限对话框里把所有者改成自己，再给自己赋"完全控制"** [S7]。

#### 2.6.4 两个核对权限的入口

1. **注册表编辑器**：定位到目标键 →「编辑」菜单 →「权限」 [S7]。
2. **PowerShell**：`Get-Acl` 读取、`Set-Acl` 写入（官方示例用 `RegistryAccessRule` 给指定用户加 `FullControl`） [S7][S21]。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 只读：查看某个键的权限清单（不会改动任何东西）
Get-Acl -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion"
```

> [!tip] 改之前先看一眼权限，比出事之后再救便宜
> 官方的建议顺序是"先看现有权限，再决定要不要动" [S7]。本章 2.7.7 的风险 checklist 里也会再出现这一条。

### 2.7 备份与回滚（本章强制主线）

**这一节必须完整读完，再往下看修改命令。** 官方的警告不是吓唬人，它把"错误修改注册表"的后果写成了"可能需要重新安装操作系统"。

#### 2.7.1 官方的两条警告原文

**Caution 级**（来自 `reg` 命令页）：「除非没有替代项，否则不要直接编辑注册表。注册表编辑器绕过标准安全措施，允许降低性能、损坏系统甚至要求重新安装 Windows 的设置。……**如果必须直接编辑注册表，请先备份它。**」 [S8]

**Warning 级**（来自 KB256986）：错误地修改注册表"**可能需要重新安装操作系统才能解决。Microsoft 不能保证可以解决这些问题**" [S6]。

同时也要记下官方的另一半态度：**编辑注册表有时"可能是解决产品问题的最佳方法"** [S6]。所以本章的口径不是"永远别碰"，而是"**没备份就别碰**"。

> [!warning] 两页警告的语气强度不一样，不要合成一个版本
> `reg` 命令页用 Caution 级，KB256986 用 Warning 级并明确承认"有时必须改" [S8][S6]。两段都是官方原文，**强度不同是事实本身**，不要改写成更强或更弱的版本。

#### 2.7.2 官方推荐的修改顺序

官方的建议是：**使用 Windows 用户界面更改系统设置，而不是手动编辑注册表**；如果 Microsoft 知识库针对你的问题给出了分步说明文章，则「建议完全按照这些说明操作」 [S6]。

翻译一下这条顺序：**能用设置界面（控制面板 / 设置 / 组策略 / MMC）改的，就别动注册表。** 只有当设置界面里根本没有这个选项时，才轮到手动编辑 [S6]。

#### 2.7.3 主路径：导出 `.reg` → 需要时导入还原

这是官方覆盖范围最广的一条路（该页面适用于 Windows 11 / Windows 10 / Windows 8.1）[S18]。

**方式一 · regedit 界面**（官方给出步骤最完整的一条）[S18]：

1. 「开始」→ 搜索 `regedit.exe` → 回车。**若有管理员密码或确认提示，需提供**（官方原文即含此提示）；
2. 在注册表编辑器中找到并单击要备份的项或子项；
3. 「文件」>「导出」；
4. 在"导出注册表文件"对话框中，选择保存位置并输入备份文件名；
5. 「保存」。

还原时：「文件」>「导入」→ 选择备份文件 →「打开」 [S18]。

> 环境：regedit（注册表编辑器界面）｜ 版本：全版本适用 ｜ 权限：官方明写会有管理员密码或确认提示，即导出与导入都按提权处理 [S18]

**方式二 · 命令行 `reg.exe`** [S13][S14]：

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 备份：把某个键（含其下所有子项和值）导出为 .reg 文件
reg export "HKLM\SOFTWARE\MyApp" AppBkUp.reg /y

:: 还原：把这个 .reg 文件导入回注册表
reg import AppBkUp.reg
```

几条必须知道的边界 [S13][S14]：

- `reg export` 的文件名**必须带 `.reg` 扩展名**；`/y` 表示覆盖同名文件时不提示；**仅适用于本地计算机**；键名含空格必须加引号；
- `reg import` 的文件**必须由 `reg export` 提前创建**，同样仅适用于本地计算机；
- 返回值 **0 = 成功 / 1 = 失败**，可以用于脚本判断。

> [!warning] `reg export / import` 是否需要管理员，官方未说明
> 上面那张表里，只有 **regedit 界面**的导出/导入有官方明确的"会有管理员密码或确认提示" [S18]。而 **`reg export` / `reg import` 是否需要管理员权限，官方页面全未明示**——本章**不做推断**，一律标注"官方未说明" [S13][S14]。这一条对 `reg save` / `reg restore` / `reg load` / `reg unload` 同样成立（见 2.7.4）。

#### 2.7.4 进阶路径：整键快照 → 写回（`.hiv`）

除了导出文本格式的 `.reg`，还有一条更"原始"的路径：把整个键原样快照成一个二进制文件（`.hiv`），需要时写回。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 编辑前先做整键快照（官方指定的"编辑前必做"动作）
reg save "HKLM\Software\MyApp" AppBkUp.hiv /y

:: 编辑失败时写回原始子项（会覆盖该键的现有内容）
reg restore "HKLM\Software\MyApp" AppBkUp.hiv

:: 只做临时加载排查，用完必须卸载
reg load   HKLM\TempHive TempHive.hiv
reg unload HKLM\TempHive
```

官方在 `reg save` 的备注里直接把"备份"写成了必做动作：

> 「在编辑任何注册表项之前，**必须**使用 `reg save` 命令保存父项和子项。如果编辑失败，则可以使用 `reg restore` 还原原始子项。」 [S15][S16]

几条边界 [S15][S16][S17][S8]：

- `reg restore` 会**覆盖**目标键的现有内容；
- `reg restore` 用的文件**必须由 `reg save` 创建**，且**必须是 `.hiv` 扩展名**；
- `reg load` 的定位是"**故障排除或编辑注册表项的临时文件**"式操作；`reg unload` 的定义就是"删除使用 `reg load` 加载的注册表部分"——所以 **load 之后必须 unload**，否则那块内容会一直挂在 `HKLM` 下。

#### 2.7.5 整机级兜底：备份"系统状态"

如果要备份的是**整个注册表**，官方给的办法不是"导出某个键"，而是用**备份工具备份"系统状态"**——官方说明"系统状态包括注册表、COM+ 类注册数据库和启动文件"；还原时走"**从备份还原系统状态**"。备份系统状态还会在 `%SystemRoot%\Repair` 文件夹中生成注册表文件的更新副本 [S6]。

> [!warning] "备份整个注册表"这句话，含义并不统一
> 一份官方资料把"备份整个注册表"指向**备份系统状态**（整机快照）[S6]；另一份面向普通用户的资料（覆盖 Win11）则只教 **regedit 的「导出 / 导入」**，而那是**按键导出** [S18]。两者不冲突，但覆盖面完全不同。
>
> 所以务必分清：**按键级备份** = 导出 `.reg`（只保住了你导出的那一个键）；**整机级备份** = 备份系统状态（保住整台机器）。**把"导出 `HKLM\Software` 下的某一个键"当成"备份了整个注册表"，是一个非常常见也非常危险的误解** [S6][S18]。

#### 2.7.6 系统还原：只作附注，不是回滚主路径

还有一条整机级的回滚路径是**系统还原**（还原点）。

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方明确要求"以管理员身份运行" [S26]

```powershell
# 在 C: 上启用系统还原功能
Enable-ComputerRestore -Drive "C:\"
```

官方的几条限制 [S26]：

- 在 Windows Vista 及更高版本上，**必须用"以管理员身份运行"打开 Windows PowerShell** 才能运行该 cmdlet；
- **要在任何驱动器上启用系统还原，必须先在系统驱动器上同时启用**；
- **不能用于外部驱动器或远程网络驱动器**；
- 可以用 `Rstrui.exe` 查看每个驱动器的还原状态。

> [!warning] 不要把系统还原写成注册表回滚的"主路径"
> 官方关于系统还原的那一页，正文称"系统还原点和 ComputerRestore cmdlet **仅在 Windows 7、Windows Vista 和 Windows XP 等客户端操作系统上受支持**"，但同一页的"适用于"和该 cmdlet 在 Windows 10 / 11 的 PowerShell 5.1 里仍然存在——**文档的版本声明明显滞后** [S26]。与此同时，另一份覆盖 Windows 11 的官方页面（2.7.3 的主路径来源）**通篇没有提到系统还原**，只给 regedit 导出 / 导入两条路径 [S18]。
>
> 因此本章口径是：**回滚主路径 = 导出 `.reg` → 需要时导入还原**；系统还原**只作整机级兜底的一条附注**，并注明官方版本声明存疑 [S18][S26]。

#### 2.7.7 编辑前的官方风险 checklist

以下是官方在"修改注册表之前"要求你确认的事项，原样落地 [S8][S6][S7]：

> [!warning] 除非没有替代项，否则不要直接编辑注册表
> （Caution 级，官方原文）注册表编辑器"绕过标准安全措施，允许降低性能、损坏系统甚至要求重新安装 Windows 的设置"。**能用控制面板的程序或 MMC 安全地改的设置，就不要手动改注册表** [S8]。

> [!warning] 改错了，Microsoft 不能保证能修好
> （Warning 级，官方原文）"如果使用注册表编辑器或使用其他方法错误地修改了注册表，则可能会发生严重问题。这些问题可能需要重新安装操作系统才能解决。Microsoft 不能保证可以解决这些问题。" [S6]

> [!warning] 遇到权限不足的键：先取得所有权
> 官方给出的唯一解法是：启用 `SE_TAKE_OWNERSHIP_NAME` 特权，并以 `WRITE_OWNER` 权限打开该键 [S7]，即"把所有者改成自己，再赋完全控制"（见 2.6.3）。

> [!tip] 改之前的两件事
> 一是**备份并分清级别**：主路径导出 `.reg`（按键级）、进阶 `reg save` 出 `.hiv`（整键快照）、整机级是备份系统状态 [S18][S15][S6]；二是**先核对现有权限**：注册表编辑器 → 定位到键 →「编辑」>「权限」 [S7]。

### 2.8 查询、修改、删除：reg.exe 与 PowerShell 对照

前面把"为什么"和"怎么保命"讲完了，这一节才是命令清单。**所有修改类命令请在自建的键上练习**，不要拿系统关键键做实验。

下列 `reg` 命令块的权限标注统一为"官方未说明"（依据见 2.7.3 的 [!warning]）。顺带说明一条常被问到的：**修改 `HKEY_LOCAL_MACHINE` 下的键是否必须管理员权限，官方文档同样没有明示**，本章不推断——你在实际操作中如果被拒绝访问，请按 2.6.3 的"取得所有权"思路处理 [S7]。

#### 2.8.1 `reg query`：先看清楚，再动手

这是本章你**最应该熟练**的一条命令——它只读，不改任何东西。完整语法如下 [S9]：

```bat
reg query <keyname> [{/v <valuename> | /ve}] [/s] [/se <separator>] [/f <data>]
          [{/k | /d}] [/c] [/e] [/t <Type>] [/z]
```

各参数的含义 [S9]：

| 参数 | 作用 |
|---|---|
| `/s` | 递归查询所有子项和值 |
| `/f <data>` | 指定要搜索的数据或模式 |
| `/k` | 仅搜索**键名**——**必须与 `/f` 同时使用** |
| `/d` | 仅搜索**数据** |
| `/c` | 区分大小写 |
| `/e` | 仅返回**完全匹配**的结果 |
| `/t <Type>` | 限定类型，可选 `REG_SZ`、`REG_MULTI_SZ`、`REG_EXPAND_SZ`、`REG_DWORD`、`REG_BINARY`、`REG_NONE` |
| `/z` | 附带显示该类型的等效数字 |

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 查一个具体的值
reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion" /v ProgramFilesDir

:: 递归搜索：/k 表示只搜键名，必须与 /f 一起用
reg query "HKLM\SOFTWARE\Microsoft" /s /f asp.net /k

:: /ve 表示查询"没有值名称"的那个默认条目
reg query "HKLM\SOFTWARE" /ve
```

#### 2.8.2 `reg add`：新增值（但不能凭空造一棵子树）

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 新增一个二进制值（/f 免确认）
reg add "HKLM\Software\MyCo" /v Data /t REG_BINARY /d fe340ead /f

:: 新增一个多字符串值（\0 分隔各项）
reg add "HKLM\Software\MyCo" /v MRU /t REG_MULTI_SZ /d fax\0mail\0

:: 新增一个可扩充字符串值 —— 注意百分号要用 ^ 转义
reg add "HKLM\Software\MyCo" /v Path /t REG_EXPAND_SZ /d ^%systemroot^%
```

两条关键提示 [S10]：

- **`reg add` 无法通过此操作添加子树**——它能在已有路径下加值，但**不能一次性造出一整串新键**；
- **`REG_EXPAND_SZ` 类型的数据里，百分号 `%` 必须用插入符号 `^` 转义**，写成 `^%systemroot^%`。

`/t` 可选的类型清单：`REG_SZ`、`REG_MULTI_SZ`、`REG_DWORD`、`REG_DWORD_BIG_ENDIAN`、`REG_DWORD_LITTLE_ENDIAN`、`REG_BINARY`、`REG_LINK`、`REG_FULL_RESOURCE_DESCRIPTOR`、`REG_EXPAND_SZ` [S10]。

#### 2.8.3 `reg delete`：删值不是删键

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 危险操作 —— 动手前务必先 reg export 备份
reg delete "HKLM\Software\MyCo\MyApp\Timeout" /f
reg delete "HKLM\Software\MyCo" /v MTU /f
```

参数含义 [S11]：

- **`/va`**：删除指定键中的**所有值**，**但不会删除其中的子项**；
- **`/v <name>`**：删除特定的值；
- **`/ve`**：只删除"没有值名称"的那个默认条目；
- **`/f`**：免确认。

#### 2.8.4 `reg copy`：复制键

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: /s 表示连同该项下所有子项和值一起复制
reg copy "HKLM\Software\MyCo\MyApp" "HKLM\Software\MyCo\SaveMyApp" /s
```

两条行为 [S12]：**只有指定 `/s` 才会连同所有子项和条目一起复制**；而且**复制子项时此命令不要求确认**（不会弹提示）。

> [!tip] `reg copy` 页面有一处官方笔误
> `reg copy` 页面文末残留了"`reg 比较`作的返回值"字样（那是 `reg compare` 的文案没清理干净），与命令本体不对应，属官方页面笔误 [S12]。**引用返回值语义时以页面正文为准：0 = Success / 1 = Failure。**

#### 2.8.5 PowerShell 的等价写法与差异

同一批操作，PowerShell 侧用"Item / ItemProperty"这一组 cmdlet 完成 [S21]：

| 想做的事 | 用哪个 cmdlet |
|---|---|
| 设置值 | `Set-ItemProperty` |
| 新建值 | `New-ItemProperty` |
| 复制值 | `Copy-ItemProperty` |
| 移动值 | `Move-ItemProperty` |
| 重命名值 | `Rename-ItemProperty` |
| 删除值 | `Remove-ItemProperty` |
| 删除键 | `Remove-Item`（**项包含子项时默认弹确认**，加 `-Recurse` 免提示） |
| 清空整个键的所有值（保留键本身） | `Clear-Item` |

> 环境：PowerShell ｜ 版本：5.1 & 7 ｜ 权限：官方未说明

```powershell
# 只读：看一个值（不会改动任何东西）
Get-ItemProperty -Path HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion -Name "ProgramFilesDir"

# 写值：必须显式给出 -Type，否则默认写成 String
Set-ItemProperty -Path "HKCU:\Software\Demo" -Name "NoOfEmployees" -Value 823 -Type DWord

# 只删值，不删键
Remove-ItemProperty -Path "HKCU:\Software\Demo" -Name "NoOfEmployees"
```

两个最容易出错的差异：

> [!warning] `Set-ItemProperty` 的 `-Type` 默认是 `String`，不是自动判断
> `Set-ItemProperty` 的动态参数 `-Type` **默认为 `String`（也就是 `REG_SZ`）** [S21]。所以**写数字型的值时必须显式指定 `DWord` / `QWord`**，否则类型会被写成字符串——表面上看"值写进去了"，但类型错了，程序读到的就不是数字。可选值包括 `ExpandString`、`Binary`、`DWord`、`MultiString`、`QWord`、`Unknown`（`Unknown` 表示不受支持的类型，如 `REG_RESOURCE_LIST`） [S21]。

> [!warning] `Remove-Item` 和 `Clear-Item` 不是一回事
> **`Remove-ItemProperty` 只删值**；**`Remove-Item` 删的是键本身**，而且**当这个键里还有子项时，它默认会弹确认框**，只有加 `-Recurse` 才不提示 [S21]。另外 **`Clear-Item` 是把一个键的所有值清空，但保留键本身** [S21]。删错一个词，后果完全不同。

#### 2.8.6 官方提醒：能用管理接口就别直接改注册表

官方在讲注册表提供程序时给了一个很好的示范：把某个服务的启动类型从 Automatic 改成 Manual，**既可以**用 `Set-ItemProperty -Path $path -Name Start -Value 3` 直接写注册表值，**也可以**用 `Set-Service -Name Spooler -StartupType Automatic` 通过专用命令改回去 [S21]。

官方的意思很明确：**能通过管理接口改的，就别去动注册表值本身。**

#### 2.8.7 `reg` 的根键规则

`reg` 命令的 `keyname` **必须包含一个有效根键**。本地有效的根键有五个：`HKLM`、`HKCU`、`HKCR`、`HKU`、`HKCC`；而**指定远程计算机时，只有 `HKLM` 和 `HKU` 有效** [S9][S8]。

### 2.9 实用路径速查与开机自启

#### 2.9.1 开机自启一共四个键

`Run` 和 `RunOnce` 各有 HKLM 与 HKCU 两个版本，**共四个**，都在 `Software\Microsoft\Windows\CurrentVersion\` 下 [S19]：

| 用途 | 完整路径 |
|---|---|
| 所有用户，每次登录运行 | `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` |
| 所有用户，仅运行一次 | `HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce` |
| 当前用户，每次登录运行 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` |
| 当前用户，仅运行一次 | `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce` |

行为差异是这一节的核心 [S19]：

- `Run` 键让程序在**每次**用户登录时运行；
- `RunOnce` 键让程序运行**一次，然后删除该键**；
- 这些键的数据值是一条**不超过 260 个字符**的命令行，形式为 `说明-字符串 = 命令行`；
- **如果在同一个键下注册了多个程序，这些程序的运行顺序是不确定的**。

> [!note] 这些键是靠"登录事件"触发的
> 官方口径是：用 `Run` / `RunOnce` 注册表项**使程序在用户登录时运行**——`Run` 键是"每次用户登录时运行"，`RunOnce` 是"运行一次，然后删除该键" [S19]。所以"往 Run 里写东西"和"程序会运行"之间，中间那一步是**登录事件**——这也解释了为什么改完自启项，通常要重新登录甚至重启才看得到效果。

#### 2.9.2 `RunOnce` 的三个行为细节（与 `!`、`*` 前缀）

`RunOnce` 藏了三个容易记反的细节 [S19]：

1. **`HKLM\...\RunOnce` 仅在重新启动后、管理员组的成员登录时才执行**；
2. **删除值的时机**：`RunOnce` 默认在命令行**运行之前**删除值；如果**在值名称前加感叹号 `!`**，删除就会被**延迟到命令运行之后**。官方解释了原因：没有 `!` 前缀时，一旦这次运行失败，下次开机就不会再让关联程序运行了；
3. **安全模式**：默认情况下，**计算机以安全模式启动时会忽略这些键**；如果**在值名称前加星号 `*`**，就能**强制该程序在安全模式下也运行**。

> [!warning] `!` 和 `*` 是最容易记反的两个前缀
> 记法：**`!` 管"什么时候删"**（加了它 → 先运行后删；不加 → 先删后运行）；**`*` 管"安全模式跑不跑"**（加了它 → 安全模式也跑）[S19]。另外别忘最易忽略的那条：**`HKLM\...\RunOnce` 只在管理员组成员登录时才执行**——标准用户登录时它根本不会跑 [S19]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：官方未说明

```bat
:: 四个自启键分别看一眼（只读，安全）
reg query "HKLM\Software\Microsoft\Windows\CurrentVersion\Run"
reg query "HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce"
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run"
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce"
```

#### 2.9.3 文件关联三要素：verb、命令字符串、ProgID

右键菜单和文件关联之所以容易看晕，是因为三个词都要先解释 [S23][S24]：

- **verb（谓词）**：指右键菜单里的**一条命令项**。它对应的命令字符串形如 `"My Program.exe" "%1"`——**任何可能包含空格的元素都必须加引号**（这就是为什么程序路径外面要包一层引号） [S23]；
- **ProgID**：文件类型的**登记名**，标准格式是 `厂商或应用.组件.版本`，例如 `Word.Document.6` [S24]；
- **键位置**：`HKEY_CLASSES_ROOT\<ProgID>\shell\<verb>\command`，其中 `(Default)` 条目就是那条命令行 [S23]。

#### 2.9.4 一个免提权技巧

因为 HKCR 是 `HKCU\Software\Classes` 与 `HKLM\Software\Classes` 的组合（见 2.2.3），**可以把自定义的 verb 注册在 `HKEY_CURRENT_USER\Software\Classes` 下**——官方点明了这么做"**主要好处是不需要提升权限**" [S25]。

> 环境：cmd ｜ 版本：全版本适用 ｜ 权限：不需要提升权限（官方说明写在这个位置的主要好处就是免提权）[S25]

```bat
:: 示意：把一个自定义 verb 注册在当前用户名下（路径依据 S25，命令行形式依据 S23；非官方示例）
reg add "HKCU\Software\Classes\MyApp.Document\shell\MyVerb\command" /ve ^
  /d "\"My Program.exe\" \"%1\"" /f
```

> [!tip] 这条技巧为什么值得记住
> 它把 2.2.3 那条"不要直接写 HKCR"的规则变成了好处：写在 HKCU 那边，既符合官方要求，又**不需要管理员权限** [S25][S6]——这是本章里少数几条有官方明确权限说法的路径之一。

#### 2.9.5 实用路径速查表

下面只收录有官方来源的路径：

| 用途 | 路径 | 来源 |
|---|---|---|
| 开机自启（四键） | 见 2.9.1 的表 | [S19] |
| 文件右键菜单命令（verb） | `HKCR\<ProgID>\shell\<verb>\command` | [S23] |
| 某程序处理任意文件类型的默认过程 | `HKCR\Applications\<MyProgram.exe>\shell\...` | [S23] |
| 类级右键菜单（官方真实示例） | `HKEY_CLASSES_ROOT\DesktopBackground\Shell` | [S25] |
| 无需提权注册自定义 verb | `HKEY_CURRENT_USER\Software\Classes` | [S25] |
| 32 位程序在 64 位系统上的视图 | `HKEY_LOCAL_MACHINE\Software\WOW6432Node`（**保留键，不应直接使用**） | [S6][S20] |
| 硬件 / 即插即用历史 | `HKLM\HARDWARE`（含 `DESCRIPTION`、`DEVICEMAP`、`RESOURCEMAP`、`ACPI`、`UEFI`） | [S21][S1] |
| 用户配置文件 hive 的键位置 | `HKEY_USERS` 下，每个登录用户一个 | [S2] |
| 硬件配置文件信息 | `HKLM\System\CurrentControlSet\Hardware Profiles\Current`（即 `HKEY_CURRENT_CONFIG`） | [S4] |
| 系统信息的版本类路径 | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion` | [S22] |

> [!warning] 本章不写的一些"网上常见说法"
> 通配 verb 形态 `HKCR\*\shell`、以及"用某个键给**所有文件**加右键菜单"这类写法，**官方来源中没有出现**，本章**不写**，也不做推断 [S23][S25]。如果你想给某类文件加菜单项，请按 2.9.3 讲的 **ProgID 级** verb 来写。

> [!tip] 看到 `@%SystemRoot%\shell32.dll,-154` 这种值，别手动改
> 文件关联区里会出现形如 `@%SystemRoot%\shell32.dll,-154` 的"间接字符串"，看着像乱码 [S24]。**把它当成一条警告就够了：这类值由系统间接指向资源，不要去手动编辑它**——本章不解释它的语法。

### 本章小结

> [!summary] 小结
> - **四个基本词**：注册表是分层数据库（树），节点叫**键**，键下可同时有**子项**和**值**；键名不能含反斜杠、不本地化，值名称和数据可以含反斜杠 [S1]
> - **五个根键**：HKLM 管整机物理状态、HKCU 管当前用户（映射到 HKU 中该用户的分支，按进程建立）、HKCR **不是真实位置而是合并视图**、HKCC 只是别名、`HKEY_PERFORMANCE_DATA` 的数据并不真的在注册表里 [S4][S6]
> - **Hive 与磁盘文件**：机器级支持文件**大部分**在 `%SystemRoot%\System32\Config`；用户级 hive 的承载文件是 `NTUSER.DAT` / `NTUSER.DAT.LOG`，**其磁盘位置两份官方资料说法不一致、都没提现代路径**，故本章只用"用户配置文件目录"表述、不写死路径；`.log` / `.alt` / `.sav` **不要删** [S2][S6]
> - **值类型是三副面孔**：`REG_SZ` ↔ "字符串值" ↔ `-Type String`；`REG_DWORD` 是 32 位、`REG_QWORD` 是 64 位；`REG_MULTI_SZ` 结尾要**两个**隐藏结束符且**不能有空项**；字符串终止符是读写注册表最常见的陷阱 [S5][S6][S21]
> - **尺寸上限**：值名称 ≤16,383 字符；值数据 >2,048 字节要改存文件；一个键所有值合计 ≤64 K；`Run` 键命令行 ≤260 字符 [S6][S19]
> - **两套视图**：32 位与 64 位程序默认各看一套，32 位那套在 64 位程序眼里挂在 `WOW6432Node` 下（**保留键，不应直接使用**）；实际会用的只有 `/reg:32` 与 `/reg:64` [S20][S9][S6]
> - **备份与回滚（本章主线）**：主路径 = **导出 `.reg` → 需要时导入还原**（覆盖 Win11）[S18][S13][S14]；进阶 = `reg save` → `reg restore`（`.hiv`，官方明写"编辑前必须 reg save"）[S15][S16]；整机级 = 备份"系统状态" [S6]；**系统还原只作附注，不是回滚主路径**（官方版本声明存疑）[S26]
> - **两类备份别混**：**按键级**是导出 `.reg`（只保住导出的那个键）；**整机级**才是备份系统状态 [S6][S18]
> - **命令边界**：`reg add` **不能添加子树**；`reg delete /va` **只删值不删子项**；`Set-ItemProperty` 的 `-Type` **默认是 `String`**，写数字必须显式指定 [S10][S11][S21]
> - **自启四键**：`Run` 每次登录运行，`RunOnce` 一次后**删除该键**；`HKLM\...\RunOnce` **仅管理员组成员登录时执行**；值名前 `!` 把删除推迟到运行之后，`*` 强制在安全模式运行；**触发时机是"用户登录"，改完通常要重新登录或重启才生效** [S19]
> - **官方未说明的位置**（本章一律不推断）：`reg export / import / save / restore / load / unload` 以及 `reg query / add / delete / copy` 的管理员权限要求 [S13]–[S17]

下一章换一个战场：离开"怎么存、怎么配"，进入"怎么用命令批量操作"。我们会把 PowerShell 的两块硬骨头啃下来——为什么它管道里流动的是**对象**而不是文本，以及**执行策略**为什么"防的是手滑，不是防坏人"。
