## 第 2 章：素材工程化 —— 让 agent「读」视频，而不是「看」视频

第 1 章解决了「该不该交给 agent」。真决定要交给它时，下一个问题立刻冒出来：素材怎么给？agent 没有眼睛，一条 30 分钟的视频和一个装满几百个片段的文件夹，对它来说都是「看不见」的黑盒。这一章解决这个交付问题：把视频翻译成 agent 最擅长的三种材料——**文本、时间轴、结构化决策**，让素材从「只能人看的视频堆」变成「agent 也能读的工程」。全章核心一句话：**全片文本化 + 关键帧按需视觉化**。

### 2.1 反模式：把几万帧丢给 LLM，只会更糟

最直觉的做法，是把视频「喂」给大模型看：抽几千张帧，连视频带图塞进 prompt，让它凭画面给剪辑意见。video-use 作者把这叫「暴力看视频」：几万帧视频对 LLM 是几千万 token 的噪音，成本高、信息密度低，而且很难稳定复盘——模型看完说不出「第几秒该剪」，只会给一堆无法回放到具体位置的模糊印象（S6）。

> [!tip] 大白话
> 让 agent 逐帧「看」视频，等于塞给它一本没有目录、没有页码、每一页还长得差不多的书。它翻完只能复述「好像讲过素材工程化」，却说不出在哪一章哪一页。所以……先把视频变成带时间码的文本和清单，它才能像查资料那样精确回答「哪一秒、发生了什么」。

正确姿势是改「读」。browser-use 的思路早已示范过：浏览器 agent 不盯着网页截图，而是读 DOM；视频 agent 也不该只盯着帧，而要读一套可操作的时间轴（S6）。落到工程上就是两层读取：第一层用 ASR 把全片变成带时间戳的文本——便宜、可全文检索；第二层只在文本证据不足、必须判断画面时才按需看图——贵，所以省着用。下面几节按这两层展开。

### 2.2 转写层：逐词时间戳，把「废料」变成决策信号

第一层是音频转写，而且必须是**逐词时间戳**级别：每个词都带着开始/结束时间。video-use 用 ElevenLabs Scribe 实现，能拿到逐词时间戳、说话人区分和音频事件（S6）；本地想不花钱试，OpenAI Whisper 也能出词级时间戳，最小可用命令如下（完整参数速查见第 5 章《工具链速查》）：

```
whisper take01.mp4 --model small --word_timestamps True --output_format json --output_dir transcript/
```

产物是 JSON，每个片段带起止秒和文本，开启词级时间戳后每段内还有 `words` 数组（示意）：

```json
{ "start": 12.4, "end": 20.1,
  "text": "大家好。呃… 今天要讲的是素材工程化。",
  "words": [
    { "word": "大家好", "start": 12.4, "end": 13.6 },
    { "word": "呃",      "start": 14.9, "end": 15.6 },
    { "word": "今天",    "start": 17.8, "end": 18.3 }
  ] }
```

为什么强调逐词？因为**剪辑的主要决策信号藏在词与词的间隙里**（S6）。上面这段，agent 一眼就能算出三件事：13.6→14.9 之间 1.3 秒静音，是正常句间停顿；14.9 秒的「呃」是口癖，候选删除；15.6→17.8 长达 2.2 秒的停顿——对口播来说十有八九是重拍或冷场，是剪切点的高置信候选。停顿、口误、重复、笑声、掌声，这些对人是「废料」的东西，一旦带上时间码，全变成可检索、可定位、可下刀的决策信号（S6）。对口播、访谈、教程这类内容，剪辑判断本来就主要来自语言节奏，转写层一次性解决。

> [!warning] 转写质量是底座
> 整个流程的地基是转写质量：转写错了，后面的剪辑判断会跟着偏（S6）。所以第 5 章的 hard rules 会有一条「不能切在词中间，必须贴合逐词时间戳下刀」——前提就是时间戳本身得可靠。另注：Whisper 对中文的词级切分质量因模型与语速而异，个别词会被切开或粘连；若实测不准，退回「句级时间戳 + 短句」也够用，只是定位粒度变粗（推断，需本机实测）。

### 2.3 汇总层：takes_packed.md，把一堆素材压成一份决策文件

一个项目往往不止一条素材：三五条口播、每条两三遍 take。让 agent 自己去十几个文件里翻不现实。video-use 的做法，是把所有转写压成一个 `takes_packed.md`，让 agent 用文本一次性「读完」整个素材库（S6）。

> [!tip] 大白话
> 把多段素材压成一份 takes_packed.md，相当于把几十小时素材的「台词 + 时间码 + 备注」抄进同一本导演工作手册。导演不用熬夜拉片，翻手册就能圈出哪几镜能用、哪几句要删。所以……这个文件是给 agent 读的地图；先有地图，后面才谈得上让 agent 提剪辑方案。

一个最小实现：脚本遍历 `transcript/` 下的 Whisper JSON，逐段摊平成 Markdown 表格：

```python
# scripts/pack_takes.py —— 汇总转写为单一决策文件（示意）
import json
from pathlib import Path

rows = []
for jf in sorted(Path("transcript").glob("*.json")):
    data = json.loads(jf.read_text(encoding="utf-8"))
    for seg in data["segments"]:
        rows.append(f"| {jf.stem} | {seg['start']:.2f}-{seg['end']:.2f} | {seg['text'].strip()} |")

Path("takes_packed.md").write_text(
    "# takes_packed\n\n| take | 时间范围 | 内容 |\n|---|---|---|\n" + "\n".join(rows),
    encoding="utf-8")
```

真项目里，这份文件还该带素材元信息：某段属于哪条 take、哪些段落被标为「口误 / 重复 / 最佳 take」。它不需要漂亮，只需要**每一行都可被时间码精确定位**——这决定了第 3 章《流水线设计与角色分工》里 agent 能不能提出「可执行、可回放」的剪辑策略，而不是含糊的一句「这段节奏不好」。

### 2.4 视觉层：按需「看图」，且只看局部

文本化解决大部分决策，但不是全部：判断停顿是否自然、重拍是否穿帮、切点画面是否连贯，光看字不够。video-use 的处理是**按需视觉检查**——只有需要判断画面时才生成局部 timeline 合成视图，把胶片帧、波形、词标签、静音间隔拼在同一张图里（S6），而不是全片抽帧。

> [!example] 简版：自己拼一个「局部证据窗」
> timeline_view 是 video-use 项目自带的工具；自己搭最小流水线时，可以用 ffmpeg 针对一个可疑时间窗抽帧，再对着 takes_packed.md 里的词标签复核：
> ```
> # 抽 take01.mp4 第 40–45 秒、每秒一帧，做局部画面核对
> ffmpeg -ss 40 -t 5 -i take01.mp4 -vf "fps=1" preview/win40_%02d.jpg
> ```

为什么强调「局部」？两个原因。一是 token：全片抽帧会退回 2.1 的反模式；只抽可疑窗口，成本可控（推断：视觉 token 单价高于文本，「能省则省」是这套分层设计的动机，S6 的行文也指向这一点）。二是上下文：单张孤立的帧没有时间语义，agent 看不出它前后的停顿与话头；而「胶片帧 + 波形 + 词标签 + 静音间隔」的合成视图，把画面证据和它所在的时间轴上下文绑在一起，agent 才知道这张图对应「哪句词之前的冷场」。判断准则一句话：**默认用文本判断；文本证据不足才看图；看图只看可疑窗口**。

### 2.5 专业版：源时间决策记录，把剪辑变成「基于证据的决策」

把「读」再推进一步的，是 Timeline Studio 的做法（S5）。它在改时间线前先做多模态分析——ASR、OCR、镜头切换、主体区域光流、音频能量、人物表情变化——但分析结果不直接变成剪辑操作，而是先沉淀成一条条「源时间决策记录」：

```json
{
  "assetId": "demo-recording",
  "sourceRange": { "start": 42.8, "end": 50.3 },
  "decision": "keep",
  "role": "primary-peak",
  "reason": "完整展示任务执行后的可见结果",
  "confidence": 0.94,
  "protectedFrames": [47.2, 48.1]
}
```

每个字段都是一道护栏：`sourceRange` 锁定这段素材的源时间范围；`decision` 是保留 / 删除 / 缩短 / 重排；`role` 说明它在叙事里承担什么角色（setup / rise / pre-impact / primary-peak / aftershock / bridge 等）；`reason` 记录为什么这么决定；`confidence` 给这条决策标把握度；`protectedFrames` 标出「绝不能删的关键画面」。这套设计让自动剪辑从「应用固定规则」（见到静音就删）变成「基于证据做编辑决策」（S5）——同一个「删静音」动作，一旦有了任务语境，才不会误删刻意保留的停顿或产品结果展示画面。

> [!tip] 大白话
> 源时间决策记录 = 剪辑版的证据链。每一刀都写清「切源素材的哪几秒、留还是删、为什么、有几成把握、哪几帧是命根子不能动」。所以……机器剪完，人能像审案卷一样逐条过；某条不同意，改的是这条记录，而不是让 agent 把整条片子重剪一遍。

对我们普通用户的启发：不必复刻 Timeline Studio 的全部工程，但这几个字段的**思想**可以直接借到第 3 章的镜头清单里——只要你打算让 agent 批量产出剪辑提案，就要求它每一条都带 `sourceRange + reason + confidence`。字段一旦被要求填写，agent 的「我觉得这里该剪」就会被逼成「这里该剪，因为……，把握……」，这也是全书 human-in-the-loop 主线最早的落地抓手。

### 本章小结

- 反模式：把几万帧丢给 LLM = token 噪音、难复盘；正确姿势是「读」——全片文本化 + 关键帧按需视觉化（S6）。
- 转写层：ASR 逐词时间戳把停顿 / 口误 / 笑声 / 掌声变成可定位的决策信号；对口播 / 访谈 / 教程，剪辑决策主要来自语言节奏（S6）。
- 汇总层：多素材压成单一 `takes_packed.md`，每行可被时间码定位，agent 才能一次性「读完」素材库（S6）。
- 视觉层：只在文本证据不足时看局部 timeline 合成视图（胶片帧 + 波形 + 词标签 + 静音间隔），不是全片抽帧（S6）。
- 专业版：源时间决策记录（sourceRange / decision / reason / confidence / protectedFrames / role）把剪辑变成「基于证据的决策」（S5），字段思想可直接借用到自己的镜头清单。
