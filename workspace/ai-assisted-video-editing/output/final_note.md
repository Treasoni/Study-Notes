# AI 助手辅助视频剪辑的方法与工作流

这份笔记回答一个实际问题：拿着 Codex CLI、Claude Code 这类编码 agent，它到底能在「剪视频」这件事上帮到哪一步，以及怎么把「素材准备 → 剪辑策略 → 安全执行 → 验证精修」搭成一套可复用的人机协作流程。全篇主线一句话：agent 把「不可读的视频堆」变成「可检查的剪辑工程」并批量产出提案，而方向、审美与最终批准始终留在人手里。围绕这条主线，七章依次回答「该不该交给它、素材怎么给、流水线怎么搭、命令怎么安全地跑、命令细节怎么用、怎么算剪完、翻车与账本怎么算」，最后收敛到全书那条判断标准——模板化内容用 agent，创意表达留自己。

## 第 1 章：AI 剪视频，到底能帮你做到哪一步

在把任何素材丢给 AI 流程之前，先花十分钟回答一个前置问题：agent 到底能帮到哪一步。这个方向判断错了，后面 pipeline 搭得再顺，也是在给错误的场景铺路。这一章不写命令，只做三件事：给 agent 一个准确的角色定位、划清能与不能的边界、学会在动手前判断「这单该不该交给它」。

### 1.1 能力画像：agent = 编排层，不是剪辑器

Codex CLI、Claude Code 这类编码 agent 与剪映 / PR 的差别，不在「会不会剪」，而在**交互通道**：它没有 GUI，也没有「眼睛」，只能在一个沙箱化 shell 里用命令驱动确定性工具——ffmpeg 转码、Whisper 转写、批量脚本（来源 S1、S3）。理解这一点，是全书的地基。

> [!tip] 大白话
> 把 agent 想成一个蒙着眼、但手速极快的车间操作员：他不「看」成品，只照你递的图纸干活。你告诉他「剪掉第 3–10 秒、音量统一到 -14 LUFS」，他能通宵干一百条；你问他「这段节奏哪里不对」，他答不上来。所以……你负责决定「剪成什么样」，他负责「稳定地剪完」。

由此得到定位：agent 是**编排层 / 操作员**，不是剪辑器。它的价值在于把「你要的效果」翻译成可执行、可复现、可批量跑的确定性命令，并基于工具输出做逻辑判断；凡依赖「看着画面做审美决定」的环节，它天然缺位。

### 1.2 两张清单：能稳定接管 vs 别指望它

**能稳定接管**（来源 S3、S4）：批量转码 / 裁剪 / 拼接，删停顿、口误与废话，长视频拆条，字幕识别与烧录，响度 / 格式 / 比例统一，多平台变体导出，代理与缩略图生成。共同点：目标可描述、验收可量化、重复性高。

**不能稳定接管**（来源 S3、S4）：节奏（机器裁剪天然「平均化」、没有呼吸感）、情绪与故事张力、逐帧精剪、判断「这里该不该插 B-roll」、品牌表述准确性、音乐与肖像等权利审查。共同点：判断依赖审美与上下文，写不成确定性规则。

> [!warning] 判断口诀
> 拿不准一项活能不能交给 agent，就问一句：**它能不能写成一条可验收的规则？** 能，大概率能稳定接管；不能，属于人的保留地。

### 1.3 结构性盲区：agent 为什么会「自信地错下去」

比「不能做」更隐蔽的是**结构性盲区**：有些错误在静态分析里根本不可见，agent 看不到，于是会在错误的方案内反复调参。典型是 concat 无损拼接引发的音画漂移——这类故障只在播放时暴露，查元数据、跑校验命令都看不出毛病。有社区实测报告拼接后音画漂移累计可达 14.86 秒，作者记录了 debug 到深夜的全过程（社区实测，非权威数据，见文末 dev.to 链接）；而「agent 会因此反复调参却越改越远」是基于其工作方式的推断。

> [!tip] 大白话
> 这像装修队只照图纸、从不去现场：图纸上墙是直的，实际墙体早歪了，他们只会反复研究「怎么把砖贴得更齐」，不知道方向从一开始就错了。所以……凡「只能在成品上靠眼睛发现」的问题，都要由人设验证点兜住，不能指望 agent 自查。

### 1.4 效率真相：模板化 vs 创意

效率数字必须分场景看。以下来自社区二手聚合、含营销水分，只作定性参考（来源 S4）：

- **模板化内容**（口播 / 拆条 / 带货 / 知识讲解）：11.2 小时的口播素材，机器处理约 10 分钟、人工复核约 40 秒出一条；日产出可从 6 条提到 30 条。结构固定、套路明确，agent 提效显著。
- **创意内容**：一个反例——改 6 版花了 6 小时。当方向、审美、叙事都要人反复定夺时，agent 的「快」没有意义，反而放大迭代成本。

所以全书反复出现的那条判断标准，第一章先立在这里：**模板化内容用 agent，创意表达留自己**（来源 S4）。

### 本章小结

- agent = 编排层 / 操作员：无 GUI、无「眼睛」，经沙箱 shell 驱动 ffmpeg / Whisper 等确定性工具（来源 S1、S3）。
- 能稳定接管的活，共同点是「可写成规则、验收可量化」；不能接管的，共同点是「靠审美与上下文」。
- 结构性盲区（如 concat 音画漂移）静态分析不可见，agent 会「自信地错下去」，需要人设验证点兜底。
- 效率真相分场景：模板化内容显著提效，创意内容「6 小时改 6 版」说明快是双刃剑。
- 判断标准一条：模板化用 agent，创意留自己。

## 第 2 章：素材工程化 —— 让 agent「读」视频，而不是「看」视频

第 1 章解决了「该不该交给 agent」。真决定要交给它时，下一个问题立刻冒出来：素材怎么给？agent 没有眼睛，一条 30 分钟的视频和一个装满几百个片段的文件夹，对它来说都是「看不见」的黑盒。这一章解决这个交付问题：把视频翻译成 agent 最擅长的三种材料——**文本、时间轴、结构化决策**，让素材从「只能人看的视频堆」变成「agent 也能读的工程」。全章核心一句话：**全片文本化 + 关键帧按需视觉化**。

### 2.1 反模式：把几万帧丢给 LLM，只会更糟

最直觉的做法，是把视频「喂」给大模型看：抽几千张帧，连视频带图塞进 prompt，让它凭画面给剪辑意见。video-use 作者把这叫「暴力看视频」：几万帧视频对 LLM 是几千万 token 的噪音，成本高、信息密度低，而且很难稳定复盘——模型看完说不出「第几秒该剪」，只会给一堆无法回放到具体位置的模糊印象（S6）。

> [!tip] 大白话
> 让 agent 逐帧「看」视频，等于塞给它一本没有目录、没有页码、每一页还长得差不多的书。它翻完只能复述「好像讲过素材工程化」，却说不出在哪一章哪一页。所以……先把视频变成带时间码的文本和清单，它才能像查资料那样精确回答「哪一秒、发生了什么」。

正确姿势是改「读」。browser-use 的思路早已示范过：浏览器 agent 不盯着网页截图，而是读 DOM；视频 agent 也不该只盯着帧，而要读一套可操作的时间轴（S6）。落到工程上就是两层读取：第一层用 ASR 把全片变成带时间戳的文本——便宜、可全文检索；第二层只在文本证据不足、必须判断画面时才按需看图——贵，所以省着用。下面几节按这两层展开。

### 2.2 转写层：逐词时间戳，把「废料」变成决策信号

第一层是音频转写，而且必须是**逐词时间戳**级别：每个词都带着开始/结束时间。video-use 用 ElevenLabs Scribe 实现，能拿到逐词时间戳、说话人区分和音频事件（S6）；本地想不花钱试，OpenAI Whisper 也能出词级时间戳，最小可用命令如下（完整参数速查见第 5 章《工具链速查》）：

```
whisper take01.mp4 --model small --word_timestamps True --output_format json --output_dir transcript/
```

产物是 JSON，每个片段带起止秒和文本，开启词级时间戳后每段内还有 `words` 数组（示意）：

```json
{ "start": 12.4, "end": 20.1,
  "text": "大家好。呃… 今天要讲的是素材工程化。",
  "words": [
    { "word": "大家好", "start": 12.4, "end": 13.6 },
    { "word": "呃",      "start": 14.9, "end": 15.6 },
    { "word": "今天",    "start": 17.8, "end": 18.3 }
  ] }
```

为什么强调逐词？因为**剪辑的主要决策信号藏在词与词的间隙里**（S6）。上面这段，agent 一眼就能算出三件事：13.6→14.9 之间 1.3 秒静音，是正常句间停顿；14.9 秒的「呃」是口癖，候选删除；15.6→17.8 长达 2.2 秒的停顿——对口播来说十有八九是重拍或冷场，是剪切点的高置信候选。停顿、口误、重复、笑声、掌声，这些对人是「废料」的东西，一旦带上时间码，全变成可检索、可定位、可下刀的决策信号（S6）。对口播、访谈、教程这类内容，剪辑判断本来就主要来自语言节奏，转写层一次性解决。

> [!warning] 转写质量是底座
> 整个流程的地基是转写质量：转写错了，后面的剪辑判断会跟着偏（S6）。所以第 5 章的 hard rules 会有一条「不能切在词中间，必须贴合逐词时间戳下刀」——前提就是时间戳本身得可靠。另注：Whisper 对中文的词级切分质量因模型与语速而异，个别词会被切开或粘连；若实测不准，退回「句级时间戳 + 短句」也够用，只是定位粒度变粗（推断，需本机实测）。

### 2.3 汇总层：takes_packed.md，把一堆素材压成一份决策文件

一个项目往往不止一条素材：三五条口播、每条两三遍 take。让 agent 自己去十几个文件里翻不现实。video-use 的做法，是把所有转写压成一个 `takes_packed.md`，让 agent 用文本一次性「读完」整个素材库（S6）。

> [!tip] 大白话
> 把多段素材压成一份 takes_packed.md，相当于把几十小时素材的「台词 + 时间码 + 备注」抄进同一本导演工作手册。导演不用熬夜拉片，翻手册就能圈出哪几镜能用、哪几句要删。所以……这个文件是给 agent 读的地图；先有地图，后面才谈得上让 agent 提剪辑方案。

一个最小实现：脚本遍历 `transcript/` 下的 Whisper JSON，逐段摊平成 Markdown 表格：

```python
# scripts/pack_takes.py —— 汇总转写为单一决策文件（示意）
import json
from pathlib import Path

rows = []
for jf in sorted(Path("transcript").glob("*.json")):
    data = json.loads(jf.read_text(encoding="utf-8"))
    for seg in data["segments"]:
        rows.append(f"| {jf.stem} | {seg['start']:.2f}-{seg['end']:.2f} | {seg['text'].strip()} |")

Path("takes_packed.md").write_text(
    "# takes_packed\n\n| take | 时间范围 | 内容 |\n|---|---|---|\n" + "\n".join(rows),
    encoding="utf-8")
```

真项目里，这份文件还该带素材元信息：某段属于哪条 take、哪些段落被标为「口误 / 重复 / 最佳 take」。它不需要漂亮，只需要**每一行都可被时间码精确定位**——这决定了第 3 章《流水线设计与角色分工》里 agent 能不能提出「可执行、可回放」的剪辑策略，而不是含糊的一句「这段节奏不好」。

### 2.4 视觉层：按需「看图」，且只看局部

文本化解决大部分决策，但不是全部：判断停顿是否自然、重拍是否穿帮、切点画面是否连贯，光看字不够。video-use 的处理是**按需视觉检查**——只有需要判断画面时才生成局部 timeline 合成视图，把胶片帧、波形、词标签、静音间隔拼在同一张图里（S6），而不是全片抽帧。

> [!example] 简版：自己拼一个「局部证据窗」
> timeline_view 是 video-use 项目自带的工具；自己搭最小流水线时，可以用 ffmpeg 针对一个可疑时间窗抽帧，再对着 takes_packed.md 里的词标签复核：
> ```
> # 抽 take01.mp4 第 40–45 秒、每秒一帧，做局部画面核对
> ffmpeg -ss 40 -t 5 -i take01.mp4 -vf "fps=1" preview/win40_%02d.jpg
> ```

为什么强调「局部」？两个原因。一是 token：全片抽帧会退回 2.1 的反模式；只抽可疑窗口，成本可控（推断：视觉 token 单价高于文本，「能省则省」是这套分层设计的动机，S6 的行文也指向这一点）。二是上下文：单张孤立的帧没有时间语义，agent 看不出它前后的停顿与话头；而「胶片帧 + 波形 + 词标签 + 静音间隔」的合成视图，把画面证据和它所在的时间轴上下文绑在一起，agent 才知道这张图对应「哪句词之前的冷场」。判断准则一句话：**默认用文本判断；文本证据不足才看图；看图只看可疑窗口**。

### 2.5 专业版：源时间决策记录，把剪辑变成「基于证据的决策」

把「读」再推进一步的，是 Timeline Studio 的做法（S5）。它在改时间线前先做多模态分析——ASR、OCR、镜头切换、主体区域光流、音频能量、人物表情变化——但分析结果不直接变成剪辑操作，而是先沉淀成一条条「源时间决策记录」：

```json
{
  "assetId": "demo-recording",
  "sourceRange": { "start": 42.8, "end": 50.3 },
  "decision": "keep",
  "role": "primary-peak",
  "reason": "完整展示任务执行后的可见结果",
  "confidence": 0.94,
  "protectedFrames": [47.2, 48.1]
}
```

每个字段都是一道护栏：`sourceRange` 锁定这段素材的源时间范围；`decision` 是保留 / 删除 / 缩短 / 重排；`role` 说明它在叙事里承担什么角色（setup / rise / pre-impact / primary-peak / aftershock / bridge 等）；`reason` 记录为什么这么决定；`confidence` 给这条决策标把握度；`protectedFrames` 标出「绝不能删的关键画面」。这套设计让自动剪辑从「应用固定规则」（见到静音就删）变成「基于证据做编辑决策」（S5）——同一个「删静音」动作，一旦有了任务语境，才不会误删刻意保留的停顿或产品结果展示画面。

> [!tip] 大白话
> 源时间决策记录 = 剪辑版的证据链。每一刀都写清「切源素材的哪几秒、留还是删、为什么、有几成把握、哪几帧是命根子不能动」。所以……机器剪完，人能像审案卷一样逐条过；某条不同意，改的是这条记录，而不是让 agent 把整条片子重剪一遍。

对我们普通用户的启发：不必复刻 Timeline Studio 的全部工程，但这几个字段的**思想**可以直接借到第 3 章的镜头清单里——只要你打算让 agent 批量产出剪辑提案，就要求它每一条都带 `sourceRange + reason + confidence`。字段一旦被要求填写，agent 的「我觉得这里该剪」就会被逼成「这里该剪，因为……，把握……」，这也是全书 human-in-the-loop 主线最早的落地抓手。

### 本章小结

- 反模式：把几万帧丢给 LLM = token 噪音、难复盘；正确姿势是「读」——全片文本化 + 关键帧按需视觉化（S6）。
- 转写层：ASR 逐词时间戳把停顿 / 口误 / 笑声 / 掌声变成可定位的决策信号；对口播 / 访谈 / 教程，剪辑决策主要来自语言节奏（S6）。
- 汇总层：多素材压成单一 `takes_packed.md`，每行可被时间码定位，agent 才能一次性「读完」素材库（S6）。
- 视觉层：只在文本证据不足时看局部 timeline 合成视图（胶片帧 + 波形 + 词标签 + 静音间隔），不是全片抽帧（S6）。
- 专业版：源时间决策记录（sourceRange / decision / reason / confidence / protectedFrames / role）把剪辑变成「基于证据的决策」（S5），字段思想可直接借用到自己的镜头清单。

## 第 3 章：流水线设计与角色分工 —— 从需求到成片

第 1 章回答「该不该交给 agent」，第 2 章回答「素材怎么让 agent 读」。但真正动手剪一条片子时，你面对的不是单条命令，而是一串环节：素材从哪来、每一步产出什么、谁有权拍板。这一章给出一条可复用的阶段化流水线骨架，讲清每一站会吐出什么「可检查的中间产物」，并把「agent 提案、人批准」的角色分工落到每个环节上。

### 3.1 一条骨架：从只读素材到平台变体

把多份素材剪成成片，本质是把「不可读的视频堆」逐级翻译成「越来越接近成品的可检查工程」。综合三份实现报告，一条收敛后的流水线骨架如下（来源 S3/S5/S6）：

```mermaid
flowchart LR
    A[素材：只读源 + 受控项目夹] --> B[inventory 转写/盘点]
    B --> C[剪辑策略 / 镜头清单提案]
    C --> D[人审候选：缩略图 / 入出点边界]
    D -- 打回 --> C
    D -- 通过 --> E[生成 JSON/CSV 中间时间线或 EDL]
    E --> F[校验]
    F -- 失败 --> E
    F --> G[渲染 preview]
    G --> H[逐切点自检]
    H --> I[人工进剪映/PR 精修]
    I --> J[锁 master]
    J --> K[平台变体导出]
```

读这张图有三个要点。

第一，**每一站都吐出一件「能单独检查」的东西**，而不是把所有工作攒到最后一次性揭晓。素材入库后是 inventory（转写/盘点文件），之后是镜头清单，再之后是中间时间线、校验报告、preview 成片。只要某一步的产物能被单独打开检查，人就不必「等到渲染完才发现方向错了」。

第二，**中间夹着两个必须由人拍板的闸门**：镜头清单要人审，精修后要人锁 master。这正是「human-in-the-loop」的含义——agent 可以高速跑完大多数环节，但「剪成什么样」由人在闸门处决定。

第三，回环是常态不是异常。人审打回镜头清单、校验失败退回中间时间线，都是设计内的路径，不是事故。流水线的价值不是「一次走通」，而是「每次返工都发生在更便宜的环节」——打回一张表，远比渲染完再推翻便宜。

### 3.2 谁负责：agent 提案，人批准

这张表把 11 个阶段的责任人摊开。判据沿用全书主线：**agent 把不可读的视频堆变成可检查的剪辑工程，人保留方向、审美与最终批准**（来源 S5/S6）。

| 阶段 | 谁主导 | 人的动作 | 关键产物 |
|---|---|---|---|
| 素材入库 | 人定规则 | 划定只读源与受控项目夹 | 只读素材 + 工作副本 |
| inventory 转写/盘点 | agent | 抽查转写/盘点是否漏错 | `takes_packed.md`（上一章的单一决策文件） |
| 剪辑策略 / 镜头清单提案 | agent | 给定方向（受众、CTA、风格） | 镜头清单（草案） |
| 人审候选 | 人 | 对缩略图/边界逐条批 | `review_status` 打标的镜头清单 |
| 生成中间时间线 / EDL | agent | — | `.json` / `.csv` / `.edl` |
| 校验 | agent | 复核关键项 | 校验报告 |
| 渲染 preview | agent | — | `preview.mp4` |
| 逐切点自检 | agent + 人 | 快速过一遍 preview | 自检清单 |
| 人工精修（剪映/PR） | 人 | 节奏、审美、品牌、权利 | 精修工程 |
| 锁 master | 人 | 最终批准 | master 成片 |
| 平台变体导出 | agent | 抽查各变体 | 各平台成片 |

注意两点。其一，「inventory」这一步的产物和方法是上一章的主角：ASR 逐词时间戳转写、汇总成 `takes_packed.md`。在流水线语境里，它是第二站的输入，不是可选项。其二，「人审候选」发生在生成任何时间线之前——agent 只提交「缩略图 + 入出点边界」供人快速判断，而不是提交一段粗剪让你再看一遍视频（来源 S3）。这正是把决策成本从「看视频」压到「看表格」的关键设计。

正因中间有这些确认点，这条流水线天然不适合「完全无人批量」；要不要牺牲确认点换一键自动，是第 7 章反模式要算的账，本章先记下这个取舍。

### 3.3 中间产物：镜头清单、EDL 与 .timeline

流水线里流动的不是视频，而是三种形态的「中间时间线」。分清它们，才不会在交接时把格式和用途搞混：

- **镜头清单（shot manifest）**：面向人审的决策表。描述「打算怎么剪」——用哪段素材、放在哪个叙事位置、是否已获批。
- **中间时间线 JSON/CSV / EDL**：面向机器执行的时间线。描述「按什么顺序、取哪段、拼成多长」，喂给校验与渲染。
- **.timeline 工程包**：面向后续编辑的交付物。人拿进剪映/PR 继续精修的入口（详见 3.5）。

镜头清单的字段设计直接决定「人审」是否高效。参考 S3 的做法，一条镜头至少应带这些字段（来源 S3）：

```json
{
  "shot_id": "shot_014",
  "beat_type": "proof",
  "asset_id": "take_07.mov",
  "source_in-out": { "in": 12.34, "out": 18.9 },
  "voice_line": "于是我们测了三个方案，只有这个在真机上扛住了",
  "caption_id": "cap_014",
  "review_status": "pending"
}
```

逐字段看：

- `beat_type` 是这条镜头承担的**叙事功能**，取值来自对参考片的拆解（hook/context/proof/objection/transition/CTA，见 3.4）。
- `asset_id` 是素材唯一标识，`source_in-out` 是它在**原始素材**上的入出点。注意这里的入出点是「源素材时间轴」，不是输出时间轴——字幕要用输出时间轴，是第 5 章的 hard rule，两者别混。
- `voice_line` 是对应台词/口播文本，供人不用开视频就能核对内容；`caption_id` 关联字幕条目，保证字幕与语音的对应关系在流程里可追踪（来源 S3）。
- `review_status` 是人审的落点。取值建议为 `pending / approved / replaced / rejected`（此为建议值，推断）：pending 待审，approved 放行，rejected 打回，replaced 表示「这镜被替换过」——这个状态要保留，因为它让「返工历史」可见。

JSON 适合机器读写，但给人审时 CSV 更易在表格里批量勾选。CSV 无法表达嵌套的 `source_in-out` 对象，就把它摊平为两列：

```csv
shot_id,beat_type,asset_id,source_in,source_out,voice_line,caption_id,review_status
shot_014,proof,take_07.mov,12.34,18.90,于是我们测了三个方案只有这个扛住了,cap_014,pending
shot_015,hook,take_02.mov,0.00,6.50,90%的人剪口播都在做无用功,cap_015,pending
shot_016,cta,take_09.mov,40.10,45.00,评论区告诉我你的剪法,cap_016,pending
```

> [!tip] 大白话
> 把镜头清单想成后厨的传菜单：每行写清「用哪份原料（asset_id）、取哪一段（source_in-out）、做成哪道菜（beat_type）」，人坐在传菜口对着单子打勾，不必每道菜都亲自下锅。所以……「审一张表」比「审一遍视频」便宜一个数量级，这就是 agent 能批量提案、人只做判断题的基础。

清单审完，agent 把 `review_status == approved` 的镜头编译成中间时间线。需要与外部剪辑软件交换时，可再导出 EDL。EDL 是剪辑业的通用交换格式，用**帧时码**而非秒——下面这段是示意（按 25fps 折算、只列视频轨，真实 EDL 需按轨道展开）：

```edl
TITLE: 平台讲解版_r1
FCM: NON-DROP FRAME

001  AX       V     C        00:00:00:00 00:00:06:12 00:00:00:00 00:00:06:12
*FROM CLIP NAME: take_02.mov

002  AX       V     C        00:00:12:08 00:00:18:22 00:00:06:12 00:00:12:26
*FROM CLIP NAME: take_07.mov
```

镜头清单审完就直接进入执行，前提是它被设计成**可局部替换**。这引出 S3 的一条关键约定：**拒一镜，只换一个引用，而不是重建整条时间线**（来源 S3）。人打回某镜时，agent 只替换这一镜的引用——换 `asset_id` 或改 `source_in-out` 的入出点，其他镜头的引用原样保留，然后整体升一个修订号，重新走校验。为什么能这么省？因为每条镜头都带 `beat_type`，叙事结构由 beat 序列承担；换掉某段的素材，故事顺序并不受影响，返工的 diff 很小、复核很快，也不会引发连锁误差。

> [!tip] 大白话
> 把「重建」想成推倒整面墙重砌，把「换引用」想成只抽换其中一块砖：墙的结构（故事顺序）没动，换完拿尺子量一下（diff）就能确认。所以……镜头清单要按「一镜一引用」设计，让人审的返工成本从「整组重剪」降到「换一块砖」。

### 3.4 参考片拆解：「功能拍」不是逐镜头抄

很多人让 agent「照着这条爆款剪」，这是对参考片的误用。参考片的价值不在运镜和 B-roll，而在**结构**：它每一段在说服/吸引观众这件事上承担什么任务。S3 的做法是把参考片切成「功能拍」，逐一标注功能（来源 S3）：

| 功能拍 | 它解决什么问题 |
|---|---|
| hook | 开头抓注意力：反常识、悬念、利益点 |
| context | 交代背景与问题 |
| proof | 给证据：演示、数据、实测 |
| objection | 预判并回应观众质疑 |
| transition | 转场，把叙事推到下一段 |
| CTA | 收尾引导行动：关注、评论、下单 |

拆解时不要抄参考片的画面，只抄它的**功能序列**。比如一条参考片的结构是 hook → context → proof → CTA，那你的镜头清单也按这个 beat 顺序搭骨架；然后从**你自己的素材库**里，为每个 beat_type 找对应的镜头——参考片 hook 用了一个反常识提问，你要找的是自己素材里「哪段最像钩子」，而不是复刻它的开场画面。

这套词汇同时回填到镜头清单的 `beat_type` 字段：`beat_type` 的合法取值就是这六个功能拍。于是「拆参考片」和「写镜头清单」共用同一套语言——参考片负责定骨架，镜头清单负责往骨架里填你的素材。这也是 3.3 里「拒一镜只换引用」能成立的深层原因：每条镜头的叙事身份（beat）是稳定的，变的只是填充它的素材。

### 3.5 交付物约定：成片 + 可编辑工程双输出

流水线的终点不是一条视频，而是**两件东西**（来源 S5/S6）：

1. **成片**：preview 与最终导出的各平台变体（横版/竖版、不同字幕、不同时长）。
2. **可编辑工程**：`.timeline` 工程包或 `edit/` 输出目录，连同镜头清单、中间时间线一起保留。

为什么「工程」和「成片」一样重要？因为人必须保留最终精修权——节奏、审美、品牌准确性、权利审查都发生在精修环节，而人需要一条「不必从零开始」的入口。只交一条渲染好的 mp4，等于把「最后一公里」的编辑权也交给了流程；交一份可编辑工程，人才能在剪映/PR 里接手第 9 站的精修。

两个配套约定值得现在就立下（推断，细化在第 6 章验证门展开）：

- **preview 与导出用同一套合成规则**。preview 不是「示意一下」的假货，它和最终导出走相同的字幕、裁切、拼接逻辑，否则「审 preview 通过、导出翻车」会反复发生（来源 S5/S6）。
- **可编辑工程的形态因工具而异**。走 PR，EDL 或中间时间线可直接导入成粗剪轨道；走剪映，草稿互操作属版本敏感、无稳定公开 schema，需保守处理（来源 S3）。双交付的真正含义是「中间产物与成片同源、可据此重建」，而不是承诺任何软件都能一键打开 `.timeline`。

### 本章小结

- 标准流水线：只读源 + 受控项目夹 → inventory → 镜头清单提案 → 人审候选 → 中间时间线/EDL → 校验 → preview → 逐切点自检 → 人工精修 → 锁 master → 平台变体导出；每站都吐可单独检查的产物。
- 角色分工：agent 把不可读视频堆变成可检查剪辑工程并批量提案；人在「镜头清单审」和「锁 master」两个闸门保留方向、审美与最终批准。
- 中间产物三形态：镜头清单（人审决策表）、JSON/CSV/EDL 中间时间线（机器执行）、`.timeline` 工程包（后续编辑交付物）。
- 镜头清单核心字段：`beat_type / asset_id / source_in-out / voice_line / caption_id / review_status`；拒一镜只换一个引用，不重建整条时间线。
- 参考片拆成功能拍 hook/context/proof/objection/transition/CTA，复用结构而非抄镜头；成片 + 可编辑工程双交付，且 preview 与导出同源。

## 第 4 章：安全执行模型 —— 让 agent 批量跑命令不翻车

前三章把「一段视频」变成了可检查的剪辑工程：素材被盘点成 agent 可读的决策文件（第 2 章），流水线与镜头清单把人的批准点嵌进了流程（第 3 章）。从这一章起，agent 要真正动手批量跑命令了。而视频素材不可再生——一次写错源路径的覆盖、一条 `rm`，代价是整场拍摄。安全执行模型要做的，就是在「默认只读 + 最小写权限 + 可回滚 + 事务式命令」的护栏里让 agent 放手干活：快，但不翻车。

### 4.1 三条底线：默认只读、目录边界、最小权限

官方文档里，Claude Code 与 Codex CLI 共享同一套安全底线（S1、S2）：

- **默认只读**：会话从只读权限启动；要编辑文件、跑可能修改系统的命令，必须先征求同意。
- **工作目录边界**：只能写启动目录及其子目录；动目录之外的文件，需要额外授权（Claude Code 在 Manual 模式下连「读」目录外路径都会先问）。
- **修改/联网类命令不默认放行**：`curl`/`wget` 这类联网取内容、删除与覆盖类命令默认都要人工审批。**人工审查命令**是最后一道兜底，谁也替不了你。

Claude Code 把这套默认行为称作 Manual 模式：内置只读命令（`ls`、`cat`、`git status`）免问直接跑；其余未匹配到规则的命令一律 fail-closed 默认要审批；可疑 bash 即使之前放行过，也要人工再审一遍（S2）。

> [!tip] 大白话
> 把 agent 想成拿临时工牌进剪辑间的外包操作员：工牌默认只让他「看」，不让他「改」；想动你启动目录之外的东西、想跑联网或删除命令，都得你当场刷一次脸。所以……「默认只读 + 逐条批准」不是不信任，而是把「一次手滑 = 素材全没」这类事故从源头挡住。

### 4.2 两套 agent 的权限机制速览：Claude Code 与 Codex CLI

先说 Claude Code 的几个关键旋钮（S2）：

- **allowlist**：把频繁使用的安全命令加进放行名单，缓解「每跑一条都要点一次」的提示疲劳；但对可疑命令仍然人工复核。
- **permissions.deny**：硬拦整类命令（如彻底禁掉 `curl`/`wget` 联网取内容）。deny 优先于 allow。
- **沙箱 bash 与 `/sandbox`**：给 bash 加文件系统与网络隔离，用 `/sandbox` 划定 agent 可以自治工作的边界。
- **Accept Edits**：自动批准工作目录内的文件编辑和一组固定文件系统命令（`mkdir`/`touch`/`rm`/`mv`/`cp`/`sed`），范围外的操作仍会询问。
- **ConfigChange hooks**：在会话期间审计甚至拦截对配置的改动，适合团队强制权限标准。

项目级 settings 大致长这样（示意，规则语法与 glob 以当前版本文档为准）：

```jsonc
// .claude/settings.json（项目级，示意）
{
  "permissions": {
    "allow": ["Bash(ffprobe:*)"],   // 只读探测类，常放行
    "deny": [
      "Bash(rm *)",                  // 禁止删除
      "Bash(curl *)"                 // 禁止联网取内容
    ]
  }
}
```

Codex CLI 的审批模型**以你安装的版本实测为准**：写作期它的官方安全/审批文档入口正在迁移（README 指向的文档站改版中），无法从官方文档确认 `approval_policy` 等配置键的当前取值。落地时直接查安装版的 `codex --help`、配置命令与随版本附带的文档，不要抄网上过时的键名（S1 缺口，推断）。能确定的是它同样在本地沙箱 shell 里驱动命令（S1），所以「默认只读 + 最小权限」的底线不变，变的只是具体开关叫什么。

### 4.3 媒体批处理的工程护栏：只读源、副本、固定版本、隔离输出

ffmpeg 这类工具默认「就地覆盖」，批量跑几十条时源路径一旦写错就是连环事故。媒体批处理实践把规则收敛成五条（S3，S4 佐证）：

1. **源素材只读**：原始素材目录不让 agent 写，从权限层物理挡住。
2. **复制工作副本**：转写、试剪、批量全在副本上做，源保持原样。
3. **固定版本**：agent、ffmpeg、Whisper、yt-dlp 版本固定——滤镜参数与 CLI 行为跨版本会变，版本漂移是「昨天能跑今天炸」的头号来源。
4. **写权限只限指定输出目录**：所有成品只落进 `edit/`。
5. **密钥不落项目文件**：API key/token 只放环境变量或系统钥匙串，不进脚本、不进配置、不进仓库。

配套的目录约定如下（推断，通用工程实践）：

```
project/
├── source/   # 只读源素材（母带，agent 无写权限）
├── work/     # 可写工作副本：转写/盘点/试验都在这
└── edit/     # 唯一允许落盘的输出目录
```

> [!tip] 大白话
> 把源素材想成档案馆的馆藏原件：只许在复印件（work/ 副本）上批注，改坏了扔了重印一份就行，原件永远安全。密钥则像保险箱里的钥匙，只在你启动 agent 前放进环境变量/钥匙串，绝不写进项目文件——否则一次误提交，等于把钥匙贴在档案馆门口。

### 4.4 事务式写入：失败整组停、重跑不双写

一次剪辑可能同时改画面、字幕、配音。只成功一半，工程就进了不一致状态。Timeline Studio 的做法是把命令层做成**数据库式事务**（S5）：

- **projectRevision 拒旧计划**：计划基于工程的某个版本生成；执行时发现工程已变，拒绝应用旧计划。
- **操作前置条件**：片段仍在某条轨道、时间范围仍有效、仍绑定对应音频……条件不满足就不执行该操作。
- **一意图一事务**：一个用户可见意图 = 一个事务；任一关键操作失败，整组修改停止。
- **operationId 幂等**：计划携带稳定 ID；重复执行同一计划不会重复插入素材或字幕。
- **结构化错误**：失败信息明确报「缺哪个素材、哪条命令不受支持、工程的哪项状态不符合预期」。

```bash
# 伪命令（以实际 skill 的命令名为准）
project.inspect work/project.timeline    # ① 读当前版本与结构
project.diff   work/edit-plan.json       # ② 非写入校验
project.run    work/edit-plan.json       # ③ 事务执行，输出新工程
```

```json
{
  "version": 1,
  "projectRevision": 6,
  "operationId": "promo-cut-v3",
  "operations": [
    { "type": "visual.trim",   "clipId": "visual-demo",    "sourceStart": 12.4, "sourceEnd": 18.7 },
    { "type": "caption.update", "clipId": "caption-result", "start": 24.2,       "end": 28.6 }
  ]
}
```

同一 `operationId` 重跑不双写；任一操作失败，整组回滚到一致状态。没有时间线工程、只有裸 ffmpeg 批处理时，把同一思想套上去：输出到独立的 run 目录、脚本带唯一 run id、任一步失败立即整组停止——「失败整组停、重跑不双写」是不依赖具体工具的事务护栏（推断）。

> [!tip] 大白话
> operationId 像快递单号：同一单号重复提交，不会发两件货。所以……哪怕 agent 跑一半失败、或你手动重跑同一批，字幕和片段也不会被插两遍——结果可预测、可回滚。

### 4.5 run 之前的最后一道闸：inspect → diff → run

第 1 章讲过结构性盲区：有些错误在静态分析里不可见，agent 会在错误的方案里反复调参。因此 run 之前要强制加两道不花钱的闸（S5）：

- **inspect 读结构**：读当前工程的版本、轨道、片段、字幕与媒体归档，先搞清「现状是什么」。
- **diff 非写入校验**：执行前先算出差异并验证，提前发现片段 ID 不存在、时间范围无效、轨道类型不兼容、工程版本不匹配、素材缺失、当前渲染器处理不了某属性——**此时什么都还没被改**。
- **run 执行**：前置条件成立，才事务性执行。

人在环里的用法很简单：**让 agent 先把 inspect 与 diff 的结果贴给你看，你再批准 run**。几百毫秒的只读检查，换来的是错误计划永远不会落到真实素材上。

> [!tip] 大白话
> 把 run 想成装修队进场动工：inspect 是重读一遍现场图纸，diff 是把「要敲哪几面墙、每面墙从哪到哪」列成清单先给你签字——清单里要是混进承重墙（素材缺失、ID 不存在），当场就停，不必等敲完再补救。所以……批处理前那几十秒的只读检查，是全程最便宜的一份保险。

## 第 5 章：工具链速查 —— FFmpeg / Whisper / yt-dlp 的 hard rules

前面几章搭好了「素材工程化 → 策略提案 → 人审 → 安全执行」的骨架，但真正让流水线稳定跑起来的，是这一层命令级细节。本章把支撑流水线的 hard rules 收拢成速查：**核心只有两条主线——「无损」和「不炸音频」**。这些规则听起来不像创意，却恰恰决定了 AI 剪辑能不能稳定工作（S6）。每条规则给最小可用命令 + 一句话解释，按需查阅即可，不必一次背完。

> [!tip] 大白话
> 把这几条 hard rules 想成厨房的「生熟分开」：不是让菜更好吃，是让流程不出食品安全事故。所以……本章没有一条命令在教你怎么剪得「好看」，全在教你怎么剪得「不坏」——不重编码损画质、不爆音、不把字幕叠没。

### 5.1 无损三件套：stream copy、concat demuxer、编码参数一致

**规则：多段素材先分段抽取，再无损 concat（`-c copy` + concat demuxer），避免反复编码；拼接前提是各片段编码参数一致**（S6；无损 concat 前提另见 P1 LensB）。

第一件：单段无损剪切。`-c copy` 表示**不重编码**，只把选中区间的码流原样拷贝进新容器，速度接近实时、画质零损失：

```bash
# 从 take01.mp4 抽出 00:01:23.500 起共 8 秒，不重编码（-ss / -t 放在 -i 之前做输入定位）
ffmpeg -ss 00:01:23.500 -t 8.000 -i take01.mp4 -c copy edit/clip_a.mp4
```

> [!warning] `-c copy` 的代价：切点吸附关键帧
> 不重编码意味着不能精确到任意帧——输出会从**前一个关键帧**开始，实际长度可能比你要的多出几帧到一两秒。它适合「粗切、抽素材、攒预览」；要精确下刀，见 5.2 的重编码版本。这也是第 6 章验证门要逐切点查「多帧/跳帧」的原因。

第二件：无损拼接。先把所有片段写进一个清单文件，再用 concat demuxer 一次性组装：

```bash
# concat.txt（放在项目根目录，路径相对当前工作目录，空格需转义）
file 'edit/clip_a.mp4'
file 'edit/clip_b.mp4'
file 'edit/clip_c.mp4'
```

```bash
# 清单文件做输入，-c copy 不重编码拼接
ffmpeg -f concat -safe 0 -i concat.txt -c copy edit/assembly.mp4
```

第三件是前提，也是最常被忽略的：**concat demuxer 只在各片段编码参数一致时可靠**——同 codec、同分辨率/帧率、同采样率/声道数。来自不同来源（手机、相机、录屏、下载）的片段直接拼，轻则花屏音画错位，重则就是第 1 章那个「agent 看不到的漂移」。所以正规套路是：**在抽取阶段就把片段统一成同一种中间格式**，再 concat：

```bash
# 统一中间格式：H.264 + yuv420p + AAC 48kHz 双声道（只需对要拼接的片段做一次）
ffmpeg -i edit/clip_b.mp4 -c:v libx264 -pix_fmt yuv420p -crf 18 -c:a aac -ar 48000 -ac 2 edit/clip_b_norm.mp4
```

> [!tip] 大白话
> 把 `-c copy` 想成搬家工人只搬箱子、绝不开箱重打包：快且无损；但前提是这批箱子规格得一样，否则搬进同一间屋子根本摞不起来。所以……「无损拼接」真正的功夫在拼接之前——先把各片段统一规格，最后那步 `-c copy` 才敢说无损。

### 5.2 不炸音频规则：30ms fade + 不在词中间下刀

**规则一：每个剪切点加 30ms audio fade，防爆音**（S6）。硬切会产生一个近乎瞬时的音量跳变，听感是「啪」的一声。30ms（0.03 秒）足够把跳变抹平、又短到人耳几乎察觉不到是淡入淡出。

fade 属于音频重编码，无法 `-c copy`，所以它和「精确剪切」合并在同一条命令里做——只对切出来的短段编码一次，成本可控：

```bash
# 精确切 8 秒 + 首尾各 30ms 音频 fade（afade: in 从 0 开始 0.03s，out 在 7.97s 开始 0.03s）
# 注意：st 用「片段时长 - 0.03」算 fade-out 起点；时长以 ffprobe 实测为准
ffmpeg -ss 00:01:23.500 -t 8.000 -i take01.mp4 \
  -af "afade=t=in:st=0:d=0.03,afade=t=out:st=7.97:d=0.03" \
  -c:v libx264 -crf 18 -c:a aac -b:a 160k edit/clip_a.mp4
```

**规则二：不能切在词中间，剪切点必须贴合逐词时间戳**（S6）。转写层给的逐词时间戳就是这里的「下刀坐标」：把词的起点/终点当作候选切点，宁可多留半个词也不把词拦腰切断（S6）。音频信号层面，「词中间」往往是辅音或气声密集区，切在这里比切在词间静音更容易出爆音。

> [!tip] 大白话
> 30ms fade 像给剪切边贴一条 3 厘米的透明胶带：不让毛边硌手。不在词中间下刀，则是「剪句子挑逗号处剪，别从字中间劈开」。所以……两条都是「把切口弄干净」，前者治物理爆音，后者治听感断字。

### 5.3 字幕的时序与层级：输出时间轴 + 滤镜链最后 + 首版不烧录

字幕有三条独立规则，别混在一起记：

**① 字幕滤镜放滤镜链最后**（S6）。只要后面还跟着 scale / crop / pad 等任何视频滤镜，字幕就可能被二次缩放遮住或裁掉。凡要烧录字幕，`subtitles=` 必须是 `-vf` 链的**最后一个**：

```bash
# 竖版 9:16 + 字幕：scale 先适配、pad 再补边、subtitles 放最后
ffmpeg -i edit/assembly.mp4 \
  -vf "scale=1080:1920:force_original_aspect_ratio=decrease,pad=1080:1920:(ow-iw)/2:(oh-ih)/2,subtitles=out.srt" \
  -c:v libx264 -crf 20 -c:a copy edit/preview.mp4
```

**② 字幕时间用输出时间轴，不是素材时间轴**（S6）。从源素材切走 1:40 后，原本在 `00:02:00` 的词在成片里是 `00:00:20`。若拿源 SRT 直接烧，字幕会全部错位。正确做法是让字幕从生成起就基于**输出时间线**。

**③ 首版不烧录字幕**（S3）。烧录是把文字焊死在画面上，之后改错别字、断句、样式都要重渲染。第一稿保持 `.srt` / `.ass` 这类可编辑数据；TTS 语音与字幕要从**同一份锁定的脚本**生成，保证词、时间、审阅意见始终对得上（S3）。等文案、断句、时长都过审了，最后导出时再走上面那条烧录命令。

> [!tip] 大白话
> 把「素材时间轴 vs 输出时间轴」想成搬家前后的页码：书在原书架上是第 100 页，搬走前面 90 页后它在新书架是第 10 页，字幕标的是「新书架的页码」。所以……删改越多，越不能拿素材原时间戳硬套，字幕必须跟着输出时间线重排。

### 5.4 素材获取：yt-dlp 下载与 Whisper 转写的最小命令

流水线第一步常是「拿一段参考片或自己的历史素材做 inventory」。下载用 yt-dlp，转写用 Whisper，二者可串成一条最小组合：

```bash
# 只取音频做转写（-x = 抽取音频，需本机已装 ffmpeg；产物进 edit/）
yt-dlp -x --audio-format mp3 -o "edit/ref_%(id)s.%(ext)s" "视频URL"

# 或要整段视频做参考（自动选最佳画质，ffmpeg 负责合并/封装）
yt-dlp -f "bv*+ba/b" -o "edit/ref_%(id)s.%(ext)s" "视频URL"
```

```bash
# Whisper 转写出 SRT（语言 zh，模型 small，产物统一落 edit/transcripts/）
whisper "edit/ref_音频或视频文件" --model small --language zh --output_format srt --output_dir edit/transcripts/
```

转写是整套流水线的「读」底座（S6 中视频-use 用的是 ElevenLabs Scribe，这里换成本地 Whisper 同理）——**转写错了，后面所有剪辑判断跟着偏**。两条补充：

- Whisper 官方 CLI 默认给的是**句子级**时间戳；要拿 5.2 需要的**逐词**时间戳，得走 Python API 的 `word_timestamps=True`（推断，具体以你安装的版本 `whisper --help` / 官方文档为准）。
- 下载视频的版权按第 1 章口径处理：只拿你有权使用的素材，自动化不清除权利问题（S3）。

### 5.5 目录卫生：产物一律进独立输出目录

**规则：所有输出放素材目录旁的 `edit/`（或独立输出目录），源素材目录保持干净只读**（S6）。这既避免中间产物污染素材，也让 agent 的写权限能精确圈定在 `edit/` 内——呼应第 4 章「写权限只限指定输出目录」的护栏（S3/S6）。约定俗成的结构：

```text
my-project/
├── take01.mp4  take02.mp4   # 源素材：只读，不进脚本改
├── concat.txt               # 中间清单：可随时重生成
├── edit/                    # 所有产物：抽取段、归一化段、assembly、preview、字幕
│   ├── clip_a.mp4
│   ├── assembly.mp4
│   ├── out.srt
│   ├── preview.mp4
│   └── transcripts/
└── shots.csv                # 镜头清单（第 3 章产物）
```

因为源素材从不被改写，`edit/` 可以随时整目录清空重来——这就是幂等与可回滚在目录层面的落地。

### 本章小结

- 无损拼接三件套：`-c copy` 抽段、concat demuxer 组装、各片段编码参数一致是前提；参数不齐先统一中间格式（S6 + P1 LensB）。
- 每个剪切点 30ms audio fade 防爆音；剪切点贴合逐词时间戳、不切在词中间（S6）。
- 字幕三条：滤镜链最后、用输出时间轴、首版不烧录、TTS/字幕从单一锁定脚本生成（S6/S3）。
- 素材获取最小组合：yt-dlp 下载 + Whisper 转写出 SRT；转写质量是整个流程的底座（S6）。
- 目录卫生：源素材只读、所有产物进 `edit/`，呼应第 4 章的最小写权限护栏（S3/S6）。

## 第 6 章：验证门与人工精修 —— 怎么判断「剪完了」

前面几章把流水线推到了「渲染 preview、导出成片」这一步，但这恰是很多自动化剪辑翻车的地方：agent 报告「渲染成功、退出码 0」，不等于视频真的能用。本章回答一个必须由人回答的问题——**凭什么说「剪完了」**：先过两层可命令化的验证门，再逐剪切点自检，最后把「好不好」的终审交回给人。

### 6.1 两层验证门：先验工程，再验成片

第 3 章《流水线设计与角色分工 —— 从需求到成片》定了「成片 + 可编辑工程」双交付，所以「完成」要两个对象分别达标。第一层验工程、第二层验成片，顺序不能反：工程结构错了，重导出多少次都一样（S5）。

> [!tip] 大白话
> 把两层验证想成收房验收：工程验证是查图纸和管线——墙砌没砌、电线走得对不对；视频验证是拎包试住——灯亮不亮、会不会跳闸。agent 说「渲染完成」只等于施工队交了钥匙，两套检查都过了，你才签字收房。

**工程验证 checklist**（S5）：

- [ ] 轨道数量与计划一致
- [ ] 主画面连续、无空洞
- [ ] 片段顺序与时长符合镜头清单
- [ ] 每条字幕都绑定到一段可听见的对应语音
- [ ] 媒体文件已归档进工程包
- [ ] 工程能重新打开
- [ ] 预览首帧能正常显示

**视频验证 checklist**（S5）：

- [ ] 容器与编码正确（如 mp4 / H.264 + AAC）
- [ ] 视频尺寸、时长符合交付简报
- [ ] 整段能完整解码
- [ ] 音频轨存在
- [ ] 字幕、Overlay、效果可见
- [ ] 转场边界无停顿或重复帧
- [ ] 无声道错位与异常静音

第一扇门里最常漏的是「字幕绑定语音」——字幕在、却没有对应声音，是自动化字幕的典型病（S5）；第二扇门里最容易骗过眼睛的是转场边界与声道，这两类恰好要用命令去查。

### 6.2 用 ffprobe 把「看一眼」变成「查一下」

两层验证里凡是能命令化的，都别靠肉眼。下面四条都是标准用法，直接对产物跑，逐条对应 6.1 视频验证项：

```bash
# 1) 容器/编码/尺寸/时长/音轨一览
ffprobe -v error -show_entries \
  format=format_name,duration,size \
  :stream=index,codec_type,codec_name,width,height,r_frame_rate,sample_rate,channels \
  -of default=noprint_wrappers=1 final.mp4

# 2) 完整解码冒烟：全程解码到 null，任何解码错误都会打到 stderr
ffmpeg -v error -i final.mp4 -f null -

# 3) 冻结帧/重复帧检测：转场停顿、重复帧会打印 freeze_start / freeze_end
ffmpeg -i final.mp4 -vf freezedetect=n=-60dB:d=0.4 -map 0:v -f null -

# 4) 异常静音/声道：过长的静音段会打印 silence_start / silence_end
ffmpeg -i final.mp4 -af silencedetect=noise=-40dB:d=0.5 -f null -
```

第 2 条性价比最高：它强制解码每一帧，音画漂移、坏帧这类「静态分析不可见」的问题常在解码阶段现形（呼应第 1 章的结构性盲区）。第 3、4 条专补肉眼容易漏的「转场停顿/重复帧」与「异常静音」。

### 6.3 逐剪切点自检：跳帧、爆音、字幕遮挡

整片指标通过还不够，真正的坑集中在切点附近——这正是第 5 章《工具链速查 —— FFmpeg / Whisper / yt-dlp 的 hard rules》那几条规则（30ms audio fade、不在词中间下刀、字幕滤镜放最后）要防的东西。自检思路：把镜头清单/EDL 里的每个剪切时间点导出来，逐个在切点前后开一个小窗口检查。

```bash
# audit_cuts.sh —— 逐剪切点自检骨架（启发式，最终判断仍靠人眼/人耳）
# 用法: bash audit_cuts.sh final.mp4 cut_times.txt  （cut_times.txt 每行一个切点秒数）
file="$1"; cuts="$2"
while read -r t; do
  s=$(awk -v t="$t" 'BEGIN{printf "%.3f", (t-0.12 < 0 ? 0 : t-0.12)}')
  e=$(awk -v t="$t" 'BEGIN{printf "%.3f", t+0.12}')
  echo "== 剪切点 @ ${t}s =="
  # A. 视频：窗口内实际解码帧数应 ≈ 帧率×0.24s；明显偏少 = 疑似跳帧
  ffprobe -v error -count_frames -select_streams v:0 \
    -read_intervals "${s}+0.24" -show_entries stream=nb_read_frames \
    -of default=noprint_wrappers=1 "$file"
  # B. 音频：解码窗口统计音量，峰值接近 0dB = 疑似爆音/clipping，交耳朵复核
  ffmpeg -i "$file" -ss "$s" -to "$e" -af volumedetect -f null - 2>&1 \
    | grep -E "max_volume|mean_volume"
done < "$cuts"
```

这条脚本只做「数量级」告警（推断的简化方案，阈值需按素材自调）：帧数对不上就去看这一刀是否跳帧，音量顶到 0dB 就去听是否爆音。字幕遮挡命令查不出来，靠源头规则（字幕滤镜放滤镜链最后）防，精修时再到真实平台画幅上逐条看（S6）。

### 6.4 preview 即导出：同一条合成规则

「预览正常、导出坏了」几乎都来自同一根因：预览与导出走了两套合成规则（S5 明说预览走播放路径、导出走独立合成路径时就易出此类问题）。所以流水线立一条纪律：**preview 与最终导出共用同一条渲染命令、同一个滤镜图，只允许码率、分辨率这类显式声明的参数不同**。preview 通过≈导出通过，前提是二者除那几个参数外完全同源（S5/S6）。做不到同源时，最终导出后必须重跑 6.2 全套命令加一次人工抽检，不能拿 preview 结果代替。

### 6.5 人工精修：时机、范围与「谁说了算」

两层验证门保证「工程没坏」，但保证不了「片子好看」——这落在 agent 保留地之外（回看第 1 章两张清单）。

**时机**：preview 通过两层验证之后、锁 master 之前。拿着第 3 章交付的可编辑工程（.timeline / edit 目录）进剪映或 PR，人在这里调整表达与审美（S5/S6）。太早进去是在替 agent 补工程 bug，太晚则改动成本高。

**范围**（S3/S5/S6）：

- **方向与节奏**：hook 成不成立、proof 来得到不到位、CTA 顺不顺；机器只能删停顿、查重复，判断不了情绪转折可不可信。
- **审美**：字幕断行与样式、动画、封面；字幕要到真实平台画幅上看，而不是桌面预览。
- **品牌准确性**：产品颜色、包装版本、是否混入未授权创作者——「长得像」的素材最容易在此翻车。
- **权利审查**：自动化不清权。参考片、音乐、肖像、字体、声音模型的授权记录要人工核对并留存（S3）。

**谁说了算**：agent 产出的镜头清单/EDL 从头到尾只是提案，不是真相（S3/S6）。人在第 3 章镜头清单上批的 review_status 要一路带到交付审计——谁在何时批准了哪一版，是可追溯的批准链，而不是一句「AI 剪的」。

### 6.6 剪映草稿互操作：保守策略

若目标是「让 agent 直接产出可编辑的剪映草稿」，这是全流程版本敏感度最高的一环（S3）。剪映官方功能页确认了智能分割、配音、多轨等能力，但**没有可供第三方稳定依赖的公开官方草稿 schema**（S3）；社区里改草稿的脚本普遍撞版本墙（模板与导出版本各自受限——推断，需按你所用版本实测）。保守做法三条：

1. **adapter 与核心清单分离**：剪映适配只放在最外层，核心镜头清单/EDL 保持工具无关（S3），换工具不重建。
2. **先备份、后测试**：每次剪映更新后，先复制工程、在一次性草稿上验证 adapter，再用于真实项目。
3. **不把「能导进去」当「schema 稳定」**：能成功一次，不等于下个版本还能成功。

### 本章小结

- 「剪完了」由两扇门定义：先过工程验证（结构/字幕绑定/可重开），再过视频验证（容器/解码/转场/声道），顺序不可反。
- 能命令化的验证一律命令化：完整解码冒烟（`ffmpeg -v error -i in -f null -`）性价比最高，freezedetect / silencedetect 补上眼睛易漏的两类问题。
- 逐剪切点自检是第三道网，专查切点附近的跳帧与爆音；字幕遮挡靠「滤镜链最后」从源头防。
- preview 与导出必须同一条合成规则，否则 preview 通过没有意义。
- 人工精修时机在「两层验证后、锁 master 前」，范围是方向、审美、品牌准确性与权利审查；批准权在人，提案权在 agent。
- 剪映草稿互操作是版本敏感区：adapter 与核心清单分离、先备份、一次性草稿测试、不假设 schema 稳定。

## 第 7 章：反模式与实战问答 —— 为什么会翻车、账怎么算

前六章都在讲「怎么搭对」，这一章反过来问一句：没搭对的，到底翻在哪？以及动手前你最想知道的——这单交给 agent，账怎么算。作为收束章，我用问答体把散落在素材里的失败案例与争议点归拢，最后落回那条判断标准。

### 7.1 四大反模式速览：翻车翻在同一个病根

| 反模式 | 为什么翻车 | 正确做法（回指章节） |
|---|---|---|
| 让 agent「看」视频：把几万帧丢给它 | 帧全是 token 噪音，审不过来也复盘不了 | 把素材压成「文本 + 时间轴 + 结构化决策」（第 2 章） |
| 无人值守：跳过人审直接批量跑 | agent 产出的是提案不是真相，错就整批错 | 保留「策略提案 → 人审 → 执行」确认点（第 3、4 章） |
| 创意内容硬套 agent：改 6 版花 6 小时 | 方向、审美都要人定夺时，快反而放大迭代成本 | 先判断内容类型再决定交不交（第 1 章） |
| concat 音画漂移下让 agent 反复调参 | 漂移属「静态分析不可见」，agent 在错误方案里越改越远 | 靠人设验证点兜底（第 6 章两层验证门） |

后两行的「6 小时 6 版」与「音画漂移 14.86 秒」都来自社区实测、未经独立复核，这里只取方向性含义：前者说明创意迭代不该交给 agent，后者说明有些错误只有人能看见。

### 7.2 无人值守的诱惑，与确认点的真实成本

>S6 的立场很明确：保留「先策略后执行」的确认点，意味着这套流水线不适合「完全无人」的批量生产（S6）。可 S4 里相当比例的用户，要的偏偏是一键自动（S4）。矛盾怎么解？

先算两笔账。一个确认点只花几十秒到几分钟，总成本随决策点数量**线性**增长；跳过确认点一旦出错，一批几百条跑完再返工，成本随批规模**倍增**，还叠加「agent 在错误方案里反复调参」的隐患。两相比较，确认点不是流水线的累赘，而是最便宜的保险；真正贵的是「无人值守地错到底」。

> [!tip] 大白话
> 把确认点想成工厂出货前的抽检：每批抽几件看，花几分钟，拦住的是整批返工。所以……人审不是拖慢流水线，是用最小的线性成本，避开最大的倍增损失。

现实折中是给确认点降级：模板固定后头几条全审，之后只审 agent 标了 low-confidence 的切点——第 3 章镜头清单里的 `review_status` 字段就是干这个的。闸门还在，成本没拉满。

### 7.3 剪映互操作：两种叙事，怎么选

这是素材库里最明显的分歧（见 02_deep_research 的 Contradictions）：

- **保守派（S3）**：剪映草稿没有稳定公开 schema、版本敏感，NemoVideo 明示「无法验证稳定公开 schema」，只能先备份、一次性草稿测试。
- **生态派（S4）**：把「Codex + 生态工具直接操剪映、一键成片」当既成现实在讲。

两种叙事可能都对，区别在**你把剪映放在流水线的哪个位置**。若要整条链路（含最终精修）都自动化跑在剪映草稿层，你选的是生态派，同时要接受它的版本墙与「剪映一升级就断」的风险；若只是把剪映当人工精修的收尾工具，就选保守派——agent 产出中间时间线 / EDL（第 3 章）与「成片 + 可编辑工程」双交付（第 6 章），人进剪映做最后微调。对大多数仍保留「人做最终批准」的 human-in-the-loop 流水线，保守派更稳：它不赌剪映内部结构，只赌双方都认的导出格式。

### 7.4 账本怎么算：先承认没有系统量化

成本账最该警惕的是：**token 消耗、机时、渲染耗时都缺逐项测量**，素材里只有 S4 的定性描述，而 S4 是二手聚合、含营销水分（S4）。所以本书不给你「每分钟素材多少钱」这种貌似精确的 ROI——它的精度是假的。能保留的是两条定性结论：模板化内容（口播 / 拆条 / 带货 / 知识讲解）agent 提效显著（数字见第 1 章）；创意内容迭代到不划算。

> [!warning] 降权原则
> 看到「10 分钟干一个月」「几百倍提效」这类峰值数字，先问两句：素材是不是同构批处理？有没有把人的复核时间算进去？社区二手数字按方向性结论读，别按财务精度读。

具体到某一单，判断只要两个「是 / 否」：内容是否模板化、你接不接受为效果反复精调。它们不需要精确到分毛的成本表。

### 7.5 一条判断标准收尾

把全书收束成一句话，正是第 1 章立下的那条：**模板化内容用 agent，创意表达留自己**（S4）。前面六章的方法与工具，都是为了让「可模板化」的那部分安全、可验证地交给 agent；而「什么是好、要什么感觉」永远由你保留。账算不清时，回到这条判断标准，比任何 ROI 公式都可靠。

### 本章小结

- 四大反模式共享同一个病根：让 agent 干它干不了的事——「看」视频、无人值守、精修创意、自查结构性错误。
- 确认点成本线性、出错成本倍增；保留人审是流水线最便宜的保险，可用「审样张 + 审低置信切点」降级。
- 剪映互操作选保守派还是生态派，取决于剪映是「人工收尾工具」还是「全自动链路」，对 human-in-the-loop 默认选保守派。
- 成本账缺系统量化，二手效率数字降权、只取定性结论。
- 全书判断标准一条：模板化用 agent，创意留自己。

至此主线七章收束。若只读不练，建议回到第 2、5 章，拿一段自己的素材跑通「转写 → 盘点 → 提案 → 人审 → 执行 → 验证」的最小闭环，再回来看这章的反模式，体会会完全不同。
