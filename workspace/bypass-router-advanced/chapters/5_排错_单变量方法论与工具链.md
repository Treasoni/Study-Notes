# 第 5 章 排错：单变量方法论与工具链

「有时能通、有时不通」是最难查的一类故障：现象随机，看起来每个组件都可能有责任。这一章把前四章的机制收束成一套排错方法——先用单变量法把问题锁到具体一层，再用有官方锚点的命令验证。定位上，本章只处理**进阶现象**（非对称路径、flowtable 卸载）；**基础排错流程**（ping 网关、检查 DNS、确认转发等常规动作）见既有笔记 [[软路由教程/旁路由原理详解]]，不在此重复。

## 5.1 单变量方法论

排错第一原则是**别让多个变量同时动**。这条来自社区经验（S9）：**"不要把订阅、DNS、规则分流和系统代理混在一起排查。先固定变量，只看一层。"** 判定方式示例为「先测 IP，再测域名」[^c5-s9]。本笔记录入它只作**方法论**：S9 无署名、无发布日期，**不得作为配置语义依据**。

把它落成一张可执行的判定顺序：

1. **先测 IP**（如 `ping 1.1.1.1`）——先排除「转发/出口」这一层。
2. **再测域名**（如 `nslookup example.com`）——IP 通而域名不通，问题在 DNS 层。
3. **最后看代理规则/订阅**——前两层都通仍异常，才轮到代理层。
4. **每一步只改一个变量再复测**，否则现象会重新变回随机。

> [!tip] 大白话
> 把排错想成修水管：一次只拧一个阀门，看水到底从哪一段漏。若同时关好几个阀，就算不漏了你也说不清是哪个起了作用。所以「先测 IP，再测域名」不是两句咒语，而是逼你把变量逐个固定下来。

## 5.2 非对称路径的现象序列与 conntrack 归因

有一类「能通但会卡」的现象只发生在**上下行路径不一致**时。社区经验（S8）给出了它的事故序列——注意：**作者仅作文字描述，并未给出抓包命令**[^c5-s8]：

1. 客户端发 SYN；
2. 客户端收 SYN+ACK；
3. 客户端发 ACK；
4. 客户端发 payload；
5. （**无**回应的 ACK）；
6. 客户端重复收到 SYN+ACK；
7. 重传 payload，仍无 ACK。

S8 作者的归因是：**"由于服务器回应的SYN + ACK没有经过OpenWrt，使得OpenWrt没有正确追踪TCP连接"**，进而**"OpenWrt认为客户端后续的数据包是'无效数据包'，并丢弃"**[^c5-s8]。这是作者自己的解释，而且作者**明确自述**：**"具体conntrack的工作方式和该问题的出现条件，有待进一步验证"**——因此本笔记**只把它当作一条待验证的线索，不升级为确定结论**。

它之所以可能成立，与第 1 章的一个事实接得上：**回程也走 PREROUTING**（官方原文：「虽然网关访问公网 IP 不需要经过PREROUTING链，但被访问的服务器向网关返回信息时要经过PREROUTING链……」）[^c5-s1]。当回程路径**不经过** OpenWrt 时，连接跟踪就只看到了半程。

> [!tip] 大白话
> 把 conntrack 想成门卫手里的访客登记本：客人从正门进来（去程）登记了一次，可回程要是从后门溜出去、没再经过门卫，登记本就只记了「进」没记「出」。门卫于是把后面顺着正门来的同一位客人当成生面孔（无效数据包）拦下。这只是社区作者给出的解释，他自己也说「有待进一步验证」——所以先当线索、别当定论。

## 5.3 从社区口头路径到官方条目

S8 给的处置是**口头描述界面**（"防火墙页面里关闭某个开关"），无法逐字引用、也说不清语义。必须把它落到 OpenWrt 官方条目名上，才有可核验的落点。

**处置路径一**：**"在OpenWrt中解决的方法也很简单，首先在'防火墙'页面中关闭'丢弃无效数据包'"**（S8）[^c5-s8] → 对应**官方全局条目 `drop_invalid`**（boolean，**文档默认值 `0`**），条目原文**"Drop invalid packets (e.g. not matching any active connection)."**，LuCI 界面名 `_('Drop invalid packets')`[^c5-sg1-01]。

**处置路径二**：**"若OpenWrt通过独立线路（在防火墙的WAN Zone）连接主路由，则在一些特定情况下（比如因为一些组网需求，对一些内网网段开启了masquerade），还要打开WAN Zone – 编辑 – 连接追踪设置 – 允许'无效'流量"**（S8）[^c5-s8] → 对应**官方 zone 级 `masq_allow_invalid`**（boolean，**文档默认值 `0`**）[^c5-sg1-01]。

**这两项的归属必须分清**（复核修正 ②）：

- **条目原文出自 SG1-01（wiki 页 Zones 表）**："Do not add `DROP INVALID` rules, if masquerading is used."，续句："The `DROP` rules are supposed to prevent NAT leakage (see commit in firewall3)."[^c5-sg1-01]
- **LuCI 侧的界面名与说明原文出自 SG1-02（LuCI 上游源码 `zones.js` 第 291 行）**，位于 zone 弹窗的 **conntrack 页签**：界面名 `_('Allow "invalid" traffic')`，说明原文 `_('Do not install extra rules to reject forwarded traffic with conntrack state <em>invalid</em>. This may be required for complex asymmetric route setups.')`[^c5-sg1-02]。

**含 `asymmetric` 的那句只属 SG1-02，绝不可挂到 SG1-01 的 wiki 页名下**——复核已确认 `asymmetric` 一词**未出现在 `firewall_configuration` wiki 页上**。

由此得到一条**纠正**（T-8）：OpenWrt 官方**只存在上述两个** invalid 相关条目——全局 `drop_invalid` 与 zone 级 `masq_allow_invalid`；**「zone 级允许无效流量」不是独立的 conntrack 选项**，S8 的口头路径对应的就是 `masq_allow_invalid`[^c5-sg1-01]。

一处互相印证：conntrack 工具文档自身也把 INVALID 与丢弃规则集关联起来——**"You have a stateful rule-set that drops traffic in INVALID state."**[^c5-sg3-02]，与 `drop_invalid` / `masq_allow_invalid` 的语义一致。

落到配置上，两个条目的位置是（取值以本机为准）：全局段 `firewall.@defaults[0].drop_invalid`，zone 末端的 `masq_allow_invalid`。

> [!tip] 大白话
> 把这两条想成门卫的两张备注：`drop_invalid` 是「凡是登记本上查无此人的包裹，一律拒收」（全局默认关）；`masq_allow_invalid` 是「如果这栋楼的侧门在做地址伪装（masquerade），就**别**贴那种一概拒收的告示，免得把正常包裹也拦掉」（zone 级、默认关）。S8 教程里说的「允许无效流量」，官方名字就是后者；官方其实只有这两个开关，没有第三个。

## 5.4 有官方锚点的命令集

上一节的推理要落地，靠的是几条官方命令。**以下全部取官方 man page 锚点，不采用社区转述。**

**① 双向抓包——必须分别指定接口。** tcpdump 的 `-i`/`--interface` 官方用途为 **"Listen, report the list of link-layer types, … on interface."**[^c5-sg3-01]，一次只作用于一个接口。**因此不能用单一接口推断全链路**：去程与回程可能走不同接口，回程只在 WAN 侧可见时，只抓 LAN 侧会误判「没有回应」。

```bash
# 去程接口（LAN 侧）：看客户端发出的包
sudo tcpdump -i br-lan -n 'host <客户端IP> and port 443'

# 回程接口（WAN 侧）：回程可能只在此接口可见，必须单独抓一次
sudo tcpdump -i eth1 -n 'host <客户端IP> and port 443'
```
两个接口各打印一段方向相反的序列（`>` 去程、`<` 回程）；若 WAN 侧有回包而 LAN 侧看不到，说明回程没走回旁路由。

**② 握手判定。** 官方握手序列原文：**"1) Caller sends SYN　2) Recipient responds with SYN, ACK　3) Caller sends ACK"**；`tcpflags` 官方释义为 **"some combination of S (SYN), F (FIN), P (PSH), R (RST), U (URG), W (CWR), E (ECE), e (AE) or `.` (ACK)"**[^c5-sg3-01]。用它就能**定位 5.2 序列里缺失的那一步**——正常应看到 SYN → SYN,ACK → ACK 三步齐全。

```bash
# 官方示例：打印每个 TCP 会话的起止包（只显示带 SYN 或 FIN 的包）
sudo tcpdump -n 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'
```
输出中每次会话应成对出现 SYN 与 FIN；若只见 SYN、SYN,ACK 而不见结尾，即为半程会话的旁证。

**③ 连接跟踪查看。** 官方原文 **"You can list the existing flows using the conntrack utility via command:"**，后接 `# conntrack -L`；过滤示例 `# conntrack -L -p tcp --dport 993`，并说明 **"You can filter out the listing without using grep"**[^c5-sg3-02]。

```bash
conntrack -L                      # 列出全部连接跟踪条目
conntrack -L -p tcp --dport 993   # 官方过滤示例：只看目的端口 993 的 TCP 流
```
输出每行一条流；对照 5.2 的客户端连接，能看出它是否被记为有效状态。

**④ NAT 规则查看。** `-L` 官方原文 **"List all rules in the selected chain. If no chain is selected, all chains are listed. Like every other iptables command, it applies to the specified table (filter is the default), so NAT rules get listed by"**，官方示例为 `iptables -t nat -n -L`[^c5-sg3-03]。

```bash
iptables -t nat -n -L
```
核对是否存在把客户端流量改写/转发的 NAT 与跳转规则；**`-t nat` 不能省**——不加它默认查的是 `filter` 表，NAT 规则一条也不会列出来。

> [!tip] 大白话
> 这四条命令是四把不同的手电筒：抓包照「路上发生了什么」，握手序列照「有没有走完三步」，conntrack 照「门卫登记本记了什么」，iptables 照「改写地址的规则贴在哪」。别指望一把照全——尤其抓包，`-i` 一次只照一个口，想同时看前后门就得开两次。

## 5.5 与 flowtable 的交叉验证

前面几节都把「连接没被正确跟踪」当线索。但漏包还有另一个更隐蔽的来源：**连接已经被 flowtable 卸载**（第 2 章）。判据仍是 `conntrack -L`，只看行末标签与计数器：

```bash
conntrack -L
# 关注每行末尾是否带 [OFFLOAD] 或 [HW_OFFLOAD]
# 并观察配套计数器是否不再增长
```

**必须同时认识两个标签**：`[OFFLOAD]` 指**软件**卸载，`[HW_OFFLOAD]` 指**硬件**卸载。**开了 `flow_offloading_hw` 的连接带的是 `[HW_OFFLOAD]` 而非 `[OFFLOAD]`，且存在 workqueue 延迟**——只按「找 `[OFFLOAD]`」去查，会在硬件卸载场景里一个标签也找不到，从而误判「未被卸载」。标签差异与延迟的机制细节见第 2 章 2.4，此处不重复；本节的增量只是把它接进排错闭环。

**闭环**：第 1 章说透明代理靠 Netfilter 路径在接管点截流，第 2 章的 [推断] 说 flowtable 会让 ingress 之后的 Netfilter hook 看不到这些包；两条合起来就是一个判据——**若连接带卸载标签，代理拦不到属预期，不是故障**。这正是社区教程里那些「万能修复」最容易误导的一类现象：读者以为代理坏了，其实是包根本没走到代理值班的那道 hook。

> [!tip] 大白话
> 想成快递被走了「已直送」的快速通道：包裹在第一个分拣口就贴了直送标（卸载标签），后面各道人工柜台自然都见不到它。你去柜台问「为什么没收到」，柜台也只能说「这些件根本没到我这」。所以查到卸载标签时，先别急着修代理——先确认是不是它本来就该绕过去。

## 小结

- **方法论**（社区经验 S9）：先固定变量、只看一层，例如「先测 IP，再测域名」；S9 无署名、无发布日期，**只作方法论，不作配置语义依据**[^c5-s9]。
- 非对称路径的现象序列与 conntrack 归因来自**社区经验**（S8），且作者自述**"有待进一步验证"**——本笔记不升级为确定结论；该序列**仅为文字描述、无抓包命令**[^c5-s8]。
- 社区口头路径须落到**官方条目**：全局 `drop_invalid` 与 zone 级 `masq_allow_invalid`（S8 的「允许无效流量」对应的就是后者）；官方**只有这两个** invalid 条目[^c5-sg1-01]。**T-7 的条目原文属 SG1-01（wiki）**，**含 `asymmetric` 的 LuCI 说明属 SG1-02（`zones.js:291`）**，归属不可互换[^c5-sg1-02]。
- 命令一律取**官方 man page 锚点**；`-i` 一次只作用于一个接口，**去程与回程须分别指定**，不能用单一接口推断全链路[^c5-sg3-01]。
- `conntrack -L` 兼作两类判据：连接跟踪是否正常，以及连接是否被卸载（`[OFFLOAD]` / `[HW_OFFLOAD]`）；带卸载标签时代理拦不到属预期[^c5-sg2-01]。

全篇五章反复撞见同一个结构性事实：**旁路由这一层没有权威单一文档**，官方只覆盖到组件层，「旁路由该怎么配、怎么查」的实践写法主要来自社区事实标准。因此本笔记的每个结论都尽量回到可逐字核验的官方锚点，遇到社区口径冲突则并列呈现、不替读者裁决——这套态度本身就是应对这类主题最实用的方法。
