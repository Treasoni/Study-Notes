## 1. 概述 
在当今的部署和运维世界中，直接在物理服务器上运行我们的服务的情况并不常见。我们通常会在选择虚拟主机（本地或云端）或使用像 Docker 这样的容器之间做出决定。
这种向更高抽象层次的转变需要我们掌握 [基础设施即代码 (IaC)](https://baeldung.cn/cs/containers-vs-virtual-machines#/en/topics/automation/what-is-infrastructure-as-code-iac) 和容器编排技术，如 Kubernetes。但我们可以通过更小的步骤来实现一些优势。
在本教程中，我们将探讨虚拟化和容器化。我们将比较技术上的差异和权衡。
## 2. 为什么需要抽象？ 
在最简单的配置中，我们将应用程序和服务托管在安装在服务器计算机上的操作系统（Linux、Windows 等）中
这仍然是无数小型企业的服务器机房中的常见情况。
然而，广泛的虚拟化始于 2000 年代中期的数据中心和云端。**容器的使用，由 Docker 领导，在 2010 年代中期标准化并获得了发展动力。**
是什么持续推动着这些技术的采用？
当我们以这种方式运行服务时，我们可以获得以下优势
**灵活性和可扩展性** ：如果我们需要扩展或缩小服务器的功能，我们可以轻松更改配置或将其复制到另一台主机。如果我们需要运行更多服务，我们可以启动更多的虚拟机、云实例，或将容器添加到我们的 Pod 中。
**资源利用率：** 如果我们需要大量的服务器来处理某些事情，但仅限于每月一次，我们不再需要让这些服务器其余时间空闲。我们可以根据需要动态分配硬件（计算和存储）资源
**进程隔离：** 与其跟踪安装在单一系统上的各种服务，我们可以将每个服务的代码、配置和依赖项分开保存。这意味着更新一个服务不会破坏另一个服务。此外，我们可以防止一个占用大量资源的应用程序拖慢所有其他应用程序的速度
**配置和变更管理：** 如果我们需要更改一个重要的系统，我们可以创建一个虚拟机的快照。如果情况变得非常糟糕，我们可以快速撤销更改，并且不会比以前更糟。此外，当我们在一次处理一个服务时，记录配置和更改会变得更加简单。当我们转向基础设施即代码，使用 Terraform 或 Ansible 等工具编写配置时，这些定义可以帮助我们避免任何遗忘或“临时”的基础设施更改。
## 3. 虚拟化基础 
虚拟化指的是在软件中运行虚拟机。 “主机”系统运行虚拟化软件，通常称为 hypervisor。“客户”系统在 hypervisor 中运行。 “客户”操作系统几乎不知道自己没有直接运行在硬件（“裸机”）上
虚拟化软件的一些示例
  * VMware [Workstation](https://www.vmware.com/products/workstation-player.html) 或 [ESXi](https://www.vmware.com/products/esxi-and-esx.html)
  * [VirtualBox](https://virtualbox.net.cn/) – 它是免费的，并且适合于桌面使用
  * [DosBox](https://www.dosbox.com/) – 它是一款著名的老游戏模拟器，但也能够运行完整的操作系统，例如 BeOS
  * Microsoft 的 [Hyper-V](https://docs.microsoft.com/en-us/windows-server/virtualization/hyper-v/hyper-v-technology-overview)


我们可以使用这些工具来部署应用程序，例如 wiki 及其数据库，或网络监控套件。
我们也可以在开发桌面中使用这些工具，以安全地试验其他环境。
在 2000 年代中期，Intel 和 AMD 在其 CPU 上添加了虚拟化扩展（Intel VT 和 AMD-V，或 SVM 模式）。这些是今天服务器的标准功能；但是，在台式机上，我们可能需要在 BIOS 设置中启用它们。 这种硬件辅助大大简化并加速了虚拟机监控程序。
### 3.1. 虚拟机能做什么？ 
**当我们使用虚拟机镜像而不是“裸机”服务器安装时，我们会获得可移植性。** 虚拟机镜像是标准化的，因此我们可以根据需要轻松地在不同的主机之间迁移它们。 许多虚拟机监控程序甚至支持实时迁移，虚拟机在从一台物理机无缝传输到另一台物理机的过程中，会继续运行。
AWS、GCP 和 Azure 等云服务提供的不仅仅是虚拟操作系统安装。但它们的基础建立在虚拟机实例之上。我们不必购买新硬件并自行安装 Ubuntu Server。我们只需指定想要付费的 RAM 和 CPU 资源，请求特定的操作系统，就可以开始了。
虚拟机，就像任何完整的操作系统安装一样，必须启动并提供其自身的所有功能。每个虚拟机都可以运行完全不同的 Linux 内核或发行版。我们还可以运行其他操作系统，例如 Windows 或 BSD。 这使我们的访客彼此完全隔离，有助于提高安全性并简化配置和依赖项。 它也更重，占用更多的空间和 CPU。
从用户的角度来看，虚拟机与物理机完全相同。
## 4. 容器基础知识 
容器引擎（如 Docker）在完整的操作系统（如 Linux）上运行。操作系统提供内核和相关服务（文件系统、网络、进程管理）。
容器提供运行特定服务所需的所有其他内容。
  * 代码或应用程序二进制文件
  * 依赖项，例如库
  * 可能包含解释器或运行时环境，例如 Python 或 JRE
  * 配置和本地化，例如环境变量或用户帐户


所有这些元素都固定到特定版本。想想 _node_ 的 package-lock.json 文件，或者 _pip_ 的 requirements.txt 文件：容器使用来自特定镜像的命令和库。我们可以要求它使用镜像中的最新版本，或者我们可以指定确切的版本。 这样，当我们使用容器时，我们也指定了我们的软件环境（除了由主机操作系统确定的内核版本）。
### 4.1. Docker 的作用 
对于我们中的许多人来说，“[Docker](https://www.docker.com/resources/what-container)”和“容器”是同义词。虽然我们知道其他容器引擎存在（例如 Red Hat 的 [Podman](https://podman.org.cn/)），但我们可以从 Docker 生态系统中学习容器架构和使用的基本知识。
Docker 还 [托管着大量的容器镜像库](https://hub.docker.com/)，我们可以从中构建和运行自己的本地容器。
**容器镜像就像我们正在运行的容器的模板。** 当容器运行时加载并运行它们时，它们才成为容器。容器在使用的内核和操作系统之上运行，并添加所需的所有其他内容。它们通常构建在一个最小的源镜像之上，例如流行的“[alpine](https://hub.docker.com/_/alpine/)”。
我们使用容器镜像的主要重点是打包特定的应用程序或服务及其所有相关的依赖项。例如，我们可以 [部署 Java WAR 存档及其服务器。](https://baeldung.cn/docker-deploy-java-war)
在 Docker 的术语中，我们从 Docker Hub 拉取镜像。然后，我们在本地容器引擎或运行时（containerd、Docker 的引擎以及 CRI-O 是一些例子）上运行它。
### 4.2. 联合或分层文件系统 
**容器比虚拟机小得多。这转化为更少的存储空间，但也意味着近乎即时的启动时间。**
如前所述，容器镜像可以选择性地仅包含应用程序所需的操作系统元素。
它们体积小的另一个秘诀在于，它们不是使用各自独立的文件系统，而是在基础镜像之上分层构建。基础镜像保持只读状态，任何更改都只发生在容器内的本地层中。
如果一个系统运行从同一基础镜像派生的容器，它只需要一份只读层的副本。节省更多空间！
### 4.3. 托管容器 
我们可以使用容器来保持与我们的开发、测试和生产环境同步。再也不会出现“但在我的机器上可以运行！”的问题了。
在生产中使用它们时，我们可以拉取、自定义和运行镜像作为部署的一部分。但即使我们在云实例上执行此操作，仍然会给我们带来大量管理和运维工作。
云提供商支持直接使用我们的容器镜像。例如，[Amazon Fargate](https://aws.amazon.com/fargate/) 接受一个镜像，并在进行一些资源配置后使其可用。
[Kubernetes](https://kubernetes.ac.cn/) 是事实上的容器编排标准，为我们的容器化应用程序增加高可用性和自我修复功能。它也增加了更多的复杂性。但即使我们现在可能认为不需要 k8s，现在通过容器化我们的应用程序来为它做准备，有助于我们为未来的扩展做好准备。
## 5. 结论 
虚拟机和容器解决了类似的问题。但虚拟机需要更多的开销、镜像以及为每个实例运行整个操作系统。
容器在单个操作系统下或通过编排在群组中运行。它们提供易于替换的轻量级服务。
在本文中，我们比较了运行完整的虚拟机与在容器中运行我们的应用程序。
虚拟机可能更适合需要灵活性的长期安装。容器几乎适用于所有其他情况。
