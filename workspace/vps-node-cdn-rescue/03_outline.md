### 第一章：CDN 是什么

- **篇幅**：1700–2000 字
- **核心问题**：CDN 到底是"帮你加速的缓存网络"，还是"挡在源站前面的反向代理"？它凭什么把请求送到离用户更近的地方？
- **节（含落地顺序标注）**：
  - 1.1 **它是什么**：地理分布的服务器群 + 缓存 + 回源；CDN ≠ 虚拟主机
  - 1.2 **具体产物长什么样**：一次请求的完整链路（用户 → 就近边缘节点 → 缓存命中直接返回 / 未命中回源 → 写入缓存并返回）
  - 1.3 **带具体值的例子**：同一条记录，被代理时 DNS 答的是 Cloudflare anycast IP、灰云时答的是源站真实 IP
  - 1.4 **对比表**：① DNS unicast 路由 vs anycast 路由（就近判断依据、故障切换表现）② 缓存命中 vs 回源（谁把流量接走、钱花在哪）③ 可缓存 / 动态内容 / 非 GET 方法的回源差异
  - 1.5 **`[!tip] 大白话`**：CDN 像小区门口的便利店——货从远处仓库（源站）来，但常买的东西已经放在你楼下
  - 1.6 顺带说清代价：依赖第三方、多一层攻击面、跨源不共享缓存可能反而更慢；CDN 片区被封或被关停则整站故障

### 第二章：为什么 CDN 能救被墙节点（原理与边界）

- **篇幅**：1900–2200 字（本篇核心增量，按 P3 拍板加厚）
- **核心问题**：套了 CDN 之后，封锁方"看得见"的是什么？这层保护从哪来，又到哪为止？
- **节（含落地顺序标注）**：
  - 2.1 **它是什么（第一层原理：换脸）**：代理记录让 DNS、SNI、Host 三者都指向 CDN 上的那个域名，源站真实 IP 不出现在任何一层
  - 2.2 **具体产物长什么样（第二层原理：附带损害）**：domain fronting 的抗封锁逻辑 → domain shadowing 为何更难封
  - 2.3 **带具体值的例子（第三层原理：被动检测下的 CDN AS）**：GFW 对"全加密流量"的被动检测机制、豁免规则思路、封锁的端口范围与残余封锁时长、CDN AS 未在该机制受影响之列的**原语境**
  - 2.4 **对比表**：三层原理各自拦住什么 / 各自拦不住什么
  - 2.5 **边界清单（加厚，本章不可省的增量，目标 700–900 字）**：
    - 换脸救不了域名被污染（域名侧被污染时，解析根本到不了 Cloudflare）
    - 附带损害依赖审查方不愿扩大伤害；CDN 方一旦被施压可自废该特性（domain fronting 已被厂商主动关闭的历史）
    - 被动检测这条的时间限定：`2021-11 ~ 2023-02`，且口径为"2022-05 扫描、仅 port 80"
    - CDN 自身被整段封锁时方案整体失效；CDN 片区故障时整站故障
    - 方案不可用时怎么办：**对照面板流第 9 章的"分层排除 + 换 IP"路径** → 链 `[[09 节点被墙的判定与换 IP（分厂商分操作）]]`
  - 2.6 **`[!tip] 大白话`**：像用"大商场"当收货地址——想拦你，就得连整个商场一起封

### 第四章：把节点套上 CDN（TLS / 端口 / WS）

> **本章硬性边界**：**不含"安装面板 / 搭建节点"**。面板侧只给**一句话指路**（见 4.4），其余全部围绕 Cloudflare 侧与 Xray 侧的配置条件展开。

- **篇幅**：2200–2500 字（加厚端口表与 TLS 五模式，按 P3 拍板）

- **节（含落地顺序标注）**：
  - 4.1 **端口**（**加厚**）：Cloudflare 默认代理哪些端口（HTTP / HTTPS 两组合并逐项，13 个端口完整列全）；哪些端口"可代理但缓存被禁用"（10 个，逐项）；**免费版想要额外端口只有"放弃代理"一条路**（灰云 = 自毁方案、Spectrum 全端口 = 企业版，标明这是两条官方事实的合成结论）；中国方向的端口限定；非标准端口被扫描器报"开放"的官方解释；**缓存结论属排除推论**，须标注
  - 4.2 **TLS 模式**（**加厚**）：**它是什么**（同时管访客↔CF 与 CF↔源站两段连接）→ **具体产物**（五种模式逐档）→ **带具体值例子**（选 Full 与选 Full (strict) 时源站证书分别要满足什么，逐条列）→ **对比表**（模式 × 访客侧 × 源站侧 × 证书要求 × 适用场景）→ **`[!tip] 大白话`**（两段路，两个关卡）；自动模式的存在与退出方式只作一句提示
