# 第 2 章 为什么 CDN 能救被墙节点（原理与边界）

上一章我们把 CDN 讲成了「缓存 + 加速」。但缓存和加速本身与被墙毫无关系——一个纯缓存的 CDN 不会让你的节点变得更难封。真正让它能救节点的，是它在网络拓扑里的第二个身份，以及这个身份背后的三层原理。这一章要回答的是：套上 CDN 之后，封锁方「看得见」的是什么？这层保护从哪来，又到哪为止？

## 2.1 第一层原理：换脸

最直接的一层是：**你的源站 IP 不再出现在公开的解析答案里**。当一条记录被设为代理，DNS 查询返回的是 Cloudflare 的 anycast IP，而不是源站真实 IP（来源：B-1 | `## Proxied records`、`### Example`）。请求因此先进入 Cloudflare 的网络；而 Cloudflare 作为反向代理，会把请求代理回源站——**所有请求都要穿越 Cloudflare 网络，才到达客户的网络**（来源：A-2 | `## Cloudflare CDN architecture and design`）。封锁方在这一层看到的，是一个 CDN 地址。

只藏 IP 还不够。USENIX Security 2021 关于 domain shadowing 的论文指出，该手法能让连接的**全部「指示器」——连接 URL、TLS 连接的 SNI、HTTP(S) 请求的 Host 头——看起来都属于那个被允许的域名**（来源：A-5 | Abstract）。换句话说，不只是「你连的是谁」被换掉了，「你说你要访问谁」也被换掉了。这三者同时对外呈现为同一个被允许的域名，是这一层原理的完整形态。

## 2.2 第二层原理：附带损害

如果只是换脸，封锁方大可以「顺手把你换上的那张脸也封掉」。它没有这么做，是因为这样做要付出代价——这个代价有个名字：**附带损害**（collateral damage）。

domain fronting 的手法依赖一个实现细节：许多 CDN **不检查 SNI 与 Host 头的一致性**，只凭 Host 头转发请求。于是用户可以连到 CDN 边缘、请求一个被允许的域名（front domain），却把 Host 头设成被封锁的域名（来源：D-2 | §2.3）。要封掉这种做法，审查方**必须封掉该 CDN 上的所有域名**——否则只要还有一个被允许的域名，它就能当日落域名，让同一 CDN 上其他所有域名重新可用（来源：D-2 | §2.3）。由于 CDN 服务在当今互联网极为普遍，许多有价值的域名也由 CDN 提供，**彻底封锁一个（大型）CDN 对很多审查方而言并不可行**（来源：D-2 | §2.3）。OONI 术语表把这种「依赖审查方不愿造成大面积误伤」的思路称为 **collateral freedom**（来源：C-5 | `Domain fronting`，仅作术语对照）。

**domain shadowing 比 domain fronting 更难封**。在 domain fronting 的情形下，若审查方认为封锁某个域至关重要，仍可以选择整段封掉承载它的那个 CDN；但在 domain shadowing 的情形下，要封锁一个域，审查方**必须封掉所有允许 domain shadowing 的 CDN**，其附带损害比 domain fronting 大得多（来源：D-2 | §6.1.3 IP Blocking）。更进一步，**封掉某一个 CDN 也不能禁用 domain shadowing**——用户可以换到其他仍允许该手法的 CDN（来源：D-2 | §6.3.3 Completely Blocking a CDN）。

这套机制之所以成立，还因为 CDN 很难「把后门关掉」：设置任意后端域是 CDN 的合法能力，就如同 DNS 的 CNAME 可以让一个域名指向任意另一个域名、名字服务器既无兴趣也无能力去核验两者的关系；现实中网站把客服等业务外包给第三方（例如把子域 CNAME 指向 `example.zendesk.com`）正是靠这个能力运作的（来源：D-2 | §6.2.1 Limiting the Back-end Domain）。所以，**附带损害不是审查方的善意，而是 CDN 自身业务决定的成本**。

## 2.3 第三层原理：被动检测下的 CDN AS

前两层讲的是「看不见你」。第三层讲的是另一回事：**即使审查方在检测「全加密流量」，大型 CDN 的地址段也不在受影响之列**。

这个结论出自 GFW Report 的 USENIX Security 2023 论文。论文测量的是 GFW 自 **2021 年 11 月**起部署的一套新机制：**对「全加密流量」做纯被动的实时检测与封锁**，影响范围包括 Shadowsocks、VMess、Obfs4 等协议（来源：A-6 | Abstract；§1）。论文作者**推断**出的做法是：GFW 不正面定义「全加密流量」，而是先用**至少五条粗粒度豁免规则**放过那些「不像全加密」的流量，其余一律封锁（来源：A-6 | §4 Algorithm 1）：

| 规则 | 内容（面向客户端发出的首个 TCP 载荷） |
|---|---|
| Ex1 | 置位比特比例 ≤ 3.4 或 ≥ 4.6 |
| Ex2 | 前 6 个（或更多）字节落在 `[0x20,0x7e]`（可打印 ASCII） |
| Ex3 | 超过 50% 的字节落在 `[0x20,0x7e]` |
| Ex4 | 超过 20 个连续字节落在 `[0x20,0x7e]` |
| Ex5 | 匹配 TLS 或 HTTP 的协议指纹 |

其中 TLS 的豁免依赖头 3 字节匹配 `[\x16-\x17]\x03[\x00-\x09]`；HTTP 的豁免依赖「方法名 + 一个空格」，**大小写不敏感，但把方法名拼错就不再豁免**（来源：A-6 | §4.3）。另有两点值得记住：中文（UTF-8 与 GBK）字符**不享受任何豁免**（来源：A-6 | §4.2）。

被判定后的处置方式也很具体（来源：A-6 | §4.4）：

- **只丢「客户端 → 服务器」方向的包**，服务器发往客户端的包不受影响；
- 该机制**仅作用于 TCP**，UDP 不触发；
- 封锁可发生在 **1–65535 全部端口**——所以换非标准端口并不能规避；
- 触发后同一 3 元组（客户端 IP、服务器 IP、服务器端口）被**残余封锁 120 或 180 秒**，且计时器不因后续发包而重置；
- 封锁是**概率性**的，单连接被封锁的概率约为 **26.3%**（来源：A-6 | §6.3）。

而「哪些地址段会被检测」这件事，论文在 **2022 年 5 月**做过一次 10% IPv4 扫描，**只扫 TCP 80 端口**：5.5 百万个 IP 中 **98% 不受影响**；受影响的 AS **都是向个人出售 VPS 的供应商**（如 Alibaba US、Constant，以及 Amazon / Digital Ocean / Linode 的部分前缀），而 **Akamai、Cloudflare 这类大型 CDN 的 AS 不在受影响之列**（来源：A-6 | §6.2 Figure 4 说明段）。

> [!warning] 这条结论的语境极窄，必须连着限定一起读
> 「CDN AS 不在受影响之列」**严格限于「全加密流量被动检测」这一个机制**，且它出自 **2022 年 5 月、仅 port 80** 的一次扫描，观察窗口为 **2021-11 ~ 2023-02**。它**不能**推出「CDN 对其它封锁手段免疫」，也**不能**推出「CDN 是当局的有意豁免」。作任何 2026 年现状陈述都不由该论文支撑（来源：A-6 | Abstract、§6.2、§6.3；02_deep_research.md | §三-12）。

## 2.4 三层原理各自拦住了什么

| 原理层 | 它挡住的是什么 | 它挡不住的是什么 |
|---|---|---|
| 第一层：换脸（隐藏源站 IP 与域名指向） | 直接扫描 / 直连源站 IP 的封锁与暴露 | 域名本身被污染的路径（解析根本到不了 CDN） |
| 第二层：附带损害（封一个域要连坐整个 CDN） | 「顺手封掉你的域名」这种低成本做法 | 审查方愿意承受附带损害时的整段封锁；CDN 主动废除该特性 |
| 第三层：被动检测豁免（CDN AS 不在受影响之列） | 「全加密流量被动检测」这一种机制下的封禁 | 其它封锁手段；该机制本身的后续扩展（作者判断该机制属临时性） |

## 2.5 边界清单：CDN 救不了什么

这一节是本章最不能省的部分。前面三层的每一层都有它的反例，看清它们才知道什么时候该转向别的手段。

**（一）换脸救不了域名被污染。** 第一层原理的前提是「解析能正常走到 Cloudflare」。如果封锁发生在域名解析这一层——查询被投毒、返回伪造答案——请求**根本到不了 Cloudflare**，那么无论源站 IP 藏得多好都没有意义。把你暴露在外的不是 IP，而是那串域名；换脸解决不了门牌号被人改掉的问题。

**（二）附带损害不是承诺，是可撤销的商业选择。** 第二层原理之所以成立，靠的是审查方「不愿扩大伤害」加 CDN「不愿关掉合法功能」两件事同时成立。但后者是会变的：论文记录了 domain fronting 的兴衰——在 2015 年被提出后，**近两年间许多 CDN（例如 Google Cloud CDN、Amazon CloudFront）意识到该手法并开始废止它，手段是强制 SNI 与 Host 头一致**，这迫使不少规避系统停服，或转向更小、封锁成本更低的 CDN（来源：D-2 | §2.3）。同一篇论文也直言：domain shadowing 一旦被公开知晓，很可能遭遇与 domain fronting 相同的命运——**CDN 提供商可能迫于压力而禁用它**（来源：D-2 | §6.2）。换句话说，这一层保护依赖商业与政治权衡，而不是技术上的不可关闭。

**（三）第三层结论有时间与口径双重限定。** 「CDN AS 不在受影响之列」只在**全加密流量被动检测**这一机制、且在 **2021-11 ~ 2023-02** 的观察窗口内成立，其依据是 **2022 年 5 月、仅 port 80** 的扫描；论文作者本身也判断该机制属「临时性」，审查方随时可扩展（来源：A-6 | §4.4、§6.2）。把它读成「CDN 对封锁免疫」是明确的外推错误。

**（四）CDN 自身被整段封锁时，方案整体失效。** 第二层原理的另一面是：一旦审查方认为封掉这个 CDN 的收益大于代价（CDN 越小，代价越低），整段封锁就会发生；到那一步，被你藏在后面的所有东西一起不通。同样地，**CDN 自己的片区故障也会造成整站故障**（来源：A-4 | `There are also downsides to using CDNs`）。

**（五）方案不可用时的退路。** 如果你撞上了上面任一条边界——尤其是「域名被污染」这类换脸救不了的情形——正确的下一步不是继续在 CDN 上折腾，而是回到「分层排除 + 换 IP」那条路径。完整的操作路径已写在面板流 `[[09 节点被墙的判定与换 IP（分厂商分操作）]]` 中，本篇不重复；你只需要记住：**CDN 是一条备选路线，不是唯一路线，也不是在所有被墙形态下都成立。**

> [!tip] 大白话
> 把第二层原理想成「用大商场当收货地址」：快递员想拦你，就得连整个商场一起封——可商场里还有几百家别的店在正常营业，封了会把所有人都得罪。所以你的包裹能混进去。domain fronting 用的是商场「不看收件人和招牌是否一致」这个漏洞，domain shadowing 用的则是商场「允许你填任意收货方」这项正经业务。
> 但这个比方也说明了边界：**商场是会被施压的**（它可以自己改规矩，正如 Google Cloud CDN 们废止了 domain fronting），**模仿商场也是没用的**（如果对方铁了心要连商场一起封，你的包裹就一起被拦——这正是「CDN 被整段封锁」）。至于第三层，那只是「商场这个地址段不在这台检测仪的扫描名单里」，**不是「商场能躲开所有检查」**。

### 本章小结

- 第一层原理是「换脸」：代理记录的 DNS 答案不含源站 IP，且连接 URL、TLS SNI、HTTP(S) Host 对外全部呈现为同一被允许域名（来源：B-1 | `## Proxied records`；A-5 | Abstract）。
- 第二层原理是「附带损害」：封一个域要连坐整个 CDN 上所有域名，故审查方顾虑代价；domain shadowing 需要连坐**所有**允许该手法的 CDN，比 domain fronting 更难封（来源：D-2 | §2.3、§6.1.3、§6.3.3）。
- 第三层原理是「被动检测豁免」：GFW 全加密流量被动检测机制下，**Akamai、Cloudflare 这类大型 CDN AS 不在 2022-05、仅 port 80 扫描的受影响之列**（来源：A-6 | §6.2）。
- 该第三层结论必须带限定读：仅指全加密流量被动检测这一机制、观察窗口 2021-11 ~ 2023-02，不能外推为「CDN 免疫」或「有意豁免」（来源：A-6 | Abstract、§4.4；02_deep_research.md | §三-12）。
- 边界清单：域名被污染救不了；附带损害是可被厂商撤销的商业选择（domain fronting 已被强制 SNI=Host 关停）；CDN 被整段封锁或片区故障时方案整体失效；退路是面板流第 9 章的分层排除与换 IP（来源：D-2 | §2.3、§6.2；A-4 | `There are also downsides to using CDNs`）。
