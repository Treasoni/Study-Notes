# LLM Prompt Caching 提示缓存

> [!info] 概述
> **Prompt Caching（提示缓存）是 Claude API 和 Claude Code 的核心成本优化机制**——将不变的提示前缀缓存复用，避免重复计费和传输，可降低 **90% 的输入 token 成本** 和 **80% 的延迟**。理解缓存原理是高效使用 Claude Code 的关键。

---

## 一、什么是 Prompt Caching

### 通俗理解

> [!tip] 大白话
> 提示缓存就像**教室里的黑板**——老师把公式写一次在黑板上，全班同学反复看，不需要每问一道题就重新写一遍。

在 LLM 调用中，每次请求都会带上系统提示、工具定义、历史对话等。这些内容在连续对话中大量重复。如果每次都传完整的上下文：
- Token 浪费巨大（相同内容反复计费）
- 延迟高（传输和编码时间）
- API 成本线性增长

**Prompt Caching 的解决方案**：标记提示中可复用的前缀/后缀，服务端缓存计算结果，后续请求只传变化部分。

### 缓存命中 vs 未命中

> [!tip] 大白话
> **命中** = 这页纸之前抄过，服务端直接复用，只收少量费用；**未命中** = 每次都要从头抄一遍，全价计费。

```
未命中（首轮）:
┌──────────────────────────────────┐
│ 系统提示 │ CLAUDE.md │ tools │ query │  ← 全部传输 + 全部计费
└──────────────────────────────────┘

缓存命中（后续轮）:
┌──────────────────────────────────┐
│ 系统提示 │ CLAUDE.md │ tools │ ██ │  ← 缓存部分免费/低价
│                              │   │
└──────────────────────────────┴───┘
                               ↑
                          只传新的 query
```

> [!tip] 核心收益
> - **写入成本**：比未缓存高 10%（一次性代价）
> - **读取成本**：比未缓存低 **90%**（每次复用都赚）
> - **适用场景**：多轮对话、系统提示稳定的应用

---

## 二、缓存什么内容

### 缓存机制

Claude API 会对以下内容自动缓存：

| 缓存对象 | 最小长度 | 缓存 TTL | 说明 |
|---------|---------|---------|------|
| System Prompt | 1024 tokens | 5 分钟 | 系统提示词 |
| Tools 定义 | 1024 tokens | 5 分钟 | 工具描述和 schema |
| Messages 前缀 | 1024 tokens | 5 分钟 | 连续的对话前缀 |
| 图片 | 100 tokens | 5 分钟 | 图片内容 |

> [!warning] 关键约束
> - **最小缓存块 1024 tokens** — 小于 1024 的不缓存
> - **5 分钟 TTL** — 两次请求间隔超过 5 分钟，缓存自动失效
> - **必须精确匹配** — 哪怕改一个空格，缓存也作废，需要重新写入

> [!tip] 大白话
> 三条硬规矩：**太小不缓存**（不足 1024 token 不划算）、**太久不缓存**（间隔超过 5 分钟作废）、**改一丁点就作废**（逐字节精确匹配）。

### 缓存断点

> [!tip] 大白话
> **缓存断点**就是提示词里能「分段打勾」的位置——前面的段落没变，就只在最后一格写上新的提问。

提示中可以被缓存的"断点"位置：

```
[ SYSTEM PROMPT ]       ← 缓存点 1（多轮不变的固定前缀）
[ TOOLS ]               ← 缓存点 2（工具定义）
[ Messages:             
    [user]: "问题1"     
    [assistant]: "回答1" ← 缓存点 3（历史消息前缀）
    [user]: "问题2"     
    [assistant]: "回答2" 
    [user]: "问题3"     ]  ← 仅这部分是新内容，需要传输
```

## 三、Claude Code 中的缓存架构

### 五层缓存结构

```
请求结构（从稳定到动态）:
┌─────────────────────────────────┐
│ ① System Prompt                  │ ← 可用期内 100% 缓存
│   (角色、任务、安全规则)           │
├─────────────────────────────────┤
│ ② CLAUDE.md + Project Memory     │ ← 项目不变时缓存
│   (项目规则、编码规范)             │
├─────────────────────────────────┤
│ ③ Tools 定义                     │ ← 工具集不变时缓存
│   (Read/Write/Bash 等描述)       │
├─────────────────────────────────┤
│ ④ 历史消息前缀                    │ ← 5 分钟 TTL 刷新
│   (前 N-1 轮对话)                │
├─────────────────────────────────┤
│ ⑤ 当前用户输入                    │ ← 不缓存，每次变化
└─────────────────────────────────┘
```

### 项目中的缓存优化实践

你的项目 `.claude/rules/common/prompt-cache.md` 已经定义了完整的缓存策略：

> **核心原则**：稳定内容在前，动态内容在后。

```markdown
# Prompt Cache Rules - 提示顺序

1. 稳定的角色、任务边界、安全规则
2. 稳定的工具约束、输出格式、质量要求
3. 稳定的示例（仅在显著改善结果时）
4. 动态参数：用户请求、文件摘录、日期、运行时状态
```

这条规则正好对应到**缓存断点**：1-3 条属于 5 分钟 TTL 内的稳定可缓存前缀区，第 4 条动态内容放末尾，只承担最小传输与计费。Subagent 调用也应复用同一套稳定前缀模板，保证跨调用前缀一致、命中率稳定。

### 1M 上下文与更大的缓存窗口

2026 年 6-8 月，Claude Code 默认模型升级为 **Claude Sonnet 5 / Opus 5**，两者都原生支持 **1M token 上下文**。上下文变大，直接影响缓存策略：

| 维度 | 200K 时代 | 1M 时代 |
|------|----------|---------|
| 最大上下文 | 200K tokens | 1M tokens |
| 缓存窗口 | 受 200K 上限约束 | 更大，可缓存更长的历史前缀 |
| 长任务 | 常需 `/compact` 压缩 | 可直接承载更长会话，命中率更高 |
| 超限处理 | 主动压缩 | 自动压缩到窗口内 |

> [!tip] 大白话
> 上下文从 200K 扩到 1M，就像黑板从一面墙变成一整面教室——能提前写好并复用的内容更多，缓存窗口更大。

如果你不希望使用 1M 上下文（例如担心费用，或想保持旧的自动压缩行为），可以设置环境变量：

```bash
# 强制所有原生 1M 模型回到 200K，超出部分自动压缩
CLAUDE_CODE_DISABLE_1M_CONTEXT=1
```

> [!warning] 注意
> `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 关闭的是「1M 上下文」特性，**不是缓存本身**。它让模型回到 200K 窗口 + 自动压缩；缓存命中策略仍适用，只是窗口变小、更依赖 `/compact` 或分段设计。

### JSON Schema 断点

Claude Code 中有一个重要的缓存优化机制——**JSON Schema 缓存断点**：

```json
{
  "type": "object",
  "properties": {
    "response": { "type": "string" }
  }
}
```

如果最终输出始终包含相同的 JSON Schema 定义，应放在系统提示的稳定区域，使其可被缓存。这对 `/review-pr`、`/commit` 等固定输出格式的命令尤其有效。

## 四、影响缓存命中的因素

### ✅ 这些操作会保持缓存

| 操作 | 对缓存的影响 |
|------|------------|
| 同一会话连续对话 | 历史前缀持续命中 |
| 修改用户查询内容 | 无影响（查询在动态部分） |
| 使用相同的 CLAUDE.md | 稳定前缀不变 |
| 短时间内继续对话 | 在 5 分钟 TTL 内 |
| 上下文落在 1M 窗口内 | 更长的历史前缀可被缓存 |

### ❌ 这些操作会破坏缓存

| 操作 | 原因 |
|------|------|
| `/clear` | 清空所有上下文，重置缓存 |
| `/compact` | 对话被压缩摘要替代，缓存点重置 |
| 修改 CLAUDE.md | 缓存前缀变更 |
| 修改 settings.json（工具相关） | 工具定义变化 |
| 间隔超过 5 分钟再发消息 | 缓存 TTL 过期 |
| 切换模型 | 不同模型独立缓存 |
| `/rewind` | 对话状态变更 |
| 切换 `CLAUDE_CODE_DISABLE_1M_CONTEXT` | 上下文窗口变化，缓存前缀失效 |
| 触发自动压缩 | 早期内容被摘要替代，缓存点重置 |

### 缓存命中率诊断表

| 现象 | 原因 | 解决 |
|------|------|------|
| `/context` 显示 token 消费高 | 缓存命中率低 | 检查前缀稳定性 |
| 连续发送消息间隔长 | 5 分钟 TTL 过期 | 缩短思考/操作时间 |
| 工具定义频繁变化 | 每次调用不同工具集 | 合并工具调用 |
| CLAUDE.md 过长 | 超过缓存有效区 | 精简到 200 行以内 |
| 长任务中早期内容丢失 | 触发了自动压缩 | 确认是否超过 1M 窗口，或设 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 固定 200K 行为 |

## 五、缓存优化实践

### 1. 稳定前缀设计

```markdown
# ❌ 差 — 动态内容在前面
{{current_date}} {{user_name}}
You are a coding assistant.
Project rules: ...

# ✅ 好 — 稳定内容在前面
You are a coding assistant.         ← 缓存
Project rules: ...                  ← 缓存
{{current_date}} {{user_name}}     ← 动态
```

### 2. CLAUDE.md 优化

```markdown
# ❌ 差 — 太长，降低有效缓存密度
- 包含大量示例代码
- 500+ 行规则文件
- 动态时间戳

# ✅ 好 — 精简稳定
- 只写核心规则（≤ 200 行）
- 示例代码用 @ 引用外部文件
- 不含动态内容
```

### 3. Skill 设计原则

Skills 的 `SKILL.md` 本质上是注入到上下文的提示前缀：

```markdown
# 稳定前缀（可缓存）
role: code-reviewer
rules: [check security, check performance]
output: JSON schema

# 动态参数（不可缓存，放最后）
target_file: {{user_input}}
focus_area: {{user_selection}}
```

### 4. Subagent 调用优化

每个 Subagent 有独立上下文，缓存也是独立的：

```markdown
# ❌ 差 — 每个 Subagent 自定义系统提示
agent A: "Review this code for bugs..."
agent B: "Review this code for style..."

# ✅ 好 — 共享稳定模板
agent A: uses template "reviewer" + query "bugs"
agent B: uses template "reviewer" + query "style"
```

### 5. 长上下文分段缓存（1M 时代）

1M 上下文下缓存窗口更大，但 5 分钟 TTL 和「精确匹配」约束不变。对长任务，把提示拆成稳定分段，让每段尽量复用：

```
[ SYSTEM PROMPT ]        ← 稳定段 1：角色 + 安全规则（长期缓存）
[ PROJECT RULES ]        ← 稳定段 2：CLAUDE.md / 项目规范（项目内不变）
[ TOOLS ]                ← 稳定段 3：工具定义（工具集不变）
[ 历史消息前缀 ]          ← 动态但可缓存段：5 分钟 TTL 内刷新
[ 本次任务输入 ]          ← 动态段：每次变化，不缓存
```

- 稳定段放在前面，让命中概率最高的部分覆盖最大缓存窗口。
- 长上下文下，历史前缀可缓存量更大：尽量少用 `/compact`，让对话自然续写以保持前缀连续。
- 只有确认会超出窗口时才 `/compact`，接受一次性重新写入成本，换取后续命中。

> [!tip] 大白话
> 分段缓存 = 把「长期不变的课本」和「每次新写的作业本」分开。1M 时代课本能放更多内容，作业本只写最后几行。

### 6. 监控缓存效果

```bash
# 查看当前token消耗
/context

# 查看费用明细
/cost

# 调试模式查看缓存命中
claude --debug
```

## 六、与其它优化手段对比

| 机制 | 解决的问题 | 作用层 | 配置难度 |
|------|----------|--------|---------|
| **Prompt Caching** | 重复前缀的 token 成本 | API 层（自动） | ⭐ 无需配置 |
| **`/compact`** | 对话过长导致 token 浪费 | 会话层（手动） | ⭐ 一条命令 |
| **`.claudeignore`** | 遍历无关文件 | 文件层（手动） | ⭐⭐ 写规则 |
| **`claudeMdExcludes`** | 加载过多 CLAUDE.md | 配置层（手动） | ⭐⭐ 写配置 |
| **Skill 渐进披露** | 一次性加载太多指令 | 架构层（设计） | ⭐⭐⭐ 需规划 |

> [!tip] 关系
> Prompt Caching 是**透明的底层优化**，不需要你做任何事就能生效。但你写的 CLAUDE.md、Skills、Subagent 设计**决定了缓存能有多高的命中率**。1M 上下文只是把缓存窗口变大，命中率仍取决于前缀设计。

## 七、常见误区

### ❌ "缓存命中了就不用付钱"

缓存命中仍然需要付费——只是费用大幅降低（约 10% 的原价）。完全免费的是"剪枝"（某些前缀被完全剪裁）。

### ❌ "内容一样就一定能缓存"

必须**逐字节精确匹配**。格式化的差异（如 Markdown vs 纯文本）、换行符差异都会导致缓存失效。

### ❌ "缓存越大越好"

缓存块有最小 1024 token 的要求。对于短消息链，缓存反而没有意义。同时，如果前缀变化频繁，缓存写入成本反而更高。

### ❌ "5 分钟 TTL 很短，不实用"

在活跃的编程会话中，每轮对话通常只需 10-60 秒。只要连续工作不断，5 分钟足够覆盖整场编码会话。

### ❌ "1M 上下文就不需要缓存了"

缓存解决的是**重复前缀的成本**，1M 上下文解决的是**装得下多少内容**。两者互补：上下文越大，可复用的稳定前缀越多，缓存省得越多。`CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 关掉的是 1M 窗口，**不是缓存**。

## 小结

- **Prompt Caching 是透明的底层优化**：稳定前缀被服务端缓存，命中后读取成本降低约 90%，写入成本仅 +10%。
- **三个硬约束**：最小缓存块 1024 tokens、5 分钟 TTL、逐字节精确匹配。
- **Claude Code 缓存分层**：System Prompt → CLAUDE.md → Tools → 历史消息前缀 → 当前输入，稳定在前、动态在后。
- **1M 上下文放大缓存收益**：Sonnet 5 / Opus 5 原生 1M 上下文，缓存窗口更大；`CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 可强制回 200K 自动压缩。
- **你的设计决定命中率**：CLAUDE.md、Skills、Subagent 模板写得越稳定，缓存收益越高。

## 常见问题（FAQ）

**Q1：缓存命中了要付钱吗？**
要付，但约 10% 原价（读取价远低于写入价）。

**Q2：为什么我改了 CLAUDE.md，缓存就不生效了？**
缓存要求逐字节精确匹配，任何前缀改动都会使缓存失效，需重新写入。

**Q3：5 分钟 TTL 够用吗？**
够。活跃编码会话每轮对话通常 10-60 秒，只要连续工作不中断就能持续命中。

**Q4：1M 上下文会不会更贵？**
Sonnet 5 促销期 $2/$10 每 Mtok（截至 2026-08-31）。1M 上下文 + 缓存命中能显著摊薄长会话成本；不需要时可设 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 回 200K 自动压缩。

**Q5：怎么判断当前缓存是否生效？**
用 `/context` 查看 token 消费、`/cost` 查看费用明细，或 `claude --debug` 查看缓存命中日志。
