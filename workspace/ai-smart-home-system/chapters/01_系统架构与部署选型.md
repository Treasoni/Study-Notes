# 第一章 系统架构与部署选型：为什么是 HAOS 为主 + Container 为辅

> 笔记类型：实战构建指南（practice）｜学习深度：精通
> 素材来源：`02_deep_research.md` §1、§6（时效性修正 #1）
> 前置关联：[[Home Assistant 三种部署方式对比与选型.md]]

> [!summary] 本章回答三个问题
> 1. 这套系统长什么样？（四层架构地图）
> 2. 为什么不能照搬报告的 Supervised 方案？（官方弃用修正）
> 3. 为什么最终是「HAOS 为主 + Container 为辅」？

要交付一套「给完全非技术用户也能一键部署」的跨品牌 AI 智能家居系统，第一件事不是写代码，而是选对地基：HA 以哪种形态安装、Agent 放在哪一层、设备怎么被统一管起来。选错部署方式，后面所有「家电式开箱即用」「免维护」的承诺都会在第一步就破功。本章先给你一张四层架构地图，再解释为什么官方已经弃用的 Supervised 不可能是答案，最后落到「HAOS 为主 + Container 为辅」这条主线，并说明它如何支撑后面每一章的动手任务。

## 1.1 四层架构总览

整个系统按职责切成四层，从上到下依次是用户交互层、智能体层、核心平台层、基础设施层：

```text
┌────────────────────────────────────────────────┐
│ 用户交互层    微信 / HA App / Web / 语音         │
└──────────────────────┬─────────────────────────┘
                       ↓
┌────────────────────────────────────────────────┐
│ 智能体层       Agent（自定义 Add-on）            │
│               + DeepSeek Function Calling       │
└──────────────────────┬─────────────────────────┘
                       ↓
┌────────────────────────────────────────────────┐
│ 核心平台层     Home Assistant Core              │
│               （设备管控 + 自动化引擎）            │
└──────────────────────┬─────────────────────────┘
                       ↓
┌────────────────────────────────────────────────┐
│ 基础设施层     HAOS（Supervisor + Docker）       │
│               （Add-on 商店 + 快照 + OTA）       │
└────────────────────────────────────────────────┘
```

四层拆分的价值在于每一层都能独立演进：换掉 DeepSeek 换成别的模型，不影响设备层；给用户加一个语音入口，不碰智能体核心逻辑；底层从一台 HAOS 主机迁移到另一台（快照恢复），上层无感知。对产品而言，这意味着「可替换」和「可测试」。

每一层只干一件事，层与层之间通过定义好的接口（REST API / 工具调用）通信：

- **用户交互层**：用户唯一能感知的一层。微信、HA App、Web、语音音箱都挂在这里，只负责把用户的话转成一条「意图」，不直接碰设备。
- **智能体层**：系统的「大脑」。Agent 以自定义 Add-on 形态跑在 HAOS 的 Supervisor 里（FastAPI 代码与 Container 版完全复用），接收自然语言，用 DeepSeek Function Calling 把「把客厅灯调暗」解析成结构化工具调用，再调 Home Assistant 的 REST API。这一层是「AI 智能家居」区别于「一堆品牌 App」的关键。
- **核心平台层**：Home Assistant Core。所有品牌设备都收敛到这里统一管理，自动化引擎（automation / script / Blueprint）也在这层跑。因为有这一层，上层不需要关心米家、涂鸦各自对应的私有协议。
- **基础设施层**：HAOS（Home Assistant Operating System）。嵌入式只读 Linux，开机即用，内建 Core + Supervisor + Docker；Supervisor 全托管 Add-on 商店、快照备份、约每 8 小时 OTA 自动更新（OS/内核/Supervisor/Core）。「家电式免维护」的承诺就落在这层。

用一句话描述一条控制指令如何从对话走到设备执行：

> 用户在微信说「把客厅灯调暗」→ 智能体层把它交给 DeepSeek 解析成工具调用（`light.turn_on` + brightness）→ 通过 REST API 发给核心平台层 → HA 查实体状态、调用对应品牌设备的 service → 设备执行，结果沿原路返回对话。

## 1.2 官方部署方式现状与 Supervised 弃用修正

### 官方弃用时间线

Home Assistant 官方安装方式在 2025 年发生了结构性变化深度收集 §1、§6：

- **2025-05-22**：官方发布弃用公告；
- **2025.12**：Supervised 与 Core 安装方式正式弃用；
- **2025.12 起**：仅支持 x86_64 / aarch64 架构（i386 / armhf / armv7 已 EOL）。

这意味着任何以 Supervised 为底座的方案，从 2025.12 起都站在一条官方不再维护的路径上。桌面报告最终决策选的是 HA Supervised，而本项目核心约束是「面向完全非技术用户一键部署」——把客户放到官方已弃用的路径上，后续升级、安全补丁都会变成长期负担。所以报告方案必须修正，这是本章选型逻辑的出发点。

### 为什么「非技术用户一键部署」排除了 Supervised

[[Home Assistant 三种部署方式对比与选型.md]] 里已经对比过三种方式，这里只看结论：Supervised 的定位是把整台 Linux 主机交给 HA 来管，依赖严格（仅 Debian 12、不接受衍生版）、维护难度 Expert，天然不适合作为可脚本化、可复制的交付渠道。而官方在 2025.12 之后只剩两条可用路径——HAOS 与 Container。真正能承担「家电式」体验的是 HAOS：嵌入式只读 OS + Supervisor 全托管，开机即用；Container 则是给「已有 Docker 主机、愿意自己维护」用户的次级渠道。

这次弃用对本项目的意义不只是「换一种安装方式」，它直接决定了交付形态：因为 HAOS 是官方推荐路径（"most convenient"），我们才能把 Agent 打包成自定义 Add-on（`config.json` + `Dockerfile` + `run.sh`，Git 仓库托管，Add-on Store 一键安装），让用户在 HAOS 上完全不用碰命令行；如果走 Supervised，交付就会退化成「帮用户装一个严格限定的 Linux + 引导 HA 安装向导」，既不可复现也不可审计。另外要注意，Supervised 只是报告 6 处过时信息中的第 1 处，完整清单会在第 8 章 8.3 节统一回顾。

> [!warning] 别再用 Supervised 做交付渠道
> Supervised 已弃用（公告 2025-05-22，2025.12 生效）。任何基于它的教程、报告结论都要先做时效性修正——这是本项目与桌面报告最大的决策分歧点。

## 1.3 HAOS vs Container 取舍

弃用 Supervised 之后，官方还剩两条可用路径：HAOS 与 Container。本项目「HAOS 为主 + Container 为辅」的分工如下深度收集 §1、§2：

- **HAOS（主）**：官方推荐（"most convenient"），嵌入式只读 Linux，开机即用；内建 Core + Supervisor + Docker。Supervisor 全托管：Add-on 商店、快照备份、自动更新（约每 8 小时 OTA，覆盖 OS/内核/Supervisor/Core）。部署形态：预建 VM 镜像（ova/qcow2/vdi/vmdk/vhdx，UEFI 必需）/ 预刷迷你主机 / 定制盒子；硬件最低 2GB/2vCPU/32GB，推荐 4GB。
- **Container（辅）**：官方正式路径，HA 以容器形态运行，镜像为 `ghcr.io/home-assistant/home-assistant:stable`（Docker Hub 旧镜像自 2023.7 起已弃用，当前稳定版 2026.7.2）。HA Core 与 Agent 同 compose 编排，`install.sh` 一条命令完成部署；服务「已有 Docker/NAS 主机」的用户。

| 维度 | HAOS（主） | Container（辅） |
|------|-----------|----------------|
| 官方定位 | ✅ 推荐（"most convenient"） | 正式路径，官方镜像分发 |
| 核心形态 | 嵌入式只读 OS，整机系统 | 容器化应用，Docker 托管 |
| 内建组件 | Core + Supervisor + Docker | 仅 Core（无 Supervisor / Add-on） |
| Add-on 商店 | ✅ | ❌ |
| 自动更新 | ✅ 约每 8h OTA（OS/内核/Supervisor/Core） | ❌ 手动 pull 重建 |
| 快照备份 | ✅ 托管 | ❌ 手动 |
| Agent 集成 | 自定义 Add-on，Store 一键装 | 同 compose 编排 sidecar |
| 部署动作 | 导入 VM 镜像 / 刷机，开机即用 | docker compose 一条命令 |
| 适用前提 | x86_64 / aarch64 专用主机；最低 2GB/2vCPU/32GB（推荐 4GB）；UEFI | Docker Engine 23.0+（Docker Desktop 不可用） |

两条路径共享的硬性前置：

- **2025.12 起仅 x86_64 / aarch64**——32 位设备（i386 / armhf / armv7）已 EOL，老硬件跑不了新版本；
- **Container 额外要求 Docker Engine 23.0+**（官方明确 Docker Desktop 不可用）；HAOS 内建 Docker，无需单独安装。

另外，Container 次级路线有 3 个安装时就要记住的参数（第 3 章会用到）：

- `TZ=Asia/Shanghai` 必须显式设置；
- `--network=host` 是官方推荐，mDNS / SSDP 设备发现依赖它；
- `--privileged` 仅在需要 USB / Zigbee 设备时开启。

> [!note] 为什么不是「HAOS 或 Container」二选一
> 两者服务的人群不同：HAOS 服务「完全非技术用户、要稳定免维护」的用户，Container 服务「已有 Docker/NAS 主机、愿意自己维护」的用户。本项目主线是前者，Container 作为次级渠道，所以是「主 + 辅」而不是二选一。

> [!tip] 什么时候走 Container
> 当交付对象已经有可用的 Docker 主机（NAS / VPS 也可），愿意接受手动维护（更新、备份、反代都要自己来）时，Container 的「一条命令 + 同 compose 编排」更轻量。它仍然满足 2025.12 起的架构前提，但没有 Add-on 生态与 OTA 自动更新。

## 1.4 选型结论与阅读地图

**最终结论：HAOS 为主 + Container 为辅。** 归纳成三条理由：

1. Supervised 已弃用，不能作为面向非技术用户的交付渠道；
2. HAOS 命中核心约束「完全非技术用户 + 稳定运行」——官方推荐（"most convenient"）、嵌入式只读 OS、Supervisor 全托管（Add-on 商店 + 快照备份 + 约每 8 小时 OTA 自动更新），家电式免维护；Agent 打包为自定义 Add-on，FastAPI 代码复用，Add-on Store 一键装；
3. Container 覆盖「已有 Docker/NAS 主机」用户，作为次级渠道。

## 本章小结

- 四层架构 = 用户交互层 → 智能体层 → 核心平台层 → 基础设施层（HAOS）；一条控制指令从对话走到设备执行要贯穿这四层。
- Supervised 已弃用（2025-05-22 公告 → 2025.12 生效），不能作为面向非技术用户的交付渠道。
- 选型结论 = HAOS 为主 + Container 为辅：HAOS 提供家电式免维护（自动更新 + 快照 + Add-on 商店），Container 服务已有 Docker 主机用户。
- 两个部署方式共享硬性前置：2025.12 起仅 x86_64 / aarch64；Container 额外要求 Docker Engine 23.0+（Docker Desktop 不可用）。
- 全笔记 8 章 = 一条端到端主线，本章是地图，后续每章补上系统的一块。
