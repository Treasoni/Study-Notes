# 第八章 产品化复制与时效性风险

> 笔记类型：实战构建指南（practice）｜学习深度：精通
> 素材来源：深度收集素材 §5、§6、§7、§8
> 前置关联：[[Home Assistant 三种部署方式对比与选型.md]]、[[04_无头onboarding自动化|第四章 无头 onboarding]]、[[07_场景模板与自动化|第七章 场景模板与自动化]]

> [!summary] 本章回答三个问题
> 1. 一个人把系统做出来后，怎么复制给多个客户而不互相污染？
> 2. HAOS 为主的分发怎么做：预建镜像/盒子 + Add-on 仓库 + Blueprint，Container 又降级成什么角色？
> 3. 报告里哪些结论已经过期、哪些决策还悬而未决？

前七章你已经把「一键部署 → 跨品牌接入 → AI 对话 → 场景自动化」整条链路在自己机器上跑通了。但「自己跑通」和「复制给多个客户」之间隔着两道坎：一是怎么在不泄露每个客户密钥、不被上一个客户的设备 ID 污染的前提下重复交付；二是你基于桌面报告得出的一堆结论，哪些会随官方弃用和上游版本迭代而失效。本章就是把这套系统「产品化」的最后一公里：先给出三层分离的复制策略，再说明 HAOS 为主的分发矩阵（预建镜像/盒子 + Add-on 仓库 + Blueprint，Container 降为次级），最后把报告 6 处时效性修正和 9 项待实测决策一次性盘点清楚，并给出一份可执行的维护节奏。

## 8.1 三层分离复制策略（HAOS 适配）

先想清楚一个问题的本质：**多个客户之间的差异到底在哪？** 其实只有两处——密钥（DeepSeek API Key、品牌设备的 token 与网关 key）和实体映射（同一个「客厅灯」，在客户 A 是 `light.living_room_1`，在客户 B 是 `light.living_room_2`）。如果直接复制整个配置目录，会连上一个客户的设备 token、网关 key、实体 ID 一起带过去，既泄露密钥，又把场景模板污染成「只对上一个客户有效」。

所以复制策略的核心是**把差异隔离到最小范围**，用三层结构把「可公开的模板」和「每个客户独有的配置」分开。这套三层结构在 HAOS 上仍然成立，只是每层的载体变了：模板层从「可入库的 config 目录」变成「镜像构建配方 + Add-on 仓库 + 场景包」，运行时层从「docker-compose 拉起的容器」变成「HAOS 上 Supervisor 托管的环境」：

```text
ai-smart-home-system/
├── image-recipe/              # 模板层（主渠道）：镜像构建配方
│   ├── ova/                   # ova 打包配方 → 预建 VM 镜像（导入即用）
│   ├── addons/                # 自定义 Add-on 仓库（Agent，Git/Gitee 托管）
│   │   └── agent/             # agent add-on：config.yaml + run.sh
│   └── scenes/                # 场景包：blueprint yaml / packages
├── customers/
│   ├── _template/             # 客户配置空模板
│   │   ├── .env.example
│   │   └── entity_map.example.yaml
│   └── customer-B/            # 真实客户层：不入库（gitignore）
│       ├── .env               # TZ / DEEPSEEK_API_KEY / HAOS-CN 镜像变量
│       └── entity_map.yaml    # 口语别名 → 该客户实体 ID
├── scripts/
│   ├── build-image.sh         # 产品升级时重跑：打包 ova / 生成预刷镜像
│   └── inject_customer.sh     # 首次引导：注入 .env 与 entity_map（密钥不进镜像）
└── docker-compose.yml         # 仅 Container 次级分发使用，全部 ${VAR} 参数化
```

> 这套树对应 HAOS 主渠道；Container 次级分发沿用第 3 章的 `config.template/` + `scripts/install.sh` 结构，见 8.2 渠道三。

三层各自的定位：

| 层 | 内容 | 是否入库 | 改动频率 |
|------|--------|----------|----------|
| 模板层 `image-recipe/` | 镜像构建配方、Add-on 仓库、场景包 | 是 | 产品升级时 |
| 客户层 `customers/<id>/` | `.env` + `entity_map.yaml` | 否（gitignore） | 每个客户部署时 |
| 运行时层（HAOS） | Supervisor 托管环境 + Add-on 配置 / `.storage` | 否 | 每次部署生成 |

三层的意义在于**让「可以分享」和「必须保密」永远不混在一起**：

- **模板层**没有任何密钥，可以公开、可以入库、所有客户共享一份。第 7 章预置的 `custom_components` 会在 `build-image.sh` 构建镜像时烘焙进去，packages 场景、blueprint 作为场景包放这一层；客户拿到的预建镜像由它构建，密钥从不写入镜像。
- **客户层**只放每个客户独有的两个文件，且由 `.gitignore` 强制排除——绝不提交设备 token、网关 key、客户凭据。HAOS 上这些差异通过**首次引导 + `.env`/Add-on 配置注入**进系统，而不是写死在镜像里。
- **运行时层**是 HAOS 上由 Supervisor 托管的环境：Add-on 配置（HA token / DeepSeek key）由客户在 UI 填写，或由部署方预置进 `.storage`，保证「进到运行时的就是校验过的」。

注入与校验的流程（示意）如下。因为 HA 的 YAML 没有变量机制，多客户的实体引用要在**构建期**用 `envsubst` / jinja2 / codegen 替换，再注入运行时：

```bash
# HAOS 主渠道：首次引导注入 + Supervisor 校验（示意，在 HAOS 控制台/SSH 执行）
inject_customer() {
  local customer="$1"

  # 1. 注入客户 .env 变量（密钥只在运行时注入，不进镜像）
  set -a; source "customers/$customer/.env"; set +a

  # 2. codegen 按 entity_map 重写场景包里的实体引用
  python3 scripts/codegen_entities.py \
    --map "customers/$customer/entity_map.yaml" \
    --dir image-recipe/scenes

  # 3. 校验运行时配置（Supervisor CLI）
  ha core check
}
```

最后一步的 `ha core check` 是上线前必做的闸门：它会把 configuration、场景包、blueprint 全部解析一遍，任何写错的 domain、引用了不存在的实体、YAML 语法错误都会在这里暴露，而不是等客户运行时才发现。

## 8.2 分发矩阵：HAOS 为主，Container 为辅

三层分离解决的是「配置怎么组织」，分发渠道解决的是「成品怎么送到客户手里」。分发以 **HAOS 为主**：主渠道是预建 VM 镜像（ova 打包、导入即用）、预刷迷你主机、定制盒子；场景与 Agent 层通过 Add-on 仓库 + Blueprint 增量下发；git clone + install.sh 保留为 **Container 次级分发**，仅适合已有 Docker 主机用户。三类分发方式的适用对象完全不同：

| 维度 | 预建镜像 / 预刷主机 / 盒子（主） | Add-on 仓库 + Blueprint（增量） | git clone + install.sh（Container 次级） |
|------|--------------------------------|----------------------------------|------------------------------------------|
| 交付对象 | 整套 HAOS 环境（含预置组件/场景/Agent） | 仅场景层或 Agent 层，增量下发 | 整个系统（config + Agent + compose） |
| 客户前提 | 能导入 ova / 购买预刷主机或盒子 | 已运行同一套 HAOS | 已有 Docker 主机，能跑命令行 |
| 安装动作 | 导入镜像/开机 → 首次引导注入 `.env` | Add-on Store 添加仓库 → 一键安装 | `git clone` + `./install.sh` |
| 可审计性 | 中（镜像构建配方可审计，密钥不进镜像） | 高（Add-on/blueprint 源码可见） | 高（全量源码可见） |
| 更新方式 | 重新下发新镜像 / Supervisor 更新 | Add-on 仓库拉新版本 / 替换 blueprint | `git pull` + 重新渲染 |
| 典型适用 | 非技术客户、整机交付 | 已部署客户的功能增量 | 已有 Docker 主机的技术型用户 |

**渠道一：预建 VM 镜像 / 预刷主机 / 定制盒子（主渠道）**。这是首版产品的核心交付形态：把 HAOS + 预置 custom_components + 场景包 + Agent Add-on 打包成 ova 镜像，客户导入虚拟机（VMware / VirtualBox / Proxmox）即用；更进一步是预刷迷你主机或定制盒子，开箱即用。客户差异（密钥、实体映射）**绝不能进镜像**——只能通过首次引导 + `.env`/Add-on 配置注入，否则镜像一泄露就等于把所有客户的密钥泄露，这正好又绕回 8.1 的三层分离。复制给第二个客户的流程收敛成三件事：

```bash
# 场景：为第 2 个客户 customer-B 交付一套 HAOS 部署
# 1. 拿到预建 ova 镜像（产品升级时 scripts/build-image.sh 重打）
#    → 客户导入虚拟机 / 预刷主机 / 定制盒子开机

# 2. 首次引导注入客户差异（密钥、实体映射，不进镜像）
./scripts/inject_customer.sh --customer customer-B
#    - 或由客户在 Add-on UI 填 HA token / DeepSeek key

# 3. 场景/Agent 增量下发：Add-on 仓库 + Blueprint
#    客户在 Add-on Store 添加自定义仓库（Git/Gitee 托管）→ 一键安装 Agent
```

**渠道二：Add-on 仓库 + Blueprint（场景/Agent 增量下发）**。这一层做「已有客户的功能增量」。Blueprint 最轻，只把自动化场景做成 yaml 交给已有 HA 的用户，路径 `config/blueprints/automation/<author>/<file>.yaml`，UI 里 `use_blueprint:` 实例化。Agent 分发走自定义 Add-on 仓库：仓库用 Git/Gitee 托管，客户在 Add-on Store 添加仓库后一键安装；Add-on 配置（HA token / DeepSeek key）由客户在 UI 填，或由部署方预置 `.storage`。它不包含 onboarding、不包含整套镜像链——只交付「场景 + Agent」这一增量，适合已部署客户的功能迭代，不适合作为首版交付形态。

**渠道三：git clone + install.sh（Container 次级分发）**。作为次级分发保留给**已有 Docker 主机**的技术型用户或部署团队代跑。项目本身是一个 git 仓库，`config.template` + `scripts` + `docker-compose.yml` + Agent 源码全在里面，放在 Gitee 上（国内拉取更快）。复制给第二个客户 = 克隆仓库 + 建 `customers/<id>` + 跑一条命令。它的可审计性最高——交付给客户的就是仓库本身，部署人员能看到每一步在做什么，排错时可以翻到第 3 章的 `install.sh` 逐段核对。复制流程如下：

```bash
# 场景：为第 2 个客户 customer-B 复制一套 Container 部署（次级分发）
# 1. 克隆项目仓库
git clone https://gitee.com/your/ai-smart-home-system.git ~/ha-deploy
cd ~/ha-deploy

# 2. 创建客户配置层（.env 与 entity_map.yaml 不入库）
mkdir -p customers/customer-B
cp customers/_template/.env.example customers/customer-B/.env
cp customers/_template/entity_map.example.yaml customers/customer-B/entity_map.yaml

# 3. 编辑该客户的密钥与实体映射
vim customers/customer-B/.env            # DEEPSEEK_API_KEY / TZ / 镜像变量
vim customers/customer-B/entity_map.yaml # "客厅灯" → 该客户的 light.xxx

# 4. 一条命令渲染 + 拉起
./install.sh --customer customer-B

# 5. 校验运行时配置（容器内）
docker exec homeassistant hass --script check_config -c /config
```

注意 `install.sh` 与第 3 章的差别：多了 `--customer` 参数后不再交互式询问 `.env`，而是直接读取 `customers/<id>/.env`，再按 8.1 的三层流程渲染。「第二个客户」的部署就收敛成**新建目录 + 填两个文件 + 跑一条命令**，全程不接触第一个客户的任何密钥。这条渠道的定位是「已有 Docker 主机用户」，不再是主渠道。

## 8.3 时效性修正清单回顾

第 1 章提过，桌面报告里有 6 处过时信息需要修正。把这份清单完整回顾一遍，因为它代表一类**结构性风险**：上游（HA 官方 / DeepSeek / 各品牌仓库）随时可能再次弃用或改接口，修正不是一次性动作：

| # | 报告说法 | 2026-08 现状修正 | 对本项目的意义 |
|---|---------|------------------|----------------|
| 1 | Supervised 作为部署底座 | HAOS 为主 + Container 为辅（Supervised 2025.12 弃用） | 部署形态整体改写：主渠道变为预建 VM 镜像/盒子 + Add-on 仓库；`install.sh` 降为 Container 次级分发 |
| 2 | 用 `deepseek-chat` | 改用 `deepseek-v4-flash`（旧名 2026-07-24 停用） | Agent 的模型名、thinking、tool_choice 都要按 V4 写 |
| 3 | ACR 个人版镜像站可匿名拉取 | 不能匿名，须 `docker login`；ghcr 走代理链 | Container 次级分发的镜像分发通道必须重新决策（见 8.4 事项 8） |
| 4 | 预置 `xiaomi_gateway3` | 改用米家官方 `xiaomi_home` | 米家接入换成官方 OAuth 路线，预置清单改写 |
| 5 | 存在 `auto_climate` blueprint | 不存在，需自建或换通用 climate blueprint | 场景模板不能照抄报告，第 7 章已改为自建 |
| 6 | 华为可接入 | 无可靠路径，只给指引（Matter / 反向控制） | 华为从「可接入」降级为「文档指引」 |

注意第 1 和第 2 项是「已经发生且不可逆」的硬变更，第 3-6 项是「事实与报告不符」的修正。这张表的价值在于：它既是本项目与桌面报告所有分歧点的索引，也是以后每次升级前要逐条复核的检查清单。

## 8.4 待实测与产品决策事项（9 项）

如果说 8.3 是「过去的信息需要修正」，这里就是「现在的信息还不够」。9 项事项决定了首版产品敢承诺什么、不敢承诺什么，每一项都对应一个明确的追踪来源：

| # | 事项 | 要实测/决策什么 | 影响范围 | 追踪来源 |
|---|------|----------------|----------|----------|
| 1 | HAOS-CN 依赖与镜像链大陆实测 | `haos` 安装源 / 镜像站在中国大陆家庭宽带的真实可用性 | 镜像构建配方、首次引导默认值 | HAOS-CN 镜像站 / 瀚思彼岸论坛 |
| 2 | `xiaomi_home` 弃用告警 | 是否已有 v0.4.8+ 修复 `battery_level`（HA 2026.8 将移除该属性） | HA Core 版本锁定策略、米家接入稳定性 | XiaoMi/ha_xiaomi_home Releases & Issues |
| 3 | 美的 V3 token | NetHome Plus Token 接口对中国区新设备是否仍可用 | 美的接入承诺（能否写进 MVP 向导） | wuwentao/midea_ac_lan（Issue #530） |
| 4 | onboarding API 有效性 | 在 2026 stable（2026.7.x）上是否仍有效 | 「5 分钟承诺」边界、是否回退 `.storage`/浏览器向导 | home-assistant.io onboarding / HA Community |
| 5 | 第三方工具依赖取舍 | 是否接受 `Xiaomi-cloud-tokens-extractor`、`msmart-ng` 取 token | 合规风险、首次人工步骤清单 | 各工具仓库 |
| 6 | 首版主推品牌组合 | 阶段 C 品牌向导先做哪几个品牌 | 向导工作量、5 分钟承诺范围 | 设备保有量调研 |
| 7 | Agent 分发通道 | 自定义 Add-on 仓库（Git/Gitee）托管的地址与更新策略 | Agent 安装体验、客户密钥安全 | Add-on 仓库托管规范 |
| 8 | 镜像构建（ova 打包） | 用哪套配方（Packer/OVF）构建预建 VM 镜像、Container 镜像经哪里分发 | 主渠道交付形态、客户导入兼容性 | 镜像构建工具链 / ACR 文档 / Docker Hub |
| 9 | 盒子/硬件供应链 | 预刷迷你主机、定制盒子的选型与合作 | 整机交付承诺、硬件成本 | 硬件供应链调研 |

前 4 项是**纯技术待实测**，实测结论直接改写第 2、5 章的默认参数；后 5 项是**产品决策**，决定首版的承诺边界和合规姿态。特别是第 5 项，使用第三方工具提取品牌 token 属于「借道」官方未提供的接口，要在 MVP 阶段就明确接受程度，而不是等上线后再补。

**阅读与维护建议**：上游变更节奏并不一致——HA 官方每月一个大版本，breaking changes 集中在 release notes；DeepSeek 的模型与定价在 api-docs.deepseek.com 更新；各品牌仓库以 tag 和 Issue 为主。建议按这个节奏维护：

1. **季度复查**：每季度把 8.3 的 6 项清单和 8.4 的 9 项事项各过一遍，看是否有新的弃用公告或修复。
2. **升级前强制检查**：每次 HA 大版本升级前，必须重跑一遍 8.3 清单——升级本身就可能是新的「时效性修正」。
3. **订阅关键来源**：home-assistant.io release notes、api-docs.deepseek.com、`XiaoMi/ha_xiaomi_home`、`wuwentao/midea_ac_lan`（Issue #530）、`xZetsubou/hass-localtuya`、`mmalolepszy/hon-revived`、HAOS-CN 镜像站。
4. **用版本锁定防漂移**：第 7 章的做法继续沿用——`manifest.json` 的 version 对齐发布 tag，CI 校验防漂移；无 HACS 就无自动更新，漂移只能靠构建期校验兜住。
5. **实测一项销项一项**：9 项待实测里每解决一项，就回到深度素材对应章节更新状态，避免「以为测过、其实没测」。

## 本章小结

- 三层分离复制策略 = 模板层（镜像构建配方 + Add-on 仓库 + 场景包，可入库）→ 客户层（`.env` + `entity_map.yaml`，不入库）→ 运行时层（HAOS 上 Supervisor 托管），把客户差异隔离到最小范围，密钥永不混入模板。
- 分发以 HAOS 为主：预建 VM 镜像 / 预刷主机 / 盒子（主渠道）+ Add-on 仓库 + Blueprint（场景/Agent 增量）；git clone + install.sh 降为 Container 次级分发，仅适合已有 Docker 主机用户。
- 报告 6 处时效性修正已全部采纳，它们代表一类「上游弃用/改接口」的结构性风险，需要持续跟踪而非一次性修复。
- 9 项待实测/决策事项决定首版承诺边界，每项都有明确追踪来源；第 5 项第三方工具依赖属于合规决策，要尽早定调。
- 维护建议 = 季度复查 8.3/8.4 清单 + 每次 HA 大版本升级前强制检查 + 订阅关键上游来源 + 版本锁定防漂移。
