## 第 2 章 把网盘聚合进来

第 1 章结束时，你有了一个能登录、数据能持久化的 OpenList 实例——但网页端里空空如也。OpenList 本身不存放你的文件，它只是把你已有的存储（本地目录、对象存储、网盘）**一条一条挂进来**，对外合成一个统一目录。本章要解决的就是这件"挂载"的事：`Mount Path` 这个字段到底填什么、留空或重名会看到什么官方报错、排序与令牌复用怎么用、缓存与代理这两个容易混的开关怎么分，最后用一个本地存储驱动把整条流程走通一次。

> [!warning] 执行环境先对齐
> 本章仍以 **Linux 宿主机 + Docker（承接第 1 章）** 为准。你本机是 Windows + Git Bash，本章出现的路径示例如 `/root`、`C:` 是官方文档为两套系统各给的示例，请按你实际运行 OpenList 的环境来理解（详见 2.6 的说明）。本章**不含可执行命令**——素材性质就是界面配置字段加官方报错原文，不硬凑命令。

本章主干来源是 OpenList 官方文档页 [OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)，示例驱动来自 [OpenList Docs — 本地存储驱动](https://doc.oplist.org/guide/drivers/local)，用户字段来自 [OpenList Docs — 用户与权限](https://doc.oplist.org/guide/advanced/user)。下文凡加引号的文本均已回源逐字核对。

### 2.1 存储模型：逐条添加，`Mount Path` 有"三义"

OpenList 的存储不是"自动发现"的，而是你在后台**手动新增一条又一条**。每条存储都必须有一个 `Mount Path`（中文界面叫「挂载路径」）。官方对这个字段的定义一句话讲完了三件事：

> 「挂载项的唯一标识，对外展示的名称，要挂载到的位置。如果要挂载到根目录，请填写 `/`。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

这句话把 `Mount Path` 拆成了三重身份，三义同时成立，缺一不可：

| 身份 | 含义 | 直接后果 |
|---|---|---|
| 唯一标识 | 它在数据库里代表这一条挂载项 | 所以它**不能重名**（见 2.2） |
| 对外展示的名称 | 用户在网页端看到的目录名 | 你填 `我的网盘`，网页端就出现 `我的网盘` 这个目录 |
| 要挂载到的位置 | 这条存储被"安放"在哪个路径上 | 填 `/` 表示挂到根目录 |

因为三义叠在同一个字符串上，`Mount Path` 的值同时决定了"它叫什么"和"它在哪"，这也是后面两条硬约束、以及第 3 章 WebDAV 路径问题的根源。

> [!warning] 待核实（Q6）：`Mount Path` 能不能嵌套？
> 一个自然会冒出来的问题是：`Mount Path` 可否写成嵌套形式（例如 `/A/B`）？如果可以，它会怎样影响对外路径、又是否会进入 WebDAV 的 URL？**官方这一页没有说明**，其余已收集的来源也未涉及。本笔记把这一点标记为 **待核实/未证实**，本章不给结论，也不做推测性断言。
>
> 相关但不同的问题——`Mount Path` 是否构成 WebDAV 路径的一部分（即 `/dav/<挂载路径>` 这种拼接是否存在）——属于**第 3 章**的议题（对应 Q2）。本章只把"`Mount Path` 是对外名称、也可能参与对外路径"这个可能性**提出来**，不下结论。

> [!tip] 大白话
> 把 `Mount Path` 想成给一块硬盘贴的**门牌**。这块门牌同时干三件事：物业用它区分是哪一户（唯一标识）、访客按它找门（对外名称）、它本身就钉在某个位置（挂载位置）。所以门牌不能重复贴，也不能空着——2.2 的两条报错，就是"门牌重了"和"没贴门牌"。

### 2.2 两条硬约束与官方报错原文

官方用两个 `DANGER` 块给了两条必守规则，并各附了报错原文。以下引号内文本均逐字来自同一页。

#### 约束一：不能留空

> 「挂载路径名称是必填项，不能为空，否则会报错：」
> ```text
> Key: 'Storage.MountPath' Error:Field validation for 'MountPath' failed on the 'required' tag
> ```
> 「解决方案：如果要挂载到根目录，请填写 `/`。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

> [!note] 这条报错在本页出现了两次，且两次不完全一样
> 官方页面的英文段和中文段各贴了一遍同一条报错，差异只在一处空格：
>
> | 出现位置 | 原文 | `Error:` 后 |
> |---|---|---|
> | 英文段 | `Key: 'Storage.MountPath' Error: Field validation for 'MountPath' failed on the 'required' tag` | **有空格** |
> | 中文段 | `Key: 'Storage.MountPath' Error:Field validation for 'MountPath' failed on the 'required' tag` | **无空格** |
>
> 除这个空格外，两处的字段名大小写完全一致：结构体前缀 `Storage.MountPath`、字段名 `MountPath`（首字母大写）、标签 `'required'`（全小写）、`'MountPath'` 两侧的单引号也都在。你在日志或界面里搜索这段报错时，**不要因为一个空格对不上就以为找错了**。

#### 约束二：不能重名

> 「不能使用重复的挂载路径名称，否则会报错：」
> ```text
> Failed create storage in database: UNIQUE constraint failed: x_storages.mount_path
> ```
> 「解决方法：使用 [别名](https://doc.oplist.org/guide/drivers/alias) 对多个挂载项目进行聚合。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

这条同样在英文段和中文段各出现一次，但差异**不只是空格**——是句子本身不同：

| 出现位置 | 原文开头 |
|---|---|
| 英文段 | `Failed **to** create storage in database: UNIQUE constraint failed: x_storages.mount_path` |
| 中文段 | `Failed create storage in database: UNIQUE constraint failed: x_storages.mount_path` |

后半句两边一致：`UNIQUE constraint failed: x_storages.mount_path`。

> [!warning] 两条报错的命名风格不同，别混着抄
> 观察两条原文本身即可发现：校验那条用的是 Go 结构体风格的命名（`Storage.MountPath`、`MountPath`，首字母大写），数据库那条用的是 SQL 风格的小写表名与列名（`x_storages.mount_path`，下划线分隔）。它们来自同一个系统里两个不同的检查环节——**一个是字段校验，一个是数据库唯一约束**。比对报错时按各自原样匹配，不要把两套命名相互改写。

**为什么会被唯一约束卡住？** 因为 §2.1 说过，`Mount Path` 兼任"唯一标识"。官方给的解法不是"允许重名"，而是换一种做法：**用别名（alias）存储把多个挂载项聚合起来**——先把各条存储挂到互不重名的路径下，再新建一条别名存储，把这些路径都收进去，对外只暴露一个入口。这条解法只被官方点名给出了链接，本章按原样转述其思路，不展开别名存储的字段细节。

> [!tip] 大白话
> 留空报错，就像表格里的"必填项"没填，系统直接把表单打回来——官方告诉你"挂到根就填 `/`"，`/` 是合法的非空值。重名报错，就像同一个小区里不能有两户门牌号完全一样，物业（数据库）直接拒绝录入；官方给的变通办法不是改门牌规则，而是"建一个大堂（别名存储），把几户的门都开向它"。

### 2.3 `Order` 与 `Remark`：排序、以及令牌复用

这两个字段都是可选的，但各有用途。

#### `Order`（序号）：控制先后

> 「当挂载多个驱动时，用于排序。越小越靠前。可以填写负数。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

两个要点：数字**越小越靠前**（不是越大越靠前）；并且**可以为负**，所以想让某条存储永远排第一，填个负数即可。

#### `Remark`（备注）：放着好看，但首行有特殊语法

`Remark` 的基础用途很简单：

> 「您可以添加备注，以方便管理。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

真正需要记住的是它的**引用（Reference）子功能**：把 `Remark` 的**第一行**写成特定格式，就能让这条存储复用另一条已挂载存储的认证令牌，从而"同一个 Token 多个网盘使用"。

官方给出的用法是：

> 「**使用方法**：在存储设置中将`备注(Remark)`的第一行设置为：**ref:/挂载路径**」
> 「**注意事项**：`ref:/` 为小写英文和符号」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

也就是说，`ref:/mount_path` 里的 `mount_path` 要换成**目标存储实际使用的挂载路径**，并且 `ref:/` 这段前缀必须是小写。

> [!warning] `ref:` 不是通用功能，官方列了支持清单
> 官方明确写了当前支持范围，原文（英文段的驱动名）为：`139Yun`、`AliyundriveOpen`、`189CloudPC`、`123PanShare（ref 123Pan）`、`Cloudreve V3 / V4`；中文段对应写作：中国移动云盘、阿里云盘Open、天翼云盘客户端、123云盘分享（引用123云盘）、Cloudreve V3 / V4。
>
> 注意最后一项 `123PanShare（ref 123Pan）` 的括号注明了它的引用来源是 123 云盘本身。**你挂的驱动不在这个清单里，`ref:` 就用不上**——这一点在排障时很关键：写下 `ref:` 却没生效，先回来核对驱动是否在支持列表内。

> [!tip] 大白话
> `Order` 是排序号，越小越靠前、还能填负号，等于允许你插队。`Remark` 平时就是贴张便利贴；但如果便利贴**第一行**按规矩写 `ref:/xxx`，它就变成"我这张会员卡的信息跟隔壁那户共用"的声明——不过只有官方点名的那几种网盘支持这种共用。

### 2.4 缓存两层：`Cache Expiration` 与 `Custom Cache Policies`

OpenList 有两个跟"缓存时间"有关的字段，层级不同，别当成一回事。

#### 第一层：`Cache Expiration`（缓存过期）——全局一刀切

> 「目录结构的缓存时间。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

官方口径就这一句。请特别留意它管的是**目录结构**：它决定 OpenList 隔多久才去重新拉一次远端目录列表，不是文件内容或传输层缓存。把它调大，目录更"迟钝"但不那么频繁请求远端；调小则相反。

#### 第二层：`Custom Cache Policies`（自定义缓存策略）——按路径细调

> 「目录路径缓存时间（单位：分钟）。可以通过模式匹配来自定义某些文件路径的缓存时间。配置支持通配符：
> - `*` 匹配单层目录。
> - `**` 匹配多层目录。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

**注意单位是分钟**（和 `Cache Expiration` 的表达方式不同）。官方给的示例配置如下（中文版原文）：

```text
/剧集/已完结/*:60
/剧集/更新中/*/**:10
/剧集/归档/**:30
```

官方对每行的解释同样值得逐条对照，因为 `*` 与 `**` 的差别正是最容易用错的地方：

- `/剧集/已完结/*:60`——`*` 只匹配**单层**，所以 `/剧集/已完结` 下**直接**包含的项缓存 60 分钟；**不包含更深层**，例如 `/剧集/已完结/A/B` 不会被这条命中。
- `/剧集/更新中/*/**:10`——这是"单层 + 多层"的组合：它要求路径先有一层（`*`）再多层（`**`），因此 `/剧集/更新中` 下**直属的**目录**不会**命中这条规则，`/剧集/更新中/A/B`、`/剧集/更新中/C/D` 才会。
- `/剧集/归档/**:30`——`**` 匹配多层，所以 `/剧集/归档` 下的内容（**包括任意层级的子目录**）都缓存 30 分钟。

也就是说：`**` 是"往下无限深"，`*` 是"只此一层，不再往下"。把 `*` 误当 `**` 用，最常见的症状就是"深层的目录规则没生效"。

> [!tip] 大白话
> `Cache Expiration` 像整个仓库统一规定"每 X 分钟盘点一次货架"；`Custom Cache Policies` 则是给个别货架单独写规则。`*` 是"只看这一排"，`**` 是"这一排以及下面所有层"——`/剧集/更新中/*/**` 读作"先跨过一排，再往下无限深"，所以恰好贴着 `/剧集/更新中` 的那层反而漏网。

### 2.5 代理两件事别混：`Web proxy` 与 `Webdav policy`

这是本章最容易混的一处，官方甚至专门加了一段说明来澄清。

先看两个字段各自是什么：

- **`Web proxy`（Web 代理）**——「网页预览、下载和直接链接是否通过中转。如果你打开此项，建议你设置 [site_url](https://doc.oplist.org/configuration/configuration#site-url)，以帮助OpenList更好的工作。」
- **`Webdav policy`（WebDAV 策略）**——「是在使用 WebDAV 功能时候的选项」，三选一：

| 取值 | 官方说明 | 代价 |
|---|---|---|
| **302 重定向** | 重定向到真实链接 | 「虽然不会消耗流量，但是不建议共享使用，有封禁账户的风险」 |
| **使用代理 URL** | 重定向到代理 URL | 「会消耗搭建代理URL的流量」 |
| **本机代理** | 直接通过本地中转返回数据 | 「最佳兼容性」，「会消耗搭建 OpenList 设备的流量」 |

官方对默认值的说法是：**有 302 选项时默认为 302，没有 302 选项时默认为本地代理**；想走代理 URL，需要你自己填好并**手动切换**过去。换句话说，默认值取决于该驱动有没有提供 302 能力。

然后是那条专门用来防混淆的说明：

> 「**Web代理**：是使用网页时候的策略，默认为本地代理，如果填写了代理URL并且启用了Web代理使用的是代理URL
> **WebDAV策略**：是在使用WebDAV功能时候的选项……
>
> 两者是不同的配置。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

还有第三个相关字段 **`Download proxy URL`（下载代理 URL）**：

> 「开启代理时不填写此字段，默认使用本机进行传输。」——[OpenList Docs — 驱动通用字段](https://doc.oplist.org/guide/drivers/common)

所以这三个字段的正确心智模型是：**`Web proxy` 管"网页端"的预览/下载/直链，`Webdav policy` 管"WebDAV 功能"，`Download proxy URL` 是它们背后的代理地址；不填地址就走本机中转。**

> [!warning] 典型混淆：改了没生效
> 很多人的第一反应是"我要让 WebDAV 走代理"，然后跑去开 `Web proxy` ——这改的是**网页端**的策略，对 WebDAV 不生效。要影响 WebDAV，必须改 `Webdav policy`，且如果目标是代理 URL，还要**手动把策略切换过去**（默认不一定是它）。第 6 章的排障表会把这条单列一行。

> [!tip] 大白话
> 把 OpenList 想成一栋楼，`Web proxy` 是**大堂访客通道**的规则，`Webdav policy` 是**专属货运通道**的规则——两套门禁各管各的。你在访客通道上加了闸机，货运通道当然不会变；要动货运，得去改货运那套。至于"代理地址"（`Download proxy URL`），就是两条通道共用的那个中转站地址，不填，货就自己扛（本机中转）。

### 2.6 用一个真实驱动走通：本地存储

现在把上面的字段落到一条真实存储上。**建议先用本地存储驱动（Local storage）打通闭环**——这样一旦出问题，你能确定问题出在"配置"上，而不是"网盘驱动 / 鉴权"上。等本地这条路走顺了，再换成真实网盘驱动。

本地驱动的官方定位是：

> 「支持挂载本机的目录。」——[OpenList Docs — 本地存储驱动](https://doc.oplist.org/guide/drivers/local)

#### 必填：`Root folder path`（中文界面「根文件夹ID」）

> 「您要挂载的文件夹的路径。 例如：
> - Linux: `/root`
> - Windows: `C:`」——[OpenList Docs — 本地存储驱动](https://doc.oplist.org/guide/drivers/local)

字段名在英文界面是 `Root folder path`、中文界面是「根文件夹ID」——"文件夹ID"这个译名容易让人误以为要填某种 ID，其实它要的就是**一个目录路径**，官方示例里 Linux 填 `/root`、Windows 填 `C:`。

> [!warning] 注意"本机"是容器视角（本笔记的编排说明，非官方示例）
> 官方只说"挂载**本机**的目录"。第 1 章我们是把 OpenList 跑在 Docker 容器里的，所以这里的"本机"指的是 **OpenList 进程所在的环境（容器内部）**，而不是你按下鼠标的那台 Windows。官方本地驱动页**完全没有涉及容器场景**，所以这里有两件事要如实说明：
> - 如果你想挂载宿主机的某个目录，需要把该目录**额外映射进 OpenList 容器**——这一步不在官方本地驱动页的范围内，本笔记不虚构命令，留作你自己按第 1 章的 `-v` 语法扩展。
> - 只想**先把链路跑通**时，更省事的做法是把 `Root folder path` 指向一个容器内**确实存在且有文件**的目录。第 1 章已经有一个现成的映射：宿主机目录映射到了容器内 `/opt/openlist/data`。你在宿主机那个目录下新建一个测试子目录、放一个文件进去，容器内同一路径下就能看到它——用这条既有映射做冒烟测试，不需要动任何 Docker 配置。
>
> 上面这段"用第 1 章映射做测试"是**由第 1 章的映射事实 + 本地驱动字段拼装出的编排**，官方并未给出此示例。

#### `Recycle bin path`（回收站路径）：留空 = 永久删除

> 「回收站的路径，如果为空则永久删除或保持“永久删除”
> 如果填写此路径在删除本地存储文件时会将文件移动到此文件夹內，让你有一次后悔的机会。」——[OpenList Docs — 本地存储驱动](https://doc.oplist.org/guide/drivers/local)

填写方式与挂载路径同理，官方同样给了 Linux `/root`、Windows `C:` 两个示例，并给了一条非常实在的提醒：

> 「如果不知道是否填写正确，可以先自己在测试环境进行测试一下再进行生产环境使用」——[OpenList Docs — 本地存储驱动](https://doc.oplist.org/guide/drivers/local)

这条提醒值得当回事：`Recycle bin path` 之所以危险，是因为它填错时不会立刻报错，而是等到你删文件那一刻才暴露——要么没进回收站直接删了，要么进了个你找不到的目录。

#### 缩略图：视频要 `ffmpeg`，PDF 缩略图仅 macOS

本地存储的视频缩略图：

> 「需要使用 `ffmpeg` 工具来添加.」——[OpenList Docs — 本地存储驱动](https://doc.oplist.org/guide/drivers/local)

这正是第 1 章讲镜像标签时提过的 `latest-ffmpeg` 后缀的用武之地——官方镜像文档里那张预装环境表写明 `ffmpeg` 后缀是「预装 ffmpeg 的镜像，用于本地存储缩略图」。也就是说，如果你用默认的 `latest` 镜像，本地视频缩略图会因为缺少 `ffmpeg` 而不可用；要用这条，回去换成带 `-ffmpeg` 的标签。

PDF 缩略图则是另一套限制，官方说明得很清楚：它**默认关闭**，而且**只有 OpenList 运行在 macOS 上时才可用**（调用系统 Quick Look 工具渲染 PDF 首页）。启用步骤是：

1. 开启 `Thumbnail`（缩略图）。
2. 开启 `PDF thumbnail`（PDF 缩略图）。
3. 「建议配置 `缩略图缓存目录（Thumb cache folder）`，避免重复渲染同一 PDF 文件。」

官方并补充了一句成本提醒：

> 「缓存未命中时会执行渲染，可能额外消耗 CPU 和内存。」——[OpenList Docs — 本地存储驱动](https://doc.oplist.org/guide/drivers/local)

所以：Linux 部署 + 本地存储，PDF 缩略图这条路**走不通**（仅 macOS），别在这上面耗时间；视频缩略图则要先换 `-ffmpeg` 镜像。

> [!tip] 大白话
> `Root folder path` 就是"你要挂的是哪个文件夹"，填一个路径而已，别被"根文件夹ID"这名字唬住。`Recycle bin path` 是"删东西先丢哪个垃圾桶"，不填就等于"删了直接烧掉，没有后悔药"——所以官方才叮嘱你先测试。缩略图那两条是**能力问题**：视频封面得有 `ffmpeg` 这个"剪辑小工"在容器里；PDF 封面更挑，只有 macOS 宿主机才雇得起它。

### 2.7 权限前置：知道有这几个字段就够了（详述留第 3 章）

本章先不展开权限体系，但有几个字段和一条安全机制你必须先知道它们存在——否则下一章开 WebDAV 时会一头雾水。

用户侧的三个基础字段（[OpenList Docs — 用户与权限](https://doc.oplist.org/guide/advanced/user)）：

| 字段 | 官方说明 |
|---|---|
| `Username` | 「登录用户名。」 |
| `Password` | 「登录密码。」官方注明「密码对游客是无效的。」 |
| `Base path` | 「用户登录时看到的根路径。」 |

两条与安全直接相关、且容易让你"莫名其妙进不去"的机制：

1. **连续密码错误会封 IP。** 官方原文：「如果连续输入6次密码错误会对当前IP封禁30分钟无法输入账号密码登录，但是不会影响其它IP，只针对输入6次密码错误的IP。」并且给了解法——「重启可立刻消除30分钟封禁时间。」注意它的封禁对象是 **IP，不是账号**，所以别的 IP 不受影响；被自己封了，重启 OpenList 即可立刻解封。
2. **游客账户默认停用。** 官方原文：「游客账户默认停用，如果要启用游客账户请手动关闭停用。」如果你在网上看到 `Guest user is disabled, login please` 这句提示，原因就在这里。

官方在同一页给了一条安全提醒，措辞很重，值得原样记住：

> 「添加用户可能会使其他账户获得文件和服务器侧功能的访问能力。请使用强且唯一的密码，仅授予必要的最小权限，并仅为可信用户创建账户。因用户或权限管理不当而导致的安全事件，由管理员用户承担责任。」——[OpenList Docs — 用户与权限](https://doc.oplist.org/guide/advanced/user)

**权限项本身（`WebDAV 读取`、`WebDAV 管理`、重命名、删除等）是第 3 章的主题**——那里会讲清"为什么 WebDAV 不是找一个总开关，而是给用户开权限项"。本章你只需记住：用户、密码、基本路径、封禁机制、游客停用这几件事确实存在，且都在「后台 → 用户」里。

> [!tip] 大白话
> 这里先给你三块拼图：用户名密码是"进门的钥匙"，`Base path` 是"进门后你能看到几个房间"（房间范围），游客账户则是"给不认识的访客留的那扇门"——默认是关着的。另外还有一条防盗机制：连续输错 6 次密码，这门会**从你所在的这个门牌号（IP）**上锁 30 分钟，重启一下就能立刻解开。

### 2.8 章末可跑产出（自检清单）

本章没有命令，产出一律在 **OpenList 网页后台 + 浏览器**里验证。建议顺序：**先用本地存储驱动打通，再换真实网盘驱动**——这样能把"配置填错"和"网盘驱动/鉴权出问题"这两类原因分开定位。

- [ ] 在后台新增存储页，选择**本地存储驱动**，`Mount Path` 填一个非空且不与已有存储重复的值（想挂到根就填 `/`）。
- [ ] `Root folder path` 按 2.6 的说明，指向一个 OpenList 进程确实能访问、且**里面确实有文件**的目录。
- [ ] 保存成功，**没有**看到 `Key: 'Storage.MountPath' Error: ...` 或 `UNIQUE constraint failed: x_storages.mount_path` 这两类报错。
- [ ] 回到网页端根路径下，**能看到**你刚挂上的那条存储（名称就是 `Mount Path` 的值）。
- [ ] 点进去，**能浏览至少一个文件，并且能下载它**——这是本章链路真正跑通的判据。
- [ ] （可选，验证持久化）重启 OpenList 容器，刷新网页——新增的存储仍在，说明第 1 章的数据目录映射依然有效。
- [ ] （可选）用 `Order` 调一次排序，确认"数字越小越靠前"；如果你有支持清单内的网盘，可以试着在 `Remark` 首行写 `ref:/<目标挂载路径>`。

如果第 4 项卡住（看不到文件），按这个顺序回查：`Root folder path` 指向的目录是不是空的、或根本不是 OpenList 进程能访问的路径（容器场景尤其容易踩，见 2.6 的警告框）；`Mount Path` 是不是填了 `/` 把内容铺在根目录、被你误当成"没挂上"。

### 本章小结

- OpenList 的存储是**逐条手动添加**的模型；每条存储的 `Mount Path` 同时是**唯一标识 / 对外展示名 / 挂载位置**，填 `/` 表示挂到根目录。
- 两条硬约束各有官方报错原文：留空报 `Key: 'Storage.MountPath' Error: ... 'required' tag`（页面出现两次，`Error:` 后空格有无不同）；重名报 `UNIQUE constraint failed: x_storages.mount_path`（英文段为 `Failed to create`、中文段为 `Failed create`），官方解法是**用别名存储聚合**。
- `Order` 越小越靠前、可填负数；`Remark` 首行写 `ref:/挂载路径`（`ref:/` 须小写）可复用令牌，但**仅支持 139Yun、AliyundriveOpen、189CloudPC、123PanShare、Cloudreve V3/V4** 这几种驱动。
- 缓存分两层：`Cache Expiration` 是**目录结构**的全局缓存时间；`Custom Cache Policies` 按路径设**分钟数**，`*` 匹配单层、`**` 匹配多层。
- `Web proxy`（网页端策略）与 `Webdav policy`（WebDAV 策略，302 重定向 / 代理 URL / 本机代理，默认取决于驱动有无 302 选项）是**两个不同配置**；`Download proxy URL` 留空则默认本机传输。
- 示例驱动走的是本地存储：`Root folder path`（中文「根文件夹ID」）、`Recycle bin path`（留空 = 永久删除）、视频缩略图需 `ffmpeg`（对应第 1 章的 `-ffmpeg` 镜像后缀）、PDF 缩略图默认关且**仅 macOS**。
- 权限前置只需记住：用户字段 `Username` / `Password` / `Base path`、连续 6 次密码错误封该 IP 30 分钟（重启即解）、游客账户默认停用；**权限项细节留给第 3 章**。
