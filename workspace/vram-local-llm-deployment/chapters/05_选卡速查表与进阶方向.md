## 选卡速查表与进阶方向

前面四章，你从「显存是什么」一路走到「用 Ollama 跑起本地模型」。最后一章做两件事：把前面所有经验收成一张**能直接照抄的选卡/评估速查表**；再带你看一眼 vLLM、多卡、KV Cache 优化、MoE 这四个进阶名词**各自解决什么问题**——不要求你现在掌握，只求以后听到不慌，知道往哪个方向继续学。

### 5.1 本地部署选卡/评估速查表

#### 5.1.1 按预算/用途的选卡决策表

选卡只有一个核心原则：**先看显存，再看型号**。显存决定装不装得下，其他参数决定快不快。按你的用途和预算，直接对照这张表：

| 你的情况 | 建议显存 | 参考 | 能跑到的模型上限 |
|----------|----------|------|------------------|
| 尝鲜/低预算 | 12GB 起步 | 入门级卡 | 7-8B 模型 Q4/Q8 |
| 日常学习主力 | 16GB | 中端卡 | 14B 模型 Q4（甜点档） |
| 认真跑大模型 | 24GB | RTX 4090 / 5090 级别 | 27B-32B 模型 Q4 |
| 追求更好质量 | 32GB | 高端卡 | 27B-32B 模型 Q8 完整装入 |
| 生产/服务化 | 80GB 以上 | A100/H100 级别 | 大参数模型 + 高并发 |

几个容易踩的边界，提前说清楚：

- **16GB 是多数人的甜点档**：能舒服跑 14B 级模型，性价比最高。
- **24GB（RTX 4090）**：个人本地能跑 27B-32B 的 Q4，是「个人认真玩」的主流选择。
- **70B 级模型**：即便 32GB 也装不下（Q4 也要 40GB 以上），必须靠卸载或生产级硬件，别指望消费级单卡。

#### 5.1.2 口诀：显存够，先升量化档，而不是换更大模型

整个本地部署圈最实用的一句口诀：

> **显存够，先升量化档，而不是换更大模型。**

升级显卡的成本远高于换个量化档位。16GB 卡想把体验往上提，优先把 14B 从 Q4 升到 Q8（质量明显变好，显存还够）；而不是硬上 32B 的 Q3——体积小了但质量下降明显，体验未必更好。显存不够时方向相反：先降档、再换小模型（第 4 章的 OOM 三板斧）。

#### 5.1.3 入门 / 进阶 / 生产三档配置建议

把上面的表浓缩成三档可直接照抄的「标准配置」：

| 档位 | 显存 + 模型 | 工具链 | 适合谁 |
|------|-------------|--------|--------|
| 入门 | 12GB 起步 + 7-8B Q4 | Ollama | 想体验本地模型、低成本跑通全流程 |
| 进阶 | 24GB（4090 级别）+ 27B-32B Q4 | Ollama / llama.cpp | 个人日常主力，兼顾质量与速度 |
| 生产 | 80GB 级 + FP8/BF16 | vLLM | 要服务多个用户、追求高并发与稳定 |

入门和进阶档，Ollama 一条命令就能跑；生产档通常用更高精度的 FP8/BF16 配合 vLLM，牺牲一点显存利用率换质量和吞吐。

### 5.2 进阶方向速览

下面四个名词，都是「显存不够用 / 想塞更大模型」催生出来的解法。逐个认识一下。

#### 5.2.1 vLLM 与 PagedAttention（分页复用 KV Cache）

**解决什么问题**：并发很多请求时，KV Cache 碎片化浪费。

传统推理时，每个对话会独占一块连续的显存存 KV Cache，聊完释放，中间留下很多没法利用的小碎片；请求一多，显存被碎片白白吃掉。**vLLM** 的高吞吐秘密在 **PagedAttention**：把 KV Cache 切成小块「页」，像操作系统管理内存一样按需分配、用完回收、整页复用。实测同环境比 Transformers 快约 2 倍、显存吃得更满。

> [!tip] 大白话
> 把 KV Cache 想成仓库货架。传统方式是每轮对话独占一整柜子，聊完柜子还锁着、别人不能用；vLLM 是共享货架，谁需要就取哪一格，格子随时回收复用。同样的仓库面积，能放下的对话多得多。

一个 vLLM 启动示例（参数来自实战案例：显存利用率 0.96、上下文 1024）：

```bash
# vLLM 启动示例（模型名按你实际拉的替换）
VLLM_USE_V1=0 vllm serve 模型名 --gpu-memory-utilization 0.96 --max-model-len 1024
```

> [!note] 提示
> 消费级单卡也能跑 vLLM（比如 24GB 卡用 NF4 4bit + 双量化硬上 32B），但 vLLM 的主要舞台是高并发服务。个人单机对话，Ollama/llama.cpp 通常更省心。

#### 5.2.2 多卡：张量并行（TP）

**解决什么问题**：一张卡装不下超大的模型。

**张量并行（Tensor Parallelism，TP）** 把权重按卡数分片，每张卡只放 1/TP 的权重，多张卡协作算同一个模型。TP=2 就是两张卡各放一半权重。它需要框架专门支持（vLLM、llama.cpp 等都支持多卡），成本高、配置复杂，个人很少用——主要用于模型大到单卡实在装不下的场景。

> [!tip] 大白话
> 把张量并行想成几个人合伙抬一张超大的桌子。一个人抬不动，就切成几块、每人抬一块，步伐一致地往前走。每人的负担只有原来的 1/TP，但所有人必须配合好，少了谁都不行。

#### 5.2.3 KV Cache 量化（NVFP4）与 GQA

**解决什么问题**：KV Cache 太大，吃掉本可留给权重的显存（第 2 章的「显存杀手」）。

两条路线，一条是「事后压缩」，一条是「天生省」：

- **NVFP4（KV Cache 量化）**：NVIDIA 把 KV Cache 从 16-bit/FP8 量化到 4-bit，显存比 FP8 再降约 50%，同样显存能容纳的上下文容量翻倍，精度损失小于 1%。目前主要面向 Blackwell 数据中心卡。
- **GQA（分组查询注意力）**：模型架构层面的优化，多个查询头共享一组 Key/Value，从源头减少 KV Cache 体积。选模型时，名字里带 GQA 的架构天生更省 KV Cache。

#### 5.2.4 MoE：下载小、显存不小的「陷阱」

**解决什么问题**：同样是「聪明的大模型」，MoE 架构下载小、算得快，但显存需求并不小。

**MoE（混合专家）** 模型总参数很大，但每次计算只激活一部分「专家」。问题在于：**推理时必须把全部权重都加载进显存**，一个都不能少。所以它有个反直觉的坑——下载体积小，不代表显存需求小。举个例子：一个 16B 的 MoE 模型，下载才 6GB，实际要占约 23GB 显存。判断装不装得下，永远看**总参数量 × 精度**，别被下载体积骗了。

> [!tip] 大白话
> 把普通模型（Dense）想成一栋普通房子，MoE 想成一栋大别墅。别墅整栋都要装修到位（显存必须装下全部权重），但住的时候每次只开一个客厅（只激活部分专家），所以住着不费电（算得快）。装修费按整栋算、电费按开灯的房间算——这就是「下载小、显存不小」的原因。

真实例证：DeepSeek-R1 有 671B 参数，加载时要装下全部 671B 权重，但激活计算只按约 37B 算——大参数的「月租」一分不少，省的是「按量计费」那部分。

### 5.3 学习路径延伸：下一步去哪

走完这条路线，你已经具备：

- 分得清显存、内存、硬盘，看懂显卡四大参数；
- 用公式 + 速查表估算「我的显卡能跑多大模型」；
- 用 Ollama 一行命令在本地跑起量化模型，并确认它在用 GPU；
- 遇到 `CUDA out of memory`，按三板斧自己排障。

下一步按兴趣选一条：

- **想深入原理**：精读一两篇官方显存估算文档（如阿里云 PAI），自己动手用公式核算不同模型的显存，把速查表背后的逻辑吃透。
- **想多玩模型**：去 Ollama 模型库、Hugging Face 试不同参数和量化档位的模型，亲手验证第 4 章速查表里的数据。
- **想上强度**：学 vLLM 部署、多卡张量并行、KV Cache 优化，把本地推理从「小玩具」做成「小服务」。
- **想追前沿**：关注 MoE、GQA、NVFP4 这些趋势，理解它们如何在不加显存的前提下塞进更大的模型。

---

显存是 GPU 的专属工作台——装不装得下看容量，快不快看带宽；大模型的显存账单，是权重的固定月租加上 KV Cache 的按量计费；量化是把大模型塞进显存的钥匙；而这张速查表，就是你以后每次动手前的对照清单。恭喜你走完这条路线，现在可以打开终端，跑出属于自己的第一个本地模型了。
