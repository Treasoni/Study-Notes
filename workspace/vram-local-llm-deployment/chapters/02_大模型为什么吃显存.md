## 大模型为什么吃显存

上一章认识了显存这张「GPU 专属工作台」。这一章来解决真正让你头疼的问题：为什么一个开源大模型，下载才几个 GB，跑起来却要吃掉十几 GB 甚至几十 GB 显存？答案是一张**显存账单**——它不是一整笔巨款，而是两栏：**权重（固定月租）+ KV Cache（按量计费）**。看懂这两栏，你就掌握了本地跑模型的核心心法。

### 2.1 模型为什么必须装进显存才能跑

先回到第 1 章那条铁律：**GPU 只能读显存里的数据计算。** 大模型本质上是一张巨大的「权重表」，模型每次回答都要对着这张表反反复复做乘法运算。权重表放在哪，直接决定了 GPU 干活快慢：

- 放在**显存**里：GPU 随手就能取，算得快。
- 放在**内存**里：GPU 够不着，只能靠 CPU 慢吞吞地搬运，速度慢几十上百倍，几乎不可用。

所以「模型必须装进显存才能跑」不是偏好，是硬约束。装不装得下，就成了本地部署的第一道门槛。

### 2.2 权重：模型的「固定身价」

权重（weights）是模型「学会的知识」，也是占显存的大头。它的特点是：**不管你有没有在对话，只要模型一加载，这部分显存就先被占掉了。** 就像房租，不住人也得按月付。所以我们叫它「固定月租」。

> [!tip] 大白话
> 把大模型的显存账单想成手机话费。权重 = 固定月租，只要套餐在就天天扣，不管你这月打没打电话；KV Cache = 按量计费的流量，用多少算多少。看本地部署够不够显存，先把月租这项算清楚，再估流量。

#### 2.2.1 参数量：7B = 70 亿个参数

权重大小由两件事决定，第一件是**参数量**。参数（parameter）是模型里一个个可调整的「旋钮」，模型的智能就藏在这几十亿个旋钮的取值里。7B = 70 亿（Billion）个参数，30B、70B 同理。参数量越大，模型越「聪明」，但要装的显存也越多。

> [!tip] 大白话
> 把模型想成一本超大的词典，每个参数是一个词条。词典越厚（参数量越大），能解释的词越多、越聪明，但这本词典本身就占地方。注意：这里只说了「词典有多厚」，每个字用几格墨水来写，是下一小节的事。

#### 2.2.2 精度：FP32/FP16/INT8/INT4 每参数占几个字节

决定权重占多少显存的第二件事，是**精度**——每个参数用几个字节来存。同样的参数，存得越「精细」占得越多：

| 精度 | 每参数字节数 | 直观叫法 |
|------|-------------|----------|
| FP32 | 4 字节 | 全精度 |
| FP16 / BF16 | 2 字节 | 半精度（消费级标准） |
| INT8 | 1 字节 | 8bit 量化 |
| INT4 | 0.5 字节 | 4bit 量化 |

> [!tip] 大白话
> 精度决定每个词条用几格墨水来写。FP32 用 4 格，写得最精细；FP16 用 2 格；INT4 只用半格，字迹潦草但省纸。同一本词典，用不同精度写，体积差好几倍。所以 7B 模型用 FP16 要 14GB，用 INT4 只要 3.5GB——这就是第 3 章「量化」的威力。

#### 2.2.3 估算公式：权重显存 = 参数量 × 每参数字节数

把两件事乘起来，就得到权重显存的估算公式：

```text
权重显存（GB）= 参数量 × 每参数字节数
```

注意单位换算：参数量是「个」，每参数字节数是「字节」，乘出来是字节；要除以 10 亿才换算成 GB（10 亿字节 ≈ 1GB）。

#### 2.2.4 动手算：7B FP16 ≈ 14GB、32B ≈ 60GB

拿公式算两个最常见的例子：

- **7B FP16**：70 亿 × 2 字节 = 140 亿字节 ≈ **14GB**。
- **32B FP16**：320 亿 × 2 字节 = 640 亿字节 ≈ **60GB**。

看到差距了吗？一个 7B 模型的「固定月租」就是 14GB——这已经超过很多人的 8GB 显卡总显存了。这也解释了第 1 章里「32GB 内存 + 8GB 显存照样报 CUDA OOM」：那 14GB 权重必须住进 8GB 的显存，内存再大也无济于事。

### 2.3 KV Cache：每次对话的「临时便签」

权重是固定月租，但模型一旦开始「聊天」，就会产生第二笔开销：**KV Cache**。它像每次对话临时贴上的便签，随聊随长、随增随占，所以是「按量计费」。

#### 2.3.1 为什么需要它（以存代算，避免重复计算）

模型生成回答是「一个字一个字往外蹦」的。每生成一个新字，模型都要重新「看一眼」已经生成过的整段内容。如果不缓存，生成 100 个字，前面每个字都要被反复重算，总计约 5050 次计算；有了 KV Cache，把算过的 Key 和 Value 存下来，新字只需接着算一次，总共只要 100 次。

一句话：**KV Cache 是以存代算**——花一点显存，换掉大量重复计算，否则模型慢到没法用。

> [!tip] 大白话
> 把 KV Cache 想成读书时的书签。没有书签，每次读到哪了都要从头翻一遍；插上书签，直接翻到上次的位置接着读。每轮对话都会多插一个书签，对话越长、书签越多，占的书页（显存）也越多。

#### 2.3.2 随上下文长度 × 并发线性增长

KV Cache 的大小由两个因素相乘决定：**上下文长度**（一次对话多长）和**并发数**（同时几个对话）。两者都是「每涨一点、显存线性涨一点」。

一个直观例子（Llama-3 70B 级别）：上下文 4K 时，每个请求约 160MB；上下文拉到 32K，每个请求约 1.28GB——翻了 8 倍。如果同时有几十个请求在跑，KV Cache 会迅速膨胀，甚至反超权重成为显存大头。

> [!tip] 大白话
> 把显存想成一个停车场。权重是几辆常驻大车，一直占着固定车位；KV Cache 是每来一个请求就多停一辆的小车。上下文越长，每辆车越大；并发越高，车越多。车位（显存）是固定的，车一多必然停不下。

#### 2.3.3 长上下文为什么是显存杀手

上下文窗口（context window）是模型一次能「看到」多少内容的能力，常被厂商当卖点宣传：32K、128K 甚至更多。但窗口开多大，KV Cache 就线性涨多大——**「支持长上下文」和「长上下文不占显存」是两回事**。

实际部署时，把上下文参数从 2048 拉到 4096、8192，KV Cache 跟着翻倍涨。很多人一上来把上下文拉满，结果 12GB 的卡直接被撑爆，报错 `CUDA out of memory`。这几乎是本地部署第一大坑。

> [!note] 进阶脚注
> 业界也在解决 KV Cache 膨胀：NVIDIA 的 NVFP4 技术把 KV Cache 压到 4bit，显存比 FP8 再降约 50%，同样显存能容纳的上下文容量翻倍（面向 Blackwell 数据中心卡，消费级暂用不上）。这是后话，入门阶段知道「KV Cache 是线性增长」就够。

### 2.4 推理还有哪些开销：激活值 + 框架开销 + 安全系数

权重 + KV Cache 是两大主力，但完整账单还有三笔零头，加起来也不能忽略：

- **激活值（activations）**：前向计算时层与层之间传递的中间张量，随模型跑动临时产生。简化估算约为权重的 10%（7B 模型、2048 上下文，约 1.4GB）。
- **框架开销**：CUDA 驱动、推理引擎本身也要占 1-2GB 显存。
- **安全系数**：估算只是起点，显存会被系统悄悄吃掉一点（比如 24GB 卡实际可用约 22GB），所以建议按一定比例预留余量。

推理的完整估算式可以写成：

```text
推理显存 ≈（权重 + KV Cache + 激活值）× 安全系数 + 框架开销
```

| 组成 | 特点 | 估算参考 |
|------|------|----------|
| 权重 | 固定月租，加载即占 | 参数量 × 每参数字节数 |
| KV Cache | 按量计费，随上下文 × 并发涨 | 上下文越长、并发越高越大 |
| 激活值 | 计算时临时产生 | 简化约权重的 10% |
| 框架开销 | 引擎本身占用 | 约 1-2GB |
| 安全系数 | 兜底余量 | 推理建议 1.2-1.5 倍 |

### 2.5 顺带一提：训练 vs 推理（为什么训练更吃显存）

前面算的都是「推理」——用现成模型回答问题。如果是「训练」——教模型学习，账单会暴涨好几倍。差别在于训练除了权重，还要额外保存：

- **梯度（gradient）**：每次更新权重前的「草稿」，告诉模型往哪个方向调。
- **优化器状态（optimizer state）**：Adam 等优化器为每个参数额外保存的「账本」，每参数约 8 字节。

> [!tip] 大白话
> 把训练想成做一道超难的数学题。推理只是抄答案（用权重），训练要从头推导：既要写过程草稿（梯度），又要记账对账（优化器状态），占的地方自然比「只看答案」多好几倍。LoRA、QLoRA 这类微调技巧，就像只对答案的最后一页做小改动，不用重写整本书，所以省显存。

用官方数字对比最直观（7B 模型）：

| 任务 | 大致显存需求 |
|------|-------------|
| 推理（FP16 权重） | 约 14GB |
| 全参数微调 | 约 87GB |
| LoRA 微调 | 约 18GB |
| QLoRA（4bit）微调 | 约 7.6GB |

这就是为什么训练通常是多卡数据中心的活，而消费级显卡一般只做推理；就算微调，也要优先选 LoRA/QLoRA 这类省显存的方案。

---

**本章小结**

- 大模型必须整体装进显存才能跑，因为 GPU 只能读显存里的数据。
- 显存账单有两栏：**权重（固定月租）+ KV Cache（按量计费）**。
- 权重显存 = 参数量 × 每参数字节数；7B FP16 ≈ 14GB、32B FP16 ≈ 60GB。
- KV Cache 以存代算，随上下文长度 × 并发线性增长，长上下文是显存杀手。
- 完整推理账单 =（权重 + KV Cache + 激活值）× 安全系数 + 框架开销。
- 训练比推理多吃「梯度 + 优化器状态」，7B 全参微调约 87GB，LoRA/QLoRA 可大幅降低。

下一章，面对「原生 FP16 的 7B 模型就要 14GB，普通显卡装不下」这道门槛，我们祭出那把钥匙——**量化**：把大模型像行李一样压缩打包，让它在显存里安家。
