## 方向 1：显存基础

### 精读笔记

#### 资料 1: 一文看懂显卡的显存容量/频率/位宽/带宽（中关村在线 2023-06）
- **核心观点**: 显存是「显卡自带的内存」，四大参数：容量（GB）、频率（MHz）、位宽（bit）、带宽（GB/s）。公式：带宽 = 频率 × 位宽 ÷ 8。容量与性能不成正比：不足会爆显存掉帧，过剩不提升性能。
- **关键数据**: 位宽梯度 128/192/256/384bit；1080P≈6GB、2K≈8GB、4K≥12GB
- **我的笔记**: 「水站」四件套类比可作主线：容量=水池大小、频率=进水管流速、位宽=水管直径、带宽=进水总速度。「容量≠性能」可用 RTX3060 12GB 打不过 RTX3080 10GB 佐证。

#### 资料 2: 别再分不清显存和内存了！一文讲透AI算力的核心秘密（阿里云 2026-01-25）
- **核心观点**: 厨房分工类比：CPU=总厨用内存（中央备料台），GPU=炒锅团队用显存（猛火灶台）。核心规则「GPU 只能读显存里的数据计算，内存再大只是中转仓库」。从服务对象/容量/带宽/设计目标/物理位置/成本六维对比。
- **关键数据**: 显存带宽是内存数十倍（DDR5 50-100 GB/s vs GDDR6X/7 500-1000 GB/s vs HBM3 2-5 TB/s）；HBM 每 GB 成本可达内存百倍；7B 模型约 14GB，32GB 内存+8GB 显存加载报 CUDA OOM；AI 入门 ≥12GB、进阶 24GB、企业 80GB+HBM
- **我的笔记**: 必写三句：①CUDA out of memory = 显存不够，加内存条没用；②爆显存（中途崩溃）vs 爆内存（整机卡顿）现象不同；③本地跑 7B-13B 模型 12GB 显存起步。

#### 资料 3: 什么是显存：GPU计算的核心存储单元解析（百度智能云 2025-09-15）
- **核心观点**: 显存是专为 GPU 设计、与核心直连的高速存储。讲解容量/带宽/位宽公式、渲染管线角色、CUDA 显存管理生命周期、选型优化与故障诊断。
- **关键数据**: RTX 4090 384bit ≈1TB/s；RX 7900 XTX 20Gbps×384bit=960GB/s；位宽 256→128 显存带宽性能降 32%；显存 >95℃ 会出错建议 <85℃
- **我的笔记**: 作「进阶章节」素材：①两个带宽实证例子把公式变具体；②「位宽减半→性能降 32%」证明带宽价值；③「显存是渲染管线的工作台」。

#### 资料 4: 初探GPU：显存有何不同（腾讯云 2025-07-23 / 2026-07 转载）
- **核心观点**: CPU 求低延迟（内存位宽一直 64bit）、GPU 求高带宽（显存带宽 >> 内存）。公式「带宽 = 传输速率 × 位宽」；梳理 GDDR5/6/6-X/7 演进与 HBM 3D 堆叠。
- **关键数据**: CPU 内存位宽 64bit；GDDR7 用 PAM-3；HBM 位宽 1024bit+ 起步
- **我的笔记**: 「高速公路」类比：位宽=车道数、传输速率=时速。GDDR 代际倍速演进适合做时间线小图。

### 核心概念清单
- **显存（VRAM）**: 焊在显卡上、与 GPU 直连的专属高速存储
- **内存（RAM）**: CPU 的系统通用存储，插主板上可升级；与显存分工不同、不可互换
- **显存容量**: 能装多少数据（GB），决定「装不装得下」
- **显存频率**: 工作频率（MHz），决定读写快慢；≠GPU 核心频率
- **显存位宽**: 一个时钟周期能传多少 bit，相当于马路宽度
- **显存带宽**: 每秒传多少数据（GB/s），= 频率 × 位宽 ÷ 8，核心性能指标
- **GDDR**: 消费级主流显存（5/6/7），高频率+大位宽堆带宽
- **HBM**: 数据中心级，3D 堆叠+TSV，位宽 1024bit+，成本极高

### 常见坑
1. 显存≠内存：GPU 只能读显存，加内存条救不了 CUDA OOM
2. 容量≠性能：显存大不代表卡好，带宽更关键
3. 位宽≠频率：两者共同决定带宽；显存频率≠核心频率
4. 显存不是越大越好：够用即可（1080P 约 6GB）
5. 爆显存 vs 爆内存现象不同：前者崩溃报错、后者整机卡顿

### 最佳讲解顺序
1. 建立分工：GPU 做什么 → 显存是 GPU 的「专属工作台」（厨房/猛火灶台）
2. 显存 vs 内存对照表，点明「不可互换」
3. 容量（水池）→ 频率（流速）→ 位宽（水管），用「带宽=频率×位宽÷8」串联
4. 强调带宽是「速度关键」：7900XTX 960GB/s、4090 1TB/s 落地
5. 容量与性能：够用即可 + 爆显存场景 + 分辨率建议
6. 收尾扫盲：GDDR vs HBM + 选购建议（AI 入门 12GB 起步）

## 方向 2：为什么吃显存

### 精读笔记

#### 资料 1: 估算大模型所需显存（阿里云 PAI，官方文档）★ 全篇骨架
- **核心观点**: 基础公式：参数量 × 每参数字节数（FP32=4B、FP16/BF16=2B、INT8=1B、INT4=0.5B）。推理显存 = 权重 + 激活值 + KV Cache + 框架开销(1-2GB)；微调还要加梯度与优化器状态。MoE 需加载全部参数但激活值按激活参数算。估算仅作起点，以 nvidia-smi 为准。
- **关键数据**: 7B FP16 权重≈14GB；7B 全参微调≈87GB、LoRA≈18GB、QLoRA(4-bit)≈7.6GB；激活值与 KV Cache 简化估算各约为权重 10%（7B、s=2048 各≈1.4GB）；Adam 优化器状态每参数 8 字节；DeepSeek-R1-671B 加载全 671B 但激活只按 37B
- **我的笔记**: 「大词典+墨水」：模型是词条，精度决定每个词条用几格墨水，FP16 用 2 格、INT4 用半格，7B 从 14GB 缩到 3.5GB。训练要多带「草稿本（梯度）」和「账本（优化器状态）」。

#### 资料 2: How Much Memory Llama-3?（MLSys，WebFetch 403 已用搜索补全）
- **核心观点**: 强调「峰值显存 ≠ 权重显存」：推理需要 权重 + KV Cache × 并发数。KV Cache 随上下文线性增长，并发升高时 KV Cache 可反超权重。缓解：INT4 量化、GQA、KV Cache 量化、张量并行、vLLM/PagedAttention。
- **关键数据**: Llama-3 70B：FP16≈140GB、INT8≈70GB、INT4≈35GB；KV Cache 4K 上下文 160MB/请求、32K 1.28GB/请求；INT4(35GB)+开销≈45GB 时 4K 下可支持约 280 并发、32K 下仅约 35 并发；70B 训练 FP16 总内存≈630GB 需 8×H100
- **我的笔记**: 「停车场」：权重是常驻大车，KV Cache 是每来一个请求多停一辆的车，上下文越长并发越高车位越紧张。「并发 × KV Cache」视角其他资料少讲，值得复用。

#### 资料 3: LLM 内存需求计算方式（阿里云开发者 2025-10-14，正文 JS 渲染仅摘要，需写作前二次核对）
- **核心观点**: GPU 上 LLM 内存主要由权重和 KV Cache 构成。KV Cache 随 batch 和序列长度线性增长，显著影响显存、限制吞吐与长上下文处理。
- **关键数据**: 7B FP16 权重≈14GB；（聚合）训练内存系数约 18（7B≈126GB）；（聚合）Llama-70B 32K 上下文 10 并发 KV Cache 可达约 800GB
- **我的笔记**: 「固定月租 + 按量计费」：权重是常驻用户，KV Cache 是每次对话的临时便签，上下文越长便签越多。点破「显存账单有两栏」。

#### 资料 4: 使用 NVFP4 KV 缓存优化大批次与长上下文推理（NVIDIA 官方博客）
- **核心观点**: KV Cache 是「以存代算」：缓存已生成 token 的 Key/Value 避免重复计算。NVFP4 将 KV Cache 从 16-bit/FP8 量化到 4-bit，显存比 FP8 再降约 50%，上下文容量翻倍。面向 Blackwell，配合 TensorRT Model Optimizer。
- **关键数据**: 显存比 FP8 降约 50%、上下文容量翻倍；命中率最高 +20%、首 token 延迟最高降 3 倍；精度损失 <1%（Ruler 64K: NVFP4 94.6% vs FP8 95.5%）
- **我的笔记**: 「书签」：KV Cache 是读书书签，没它每次要重翻整本书（生成 100 字要算 5050 次，有缓存只要 100 次）。NVFP4/Blackwell/TensorRT 偏工程，适合作进阶佐证，不入正文主线。

### 核心概念清单
- **参数量**: 模型里可调权重个数，7B = 70 亿个；决定「模型本身多大」
- **精度**: 每个参数用几个字节存（FP32=4B、FP16=2B、INT8=1B、INT4=0.5B）
- **权重显存**: = 参数量 × 每参数字节数，模型的「固定身价」，一加载就占
- **KV Cache**: 缓存已生成 token 的 Key/Value 以免重复计算；随上下文长度 × 并发线性增长
- **上下文长度**: 模型一次能「看到」的 token 数；越长 KV Cache 越大
- **激活值**: 前向计算时层间传递的中间张量
- **安全系数**: 估算额外预留比例（推理 1.2-1.5，训练 1.8-2.5）
- **量化**: 把参数或 KV Cache 降到更低精度换显存
- **优化器状态**: 训练时 Adam 额外保存的矩（每参数约 8 字节），训练远比推理吃显存
- **张量并行(TP)**: 权重按卡数分片，每卡只放 1/TP

### 常见坑
1. 只算权重不算 KV Cache：长上下文 + 并发时 KV Cache 反超权重照样 OOM
2. 上下文拉满当卖点：窗口开多大 KV Cache 就线性涨多大
3. 把「量化后权重显存」当「实际总需求」：INT4 35GB 还要 + KV Cache + 开销 + 安全系数
4. 拿推理显存套训练：训练系数约 18（7B 全参微调≈126GB，不是 14GB）
5. 忽略 CUDA out of memory 报错本身：报错里的 X GB 就是正要分配的那块
6. 拿官方示例数字套所有模型：不同结构（GQA、MoE）KV Cache 差异巨大

### 最佳讲解顺序
1. 显存是什么，为什么模型必须装进 GPU 显存才能跑
2. 权重显存 = 参数量 × 精度：先算「固定月租」，7B FP16 ≈ 14GB
3. 量化：把行李压缩，月租降到 1/4
4. 运行时还要什么：激活值 → KV Cache（书签/便签）
5. 上下文长度为什么是显存杀手：KV Cache 线性增长 × 并发
6. 训练 vs 推理：训练多带梯度 + 优化器状态
7. 兜底：安全系数；排障顺序「量化 → 降并发 → 降上下文 → 并行分片」
8. 进阶彩蛋：GQA / NVFP4 / PagedAttention

## 方向 3：本地部署实战

### 精读笔记

#### 资料 1: 国产开源 LLM 本地部署 2026 完整指南：硬件怎么挑（ofox 2026）
- **核心观点**: 选硬件先分清 Dense 与 MoE：Dense 全部参数参与计算，MoE 显存必须装下全部权重、算力只看激活参数。显存门槛由「参数量 + 量化档位」决定。个人学习用 RTX 4090/5090 + 27B Q4_K_M；生产用 FP8/BF16 + vLLM。
- **关键数据**: 27B Dense Q4_K_M≈18GB、4090 约 25 tok/s@64K，BF16≈54GB 需 80GB 卡；每 10 亿参数：BF16≈2GB、FP8≈1GB、INT4≈0.5GB；GLM-5.1 754B MoE：BF16≈1500GB→FP8≈754GB→INT4≈377GB→Q2_K≈180GB；16GB 卡只能跑 Q3_K_M 约 20 tok/s；Q4 相对 BF16 能力下降 1-3%，严肃使用建议 Q5_K_M
- **我的笔记**: 「房子 vs 客厅」讲 Dense/MoE：MoE 整栋房都要装修（显存放全部权重），每次只开一个房间（激活专家少）算得快。选卡口诀「先看显存、先量化」。

#### 资料 2: Ollama 官方文档 Importing a Model（官方文档，原 import.md 已改名 import.mdx）
- **核心观点**: 官方权威说明如何把 GGUF/Safetensors 模型或 LoRA 导入 Ollama：写 Modelfile（FROM + ADAPTER），再 `ollama create` 构建；支持 `-q/--quantize` 一键自动量化。
- **关键数据**: 导入 GGUF：Modelfile 写 `FROM /path/to/file.gguf` 然后 `ollama create my-model`；自动量化：`ollama create --quantize q4_K_M mymodel`；支持档位 q8_0、q4_K_S、q4_K_M；支持 Llama 2/3/3.1/3.2、Mistral/Mixtral、Gemma 1/2、Phi3
- **我的笔记**: 「菜谱」比喻：Modelfile 是菜谱，FROM 是原料，ollama create -q 是自动加调料（量化）。

#### 资料 3: 万字详解：如何用 Ollama、llama.cpp 把大模型跑在本地消费级显卡（阿里云开发者）★ 动手篇主线
- **核心观点**: Ollama 与 llama.cpp 两条路线。显存估算公式 + Q4_K_M 首选 + 上下文线性吃显存。Ollama 主打一键（注意 tag 带 q4_K_M 避免拉到 FP16）；llama.cpp 用 `-ngl` 控制 GPU 层数，显存不足降级 CPU 只变慢不报错。OOM 排障顺序：降上下文→降量化→offload→换小模型。
- **关键数据**: 显存≈参数量×位宽÷8×1.2；7B Q4≈4GB、14B≈8GB、27B≈15-16GB；同一 7B：Q4_K_M≈4GB vs Q8≈8GB；上下文 2048≈1-2GB、4096/8192 翻倍；`ollama ps` 看 /GPU 字段；llama.cpp `-ngl 33`；8GB 笔记本 partial offload 跑 32B Q4_K_M ≈10.8 tok/s
- **我的笔记**: 比喻：量化档位=压缩率（Q4 像 zip 高压、Q8 像轻压缩）；上下文=临时黑板，越大越占地方。可作实战章节主骨架。

#### 资料 4: RTX4090 单卡跑 Qwen3-32B：4bit 量化 + Transformers 与 vLLM 双方案（阿里云开发者 2026-08-09）
- **核心观点**: 24GB 单卡用 bitsandbytes NF4 4bit + 双量化硬上 32B。原生 BF16 需约 59.7GB，量化后权重约 15GB。vLLM 靠 PagedAttention 分页复用 KV cache，同环境快约 2 倍、显存吃更满，是消费级跑大参数模型的最优解。
- **关键数据**: 32B BF16≈59.7GB；4bit 理论≈14.9GB；双量化再省约 1.5GB；4090 实际可用约 22GB（24GB - 约 2GB 系统占用）；vLLM `gpu_memory_utilization=0.96`、`max_model_len=1024`、`VLLM_USE_V1=0`；实测 vLLM 11.30 tok/s / 22.29GB vs Transformers 5.78 tok/s / 17.93GB
- **我的笔记**: 「行李打包」：BF16 是原包装、4bit 是压缩袋、双量化是压缩袋再抽真空。vLLM 分页 KV cache 比作「仓库共享货架」，Transformers 是「每轮对话独占一柜子」。

#### 资料 5: What AI Models Can You Run with 8/12/16/24/32 GB VRAM?（canitrun.net 略读）
- **核心观点**: 按显存档位给出「能跑啥模型」清单。16GB 是多数人甜点档；24GB（4090）可跑 32B Q4；32GB 的优势是 27B-32B 从 Q4 升到 Q8。70B 即便 32GB 也装不下。显存够时优先升量化档，而非换更大参数模型。
- **关键数据**: 8GB：Gemma3-4B Q4≈5GB、Qwen3-8B Q4≈7.5GB；12GB：Qwen3-8B Q8≈11.5GB、Phi-4 14B Q4≈9.9GB；16GB：Qwen3-14B Q4≈12GB、DeepSeek R1 14B Q8≈16GB；24GB：Qwen3-32B Q4≈23GB；32GB：Qwen3-32B Q8 完整装入、Llama3.3-70B Q4≈43.5GB 需卸载
- **我的笔记**: 直接做成「我的显卡能跑啥」查表。口诀「显存够，先升量化档，而不是换更大模型」。

### 核心概念清单
- **参数量（B）**: 模型的「脑细胞」数量，越大越聪明但越占显存
- **FP16/BF16**: 标准精度，每参数 2 字节；BF16 是消费级常用计算精度
- **量化**: 权重从 2 字节压到 1 字节（INT8）或 0.5 字节（4bit），少量精度换显存减半以上
- **Q4_K_M**: 4bit 量化主流档位（K=k-quants 更精细），效果/速度均衡，社区默认首选
- **GGUF**: llama.cpp/Ollama 的模型封装格式，文件名后缀带量化档位
- **Ollama**: 一键部署工具，`ollama pull/run` 即用，内置 OpenAI 兼容 API
- **llama.cpp**: C++ 底层推理引擎，`-ngl` 控制 GPU 层数，不足时降级 CPU
- **vLLM**: 高吞吐推理引擎，PagedAttention 分页复用 KV cache
- **KV Cache**: 存对话上下文的「便签」，随上下文线性增长
- **OOM**: Out of Memory，显存爆掉程序崩溃的报错
- **offload**: 部分层从显卡挪到 CPU 内存跑，慢但能跑
- **MoE**: 混合专家架构，总参数大但每次只激活部分
- **显存估算公式**: 所需 GB ≈ 参数量（B）× 位宽 ÷ 8 × 1.2

### 常见坑
1. 内存冒充显存：模型被装进 CPU 内存而非显存，慢 10-100 倍；`ollama ps` 看 /CPU 要排查
2. 选错量化档位：Q4 约 4GB、Q8 约 8GB；`ollama pull` 不指定 tag 可能拉到 FP16（7B 直接 14GB）
3. 上下文开太大：默认大上下文把 12GB 卡撑 OOM；降 `--num-ctx 2048/1024` 即可
4. 显存被系统悄悄吃掉：24GB 卡实际可用约 22GB，估算留余量
5. 被 MoE 文件体积骗了：16B MoE 下载才 6GB，实际显存要 23GB
6. vLLM + bitsandbytes 的 V1 引擎不兼容：报量化加载错，需设 `VLLM_USE_V1=0`

### 最佳讲解顺序
1. 先立「显存硬门槛」：公式算出 7B 原生 14GB、32B 原生 60GB
2. 再给「量化这把钥匙」：FP16→INT8→4bit 压缩比与精度损失，点出 Q4_K_M 首选
3. 给「查表」：8/12/16/24/32GB 各能跑啥
4. 给「动手工具链」：Ollama 一条命令跑通（pull → run → ps 看 /GPU）；再讲 llama.cpp 进阶
5. 给「OOM 排障三板斧」：降上下文 → 降量化 → offload/换小模型
6. 进阶「硬上大模型」：NF4+双量化在 24GB 跑 32B；vLLM vs Transformers
7. 收尾「怎么选自己的配置」：按用途与预算决策表，强调「显存够就升量化档」

## 综合分析

### 三个方向的逻辑链（全篇骨架）
1. **概念层**（方向 1）: 显存是 GPU 的「工作台」，容量决定装不装得下、带宽决定快不快 —— 与内存的「不可互换」是零基础第一课
2. **原理层**（方向 2）: 模型占用 = 参数量 × 精度（固定月租）+ KV Cache/激活值（按量计费）；量化是把行李压缩
3. **实战层**（方向 3）: 「我的显卡能跑多大模型」有公式 + 查表 + Ollama/llama.cpp 一条命令落地
