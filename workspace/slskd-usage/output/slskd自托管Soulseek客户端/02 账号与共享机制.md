## 第 2 章 账号与共享机制

第 1 章结束时容器里跑着一个能登进去的 slskd，但它是空转的：`soulseek.username` / `soulseek.password` 还没填，`shares.directories` 还是空的。这一章处理这两个空白，外加三个迟早会撞上的问题——共享到底要满足什么要求、`50300` 入站不通时从哪里查起、以及 Relay（中继）模式到底解决什么。

这一章有个特殊之处：**它要花不少篇幅去写「官方没有说什么」。** Soulseek 没有网页注册入口，共享要求也不在任何一份官方文档里被完整定义，而社区里流传的说法经常被当成官方规则转述。把能确证的和说不准的分开摆，比给一个听起来确定的答案更有用。

### 2.1 账号：官方口径与官方未说明的部分

slskd 配置里唯一没有默认值的必填项，就是一对 Soulseek 凭据：`soulseek.username` 与 `soulseek.password`（`Options.cs:1725`、`:1735`，代码默认都是 `null`）。多数人配到这里时会很自然地去找注册入口——去 slskd 的 Web UI 里找，或者去 slsknet.org 上找。**这两条路都不存在。**

先把结论摆成一张表，后面每一小节展开其中一行：

| 问题 | 官方口径 | 证据状态 |
| --- | --- | --- |
| 官方站点有没有注册入口？ | 没有 | 已证实（可现场复核） |
| 账号创建发生在哪一步？ | 官方从未说明 | 未说明（社区有旁证，须单独标注） |
| 用户名会不会被回收？ | 会：30 天不登录即清除 | 官方 FAQ 明文 |
| 捐款之后呢？ | 永不过期 | 官方站点公告明文 |
| 密码能不能找回？ | 无机制 | 社区协议文档（须标注为社区逆向） |
| 访问权稳不稳定？ | 可随时撤销 | 官方规则页明文 |

> [!warning] 别把 slskd 的 Web UI 账号当成 Soulseek 账号
> slskd 的 Web UI 默认登录是 `slskd` / `slskd`（`config/slskd.example.yml` 的 `web.authentication` 段），这**只是你自己这个管理界面的口令**，和 Soulseek 网络账号无关，也不能用来注册 Soulseek 账号。两套凭据在配置里分属 `web.authentication.*` 与 `soulseek.*`。

#### 官方站点无注册入口的证据

与其论证「没有」，不如给三条可以当场复核的观察。以下都是本次核对时的实测结果（站点为 `slsknet.org`）：

| 观察对象 | 结果 |
| --- | --- |
| `https://www.slsknet.org/news/user/register` | HTTP **403**，页面标题 `Access denied`，正文 `You are not authorized to access this page.` |
| 站点主菜单项 | 共 8 项，**没有 Register / Sign up**：Home、About Soulseek、Download、Forum、Changelog、FAQ、Rules、Donate |
| `/news/user/login` 的用户名栏提示 | `Enter your Soulseek username.` —— 填的是 **Soulseek 用户名本身**，不是另一个「网站账号」 |

第三条尤其能说明问题：登录用的是 Soulseek 身份，而不是「注册一个站点账号再关联 Soulseek」。它从侧面支持「账号不是在这个网站上创建的」。

站点隐私条款里有一段长得像注册条款的句子：

> When you are required to open an account to use or access the Site or Service, you must complete the registration process by providing the complete and accurate information requested on the registration form.

这是法律模板里的**条件句**（「当你被要求开账号时……」），描述的是「如果有注册表单，你得如实填」；而页面上并不存在这样的表单，注册接口本身返回 403。不要把它当作「官方要求你去注册」的依据。

#### 账号创建发生在哪一步：官方未说明（社区旁证单独标注为旁证）

这是本节最容易写错的一点。官方**既没有提供注册入口，也没有在任何文档里说明账号是在什么时候被创建的**。关于「第一次用一个没人用过的用户名登录会发生什么」，只能给出观察与旁证，不能给出官方承诺。

社区旁证（须标注为社区逆向，非官方）：nicotine-plus 仓库维护的协议文档 `SLSKPROTOCOL.md` 把 `INVALIDPASS` 的语义定义为「已存在用户的密码不正确」。这个区分意味着服务端对「全新用户名」与「已占用用户名 + 错误密码」是两套处理，即未占用的用户名会被直接接受，账号实际上在首次登录时被登记。（该文件本机未缓存，此处为上游研究记录所载的社区旁证、未回源原文。）

因此正确的写法是这样一句话：

> 官方既未提供注册入口，也未说明账号创建发生在哪一步；实践中以未被占用的用户名首次登录即被接受。后者是社区旁证，不是官方承诺。

**要明确否掉的反例**：社区里流传很广的「必须先装官方客户端 SoulseekQt 注册一个账号」，在官方站点与官方文档里找不到任何对应表述。这是一个**社区推断，不是官方要求**。官方确实推荐使用官方客户端（见 §2.5 的规则页原文），但那是「推荐使用」，不是「注册的前置条件」——两件事被社区合并成了一句顺口溜。

#### 用户名回收规则与捐款永不过期

这一条官方写了明确规则。官方 FAQ 里关于用户名回收的原文（站点 FAQ 条目，由站点管理员发布）：

> Soulseek recycles usernames after a full month of the person not logging in to conserve server memory. If you do not have privileges, your username will be cleared when 30 days have passed without you logging on or when your privileges have expired, whichever comes last.

拆成表更清楚：

| 情形 | 用户名会怎样 |
| --- | --- |
| 普通账号（无 privileges） | 连续 30 天不登录即被清除，用户名可被他人占用 |
| 有 privileges 但会到期 | 取「满 30 天未登录」与「privileges 到期」中**较晚**的那个 |
| 做过一次性捐款（$5 起） | 用户名**永不过期** |

捐款那条来自官方站点公告原文：

> we've added two small, but permanent perks that come with any one-time donation of $5 or more. First, your username will never expire. We usually clear usernames that haven't been logged into for more than 30 days to conserve on server memory. That won't affect the username under which you've made the donation.

运维含义很直接：**长期不上线的实例，用户名会被回收。** 如果你的实例只是间歇性启动（家里那台 NAS 隔几个月才开一次），要么让它定期上线，要么按捐款规则处理。用户名一旦被回收并被他人占用，原来的下载队列、对方的共享记录、以及别人建立在你用户名上的任何关联都不会跟着回来。

#### 密码无法找回

上游研究记录的协议文档（社区逆向）记载：**没有重置遗忘密码的机制**（同样标记为社区来源、原文未回源）。与上一节的回收规则合起来看：

> 按「密码不可恢复」处理是唯一安全的工作假设。

一处需要如实并列的观察：站点登录页上确实存在 `Request new password` 页签。它与「Soulseek 网络账号的密码」是什么关系，官方没有说明——可能对应站点自身的账号体系，也可能不适用于网络账号。所以这里只能并列陈述，**既不能断言「密码一定找不回」，也不能断言「站点的找回功能就是网络账号的找回」**。操作方法上，把凭据另存一份。

#### 访问权可撤销 / 滥用后果（客观引述，不作劝诫）

官方规则页（`slsknet.org` 的 Rules 页）里三句与运维直接相关，逐字引述：

> Soulseek® is an unsupported service. Access to the SoulSeek® server is a privilege; not a right. It may be revoked at any time, for any reason.

> Server or chatroom abuse will result in your connection being closed and your ISP notified. This may result in a possible account termination.

> Administrators can kill any connections without prior notice for any reason.

对工程实践的含义：服务被官方明确定义为 unsupported，不存在「官方会帮你修」这回事；滥用路径的后果包含通知 ISP；管理员可无预警断开连接，所以日志里的「突然断连」未必是你这边的问题，客户端应当能自动重连。

规则页同时也包含关于版权材料的声明段落，原文可在该页直接查阅。本分册只作技术层面的引述与解释，不就此展开判断，也不构成任何法务意见。

> [!tip] 大白话
> 把 Soulseek 账号想成**网吧的会员号**：你不是在网吧官网上填表注册，而是第一次去前台报一个没人用过的名字，前台看这名字空着，就记给你了。所以「注册」这个动作实际发生在**你第一次登录的时候**——这就解释了为什么全站找不到注册页。
>
> 再往下推两层：你 30 天不出现，前台为了省地方会把名字回收给别人用；你交了 5 块钱办卡，名字就永久保留。卡丢了、密码忘了，前台没有「找回密码」这道流程。
>
> 所以：**不要去 slskd 里找注册按钮，也不要去 slsknet.org 上找**——两处都没有。直接在一个空用户名上填密码登录，就是「注册」。

### 2.2 共享要求：必须分三层写

「不共享会被限速」「共享少于一万个文件会被 ban」——这些说法混在一起讲的时候几乎一定会写错，因为**它们是三层不同的东西，主语各不相同**：

1. **服务器规则层面**——Soulseek 官方对你是否共享文件有硬性门槛吗？
2. **对端客户端的 autoban（自动封禁）**——别人在自己客户端里设的阈值，作用在你的下载请求上。
3. **slskd 内置的 `leechers` 组**——你自己这套 slskd 对「不共享的人」怎么处理。

#### 第一层 —— 服务器规则层面

结论先说：**服务器规则层面没有强制共享门槛。**

逐句核对官方规则页全文后的结果：该页**没有任何**「最低共享文件数」「最低共享容量」条款。规则页只做两件事——声明访问权是特权且可随时撤销，以及列举禁止行为（见 §2.5）。官方 FAQ 里同样没有门槛条款。

有两条与共享相关的表述容易被误读成门槛，单独标出来：

| 表述 | 它实际是什么 | 它不是什么 |
| --- | --- | --- |
| 分布式网络（distributed network）：仅在没有共享任何文件时才建议关闭 | 一条**功能建议**（`docs/config.md` 的 Distributed Network 段） | 不是「不共享就受罚」 |
| 官方客户端里有空共享警告机制 | 官方**客户端**层面的提示（见下一小节） | 不是服务器层面的门槛 |

#### 第二层 —— 对端客户端里用户自设的阈值（社区，须明确标注）

真正让你「下不到东西」的压力，绝大多数来自**对端用户自己的客户端设置**，而不是服务器。

社区讨论里常见的「共享少于 N 个文件 / N GB 就拒绝你的下载请求」，是**那个用户在自己的客户端里设的**，属社区惯例。上游研究记录里出现过「低于数千文件量级即拒绝」这类具体数字，但**这些数字完全由对端用户自定，没有官方标准，也没有统一口径**——同一个数值在 A 那里放行、在 B 那里把你拦下。本机未回源那些具体引用，此处按社区惯例（低可信度）处理，不给数字背书。

标准写法是：

> 「必须共享 X 个文件 / X GB 才能下载」这类阈值**不是官方规则**。把对端 user info 里看到的 autoban 阈值当成官方要求，是最常见的误解。

技术机制是：对端客户端能读到你的用户信息，其中包含你的共享文件数与目录数，部分客户端的用户据此配置了自动拒绝或自动踢队列的规则。这是**单向规则**——由对端施加于你，你无法修改，也无法申诉。

#### 第三层 —— slskd 内置 leechers 组的限速

slskd 自己也有一套「反 leecher」机制，但手段是**分组与限速**，不是拒绝连接。官方配置文档里 `leechers` 组的定义原文：

> The `leechers` built-in group contains users that have not been explicitly added to a user-defined group, are not privileged, and have shared file and/or directory counts less than the configured `thresholds` for the group. By default, users must share at least one directory with one file to avoid being identified as leechers.

关键点：识别阈值是**「至少 1 个目录，且其中至少 1 个文件」**，且这不是随手举例，而是代码默认值：

| 键 | 代码默认值 | 出处 |
| --- | --- | --- |
| `transfers.groups.leechers.thresholds.files` | `1` | `Options.cs:1193` |
| `transfers.groups.leechers.thresholds.directories` | `1` | `Options.cs:1199` |

另一条官方明确的限制：**不能把用户显式塞进内置组**，但可以调整内置组的优先级、槽位数、速度与排队策略（`privileged` 组除外）。

> [!warning] `leechers` 组只影响你**上传**给别人
> 被归入 `leechers` 的后果是「从你这里下载更慢 / 排队位置更少」，**不是你下的东西变慢**。组配置作用于你作为**服务方**的行为，与你能不能下载别人的东西无关。

【EX-12】`slskd.yml`：`leechers` 组阈值片段（取自 [[01 部署与运行]] 的 EX-06 对应段落）

```yaml
# 文件：slskd.yml（取自 [[01 部署与运行]] 的 EX-06 对应段落）
# 位置：transfers.groups —— 内置 leechers 组
transfers:
  groups:
    leechers:
      thresholds:
        files: 1
        directories: 1
      upload:
        priority: 999
        strategy: roundrobin
        slots: 1
        speed_limit: 100
```

`upload` 那几个取值的**语义与取值规则**（包括「数字越小优先级越高」）在 `[[03 日常使用与配置详解#3.7 用户组与优先级（transfers.groups）|§3.7 用户组与优先级]]` 里讲。这里只声明：上面是示例文件里的取值，**不是要你照抄的推荐值**。

#### 官方对"客户端内置 autoban"的立场

官方客户端自己对自动封禁是什么态度？这一条有直接的一手材料。

【EX-35】官方站点公告原文（`node/523`，引用块）

> [!example] 官方站点公告原文（节选）
> One of the most oft requested features over the years, and one I've always resisted strongly is that of automatically banning users who aren't visibly sharing anything from one's download queue.
>
> Still, outright banning has always struck me as too harsh a measure in this case.
>
> And for that purpose I've implemented an automatic empty share warning mechanism in tonight's build.

这则公告由 Nir（SoulseekQt 客户端的开发者）发布，信息量很大：自动封禁不共享用户是**被反复请求的功能**，但开发者说他一贯强烈抵制；理由是「直接封禁在这种情形下过于严苛」；他的替代方案是**空共享警告机制**。

也就是说：服务器不设门槛（第一层），官方客户端也不自动封禁、只做警告（本小节）。**「不共享就封杀」既不是服务器规则，也不是官方客户端的默认行为**——它出现在第三方或用户自行配置的客户端里。

slskd 这边维护者的立场方向一致（GitHub issue #330）：

> I don't think I will add support for auto-banning for leechers because that's a permanent fix for what might be a temporary (and unintentional) problem. I'm working on user groups now, and leechers will be identified and placed in a special group. Users can then set limits for leechers, including disallowing downloads entirely.

即：slskd 不做自动封禁，而是把 leechers 识别出来放进专门的组，让用户自己决定给这个组什么限制。这就是第三层那套机制的设计意图。

#### 三层如何互相作用（一张对照表）

| 层 | 谁定的 | 作用在谁身上 | 具体表现 | 你能改吗 | 来源与可信度 |
| --- | --- | --- | --- | --- | --- |
| ① 服务器规则 | Soulseek 官方 | 所有人 | 没有最低共享门槛；但访问权是特权，可随时撤销 | 不能 | 官方规则页原文（已回源核对全文，无门槛条款） |
| ② 对端客户端的 autoban | 对端用户自己 | 你的**下载请求** | 请求被拒、排队被踢、连接被断开 | 不能（那是对端的客户端） | 社区惯例，低可信度，未回源具体引用 |
| ③ slskd 的 `leechers` 组 | 你（在你自己的 slskd 里） | 连到你的**下载者** | 你能给 leechers 设槽位与限速 | 能 | 官方文档 + 代码默认值（`Options.cs:1193`、`:1199`） |

三层叠加起来的完整图景：① 不设门槛，所以你不共享不会直接导致服务器处置你；② **才是**「不共享就下不到东西」的主要来源，且是别人对你的单向规则；③ 是你对别人的单向规则，且只影响上传侧。

值得写出来的一个反直觉推论：**「多共享 → 能下到更多东西」在 ① 和 ③ 层面都不成立，它成立的原因完全在 ②**——你的共享规模会出现在对端能读到的用户信息里，对端用户按自己设的规则决定放不放你进来。所以「共享」在这个网络里是**社区层面的互惠信号**，而不是服务器强制的义务。

> [!tip] 大白话
> 把 Soulseek 想成一条商业街，共享这件事有三层规矩：
>
> - **① 物业**（Soulseek 官方）：不管你消费多少，只要别闹事就让你在街上走；但物业有权随时请你出去。
> - **② 每家店主**（对端用户）：自己贴告示。有的店主看你兜里空着，就把你拦在门外——**这条告示是店主自己写的，物业从没规定过**。
> - **③ 你自己的店**（你的 slskd）：也有规矩。发现来你店里的人从来不进货（不共享），你会把他安排到**慢车道**（`leechers` 组），给他少的位置和低的速度。这只是「服务慢一点」，不是「不让他进」。
>
> 所以「不共享到底会怎样」，**必须先问清楚问的是哪一层**。把第 ② 层的店主告示当成物业规定，是这几节里最需要纠正的误解。

### 2.3 共享目录怎么配（操作面）

这一节只讲操作面：键写在哪、路径有什么约束、第一次扫描是怎么回事、去哪看扫描状态。共享目录之外那些配置源优先级与列表合并陷阱属于第 3 章。

#### 共享目录键与首次扫描

共享目录的配置键是 `shares.directories`。三种配置方式等价（对应关系见 §1.4）：

| 方式 | 写法 |
| --- | --- |
| `slskd.yml` | `shares.directories` 下的列表项 |
| 环境变量 | `SLSKD_SHARED_DIR`（多路径的分隔符见 `docs/config.md` 的 Shares 段） |
| 命令行 | `--shared` |

路径约束有三条，都是官方文档明写的（`docs/config.md` Shares 段）：

> Paths must be absolute, meaning they must begin with `/`, `X:\`, or `\\`, depending on the system. Relative paths, such as `~/directory` or `../directory`, are not supported. Sharing a root mount on a unix-like OS (`/`) is also not supported.

翻译成三条硬规则：

- **必须绝对路径**，不接受 `~/music` 或 `../music`；
- **不允许把根挂载 `/` 当共享目录**（容器部署里最容易踩：有人写了 `- /:/host`）；
- 路径别名有唯一性约束，重复会被拒绝。

文档还给了两条写法糖：路径前加 `-` 或 `!` 表示**排除**该路径；加 `[别名]` 前缀可以给共享目录起别名。这两条属第 3 章的共享进阶内容，这里只留提示。

【EX-11】`slskd.yml`：共享目录与排除项片段（取自 [[01 部署与运行]] 的 EX-06 对应段落）

```yaml
# 文件：slskd.yml（取自 [[01 部署与运行]] 的 EX-06 对应段落）
# 位置：shares
shares:
  directories:
    - /music
  filters:
    - \.ini$
    - Thumbs.db$
    - \.DS_Store$
  cache:
    storage_mode: memory
    workers: 16                 # 示例文件取值；代码默认 = CPU 核心数（依机器而异）
    retention: ~                # 不自动重扫
```

应用启动后会对共享目录做一次**全量扫描**，结果写进缓存（`docs/config.md` Cache 段）。扫描是 I/O 密集型操作：要读每个文件的元数据（时长、码率、采样率等），并用多个 worker 并发处理。默认并发数不是写死的——代码默认是 `Environment.ProcessorCount`（`Options.cs:885`），有几个核就用几个；上面示例里的 `16` 是官方示例文件给的取值。文档同时提醒 worker 数量并非越大越好。

`cache.retention` 的代码默认是 `null`（`Options.cs:894`），含义是**不自动重扫**。所以改完共享目录别指望它悄悄刷新——需要触发一次扫描。仓库里为此留了开关 `flags.force_share_scan`（`Options.cs:431`），打开后强制做一次共享扫描。改配置后要不要重启取决于配置源与热重载行为，见 §3.4。

#### 默认排除项

这里有一个**文档示例与代码默认值不一致**的地方，正是本分册反复强调「以代码为准」的实例：

| 对象 | 值 | 性质 |
| --- | --- | --- |
| `shares.filters` 的**代码默认值** | `[]`（空列表，即不过滤任何文件） | `Options.cs:757`：`= Array.Empty<string>()`；文档明写 "the list is empty by default" |
| EX-11 里的三条正则 | `\.ini$`、`Thumbs.db$`、`\.DS_Store$` | 官方示例文件与文档给出的**示例值**，不是默认值 |

> [!warning] 这三条排除项不会自动生效
> `\.ini$` / `Thumbs.db$` / `\.DS_Store$` 是官方**示例**里的常见噪音文件排除项，**代码默认是空列表**。不显式写进 `shares.filters`，这些文件一样会被共享出去。反过来说，如果你想共享 `.ini` 文件，不写这条过滤器正好。

两条行为说明（均出自 `docs/config.md` Shares 段）：过滤器是**正则表达式**，匹配默认**大小写不敏感**；`shares.directories` 与 `shares.filters` 是全量替换语义、不做增量合并——后者属第 3 章的配置源坑，此处只做指路。

#### 扫描慢与第 1 章 HEALTHCHECK 宽限期的呼应

第 1 章讲过官方镜像的健康检查：

```dockerfile
# Dockerfile 第 63 行
HEALTHCHECK --interval=60s --timeout=3s --start-period=60m --retries=3 CMD wget -q -O - http://localhost:${SLSKD_HTTP_PORT}/health
```

注意 `--start-period=60m`：容器启动后的**前 60 分钟**内健康检查失败不会被计入 `--retries`，也就是不会把容器标记为 unhealthy。这个异常宽松的宽限期，原因就是本章的共享扫描——共享目录如果是几十万文件的规模，首次扫描可能持续很久，而扫描期间应用正常运行，只是共享列表还没建好。

两个直接含义：

- 如果你把 `--start-period` 改小（或用别的编排工具覆盖了健康检查），大共享库场景下容器会被反复判为 unhealthy 并重启，陷入恶性循环；
- 首次扫描完成前，你的共享对网络是不完整的。`shares.cache.storage_mode` 默认为 `memory`（`Options.cs:875`）；如果用 `disk` 模式，扫描结果会落到磁盘上、重启后不必重扫，大库场景可以考虑这个取舍。

#### 在哪看共享状态（Web UI System → Shares，详见证第 3 章 §3.3）

Web UI 的 `System`（系统）页有七个页签：`Info`、`Options`、`Shares`、`Files`、`Data`、`Events`、`Logs`，其中 `Shares` 就是共享扫描的状态视图。一个细节值得记住：**扫描处于待处理状态时，`Shares` 页签上会出现一个黄色感叹号图标**（前端源码里这个图标挂在 `state.shares.scanPending` 为真的分支上）。不确定扫描做没做完时，先看那个页签有没有黄标。

`Shares` 页里具体的读法与操作（目录列表、文件计数、重扫入口）属于 `[[03 日常使用与配置详解#3.3 其余视图速览|§3.3 共享目录、过滤器与黑名单]]`。

### 2.4 入站连接与端口自检

这一节解决「别人连不上我」这一类问题。它的写法有点特别：不是给一个确定的排错结论，而是**先纠正一个流传很广的错误表述**，再给一个可执行的判定顺序。

#### 监听端口语义（回指 §1.1 的 50300，不复述 5030/5031）

三条端口线的完整语义已经在 `[[01 部署与运行#1.1 先分清三条线：端口语义|§1.1 先分清三条线：端口语义]]` 里钉死了，此处不复述 Web UI 的两个端口，只强调其中一条：

- `50300` = Soulseek **对端连进来**的监听端口（代码默认值 `Options.cs:1770`，环境变量 `SLSKD_SLSK_LISTEN_PORT`）。

它是「别人来敲的门」，与 Web UI 端口互不相干：Web 端口只决定你能不能打开管理界面，`50300` 才决定你在 Soulseek 网络里是不是一个**可被连接的节点**。

官方文档对「监听端口配错会怎样」的描述比多数人预期的范围更宽（`docs/config.md` 的 Listen IP Address and Port 段）：

> Symptoms of a misconfigured listen port include poor search results and the inability to browse or retrieve user information for some users.

症状不只是「别人下不到你的文件」，还包括**搜索结果变差**和**无法浏览部分用户**。这解释了一个常见误判：以为「能搜到、能下载」就说明端口没问题——入站不通时下载依然可能可用（你主动连出去），只是对端连不回来。

还有一条必须知道的事实：**slskd 没有内置 UPnP / NAT-PMP 自动端口映射。** 官方 FAQ 在讲端口问题时提到官方客户端和 SoulseekQt 都使用名为 UPnP 的协议去让路由器认识监听端口，而 slskd 不做这件事。仓库里对应的讨论是 issue #908，维护者对加入该功能的表态持保留（出于安全考虑），并明确如果要加也「肯定是可选的、默认关闭」。对你的操作含义是：**路由器上的端口转发必须手工做。**

#### issue #1429：已定性的环境问题

仓库里一个已被关闭、并被明确定性为**环境/配置问题**的 issue：

| 项 | 内容 |
| --- | --- |
| 标题 | Cannot view or browse my own slsk user |
| 现象 | 在 Web UI 里搜索自己的用户名，出现 `Failed to establish a direct or indirect message connection to [username] ([ip address]:50300)` |
| 报告者补充 | 路由器上已做端口转发；官方端口检测工具显示 50300 closed；换成 Nicotine+ 在同一台机器用同一端口时，检测显示 open 且能浏览自己 |
| 报告者环境 | 用 WireGuard 连到一台 VPS；本机装有 ufw 防火墙 |
| 维护者回复 | 无法浏览自己通常意味着端口转发没正常工作，并反问是否在用 VPN、是否有软件防火墙在拦入站连接 |
| 关闭结语 | Closing because this is an issue related to setup specifics and is not a problem with the application itself |
| 状态 | CLOSED / COMPLETED |

定性清楚：**项目方的结论是「端口转发与防火墙这类本机环境问题」，不是应用缺陷。** 这个 issue 的场景是「自己浏览自己失败」，其前提正是「入站本应可用」。

#### issue #1805：未定性的疑难（状态仍 OPEN）

另一个 issue 讲的是**完全不同**的一种情形，且**至今没有结论**：

| 项 | 内容 |
| --- | --- |
| 标题 | Listen port externally unreachable despite successful local bind |
| 现象 | 本机绑定成功（本机探测显示端口 open），但外部端口检测（含官方工具）显示 closed |
| 关键对照实验 | 用 Python 在**同一个端口、同样的 `0.0.0.0` 绑定**上跑一个 TCP listener，外部检测立刻显示 open；换回 slskd 又变 closed |
| 版本时间线 | 在 0.24.5.0 时出现，升级到 0.26.0 后仍然存在 |
| 维护者回复（大意） | 询问是否配置了 `listen_ip_address`；提到 Soulseek.NET 有一个尚未发布的改动，用于修复「listener 的 accept 循环可能停止」这一潜在但可能性很低的缺陷；但认为那种情形下操作系统仍会接受连接、端口检测应显示 open；建议尝试旧版本 |
| 其他人补充 | 类似问题在官方 Windows 客户端和 Nicotine+ 上也出现过；而需要监听端口的其他应用（如文件同步类工具）一切正常 |
| 状态 | **OPEN**，尚未定性，维护者仍在做最小复现实验 |

那个对照实验的分量值得点出：在同一台机器、同一个端口上把 slskd 换成 Python listener，外部检测结果立刻反转。这一实验**排除了「用户侧端口转发没做」这个最常见的嫌疑**——这正是它与 #1429 的根本差别。

#### 两者的正确表述方式：两种状态，不是两个相反结论

这是本节的强制口径。把这两个 issue 写成「#1429 说是端口问题、#1805 说不是端口问题」是**错的**，因为：

- 它们描述**不同场景**：#1429 是「自己浏览自己失败」，前提是入站本应可用；#1805 是「本机绑定成功但外部扫描显示关闭」，并做了同端口对照实验；
- 它们处于**不同状态**：#1429 已定性并关闭；#1805 仍未定性、仍 OPEN。

正确的表述是「**两种状态**」：一类是已被判定为环境/配置问题的情形（#1429），另一类是仍未定性、连项目方都在继续排查的情形（#1805）。判定顺序上的意义是：**当你的自检呈现出 #1805 那种特征（本机绑定正常、同端口对照实验正常、但 slskd 的外部可达性异常）时，不要先入为主地归因到自己的端口转发配置**，这属于未定性的疑难，应当记录版本与复现细节。

| | #1429 | #1805 |
| --- | --- | --- |
| 标题 | Cannot view or browse my own slsk user | Listen port externally unreachable despite successful local bind |
| 场景 | 自己浏览自己失败 | 本机绑定成功但外部不可达 |
| 关键对照 | 换 Nicotine+ 同端口 → open | 同端口 Python listener → open |
| 项目方结论 | 环境/配置问题，非应用缺陷 | 尚未定性 |
| 状态 | CLOSED / COMPLETED | OPEN |

#### 自检方法与判定顺序

可执行的判定顺序，从内到外四步。第 ③ 步的命令与 `[[01 部署与运行#1.10 首次启动与首次登录|§1.10]]` 的 EX-10 同源，此处只保留 `50300` 这一段并单独展开，不另起编号。

```bash
# 与 [[01 部署与运行]] 的 EX-10 同源，此处只保留 50300 部分
# 在「外部」机器上执行：测试目标主机的 50300 是否 TCP 可达
nc -vz <目标主机 IP 或域名> 50300

# 没有 nc 时的等价写法
timeout 5 bash -c '</dev/tcp/<目标主机 IP 或域名>/50300' && echo "50300 可达" || echo "50300 不可达"
```

| 步骤 | 在哪执行 | 命令 / 工具 | 不通时的指向 |
| --- | --- | --- | --- |
| ① 应用是否绑定 | slskd 容器内 | `ss -lntp \| grep 50300` 或 `nc -zv 127.0.0.1 50300` | 应用层问题：监听配置、`listen_port` 取值 |
| ② 容器映射是否生效 | 宿主机 | `nc -vz 127.0.0.1 50300` | compose 的 `ports:` 漏了 50300，或宿主防火墙 |
| ③ 外部是否可达 | 外部机器 | 上面的 `nc -vz <公网 IP> 50300` | 路由器端口转发 / 宿主防火墙 / ISP 层面阻断 |
| ④ 官方工具交叉验证 | 任意能访问站点的浏览器 | `https://www.slsknet.org/porttest.php?port=50300` | 与第 ③ 步互为印证 |

第 ④ 步有一个使用要点，不写清楚会导致结论无效：**该工具检测的是「访问者自己的出口公网 IP」上指定端口的可达性**，不是你在 URL 里填的任意主机（URL 参数只有端口）。返回内容形如 `IP: <你访问时的出口 IP> Port: 50300/tcp CLOSED. ...`。所以必须**从你希望被外部连进来的那条网络出口去访问这个页面**——从办公室电脑打开它，得到的是办公室出口的检测结果，与家里那台 slskd 无关。

如果 ①② 都通、③ 不通，常见原因的排查次序建议如下（先排除能自己改的，再怀疑改不了的）：

1. **路由器上没做 50300 的端口转发**——slskd 不会替你自动做（没有 UPnP/NAT-PMP，见前文）；
2. **宿主机防火墙 / 云厂商安全组**没放开 50300 的入站 TCP；
3. **ISP 层面禁止入站 TCP**——官方 FAQ 承认这种情形存在：有些用户的网络被配置成无法接受入站 TCP 连接，虽然并不常见；
4. **多层 NAT / CGNAT**（本分册不展开）。

官方 FAQ 关于路由器与 UPnP 的原文也一并放在这里，它解释了为什么「有些路由器就是配不通」：

> If you're behind a router, your router might be blocking traffic to your listening port. Both the original client and SoulseekQt use a protocol named UPnP to configure your router to recognize the listening port, but some routers (most notably Apple routers) don't support UPnP.

#### 协议混淆端口（仅见于发布说明，FAQ 未收录）

「协议混淆」（protocol obfuscation）必须标清出处，因为它的信息层级经常被误传成 FAQ 条目：

- 逐字核对官方 FAQ 页全文，`obfuscat` 一词**零命中**——混淆**不是 FAQ 条目**；
- 它出现的地方是**发布说明 / 更新日志**，两条相关原文：

> P2P communication between two clients of this version or higher will be obfuscated in an attempt to avoid detection by ISPs that are crippling Soulseek peer connections. Completely unproven at this point.

> A legend next to the listening port setting now informs you of what your obfuscated listening port number is (usually it's the listening port number+1) in case you're manually forwarding your ports.

从第二条可得出一条操作性事实：**混淆端口编号通常是监听端口 + 1**，需要手工转发端口的人要额外留意这一个；

- 关于 slskd 自身：在本地缓存的全部信源里（`Options.cs`、`docs/config.md`、`config/slskd.example.yml` 等）搜索 `obfuscat` 同样**零命中**。所以正确的表述是「**slskd 当前版本不支持协议混淆**」，而不是「可以在某个键里开启」。

> [!warning] 三句话要连在一起说
> 1. 协议混淆**只出现在发布说明里，官方 FAQ 未收录**；
> 2. 它的编号规则是「监听端口 + 1」；
> 3. slskd 当前版本**没有实现**它，因此上面那条规则对纯 slskd 部署没有直接操作意义——除非你同时在跑支持它的官方客户端。

### 2.5 客户端政策（客观技术说明）

这一节的对象是 Soulseek 官方规则页里关于「谁能连接、怎么连接」的条款。以下内容全部是**引述与解释**：引述规则页原文、解释这些条款在 slskd 场景下的技术含义、指出你可能踩到的地方。

【EX-34】官方规则页原文（引用块）

> [!example] 官方规则页原文（节选）
> Users are allowed to connect up to a maximum 5 clients from the same IP.
>
> Spammers, automated clients (robot/bot), combinations of such, or scripts otherwise failing to implement the full range of Soulseek® features are not allowed to connect to the Soulseek® service.
>
> Users are encouraged to use the official Soulseek® client available from http://www.slsknet.org . Alternative clients for platforms other than Microsoft(r) Windows(r) that implement the full range of features of the Soulseek®. Network (including chat, search, wishlist, download, upload, and respect / recognition of privileges) are tolerated.

#### 同一 IP 的连接数上限 → 对 Relay / 双客户端场景的影响

规则原文是「up to a maximum 5 clients from the same IP」——**同一个 IP 最多 5 个客户端**。对 slskd 用户有两个具体场景：

**场景一：同时跑官方客户端 + slskd。** 出口 IP 相同时，这两个客户端**都算**进 5 个的额度。如果同一出口后面还有其他机器在跑 Soulseek 客户端（家庭网络里很常见：一台老电脑挂着官方客户端，NAS 上跑着 slskd），它们一起累加。这是本节标题里那条必须提示的冲突：**上限是按 IP 计的，不是按机器计的**，多设备部署要按总连接数来算，而不是「每台机器各 5 个」。

**场景二：Relay 场景。** Relay 配置下只有 Controller 连到 Soulseek 网络，Agent 只连 Controller（官方文档原话，见 §2.6）。因此从 Soulseek 网络的角度看，一个 Relay 配置只产生 **1 个**客户端连接。

> [!note] 关于场景二的定位
> 第二点是 Relay 架构的附带性质，**不是官方为 Relay 列出的立意**（官方列的适用场景见 §2.6）。写出来是因为它确实能少占一个连接额度，但不要把它当成 Relay 的主要用途来宣传。

#### bot / 自动化客户端 / 残缺脚本

规则原文点名三类：spammers、automated clients (robot/bot)、以及「otherwise failing to implement the full range of Soulseek® features」的脚本。第三类技术上最需要注意，因为它的判据是**功能完整度**，而不是「是否由程序驱动」。

「full range of features」在第三方客户端条款里有明确列举：chat、search、wishlist、download、upload、以及 respect / recognition of privileges（识别与尊重 privileges 状态）。一个只实现搜索与下载、不处理聊天、wishlist、privileges 识别的客户端，就可能落进「残缺脚本」的表述范围。

上游研究记录里另有一条社区来源（低可信度，未回源）：协议文档提到服务端不接受随机生成的用户名，批量建号会违反服务器规则。此条仅作旁证列出，不作为技术依据。

#### 第三方客户端"被容忍"的条件

从规则页原文可拆出三个条件：

| 条件 | 原文依据 | 含义 |
| --- | --- | --- |
| 平台不是 Microsoft Windows | "for platforms other than Microsoft(r) Windows(r)" | Windows 上有官方客户端，该情形下不适用此豁免 |
| 实现完整功能集 | 原文列举 chat / search / wishlist / download / upload / privileges 识别 | 功能残缺的客户端不在豁免范围内 |
| 结果是「被容忍」而非「被支持」 | 原文用词是 "tolerated" | tolerated ≠ supported |

第三条最值得强调。同一规则页开头就把服务定性为 unsupported service，而第三方客户端的措辞是 tolerated。两句话合起来：**非 Windows 平台的完整功能客户端不会被禁止连接，但不获得任何支持承诺**——官方没有义务帮你排查 slskd 的问题。

#### 写作口径声明：只作技术说明，不作合规判断

本节只做三件事：引述规则页原文、解释这些条款在 slskd 场景下的技术含义（连接数怎么累加、功能完整度怎么判断）、指出你可能踩到的地方（同 IP 多客户端叠加）。

它**不评价**你是否应该使用 P2P 网络，**不评价**版权问题，**不评价**你是否应该使用 VPN，也不构成任何法务意见。规则页本身包含关于版权材料的声明段落，原文可在该页直接查阅；本分册不就此展开。此处给出的所有条款都可以在官方规则页上自行核对，核对时以该页当前内容为准。

### 2.6 Relay 中继模式

Relay（中继）是 slskd 里一个可选的拓扑模式：让两个或更多 slskd 实例在网络上**协作成"一个客户端"**。它不属于基础部署，但属于「知道有这个东西、知道它解决什么」的必备认知。

#### 定位：Controller / Agent 各做什么

官方文档（`docs/relay.md`）给出的定义：

> Relay mode refers to an optional configuration that allows two or more instances of slskd to work together over a network as one client.

拆成两个角色：

> The controller is the instance that connects to the Soulseek network and acts as the client; it's pretty much a standard instance of slskd. Agents are additional instances that connect to the controller, instead of the Soulseek network. These instances only relay files to the controller.

官方还给了个很好用的类比：

> You can think of Relay agents as 'remote storage' for slskd.

| | Controller（控制器） | Agent（代理） |
| --- | --- | --- |
| 连 Soulseek 网络吗 | 连 | **不连** |
| 连谁 | Soulseek 服务器（出站 2271）+ 对端客户端（入站 50300） | 只连 Controller（出站） |
| 角色 | 网络里那个真正的客户端 | 远端文件仓库 / 中继 |
| 需要对外开放入站端口吗 | **需要**（50300） | **不需要** |
| 数量 | 1 个 | 可以多个 |

`relay.mode` 的取值是 `controller`（代码默认，`Options.cs:544`）、`agent`、`debug`（供本地开发用）。

> [!warning] Relay 不是 VPN，也不改变流量归属
> Relay 只中继 slskd 自己的文件流：Agent 侧的文件经 Controller 转出去。它**不是** VPN 那样的全局网络隧道，**不代理**宿主机上其他任何流量，也不改变 Agent 主机其余流量的路由或出口归属。它解决的是「文件从哪里参与共享」的问题，不是「网络流量怎么走」的问题。
>
> 另一条容易误解的边界：Relay **不是「免端口」的万能方案**——Controller 自己仍要连 Soulseek 网络、仍需 50300 入站可达。Relay 的价值是把「必须暴露端口的机器」收敛到**一台**，而不是取消这个要求。

#### 适用场景清单

官方文档列出的适用情形（条目化转述）：

1. 想从**多个地点**供档，但不想为此开多个 Soulseek 账号；
2. 在意隐私，不想用（或不信任）VPN；
3. 想要 Soulseek 网络上的**完整功能**，但没法正确配置端口转发；
4. 是高流量用户，想把带宽压力从家庭宽带**分流**出去；
5. 想要一个**常年在线的客户端**来保住远程队列里的位置，而家里没有常开的机器。

官方补了一段说明：多数场景下你其实可以简单地在云端跑一个 slskd 实例，但要共享的文件量很大时这种做法既贵又难管；用 Relay 就能让 Agent 指向你本地的文件、接到云端实例上。

#### 安全设计：Agent 主动外连、API key + 每 Agent secret、按 IP/CIDR 限定

Relay 的安全模型，官方文档对应的原文：

> Agents connect to the controller, not the other way around, meaning your home network doesn't need to forward any ports or enable any additional incoming traffic through firewalls. The only trust involved is in the address of the controller, which you control.

> All incoming requests to the controller must be secured with an API key, and each agent is configured with an additional shared secret to ensure authenticity. Agent configuration and API keys can be scoped to a specific IP address or CIDR block to ensure only authorized agents can connect, even if API keys and shared secrets are obtained by an attacker.

> All traffic between the Relay controller and agents is (optionally) sent over HTTPS, meaning it is end to end encrypted.

拆成表：

| 机制 | 作用 | 对应配置位置 |
| --- | --- | --- |
| Agent 主动外连 | 家侧**不需要**开任何入站端口、不需要改防火墙 | 架构决定，无对应键 |
| API key | 认证所有到 Controller 的请求 | Controller 上 `web.authentication.api_keys.<名字>`，角色需为 `readwrite` |
| 每 Agent 一个 secret | 保证 Agent 身份真实性（与 API key 是**两把不同的钥匙**） | `relay.agents.<名字>.secret` |
| IP / CIDR 限定 | 即使 key 与 secret 泄露，也限制来源范围 | `web.authentication.api_keys.<名字>.cidr` 与 `relay.agents.<名字>.cidr` |
| 可选 HTTPS | Controller ↔ Agent 端到端加密 | `relay.controller.address` 用 `https://`；Controller 用自签证书时才把 `ignore_certificate_errors` 改为 `true` |

> [!warning] 版本安全底线：0.26.0
> 上游研究记录里有一条与 Relay + CIDR 白名单直接相关的缺陷记录：带 `::ffff:` 前缀的 CIDR 会被解析成匹配一切。API 鉴权侧的修复在 0.24.4，Relay 登录侧遗漏的那部分由后续 PR 修复并随 **0.26.0** 发布。结论：**用 Relay 的 CIDR 白名单时，把 0.26.0 当作安全底线**。来龙去脉见 `[[04 安全与进阶速览#4.3 API Key CIDR 绕过缺陷|§4.3 API Key CIDR 绕过缺陷]]`。

#### Controller 侧配置

【EX-13】`slskd.yml`：Relay Controller 侧片段（取自 [[01 部署与运行]] 的 EX-06 对应段落）

```yaml
# 文件：slskd.yml（取自 [[01 部署与运行]] 的 EX-06 对应段落）
# 位置：relay（controller 模式）+ web.authentication.api_keys
relay:
  enabled: true
  mode: controller            # controller（默认）、agent、debug
  agents:                     # 以 controller 模式运行时填写可接入的 agent
    home_nas:
      instance_name: home_nas # 必须与该 agent 顶层 instance_name 完全一致
      secret: <16-255 字符，本 agent 专用>
      cidr: 0.0.0.0/0,::/0

# 同一个文件里，Web 鉴权段需要为 Relay 准备一个 readwrite 角色的 key
web:
  authentication:
    api_keys:
      relay_controller_key:   # Relay controller 侧需要一个 readwrite 角色的 key
        key: <16-255 字符>
        role: readwrite
        cidr: 0.0.0.0/0,::/0
```

三处要点：

- `relay.agents` 下**每个 Agent 的 `secret` 必须各不相同**（官方文档明确要求每个 agent 使用不同的 secret）；
- 给 Relay 用的这个 API key 的 `role` 必须是 `readwrite`，`web.authentication.api_keys.*.role` 的可选值是 `readonly`、`readwrite`、`administrator`；
- 上面的 `cidr` 值 `0.0.0.0/0,::/0` 是**代码默认值**（`Options.cs:2264`、`:675`），含义是**不限制来源**。生产环境应把它收紧为 Agent 的实际出口 IP 或网段——这正是上一小节那张表里「IP/CIDR 限定」那一层。

#### Agent 侧配置

【EX-14】`slskd.yml`：Relay Agent 侧片段（取自 [[01 部署与运行]] 的 EX-06 对应段落）

```yaml
# 文件：slskd.yml（取自 [[01 部署与运行]] 的 EX-06 对应段落）
# 位置：顶层 instance_name + relay（agent 模式）
instance_name: home_nas       # 必须与 controller 上该 agent 条目的 instance_name 一致

relay:
  enabled: true
  mode: agent
  controller:                 # 以 agent 模式运行时必填
    address: https://slskd.example.com:5030
    ignore_certificate_errors: false  # 仅当 controller 用自签证书时才改为 true
    api_key: <16-255 字符，取自 controller 上一个 readwrite 或 administrator 角色的 API key>
    secret: <16-255 字符，与 controller 上为本 agent 配置的 secret 一致>
    downloads: false
```

Agent 侧有两个不对称的地方：`relay.controller.downloads` 默认为 `false`，含义是**这个 Agent 是否参与下载**（把下载任务也中继过去）；`ignore_certificate_errors` 默认 `false`，只有 Controller 用自签证书时才有必要改成 `true`——**把它当常态打开会关掉证书校验**，不要图省事。

这份差异落到容器编排上，就是「端口段有没有 `50300`」这一处区别：

【EX-16】Relay 场景的 compose 端口差异

```yaml
# 文件：docker-compose.yml（Relay 场景：对比 Controller 与 Agent 的端口段落）
services:
  slskd-controller:            # Controller：必须开放 50300（对端要连它）
    image: slskd/slskd:latest
    restart: unless-stopped
    ports:
      - "5030:5030"            # Web UI
      - "50300:50300"          # Soulseek 对端入站 —— Controller 必须有
    volumes:
      - /srv/slskd-controller:/app
      - /music:/music:ro
    environment:
      - SLSKD_REMOTE_CONFIGURATION=true

  slskd-agent:                 # Agent：只需要出站，不需要任何入站端口
    image: slskd/slskd:latest
    restart: unless-stopped
    # 注意这里没有 ports: —— Agent 不接收任何入站连接
    volumes:
      - /srv/slskd-agent:/app
      - /srv/music-archive:/music:ro
    environment:
      - SLSKD_REMOTE_CONFIGURATION=true
```

`5030`（Web UI）在 Agent 侧仍然要按需映射——那是给你自己打开管理界面的，与 Soulseek 网络无关。真正**只有 Controller 需要**的是 `50300`。

#### instance_name 必须与 Controller 上的 agent 名一致

这是 Relay 配置里最容易出错的一点，而官方文档在三处给出了**措辞略有差异**的说法，值得摆在一起看：

| 来源 | 说法 |
| --- | --- |
| `config/slskd.example.yml` 第 37 行注释 | `make sure the top-level instance_name of the agent matches!` |
| `docs/config.md` 的 Agents 段 | Agent 的**顶层 `instance_name`** 必须与 Controller 上为该 agent 配置的 `instance_name` 对应，且每个 agent 用不同的 secret |
| `docs/relay.md` 的 Quick Start 正文 | 「我们在上面配置了 `example`，所以这个实例需要命名为 `example`」 |

第三行是歧义来源：它说的 `example` 是 `relay.agents` 下的 **map key**，而**同一份示例 YAML 里该条目的 `instance_name` 写的是 `example_agent`**，Agent 侧顶层写的也是 `example_agent`。也就是说示例文件自身的正文与 YAML 在这处并不完全一致。

操作口径以字段为准：

| 概念 | 是否必须一致 | 说明 |
| --- | --- | --- |
| Agent 顶层 `instance_name` | **必须**等于 Controller 上该 agent 条目的 `instance_name` 值 | 三处代码/配置证据在这一点上一致 |
| `relay.agents` 下的 map key | **可以不同** | 它只是 Controller 内部的条目名 |

最省事的做法是让两者取同名——EX-06 里的 `home_nas` 就是这么写的：map key 是 `home_nas`，`instance_name` 也是 `home_nas`，Agent 顶层再写 `home_nas`，三处一致，不存在歧义。代码里还有一条校验：**同一份配置里出现重复的 `instance_name` 会被拒绝**（`Options.cs:568-569` 附近的校验逻辑）。

#### secret 生成命令与长度约束

【EX-15】生成 Relay secret 的命令

```bash
# 生成一个 32 字符的随机 secret（在宿主机或容器内执行均可）
./slskd --generate-secret 32

# 容器部署等价写法
docker exec -it slskd /app/slskd --generate-secret 32
```

约束三条：

| 约束 | 值 | 出处 |
| --- | --- | --- |
| 长度范围 | 16–255 字符 | `Options.cs` 的 `[StringLength(255, MinimumLength = 16)]`；官方文档同样写 16–255 |
| 需要几个 | **两个**：一个当 API key、一个当 Relay 共享 secret。两者用途不同，不要混用同一个值 | `docs/relay.md` |
| 生成哪个长度 | 长度参数可选，官方示例用的是 32 | `docs/relay.md` |

> [!warning] 不要把文档示例里的值直接抄进配置
> 官方文档在这处专门放了一句警告，原话是「**DO NOT copy/paste these values into your configuration! Use your own values, or you're opening yourself up to an attack!**」——文档里出现的任何示例 secret 都是**已经公开**的值，直接使用等于把入口敞开。

最后一条运维细节：`relay.enabled` 与 `relay.mode` 是**需要重启**的配置项（`Options.cs:534`、`:544` 所在的属性标了重启要求），改完它们不会热生效。

### 2.7 本章常见坑

| 坑 | 症状 | 处理与出处 |
| --- | --- | --- |
| **把社区 autoban 阈值写成官方规则** | 读者以为「必须共享 N 个文件」是官方要求 | 三层必须分开写：① 服务器规则无门槛，② 对端用户自设阈值属社区惯例，③ slskd 的 `leechers` 组是限速不是封禁；见 §2.2 |
| **把「必须先用官方客户端注册」写成官方要求** | 传达了一个不存在的注册前置条件 | 官方既无注册入口也未说明创建时机；「先用 SoulseekQt 注册」是**社区推断**；见 §2.1 |
| **把 #1429 与 #1805 写成「两个结论相反」** | 让读者以为项目方自相矛盾 | 是**两种状态**：#1429 已定性为环境问题并关闭，#1805 仍未定性且 OPEN；场景与对照实验都不同；见 §2.4 |
| **引用已被劫持的旧第三方域名** | 把读者导向一个非官方站点 | 全文一律改用 `slsknet.org` 的 Rules / FAQ / 各 node；见 §2.1、§2.2、§2.5 |
| **Agent 的 `instance_name` 与 Controller 上的 agent 名不一致** | Relay 连不上，且报错不直观 | Agent 顶层 `instance_name` 必须等于 Controller 上该 agent 条目的 `instance_name` **值**；map key 可以不同；见 §2.6 |
| **把 Relay 当 VPN 用** | 以为它能代理全部流量、改变流量归属 | Relay 只中继 slskd 自己的文件流，也不改变宿主机其他流量的路由；它也不是「免端口」方案——Controller 仍需 50300 入站；见 §2.6 |
| **未提示同 IP 连接数上限的冲突** | 家里同时跑官方客户端 + slskd 后莫名连接被拒 | 规则是「同一 IP 最多 5 个客户端」，按 IP 累加而非按机器；见 §2.5 |
| **把协议混淆端口当成官方 FAQ 条目写** | 读者去 FAQ 里找不到，怀疑资料有误 | 混淆**只出现在发布说明**里，FAQ 零命中；且 slskd 当前版本未实现该功能；见 §2.4 |
| **把 P2P / 版权 / VPN 合规写成劝诫或法务判断** | 越界给出合规建议 | 只作客观技术引述与解释，不作判断、不构成法务意见；见 §2.5 |
| **把 `shares.filters` 的三条排除项当成默认值** | 不写过滤器却以为噪音文件已被排除 | 代码默认是**空列表**（`Options.cs:757`）；那三条是官方示例值，不写就不生效；见 §2.3 |
| **共享目录里写了 `- /:/host` 这类根挂载** | 应用启动即报错 | 官方明确不支持把根挂载当共享目录，相对路径同样不支持；见 §2.3、`docs/config.md` |
| **Relay 的 secret 与 API key 用同一个值** | 违反官方的两把钥匙设计 | 需要生成**两个** secret，用途不同；长度须在 16–255 字符内；见 §2.6、EX-15 |

> [!summary] 本章要点
> - **账号**：官方站点**没有注册入口**（`/news/user/register` 返回 403，主菜单无 Register 项），也**从未说明**账号创建发生在哪一步；「先用 SoulseekQt 注册」是社区推断，不是官方要求。普通用户名 30 天不登录会被回收，一次性捐款 $5 起则永不回收；密码按不可恢复处理。
> - **共享要求是三层**：① 服务器规则没有最低共享门槛；② 真正的压力来自对端用户在自己客户端里设的 autoban 阈值，**那是社区惯例不是官方规则**；③ slskd 内置 `leechers` 组的做法是**限速分组**（阈值默认 1 个目录 / 1 个文件），不是拒绝连接，且只影响上传侧。官方客户端做的也是「空共享警告」而非自动封禁。
> - **共享目录**：路径必须绝对、不允许根挂载；`shares.filters` 的**代码默认是空列表**，`\.ini$` / `Thumbs.db$` / `\.DS_Store$` 只是示例值；首次扫描可能很久，这就是官方镜像健康检查给到 `--start-period=60m` 的原因；扫描中 `System → Shares` 页签会显示黄色感叹号。
> - **入站连接**：`50300` 配错的症状不只是「别人连不上」，还包括搜索结果变差、无法浏览部分用户；slskd **没有** UPnP/NAT-PMP，端口转发要手工做。#1429 已定性为环境问题并关闭，#1805 仍未定性且 OPEN——**这是两种状态，不是两个相反结论**。协议混淆只出现在发布说明里（规律是监听端口 + 1），FAQ 未收录，slskd 当前版本也不支持。
> - **客户端政策**：同一 IP 最多 5 个客户端（按 IP 累加，官方客户端与 slskd 会一起算）；第三方客户端被**容忍**（tolerated）而非**支持**。本节只作技术说明。
> - **Relay**：Controller 连 Soulseek 网络，Agent 只连 Controller，因此 Agent 侧**无需开放任何入站端口**；安全靠「Agent 主动外连 + API key + 每 Agent 独立 secret + IP/CIDR 限定 + 可选 HTTPS」；Agent 顶层 `instance_name` 必须等于 Controller 上该 agent 条目的 `instance_name` 值；secret 需生成**两个**、长度 16–255。Relay 不是 VPN，也不是免端口方案。
