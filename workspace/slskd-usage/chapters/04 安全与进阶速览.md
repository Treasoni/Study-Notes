## 第 4 章 安全与进阶速览

前三章解决的是「让 slskd 跑起来、配得对、用得上」。这一章回答另一个问题：**什么时候可以把它放到公网上，放上去之前必须改什么。** 官方 README 在介绍这个项目时直接写着它「designed to be exposed to the internet」——也就是说，暴露到公网是被支持的用法，但**默认配置不是为公网准备的**。

所以本章是一份压缩版速览：每一项只讲到「够用 + 知道去哪查」，展开成完整教程的活留给官方文档。如果你只是在家里内网自用，本章的大部分内容可以先跳过，只读 §4.1 和 §4.8 即可。

本章出现的所有 `slskd.yml` 片段，均**取自 [[01 部署与运行]] 的 EX-06 对应段落**（EX-06 是本分册唯一一份完整 `slskd.yml` 综合样例），不新增键、不另起变体。

### 4.1 默认凭据与远程配置

#### 默认凭据与公网暴露风险

Web UI 和它底层的 API **默认启用认证**，默认用户名和密码都是 `slskd`：

> Authentication for the web UI (and underlying API) is enabled by default, and the default username and password are both `slskd`.
> —— [`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 认证段

官方 README 紧接着补了一句：**「You'll want to change these if the application will be internet facing.」**（[`README.md`](https://github.com/slskd/slskd/blob/master/README.md)）。代码里的默认值同为 `slskd`（[`src/slskd/Core/Options.cs`](https://github.com/slskd/slskd/blob/master/src/slskd/Core/Options.cs) 第 2115 行附近）。

不改默认密码的后果是具体的：任何扫到 `5030` 端口的人用 `slskd`/`slskd` 登录后，拿到的是**完整的应用控制权**——能改配置、能看你的下载队列、能浏览别人的共享，如果 `remote_file_management` 是开着的，还能删你磁盘上的文件。这不是「被看一眼」的级别，是「把机器交出去」。

顺带把一个容易搞反的开关说清楚：`web.authentication.disabled` 默认是 `false`，也就是**认证默认开启**，不要以为需要「手动打开认证」。官方的建议是「Changing **both** the username and password during the initial configuration is highly recommended.」——用户名和密码都要改；只改密码、留着 `slskd` 这个用户名，等于把「这是默认安装」写在门口。

#### remote_configuration 的默认值与官方警告

`remote_configuration` 控制的是「能不能从 Web UI 远程改配置」。它的代码默认值是 `false`（`Options.cs:185`），`docs/config.md` 给出的 YAML 默认值也是 `false`（第 95 行）：

```yaml
# 文件：slskd.yml（官方给出的默认值）
remote_configuration: false
```

同一节还有一段官方警告，值得逐字读：

> By default, this option is disabled. Applications run within untrusted networks, especially those where the application is internet-facing, should consider the risks of enabling this option.
>
> **If an attacker were to gain access to the application and retrieve the YAML file, any secrets contained within it will be exposed.**
> —— [`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 第 85–87 行

第二句是关键：**开了远程配置，等于把 YAML 文件本身放到攻击者可读取的位置**，而 YAML 里装着 Soulseek 密码、API key、JWT key、gluetun 的 key。所以它泄露的不是一个开关，而是这一整套凭据。

#### 两种口径并列：快速上手语境 vs 公网部署语境

这里有一处**官方自身的口径不一致**，本分册在 §3.8 只做了指路，在此处并列呈现——这是全篇唯一必须并列、不得单向取信的条目：

| 出处 | 写法 | 语境 |
| --- | --- | --- |
| [`README.md`](https://github.com/slskd/slskd/blob/master/README.md) Quick Start | 四条示例里都带 `-e SLSKD_REMOTE_CONFIGURATION=true` | 「先把它跑起来」的上手场景 |
| [`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 第 85–95 行 | 默认 `false`，并附「internet-facing 要考虑风险」的警告 | 「公网部署」的安全场景 |
| `Options.cs:185` | 代码默认 `false` | 事实层：不做任何设置时就是关的 |

两种口径都不算错——README 的 quick start 假设你在内网第一次跑，开远程配置能少改几次文件、直接从界面调；`config.md` 的警告针对的是公网。**真正要避免的是单向取信**：既不能因为 README 里写了 `=true` 就照抄到公网机器上，也不能因为 `config.md` 警告就以为这个东西内网也不能用。

判断准则很简单：**这台机器有没有公网入口？有就保持 `false`。** 内网自用、且你有别的隔离手段时，开成 `true` 换来的是不用反复登服务器改文件。

顺带记一个更硬的手段：`docs/config.md` 第 53 行指出，**命令行参数的优先级高于所有其他源，且运行时不可变**，因此「security options, such as remote configuration, HTTPS JWT secret, and certificate」适合走 CLI。把 `--remote-configuration=false` 写死在启动参数里，可以防止有人事后通过 YAML 或环境变量把它打开。

#### remote_file_management 的默认粒度（列目录 vs 删除）

`remote_file_management` 默认也是 `false`（`Options.cs:193`）。它的粒度官方写得很清楚：

> The application offers APIs for listing and deleting files within the 'Incomplete' and 'Downloads' directories. **Listing is always allowed, while the ability to delete is disabled by default.**
> —— [`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 第 158–159 行

也就是说这个开关**只管删除**：列目录（看 Incomplete / Downloads 里有什么）**任何时候都允许**，关不掉；打开这个开关之后，API 才多出「删除」能力。所以只关心「别让人删我文件」的话，保持 `false` 即可，看文件列表这件事本身不受它控制。

#### [!tip] 大白话 + 类比（默认密码 + 开远程配置 = 把钥匙挂在门上还留了配方）

> [!tip] 大白话
> 把 slskd 想成**你家储藏室的门**：
> - 默认账密 `slskd`/`slskd` 就像**钥匙还插在门锁上**——官方没指望你自己发现，所以 README 明说了「internet facing 就改掉」。
> - `remote_configuration` 更像**在门口钉一块板，写明屋里所有柜子的密码**。它不是门锁，是「把配方挂出来」——一旦有人进了门，他不用再猜，直接照抄。
> - `remote_file_management` 则是**那把只能开垃圾桶的钥匙**：能看清单（列目录）是一直允许的，能不能动手扔东西（删除）才由它决定。
>
> 所以公网部署的第一动作永远是：**换钥匙（改账密）→ 把配方收起来（`remote_configuration=false`）→ 别随便给垃圾桶钥匙（`remote_file_management=false`）。**

### 4.2 认证机制细节

#### JWT 与 API Key 的过期语义

slskd 有两套认证凭据，用途不同（[`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 认证段）：

- **JWT**（Json Web Token）：用用户名 + 密码调一次 API 换取，之后由浏览器带着用。**会过期**，默认 TTL 是 7 天（`604800000` 毫秒）。
- **API Key**：调用方直接在 `X-API-Key` 请求头里带上，不需要先登录换 token。**不会过期**——它只有「你手动撤销」这一种失效方式。

API key 的长度被限制在 **16–255 字符**，可以用命令行 `--generate-secret` 生成一个 32 位随机值。每个 key 可以带一个角色（`ReadOnly` / `ReadWrite` / `Administrator`）和一组 CIDR（Classless Inter-Domain Routing，无类别域间路由）白名单；**primary key（走 `-k` / `SLSKD_API_KEY`）默认是 `Administrator`，其他 key 默认 `ReadOnly`**。

这里有个容易忽略的默认值：**每个 key 的 CIDR 列表默认是 `0.0.0.0/0,::/0`，也就是「任何地址都行」**（代码真值，[`Options.cs`](https://github.com/slskd/slskd/blob/master/src/slskd/Core/Options.cs) 第 2264 行；`docs/config.md` 散文里把它写成 `0.0.0.0/0,::0`，漏了一个斜杠，属文档笔误）。换句话说，**不主动写 `cidr` 就不等于做了限制**——CIDR 是一道需要你自己拉起来的闸门。

官方在这里有一条明确的不推荐：

> using API key authentication without HTTPS is **NOT RECOMMENDED**. API keys are sent in HTTP headers (and in the case of SignalR, in query parameters) and will be easily accessible to anyone eavesdropping on the network. This is a risk with JWTs as well, but JWTs expire and API keys don't.

翻译成人话：**明文 HTTP 上用 API key，等于每次请求都把钥匙喊出来一次**，而且这把钥匙不过期。要用 API key，就配 HTTPS，或者至少把 CIDR 白名单收紧。

#### 默认 JWT key 每次启动随机生成 → 重启使已签发 JWT 失效

这是最容易在容器重启后「莫名其妙被登出」的原因：

> By default, a random JWT secret key is generated at each start. It is convenient and secure, but **restarting the application will invalidate any issued JWTs**, causing users to sign in again.

想避免就自己指定一个至少 16 字符的 key（`web.authentication.jwt.key`）。但注意后半句警告：**这个 key 能用来伪造有效的 JWT，所以它本身是最高级别的秘密**——一旦泄露，别人可以绕过密码直接签一个合法 token。放在 YAML 里就意味着：`remote_configuration` 开着时，这个 key 也跟着一起暴露。

#### 不支持转发类请求头 → 反代后按 CIDR 过滤可能失效

如果你打算「用反向代理对外，然后用 CIDR 白名单只放自己人进来」，官方明确说了这条路走不通：

> Note that CIDR filtering may not work as expected behind a reverse proxy, ingress controller, or load balancer, because **the remote IP address will be that of the device that's handling ingress**. This application doesn't support the `X-Forwarded-For` header (or anything like it) because a bad actor can easily fake it. If you wish to use CIDR filtering in this scenario, you'll need to do it at the point of ingress to your network.
> —— [`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 第 951 行

后果是具体的：反代之后，slskd 看到的「来源 IP」**永远是反代那台机器的 IP**，CIDR 白名单要么把所有请求当成同一个 IP 放行、要么全部拦掉，两种都不是你要的。官方拒绝支持 `X-Forwarded-For`，理由是这种头可以随手伪造。所以**CIDR 过滤要在网络入口（防火墙 / 反代本身）做，不是交给 slskd 做**。相关小节见 [[#4.4 反向代理要点|§4.4]]。

### 4.3 API Key CIDR 绕过缺陷

这一节讲的是一个**已经修复、但版本区间分两段**的历史缺陷。之所以还要写，是因为它直接影响「Relay + CIDR 白名单」这种部署形态的安全底线。

#### 受影响版本区间

缺陷由用户报告于 2026-01-15，报告者明确写「Since updating to **0.24.3.0** my Homepage widget for slskd stopped working, and I discovered that slskd no longer properly parses the requesting IP address during API calls」，环境一栏也填的是 `slskd: 0.24.3.0`（[issue #1605](https://github.com/slskd/slskd/issues/1605)）。

现象有两面：**正常写法**（如 `10.10.20.0/24`）会因为请求来源被表示成 IPv4-mapped IPv6（`::ffff:10.10.20.51`）而**匹配失败**，日志出现 `Unauthorized request ... not included in CIDR range(s)`；而**用户试图自救、把 CIDR 也加上 `::ffff:` 前缀**之后，过滤**整个失效**——报告者原话是「effectively bypasses the filtering, making it the same as having nothing at all」。

这里有个可用的自检信号：**如果日志里的来源 IP 带 `::ffff:` 前缀**（报告者贴出的原文长这样：`Unauthorized request from IP address ::ffff:10.10.20.51: ... allowed: 10.10.20.0/24`），说明你的部署正处在会产出这种表示的形态。看到它，就应该去核对版本号和 CIDR 的写法，而不是继续加白名单条目。

#### 根因（前缀被解析成匹配一切）

维护者（jpdillingham）在同一个 issue 下的解释是：

> If you specify a CIDR with the `::fff:` prefix, the library I'm using to parse converts it to **`::/0`** for some reason.

`::/0` 是 IPv6 的「全零前缀、零位子网掩码」写法，语义就是**匹配一切地址**。所以根因链条是：请求来源被表示成 IPv4-mapped IPv6 → 用户为了「匹配上」给白名单也加 `::ffff:` 前缀 → 解析库把带前缀的 CIDR 退化成 `::/0` → **白名单变成放行全部**。

这比「匹配不上」危险得多：匹配不上只是功能坏了（会有人发现），「匹配一切」则是**看起来在工作、实际已经完全不设防**。

#### 两处修复分别落在哪个版本

维护者原话交代了为什么修了两次：

> I made a change to map these sorts of addresses back to ipv4 **here** but **I missed making the same change in the relay login logic**. I'll have a fix shortly.

于是修复分两处落地，版本也不同：

| 修复侧 | PR | 合并时间 | 随哪个版本发布 |
| --- | --- | --- | --- |
| API 鉴权侧 | [#1606 Un-map IPv4 IPv6 addresses (remove '::ffff' prefix), disallow such addresses to be specified in CIDR configuration](https://github.com/slskd/slskd/pull/1606) | 2026-01-16 | **0.24.4** |
| Relay 登录侧 | [#1714 Map IPv6-mapped IPv4 addresses to IPv4 before checking against Relay CIDR](https://github.com/slskd/slskd/pull/1714) | 2026-04-26 | **0.26.0** |

两处都能回源核对：`0.24.4` 的 release notes 在「What's Changed」里逐字列了 #1606 那条；`0.26.0` 的 release notes 里列了 #1714 那条。维护者在 issue 里也直接确认了 Relay 侧这条的归属：「This was fixed in #1714 and this issue is closed.」以及「**This was released in 0.26.0**」。

注意第二处的时间差：Relay 侧的修复**比 API 侧晚了三个多月**，中间那几个版本（0.24.4 到 0.25.x）里，API 鉴权是安全的，但 **Relay 登录那条路上的 CIDR 检查仍然可以被 `::ffff:` 绕过**。

#### 对 Relay + CIDR 白名单用户的安全底线

结论一句话：**只要你在用 Relay，并且靠 CIDR 白名单限制 Agent 的接入来源，0.26.0 就是安全底线。**

- 低于 0.26.0：即使 API 侧已经修好，Relay 登录侧仍可能被 `::ffff:` 前缀绕过，白名单等于没有。
- 如果因为别的原因暂时无法升级：不要在 slskd 这一层依赖 CIDR 白名单，改用网络层手段（防火墙规则、只在内网暴露 Controller 的端口）来限制谁能连进来。Relay 的配置骨架见 [[02 账号与共享机制#2.6 Relay 中继模式]]。

### 4.4 反向代理要点

这一节以配置片段为主。官方 [`docs/reverse_proxy.md`](https://github.com/slskd/slskd/blob/master/docs/reverse_proxy.md) 给了四套配置，这里挑必需的部分：**websocket 头、缓冲设置、子目录前缀**。少任何一项，症状都是「页面能开、但状态不更新」。

#### websocket 必需的请求头与缓冲设置

官方开篇解释了原因：

> Because slskd uses websockets in addition to standard HTTP traffic, a couple of headers need to be defined along with the standard `proxy_pass` to enable everything to work properly.

除 `proxy_pass` 之外，必须补的是三个头——`Upgrade`、`Connection "Upgrade"`、`Host`——以及关掉请求缓冲 `proxy_request_buffering off`。少任一头的典型症状是：登录、翻页都正常，但下载进度条不动、聊天不刷新——因为那条 websocket 根本没升上去。

配置里还有一个 `client_max_body_size 0;` 也别漏：`0` 在这里的语义是**不限制请求体大小**。保留 NGINX 的默认值会让大体积的上传或 API 请求被拦下，而 slskd 的某些操作（比如一次提交很多文件）确实可能撑大请求体。

#### 子目录部署的前缀设置

部署形态决定两个值怎么写：

- **子目录部署**（例如 `https://example.com/slskd`）：slskd 侧的 `URL_BASE` **必须设为 `/slskd`**，反代里的 `location` 也要对应。
- **根路径部署**（例如 `https://slskd.example.com`）：`URL_BASE` **保持默认的 `/`**。

#### 官方四套配置的指路

下面是 NGINX 子目录形态，编号 EX-23：

```nginx
# 文件：/etc/nginx/conf.d/slskd.conf（EX-23：NGINX，子目录部署；URL_BASE 需设为 /slskd）
server {
        listen 8080;

        location /slskd {
                proxy_pass http://localhost:5030;
                proxy_set_header Upgrade $http_upgrade;
                proxy_set_header Connection "Upgrade";
                proxy_set_header Host $host;
                proxy_request_buffering off;
        }

        client_max_body_size 0;
}
```

根路径形态与它并列，编号 EX-24——差异只有两处：`location` 变成 `/`，且 slskd 侧 `URL_BASE` 不设（保持 `/`）：

```nginx
# 文件：/etc/nginx/conf.d/slskd.conf（EX-24：NGINX，根路径部署；URL_BASE 保持默认 /）
server {
        listen 8080;

        location / {
                proxy_pass http://localhost:5030;
                proxy_set_header Upgrade $http_upgrade;
                proxy_set_header Connection "Upgrade";
                proxy_set_header Host $host;
                proxy_request_buffering off;
        }

        client_max_body_size 0;
}
```

官方另外还给了一份 **SWAG 子域**配置（文件名 `slskd.subdomain.conf`，放进 `nginx/proxy-confs/`），与上面并列作为第三种形态，此处不展开，按需回 [`docs/reverse_proxy.md`](https://github.com/slskd/slskd/blob/master/docs/reverse_proxy.md) 取用。

Apache 的写法更短，关键是把升级参数写进 `ProxyPass`，编号 EX-25（`URL_BASE` 设为 `/slskd`）：

```apache
# 文件：Apache 站点配置片段（EX-25：URL_BASE 需设为 /slskd）
ProxyPass /slskd/ http://the.local.ip.address:5030/slskd/ upgrade=websocket
ProxyPassReverse /slskd/ http://the.local.ip.address:5030/slskd/
```

IIS（Windows）需要先装 URL Rewrite 模块，并把 `URL_BASE` 设为 `/slskd`，然后给根站点的 `web.config` 加一条重写规则，编号 EX-26：

```xml
<!-- 文件：web.config（EX-26：IIS + URL Rewrite；先把 URL_BASE 设为 /slskd 并安装 URL Rewrite 模块） -->
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <system.webServer>
    <rewrite>
        <rules>
	    <rule name="slskd" stopProcessing="true">
                <match url="slskd(/.*)" />
                <action type="Rewrite" url="http://<ip of slskd>:<port of slskd>/slskd{R:1}" />
            </rule>
        </rules>
    </rewrite>
  </system.webServer>
</configuration>
```

四套配置覆盖 NGINX（子目录 / 根 / SWAG）、Apache、IIS。注意反代只代理 **Web UI**（`5030`/`5031`）——`50300` 是 Soulseek 对端的入站端口，不经过反代，端口语义见 [[01 部署与运行#1.1 先分清三条线：端口语义|§1.1]]。

### 4.5 VPN 集成

#### 官方原文：配置集成不改变流量路由

这一节最容易写错，所以先把官方原文放在最前面，编号 EX-37b（非代码块，逐字引用）：

> **Configuring a VPN integration does not change how network traffic to the Soulseek server or other peers is routed.**
>
> Users wishing to use a VPN are responsible for ensuring slskd is connecting through their VPN's network interface and therefore routing traffic through the VPN. This integration simply provides visibility; a way to easily apply dynamically forwarded ports, and some extremely light protection for users who do not use a "kill switch" to drop internet connectivity entirely if their VPN client disconnects.
> —— [`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 第 1207–1210 行，VPN 集成节

**第一句就是结论：配置这个集成，不改变流量走哪条路。** 后面那句解释了它到底提供什么。如果你只记住一章里的一句话，记这句就够了。

#### 它实际提供什么

按官方自己的说法，这个集成提供三样东西：

1. **可见性**（visibility）——让你能看到 VPN 当前是不是连着、转发端口是多少；
2. **便于应用动态转发的端口**（a way to easily apply dynamically forwarded ports）——VPN 连上后才拿到的那个端口，可以自动同步给 slskd；
3. **对没开 kill switch 的用户的一点极轻量保护**（some extremely light protection）——VPN 掉线时，slskd 会主动断开与 Soulseek 服务器的连接。

第三点是「极轻量」的准确含义：它保护的是**应用层的连接**，不是系统层的流量。如果你的 VPN 客户端没有 kill switch、掉线后系统仍然直连出去，那 slskd 断开 Soulseek 服务器**并不能阻止别的进程**走明文出口。

#### 轮询机制

官方对该机制的描述是：

> The VPN integration can poll an external service/application for VPN status (connectivity, forwarded port, etc) and connect or disconnect the connection to the Soulseek server according to status.

具体行为分三步：

- **首次启动**：slskd 开始轮询配置的 VPN，**在 VPN 返回「已连接」状态之前，会一直延迟连接 Soulseek 服务器**。如果开了 `port_forwarding`，VPN 还必须**给出转发端口**，slskd 才认为它「ready」。
- **运行中掉线**：VPN 客户端不响应、或返回「已不再连接」，slskd 就**断开与 Soulseek 服务器**的连接。
- **恢复**：VPN 会继续按配置的间隔被轮询，一旦重新返回 ready 状态，slskd **重新建立**与服务器的连接。

轮询间隔默认 **2.5 秒**（`polling_interval: 2500`），可调，代码里限制最小 500 毫秒（`[Range(500, int.MaxValue)]`）。官方给的取舍是：间隔越长，slskd 与 VPN 之间的流量越少、日志噪音越小，但**对 VPN 状态变化的响应也越迟**。另外有一条硬约束：**启用 VPN 时，必须有且只有一个 VPN 客户端被配置**（`If the VPN is enabled, exactly one VPN client must be configured.`），否则校验不过——代码里的校验信息就是 `VPN is enabled but no client is configured`，同时还会检查 gluetun 的 URL 必须是绝对地址（形如 `http://127.0.0.1:8000`）。

#### gluetun 侧需要开什么

slskd 原生支持 gluetun。要用起来，**gluetun 侧必须先打开它的 control server**（[`docs/vpn.md`](https://github.com/slskd/slskd/blob/master/docs/vpn.md)）。下面这份是 gluetun 侧的开法，编号 EX-27：

```yaml
# 文件：docker-compose.yml（EX-27：gluetun 侧，开启 control server 并设定鉴权角色）
services:
  gluetun:
    image: qmcgaw/gluetun
    container_name: gluetun
    cap_add:
      - NET_ADMIN
    devices:
      - /dev/net/tun:/dev/net/tun
    ports:
      - 8000:8000/tcp        # control server
      - 5030:5030/tcp        # slskd 的 Web UI（因为 slskd 与它共享网络命名空间）
    environment:
      - VPN_SERVICE_PROVIDER=protonvpn
      - VPN_TYPE=wireguard
      - WIREGUARD_PRIVATE_KEY=<your key>
      - SERVER_COUNTRIES=Netherlands
      - VPN_PORT_FORWARDING=on
      - HTTP_CONTROL_SERVER_AUTH_DEFAULT_ROLE='{"auth":"apikey","apikey":"abcd123"}'
    restart: unless-stopped
```

两个环境变量是这一步的重点：`GLUETUN_HTTP_CONTROL_SERVER_ENABLE` 设为 `on`（本示例里由 control server 的镜像默认行为覆盖，官方文档给的写法是显式设它），以及 `HTTP_CONTROL_SERVER_AUTH_DEFAULT_ROLE` 里选一种鉴权方式——官方文档选用 API key，值形如 `'{"auth":"apikey","apikey":"abcd123"}'`。

#### slskd 侧配置项

slskd 侧的 compose 与 `integrations.vpn.*` 配置如下，编号 EX-28。先看 compose：

```yaml
# 文件：docker-compose.yml（EX-28：slskd 侧，与 gluetun 共享网络命名空间）
services:
  slskd:
    image: slskd/slskd:latest
    container_name: slskd
    network_mode: service:gluetun     # 关键：与 gluetun 共享网络命名空间
    depends_on:
      - gluetun
    environment:
      - SLSKD_SLSK_USERNAME=<your username>
      - SLSKD_SLSK_PASSWORD=<your password>
      - SLSKD_VPN=true
      - SLSKD_VPN_PORT_FORWARDING=true
      - SLSKD_VPN_GLUETUN_URL=http://localhost:8000
      - SLSKD_VPN_GLUETUN_API_KEY=abcd123
    volumes:
      - ~/slskd/:/app
    restart: unless-stopped
```

YAML 状态下对应的配置项（取自 EX-06 的 `integrations.vpn` 段）：

```yaml
# 文件：slskd.yml（EX-28：取自 EX-06 的 integrations.vpn 段）
integrations:
  vpn:
    enabled: false
    port_forwarding: false
    polling_interval: 2500      # 毫秒
    gluetun:
      url: http://localhost:8000
      timeout: 1000
      auth: apikey
      api_key: <gluetun API key>
```

四个环境变量与 YAML 键的对应关系是：`SLSKD_VPN` → `enabled`；`SLSKD_VPN_PORT_FORWARDING` → `port_forwarding`（设为 `true` 会**强制 slskd 等 gluetun 给出转发端口**）；`SLSKD_VPN_GLUETUN_URL` → `gluetun.url`（gluetun control server 的默认地址是 `http://localhost:8000`）；`SLSKD_VPN_GLUETUN_API_KEY` → `gluetun.api_key`。

鉴权选择是按配置「自动降级」的：**配了 API key 就用 `apikey` 认证；没配 API key 但配了用户名，就用 `basic`；两者都没配，则对 gluetun control server 的请求完全不鉴权**。最后一种在共享网络命名空间里等于把 control server 敞开，别这么用。

> [!warning] `auth` 这个键在代码里找不到对应属性（待核对）
> 上面这段「自动降级」是按官方示例文件 `config/slskd.example.yml`（写作 `auth: apikey # or basic or none`）与 gluetun control server 的鉴权方式推断的。**逐行核对本机缓存的 `src/slskd/Core/Options.cs`（版本锚点 0.26.0）可以确认：`GluetunVpnOptions` 只有 `url` / `timeout` / `username` / `password` / `api_key` 五个属性，其中并没有 `auth`。** 也就是说这个键在**官方示例文件里有、代码里没有对应绑定**——它到底是否生效，未经证实。
>
> 本分册的处理：EX-06 与本节照官方示例保留该键（键名以示例文件为准），但**不要把「写了 `auth: apikey` 就一定会走 API key 鉴权」当成结论**。稳妥做法是配好 `api_key`，再自行确认 gluetun 那边确实接受了请求。

#### 实际路由由用户自行确保

回到 EX-28 里那个看起来不起眼的键：**`network_mode: service:gluetun`**。

它才是真正让流量走 VPN 的东西——它让 slskd 容器**共享 gluetun 容器的网络命名空间**，于是 slskd 的所有出入流量物理上就是从 gluetun 的隧道口走的。而 `integrations.vpn.*` 那一串配置**只负责观察和联动**，不负责改路由。这也正好对上官方原文后半句：使用者自己负责让 slskd 走在 VPN 的网络接口上。

所以正确的心智模型是：**`network_mode: service:gluetun` 决定「走不走 VPN」，`integrations.vpn.*` 决定「VPN 掉了要不要断开 Soulseek」。** 两件事分开，别混为一谈。

> [!tip] 大白话
> 把这个集成想成**车上的仪表盘和后视镜**：它告诉你「现在隧道通不通、出口在哪个港口」，甚至在隧道塌了的时候帮你**熄火**（断开 Soulseek）。
>
> 但仪表盘**不决定你开哪条路**。真正决定路线的是你把车挂在哪条道上——也就是 `network_mode: service:gluetun`。如果车根本没挂到隧道这条道（没共享网络命名空间），仪表盘再灵敏也没用，你的车照样在明文的大马路上跑。
>
> 所以官方那句「不改变流量路由」要这么理解：**它不是加速器，是仪表盘；路线你自己选。**

### 4.6 脚本集成的 RCE 风险

#### 官方原文

脚本集成（`integrations.scripts`）能在事件发生时跑你指定的命令。官方在这一节挂了一条 CAUTION，逐字如下，编号 EX-37b：

> **Remote Code Execution Risk**: The event data in `$SLSKD_SCRIPT_DATA` originates from the Soulseek network and may contain malicious content. Passing this data as command-line arguments could allow attackers to inject shell commands through specially crafted filenames, usernames, or other fields. For example, a filename like `song"; rm -rf /; echo "` could delete your entire filesystem if passed unsafely to a shell command.
>
> **Best practices:**
> - ✅ Read `$SLSKD_SCRIPT_DATA` as an environment variable
> - ✅ Parse the JSON and validate/sanitize individual fields before use
> - ✅ Use programming languages with proper JSON parsing (Python, Node.js, etc.)
> - ❌ Avoid using `$SLSKD_SCRIPT_DATA` in shell command substitution like `$(echo $SLSKD_SCRIPT_DATA)`
> - ❌ Avoid passing the raw data as arguments: `my_script.sh "$SLSKD_SCRIPT_DATA"`
> —— [`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 第 1165–1173 行，Scripts 节

机制层面需要知道的几件事：**事件数据被 JSON 序列化后，写进 `SLSKD_SCRIPT_DATA` 这个环境变量**；进程的工作目录是 `/scripts`；`stdout` / `stderr` 会被重定向到 slskd 的日志。也就是说，**这份数据的来源是 Soulseek 网络**——文件名、用户名等字段都是别人可写的，因此必须当作不可信输入。

配置形态上还有个小提示：`run` 支持 `command`、`args`、`arglist` 三种写法，官方明确说 **`arglist`（参数列表）比 `args`（整串）更容易正确转义**。如果一定要传参数，用 `arglist` 而不是自己拼字符串——但注意，这并不能替代「先按 JSON 解析、再逐字段校验」，它只是降低了引号层面的出错概率。

#### 正确用法与禁止用法对照

对照下面这份写法，编号 EX-29：

```bash
# 文件：/scripts/handle_event.sh（EX-29：正确用法 vs 禁止用法对照）

# ❌ 禁止：命令替换——文件名里的 `$(...)` 会被当作命令执行
value=$(echo $SLSKD_SCRIPT_DATA)

# ❌ 禁止：把原始数据直接当参数传——shell 会整段重新解析
my_script.sh "$SLSKD_SCRIPT_DATA"

# ✅ 正确：把环境变量交给有 JSON 解析能力的语言处理，逐字段校验后再用
python3 - <<'PY'
import json, os, re
raw = os.environ.get("SLSKD_SCRIPT_DATA", "")
data = json.loads(raw)                      # 按 JSON 解析，不做 shell 求值
name = str(data.get("localFilename", ""))
if not re.fullmatch(r"[A-Za-z0-9._ -]{1,200}", name):   # 白名单式校验
    raise SystemExit("unexpected filename")
print(name)
PY
```

核心差别只有一条：**永远不要把这串数据交给 shell 去「再解释一遍」**。读环境变量（`$SLSKD_SCRIPT_DATA` 本身是安全的）、按 JSON 解析、逐字段校验——官方给的唯一安全路径就是这个顺序。两个 ❌ 都是把数据交回给 shell 求值，等于把「别人写的文件名」当成「你写的命令」来跑。

### 4.7 其他集成与特性速览

这一节全部保持压缩口径：**是什么 + 安全代价 + 去哪查**。

#### integrations 下的五个子项

`integrations` 下分两类（[`docs/config.md`](https://github.com/slskd/slskd/blob/master/docs/config.md) 第 1067 行起）：

| 子项 | 类别 | 一句话 | 安全代价 |
| --- | --- | --- | --- |
| `webhooks` | 用户自定义 | 事件发生时向外发 HTTP 请求 | 出站地址与 header 里可能带凭据；事件体含文件名等网络数据 |
| `scripts` | 用户自定义 | 事件发生时跑本地命令 | **RCE 风险**，见 [[#4.6 脚本集成的 RCE 风险|§4.6]] |
| `vpn` | 系统内置 | 轮询 VPN 状态并联动连接 | 见 [[#4.5 VPN 集成|§4.5]] |
| `ftp` | 系统内置 | 下载完成后上传到远端 FTP | FTP 凭据落盘；可关证书校验（默认关） |
| `pushbullet` | 系统内置 | 私聊 / 被 @ 时推送通知 | access token 落盘；默认开启两类通知 |

「用户自定义」指行为由你定义（去哪、跑什么），「系统内置」指行为是应用逻辑的一部分，你只能配参数。三类系统内置集成里，`vpn` 与 `ftp` / `pushbullet` 的定位差别也值得点一句：`vpn` 影响的是**连接本身**（连同源），而 `ftp` / `pushbullet` 是**事后的搬运与通知**，它们出问题不会让 slskd 断开 Soulseek。

还有一处命名坑要记：`docs/config.md` 在 Webhooks 一节用复数 `integrations`，在 Scripts / VPN / FTP / Pushbullet 各节却写成了单数 `integration`；`config_slskd.example.yml` 与代码**通篇用复数**。**以复数 `integrations` 为准**——单数 `integration` 是退役哨兵，写进 YAML 会让应用启动失败（详见 [[03 日常使用与配置详解#3.10 本章常见坑|§3.10]] 的 M3）。

#### webhook 的事件与重试设置

webhook 的请求**永远是 `POST`，事件数据永远放在 body 里（JSON）**。配置由四部分组成：名字（排错用）、触发事件列表（`on`）、`call`（目标地址、可选 headers、是否忽略证书错误）、以及超时和重试。默认值官方写明：**超时 5 秒，每个事件只尝试一次**。

`on` 列表里可以直接写具体事件名（如 `DownloadFileComplete`），也可以写 `All` 表示所有事件。`call.headers` 支持自定义请求头——如果你对接的是另一台 slskd 或同类服务，这里就是放 `X-API-Key` 或 `Authorization: Bearer ...` 的位置（示例见 `config_slskd.example.yml` 的 `integrations.webhooks` 段）。

事件对象本身有几个公共字段值得记：`Id`（去重用，因为**同一事件可能被投递多次**）、`Timestamp`（UTC，**不保证按时间顺序到达**）、`Version`、`Type`。事件类型会随版本变化，具体形态以仓库里的 `Events.cs` 为准。逐个事件的参数清单属于分册边界，此处只指路。

#### metrics：默认关闭、默认凭据、暴露的信息

`metrics.enabled` 默认 **`false`**，启用后暴露在 `/metrics`。认证**默认是开着的，而且凭据与 Web UI 的默认值相同（`slskd` / `slskd`）**：

> If the application will be exposed to the internet, it's a good idea to **leave this disabled or to set credentials other than the defaults**. Elements of the system configuration, like **operating system, architecture, and drive configuration** are included and can this can make it easier for an attacker to exploit a vulnerability in your system. `[sic]`

也就是说，公网上开 metrics 又不改凭据，等于**免费告诉别人你跑在什么系统、什么架构、磁盘怎么分的**。启用片段编号 EX-30（取自 EX-06 的 `metrics` 段）：

```yaml
# 文件：slskd.yml（EX-30：取自 EX-06 的 metrics 段；EX-06 中 enabled 为 false，此处改为 true 即为启用）
metrics:
  enabled: true
  url: /metrics
  authentication:
    disabled: false
    username: slskd
    password: slskd
```

#### swagger 与「哪些选项支持 Run-Time Overlay」的权威入口

`feature.swagger` 默认 `false`，启用后在 `/swagger` 提供 OpenAPI 定义与 SwaggerUI。它的定位官方写得很清楚：给「developing against the application API and/or creating a new web interface」的人用。

它还有一个容易被忽略的用途：**Run-Time Overlay（运行时覆盖）的完整可用选项清单，唯一的权威出处就是这个 OpenAPI 规范**。官方在讲 Run-Time Overlay 时明确指路「the full set of available options can be found in the OpenAPI specification that can be generated by enabling the 'swagger' feature」——目前实际只有 `listenPort` 和 `listenIpAddress` 两项支持。启用片段编号 EX-31（取自 EX-06 的 `feature` 段）：

```yaml
# 文件：slskd.yml（EX-31：取自 EX-06 的 feature 段；EX-06 中为 false，此处改为 true 即为启用）
feature:
  swagger: true
```

#### 搜索侧限流：官方标注的风险等级

`throttling.search.incoming` 这一组，官方直接挂了一个风险标签：

> [!warning]
> **Application Stability Risk**: The options in this section control the behavior of the application at the limits of the hosting environment's performance. **Increasing values can result in unintended behavior and crashes.** Support for users that increase these values will be limited.

三个选项与默认值分别是：`concurrency`（默认 `10`，同时处理的搜索响应数）、`circuit_breaker`（默认 `500`，可排队的上限，**超过就直接丢弃消息、不做处理**）、`response_file_limit`（默认 `500`，单次搜索响应最多返回多少文件）。官方给的调节方向是：**调高**在强机器上可能提升吞吐但默认值之下收益通常很小、且会增加崩溃风险；**调低**会降吞吐但缓解 I/O 争用、在低配硬件上更稳。属于「有明确性能边界需求时再动」的一组，不要顺手改。

#### MCP / 第三方生态（打折口径）

MCP / 第三方 Web UI 生态**没有官方一手依据**，本项目在探测阶段也只是记录为「第三方项目、成熟度需自行评估」。因此这里保持**打折口径**：它是一个**方向**，不是一套**成熟的推荐方案**；不给出具体项目推荐，也不写接入步骤。需要的话按独立课题自行评估——本分册把它明确划在边界之外。

### 4.8 公网部署最小动作清单

下面这份清单（编号 EX-32）是「把 slskd 暴露到公网之前」的最低要求。每项一句话，具体的「为什么」指向对应小节。它不是完整加固指南——本分册只覆盖到这里；清单之外的强化（主机防火墙、告警、备份策略等）属于运维范畴。

- [ ] **改掉 Web UI 默认账密**（`slskd`/`slskd`），用户名和密码都改 —— 见 [[#4.1 默认凭据与远程配置|§4.1]]

- [ ] **`swagger` 保持禁用**，除非你正在对接 API —— 见 [[#4.7 其他集成与特性速览|§4.7]]
- [ ] **不用脚本集成；若要用，严格按「读环境变量 + JSON 解析」写** —— 见 [[#4.6 脚本集成的 RCE 风险|§4.6]]
- [ ] **确认 `50300` 的入站是你要的暴露面**：它必须能被人连进来，但那是 Soulseek 对端，不是给人访问 Web 用 —— 见 [[02 账号与共享机制#2.4 入站连接与端口自检|§2.4]]

### 4.9 本章常见坑

| 坑 | 症状 | 处理与出处 |
| --- | --- | --- |
| **以为「配置了 VPN 集成，流量就会走 VPN」** | VPN 开着，但流量实际走了明文出口 | 集成**不改变路由**；路由靠 `network_mode: service:gluetun` 共享网络命名空间保证；见 §4.5、`docs/config.md:1207-1210` |
| **metrics 用默认凭据、或公网保持开启** | 陌生人能读到系统 / 架构 / 磁盘配置 | 公网保持禁用或改凭据；见 §4.7、`docs/config.md:1368-1370` |
| **反代之后仍指望按 CIDR 白名单过滤** | 白名单要么全放行、要么全拦 | 应用不支持 `X-Forwarded-For`；CIDR 过滤要在网络入口做；见 §4.2、`docs/config.md:951` |
| **自定义 JWT key 泄露** | 别人可绕过密码伪造有效 JWT | key 是最高级别秘密；开了 `remote_configuration` 时尤其危险；见 §4.2、`docs/config.md:927` |
| **脚本集成里做命令替换 / 直接传参** | 恶意文件名可注入 shell 命令 | 只读环境变量 + JSON 解析 + 逐字段校验；见 §4.6、`docs/config.md:1165-1173` |
| **在低于 0.26.0 的版本上用 Relay + CIDR 白名单** | 白名单被 `::ffff:` 前缀绕过，等于不设防 | 升到 ≥ 0.26.0，或把限制挪到网络层；见 §4.3、issue #1605 / PR #1714 |
| **M1 单向取信（两种口径只留一种）** | 要么把 README 的 `=true` 抄上公网，要么以为内网也不能开 | 两个语境并列呈现；见 §4.1、上游 §六 M1 |
| **MCP / 第三方生态被写成成熟方案** | 给出了未经一手验证的接入步骤 | 保持打折口径、不推荐具体项目；见 §4.7、上游 §八 O10 |
| **把 P2P / 版权 / VPN 合规写成劝诫或法务判断** | 越出技术说明的边界 | 本章只作客观技术说明；见 §4.5、上游 §九 强制约束 8 |

> [!summary] 本章要点
> - **公网部署三件套**：改默认账密、`remote_configuration` 保持 `false`、`remote_file_management` 保持 `false`。`remote_configuration` 在 README 上手示例里写作 `=true`，而 `config.md` 默认 `false` 并附安全警告——**两种口径并列，内网自用与公网部署是两个语境**。
> - **两套凭据的差别是「过不过期」**：JWT 会过期（默认 7 天）、API key 不会；默认 JWT key 每次启动随机生成，所以重启会让已签发的 JWT 全部失效。
> - **CIDR 过滤在反代后面不可靠**：应用不支持 `X-Forwarded-For`，看到的永远是入口设备的 IP。
> - **CIDR 绕过的安全底线是 0.26.0**：缺陷分两处修——API 侧随 0.24.4（PR #1606），Relay 登录侧随 0.26.0（PR #1714）。在用的 Relay + CIDR 白名单必须 ≥ 0.26.0。
> - **反代的成败在四个头/参数**：`Upgrade`、`Connection "Upgrade"`、`Host`、`proxy_request_buffering off`；子目录部署要把 `URL_BASE` 设成对应前缀。
> - **VPN 集成不改变流量路由**：它只提供可见性、动态端口与极轻量保护；真正让流量走 VPN 的是 `network_mode: service:gluetun`。
> - **脚本集成的输入来自网络**：只读 `$SLSKD_SCRIPT_DATA` 环境变量 + JSON 解析 + 逐字段校验，禁止命令替换与直接传参。
> - **`metrics` 默认关闭但默认凭据是 `slskd`/`slskd`**，公网保持禁用或改凭据；`swagger` 默认关闭，是 Run-Time Overlay 可用选项的权威入口。

到这里，本分册从「把容器跑起来」一路走到了「把它安全地放上公网」。四章覆盖的是一条完整的落地线：部署与运行 → 账号与共享机制 → 日常使用与配置详解 → 安全与进阶速览。中途遇到的具体报错、平台差异和进阶玩法，本分册只给到「够用 + 知道去哪查」，展开的部分留给后续分册与官方文档。回到目录见 [[README|目录]]。
