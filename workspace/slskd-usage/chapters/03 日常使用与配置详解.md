## 第 3 章 日常使用与配置详解

前两章把机器跑起来了、也搞清楚了账号与共享的来龙去脉。但从这一刻起，你面对的是一个没有说明书的 Web 界面和一份「改了不一定生效、改错直接不启动」的配置文件——这一章就是来补这两块空白的：先带你走完搜索 → 筛选 → 下载 → 队列 → 上传的日常动作，再把 `slskd.yml` 的配置体系（优先级、合并陷阱、顶层键、用户组、目录/过滤/黑名单）一次讲透。

### 3.0 开篇声明：官方无 Web UI 操作文档

#### 官方文档目录实际包含哪些文件

官方文档索引 `docs/README.md` 逐条列出的全部内容如下（[docs/README.md](https://github.com/slskd/slskd/blob/master/docs/README.md) 全文）：

### 3.1 搜索与结果筛选（核心工作流）

搜索是 slskd 最核心的日常动作，也是全章操作密度最高的一节。这一节按「发起搜索 → 读结果卡片 → 排序 → 开关 → 筛选 → 边界怪癖」的顺序走一遍。

#### 发起搜索与结果卡片读法

左侧导航的 **Search**（路由 `/searches`）是搜索入口。页面上方是一个搜索输入框，输入框的 `placeholder` 文案是 `Search phrase`（源码 `components/Search/Searches.jsx`）。输入短语回车即发起搜索。

搜索本身是**异步**的：提交后先进入进行中状态，界面上会显示形如 `Found N files (plus M locked) from K users` 的实时进度提示；搜索结束后才从服务端一次性拉取全部响应（源码 `components/Search/Detail/SearchDetail.jsx`）。

搜索列表（`components/Search/List/SearchList.jsx`）的列是固定的七列，从源码里可以逐列对上：

| 列 | 内容 |
| --- | --- |
| 状态图标 | 由搜索状态映射而来的图标（见下表） |
| Search | `searchText`，一个链接，点进去看结果详情 |
| Files | 命中的文件总数 |
| Locked | 需付费「解锁」才能下载的文件数，前面带一个黄色锁图标 |
| Responses | 响应该搜索的用户数 |
| Ended | 结束时间（本地时间格式）；未结束显示 `-` |
| 操作 | 一个图标按钮：已完成 → 删除；否则 → 停止 |

列表默认**按开始时间倒序**排列（最新在最上）。搜索状态的取值在源码注释里列得很清楚（`components/Search/SearchStatusIcon.jsx`）：进行中一侧是 `None` / `Queued` / `Requested` / `InProgress`，完成一侧分两类——**好结果**是 `Completed, TimedOut`、`Completed, ResponseLimitReached`、`Completed, FileLimitReached`（这三种仍然用绿色对勾图标，表示「搜完了，只是被超时/响应数/文件数上限截断」），**坏结果**是 `Completed, Errored`、`Completed, Cancelled`。

搜完之后进入结果详情页。每个响应（也就是每个对端用户）渲染成一张结果卡片（`components/Search/Response.jsx`）：

- **卡片头部**：一个折叠箭头（点击折叠/展开该用户的文件）；一个圆点图标——**绿色表示该用户有免费上传槽位，黄色表示没有**；用户名；最右侧一个红色 ✕，点一下把**这个用户的全部结果**从当前视图里隐藏掉（只是本页隐藏，不会影响对端）。
- **卡片元信息**：形如 `Upload Speed: 1.2 MB/s, Free Upload Slot: YES, Queue Length: 3` 的一行，三项分别是上传速度、是否有免费槽位、排队人数。
- **文件表**（`components/Shared/FileList.jsx`）：五列——勾选框、`File`、`Size`、`Attributes`、`Length`。文件按文件名排序。属于「锁定」分组时，目录图标显示为锁形且整块半透明。
- **下载按钮**：只有勾选了至少一个文件才出现，按钮文案是 `Download`，右侧带一枚标签 `N files, 1.2 GB`（N 与总大小随勾选实时变化）。

#### 排序：只有两项及各自方向

结果详情页左上角是一个排序下拉（`search-options-sort`）。**它只有两项**，而且方向是写死的（源码 `components/Search/Detail/SearchDetail.jsx`）：

| 下拉选项文案 | 值 | 排序方向 |
| --- | --- | --- |
| `Upload Speed (Fastest to Slowest)` | `uploadSpeed` | 降序（默认选中） |
| `Queue Depth (Least to Most)` | `queueLength` | 升序 |

也就是说，**没有按文件大小排序、没有按文件名排序、没有按响应时间排序**。默认是上传速度从快到慢——这意味着默认视图把「快但是排队很长」的用户排在最前面，如果你更在意「不用等」，就该切到 `Queue Depth`。

#### 三个开关与各自默认值

排序下拉右侧是三个开关，都是 toggle 样式（源码同上）：

| 开关文案 | 内部名 | **默认值** | 作用 |
| --- | --- | --- | --- |
| `Hide Locked Results` | `hideLocked` | **开（true）** | 隐藏锁定结果 |
| `Hide Results with No Free Slots` | `hideNoFreeSlots` | 关（false） | 隐藏没有免费上传槽位的用户 |
| `Fold Results` | `foldResults` | 关（false） | 新出现的结果卡片默认折叠 |

**只有第一个开关是默认打开的。**注意它的实现方式：开关打开时，代码不是「跳过锁定文件」，而是把每条响应的 `lockedFileCount` 直接置 0、`lockedFiles` 清空，再交给后续过滤。这个实现细节会在本节末尾的边界行为里咬人。

#### 筛选语法全表（含别名与语义）

排序下拉右边是筛选输入框，标签为 `Filter`。它的解析逻辑全部在 `src/web/src/lib/searches.js` 的 `parseFiltersFromString()` 与 `filterResponse()` 两个函数里——**这是本章最需要逐字核对的一段代码**，因为官方没有任何一份筛选语法文档。

```text
                              ← EX-19（上）：筛选语法速查表
```

筛选输入框把内容按空格切成若干「词」，然后分成三类处理：带 `:` 的走数值过滤器，`is*` 开头的走布尔过滤器，其余的当成文件名关键词。整串是**不区分大小写**的（正则都带 `i` 标志）。

| 语法 | 别名 | 语义（严格按源码） |
| --- | --- | --- |
| `minbitrate:N` | `minbr:` | 剔除 `bitRate < N` 的文件 |
| `minbitdepth:N` | `minbd:` | 剔除 `bitDepth < N` 的文件 |
| `minfilesize:N` | `minfs:` | 剔除 `size < N` 的文件（单位与大小列一致） |
| `minlength:N` | `minlen:` | 剔除 `length < N` 的文件（**秒**） |
| `minfilesinfolder:N` | `minfif:` | 若该响应的文件总数（含锁定）小于 N，则**整条结果的 `files` 置空** |
| `isvbr` | — | 只保留 `isVariableBitRate` 为真的文件 |
| `iscbr` | — | 剔除 `isVariableBitRate` 为 undefined 或为真的文件（即只留明确的 CBR） |
| `islossless` | — | 只保留同时有 `sampleRate` 与 `bitDepth` 的文件 |
| `islossy` | — | 只保留这两个字段都没有的文件 |
| `词` | — | 文件名必须**同时包含全部**关键词（多个词之间是 AND） |
| `-词` | — | 文件名包含该词则剔除 |

几个从代码里读出来的、表格里值得单独拎出来的事实：

1. **数值过滤器是「剔除小于 N」，不是「保留等于 N」**。写 `minbitrate:320` 得到的是「码率 ≥ 320」的全部文件，不是只有 320。
2. **多个关键词之间是 AND**。源码里判断的是「命中关键词条数 === 关键词总数」，任一没命中就整条剔除。想要「或」的语义做不到。
3. **带 `:` 的词不会进入文件名关键词**。所以 `minbitrate:320` 只当过滤器用，不会被拿去当文件名匹配。
4. **`is*` 系列是「子串包含」判定**，不是单词边界匹配（正则就是裸的 `/isvbr/iu`），理论上文件名关键词里出现 `isvbr` 字样也会触发它。
5. **`minfilesinfolder` 是响应级过滤**，一旦不达标就把整条结果的 `files` 清空，而不是逐文件筛。

```text
                              ← EX-19（下）：组合示例
```

下面这串组合示例是**按上表拼接出来的，非信源原文**，官方没有任何组合示例：

```text
minbitrate:320 islossless -live minfilesinfolder:5
```

按源码逐项翻译它的含义：只保留码率 ≥ 320 Kbps 的文件；只保留同时带采样率与位深的（无损）文件；文件名里含 `live` 的剔除；如果某个用户的响应里文件总数不足 5 个，这个用户整条结果被清空；剩下的结果仍按「上传速度从快到慢」排序。

> [!warning] 输入框自带的 placeholder 会误导你
> 筛选输入框的 `placeholder` 里演示了这样一段（源码原文）：
> ```text
> lackluster container -bothersome iscbr|isvbr islossless|islossy
> minbitrate:320 minbitdepth:24 minfilesize:10 minfilesinfolder:8 minlength:5000
> ```
> 注意里面用了 `iscbr|isvbr`、`islossless|islossy` 这种带竖线的写法。但解析函数是**对每个 `is*` 词组独立做一次正则测试**的，根本没有实现「或」的语义——`iscbr|isvbr` 这样写会把 `iscbr` 和 `isvbr` **同时**置为真，而这两个条件的交集是空集，结果是所有文件都被剔除、界面看起来像「筛选把结果清空了」。请把 placeholder 里的竖线当反例看，不要照抄。

#### Attributes 列的渲染规则

`Attributes` 列的内容由 `src/web/src/lib/util.js` 的 `formatAttributes()` 决定，规则一共三条，按优先级从上到下：

| 判断 | 输出 |
| --- | --- |
| 同时有 `sampleRate` 与 `bitDepth` | `位深/采样率kHz`，例如 `24/96kHz` |
| 否则，`isVariableBitRate` 为真 | `N Kbps, VBR`，例如 `320 Kbps, VBR` |
| 否则 | `N Kbps`；若 `bitRate` 为空则整格为空字符串 |

采样率那一条里做了 `sampleRate / 1000` 的换算，所以输出的是 kHz；位深直接原样输出。这也是为什么无损文件在 `Attributes` 列一眼能认出来——它是唯一会显示成 `24/96kHz` 这种形式的一类。

#### 两处已知边界行为（标注"源码可读，实际效果需自测"）

下面两条都是从源码逻辑里读出来的真实行为，不是猜测；但它们最终「看起来是什么效果」依赖于运行时数据，所以官方口径与实测都缺位，请当成**已知怪癖**而非确定结论。

**边界一：`minfilesinfolder` 的名字和它比的东西对不上。**

从名字看，它像是「这个目录里至少有 N 个文件」。但源码里比较的是 `response.fileCount + response.lockedFileCount`——这是**该用户整个响应的文件总数**，不是「某个目录内的文件数」。也就是说，一个用户如果把整张专辑的文件分散汇报在三个目录里，`minfilesinfolder:8` 判定的是「这三个目录加起来够不够 8 个」，而不是「有没有哪个目录里有 8 个」。命名与行为不一致，是源码里可读的事实；实际使用中它能不能达到你想要的「凑齐整张碟」效果，需要自测。

**边界二：默认打开的 `hideLocked` 会静默削弱 `minfilesinfolder`。**

前面说过，`hideLocked` 为真时，代码先把 `lockedFileCount` 置 0，然后才把这条响应交给 `filterResponse()`。而 `minfilesinfolder` 正是在 `filterResponse()` 里用 `response.fileCount + response.lockedFileCount` 做比较的——此时 `lockedFileCount` 已经是 0。所以**在默认开关下，`minfilesinfolder` 只数非锁定的文件**，你输入的数字实际是在跟一个被削过的总数比。

> [!example] 一个可代入的对照
> 某个用户响应里非锁定文件 6 个、锁定文件 6 个，总共 12 个。
> - `Hide Locked Results` **关闭**时：`6 + 6 = 12`，`minfilesinfolder:10` 通过。
> - `Hide Locked Results` **开启**（也就是默认）时：`6 + 0 = 6`，`minfilesinfolder:10` 不通过，这个用户**整条结果被清空**——看起来像「筛掉了本来能用的结果」。
>
> 想验证这一点，最直接的做法是同一组结果下切换这个开关，观察结果卡片数量是否变化。源码可读，实际效果需自测。

#### [!tip] 大白话

> [!tip] 大白话
> 把筛选输入框当成**电商的筛选侧栏**：`minbitrate:320` 类似「码率 ≥ 320」，`-live` 类似「不含关键词 live」。区别在于电商给你的是勾选框，而 slskd 只认英文缩写，还得你自己敲；而且它**没有「或」这个概念**，几个条件只能一路「并且」下去。
> 所以筛选框更像在写一条极简的查询语句，而不是在点勾选框：先想清楚「我要的是全部条件同时满足的结果」，再决定敲哪几个词。

### 3.2 下载、上传与队列管理

搜索的产物是「文件」，而这一节讲的这两条「管子」才是真正搬运文件的地方。搞懂队列，才能在高峰期判断「我到底该等，还是该换个人下」。

#### Downloads / Uploads 视图与批量操作分组

左侧导航的 **Downloads**（`/downloads`）和 **Uploads**（`/uploads`）**共用同一套组件**，只是传入的 `direction` 不同（源码 `components/Transfers/Transfers.jsx` 只有一个 `direction` 参数）。所以下面讲的按钮、列、操作，两边完全对称——唯一的方向性差异是：重试只对下载有意义，所以 Uploads 页面上不渲染重试按钮。

页头是一个批量操作条（`components/Transfers/TransfersHeader.jsx`），三个按钮各自带一个下拉，**每个下拉的选项和默认项都不一样**：

| 按钮 | 下拉选项 | 默认选中 | 实际匹配的状态 |
| --- | --- | --- | --- |
| Retry（仅下载方向） | `Errored` / `Cancelled` / `All` | `Errored` | Errored → `Completed, TimedOut`、`Completed, Errored`、`Completed, Rejected`；Cancelled → `Completed, Cancelled`；All → 所有可重试状态 |
| Cancel | `All` / `Queued` / `In Progress` | `All` | Queued → `Queued, Locally`、`Queued, Remotely`；In Progress → `InProgress` |
| Remove | `Succeeded` / `Errored` / `Cancelled` / `Completed` | `Succeeded` | Succeeded → `Completed, Succeeded`；Errored → 三种失败态；Cancelled → `Completed, Cancelled`；Completed → 所有含 `Completed` 的状态 |

按钮文案会跟着下拉走，例如选了 `All` 就显示 `Retry All`，选了 `Errored` 就显示 `Retry All Errored`；Remove 那一颗永远显示成 `Remove All Succeeded` 这种形式。

> [!warning] 「Remove All Succeeded」是默认动作，别手滑
> Remove 的默认选项是 `Succeeded`，也就是「把已成功的记录清掉」。这看上去无害，但清掉的是**记录**而不是文件——文件还在盘上，只是列表里没了。如果你正等着看某个下载到底成功没有，先在页头确认一下当前选的是不是 `Succeeded`。

#### 传输表列与单文件操作（重试 / 插队）

每条传输按「用户 → 目录」两层分组渲染：外层是用户卡片（`TransferGroup.jsx`，卡片头是用户名，可折叠），内层是目录分组，目录分组里是一张传输表（`components/Transfers/TransferList.jsx`）。

传输表的列一共五列：

| 列 | 内容 |
| --- | --- |
| 勾选框 | 逐文件多选；表头的勾选框是「全选本目录」 |
| File | 文件名 |
| Progress | 进行中的显示百分比进度条；其余状态显示一个**按钮**，按钮文字就是状态本身 |
| Size | `已传 / 总量` 形式的字节数 |
| 详情图标 | 一个灰色 info 图标，点开弹出该传输的全部字段（`TransferDetails`） |

真正好用的是 **Progress 列那颗按钮**——它**同时承担了单文件操作入口**。源码里的判定规则是：

| 当前状态属于 | 按钮行为 | 按钮上的图标 |
| --- | --- | --- |
| 可重试（`Completed` 且不是 `Succeeded`） | 点击 = 重试该文件 | `redo`（仅下载方向显示） |
| 排队类（状态里含 `Queued`） | 点击 = **插队/重新入队该文件** | `refresh`（仅下载方向显示） |
| 其他 | 不可点（上传方向固定不可点） | —— |

按钮文字里还会附加运行时信息，这两处都值得盯：

- `(#N)`：该文件在上游对端的排队位置；
- `(Retry #N)`：这个文件已经重试过的次数，出现过重试时按钮底色会转为黄色。

也就是说，判断「一个文件为什么卡着」不需要点开详情：**看按钮文字就够了**——`Queued, Remotely (#12)` 是在别人队列里排第 12，`Completed, TimedOut (Retry #2)` 是已经超时失败两次了。

#### 目录内补全文件的入口

搜索结果的每个目录分组下方，都有一个按钮 `Search for Additional Files in This Directory`（源码 `components/Search/Response.jsx`）。它的作用是：**就当前这个用户、当前这个目录，再要一份完整清单**，把搜索结果里没显示出来的同目录文件补进结果表。

从源码可以读到三个值得知道的细节：

1. 它调用的是「取目录内容」的接口，而不是重新发起一次搜索——所以它快，而且拿到的是该目录的**当前**内容。
2. 返回结果里**只取第 0 个（根目录）**，子目录不展开。
3. 接口只回文件名，前端会把目录名拼回文件名前面；并且**保留你已有的勾选状态**，不会因为你补全目录而丢掉选好的文件。

这就是「我只搜到这一首，但想要整张碟」的标准动作：先搜到目标文件 → 点这个按钮补全目录 → 在全目录里勾选 → 一起下载。

#### 分页行为

搜索结果**有分页**，传输列表**没有分页**——这两者的差异必须分开说。

搜索结果的分页规则（`components/Search/Detail/SearchDetail.jsx`）：初始只渲染 **5 条**，底部按钮每点一次再加载 **5 条**。按钮文案会带上账目信息，形如：

```text
                              ← 搜索结果分页按钮文案（源码原文形态）
Show 5 More Results (12 remaining, 30 hidden by filter(s))
```

等全部渲染完了，按钮会变成禁用态并显示 `All results shown. 30 hidden by filter(s)`——**后半句就是你诊断筛选写得对不对的地方**：`hidden by filter(s)` 的数量直接告诉你当前筛选剔掉了多少条结果。如果它等于总数，那基本可以确认筛选条件写过头了（回想一下前面 placeholder 里那个 `iscbr|isvbr` 陷阱）。

传输列表则完全没有分页。这是一个已知的实用痛点，官方在 **System → Data** 页签里直接写了应对办法（源码 `components/System/Data/index.jsx` 的说明文字）：

> The Uploads and Downloads pages can become unresponsive if too many transfers are displayed. If you're having trouble with either page, try using the buttons below to remove completed transfers.

对应的两个按钮是 `Clear All Completed Uploads` 与 `Clear All Completed Downloads`。所以**传输页卡顿的标准处置就是去 System → Data 清掉已完成的传输**。

#### 断点续传相关键

「续传」相关的键全部在 `transfers.download.retry` 下（[docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md) Retry Behavior 段）：

| 键 | 代码默认 | 作用 |
| --- | --- | --- |
| `transfers.download.retry.partial` | `resume` | 取 `resume` 或 `overwrite`；决定重试时是接着传还是重头覆盖 |
| `transfers.download.retry.attempts` | `3` | 失败后最多重试几次 |
| `transfers.download.retry.delay` | `5000` | 首次重试前的等待毫秒数 |
| `transfers.download.retry.max_delay` | `60000` | 退避后的最大等待毫秒数 |

官方对续传机制的解释值得原样引一段（同上文档）：

> Incomplete files are stored in subdirectories including the remote user's username and the name of the containing directory on the remote user's PC, which minimizes (but does not completely eliminate!) the risk that a partial file is resumed incorrectly.

也就是说，未完成的文件是**按「来源用户名 / 来源目录」分子目录存放**的，这样续传时才能把磁盘上的半成品和正确来源对上；官方自己用了「minimizes (but does not completely eliminate!)」这种措辞，明确承认它不能 100% 排除错配。如果你更在意「宁可重下也不能拼错」，就把 `partial` 改成 `overwrite`——代价是效率变低、且文件传完的概率会下降（官方原文同样写明了这一点）。

断点续传还牵涉到另外两组键，分别在别处讲：目的地与重名策略见 §3.4 的配置片段，`retention.files.*`（自动删除过期的已完成/未完成文件）见 §3.9。

#### [!tip] 大白话

> [!tip] 大白话
> 把下载队列想成**医院挂号**：
> - 每个对端用户是一个科室，`Queue Length` 就是你前面还有几个人；
> - 卡片头部那个圆点是「有没有空诊室」——绿色 = 有免费上传槽位，黄色 = 医生全在忙；
> - Progress 列那颗 `refresh` 图标按钮相当于「去护士台问一句、顺便插个号」，但它只能让你在**同一个科室**里重新登记，不能让你插到别人前面；
> - `Completed, TimedOut` 就是「这次号作废了」，点那颗 `redo` 按钮等于重新挂一次。
>
> 所以高峰期最省事的策略不是反复重试，而是回到搜索结果里，用 `Hide Results with No Free Slots` 把黄色圆点的用户直接过滤掉，换一个有空诊室的。

### 3.3 其余视图速览

搜索和传输之外的视图，本章只到「知道它干什么、什么时候用得上」的深度。下面每一条都能在前端源码里找到对应文件，来源统一是 `src/web/src/**`。

#### Dashboard：区间与数据块

**Dashboard**（`/dashboard`）是统计视图。顶部有一个可选的搜索栏，下面是历史统计区。历史区间一共七档，**默认 `30d`**（源码 `components/Dashboard/Dashboard.jsx`）：

| 区间标签 | 天数 | 分桶数 |
| --- | --- | --- |
| `24h` | 1 | 24 |
| `7d` | 7 | 84 |
| `30d`（默认） | 30 | 60 |
| `90d` | 90 | 90 |
| `180d` | 180 | 90 |
| `1y` | 365 | 100 |
| `All` | 不限（起点为纪元时间） | 100 |

数据块一共五类，每类都是独立请求，某一类失败不会把整页拖垮（源码里每个请求都单独 catch）：

| 数据块 | 内容 |
| --- | --- |
| summary | 汇总数字 |
| histogram | 直方图（分桶数按上表） |
| leaderboard | 排行榜，分 upload / download 两张 |
| directories | 热门目录（Top Directories） |
| exceptions | 异常统计，**每个方向各有一对**：`pareto`（帕累托分布）与 `recent`（最近若干条），upload / download 各一组 |

要用它做什么：`exceptions` 是排查「为什么上传成功率低」的入口——先看 pareto 找出占比最大的那类错误，再看 recent 看具体样本；`directories` 则能反查「我到底在往哪个目录里堆东西」。注意区间越大分桶越粗，`All` 档在数据量大时精度会明显下降。

#### Browse：目录树与本地缓存

**Browse**（`/browse`）是对端用户的共享目录浏览器。输入用户名（输入框 `placeholder` 是 `Username`）后拉取该用户的目录清单，渲染成可展开的目录树。

三个实现细节值得知道，都是源码可读的：

| 细节 | 表现 |
| --- | --- |
| 本地缓存 | 用 **IndexedDB**，数据库名 `slskd-browse`，`current` 键存当前这份目录数据；刷新页面能恢复上一次浏览的状态 |
| 路径分隔符 | 默认 `\`；若目录名里本身含 `\` 就继续用 `\`，否则会按数据里的实际情况推断 |
| 轮询 | 每 **500ms** 拉一次状态，用于感知扫描/拉取进度 |

此外，勾选过的文件集合另有 `localStorage` 里的 `slskd-browse-state` 记录（源码注释提到 localStorage 的 per-origin 配额限制，以及一个 `MAX_SELECTED_FILES` 上限）。所以**大量勾选可能被浏览器配额截断**——真要批量下整棵目录树，分批勾比一次勾满稳妥。

#### Users / Rooms / Chat

这三个视图都是「人」相关的轻量工具：

| 视图 | 路由 | 能做什么 | 源码可读的实现细节 |
| --- | --- | --- | --- |
| Users | `/users` | 输入用户名查该用户的信息（简介、共享统计等） | 输入框 `placeholder` 是 `Username`；最近查看的用户名存在 `localStorage` 的 `slskd-active-user`，刷新后自动回填 |
| Rooms | `/rooms` | 浏览并加入聊天室、看房间成员列表 | 房间列表 + 加入弹窗 + 用户列表三块 |
| Chat | `/chat` | 私聊会话列表、收发消息 | 会话**每 5 秒轮询**一次；未读会话在打开时会自动调用 acknowledge 标记已读；当前会话记在 `localStorage` 的 `slskd-active-chat` |

Chat 的 5 秒轮询意味着：**私聊不是实时的**，对方的消息最坏情况下要 5 秒后才出现在你界面上；反过来，你发出的消息只要接口返回成功就算送达，不需要等轮询。

#### System 的七个页签（本章多个自查入口都落在这里）

**System**（`/system`）是运维主入口，一共七个页签，路由名与页签一一对应（源码 `components/System/System.jsx`）——本章后面好几处的「去哪自查」都要回到这张表：

| 页签 | 路由 | 内容 | 本章/后续的用法 |
| --- | --- | --- | --- |
| Info | `/system/info` | 顶部四个按钮：`Check for Updates`、`Get Privileges`、`Restart`、`Shut Down`；下方是不可编辑的当前状态 YAML 全文 | `Restart` 按钮在「有待重启的标志」时会变黄，是判断配置是否已生效的入口（见 §3.4） |
| Options | `/system/options` | 当前生效选项的 YAML 全文，**默认只读** | `remote_configuration` 关闭时显示 `Remote Configuration Disabled`；打开后才会出现 `Edit` 按钮（见 §3.4 与 [[04 安全与进阶速览#4.1]]） |
| Shares | `/system/shares` | `Rescan Shares` / `Cancel Scan` 两个按钮 + 共享目录表 + 排除项表 | 判断「共享扫描进展」的唯一界面入口（详见证 [[02 账号与共享机制#2.3 共享目录怎么配（操作面）]]） |
| Files | `/system/files` | 两个子页签 `Downloads` / `Incomplete`，各自一个文件浏览器 | 下载与未完成目录的远程浏览；**删除能力受 `remote_file_management` 控制** |
| Data | `/system/data` | `Clear All Completed Uploads` / `Clear All Completed Downloads` 两个按钮 | 传输页卡顿的处置入口（见 §3.2） |
| Events | `/system/events` | 事件表：`Id` / `Timestamp` / `Type` / `Data`，带分页 | 调试 webhook / 脚本集成时看事件是否真的产生 |
| Logs | `/system/logs` | 日志表：`Timestamp` / `Level` / `Message` | 排错第一站；`Level` 与 `soulseek.diagnostic_level`、`debug` 相关 |

三个需要点明的交互事实：

1. **System 的入口同时出现在左右两组导航里**，而且 `Shares` 与 `Info` 两个页签的图标在有待处理事项时会变成黄色感叹号——`Shares` 的黄色感叹号表示扫描待执行（`scanPending`），`Info` 的表示有待重启或待重连（`pendingRestart` / `pendingReconnect`）。
2. **`Options` 默认不可编辑**，这是一道有意设置的安全边界：改配置默认只能改磁盘上的 YAML 文件。界面能改的前提是 `remote_configuration: true`，而那是有代价的，详见 [[04 安全与进阶速览#4.1 默认凭据与远程配置]]。
3. **`Info` 里显示的是当前状态 YAML，不是你的配置文件原文**。想看配置文件原文，得用 `Options` 里的 `Edit`（需 `remote_configuration`），或者直接看盘上的文件。

#### 主题切换

导航右组有一个 `Theme` 项，点击在 `light` / `dark` 之间切换，选择记在 `localStorage` 的 `slskd-theme`。首次访问没有记录时会跟随系统的 `prefers-color-scheme`。这是个纯前端偏好，与配置文件无关，也不影响任何传输行为。

另外，导航里还会出现两个「通知类」入口，都在源码里可读：`Pending Action`（黄圈感叹号，点击跳到 `/system/info`）和 `New Version!`（喇叭图标，弹窗显示当前版本与可用版本，按钮链到 GitHub releases）。看到 `Pending Action` 基本就等于「你有配置改了但还没生效」。

#### Agent 模式下导航被替换

如果这个实例是以 **Relay Agent** 模式运行（`relay.mode: agent`），左侧那一整组导航（Dashboard / Search / Downloads / Uploads / Rooms / Chat / Users / Browse）**会被整体替换成单个 `Agent Mode` 项**（图标是侦探），也就是说 Agent 模式下**没有搜索、没有下载页**。但**右侧那一组仍然保留**：`Theme`、连接按钮、`System`、`Log Out`。

这条限制直接决定了一件事：在 Agent 实例上，你能做的只有看状态和排错，**真正操作搜索与下载要去 Controller**。Relay 的完整定位见 [[02 账号与共享机制#2.6 Relay 中继模式]]。

### 3.4 配置文件：slskd.yml

从这一节开始进入配置体系。日常界面只能改一点点东西，真正的控制权在 `slskd.yml`——而它有几个非常容易踩的设计。

#### 配置源优先级五层

官方对优先级的表述只有一行，写在 [docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md) 的 Sources 段，原文是：

> The configuration options used by the application derive from the values specified by each of the sources, with sources higher in the hierarchy overwriting or expanding the configuration set earlier. The hierarchy is:

```text
Default Values < Environment Variables < YAML Configuration File < Command Line Arguments < Run-Time Overlay
```

逐层拆开看，「从哪来、什么时候用」是这样的（同段官方说明）：

| 层级 | 来源 | 官方给的适用场景 |
| --- | --- | --- |
| 默认值 | `Options.cs` 里的属性初始值 | 官方原话是「chosen should cover the vast majority of users」 |
| 环境变量 | 一律加 `SLSKD_` 前缀 | 「ideal for use cases involving Docker where configuration is expected to be changed neither often nor remotely」 |
| YAML 配置文件 | `<应用目录>/slskd.yml` | 官方原话「YAML configuration should be used in most cases」 |
| 命令行参数 | `--xxx` | 「loaded last, override all other configuration options, and are immutable at run time」 |
| Run-Time Overlay | 运行时 API 调用 | 「'sticky' but also volatile」 |

三个推论值得直接记住：

1. **改完不生效时，先怀疑「更高层把它盖住了」**。最常见的是：以为改 YAML 就够，其实环境变量里还留着一个旧值；或者 CLI 参数里写死了某项。
2. **CLI 参数运行时不可变**。官方明确说 CLI 是用来放「远程配置、HTTPS JWT secret、证书」这类安全项的最佳位置——因为命令行参数一旦下发，远程攻击者改不了（原话是「Choosing this source for sensitive options can prevent a remote attacker from gaining full control over the application.」）。
3. **环境变量最适合 Docker**，因为它不需要挂载任何文件就能生效；但列表型选项在环境变量里有一个专属坑，见 §3.5。

#### 环境变量前缀与列表分隔符

环境变量全部加 `SLSKD_` 前缀。列表型选项在环境变量里用**分号 `;`** 分隔，官方给的例子就是：

```bash
SLSKD_SOME_OPTION=1;2;3
```

```text
                              ← EX-20：本分册涉及的环境变量写法集
```

下面把本分册会涉及到的 `SLSKD_*` 变量集中列一处，方便对照。这一组是**按各键在 `Options.cs` 上的 `[EnvironmentVariable(...)]` 属性逐个核对过的**，不是从示例文件里抄的：

```bash
# 文件：.env（docker compose 的 environment: 段可直接照此展开）
# --- 身份与目录 ---
SLSKD_APP_DIR=/app                  # 容器内已由镜像固定为 /app
SLSKD_UMASK=0022                    # 官方镜像的默认值

# --- Web UI ---
SLSKD_HTTP_PORT=5030
SLSKD_HTTPS_PORT=5031

# --- Soulseek 账号与入站 ---
SLSKD_SLSK_USERNAME=<你的用户名>
SLSKD_SLSK_PASSWORD=<你的密码>
SLSKD_SLSK_LISTEN_PORT=50300        # 注意"双 SLSK"命名，来源见第 1 章 §1.1
SLSKD_SLSK_ADDRESS=vps.slsknet.org
SLSKD_SLSK_PORT=2271

# --- 列表型（分号分隔） ---
SLSKD_SHARED_DIR=/music;/media/singles
SLSKD_SHARE_FILTER='\.ini$;Thumbs.db$;\.DS_Store$'
SLSKD_SEARCH_REQUEST_FILTER='^.{1,2}$'
SLSKD_ROOMS=slskd;the_room

# --- 日志与行为开关 ---
SLSKD_NO_DISK_LOGGER=false
SLSKD_NO_COLOR=false
SLSKD_VOLATILE=false
SLSKD_CONFIG=/app/slskd.yml

# --- 集成（详见第 4 章） ---
SLSKD_VPN=false
SLSKD_VPN_PORT_FORWARDING=false
SLSKD_VPN_GLUETUN_URL=http://localhost:8000
SLSKD_METRICS=false
SLSKD_SWAGGER=false
```

> [!warning] 变量名是 `SLSKD_SLSK_*`，不是 `SLSKD_SOULSEEK_*`
> `soulseek.*` 这一整组在环境变量层被缩写成了 `SLSK_LISTEN_PORT` 这类形式，加上 `SLSKD_` 前缀后就是 `SLSKD_SLSK_LISTEN_PORT`。这个「双 SLSK」命名不是笔误，但**社区镜像里常见的 `SLSKD_LISTEN_PORT` 并不是官方命名**，写了不会报错、也不会生效。第 1 章 §1.1 已就这条做过完整推导，这里只作复述提醒。

#### CLI 的列表写法

同一个列表型选项，命令行形态用的是**重复参数**而不是分隔符，官方例子：

```text
--some-option 1 --some-option 2 --some-option 3
```

这构成了三种源之间「同一个选项、三种写法」的完整图景——这也正是官方文档在个别地方把自己写混的根源（见 §3.10 的 M2 / M3 / M4）。把它们摆在一起看：

| 源 | 前缀/形式 | 列表分隔 | 例子 |
| --- | --- | --- | --- |
| 环境变量 | `SLSKD_` 前缀 | 分号 `;` | `SLSKD_SHARED_DIR=/a;/b` |
| YAML | 无前缀 | YAML 数组 | `shares: { directories: [/a, /b] }` |
| 命令行 | `--` 前缀 | 重复参数 | `--shared /a --shared /b` |

顺带说明一个曾被称为「第三种键名冲突」的情况：`flags.case_sensitive_reg_ex`。它**不是**三套命名互相矛盾，而是同一个选项在三套命名空间里的三种合法写法——CLI 是 `--case-sensitive-regex`、环境变量是 `SLSKD_CASE_SENSITIVE_REGEX`、YAML 是 `flags.case_sensitive_reg_ex`（源码 `Options.cs` 里该键的 `[Argument]` / `[EnvironmentVariable]` 属性与属性名 `CaseSensitiveRegEx` 可以逐一对上）。唯一的瑕疵是官方文档的散文在指代 YAML 选项时用了环境变量的拼法。**YAML 里要写 `flags.case_sensitive_reg_ex`。**

#### 应用目录与默认配置文件位置

配置文件的位置不是独立选项，而是**由应用目录派生的**（[docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md) Application Directory Configuration 段）：

- 默认位置：`<应用目录>/slskd.yml`；
- 应用目录默认值：Linux/macOS 是 `~/.local/share/slskd`，Windows 是 `%localappdata%/slskd`；
- **官方镜像里应用目录被固定为 `/app`**；
- 想换位置，用 `SLSKD_CONFIG` 环境变量或 `--config` 命令行参数。

还有一个方便的行为：**启动时若该位置没有 YAML 文件，应用会把镜像自带的 `/config/slskd.example.yml` 复制过去**（官方原文「the example file `/config/slskd.example.yml` is copied to this location for convenience」）。注意它是复制**示例**文件，而示例文件的绝大多数行都是被注释掉的——所以复制出来的其实是一份「带目录的空白模板」，不是一份「已经调好的默认配置」。第 1 章 §1.3 已就这一点做过提醒。

#### 热重载、RequiresRestart、RequiresReconnect

官方对热重载的表述如下（同文档 YAML Configuration File 段）：

> The application watches for changes in the YAML file and will reload the configuration when they are detected. Options will be updated in real-time and transmitted to the web UI. If a server reconnect or application restart is required for changes to take effect fully, a flag will be set indicating so.

拆成三句就是：**看着文件** → **改了自动重载** → **有需要重连/重启的项就置标志**。这个「标志」在界面上表现为导航里的 `Pending Action` 提示（点击跳 `/system/info`），在 `Info` 页签里则表现为 `Restart` 按钮变黄。三类选项按生效代价区分：

| 类别 | 典型键 | 生效方式 |
| --- | --- | --- |
| 立即生效 | 上传/下载速度限制、多数用户组设置 | 改完即生效，可在运行时调整 |
| 需要重连（`RequiresReconnect`） | `soulseek.address`、`soulseek.port`、`soulseek.username`、`soulseek.password` | 置 `pendingReconnect` 标志，重连后生效 |

#### Run-Time Overlay：只支持两项，且重启即丢

最后一层配置源是 Run-Time Overlay，性质很特殊（官方原文「they are 'sticky' but also volatile, meaning they are lost when the application is restarted」）：

- **sticky**：它的值会**压过所有其他源**，而且后续改配置文件也盖不掉它（重载后依然以它为准）；
- **volatile**：但应用一重启就没了。

官方明确写出「currently only `listenPort` and `listenIpAddress` are supported」，并给了一段完整的示例调用——用 `PATCH /api/v0/options`、带一个 `administrator` 角色的 API key，body 里只放 `soulseek` 下的这两个键。还有一条非常实用的补充：**改 `listenPort` 之后不需要重连**，Soulseek 服务器会被自动更新（官方原文「the Soulseek server is updated to reflect changes in `listenPort` automatically; there is no need to reconnect.」）。

> [!warning] 别把 Run-Time Overlay 当通用覆盖手段
> 只有两个键支持。想用它去临时改上传槽位、下载目录之类的选项，是做不到的。完整的可用键清单，官方给的权威入口是启用 `feature.swagger` 后的 `/swagger` OpenAPI 定义（官方原文即指这一处）。

#### 不能在 YAML 里设置的键

有两个键**在 YAML 里写了也不会被读**，因为它们在代码里同时标了 `[JsonIgnore]` 和 `[YamlIgnore]`：

| 键 | 代码里的属性 | 为什么不能在 YAML 里设 |
| --- | --- | --- |
| `app_dir` | `[Obsolete("Used only for documentation; see Program for actual implementation")]` + `[JsonIgnore][YamlIgnore]` | 应用目录决定了 YAML 文件在哪，它要是写在 YAML 里就成了循环依赖 |
| `config` | 同上 | 同上——配置文件路径不可能由配置文件自身指定 |

两个键的注释都写着「Used only for documentation; see Program for actual implementation」：它们在 `Options.cs` 里**只是为了让命令行/环境变量的帮助文本有出处**，真实取值由 `Program` 处理。所以只能走 `APP_DIR` / `SLSKD_APP_DIR`（或 `--app-dir`）与 `SLSKD_CONFIG`（或 `--config`）。官方文档的原话说得很直白：「Because the location of the YAML file derived from this value, it can't be specified within the YAML file and must instead be set with the `APP_DIR` environment variable or `--app-dir` command-line argument.」

顺带把同一类「只在命令行/环境变量存在」的键补齐——`Options.cs` 里带 `[YamlIgnore]` 的一共七个，除了 `app_dir` / `config`，另外五个是 `--version`、`--help`、`--envars`、`--generate-cert`、`--generate-secret`，它们本身就是「命令模式」用的动作参数（`--envars` 可用来列出全部可用环境变量，是核对变量名的一个捷径），本来也没有 YAML 形态。

### 3.5 列表合并陷阱（单列一节）

这一节很短，但它是**本分册里最容易造成「配置看起来对、行为却不对」的单一原因**，所以单独成节。

#### 追加 + 覆盖的真实语义

官方在 Sources 段的开头就把这个坑写出来了，原文（[docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md)）：

> Some options can be specified as lists. In these cases, when combining configurations from multiple sources, care should be taken. .NET framework not only appends but also overwrites values. If a list of `one;two;three` is defined in an environment variable for an option, and the YAML configuration specifies a list of `foo` and `bar`, the resulting configuration will be a list containing `foo, bar, three`.

关键在于 .NET 合并列表时的行为**不是「新源替换旧源」，也不是「新源追加到旧源后面」**，而是**逐位置覆盖，短的那一份盖不满的部分保留旧值**。官方给的例子里，环境变量给了 3 个元素、YAML 给了 2 个元素，结果是「YAML 的前两个 + 环境变量的第 3 个」。用图看更清楚：

| 位置 | 环境变量（较低优先级） | YAML（较高优先级） | 最终结果 |
| --- | --- | --- | --- |
| 第 1 位 | `one` | `foo` | `foo` |
| 第 2 位 | `two` | `bar` | `bar` |
| 第 3 位 | `three` | （没有第 3 项） | `three` |

```text

```

下面用本分册会出现的一组真实选项来演示。假设你在 compose 的环境变量里配了共享目录，同时又在 `slskd.yml` 里配了一份：

```bash
# 文件：.env（较低优先级）
SLSKD_SHARED_DIR=/music;/media/singles;/media/boxsets
```

```yaml
# 文件：slskd.yml（较高优先级，取自第 1 章的 EX-06 对应段落）
shares:
  directories:
    - /music
    - /media/live
```

按「逐位置覆盖」的规则，最终生效的共享目录是：

```text
                              ← 最终生效结果（顺序不能反推，位置即优先级）
/music
/media/live
/media/boxsets
```

读法：前两位被 YAML 的 `/music`、`/media/live` 拿走；第三位 YAML 没提供，于是环境变量里的 `/media/boxsets` 保留下来。结果就是**你多分享了一个 `boxsets` 目录**——这个目录既不在你的 YAML 里，也（在你看来）不该出现。

> [!warning] 最坑的一种情况：少了一项，而不是多了一项
> 如果反过来，环境变量只有 2 项、YAML 有 3 项，你看到的结果是正常的（YAML 全盖住了）。所以**只有当低优先级源比高优先级源长时才会暴露问题**——它会「多出几个你没打算要的项」。这也意味着：合并陷阱往往是**沉默地多分享、多过滤、多进房间**，而不会报错。

#### 受影响的选项清单

受影响的判断标准很简单：**凡是数组/列表型选项，都受这条规则支配**。本分册会碰到的主要有这些：

| 键 | 在哪个源里常见 | 混设后的典型症状 |
| --- | --- | --- |
| `shares.directories` | 环境变量（`SLSKD_SHARED_DIR`）最常见 | 多分享出不想分享的目录 |
| `shares.filters` | 环境变量与 YAML 都可能 | 排除规则被「补齐」出多余的几条 |
| `filters.search.request` | 同上 | 搜索请求过滤被补齐，可能误拦 |
| `rooms` | 环境变量（`SLSKD_ROOMS`）常见 | 自动加入多余的聊天室 |
| `transfers.groups.blacklisted.members` / `patterns` / `cidrs` | 基本只在 YAML | 理论上可混设，但实际很少同时用环境变量 |
| `web.authentication.api_keys.*` 之类不是列表的键 | —— | 不受影响（非列表） |

#### 规避做法

三条做法，按推荐顺序：

1. **一个列表型选项，只在一个源里设**。这是官方提醒的本意，也是最省心的做法。既然官方推荐「多数情况用 YAML」，那就把列表全放 YAML，环境变量只放标量（端口、开关、账号）。
2. **如果必须用环境变量（例如不想挂配置文件），那就把 YAML 里的同名键整个删掉**，不要「留一个更长的 YAML 列表去盖它」——那个更长的列表会把环境变量盖干净，但一旦哪天你把 YAML 里的一项注释掉，环境变量的尾巴又会冒出来。
3. **改完列表型配置后，去 `System → Options` 核对一遍生效后的 YAML**。`Options` 页签显示的正是当前生效的完整选项，列表项的条数与内容一眼可数——这是本章最实用的一个自查动作：**不要相信你写的那份文件，要相信 `Options` 里显示的那份**。

#### [!tip] 大白话

> [!tip] 大白话
> 想象两个购物车往一个袋子里塞东西：环境变量是「先塞进去的那车」，YAML 是「后塞进去的那车」。但规则不是「后车整个倒进去」，而是**后车一格一格地占位**——占了 2 格就只盖 1、2 号位，3 号位还留着前车的东西。
> 所以你看到袋子里的东西比你以为的多，第一反应不是「谁往里加了东西」，而是「是不是有个更短的源只盖了一半」。检查顺序永远是：先看 `System → Options` 里生效的那份列表长什么样，再回头找你到底在几个地方写过这个列表。

| 陷阱键 | 正确写法 | 代码里的实际检测逻辑 |
| --- | --- | --- |
| `global` | `transfers` | `if (Groups is not null \|\| Global is not null)` → 「The 'global' and 'groups' keys have been moved under a new 'transfers' key...」 |
| `groups`（**顶层**） | `transfers.groups` | 与 `global` 共用同一条提示 |
| `integration`（单数） | `integrations`（复数） | `if (Integration is not null)` → 「The 'integration' key has been renamed to 'integrations'. Add an 's' to the end of the key to remove this error (no other changes were made)」 |
| `permissions`（**顶层**） | `transfers.download.destination.permissions` | `if (Permissions is not null)` → 「The 'permissions' keys have been moved under a new 'destination' key under transfers -> download, and the behavior has changed...」 |

三条提示的完整原文与「为什么会早退」的机制，第 1 章 §1.12 已经逐字给出（含 `warn` 是属性注释用词而非运行行为的澄清），这里不重复粘贴。**本章要多说一句的是：`integration` 单数与顶层 `groups` 这两个陷阱，恰好也是官方文档自己写错的地方**——见 §3.10 的 M3 / M4。

> [!warning] 一个哨兵键的检测语义值得单独记住
> 检测条件是「**非 null 即存在**」。也就是说，哪怕你在顶层写了一句 `groups:` 后面什么都不跟（YAML 里等于 null），在很多解析路径下也可能被判定成「不存在」而侥幸不报错；但只要你给了任何内容——哪怕是一个空列表 `groups: []`——就会被判定为「存在」，直接启动失败。**对这四个键，唯一正确的做法是彻底不写，而不是写空值。**

### 3.7 用户组与优先级（transfers.groups）

`transfers.groups` 是 `transfers` 下面最复杂的一块，也是第 2 章「共享三层」中第三层（slskd 内置 leechers 组限速）的落地位置。这一节把四类内置组、自定义组、优先级与队列策略讲清楚。

#### 四类内置组各自的定义与来源

内置组一共四个，它们的定义原文在 [docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md) 的 Built-In Groups 与 User Blacklist 两段，逐条可以这样读：

| 组名 | 成员是谁（官方定义） | 是否可配置 |
| --- | --- | --- |
| `default` | 未被显式加入任何自定义组、非 privileged、且未被识别为 leechers 的用户 | 可配置 |
| `leechers` | 未被显式加入自定义组、非 privileged，且共享的**文件数和/或目录数低于该组的 `thresholds`** 的用户。默认阈值下，「必须至少共享一个目录且其中至少有一个文件」才不算 leecher | 可配置（含 `thresholds`） |
| `privileged` | 在 Soulseek 网络上**购买了 privileges** 的用户 | **不可配置** |
| `blacklisted` | 被你说拉黑的用户（按 `members` / `patterns` / `cidrs` 三种方式指定） | 可配置（内容），但它是「拒绝交互」型而非「限速」型 |

几条从官方原文里必须原样保留的重要限定：

- `privileged` 组的固定属性是：**priority 0（最高）**、策略 `FirstInFirstOut`、可用任意多槽位至全局上限，并且**不受任何 limits 约束**（官方原文「Users in this group are also not subject to any limits; they can enqueue any number of files they wish.」）。
- 官方明确写了「**It is impossible to explicitly assign users to these built-in groups**」——内置组不能手工加人，只能调它们的参数（`privileged` 除外，它连参数都不可调）。
- `leechers` 的默认阈值就是各为 1（`thresholds.files: 1`、`thresholds.directories: 1`），所以「完全不共享」的用户一定落在 leechers 组里。
- `blacklisted` 组被明确列举**被阻止的四件事**：接收搜索结果、浏览文件、取目录内容、入队下载；并且私聊与房间消息也会被忽略。它还会**阻止新文件入队**，但已有的活跃/排队传输需要手工取消（官方原文「Any existing active or queued transfers will need to be cancelled manually.」）。

> [!note] blacklisted 组与 §3.9 的 `blacklist.*` 是两回事
> `transfers.groups.blacklisted` 用的是**用户名与用户名正则**（外加 `cidrs`）；§3.9 讲的 `blacklist.enabled` + `blacklist.file` 用的是**一个装着 IP 网段的托管文件**。两者都会导致「拒绝交互」，但入口和载体完全不同，不要混。

#### 自定义组

自定义组挂在 `user_defined` 下，**结构比内置组多一点**：除了和内置组一样的 `upload` 设置外，还可以带一个 `members` 用户名列表（[docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md) User Defined Groups 段）。官方还补了三条规则，都很关键：

1. **一个用户可以属于多个组，生效的是优先级最高的那个**（数字最小的那个）——这直接决定了 priority 的语义（见下）；
2. **如果该用户在网络上买了 privileges，显式分组会被覆盖**，生效组一律是 `privileged`；
3. **被显式分组的用户不会再被识别为 leechers**。

另外代码层面还有一条校验（`Options.cs` 的 `GroupsOptions.Validate`）：**自定义组的名字不能和内置组重名**，否则报「User defined group 'x' collides with a built in group」。

```text
                              ← EX-36：用户组配置片段（取自 [[01 部署与运行]] 的 EX-06 对应段落）
```

```yaml
# 文件：slskd.yml（片段，取自第 1 章 EX-06 的 transfers.groups 段）
transfers:
  groups:
    default:
      upload:
        priority: 500          # EX-06 采用示例文件的取值；代码默认 1（见 §3.8）
        strategy: roundrobin
        slots: 10
    leechers:
      thresholds:
        files: 1
        directories: 1
      upload:
        priority: 999          # 同上：EX-06 采用示例文件取值
        strategy: roundrobin
        slots: 1

    blacklisted:
      members:
        - <要拉黑的用户名>
      patterns:
        - <匹配用户名的正则>

#### priority 的语义方向

官方原文只有两句，方向写得毫无歧义：

> Each group has a priority, starting from 1, determining the order in which groups are prioritized in the upload queue. A lower number translates to higher priority, and Upload slots are granted to higher priority groups before lower priority groups.

所以：**从 1 开始；数字越小越优先；槽位先给高优先级组**。再加上 `privileged` 固定为 0（比任何可配置组都高），就构成了完整的优先级图景。

> [!warning] 内置组的 priority「具体该填多少」是一个未裁决问题
> `docs/config.md` 的示例给 `default: 1` / `leechers: 99`，`config/slskd.example.yml` 给 `default: 500` / `leechers: 999`，而 `Options.cs` 里的类默认值是 `1`。**三方不一致，官方没有裁决**。所以本节只讲语义方向（越小越优先）与 `privileged` 的固定值 0，**不给任何「内置组的实际生效 priority 是多少」的具体数字**。你要调这两个组，自己填一组相对大小正确、互不冲突的数字即可。

#### 队列策略的两种取值

队列策略决定「**同一个组内多个用户**的上传请求按什么顺序处理」，官方原文：

> Groups have a queue strategy, either `FirstInFirstOut` or `RoundRobin`. This setting determines how uploads from multiple users in the same group are processed; `FirstInFirstOut` processes uploads in the order in which they were enqueued, while `RoundRobin` processes uploads in the order in which the user was ready to receive the upload.

对照成中文：

| 取值 | 含义 | 适合什么场景 |
| --- | --- | --- |
| `firstinfirstout` | 按**入队先后**处理 | 先到先得，对早来的用户公平 |
| `roundrobin`（代码默认） | 按**用户就绪的先后**轮转 | 更能利用空闲用户，避免被一个慢用户卡住整队 |

有一个容易写错的点：**YAML 里要写小写无空格的形式**（`roundrobin` / `firstinfirstout`）。代码里是把枚举 `ToString().ToLowerInvariant()` 之后作为默认值的（`Options.cs` 中 `Strategy` 属性的初始化表达式即如此），示例文件里也是 `roundrobin` / `firstinfirstout` 这种形态。写 `RoundRobin` 或 `round-robin` 会有风险。

另外提醒一处**官方文档自身的不一致**：示例文件的 `my_buddies` 组用的是 `strategy`，而 `docs/config.md` 的 Example 段在同一个组里写成了 `queue_strategy`。**以示例文件与 `Options.cs` 为准，YAML 键是 `strategy`。**

#### 组级 slots / speed_limit 与全局限制的关系

这一层关系官方讲得很清楚，是三句话（[docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md) Groups 段）：

1. 全局槽位与速度是**硬上限**，「additive across all groups」；
2. 组级的 `slots` / `speed_limit` 默认是 `int.MaxValue`，等于「让位给全局限制」；
3. **如果组级限制超过全局，全局就成为约束**（原文「If group-level limits exceed global settings, global settings become the constraint.」）。

也就是说，两个层级是**取更严格者**的关系，而不是「组级覆盖全局」。放一张对照表：

| 情况 | 该组的实际可用槽位 |
| --- | --- |
| 组级 `slots` 未设（默认 `int.MaxValue`） | 用全局 `transfers.upload.slots` |
| 组级 `slots` = 3，全局 `slots` = 10 | 3（组级更严） |
| 组级 `slots` = 30，全局 `slots` = 10 | 10（全局成为约束） |

`upload.limits.*`（排队/每日/每周的上传数限制）是另一层：组级 limits **可以覆盖全局默认**；两者都没设时上传不限；想要「全局设了限制、但某个组不限」，就把该组的值设成 `int.MaxValue` 或 `2147483647`（官方原文「While not technically unlimited, this number translates to over 2 petabytes...」）。

还有一条**生效代价**上的差异必须记住：**改动槽位限制需要重启应用，而速度限制可以运行时调整**（官方原文「A change to slot limits requires an application restart to take effect, while speed limits can be adjusted at runtime.」）。这与 §3.4 的 `RequiresRestart` 表格是一致的——`transfers.upload.slots` 正是一个 `[RequiresRestart]` 键。

#### [!tip] 大白话

> [!tip] 大白话
> 把用户组想成**安检通道**：`privileged` 是固定 0 号的贵宾通道（还永不排队），`default` 是普通通道，`leechers` 是你自己划出来的慢速通道。`priority` 就是「第几号通道」——**数字小的先过**，所以 1 比 500 优先，500 比 999 优先。
> `slots` 是这条通道同时能站几个人：通道自己说「我一次放 3 个」，但总闸门（全局）说「全场同时只能进 10 个」，那最终还是更严的那个说了算。
> `strategy` 则是这条通道里的排队规则：`firstinfirstout` 是「按谁先到」，`roundrobin` 是「谁先准备好谁先过」——后者对队伍里那个动作慢的人更宽容，也更能把通道塞满。
> 所以你要是想让朋友优先，**不要**去动 `leechers` 的数字，而是建一个 `user_defined` 组、给一个比 `default` 更小的 priority。

#### 文档与代码不一致处逐条标注

上表里带加粗的地方逐条展开，共九条。这是本章最需要单独记住的部分。

**M2 · `logger` 的磁盘日志键名（语义反向，最危险的一处）。** 真值是 `logger.no_disk`（默认 `false`，意思是「**默认会写盘**」）。`docs/config.md` 的 YAML 块写的是：

logger:
  loki: ~
  disk: false

```

这里的 `disk: false` 有两重错：键名错了（该是 `no_disk`），而且**语义是反的**——如果有人照着理解成「不写盘」，实际拿到的默认行为恰好是写盘（因为默认 `no_disk: false`）。`config/slskd.example.yml` 写的是正确的 `no_disk: false`。**按 `no_disk` 写。**

#### 未裁决项：内置组 priority（只讲语义，不给数字）

**O1。** 内置组 `default` 与 `leechers` 的实际生效 priority 是多少，三方资料不一致（`docs/config.md` 的示例给 `1` / `99`，`config/slskd.example.yml` 给 `500` / `999`，`Options.cs` 的类默认是 `1`），**官方没有裁决，本分册也不裁决**。

因此本章只给两条确定的语义，不给任何具体数字：

1. **数字越小优先级越高**，从 1 开始（官方原文）；
2. **`privileged` 固定为 0**，且不可配置（官方原文「has a priority of 0 (the highest)」）。

你要动这两个组的 priority，唯一的要求是**互相之间的相对大小正确**（例如让 `leechers` 的数字大于 `default`），具体填什么数字不重要。至于「内置组到底默认排在第几」这种问题，本分册不给答案——EX-06 里那两个数字（500 / 999）是从示例文件沿用的示例值，不是默认值。

**顺带记一个同类的未裁决项（O4）：`soulseek.diagnostic_level` 的大小写。** 代码默认是小写 `info`，官方示例文件与文档示例写的是 `Info`。本章**按示例写 `Info`**，并且**不宣称任何大小写敏感规则**——大小写是否敏感、两种写法是否等价，本分册没有取证到结论。

**最后指路一条（M1）：`remote_configuration` 的推荐值。** README 的 quick-start 里出现了 `SLSKD_REMOTE_CONFIGURATION=true`，而 `docs/config.md` 给的默认值是 `false` 并附了一段安全警告，`Options.cs` 的默认值也是 `false`。这两个口径属于两个不同语境（「本机快速上手」与「公网部署」），**必须并列呈现，不做单向取信**；本分册的并列呈现落点在 [[04 安全与进阶速览#4.1 默认凭据与远程配置]]。本章只指路，不复述。

### 3.9 目录、过滤与黑名单

这一节讲三类「管边界」的配置：文件放哪、什么不共享、谁不给进。

#### 两个默认目录与自动创建

`directories` 下只有两个键，默认值都由应用目录派生（[docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md) Other Directory Configuration 段）：

| 键 | 代码默认 | 行为 |
| --- | --- | --- |
| `directories.incomplete` | `<应用目录>/incomplete` | 未完成的下载放这里 |
| `directories.downloads` | `<应用目录>/downloads` | 已完成的下载放这里 |

三个必须记住的行为差别：

1. **默认的那两个目录会在启动时自动创建**（官方原文「The application will create these directories on startup if they don't exist.」）；
2. **但你手工指定的替代目录不会**——官方原文是「Directories must exist and be writable by the application; the application will not attempt to create them.」；
3. 这两个键都带 `[RequiresRestart]`，改了要重启才生效。

> [!warning] 「自动创建」与「不会创建」只差一个条件：你有没有自己指定
> 这是本分册里最容易在容器里翻车的一条：默认路径下一切正常，改成 `/mnt/downloads` 之后就启动失败——不是因为路径不存在，而是因为你**没有先在宿主机上把它建好、也没有让它对容器内的运行身份可写**。挂载点与权限的完整讨论见第 1 章 §1.6 与 §1.9。

#### 默认排除正则

`shares.filters` 是**共享文件的排除正则列表**——凡文件名命中任一条正则的文件，就不会出现在你的共享清单里。

这里必须纠正一个流传很广的说法：**它不是「默认带三条正则」，而是「默认为空」。** 官方文档对此有两处明文：`docs/config.md` 的 Shares → Filters 段写着「a few examples are included below and in the example configuration included with the application, **but the list is empty by default**」；代码里该属性的初始化值也是空数组。

文档与示例文件给的示例排除项是这三条：

```yaml
shares:
  filters:
    - \.ini$
    - Thumbs.db$
    - \.DS_Store$
```

三条各有分工，而且**都用了 `$` 明确锚定到文件名结尾**（官方文档也特别点出这一点）：

| 正则 | 拦掉什么 |
| --- | --- |
| `\.ini$` | 各种 `.ini` 配置文件 |
| `Thumbs.db$` | Windows 生成的缩略图缓存（注意这一条前面的 `Thumbs` 没转义，`.` 在正则里匹配任意字符，所以严格说它也能匹配 `ThumbsXdb` 之类） |
| `\.DS_Store$` | macOS 的目录元数据文件 |

过滤表达式**默认不区分大小写**（官方原文「Filter expressions are case insensitive by default.」），想改成区分大小写就动 `flags.case_sensitive_reg_ex`（YAML 键的拼法见 §3.4）。

文档同时给出了两个配套事实，值得一并记住：`shares.filters` 是「一个可以放任意多条正则的数组」，且**每一条都会在启动校验时检查是否是合法正则**——写了非法正则会有明确的报错（`Options.cs` 里的 `ValidateFilters`），而不是被静默忽略。

#### 黑名单开关与托管黑名单文件（含"文件异常会导致应用退出"）

`blacklist` 下只有两个键，但它们的后果是本分册里最重的一处：

| 键 | 代码默认 | 说明 |
| --- | --- | --- |
| `blacklist.enabled` | `false` | 是否启用托管黑名单文件 |
| `blacklist.file` | `null` | 黑名单文件的路径 |

先把一处容易记反的地方点明：**代码默认是「关闭」**（`Options.cs` 里该属性没有初始化值，`bool` 即为 `false`），而文档的 YAML 块与示例文件写的是 `true`。写文档示例值时请意识到那是「示例打开」，不是默认打开。

接下来是这一节最需要逐字回源的部分。官方原文（[docs/config.md](https://github.com/slskd/slskd/blob/master/docs/config.md) Managed Blacklist 段）：

> When enabled, the specified file is validated by reading the first few lines of the file to automatically detect the format. If the file doesn't exist, can't be read, the format can't be detected, or if it contains any lines that don't match the format, the application will exit. Similarly, if the file changes while the application is running and there's an issue, the application will exit.

拆成可执行的四条：

1. **格式靠「读前几行」自动探测**，支持的格式是 **P2P、DAT、CIDR** 三种（官方原文「specifically the P2P, DAT, and CIDR formats」，代码里的枚举与「Only CIDR, P2P and DAT formats are supported」这条校验提示可以互证）；
2. **文件不存在、读不了、格式探测不出来** → 应用退出；
3. **文件里存在任何一行不符合该格式** → 应用退出；
4. **运行中文件被改动且改出问题** → 应用退出。

还有一条性能相关的提醒：黑名单内容**全部装进内存**以保证性能，所以名单越大内存占用越高，可能「significantly」。

```text
                              ← EX-17：黑名单片段 + CIDR 清单文件
```

```yaml
# 文件：slskd.yml（片段，取自第 1 章 EX-06 的 blacklist 段）
blacklist:
  enabled: true
  file: /app/blacklist_cidrs.txt
```

清单文件本身长什么样？**官方文档没有给出逐行格式定义**，只说它「containing CIDRs to blacklist」。但仓库里有一份自带的 CIDR 格式测试样本，可以直接当作格式依据——**CIDR 格式就是「每行一个网段」，`#` 开头是注释，空行会被跳过**（`src/slskd/Core/Blacklist.cs` 的 `DetectFormat` / `Load` 两处都显式跳过了空行与 `#` 开头行）：

```text
# 文件：blacklist_cidrs.txt
# 一个注释行；空行与 # 开头的行都会被跳过

1.2.4.0/24
1.2.8.0/24
1.9.96.105/32
1.9.102.251/32
```

作为对照，另外两种受支持格式的样子（同样取自仓库自带的测试样本）：**P2P 格式**是「说明文字:起始IP-结束IP」，例如 `China Internet Information Center (CNNIC):1.2.4.0-1.2.4.255`；**DAT 格式**是另一种常见的 P2P 客户端区间列表格式。实际使用中**最省事的是 CIDR**：它是三种里最不容易写错、也最容易从别的封禁列表里生成的。

> [!warning] 这份文件是「能让应用起不来」的少数配置之一
> 三个动作每次都要做全：① 文件**先建好**再开 `blacklist.enabled`；② 内容**全部**符合所选格式（多一行格式不对的注释说明就会退出）；③ 改完**别在运行时随手编辑**——运行中被改坏同样会导致退出。另外这个键带 `[RequiresRestart]`，改开关本身需要重启。稳妥的做法是：先在停机状态下准备好文件，再启动，启动成功后用 `System → Logs` 确认没有格式相关的报错。

#### 搜索请求过滤

`filters.search.request` 是**对入站搜索请求**的过滤列表：别人搜到你身上时，凡搜索词命中列表里任一条正则的，你就不参与该次搜索。它与 `shares.filters`（管「什么文件不出现在共享清单里」）是**两个不同层级的东西**，不要混。

和 `shares.filters` 一样，这里也要纠正一个常见说法：**默认是空列表，不是「默认带 `^.{1,2}$`」**。官方文档在 Filters → Search Filters 段同样写着「the list is empty by default」。

文档与示例文件给出的示例是：

| 正则 | 意图（文档注释原文的意思） |
| --- | --- |
| `^.{1,2}$` | 丢掉长度不足 3 个字符的请求 |
| `^(\.?pdf\|\.?docx\|\.?xlsx)$` | 丢掉可能在找敏感文档的请求（文档 Filters 段给的是这一组） |

同样地，它**默认不区分大小写**，且**每条都会做合法正则校验**。

> [!note] 这两组过滤默认都是「不管」
> `shares.filters` 与 `filters.search.request` 的代码默认都是空数组，文档明文也都是「the list is empty by default」。也就是说：**开箱状态下，什么文件都会共享出去、什么搜索请求都会响应**。想让边界变紧，必须自己动手加条目——而这一步恰恰是很多人以为「已经默认做好了」的地方。

### 本章小结

- **官方没有任何 Web UI 操作文档。** 文档目录只有 9 篇正文，全是部署、配置、网络与排错；本章 §3.1–§3.3 的功能面全部来自前端源码，正文里按「源码可读（已取证）」「源码可读，实际效果需自测」「官方原文（已回源）」三级标注。
- **搜索是本章的操作核心，也最容易被误导。** 排序只有 `Upload Speed`（降序，默认）与 `Queue Depth`（升序）两项；三个开关里只有 `Hide Locked Results` 默认打开；筛选语法只有 `min*` / `is*` / 关键词 / `-关键词` 四类，**没有「或」语义**，且输入框自带的 placeholder 里那个 `iscbr|isvbr` 是反例。
- **配置源是五层，越高越优先**：默认值 < 环境变量 < YAML < 命令行 < Run-Time Overlay。其中 Run-Time Overlay 只支持 `soulseek.listenPort` 与 `listenIpAddress` 两项，且重启即丢；`app_dir` / `config` 不能在 YAML 里设。
- **列表型选项跨源混设会「逐位置覆盖」**，低优先级源比高优先级源长时会沉默地多出几项。列表只在一个源里设是唯一稳妥做法，核对手段是 `System → Options` 里生效后的那份 YAML。
- **顶层键 21 个有效、4 个哨兵。** 三个域外键名（`logger.no_disk`、`integrations` 复数、`transfers.groups`）各有官方文档错误与之对应（M2/M3/M4），**写错会直接启动失败而不是报警告**；另有 M6（`retention.logs` 真值 30）、M7（`transfers.upload.slots` 真值 10）两处文档值与代码不符。
