## 第 1 章 部署与运行

slskd 是「客户端 + 服务端」形态的应用：容器里跑的是一个常驻进程，你在浏览器里操作它。这意味着部署阶段有两件事必须先想清楚——**它要监听哪几个端口**，以及**它以什么身份在容器里跑**（这直接决定下载下来的文件属于谁）。

这一章解决这两件事，外加三件升级前必须知道的事：镜像和健康检查怎么工作、哪些文件系统天生不适合放它的数据库、以及写入哪些旧配置键会让它**直接拒绝启动**。走完这一章，你应该能把一个 slskd 容器跑起来并登入 Web UI，并且知道下一步该去配什么。

### 1.1 先分清三条线：端口语义

slskd 涉及的端口一共有三条线，角色完全不同。很多新手把 `50300` 当成「Web 端口换个数字」，只在防火墙里开放了 `5030`，结果是 Web UI 能进、搜索能用、下载却永远排队——因为**别人连不上你**。所以这一节先把三条线钉死。

| 端口 | 用途 | 方向 | 代码默认值 | 容器内环境变量 |
| --- | --- | --- | --- | --- |
| `5030` | Web UI / API（HTTP） | 入站 | `5030` | `SLSKD_HTTP_PORT` |
| `5031` | Web UI / API（HTTPS，自签证书） | 入站 | `5031` | `SLSKD_HTTPS_PORT` |
| `50300` | Soulseek 对端**连进来**的监听端口 | 入站 | `50300` | `SLSKD_SLSK_LISTEN_PORT` |
| `2271` | 连到 Soulseek **服务器**的出站端口 | 出站 | `2271` | `SLSKD_SLSK_PORT` |

#### 5030 / 5031 —— Web UI（HTTP / HTTPS 自签）

`5030` 和 `5031` 是同一个 Web UI 的两种协议入口：`5030` 明文 HTTP，`5031` HTTPS，证书由应用自己生成（自签）。两者默认都开启。

- 代码真值：`web.port` 默认 `5030`，见 [`src/slskd/Core/Options.cs`](https://github.com/slskd/slskd/blob/master/src/slskd/Core/Options.cs) 第 2019 行 `public int Port { get; init; } = 5030;`（位于 `WebOptions`）。
- `web.https.port` 默认 `5031`，见同文件第 2319 行（位于 `HttpsOptions`）。
- YAML 中分别是 `web.port` 与 `web.https.port`，见 `config/slskd.example.yml` 的 `web:` 段。
- README 的描述是「starts a container instance of slskd on ports 5030 (HTTP) and 5031 (HTTPS using a self-signed certificate)」，并说明可以「access the web UI over HTTP on port 5030, or HTTPS on port 5031」（[README.md](https://github.com/slskd/slskd/blob/master/README.md) Quick Start 段）。

日常用 `5030` 就够了。`5031` 只在一种场景下有独立价值：你要把 Web UI 直接暴露到公网、又不想前面架反向代理。但浏览器一定会报「证书不受信任」，因为它是应用临时生成的自签证书，没有可信证书链。

#### 50300 —— Soulseek 入站监听（别人来敲的门）

`50300` 是 slskd 在 Soulseek 网络里的**监听端口**：它在这里等待其他用户（对端客户端）主动发起 TCP 连接，用来从你这里下载文件、浏览你的共享目录。

- 代码真值：`soulseek.listen_port` 默认 `50300`，见 `Options.cs` 第 1770 行 `public int ListenPort { get; init; } = 50300;`（位于 `SoulseekOptions`），第 1767 行的环境变量名是 `SLSK_LISTEN_PORT`。
- 这个默认值还被固化进官方镜像：`Dockerfile` 第 75 行 `SLSKD_SLSK_LISTEN_PORT=50300`。

关键区别：`50300` 是**入站**端口。你不映射它，slskd 照样能登录服务器、照样能搜索、照样能主动下载别人的文件——因为你是在主动往外连。但别人**永远连不到你**：没有人能从你这里下载文件，也无法浏览你的共享目录。所以 `50300` 必须让外部能建立 TCP 连接（宿主机端口映射 + 防火墙/路由器放行）。

> [!warning] 不要把 50300 和 Web UI 混为一谈
> Web UI 不通，你连界面都打不开，问题一目了然。`50300` 不通则表现为「一切正常，只是没人能下载我的文件」——这种沉默故障最难排查。入站可达性的判定方法与两个已知 issue 的定性状态，见 [[02 账号与共享机制#2.4 入站连接与端口自检]]。

#### 2271 —— 出站到 Soulseek 服务器

`2271` 是 slskd 主动去连的 **Soulseek 服务器**端口。它由三部分构成：

- `soulseek.address` 默认 `vps.slsknet.org`，见 `Options.cs` 第 1706 行。
- `soulseek.port` 默认 `2271`，见同文件第 1716 行 `public int Port { get; init; } = 2271;`，第 1712 行环境变量为 `SLSK_PORT`。
- 两项都带 `[RequiresReconnect]` 标注——改了要重连才生效。

这条线是**出站**的，所以路由器上不需要为它做任何入站放行。你要做的只有一件事：让容器能访问外网。它也几乎不需要改，除非你有意识地把客户端指向另一个服务器地址。

#### 容器内环境变量命名：为什么是 SLSKD_SLSK_LISTEN_PORT

第一次看到 `SLSKD_SLSK_LISTEN_PORT` 的人基本都会愣一下：为什么有两个 `SLSK`？答案是命名规则**叠加**了两层前缀：

1. 所有环境变量统一加应用前缀 `SLSKD_`（`docs/config.md` 的 Sources 段：`Each environment variable name is prefixed with SLSKD_.`）。
2. 这个选项本身的环境变量名，在代码里就叫 `SLSK_LISTEN_PORT`（`Options.cs` 第 1767 行 `[EnvironmentVariable("SLSK_LISTEN_PORT")]`）。

两层拼起来，就是 `SLSKD_` + `SLSK_LISTEN_PORT` = `SLSKD_SLSK_LISTEN_PORT`。同理：

| YAML 键 | 代码里的环境变量名 | 容器中实际变量 |
| --- | --- | --- |
| `web.port` | `HTTP_PORT` | `SLSKD_HTTP_PORT` |
| `web.https.port` | `HTTPS_PORT` | `SLSKD_HTTPS_PORT` |
| `soulseek.listen_port` | `SLSK_LISTEN_PORT` | `SLSKD_SLSK_LISTEN_PORT` |
| `soulseek.port` | `SLSK_PORT` | `SLSKD_SLSK_PORT` |
| `soulseek.address` | `SLSK_ADDRESS` | `SLSKD_SLSK_ADDRESS` |

> [!warning] SLSKD_LISTEN_PORT 这个写法不会被绑定
> `soulseek.*` 这一组在环境变量层被缩写为 `SLSK_*`，所以官方镜像里是双 `SLSK`。你在别处见到过 `SLSKD_LISTEN_PORT`，但按代码里的 `[EnvironmentVariable("SLSK_LISTEN_PORT")]` 声明，应用只认 `SLSKD_SLSK_LISTEN_PORT`，写错的名字会被忽略而不会报错。

#### [!tip] 大白话 + 类比（Web UI = 自己家的门；50300 = 邻居来敲门；2271 = 打给总台的电话）

> [!tip] 大白话
> 把 slskd 想成一间开在小区里的**自提点**：
> - `5030`/`5031` 是**你自己办公室的门**——只有你和店员进出，管界面和操作。
> - `50300` 是**店面朝向街道的那扇卸货门**——社区里的邻居（其他用户）要来这里取货。这扇门长期关着，店里照常营业，但没有人能来取货。
> - `2271` 则是**打给总台的电话**——你要先打过去报到、登记在册，才谈得上后面的事。这是你打出去的，不需要谁给你开条线路。
>
> 所以：门（5030）开在自己家；卸货门（50300）必须朝外敞开；总台电话（2271）只管打出去。

### 1.2 产物一：docker-compose.yml（推荐路径）

部署 slskd 的产物归根结底是一个 compose 文件、一条 `docker run` 命令、或一份二进制加一个 YAML。这一节先看 compose——它是官方文档讲得最完整的路径，也是绝大多数人最终会用的形态。

#### 最小可用 compose（官方镜像 + user:）

官方 README 的「With Docker-Compose」示例就是最小可用形态。下面这份直接对齐它，编号 EX-01：

```yaml
# 文件：docker-compose.yml（EX-01：官方推荐最小可用形态）
services:
  slskd:
    image: slskd/slskd:latest
    container_name: slskd
    user: "1000:1000"
    ports:
      - "5030:5030"
      - "5031:5031"
      - "50300:50300"
    environment:
      - SLSKD_REMOTE_CONFIGURATION=true
    volumes:
      - /srv/slskd:/app
    restart: always
```

四行关键信息：镜像用官方 `slskd/slskd`，身份用 Docker 内置的 `user:`，应用目录挂到 `/app`，三条端口全部映射出去。README 的 compose 示例里 `image` 写作 `slskd/slskd`（省略 tag），这里显式写出 `:latest`，与官方 `docs/docker.md` 的示例写法一致。

> [!warning] 关于 SLSKD_REMOTE_CONFIGURATION=true
> README 的 quick-start 里带着这一行，是为了让你能在 Web UI 里直接改配置。但这个开关在公网部署语境下有安全代价，且它与 `docs/config.md` 的默认值、安全警告口径不同。第 1 章不做展开，只在这里挂一句指路：见 [[04 安全与进阶速览#4.1 默认凭据与远程配置]]。内网自用阶段开着很方便，公网化之前请先读那一节。

#### 端口映射段落逐行说明（三线对应）

```yaml
    ports:
      - "5030:5030"    # Web UI HTTP：宿主 5030 → 容器 5030
      - "5031:5031"    # Web UI HTTPS（自签证书）；不打算用 HTTPS 可省
      - "50300:50300"  # Soulseek 入站监听：必须让外部能连进来，不能省
```

三个映射对应 §1.1 的三条线，但**只有一条是刚需**：

| 映射 | 是否必须 | 漏掉会怎样 |
| --- | --- | --- |
| `5030:5030` | 必须（除非只用 HTTPS 或走反代） | 打不开 Web UI |
| `5031:5031` | 可选 | 只能用 HTTP 访问，其余无影响 |
| `50300:50300` | 必须 | Web UI 正常、下载正常，但**别人连不上你**，无法上传 |

`50300` 这一项写着 `50300:50300` 只是形式上的对称，实际含义是「宿主机的 50300 转发到容器的 50300」。两边的数字不必相同——宿主机上 50300 被占用时，写成 `50300:50300` 以外的形式也可以，但容器内那一边（冒号右侧）必须保持 `50300`，否则应用监听的和映射的就不是同一个端口了。

#### 卷挂载：为什么必须挂 /app

```yaml
    volumes:
      - /srv/slskd:/app
```

`/app` 是容器内的**应用目录**（`Dockerfile` 第 76 行 `SLSKD_APP_DIR=/app`）。它装着 `slskd.yml`、SQLite 数据库（传输与搜索记录）、日志、以及默认的 `incomplete/` 与 `downloads/` 目录。官方配置文档明确写：「This value is set to `/app` within the official Docker image.」

**不挂 `/app` 的后果，镜像作者已经写进 entrypoint 了。** 启动时它会检测该路径是不是 bind mount 或 volume，不是就打印：

```
WARNING: /app is not a bind mount or volume. Configuration and data will be lost if the container is removed.
```

上面这句是按 `SLSKD_APP_DIR=/app`（`Dockerfile` 第 76 行）把变量展开后的样子；`Dockerfile` 里的原文写的是 `${SLSKD_APP_DIR}`，其余字句一致。这段警告在 `Dockerfile` 里出现了三次（第 127-129、142-144、178-180 行），对应三种身份分支——也就是说无论哪种运行方式，只要没挂载就会警告。它警告的不是「配置会丢」这么轻：**你删除容器时，账号密码、共享配置、下载队列、以及已经下载到 `/app/downloads` 的文件会一起消失。**

> [!note] 下载目录也要记得单独挂出去
> `/app` 装的是「应用数据」，不是「你的音乐库」。真正存放媒体文件的下载目录通常另外挂载（官方 `docs/docker.md` 的示例是 `/home/JohnDoe/Music:/music`），并在 `shares.directories` 里登记。共享目录如何配置见 [[02 账号与共享机制#2.3 共享目录怎么配（操作面）]]。

#### 环境变量段落（监听端口 / umask / volatile）

官方最小示例只给了 `SLSKD_REMOTE_CONFIGURATION`。实际部署里另外三个环境变量最常被用到：

```yaml
# 文件：docker-compose.yml（EX-03：在 EX-01 基础上补充 environment 段）
    environment:
      - SLSKD_REMOTE_CONFIGURATION=true
      - SLSKD_SLSK_LISTEN_PORT=50300   # 入站监听端口；改这里要同步改上面的端口映射
      - SLSKD_UMASK=0022               # 进程 umask，决定下载文件落盘的权限位
      # - SLSKD_VOLATILE=true          # 仅在使用 CoW / 网络文件系统时才考虑打开，见 §1.9
```

逐个说清：

- `SLSKD_SLSK_LISTEN_PORT`：容器内监听端口。`Dockerfile` 第 75 行把它固化为 `50300`，所以**不改也能跑**；只有在你想换端口时才需要同时改它和 `ports` 映射。
- `SLSKD_UMASK`：`Dockerfile` 第 72 行默认 `0022`。`docs/config.md` 的 Permissions 段说明，umask `022` 对应文件模式 `644`（属主读写，同组与其他人只读）。这是「下载下来的文件为什么是 `644`」的直接原因。
- `SLSKD_VOLATILE`：对应 `flags.volatile`（`Options.cs` 第 480-484 行），打开后改用内存中的 SQLite 表。它的适用场景与代价见 §1.9，这里先注释掉。

#### 两种用户写法对照（user: vs PUID/PGID）—— 二选一

```yaml
# 文件：docker-compose.yml
# EX-02：与 EX-01 二选一，传统 Linuxserver/*arr 风格的 PUID/PGID 写法
services:
  slskd:
    image: slskd/slskd:latest
    container_name: slskd
    ports:
      - "5030:5030"
      - "5031:5031"
      - "50300:50300"
    environment:
      - PUID=1000
      - PGID=1000
      - SLSKD_REMOTE_CONFIGURATION=true
    volumes:
      - /srv/slskd:/app
    restart: always
```

两份文件**只能选一份**。差别不在一行配置，而在容器启动后的整个执行路径：

| 对比项 | `user: "1000:1000"` | `PUID` / `PGID` |
| --- | --- | --- |
| 容器启动身份 | 直接以非 root 启动 | 以 root 启动 |
| 是否修改内置用户 | 否 | 是（`groupmod` / `usermod`） |
| 是否改 `/app` 属主 | 否 | 是（仅当属主不符） |
| 是否降权 | 不需要 | 用 `gosu` 降权后执行 |
| 官方立场 | **推荐** | 兼容旧习惯 |

两者的差异在 §1.6 会逐一落到 `Dockerfile` 的行号上讲清。这里先记住结论：**官方推荐 `user:`，两套写法不要混用，混用会直接退出。**

#### [!tip] 大白话 + 类比（user: 是"以谁的身份上班"；PUID/PGID 是"上班后再换工牌"）

> [!tip] 大白话
> 把容器想成一个来你家干活的**外包工**：
> - `user: "1000:1000"` 是**招聘时就说明身份**：你以「1000 号员工」的身份进门，从头到尾都不是管理员。他做出来的文件（下载的文件）自然记在 1000 号名下。
> - `PUID`/`PGID` 是**先以管理员身份进门，进门后再换工牌**：容器先以 root 进来，把内置的 `slskd` 账号的 uid/gid 改成你指定的数字，必要时把 `/app` 的属主也改掉，然后换成这个身份干活。
>
> 两条路都到得了终点，但第一条路上没人拿过管理员权限，所以官方说它「objectively superior」。你可以把「先当管理员再换工牌」理解成一段额外的、必须走对的流程——流程本身没问题，多走一步就多一个出错的机会。

### 1.3 产物二：slskd.yml（首次启动自动生成）

容器跑起来只是第一步。真正决定「能不能下载、共享哪些目录、上传怎么排队、要不要开 Relay」的，是应用目录里的那份 `slskd.yml`。这一节讲清它从哪来、放在哪，并给出**本分册唯一一份完整样例**。

#### 文件从哪来：无 YAML 时从示例复制

不需要你手工创建。官方配置文档写得很直白：

> If no such configuration file exists at startup, the example file `/config/slskd.example.yml` is copied to this location for convenience.

（`docs/config.md`，YAML Configuration File 段）

也就是说，**首次启动时如果 `<应用目录>/slskd.yml` 不存在，应用会把自带的示例文件复制一份过去**，你随后编辑这个副本即可。`Dockerfile` 第 27 行 `COPY config config/.` 把 `config/` 目录带进了构建产物，所以示例文件确实在镜像里。这个机制的好处是：你永远有一个「带全部键名和注释的起点」，不用对着文档手写键名。

> [!warning] 自动生成的是一份「示例」，不是一份「默认配置」
> 复制过去的文件里，很多值是**示例值**而不是代码默认值（比如 `transfers.upload.slots: 20`，而代码默认是 `10`）。第 3 章会给出代码真值与示例值的完整对照表，见 [[03 日常使用与配置详解#3.8 常用配置键与默认值]]。读完本章你只需要知道：看到示例文件里的数字，不要默认它就是默认值。

#### 应用目录与配置文件位置

「应用目录」是个关键概念，它同时决定四样东西的位置：YAML 文件、下载目录与未完成目录的默认位置、日志、以及 SQLite 数据库。官方文档的原话是：

> The application directory configuration option determines the location of the YAML file, the default locations of the download and incomplete directories, and the location of application working data, such as logs and SQLite databases.

（`docs/config.md`，Application Directory Configuration 段）

不同部署方式下的位置：

| 部署方式 | 应用目录 | 配置文件 |
| --- | --- | --- |
| 官方 Docker 镜像 | `/app`（`Dockerfile` 第 76 行 `SLSKD_APP_DIR=/app`） | `/app/slskd.yml` |
| 二进制 · Linux / macOS | `~/.local/share/slskd` | `~/.local/share/slskd/slskd.yml` |
| 二进制 · Windows | `%localappdata%/slskd` | `%localappdata%/slskd/slskd.yml` |

两个补充事实：

- 应用目录**不能写在 YAML 里**。官方文档解释了原因：「Because the location of the YAML file derived from this value, it can't be specified within the YAML file and must instead be set with the `APP_DIR` environment variable or `--app-dir` command-line argument.」代码层面也一致——`Options.cs` 第 216-219 行给 `AppDirectory` 属性打了 `[JsonIgnore]` 与 `[YamlIgnore]`。
- 配置文件路径可以改：默认是 `<应用目录>/slskd.yml`，可用 `SLSKD_CONFIG` 环境变量或 `--config` 命令行参数指向别处。

#### 【EX-06】全文唯一一份完整 slskd.yml 综合样例（后续所有片段都从它截取）

下面这份 `slskd.yml` 是**本分册唯一一份完整样例**。后续第 2、3、4 章里所有 `slskd.yml` 片段都从这里截取，不允许另起变体；因此它必须把后面几章会用到的段落都写全——共享目录与排除项、leechers 组阈值、Relay 的 controller 与 agent、用户组、metrics、swagger、黑名单，一个都不能少。

```yaml
# 文件：slskd.yml
# 键名以官方 config/slskd.example.yml 与 src/slskd/Core/Options.cs 为准（版本锚点 0.26.0）
```

### 1.4 产物三：docker run 命令行（与 compose 等价）

compose 文件最终会被翻译成一条 `docker run`。两者能力等价，区别只在于「一份可版本管理的文件」和「一条可粘贴的命令」。临时试用、或在没有 compose 的环境里排查问题时，命令形态更方便。

#### --user 写法

```bash
# EX-04：在宿主机执行，与 EX-01 等价的单条命令
docker run -d \
  --name slskd \
  --user 1000:1000 \
  -p 5030:5030 \
  -p 5031:5031 \
  -p 50300:50300 \
  -e SLSKD_REMOTE_CONFIGURATION=true \
  -v /srv/slskd:/app \
  --restart unless-stopped \
  slskd/slskd:latest
```

`--user 1000:1000` 与 compose 里的 `user: "1000:1000"` 是同一个东西，写法是 `UID:GID`。`-d` 是后台运行，`--restart unless-stopped` 让它在宿主机重启后自动拉起（README 的 compose 示例用的是 `restart: always`，二选一，语义略有差别）。

#### -p 三条端口映射

`-p` 的写法与 compose 的 `ports:` 一一对应：

```bash
# 三条映射的等价关系
# compose: - "5030:5030"    →  -p 5030:5030
# compose: - "5031:5031"    →  -p 5031:5031
# compose: - "50300:50300"  →  -p 50300:50300
```

官方 `docs/docker.md` 与 README 的命令行示例都同时列出这三条，顺序也是 `5030`、`5031`、`50300`——这正是 §1.1 三条线的顺序，可以用它来当记忆锚点。

#### -v 应用目录挂载

```bash
# 官方 docs/docker.md 的完整示例（含共享目录）
docker run -d \
  -p 5030:5030 \
  -p 5031:5031 \
  -p 50300:50300 \
  -e SLSKD_REMOTE_CONFIGURATION=true \
  -v /var/slskd:/app \
  -v /home/JohnDoe/Music:/music \
  -v /home/JohnDoe/eBooks:/ebooks \
  --name slskd \
  --user 1000:1000 \
  slskd/slskd:latest
```

注意这里挂了三个卷：`/app` 是应用数据，`/music` 和 `/ebooks` 是共享出去的媒体目录。**共享目录的挂载点必须与 `shares.directories` 里写的路径一致**——你把宿主的音乐目录挂到容器里的 `/music`，`slskd.yml` 里就得写 `/music`，写宿主机路径是不会生效的。

`docs/docker.md` 还给了一份「用环境变量代替 YAML 配共享目录」的等价写法：

```bash
# 用 SLSKD_SHARED_DIR 代替 shares.directories（列表用分号分隔）
docker run -d \
  -p 5030:5030 -p 5031:5031 -p 50300:50300 \
  -e SLSKD_REMOTE_CONFIGURATION=true \
  -v /var/slskd:/app \
  -v /home/JohnDoe/Music:/music \
  -v /home/JohnDoe/eBooks:/ebooks \
  -e "SLSKD_SHARED_DIR=/music;/ebooks" \
  --name slskd \
  --user 1000:1000 \
  slskd/slskd:latest
```

这里的 `;` 是列表分隔符，不是随便选的符号——官方配置文档说明：「Some options are backed by arrays or lists and allow multiple options to be set via a single environment variable. To achieve this, separate each list item by a semicolon `;` in the value」。**这也正是列表合并陷阱的源头**：同一个选项如果 env 和 YAML 都给了值，结果既不是「以 YAML 为准」也不是「以 env 为准」，而是诡异的混合结果。第 3 章详述，见 [[03 日常使用与配置详解#3.4 配置文件：slskd.yml]]。

### 1.5 产物四：二进制运行

#### 与容器路径的差异点（无 entrypoint 身份逻辑）

二进制路径是官方 README 里并列列出的第三种部署方式：

> The latest stable binaries can be downloaded from the releases page. Platform-specific binaries and the static content for the Web UI are produced as artifacts from every build if you'd prefer to use a canary release. Binaries are shipped as zip files; extract the zip to your chosen directory and run.

（[README.md](https://github.com/slskd/slskd/blob/master/README.md) With Binaries 段）

最小启动流程：

```bash
# EX-05：在宿主系统执行，解压官方 release 压缩包并首次运行
unzip slskd-<版本>-linux-x64.zip -d ~/slskd-bin
cd ~/slskd-bin
chmod +x ./slskd
./slskd            # 首次运行会创建应用目录并生成 slskd.yml
```

与容器路径相比，差异集中在三处：

| 维度 | Docker 容器 | 二进制 |
| --- | --- | --- |
| 应用目录默认位置 | `/app`（`Dockerfile` 固化） | `~/.local/share/slskd`（Linux/macOS）或 `%localappdata%/slskd`（Windows） |
| 运行身份 | 由 entrypoint 三分支决定（`--user` / PUID-PGID / root） | **就是启动它的那个系统用户**，没有内置 `slskd` 用户、没有 `gosu` 降权 |
| 进程管理 | 由 Docker 负责后台化、重启、日志 | 需要自己做：`systemd` 单元、`nohup`、或前台跑 |

README 对应用目录与配置文件的说明是：「An application directory will be created in either `~/.local/share/slskd` (on Linux and macOS) or `%localappdata%/slskd` (on Windows). In the root of this directory the file `slskd.yml` will be created the first time the application runs.」

**身份差异是最需要留意的一条。** 容器里 entrypoint 那一整套逻辑（改 uid/gid、chown `/app`、`gosu` 降权）在二进制路径下**完全不存在**——因为不需要：你用什么系统用户启动它，它就以什么身份运行、就以什么身份写文件。所以「下载的文件属主不对」这类问题在二进制路径下的解法完全不同：不是去调 `PUID`，而是去调启动它的那个用户（或 umask）。

#### 何时才考虑二进制

容器路径在绝大多数情况下更省事：镜像自带依赖、应用目录位置固定、升级就是换个 tag。二进制路径真正值得考虑的场景并不多：

- **目标平台跑不了 Docker**：比如某些 ARM 单板、受限的嵌入式系统，或你没有容器运行时的权限。
- **要和宿主机的文件系统 / 设备做更紧密的集成**：不想经过 bind mount 这一层映射。
- **你已经在用进程管理工具托管一堆服务**：新增一个 `systemd` 单元比新增一个容器更符合现有习惯。

反过来，如果你只是想在 NAS 或一台普通 Linux 服务器上跑起来，容器路径是默认选项，不必纠结。

### 1.6 三种容器运行身份（entrypoint 三分支）

§1.2 说「两套写法和不要混用」，这一节把 why 落到代码上。官方镜像的 `Dockerfile` 里有一段 heredoc 写的 entrypoint 脚本，它开头的注释就是三句话的规格说明：

```text
# supports three modes:
#   1. --user / user: (modern Docker) — container starts as non-root, skips all usermod/chown, execs the app directly.
#   2. PUID/PGID (legacy linuxserver style) — container starts as root, mutates user, chowns /app if needed, drops privileges via gosu.
#   3. neither --user nor at least one of PUID/PGID supplied - container and app run as root
```

（`Dockerfile` 第 97-100 行，注释原文）

注意镜像里预置的账号：`Dockerfile` 第 57-58 行用 `groupadd -o -g 1000 slskd` 和 `useradd -o -u 1000 -g slskd slskd` 创建了 uid/gid 均为 `1000` 的内置 `slskd` 用户。模式 ② 要改的就是这个账号的 uid/gid。

#### ① 现代 Docker：给了 --user / user:

**触发条件**：容器以非 root 身份启动，也就是 `--user` 或 compose 的 `user:` 生效了。脚本用 `if [ "$(id -u)" -ne 0 ]` 判定（`Dockerfile` 第 107 行）。

**这条分支做了什么**：

1. 检查你是否同时又给了 `PUID` 或 `PGID`——给了就报错退出（见本节末）。
2. 尝试 `mkdir -p "${SLSKD_APP_DIR}"`，失败则吞掉错误（第 116-118 行）。
3. 检查 `/app` 是否**可读且可写**；不可读写就报错退出，并把当前用户和当前属主一并打印出来：

```text
ERROR: /app is not readable and/or writable by the current user (1000:1000); currently owned by root:root (0:0).
To fix: chown -R 1000:1000 /path/to/your/mounted/app/directory
```

（第 121-125 行，变量按实际值展开）

4. 打印「没挂卷」的警告（若非 bind mount / volume）。
5. `umask "$SLSKD_UMASK"` 后**直接** `exec "$@"` 执行应用。

**关键点**：这条分支**完全跳过**了 `groupmod`、`usermod` 和 `chown`。它不修改任何账号，也不改任何目录属主。它只做两件事：确认能写 `/app`，设 umask，然后跑。这也是官方说它「objectively superior」的技术根据——**整个生命周期里没有任何一刻拥有 root 权限**。

#### ② 传统风格：给了 PUID 或 PGID

**触发条件**：不是非 root 启动（即以 root 启动），且 `PUID` 或 `PGID` 至少给了一个（`Dockerfile` 第 137 行取反，第 150 行进入该分支）。

**这条分支做了什么**：

```bash
PUID="${PUID:-1000}"    # 只给 PGID 时，PUID 回落到 1000
PGID="${PGID:-1000}"    # 只给 PUID 时，PGID 回落到 1000
```

（第 152-153 行）

1. **格式校验**：`PUID` / `PGID` 必须是数字，否则打印 `ERROR: PUID must be a non-negative integer, got '...'` 并 `exit 1`（第 155-163 行）。
2. **改组**：内置 `slskd` 组的 gid 与 `PGID` 不一致时，`groupmod -o -g "$PGID" slskd`（第 166-168 行）。
3. **改用户**：内置 `slskd` 用户的 uid 或 gid 不匹配时，`usermod -o -u "$PUID" -g "$PGID" slskd`（第 171-173 行）。
4. `mkdir -p "${SLSKD_APP_DIR}"`，并在非挂载时打印同样的卷警告（第 176-180 行）。
5. **按需 chown**（细节见本节末）。
6. `umask "$SLSKD_UMASK"` 后 `exec gosu "${PUID}:${PGID}" "$@"`——用 `gosu` 降权到指定身份再执行（第 189-190 行）。

**关键点**：`-o` 允许非唯一 uid/gid；`${PUID:-1000}` 的写法意味着「只给一个也能跑」，缺的那个会补成 `1000`。

#### ③ 都不给：以 root 运行（向后兼容行为）

**触发条件**：既没有 `--user`，`PUID` 和 `PGID` 也都是空的（`Dockerfile` 第 137 行 `if [ -z "${PUID}" ] && [ -z "${PGID}" ]`）。

**这条分支做什么**：`mkdir -p "${SLSKD_APP_DIR}"`，非挂载时打印警告，`umask`，然后 `exec "$@"`——**不降权**。脚本注释把这点说得很清楚：`# no --user supplied, neither PUID nor PGID supplied, run as root (same behavior as < 0.25.0)`（第 135 行）。

也就是说，这是 0.25.0 之前版本的行为，保留下来是为了让老用户的 compose 文件升级版本后不被打破。**它不会报错，也不会警告你正在以 root 运行**——后果要在很久以后才显现：下载的文件属主是 `root`，宿主机上你的普通账号读不了、挪不动。

> [!warning] 这是最常见的「静默踩坑」路径
> 复制了一份官方最小示例、又恰好删掉了 `--user` 那一行，容器照样启动、Web UI 照样能进、下载照样能完成。直到你想整理这些文件时才发现它们属于 root。识别方法：`ls -l` 看下载目录的属主；修复方法：见 [[03 日常使用与配置详解#3.9 目录、过滤与黑名单]] 或直接在 compose 里补上 `user:` 后重建容器。

#### 同时给 --user 与 PUID/PGID 的后果

这是**三种身份里唯一会立刻报错**的组合。`Dockerfile` 第 109-113 行：

```text
ERROR: PUID/PGID are set but the container is running as a non-root user (using --user or user:).
Use one or the other, not both. Either remove --user and set PUID/PGID, or remove PUID/PGID and use --user.
```

打印这两行后 **`exit 1`**——容器直接退出，不会有任何「部分生效」的中间状态。第二行其实就是镜像作者给出的修复指引，照做即可。

为什么必须互斥：参考 §1.6 的三分支可以看出来，模式 ① 根本不执行改账号的逻辑。如果允许两者共存，`PUID`/`PGID` 的值会被**静默忽略**，用户以为设了、实际没设——这比直接报错危险得多。所以脚本选择了「宁可拒绝启动」。

#### chown 的作用范围（非递归，仅根目录）意味着什么

模式 ② 里那段 chown 前面有一段注释，把设计意图说得很清楚：

```text
# change owner of the the app directory if it isn't correct
# we're not checking anything other than the root, and we're not recursively
# applying the changes, which might be dangerous/unwanted and/or take forever
```

（`Dockerfile` 第 182-187 行，注释原文）

对应代码是：

```bash
if [ "$(stat -c '%u:%g' "${SLSKD_APP_DIR}")" != "${PUID}:${PGID}" ]; then
    chown "${PUID}:${PGID}" "${SLSKD_APP_DIR}"
fi
```

（第 185-187 行）

拆开看，这里有**两个「只」**：

- **只检查根目录**：`stat` 的对象是 `${SLSKD_APP_DIR}` 本身，不看它下面任何一层。
- **只改根目录**：`chown` 没有 `-R`，只改 `/app` 这一个 inode。

这意味着什么？如果 `/app` 的属主已经是 `1000:1000`，entrypoint 会**什么都不做**——哪怕 `/app` 里面某个子目录或文件属于 root（比如上次用模式 ③ 跑出来的 `downloads/`），它也不会去修。反过来，如果 `/app` 属主不对，它也只修最上面这一层。

镜像作者在注释里解释了不做递归的原因：递归「might be dangerous/unwanted and/or take forever」——宿主机目录挂进来可能非常大，递归 chown 既慢又可能误伤你在容器外维护的文件。

> [!example] 一个具体症状与对应动作
> 你用模式 ③（root）跑过一段时间，下载目录里躺着一批 `root:root` 的文件。现在你切成 `user: "1000:1000"` 重启，发现**这些老文件依然改不了**（新文件正常）。原因是 entrypoint 只看 `/app` 根、只看一层，不会递归修复历史遗留。
> 正确动作是手工处理一次：
> ```bash
> # 在宿主机执行；<挂载点> 是你 compose 里 /app 对应的宿主目录
> sudo chown -R 1000:1000 <挂载点>
> ```
> 注意这是**你在宿主机上主动做的一次修复**，不是 entrypoint 会替你做的事。反过来也成立：不要指望用递归 chown 去掩盖「一直以 root 运行」这个根因，先把 `user:` 配对。

#### [!tip] 大白话 + 类比（三种身份 = 三种入职方式，第 3 种是没人管你）

> [!tip] 大白话
> 还是那位外包工，这次看**进门流程**：
> - **模式 ①（`user:`）**：入职时就登记好身份，刷卡进门，从头到尾只是一名普通员工。干净、可预期。
> - **模式 ②（`PUID`/`PGID`）**：先以「临时管理员」身份进门，进到更衣室把员工名册里的工号改成你要的号码，顺手把办公桌（`/app` 的根）换到该员工名下，再换上工牌去干活。名册改好之后一切正常，但流程长、环节多。
> - **模式 ③（都不给）**：**没人管你**。没人给你登记、没人给你换工牌，你就以管理员身份直接开工。机器照样转，直到某天有人问「这些文件怎么都记在管理员名下」。
>
> 而 `--user` + `PUID`/`PGID` 同时给，等于「既说你是普通员工，又让更衣室给你改工号」——系统干脆在门口拦下你，因为这两种说法在流程上不可能同时成立。
>
> 至于「chown 只改根目录不递归」，好比**只把办公室大门挂上你的名牌，里面每个抽屉的标签一个都不动**。门牌对了，抽屉里的旧标签还在。

### 1.7 官方立场：为什么推荐 user:

上一节已经从代码层面说明了「模式 ① 全程没有 root 权限」。这一节补官方文档的立场原文，因为它是本章少数几个**有明确官方表述**的取舍点。

`docs/docker.md` 在列出两种指定用户的方式之后，直接给了比较结论：

> Docker's built-in functionality is objectively superior; the container starts and runs as the user you specify, it never has root privileges. The `PUID`/`PGID` method starts the container as root, updates the built-in `slskd` user's user and group IDs to match the values you provided, and changes the owner of your mounted app directory to that user.

（[docs/docker.md](https://github.com/slskd/slskd/blob/master/docs/docker.md) 原文）

官方文档同时给出了那句最容易踩坑的警告——它说的是 quick-start 的最小示例：

> This configuration, however, doesn't include any shared directories, and any files that are downloaded will be owned by root.

（同文件，紧随 quick-start 命令之后）

这两句话合起来就是本章 §1.2 与 §1.6 的官方依据：**用 `user:`；如果不用，就要接受「下载文件属于 root」这个后果并自己处理**。

另外，维护者在 GitHub discussion #1289 中的表述是「To change the user, run docker with the `--user` argument or set the file permission mode/umask」（据上游研究记录 S34；该讨论原文**未缓存到本机**，此处标记为待核对）。

那么落到你自己的部署上，决策其实只有一条：

| 你的情况 | 选择 |
| --- | --- |
| 新部署，能自由选 | `user: "1000:1000"`（数字改成你宿主账号的 uid:gid） |
| 沿用既有 Linuxserver/*arr 风格模板 | `PUID`/`PGID`，但别同时写 `user:` |
| 不确定宿主 uid/gid | 在宿主机执行 `id -u && id -g` 取数字 |
| 你有 NAS 平台模板帮你填好了 PUID/PGID | 先看清模板用的是哪种方式，再决定要不要覆盖（见 §1.13） |

> [!note] uid 数字本身没有魔法
> `1000:1000` 只是官方示例里出现的数字，量级常见但并非规定。真正的要求只有一个：**这个 uid:gid 必须是你希望拥有下载文件的那个宿主账号**。填错了不会报错，只会让文件属于别人。

### 1.8 镜像、健康检查与启动宽限期

#### 镜像来源与 registry 选择

官方 README 与 `docs/docker.md` 里的示例统一使用同一个镜像名：`slskd/slskd`。README 顶部的 Docker Pulls 徽章指向 `hub.docker.com/r/slskd/slskd`，即官方镜像托管在 Docker Hub。

| 项 | 值 | 可核对的位置 |
| --- | --- | --- |
| 镜像名 | `slskd/slskd` | README 全部示例；`docs/docker.md` 全部示例 |
| 顶部 tag | `:latest` | README / `docs/docker.md` 示例；`config` 与 `docs` 中未给 pin 建议 |
| 项目主页（镜像 LABEL） | `https://slskd.org` | `Dockerfile` 第 87 行 `org.opencontainers.image.url` |

| 许可证（镜像 LABEL） | `AGPL-3.0` | `Dockerfile` 第 86 行 `org.opencontainers.image.licenses` |

镜像内部还固化了一组版本信息环境变量，可以随时在容器里查看当前跑的是哪个构建：

```bash
# 在宿主机执行：查看容器内固化的构建元数据
docker exec slskd env | grep SLSKD_DOCKER_
```

对应的 `Dockerfile` 定义在第 77-79 行：`SLSKD_DOCKER_TAG=$TAG`、`SLSKD_DOCKER_VERSION=$VERSION`、`SLSKD_DOCKER_REVISION=$REVISION`。这是**本地可核实**的那一半。

另一半需要标记清楚：上游研究记录提到过 `ghcr.io/slskd/slskd` 这个 GitHub Container Registry 镜像，以及用 `CONTAINER_VERSION` 精确 pin 构建的做法（据上游研究记录 S16，依据是 CI 配置 `.github/workflows/ci.yml`）。**该 CI 配置与构建脚本未缓存到本机，本章不引用其原文**，此处标注为待核对。可以确定的是：官方文档与 README 的所有示例都只用 `slskd/slskd`（不加 registry 前缀）且统一用 `:latest`，所以照抄官方示例不会出错。

`latest` 的升级语义同样属于「本机无一手证据」的范畴。稳妥的实践是：**升级前先读 release notes，并先跑一遍 §1.11 的旧键检查**——因为 §1.12 会讲到，某些版本升级会让旧配置直接导致启动失败。

#### HEALTHCHECK 的实现与 60 分钟 start-period 的含义

镜像自带健康检查，定义在 `Dockerfile` 第 63 行：

```text
HEALTHCHECK --interval=60s --timeout=3s --start-period=60m --retries=3 CMD wget -q -O - http://localhost:${SLSKD_HTTP_PORT}/health
```

（`Dockerfile` 第 63 行原文）

逐项拆解：

| 参数 | 值 | 含义 |
| --- | --- | --- |
| `--interval` | `60s` | 每 60 秒探一次 |
| `--timeout` | `3s` | 单次探测超过 3 秒算失败 |
| `--start-period` | `60m` | **启动后 60 分钟内，失败不计入状态** |
| `--retries` | `3` | 连续失败 3 次才标记为 unhealthy |
| `CMD` | `wget -q -O - http://localhost:${SLSKD_HTTP_PORT}/health` | 用 `wget` 请求本机 `/health` 接口 |

这里的 `${SLSKD_HTTP_PORT}` 就是 §1.1 里那个默认 `5030` 的变量（`Dockerfile` 第 73 行 `SLSKD_HTTP_PORT=5030`）。所以健康检查的实际目标地址是 `http://localhost:5030/health`，走容器内部回环，**不经过宿主机的端口映射**。

`start-period=60m` 是这份配置里最值得注意的数字：**整整 60 分钟**。这不是随手写的容错值，而是对「首次启动可能极慢」的正面承认——应用启动时要扫描全部共享目录并建立缓存，共享量大时这个扫描可能持续很久。Docker 官方对 `start-period` 的语义是：在这段时间内探测失败不算失败，只用来判断「是否已经启动完成」。

> [!warning] 不要用 healthcheck 状态判断「启动失败」
> 因为 60 分钟宽限期的存在，容器启动后 1 小时内 `docker inspect` 里可能一直显示 `starting`。这是设计如此，不是故障。判断应用是否可用，请用 §1.10 的方法直接请求 `/health`，不要盯着容器状态等。

#### 首次共享扫描可能很慢 → 对应第 2 章 §2.3

共享扫描慢是 slskd 的固有特性，不是 bug。共享目录里的文件数、目录层级、磁盘速度都会影响扫描时长，而扫描未完成前应用无法向网络提供完整的共享文件列表。

正因为这条因果链，下面三件事是连着的：

1. `Dockerfile` 给了 60 分钟的健康检查宽限期；
2. `shares.cache.retention` 默认是 `~`（`config/slskd.example.yml` 第 53 行注释写的是「retain indefinitely (do not automatically re-scan)」），即不自动重扫；
3. 共享目录怎么配、排除项怎么写、在哪看扫描状态，全部放在第 2 章讲，见 [[02 账号与共享机制#2.3 共享目录怎么配（操作面）]]。

在本章里，你只需要记住一个操作建议：**第一次配好共享目录后启动，给足时间再判断它是不是「卡住了」。**

### 1.9 系统要求与已知不兼容

这一节的内容全部指向一件事：**不要把应用的数据库放在一个「不适合数据库」的文件系统上。** 这是 slskd 部署里最容易吃暗亏的地方——配置看起来完全正确，容器也起来了，但应用响应时快时慢、甚至损坏数据。

#### 最低配置与 ARMv6 / Raspberry Pi Zero

官方系统要求文档很短，全文如下：

> Designed to run on a minimum of a Raspberry Pi 2 (or equivalent), or any system with:
> \* x86, x86_64, amd64, or ARMv7+ processor
> \* at least 512mb RAM
> \* at least 150mb disk space
>
> Users concerned about optimal performance should consider something faster.

（[docs/system_requirements.md](https://github.com/slskd/slskd/blob/master/docs/system_requirements.md) 原文）

拆成表格：

| 维度 | 最低要求 |
| --- | --- |
| 架构 | x86、x86_64、amd64 或 **ARMv7+** |
| 内存 | 至少 512 MB |
| 磁盘 | 至少 150 MB |

已知不兼容清单里，前两条都指向同一个根因：

> **ARMv6 及更早的处理器**：`Not supported by the .NET runtime. This may change in future versions.`
> **Raspberry Pi Zero（任何变体）**：`At the moment all Pi Zeros are ARMv6.`

（`docs/known_issues.md` 原文）

所以「能不能跑在 Pi Zero 上」这个问题的答案是**否**——不是因为 slskd 本身，而是因为它运行在 .NET runtime 上，而该 runtime 不支持 ARMv6。这条限制是硬性的，不是性能问题。

#### CoW 文件系统（BTRFS / ZFS）

这是本节最重要的一条。官方 known issues 对原因的解释值得逐字读：

> slskd uses SQLite to store transactional data associated with things like transfers and searches, and these reads and writes experience too much I/O latency for the application to work properly with these filesystems.

（`docs/known_issues.md` 原文）

翻译成机制：slskd 用 SQLite 存「传输记录」和「搜索记录」这类事务型数据，读写频繁且要求低延迟；而 BTRFS / ZFS 这类**写时复制（CoW, Copy-on-Write）**文件系统的每一次写都可能触发新的数据块分配、校验和计算、以及快照元数据更新，导致 I/O 延迟远高于普通文件系统。应用不是「跑不起来」，而是「跑不稳」。

官方给出的三条缓解路径（同一份文档）：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 换盘 | 应用数据放到**独立磁盘或分区**，使用不同的文件系统 | 需要额外的盘或分区 |
| RAM disk | 应用数据放内存盘 | 断电即丢 |
| volatile 模式 | 开 `flags.volatile`（见下） | 重启丢失搜索与传输记录 |

官方同时明确否掉了一条路：「Optimizations to the filesystems can be made to improve performance, but will come at a cost to most other use cases and are not recommended.」——即**不建议**为了 slskd 去改 CoW 文件系统的参数。

#### 网络文件系统（NFS / SMB / Windows 共享）

官方对这一条只给了一句话：

> For the same reasons as copy-on-write systems.

（`docs/known_issues.md`，Application data stored on network filesystems (NFS, SMB, Windows file sharing) 段）

**「同样的原因」= 同样的 I/O 延迟问题**。网络文件系统的每次读写都要经过网络往返，延迟比本地 CoW 只会更高。所以结论一样：**不要把应用数据目录放在 NFS / SMB / Windows 共享上**。

这里有一个非常容易混淆、必须分清的点：

| 放什么 | 能不能放网络文件系统 |
| --- | --- |
| **应用数据**（`/app`：数据库、日志、配置） | **不能**。这是 known issues 明确点名的 |
| **共享的媒体文件**（音乐、电子书等只读内容） | 文档没有禁止。这是你的资料库，不是数据库 |

也就是说，「我把音乐都放在 NAS 上」是常见的合理做法；「我把 slskd 的 `/app` 挂到 NAS 的共享目录上」则是踩坑。

#### volatile 模式：换来的稳定与丢掉的记录

volatile 模式是官方给 CoW / 网络文件系统用户的**逃生通道**。`docs/known_issues.md` 的原文：

> Users can also enable 'volatile mode' (`SLSKD_VOLATILE` or `flags.volatile: true`), which will use in-memory SQLite tables.  Searches and transfers will be lost when the application is restarted while in this mode.

三个要素：用 `SLSKD_VOLATILE` 或 `flags.volatile: true` 开启；底层改用**内存中的 SQLite 表**；**重启后搜索与传输记录全部丢失**。

代码层面也在 `Options.cs` 第 478-484 行确认了这一点，`[Description]` 写的是「use volatile data storage (all data will be lost at shutdown)」，并且这个选项带 `[RequiresRestart]` —— 改了必须重启才生效。

配置片段（取自 EX-06）：

```yaml
# 文件：slskd.yml（片段，取自 EX-06 的 flags 段）
flags:
  volatile: false             # 改为 true 后改用内存表，重启即丢搜索与传输记录
```

environment 写法等价：

```yaml
# 文件：docker-compose.yml（片段）
    environment:
      - SLSKD_VOLATILE=true
```

**丢了什么、没丢什么**（这是决定要不要开的关键）：

| 数据 | volatile 模式下重启后 |
| --- | --- |
| 搜索历史 | 丢失 |
| 传输记录（下载 / 上传的进度与状态） | 丢失 |
| **已下载到 `downloads/` 的实际文件** | **不丢**（文件在磁盘上，与 SQLite 无关） |
| 配置文件 `slskd.yml` | 不丢 |
| 共享目录内容 | 不丢 |

所以 volatile 的代价是「**记录**」而不是「**文件**」。如果你能接受每次重启后下载队列从零开始、需要重新搜索，那它就是让 CoW / 网络文件系统可用的合理妥协。

> [!warning] volatile 不是「性能优化开关」
> 它是**兼容手段**。如果你的应用数据本来就放在合适的本地文件系统上，打开 volatile 只会白白丢掉记录，不会带来任何好处。

#### 云主机 OOM 案例

官方 known issues 里还留了一条具体的实例记录：

> **AWS EC2 t3a.nano with Ubuntu Linux**
> The instance will run out of memory and crash every 12 hours or so. This instance size works when using Amazon Linux OS, but memory usage is very high and wouldn't be able to handle a lot of activity.

（`docs/known_issues.md` 原文）

要点有两个：第一，`t3a.nano` 这个规格已经低于 §1.9 开头那组最低要求里隐含的余量，所以在 Ubuntu 上会周期性 OOM 崩溃；第二，换成 Amazon Linux 虽然能跑，但「memory usage is very high」，仍然不适合高活跃度场景。这条案例的价值是提醒你：**512 MB 是「能跑」的门槛，不是「跑得好」的配置**。

#### [!tip] 大白话 + 类比（把数据库放在会被快照的文件系统上 = 在流水席上记账）

> [!tip] 大白话
> 把 slskd 的 SQLite 数据库想成一本**流水账**，它要求「一有交易就立刻记下，记完立刻翻页」。
> - **BTRFS / ZFS** 这类写时复制文件系统，像是**每写一个字就先给整页拍照存档**。翻页是安全了，但你记账的速度被拖垮，后面排队的人越积越多。
> - **NFS / SMB** 更远——账本不在你手边，在隔壁楼的柜子里，**每写一行都要走过去一趟**。
> - **volatile 模式**则是**改用白板记账**：写字飞快，谁都不卡了，但**一到下班擦板，当晚的流水就没了**。你收进来的货（下载好的文件）还在仓库里，不丢。
>
> 官方那句「不建议为了 slskd 去调文件系统参数」，翻译过来就是：**别为了迁就一本账本去改造整个财务室，把账本换个地方放就行。**

```text
https://<宿主机 IP>:5031        # HTTPS，自签证书，浏览器会警告
```

#### 健康检查地址与判定

健康检查接口是 `/health`，就挂在 Web UI 同一个端口上。这也是镜像 HEALTHCHECK 探测的地址（`Dockerfile` 第 63 行）。

| 判定目标 | 方法 | 期望结果 |
| --- | --- | --- |
| Web UI 进程是否活着 | 请求 `http://localhost:5030/health` | HTTP 200 |
| 容器内部是否正常 | 容器内请求同一地址（不经宿主映射） | HTTP 200 |
| 宿主机映射是否生效 | 从宿主机请求 `http://<宿主 IP>:5030/health` | HTTP 200 |

三条路径分别排掉不同层面的问题：第一条排应用本身，第二条排容器网络，第三条排端口映射。**建议按这个顺序排查**——从内到外，问题定位最快。

#### 日志里应该看到什么

先说清楚边界：**应用自身的启动日志本机没有缓存样本，本节不引用任何「官方日志原文」**，只讲可以在源码与镜像里核对的部分。

可以逐字核对的是 entrypoint 层的输出（`Dockerfile` 第 101-192 行）。成功路径下它应当**什么都不打印**（除非 `/app` 没挂载，此时打印那条 `WARNING`）。而下面这几条一定意味着出了问题：

| 日志片段 | 出现位置 | 含义 |
| --- | --- | --- |
| `ERROR: PUID/PGID are set but the container is running as a non-root user` | 第 110 行 | `--user` 与 `PUID`/`PGID` 混用，容器随即 `exit 1` |
| `ERROR: /app is not readable and/or writable by the current user` | 第 122 行 | `/app` 权限不对，容器 `exit 1`（附带修复命令） |
| `ERROR: PUID must be a non-negative integer, got '...'` | 第 156 行 | `PUID` 不是数字，容器 `exit 1` |
| `WARNING: /app is not a bind mount or volume. ...` | 第 128、143、179 行 | 没挂卷，删容器即丢配置与数据 |

如果应用因 §1.12 的退役键而拒绝启动，还会多出几条 `Validate()` 产生的校验错误——那三条的原文见 §1.12 的 EX-33。

**判断「启动成功」的可靠信号**是：`/health` 返回 200，且能用默认账密登入 Web UI。不要依赖「容器没有打印 ERROR」来判断，因为成功路径本身就是静默的。

#### 端口可达性自测（EX-10）

> [!warning] 下面这段序列是「由镜像 HEALTHCHECK 推导」的，不是信源原文
> `Dockerfile` 第 63 行的 HEALTHCHECK 只负责**容器内部的 `/health` 探测**。它没有、也无法替你验证宿主端口映射和 `50300` 的外部可达性。下面这组命令是笔者**根据该 HEALTHCHECK 的探测目标推导**出的自测序列，用于补齐它覆盖不到的两层，**不是官方提供的诊断流程**。

```bash
# 在宿主机执行：三层可达性自测
# 1) 应用层：容器内部直接请求 /health（与镜像 HEALTHCHECK 同一地址，走回环）
docker exec slskd wget -q -O - http://localhost:5030/health

# 2) 宿主映射层：从宿主机经映射端口请求
curl -sS -o /dev/null -w 'HTTP %{http_code}\n' http://localhost:5030/health

# 3) 外部可达层：50300 入站端口能否建立 TCP 连接
#    在一台「外部」机器上执行（同局域网的另一台机器，或公网上的 VPS）
nc -vz <目标主机 IP 或域名> 50300

# 没有 nc 时的等价写法
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/<目标主机 IP>/50300' \
  && echo "50300 可建立 TCP 连接" \
  || echo "50300 不可达：检查防火墙 / 路由器端口转发 / compose 的 ports"
```

各步骤的判读方式：

| 步骤 | 成功 | 失败说明 |
| --- | --- | --- |
| 1 · 容器内 `/health` | 返回 HTML | 应用本身没起来，先看日志 |
| 2 · 宿主 `5030` | `HTTP 200` | 端口映射或宿主机防火墙有问题 |
| 3 · 外部 `50300` | `succeeded` / 连接成功 | **入站不可达**：别人无法连你，只能主动下载 |

第 3 步是这次自测的重点——正如 §1.1 反复强调的，`50300` 不通**不会让 Web UI 或下载报错**，只会让你在不知不觉中失去上传。入站可达性的完整判定顺序、以及两个已知 issue 的定性状态，属于第 2 章的范畴，见 [[02 账号与共享机制#2.4 入站连接与端口自检]]。

### 1.11 升级与数据库迁移

升级 slskd 通常只是改一个 tag 然后重建容器。但应用在启动时会做一件你可能没意识到的事：**自动执行数据库迁移**。这一节讲清它的流程、出问题时的回滚步骤，以及升级前该做的准备。

#### 迁移自动执行与 backups/ 命名规则

官方迁移文档开篇即说明：

> Database migrations are used to update the structure of the application's databases to support new features or improve functionality. These migrations are applied automatically when the application starts. If a migration fails, the application will attempt to restore the database to its pre-migration state using backups created before the migration process began.

（[docs/migrations.md](https://github.com/slskd/slskd/blob/master/docs/migrations.md) 原文）

流程拆成两步（同一份文档）：

1. **备份**：在应用任何改动之前，为每个数据库创建备份。备份存放在**应用数据目录下的 `backups` 目录**里，命名格式为 `<database>.pre-migration-backup.<migration id>.db`。
2. **应用迁移**：对数据库结构与数据做必要修改。

还有一个关键细节：**每次迁移开始时会生成一个唯一的 `migration id`**。文档解释了它为什么重要：

> At the start of each migration a unique `migration id` is generated. If anything goes wrong, this ID can be used to locate the backup files created before the error occured (as subsequent migration attempts/retries will generate new backups, which may contain partially applied migrations).

也就是说，**重试会产生新的备份**，而新备份里可能含有「迁移做了一半」的脏数据。所以回滚时必须认准**第一次失败**那次生成的 id。

命名规则对照，代入具体值看更清楚：

| 数据库 | 备份文件名 |
| --- | --- |
| `transfers.db` | `transfers.pre-migration-backup.040123_123456.db` |
| 其他数据库 | `<database>.pre-migration-backup.<migration id>.db` |

这些备份都在 `<应用目录>/backups/` 下（容器里就是 `/app/backups/`）。

#### 手工回滚的分步操作

官方文档给的恢复步骤是三步。下面把每一步变成可直接执行的命令：

```bash
# EX-09：在宿主机执行，容器名与挂载路径以你的实际部署为准
# 0) 先给现有数据库留个副本（官方文档未要求，属稳妥做法）
docker exec slskd cp /app/transfers.db /app/transfers.db.broken

# 1) 定位「第一次」失败的 migration id —— 它在应用日志里
docker logs slskd 2>&1 | grep -i migration

# 2) 到 backups 目录里找对应的备份文件
docker exec slskd ls -l /app/backups/

# 3) 去掉文件名里的 .pre-migration-backup.<id> 段、移出 backups/、放回数据目录根
docker exec slskd mv /app/backups/transfers.pre-migration-backup.040123_123456.db /app/transfers.db

# 4) 重启，让应用重新尝试迁移
docker restart slskd
```

对应官方文档的三条原文：

1. **定位备份文件**：找到第一次失败的迁移尝试并记下它的 id（在应用日志里；找不到时可以认为**最旧**的那个 id 就是正确的）。
2. **恢复备份**：把备份文件改名，替换掉当前的数据库文件（文档举的例子是 `transfers.pre-migration-backup.040123_123456.db` → `transfers.db`）；并确保恢复后的文件位于**应用数据目录的根**，也就是要从 `backups/` 里移出去。
3. **重启应用**：应用会检测到恢复后的数据库，并重新尝试应用迁移。

#### 陷入重启循环时的处理

如果应用反复重启、迁移始终不成功，官方给出的处置是：

> If the application gets "stuck" in a reboot loop and can't complete migration(s) successfully, you will need to rename (or delete) the existing database files and allow the application to re-generate them.
> It should be possible to recover the old data, but the process will need to be manual. Create a GitHub issue and provide logs from the failing migration(s).

（`docs/migrations.md` 原文）

拆解成可操作的判断：

| 阶段 | 动作 | 代价 |
| --- | --- | --- |
| 先试回滚 | 按上一节的三步恢复备份 | 无损（若成功） |
| 回滚也失败 | 重命名或删除现有数据库文件，让应用重建 | **旧数据只能手工恢复** |
| 需要官方协助 | 开 GitHub issue 并附失败迁移的日志 | 需要等待 |

「重命名或删除数据库文件」这一步等于**放弃自动恢复**，所以顺序不能颠倒：先试回滚，再考虑重建。

#### 预防动作清单

官方文档给的预防建议有三条：确保磁盘空间充足、迁移过程中不要中断应用、监控日志。结合本章其他小节，可以补成一份更完整的升级前清单：

- [ ] **磁盘空间充足**：迁移前要先建备份，空间不够会直接导致迁移失败。
- [ ] **迁移过程中不要停止应用**：`Do not stop the application while a migration is in progress.` 中断可能留下半完成的数据库。
- [ ] **监控日志**：迁移过程的信息都在日志里，升级后**先看日志再放它跑**。
- [ ] **升级前跑一遍退役键检查**：见 EX-08（§1.12 会讲为什么这一步能省掉大量麻烦）。
- [ ] **升级前备份整个应用目录**：`backups/` 只是应用自己的数据库备份，不含 `slskd.yml`。稳妥做法是整目录打包一份。
- [ ] **确认应用数据不在 CoW / 网络文件系统上**：见 §1.9，迁移期的 I/O 压力更大。

旧键检查命令（EX-08）：

```bash
# 在应用目录（容器内为 /app）执行：扫出会直接导致启动失败的四个退役顶层键
# 注意正则锚定在行首 ^，避免误判 transfers.groups 下的嵌套 groups:
docker exec slskd grep -nE '^(global|groups|integration|permissions):' /app/slskd.yml

# 判读：
#   有输出 → 必须按 EX-33 的提示改写，否则升级后启动即失败
#   无输出 → 通过，但 §1.12 的其余变更点仍需人工确认
```

### 1.12 破坏性变更时间线（升级检查清单）

这一节是本章最需要「照着做」的一节。slskd 在版本演进中移动过几个顶层键的位置，而处理方式**不是打一条警告然后继续跑，而是直接拒绝启动**——应用会在配置校验阶段失败并退出。

#### 0.25.0：三个退役顶层键

`0.25.0` 这一版把三个顶层键搬了家：`global` → `transfers`、`groups` → `transfers.groups`、`integration` → `integrations`；同时新增了 `PUID`/`PGID` 支持（与 `--user` 互斥，即 §1.6 里那条 `exit 1` 规则）。

时间线的依据：`Dockerfile` 第 135 行的注释写明模式 ③ 是「same behavior as < 0.25.0」，这从侧面印证了身份逻辑的变更节点；而键名迁移的官方出处是各版本的 release notes（据上游研究记录 S17/S18，**本机未缓存 release notes 原文，此处标记为待核对**）。可以本地逐字核对的是**迁移本身的提示文案**，见本节的 EX-33。

#### 0.26.0：permissions 迁移与 retry 改名

`0.26.0` 这一版有两处变化：

1. **顶层 `permissions` 键迁移**：旧的顶层 `permissions.file.mode` 被移到 `transfers.download.destination.permissions.mode` 下面，官方明确说**行为也变了**（不是纯位置平移）。
2. **`retry.incomplete` 改名为 `retry.partial`**：这一项属于「同版内新引入的选项改名」，对既有用户不构成破坏。

第 1 条可以从 EX-33 的第三条提示里逐字读到（提示原文写的是「moved under a new 'destination' key under transfers -> download, and the behavior has changed」）。第 2 条与本机缓存可以对照的部分是：`config/slskd.example.yml` 第 74 行当前使用的键名确实是 `partial`，而 `~/.local/share` 两侧的改名历史出自 release notes（**本机未缓存，标为待核对**）。

> [!warning] O2：env / CLI 形态不在本章展开
> 上游研究记录里留了一个未裁决项——`0.26.0` 是否会因为 `--file-permission-mode` / `SLSKD_FILE_PERMISSION_MODE` 也拒绝启动，证据不足。本章的口径是：**只写「顶层 `permissions` 已迁移，旧写法会启动失败」，env 与 CLI 的对应形态不展开**。

#### 哨兵的检测机制（非 null 即存在 → ValidationResult → 启动失败）

这是本节最值得理解的一处设计，因为它解释了两个容易误判的现象：为什么提示文案里出现了 `warn` 这个词，行为却是启动失败。

机制在源码里非常直白。`Options.cs` 第 238-239、254-258、331-332 行定义了四个「哨兵」属性，形态全都一样：

```csharp
[Obsolete("temporary sentinel to warn users about breaking change.  use Transfers.Download.Destination.Permissions instead.")]
public object Permissions { get; init; } = null;
```

四个哨兵分别是 `Permissions`、`Global`、`Groups`、`Integration`。它们的关键设计有两点：

- 类型是 `object`、默认值是 `null`——**只能判断「有没有」，不承载任何真实配置**。
- 配置绑定过程中，只要 YAML 里出现了对应的键，这个属性就会被赋成非 `null`，于是「写入过旧键」这件事就被检测到了。

检测发生在顶层的 `Validate()` 里（`Options.cs` 第 345-372 行）：

```csharp
if (Groups is not null || Global is not null)
{
    results.Add(new ValidationResult("The 'global' and 'groups' keys have been moved under a new 'transfers' key.  ..."));
}

if (Integration is not null)
{
    results.Add(new ValidationResult("The 'integration' key has been renamed to 'integrations'.  ..."));
}

if (Permissions is not null)
{
    results.Add(new ValidationResult("The 'permissions' keys have been moved under a new 'destination' key under transfers -> download, ..."));
}
```

（第 354-368 行，提示文案已省略，见下方引用块全文）

流程是：**键存在（非 null）→ 加入 `ValidationResult` → 校验不通过 → 应用拒绝启动**。

> [!warning] `warn` 是属性注释用词，不是运行行为
> 哨兵属性上的 `[Obsolete("temporary sentinel to warn users about breaking change")]` 里出现了 "warn"。容易据此以为「只是警告」。**实际路径是 `ValidationResult` → 启动失败**，配置校验不通过就没有「继续运行」这个选项。上游研究记录专门指出了这个易错点。

| 旧键 | 现状 | 正确写法 | 首次变更版本 |
| --- | --- | --- | --- |
| `global` | 退役哨兵，写入即启动失败 | `transfers.*` | 0.25.0 |
| `groups`（顶层） | 退役哨兵，写入即启动失败 | `transfers.groups` | 0.25.0 |
| `integration` | 退役哨兵，写入即启动失败 | `integrations` | 0.25.0 |
| `permissions`（顶层） | 退役哨兵，写入即启动失败 | `transfers.download.destination.permissions` | 0.26.0 |

关于 `groups` 有一处特别容易中招：`groups` 这个键名在**正确的位置**（`transfers.groups`）依然合法，只有**写在顶层**才是哨兵。所以 EX-08 的检查命令才要锚定行首 `^`——不能用宽松的匹配把 `transfers:` 下面缩进的 `groups:` 一并扫出来。

### 1.13 NAS 与平台模板（须标注可信度）

NAS 平台上的部署通常走「平台自带的容器模板」，而不是自己写 compose。问题是这些模板的变量与取值，可信度差别很大。这一节按**可信度**分层呈现，每一条都带来源标注。

> [!warning] 阅读本节的正确姿势
> 下面每一条后面的「可信度」标注不是客套话，而是**决定你能不能用它去复制粘贴**的分级。标为「T3」或「未核实」的内容，请当成线索而不是事实。

#### Unraid 官方 CA 模板实测变量

| 项 | 值 | 可信度 |
| --- | --- | --- |

这些数值来自 hotio 的 Unraid 模板仓库（`hotio/unraid-templates@master/hotio/slskd.xml`）与 hotio 的容器页面。**注意这是一个第三方维护者（hotio）的模板，不是 slskd 官方发布的模板**，所以全部标为 T3。

两点值得提醒：

1. **`PUID=99` / `PGID=100` 是模板给出的默认值，不是 slskd 的默认值。** slskd 代码里根本不存在 `PUID` 这个选项——它是镜像 entrypoint 读的环境变量（`Dockerfile` 第 109 行等），默认回落到 `1000`（第 152-153 行）。模板改成 `99`/`100`（Unraid 社区惯用的 nobody / users 取值）是为了让文件属主落到 Unraid 预期的账号上。
2. **模板用的是 `PUID`/`PGID` 路线**，也就是 §1.6 的模式 ②，而不是官方推荐的 `user:`。这不矛盾——模板要适配 Unraid 的用户体系。但如果你在同一份配置里又手工加了 `user:`，就会命中 §1.6 的 `exit 1`。

#### TrueNAS 的 UID 与"组合推断"标注

| 项 | 值 | 可信度 |
| --- | --- | --- |
| TrueNAS 应用默认 UID | `568`（apps） | T1（TrueNAS 官方文档原文：「Defaults to **568** (apps)」） |
| TrueNAS 应用元数据 | `"uid": 568, "gid": 568, "user_name": "Host user is [apps]"` | T1（apps 目录元数据，经 `02_deep_research.md` §四 第 6 条转引） |
| **slskd 用 `user: 568:568`** | —— | **组合推断，非原始资料** |

前两行是 TrueNAS 官方的一手事实，但第三行不是。「把 `568:568` 写进 slskd 的 `user:`」这个具体做法，**没有找到一手出处**：唯一候选来源是一个社区 wiki，全程返回 403（含浏览器 UA），Wayback 也不可达。

所以它的定性必须写清楚：**这是「官方 `user:` 写法（T1）」+「TrueNAS 应用默认 UID = 568（T1）」两条事实组合出来的推断**，推理链本身是合理的，但它**不是一份被引用的原始资料**，不能标注为「TrueNAS 官方推荐 slskd 用 568」。

> [!note] 组合推断是什么意思
> 就像「官方说 A，官方又说 B，所以 A+B 应该可行」——这种推理很多情况下是对的，但它的证据强度和「有人明确写过 A+B 可行」完全不同。所以这里只能标为推断，不能标为原始资料。

#### 群晖：无一手资料，不写

**群晖（Synology）没有任何 slskd 的一手资料。** 能找到的只有通用的 Docker 教程外推，既不是官方文档，也不是针对 slskd 的实测记录。因此本分册不写群晖部署步骤——如果需要，只能按 §1.2 的通用 compose 自己适配，本分册不提供具体指引。

### 1.14 本章常见坑

下面这份清单以**指向条目**形式给出，每条都能回溯到本章正文或上游研究记录的条目。

| 坑 | 症状 | 处理与出处 |
| --- | --- | --- |
| **三种身份模式混用** | 容器启动即 `exit 1`，日志出现 `PUID/PGID are set but the container is running as a non-root user` | 二选一，不要同时给 `--user`、`PUID`/`PGID`；见 §1.6、`Dockerfile:107-113` |
| **没挂 `/app`** | 容器能跑但删容器后配置与数据全丢；启动时有 `WARNING: /app is not a bind mount or volume` | compose 必须有 `- /srv/slskd:/app`；见 §1.2、`Dockerfile:127-129`、`:142-144` |

> [!summary] 本章要点
> - **三条端口线**：`5030`/`5031` = Web UI（HTTP / HTTPS 自签），`50300` = Soulseek 入站监听（别人连你），`2271` = 出站连 Soulseek 服务器。只有 `50300` 不通时问题会静默发生。
> - **容器内环境变量是双层前缀**：`SLSKD_` + 代码里的变量名（如 `SLSK_LISTEN_PORT`）= `SLSKD_SLSK_LISTEN_PORT`。
> - **三种身份三分支**：`user:`（推荐，全程非 root，跳过 usermod/chown）、`PUID`/`PGID`（先 root 再 gosu 降权）、都不给（以 root 运行，向后兼容）。`user:` 与 `PUID`/`PGID` 同时给会 `exit 1`；`chown` 非递归、只改应用目录根。
> - **四份产物等价**：compose、`docker run`、二进制 + `slskd.yml`；`/app` 必须挂载，配置文件是 `<应用目录>/slskd.yml`，无文件时从 `config/slskd.example.yml` 复制。
> - **健康检查**：`wget http://localhost:${SLSKD_HTTP_PORT}/health`，带 `start-period=60m`，因为首次共享扫描可能很慢。
> - **系统要求与不兼容**：最低 Pi 2 / ARMv7+ / 512 MB / 150 MB；ARMv6（含全部 Pi Zero）不支持；**CoW（BTRFS/ZFS）与网络文件系统（NFS/SMB）不要放应用数据**，必要时用 volatile，代价是重启丢搜索与传输记录。
> - **升级**：迁移自动执行，备份在 `backups/`、命名 `<database>.pre-migration-backup.<migration id>.db`；回滚要认第一次失败的 migration id。
> - **四个退役键**（`global`、`groups`(顶层)、`integration`、`permissions`）写入即**启动失败**，靠「非 null 即存在」的哨兵属性检测，而不是警告。
> - **NAS 平台可信度分层**：Unraid hotio 模板为 T3；TrueNAS 的 `568` 为 T1，但用于 slskd 属组合推断；群晖无一手资料。
