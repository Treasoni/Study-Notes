# 第十章：虚拟网络技术全景对比与选型

## 本章要解决什么问题

从 VLAN 到 VXLAN，从 SDN 到网络命名空间，从 VMware 的三种模式到 Docker 的六种模式，再到 Kubernetes 的 CNI 插件——我们在九章的学习中走过了一条从物理到虚拟、从传统到云原生的完整技术链条。

现在，是时候把所有技术放到一张全景地图上，回答最后一个也是最重要的一个问题：**在具体的场景下，到底该用哪种虚拟网络方案？**

本章的目标不是引入新技术，而是建立一套**选型决策框架**。你将理解性能、隔离性、灵活性三者之间不可兼得的权衡关系，掌握 MTU 规划的计算方法，并拿到一张覆盖所有主流场景的选型指南。

---

## 10.1 性能总排序：谁最快？

在整个虚拟网络技术栈中，性能从高到低依次为：

```
Host 模式 > Macvlan/Ipvlan > Underlay CNI (Calico BGP) > Bridge > Overlay CNI (Flannel VXLAN)
```

**为什么是这个顺序？**

| 方案 | 延迟 (ms) | 吞吐 | 损耗来源 |
|------|-----------|------|---------|
| **Host** | ~0.02 | 95%+ 物理网卡 | 几乎无损耗，直接使用主机网络栈 |
| **Macvlan** | ~0.03 | ~9.8 Gbps | 少量 MAC 地址处理开销 |
| **Underlay CNI** | ~1.6 | ~9.2 Gbps | 路由处理 + 少量安全策略 |
| **Bridge (NAT)** | ~0.05 | 中等 | iptables DNAT/MASQUERADE |
| **Overlay CNI** | ~2.8 | ~8.4 Gbps | VXLAN 封装 + 隧道处理 |

> 这里有一个"反直觉"的点：Bridge（Docker 默认模式）的延迟比 Macvlan 高，但比 Overlay CNI 低很多。原因是 Bridge 只有同一主机内的 iptables 处理，而 Overlay 要跨越网络进行封装解封装。跨节点带来的损耗远大于单机内的 NAT 损耗。

**一个简化的记忆框架**：数据包路径上每多一次"绕路"，性能就下降一档。Host 模式直通物理网卡，Macvlan 多一个 MAC 映射，Bridge 多一次 NAT，Overlay 多一次完整的封装解封装。

---

## 10.2 核心三角权衡：隔离性 vs 性能 vs 灵活性

这是虚拟网络选型中最重要的思考框架。三个目标之间存在固有的矛盾，你不可能同时最大化三者。

```
                      性能高
                      │
                      │
        部署容易 ◄────┼────► 隔离性强
                      │
                      │
                  灵活性高
```

用具体的方案来填这个三角形的位置：

| 方案 | 隔离性 | 性能 | 灵活性 | 部署难度 |
|------|--------|------|--------|---------|
| 仅主机模式 (Host-Only) | 最高 | 高 | 最低 | 低 |
| Overlay (VXLAN) | 高 | 低 | 最高 | 最高 |
| Bridge (NAT) | 中 | 中 | 中 | 低 |
| Macvlan | 低 | 高 | 低 | 中 |
| Host | 最低 | 最高 | 低 | 最低 |

**如何权衡**：

- **安全敏感场景**（渗透测试、隔离沙箱）：优先隔离性，接受性能损失 → 仅主机模式或 Overlay
- **性能敏感场景**（数据处理、流媒体）：优先性能，降低隔离要求 → Host 或 Macvlan
- **灵活需求场景**（多团队共享、动态网络）：优先灵活性 → Overlay

## 10.3 Overlay 性能损耗：到底慢在哪里

### 10.3.1 损耗分解

Overlay 网络的"慢"不是单一原因造成的。以下是各环节的损耗分解：

| 损耗来源 | 说明 | 开销占比 |
|---------|------|---------|
| **VXLAN 封装/解封装** | CPU 执行封装和解封装操作 | ~5% |
| **安全策略/防火墙** | iptables 规则匹配（规则越多越慢） | ~20% |
| **流量镜像** | 网络监控和审计的额外处理 | ~5% |
| **veth 数据复制** | 数据在 network namespace 间拷贝 | ~3% |
| **最大总开销** | 所有损耗叠加 | **~33%** |

### 10.3.2 损耗来源图解

```
数据包在 Overlay 网络中的"额外旅程"：

    原始包 ──► veth pair 数据复制 (~3%)
              │
              ▼
          iptables 安全策略 (~20%)
              │
              ▼
          VXLAN 封装 (~5%)
              │  添加 VXLAN头 + UDP头 + 外层IP头 + 外层MAC头
              │  共 50 字节开销
              ▼
          veth 数据复制 (返回路径 ~3%)
              │
              ▼
          物理网卡
```

**两个核心结论**：

1. **最大的损耗来源不是 VXLAN 封装，而是安全策略（iptables）**。20% 的损耗来自每条规则都需要线性匹配。这就是为什么 Cilium（eBPF）能在不减少安全功能的前提下大幅提升性能——它换掉了 iptables，而不是封装层。

2. **所有损耗加起来约 33%**。这意味着 Overlay 网络的吞吐量大约是物理网络的 2/3。这个数据对容量规划非常重要——如果你的业务需要 10 Gbps 的实际吞吐，物理带宽需要预留到 15 Gbps 左右。

## 10.4 MTU 规划指南

MTU（Maximum Transmission Unit，最大传输单元）是虚拟网络中最常见、最容易忽略的问题。一个错误的 MTU 设置会导致 TCP 性能断崖式下降，且排障难度极高。

### 10.4.1 为什么 MTU 这么重要

```
标准以太网帧:
┌────────────────────────────────────────────────────┐
│  MAC头  │  IP头  │  TCP头  │  数据 (1460字节)   │
└────────────────────────────────────────────────────┘
                         总大小 = 1500 字节

VXLAN 封装的帧:
┌────────────────────────────────────────────────────────┐
│ 外层MAC │ 外层IP │ UDP │ VXLAN │ 内层MAC │ 内层IP │ 数据 │
└────────────────────────────────────────────────────────┘
                         总大小 = 1550 字节
```

当物理网络的 MTU 是 1500 时，这个 1550 字节的 VXLAN 帧会被**分片**：拆成两个包发送，接收方再重组。分片带来两个问题：
- 性能下降（一个包变两个，吞吐量减半）
- 部分网络设备丢弃分片包，导致连接中断

### 10.4.2 各场景推荐 MTU

| 场景 | 计算方式 | 推荐 MTU |
|------|---------|---------|
| 标准以太网（无隧道） | 物理 MTU | 1500 |
| VXLAN Overlay | 1500 - 50（VXLAN 开销） | **1450** |
| IPIP Overlay | 1500 - 20（IPIP 开销） | **1480** |
| 巨型帧（Jumbo Frames）+ VXLAN | 9000 - 50 | **8950** |

### 10.4.3 如何检查和调整 MTU

```bash
# 查看当前 MTU 设置
ip link show eth0 | grep mtu
# 输出示例：
# 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...

# 临时修改 MTU（重启后失效）
ip link set eth0 mtu 1450

# 永久修改 MTU（NetworkManager 系统）
# 编辑 /etc/NetworkManager/system-connections/<连接名>.nmconnection
# 在 [ethernet] 段下添加：
#   mtu=1450
# 然后重启 NetworkManager：
nmcli connection reload
nmcli connection down <连接名> && nmcli connection up <连接名>

# 永久修改 MTU（systemd-networkd 系统）
# 编辑 /etc/systemd/network/10-eth0.network
# [Link]
# MTUBytes=1450
# 然后重启：
systemctl restart systemd-networkd

# 验证 MTU 是否生效（通过 ping 测试）
# 发送一个 1473 字节的包（IP头20 + ICMP头8 + 数据1472 = 1500）
# 如果 MTU 是 1450，以下命令应该失败
ping -M do -s 1472 192.168.1.1
# -M do: 禁止分片（DF 标志）
# -s 1472: 数据部分大小（加上 ICMP 头 8 + IP 头 20 = 1500 总大小）
# 如果返回 "message too long" 或 "Frag needed"，说明 MTU 小于 1500
# 逐步调小  -s 值测试实际 MTU：
ping -M do -s 1422 192.168.1.1
# 1422 + 28 = 1450，如果成功，说明实际 MTU >= 1450
```

### 10.4.4 Docker 和 K8s 的 MTU 配置

```bash
# Docker：在 daemon.json 中设置 MTU
# 编辑 /etc/docker/daemon.json
{
  "mtu": 1450
}
# 重启 Docker
systemctl restart docker

# Flannel：在 ConfigMap 中设置 MTU
# Flannel 会自动检测物理网卡 MTU 并减去封装开销
# 但如果物理网卡启用了 9000 字节的 Jumbo Frame，需要手动设置
kubectl edit configmap kube-flannel-cfg -n kube-flannel
# 在 net-conf.json 中添加：
# {
#   "Network": "10.244.0.0/16",
#   "Backend": {
#     "Type": "vxlan"
#   },
#   "MTU": 8950
# }
```

## 10.5 全场景选型决策矩阵

现在我们将全书涉及的所有技术和场景汇聚成一张决策表。

### 10.5.1 虚拟机场景

| 你的需求 | 推荐模式 | 替代方案 | 一句话理由 |
|---------|---------|---------|-----------|
| 日常开发、上网 | NAT | 桥接（若 WiFi 允许） | 开箱即用，WiFi 友好 |
| 对外提供服务 | 桥接 | — | 独立 IP，外部直达 |
| 安全测试、恶意软件分析 | 仅主机 | — | 完全隔离，物理断网 |
| KVM 多虚拟机互访 | NAT (virbr0) | 路由模式 | 默认可用，DNS 自动 |
| KVM 高性能需求 | 桥接 (br0) | — | MAC 透传，损耗 < 5% |

### 10.5.2 Docker 场景

| 你的需求 | 推荐模式 | 替代方案 | 一句话理由 |
|---------|---------|---------|-----------|
| 单机开发测试 | 自定义 Bridge | 默认 bridge | 内置 DNS，隔离好 |
| 单机高性能 | Host | Macvlan | 性能损耗最低 |
| 跨主机通信 | Overlay (VXLAN) | — | 原生支持，不依赖网络 |
| 容器直连公司网络 | Macvlan | IPvlan | 独立 MAC，表现如同物理机 |
| 云平台部署 | Overlay 或 Bridge | — | 云平台可能屏蔽 Macvlan |
| 与虚拟机同网段通信 | Macvlan/Ipvlan | — | 避免多层 NAT 嵌套 |

### 10.5.3 Kubernetes 场景

| 你的需求 | 推荐方案 | 替代方案 | 一句话理由 |
|---------|---------|---------|-----------|
| 个人学习、实验 | Flannel VXLAN | — | 一条命令部署完成 |
| 生产环境（< 50 节点） | Calico VXLAN | Flannel（无策略需求） | 支持 NetworkPolicy，可迁至 BGP |
| 生产环境（> 50 节点） | Calico BGP | Cilium | 无封装，高性能，成熟稳定 |
| 超大规模集群（> 500 节点） | Calico BGP | Cilium | BGP 路由聚合，控制面压力低 |
| 高性能计算（HPC） | Cilium eBPF | Calico BGP | 40% TCP 吞吐提升 |
| 微服务安全（L7 策略） | Cilium | Calico（仅 L3-L4） | HTTP/gRPC 级别策略 |
| 需要流量监控 | Cilium + Hubble | — | eBPF 级可观测性 |
| 老内核（< 4.19） | Flannel 或 Calico | — | Cilium 需要 4.19.57+ |

### 10.5.4 Docker + VM 混合部署场景

| 你的需求 | 推荐方案 | 需要注意 |
|---------|---------|---------|
| 容器和虚拟机互访无 NAT | Macvlan/Ipvlan | Linux 专属 |
| 容器对外暴露服务 | 集中反向代理 | Nginx/HAProxy 做入口 |
| 跨边界访问控制 | iptables DOCKER-USER 链 | Docker 默认规则优先 |

## 10.6 实战建议：一个完整环境搭建参考

作为全书的收尾，这里提供一个结合多场景的实战建议——在一台物理机上搭建一个包含虚拟机、Docker、Kubernetes 的混合环境，让所有模式都能被验证。

### 10.6.1 环境拓扑

```
物理机 (Ubuntu 22.04, eth0: 192.168.1.10/24)
    │
    ├── VMware/KVM 虚拟机 A (桥接模式, 192.168.1.20)
    │      └── 对外提供 Web 服务
    │
    ├── VMware/KVM 虚拟机 B (仅主机模式, 172.16.1.2)
    │      └── 安全测试沙箱
    │
    ├── Docker 容器 (macvlan, 192.168.1.30)
    │      └── 与虚拟机 A 同网段通信
    │
    └── K3s 集群 (Flannel VXLAN, 10.244.0.0/16)
           ├── node-1 (本机)
           └── node-2 (笔记本或另一台物理机)
```

### 10.6.2 验证跨所有模式的连通性

```bash
# 1. 验证 Host 模式性能（作为基准）
#    iperf3 测试 Host 到外部的 TCP 吞吐
iperf3 -c iperf.example.com -t 30
#    记录基准值，如 9.8 Gbps

# 2. 验证 Bridge 模式性能
#    启动一个 iperf3 服务容器
docker run -d --name iperf-server --network bridge \
  networkstatic/iperf3 -s

docker run --rm --network bridge \
  networkstatic/iperf3 -c 172.17.0.2 -t 30

# 3. 验证 Macvlan 模式
#    创建 macvlan 网络（需要物理网络支持）
docker network create -d macvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o parent=eth0 \
  my-macvlan

docker run --rm --network my-macvlan \
  --ip=192.168.1.30 \
  alpine ping 192.168.1.20

# 4. 验证 Flannel VXLAN 跨节点通信
#    （需要在 K3s 集群中创建两个 Pod）
kubectl run pod-a --image=nginx --port=80
kubectl run pod-b --image=busybox -- sleep 3600

kubectl get pods -o wide
# 确认两个 Pod 在不同节点上

# 从 pod-b 访问 pod-a
kubectl exec pod-b -- wget -qO- <pod-a-ip>:80

# 查看网络路径
# 在 node-1 上追踪到 node-2 的 Pod 的路由
traceroute -n <pod-b-ip>
# 如果看到 flannel.1 的 IP，说明 VXLAN 隧道在工作

# 5. 验证 MTU
#    在 Flannel Pod 内测试 MTU
kubectl exec pod-b -- ping -M do -s 1422 <pod-a-ip>
# 1422 + 28 = 1450，成功说明 Flannel MTU 正确

# 尝试更大的包（应该失败）
kubectl exec pod-b -- ping -M do -s 1472 <pod-a-ip>
# 失败说明 MTU 限制生效
```

### 10.6.3 性能基准测试

```bash
# 使用 iperf3 进行 Kubernete 集群性能基准测试
# 需要创建一个 Pod 作为服务端，一个作为客户端

# 部署 iperf3 服务端
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: iperf-server
spec:
  containers:
  - name: iperf
    image: networkstatic/iperf3
    args: ["-s"]
    ports:
    - containerPort: 5201
EOF

# 部署 iperf3 客户端（确保与服务器在不同节点）
kubectl run iperf-client --image=networkstatic/iperf3 -- /bin/sh -c "sleep 3600"

# 获取服务器 IP
kubectl get pod iperf-server -o jsonpath='{.status.podIP}'

# 运行测试
kubectl exec iperf-client -- iperf3 -c <server-ip> -t 30

# 对比：在同一个节点上运行相同测试
# 通过 nodeSelector 将两个 Pod 调度到同一节点
```

核心脉络只有一条：**"从物理网络的硬隔离，到虚拟网络的软定义，再到云原生的可插拔"**。VLAN 在物理交换机上切割网络，VXLAN 在 IP 网络上叠加逻辑网络，SDN 把网络的控制权集中到软件，CNI 将网络能力标准化为插件接口。每一代技术都在解决上一代技术的局限，而理解这条演进脉络，比死记硬背任何一个配置命令都有价值。

## 本章总结

- **性能排序（从高到低）**：Host > Macvlan > Underlay CNI > Bridge > Overlay CNI
- **三角权衡**：隔离性、性能、灵活性三者不可兼得，根据场景优先级做选择
- **Overlay 最大损耗来自 iptables（~20%）**，其次是 VXLAN 封装（~5%）
- **MTU 是虚拟网络中最常见的问题**，VXLAN 减 50，IPIP 减 20，务必配置正确
- **选型决策核心**：虚拟机用 NAT/桥接/仅主机，Docker 用 Bridge/Overlay/Macvlan，K8s 用 Flannel/Calico/Cilium
- **没有"最好"的方案，只有"最适合当前场景"的方案**
