# 第四章：软件定义网络 — SDN

> 笔记类型：概念笔记
> 目标读者：已理解 VXLAN Overlay 网络原理
> 核心问题：传统网络设备"软硬一体"，谁来把网络智能从硬件中解放出来？

## 开篇

从 VLAN 到 VXLAN，我们一直在解决"如何构建更大、更灵活的虚拟网络"的问题。但有一个更深层次的矛盾始终存在：**网络设备的控制逻辑（路由协议、转发策略）和转发硬件（ASIC 芯片）被紧紧捆绑在同一台设备里**。这意味着每台交换机都是一个独立的"决策者"，网络管理员需要逐台配置，全局策略难以一致执行。

SDN（Software-Defined Networking，软件定义网络）彻底改变了这个局面。它的核心思想只有三个词：**转控分离 + 集中控制 + 可编程**。本章将带你理解 SDN 的三层架构、OpenFlow 协议如何工作，以及 Google 如何用 SDN 将网络利用率从 30% 提升到 95%。

---

## 1. SDN 的核心思想：转控分离

### 1.1 传统网络的"一体机"模式

先看一个传统交换机的内部结构：

```
传统交换机
┌─────────────────────────────────────┐
│  控制平面（Control Plane）            │
│  ├─ 运行路由协议（OSPF/BGP）          │
│  ├─ 生成 MAC 地址表                   │
│  ├─ 处理 ARP/STP 等协议报文            │
│  └─ 运行管理界面（CLI/SNMP）           │
├─────────────────────────────────────┤
│  数据平面（Data Plane / Forwarding）  │
│  ├─ ASIC 芯片：线速转发                │
│  ├─ TCAM：流表匹配查找                 │
│  └─ 队列调度：QoS                      │
└─────────────────────────────────────┘
```

**问题**：控制平面和数据平面在同一台设备上。每台交换机独立决策，全局策略（比如"所有流量走路径 A"）需要在每台设备上逐条配置。网络规模一大，配置复杂度和一致性风险急剧上升。

### 1.2 SDN 的"分离"模式

```
SDN 架构
┌──────────────────────────────────────┐
│  控制层（集中式 SDN 控制器）            │
│  ├─ 全局网络视图                       │
│  ├─ 统一策略下发                       │
│  └─ 无需逐台配置                       │
├────────────── 南向接口（OpenFlow）─────┤
│  数据层（转发设备）                     │
│  ├─ 仅执行流表规则                     │
│  ├─ 不再运行路由协议                   │
│  └─ 变成"可编程的转发管道"              │
└──────────────────────────────────────┘
```

> **想象一下**：传统网络像一支没有指挥的交响乐团——每个乐手自己决定什么时候演奏什么音符。SDN 像有指挥——指挥（控制器）掌握总谱（全局视图），乐手（交换机）只负责按指令演奏（执行流表）。

### 1.3 三个核心特征

SDN 的定义由三个相互关联的特征构成：

1. **转控分离（Forwarding-Control Separation）**：转发设备不再运行控制协议，只负责按规则转发。控制逻辑集中到控制器。
2. **集中控制（Centralized Control）**：控制器拥有全局网络拓扑视图，能做出全网最优的转发决策，而非逐台设备的局部决策。
3. **可编程（Programmability）**：网络行为通过软件定义，不再受限于硬件设备的功能集。你可以用编程的方式表达："所有视频流量走带宽大的链路"。

## 2. SDN 三层架构

SDN 架构在逻辑上分为三个层次，从下到上分别是：

```
┌─────────────────────────────────────────────────┐
│  应用层 (Application Layer)                      │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐            │
│  │ 流量工程 │ │ 安全策略 │ │ 负载均衡 │   ...     │
│  │  App    │ │  App    │ │  App    │            │
│  └────┬────┘ └────┬────┘ └────┬────┘            │
│       │           │           │                  │
├───────┴───────────┴───────────┴──────────────────┤
│  北向接口 (Northbound Interface)                  │
│  REST API / JSON / YANG                          │
├──────────────────────────────────────────────────┤
│  控制层 (Control Layer)                          │
│  ┌──────────────────────────────────────────────┐│
│  │         SDN 控制器 (Controller)               ││
│  │   ├─ 网络拓扑管理                             ││
│  │   ├─ 路径计算                                 ││
│  │   ├─ 策略引擎                                 ││
│  │   └─ 设备抽象层                               ││
│  └──────────────────────────────────────────────┘│
├──────────────────────────────────────────────────┤
│  南向接口 (Southbound Interface)                  │
│  OpenFlow / NETCONF / OVSDB                      │
├──────────────────────────────────────────────────┤
│  基础设施层 (Infrastructure Layer)                │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐            │
│  │ 交换机 1 │ │ 交换机 2 │ │ 交换机 3 │   ...     │
│  │(转发设备)│ │(转发设备)│ │(转发设备)│            │
│  └─────────┘ └─────────┘ └─────────┘            │
└─────────────────────────────────────────────────┘
```

### 2.1 基础设施层（数据平面）

这是转发设备层——物理交换机、虚拟交换机（如 Open vSwitch）、甚至是软件转发实例。

**关键特征**：这些设备不再运行任何控制协议。它们内部只保存一张**流表（Flow Table）**，包含若干条匹配/动作规则。数据包到达后，按流表规则匹配并执行对应动作（转发、丢弃、修改字段等）。

> **技术上**：数据层设备变成了"可编程的转发管道"。它的"智能"不在本地，而在控制器中。

### 2.2 控制层（SDN 控制器）

这是 SDN 的"大脑"。控制器通过南向接口与所有转发设备通信，维护全网拓扑的实时视图。

**控制器的典型功能**：

| 功能 | 说明 | 类比 |
|------|------|------|
| 拓扑发现 | 通过 LLDP 等协议发现所有设备和链路 | 画出地铁线路图 |
| 路径计算 | 根据拓扑和策略计算最优路径 | 导航规划路线 |
| 流表下发 | 将计算结果转化为流表规则推送到设备 | 给驾驶员发指令 |
| 事件处理 | 响应链路故障、设备加入等事件 | 应对突发情况 |

**知名 SDN 控制器**：OpenDaylight（Linux 基金会）、ONOS（运营商级）、Ryu（Python 轻量级）、Floodlight（Java 教育级）。

### 2.3 应用层

这是网络业务逻辑所在层。网络应用通过北向接口调用控制器的能力，实现具体的网络功能：

- **流量工程应用**：优化链路利用率
- **安全策略应用**：动态下发 ACL/防火墙规则
- **负载均衡应用**：根据实时负载分配流量
- **网络监控应用**：收集设备状态和流量统计

### 2.4 南向 vs 北向接口

| 维度 | 南向接口 | 北向接口 |
|------|---------|---------|
| **位置** | 控制层 ↔ 基础设施层之间 | 控制层 ↔ 应用层之间 |
| **协议** | OpenFlow、NETCONF、OVSDB | REST API、JSON、YANG |
| **职责** | 下发流表、收集设备状态 | 暴露网络能力给应用 |
| **对比** | 像操作系统驱动 → 控制硬件 | 像系统 API → 供 app 调用 |

## 3. OpenFlow 协议与流表

### 3.1 为什么需要 OpenFlow？

在 SDN 概念提出的早期（2008 年，斯坦福大学 Nick McKeown 团队），最大的难题是：**控制器和交换机之间用什么语言沟通？**

OpenFlow 就是答案——它是第一个标准化的南向接口协议，定义了控制器如何远程写入交换机的转发规则。

### 3.2 流表结构

OpenFlow 的核心是**流表（Flow Table）**。每条流表项由三部分组成：

```
┌─────────────────────────────────────────────────────┐
│                 流表项 (Flow Entry)                  │
├────────────┬───────────────┬────────────────────────┤
│   匹配域    │    计数器      │       动作指令          │
│ (Match)    │  (Counters)   │    (Instructions)       │
├────────────┼───────────────┼────────────────────────┤
│ 源 MAC     │ 收到包数       │ OUTPUT: 转发到端口       │
│ 目的 MAC   │ 收到字节数     │ DROP: 丢弃              │
│ 源 IP      │ 持续时间       │ SET_FIELD: 修改字段      │
│ 目的 IP    │               │ GOTO_TABLE: 跳转下一表   │
| TCP 端口   |               | GROUP: 组处理            |
│ ...        │               │ ...                     │
└────────────┴───────────────┴────────────────────────┘
```

**匹配域的多维度**：OpenFlow 支持从 L1（物理端口）到 L4（TCP/UDP 端口）的多层匹配。一条流表规则可以精确匹配"从 10.0.1.2 到 10.0.2.2 的 TCP 80 端口流量"。

**通配匹配与精确匹配**：匹配域可以指定精确值，也可以使用通配符。通配匹配常用于"匹配某个子网的所有流量"，精确匹配用于"匹配特定五元组的流量"。

### 3.3 流表匹配过程

当数据包到达 OpenFlow 交换机时：

```
数据包到达
    │
    ▼
┌───────────────┐    匹配?     ┌───────────────┐
│  流表 0        │───────YES───▶│  执行对应动作    │
│ (Table 0)     │              │  (转发/修改/丢弃)│
│  Match: ...   │              └───────────────┘
│  Action: ...  │    NO               │
└───────┬───────┘                    │
        │ GOTO_TABLE                  │
        ▼                            │
┌───────────────┐                   │
│  流表 1        │                   │
│ (Table 1)     │                   │
└───────┬───────┘                   │
        │                           │
        ▼ (所有表都不匹配)            │
┌───────────────────┐               │
│  Packet-In 消息    │───────────────│
│  发给控制器决策    │               │
└───────────────────┘               │
        │                           │
        ▼                           │
  控制器决策后：                     │
  - 下发新流表规则                    │
  - 或直接返回处理指令                │
```

> **关键机制**：第一个数据包触发"不解"时，交换机将其封装为 Packet-In 消息发给控制器。控制器根据全局策略决策后，返回 Packet-Out 消息，并可选地下发对应流表项。后续同流的数据包直接在交换机内转发，不再经过控制器。这称为**反应式转发**。

### 3.4 OpenFlow 版本演进

| 版本 | 主要增强 | 发布时间 |
|------|---------|---------|
| 1.0 | 单流表、12 个匹配域 | 2009 |
| 1.3 | 多流表流水线、IPv6、MPLS 支持 | 2012 |
| 1.5 | Egress 表、包类型感知 | 2014 |

> **现实情况**：虽然 OpenFlow 是 SDN 的"元老"协议，但在大规模生产环境中，纯 OpenFlow 方案并未成为主流。业界转向了混合方案：控制面用 SDN 理念（集中管理、自动编排），但转发面保留传统协议（BGP、OSPF）的灵活性。例如 **OpenFlow + BGP** 的混合模式在今天的数据中心很常见。

## 4. SDN 的实战价值：Google B4 案例

### 4.1 背景：Google 的"数据中心互联"难题

Google 在全球有数十个数据中心，它们之间需要高速、可靠且高效的连接。传统 WAN（广域网）的做法是：

- 使用 MPLS 或其他隧道技术
- 链路利用率通常只有 **30-40%**
- 预留大量带宽应对峰值，平时大量闲置
- 链路故障时，收敛速度慢（秒级到分钟级）

Google 面临的核心问题是：**如何在保证 SLA 的前提下，把链路利用率提上去？**

### 4.2 核心设计：集中式流量工程

Google B4 网络（2010 年启动，2012 年完成部署）的核心设计是利用 SDN 实现**集中式流量工程**：

```
Google B4 架构（简化）
┌──────────────────────────────────────────────┐
│  Central TE Server (集中式流量工程服务器)       │
│  ├─ 实时收集全网链路利用率                     │
│  ├─ 全局计算最优路径分配                       │
│  └─ 区分流量优先级（交互 > 数据 > 批量）        │
├──────────────────────────────────────────────┤
│  每个数据中心内的 SDN 网关                     │
│  ├─ 接收 TE Server 的流表规则                  │
│  ├─ 执行基于 OpenFlow 的转发                   │
│  └─ 上报链路状态                              │
└──────────────────────────────────────────────┘
```

**关键创新**：Google B4 的 SDN 控制平面只有大约 100 步（代码量很少），但它包含了复杂的**带宽分配算法**：

1. 应用不同的流量等级赋予不同权重（交互式流量 > 弹性数据 > 后台批量）
2. TE Server 实时计算最优带宽分配，最大化整体链路利用率
3. 链路故障时快速重路由（毫秒级收敛）

### 4.3 成果：从 30% 到 95%

| 指标 | 传统 WAN | Google B4 |
|------|---------|-----------|
| 链路利用率 | 30-40% | **95%** |
| 故障收敛 | 秒级 ~ 分钟级 | **毫秒级** |
| 流量管理 | 静态预留 | **动态调度** |
| 策略一致性 | 逐设备手动配置 | **集中管理** |
| 带宽浪费 | 大量闲置带宽 | **极致利用** |

> 95% 的链路利用率意味着什么？传统网络中链路利用率超过 70% 就要担心拥塞，而 Google 通过 SDN 的精细化流量调度，把链路压到了接近满载，同时保持服务质量。这相当于把现有基础设施的承载能力翻了两倍多——**多出来的每一分带宽都是 SDN 带来的"免费"收益**。

### 4.4 启示

Google B4 的实践表明：

- **SDN 的价值不在技术本身，而在它带来的业务收益**。Google 不是为"用 SDN"而用 SDN，是为了解决链路利用率低这个实际的成本问题。
- **控制面是核心**。B4 的真正竞争力不是 OpenFlow（那只是工具），而是它的 **TE 算法**——一种全局优化数学方法。
- **SDN 不一定需要纯 OpenFlow**。B4 的实际部署是混合模式：交换机仍然运行传统路由协议建立基础连通性，SDN 控制层负责覆盖优化。

## 5. SDN 与 VXLAN 的关系

VXLAN 和 SDN 经常被一起提及，但它们的角色完全不同：

| 维度 | VXLAN | SDN |
|------|-------|-----|
| **解决的问题** | 二层网络扩展（大规模虚拟网络） | 网络架构重组（转控分离） |
| **核心机制** | MAC-in-UDP 封装隧道 | 集中控制器 + 流表 |
| **关注层面** | 数据平面封装技术 | 控制平面架构设计 |
| **关系** | 隧道技术（怎么传） | 管理技术（谁决策） |

**两者可以独立存在**：
- 没有 VXLAN，SDN 也可以工作（直接用物理交换机做 OpenFlow 转发）
- 没有 SDN，VXLAN 也可以工作（通过 EVPN 或手动配置 VTEP）

**但两者配合效果最佳**：
- SDN 控制器可以作为 VXLAN 网络的"大脑"——自动管理 VTEP 配置、下发 VNI 映射、优化隧道路径
- VXLAN 为 SDN 提供了理想的 Overlay 数据面——封装后的流量完全受控制器的流表调度

> **一句话总结**：VXLAN 是路（隧道封装），SDN 是交警（集中调度）。有路没交警，车流无序；有交警没路，无路可管。

## 6. SDN 的现状与演进

### 6.1 为什么纯 OpenFlow 没有统治世界？

纯 OpenFlow（所有转发由控制器统一管理）在理想中很完美，但在实际部署中遇到挑战：

1. **可靠性问题**：控制器和交换机之间的连接一旦中断，交换机如何处理未知流量？
2. **性能瓶颈**：每个流的第一个包都要经过控制器，大规模场景下控制器成为瓶颈
3. **协议演进慢**：OpenFlow 标准化速度跟不上实际需求
4. **设备厂商抵触**：纯 OpenFlow 把交换机"降级"为通用硬件，削弱了厂商的技术壁垒

### 6.2 今天的 SDN：广义理解

今天的 SDN 已经从一个"狭义协议"演变为"广义架构理念"：

- **控制面 SDN 化**：网络设备通过 NETCONF/YANG 等协议接受集中管理，但转发面保留传统协议
- **云 SDN**：AWS VPC、阿里云专有网络等云网络的底层都基于 SDN 理念，但具体实现是各家的黑盒
- **意图网络（Intent-Based Networking）**：思科等厂商推动的下一代理念——"管理员说'要什么'，网络自动实现"

### 6.3 与后续章节的联系

本章的 SDN 思想将贯穿后续章节：

- **网络命名空间**（第五章）：Linux 内核的"软件交换机"可以看作 SDN 数据面的最小单元
- **Docker Overlay 网络**（第八章）：Docker Swarm 内置的 SDN 控制面管理 VXLAN 隧道
- **Kubernetes CNI 插件**（第九章）：Calico、Cilium 等插件本身就是 SDN 的数据面实现

## 章节总结

- **SDN 的核心是转控分离 + 集中控制 + 可编程**。将转发设备的控制逻辑抽离到集中控制器，使网络从"分布式的独立决策"变为"集中式的统一调度"。
- **三层架构**从下到上依次是：基础设施层（仅执行转发）、控制层（SDN 控制器，全局视图）、应用层（网络业务逻辑），层间通过南向接口（OpenFlow）和北向接口（REST API）通信。
- **OpenFlow 流表**是控制器的"转发指令集"——每个流表项包含匹配域、计数器和动作指令。数据包按多表流水线匹配，首包不解时触发 Packet-In 由控制器决策。
- **Google B4** 是 SDN 最著名的实战案例：通过集中式流量工程将广域网链路利用率从 30-40% 提升至 95%，证明 SDN 的商业价值远超技术噱头。
- **VXLAN 和 SDN 的关系**是"传输管道 vs 调度大脑"——两者相互独立又完美互补。VXLAN 提供灵活的数据面，SDN 提供智能的控制面。

SDN 的核心理念是"分离"，而 Linux 内核中有一个早已存在的隔离机制，它同样是虚拟网络的基石——**网络命名空间（Network Namespace）**。下一章我们将回到 Linux 内核层面，学习如何用 `ip netns` 和 `veth pair` 亲手搭建虚拟网络。
