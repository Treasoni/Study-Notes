## 第 1 章 先看清楚你要搭的是什么（名词扫盲 + 你的现实边界）

> [!summary] 一句话看懂
> 家庭影院 = **一个中枢（MoviePilot）+ 三个外援（下载器、站点、媒体服务器）**；但 MoviePilot 的「搜片 → 订阅 → 下载」必须拿 **PT 站点账号**去换，没账号就只剩「整理 + 刮削」一半能用。所以这篇给你两条路：**有账号走 A 路**，**没账号走 C 路**。

这一章不教你敲任何命令，只解决两件事：**先认识零件**（它们各叫什么、怎么串起来），以及**先划清底线**（没有 PT 账号，你到底能走到哪一步）。把这两件事想明白，后面就不会出现「装到一半才发现缺东西」的返工。

### 1.1 一句话看懂这套系统：一个中枢 + 三个外援

把整套「家庭影院」想成一家餐厅：

- **中枢 = MoviePilot（前台经理）**：它本身不做重活，只负责「下单、派活、催进度」——你说想追某部剧，它去找资源、发指令、收结果、整理入库。
- **外援 1 = 下载器（后厨）**：真正把文件搬到你硬盘上的（如 qBittorrent、Transmission）。MoviePilot 自己不下载，它调下载器干活。
- **外援 2 = 站点（供货商）**：告诉 MoviePilot「哪儿有货」。这里的「站点」多指 **PT 站点**，它是「进货渠道」。
- **外援 3 = 媒体服务器（门店）**：把整理好的片子摆上架、配好封面简介、供你点播（如 Jellyfin、Emby、飞牛影视）。MoviePilot 还会通过它的接口查库存，避免重复下同一部片。

所以一句话：**MoviePilot 只是「一环」，不是全部**。官方也把它定位成媒体库自动化管理的一环——需要通过下载器下载、通过媒体服务器展示[^c1-ready-1]。

> [!tip] 大白话
> 把 MoviePilot 想成**餐厅经理**：他自己不炒菜（不下载）、不种菜（不生产资源）、也不端盘子（不播放），只负责**安排谁来干、按什么顺序干**。少任何一个外援，餐厅都开不起来——这也正是「有没有 PT 账号」这么要命的原因（见 1.3）。

### 1.2 名词扫盲表（先扫一遍，后面就不会断片）

术语密集，先集中扫盲。**看一遍即可，不必背**，遇到时再回来查：

| 名词 | 大白话 |
| --- | --- |
| **nastool** | 这套工具的老名字，同一作者的作品。**原版已停止维护**（第 2 章细说），现在活跃的是它重做后的 MoviePilot。 |
| **MoviePilot** | 当前主线工具，一个「家庭影院自动化中枢」：把搜片、下载、整理、刮削、播放串成一条流水线。 |
| **PT 站点** | 一种**邀请制 / 考核制**的下载站点，要账号才能访问。可以理解成「会员制供货商」。 |
| **站点索引** | MoviePilot 拿站点去「查货」的动作与能力：在站点里搜资源、拉取资源清单。 |
| **认证（用户认证）** | 拿 PT 站点的账号，向 MoviePilot 证明「我是合格会员」。**没有认证，MoviePilot 就用不了站点。** |
| **索引器** | 泛指「查资源的入口」。在这里主要就是 PT 站点；MoviePilot 靠它找到片源。 |
| **下载器** | 真正执行下载的软件（qBittorrent / Transmission）。 |
| **媒体服务器** | 把片子整理成「海报墙」供播放和管理的软件（Jellyfin / Emby / Plex / 飞牛影视）。 |
| **刮削** | 给下载好的片子「配封面、简介、演员表」等元数据，让它在媒体服务器里显示得漂漂亮亮。 |
| **硬链接** | 让「同一份文件」在下载目录和媒体库各显示一份，**但硬盘上只存一份**，不占双倍空间。这是整理环节的关键机制（第 3、8 章细说）。 |
| **STRM** | 一种「指针文件」：本身不是视频，只记了一个播放地址，播放时再去取。C 路网盘方案常用。 |

### 1.3 你的现实边界：没有 PT 账号，只能走一半

这是全篇最该先知道的一句。官方把 MoviePilot 的功能**一分为二**[^c1-ready-2]：

| 它管什么 | 官方原文 | 说人话 |
| --- | --- | --- |
| 功能二分 | 「MoviePilot包括两大部分功能：文件整理刮削、资源订阅下载，其中资源订阅下载功能需要有可用的PT站点，同时这些站点中需要有一个可用于认证」 | 一半是「整理刮削」，一半是「订阅下载」；**后者必须有可用的 PT 站点，且其中要有一个能用来认证**。 |

也就是说，「搜片、订阅、自动下载」这条线，绕不开 PT 站点认证。官方在讲认证时把话说得很直白：你需要有认证站点范围内的账号，才能使用**资源搜索、订阅及下载**功能[^c1-basic-1]。

**一句话概括**：MoviePilot = 「整理刮削」+「资源订阅下载」，后者绑定 PT 站点。

> [!warning] 这是推断，不是官方原话
> 由上面的「功能二分」可以推出：**没有 PT 账号时，「文件整理刮削」那一半仍然可用，只有「资源订阅下载」不可用。**
> 请注意——这是**据官方功能二分做出的推断**，官方并未用这句话直接表述；它是把主路 A 和备选路 C 接起来的关键（第 6 章展开）。

> [!tip] 大白话
> 把 MoviePilot 想成一台**双卡双待手机**：一张卡（整理刮削）不用验证就能用；另一张卡（订阅下载）得插会员卡（PT 认证）才能打电话。你手上没会员卡，那就把能用的那张先用起来。

### 1.4 两条路的抉择地图

| 你的情况 | 走哪条路 | 你能得到什么 | 落到哪章 |
| --- | --- | --- | --- |
| 有 PT 站点账号 | **主路 A**（MoviePilot V3 全链路） | 搜片 → 订阅 → 自动下载 → 整理 → 刮削 → 播放，全自动 | 第 2–5、7–9 章 |
| 没有 PT 站点账号 | **备选路 C**（不依赖 PT 的网盘流媒体） | 片子从网盘等渠道来，播放链路立刻能跑通 | 第 6 章 + 库内既有笔记 |
| 想「两条一起要」 | **A + C 叠加** | C 解决「片子从哪来」，A 的整理 / 刮削管本地已下载的片（**推断**，见上节警告） | 第 6 章 6.3 节 |

> 两条路不是二选一——C 路可以先让你「有得看」；等哪天拿到 PT 账号，再把 A 路补上。

> [!summary] 本章小结
> - 家庭影院 = 一个中枢（MoviePilot）+ 三个外援（下载器、站点、媒体服务器）；MoviePilot 本身只是「一环」。
> - 术语先扫盲：nastool 是旧名，MoviePilot 是现在的主线；PT 站点是「会员制供货商」，认证是进门的钥匙。
> - MoviePilot 功能一分为二：整理刮削 + 资源订阅下载；后者必须有可用的 PT 站点并能认证。
> - 「没 PT 也能做整理刮削」是据官方功能二分得出的**推断**，不是官方原话。
> - 有账号走 A 路，没账号走 C 路，两者还能叠加。

**下一章预告**：既然主线是 MoviePilot，为什么不再讲老的 nastool？下一章用最短的篇幅交代「原版已成历史」，并提前拆掉一个照抄就会卡死的大坑——网上大多数旧教程的 Compose 是 V2 口径。

## 第 2 章 为什么主线是 MoviePilot V3（原版 nastool 已成历史）

> [!summary] 一句话看懂
> 原版 **nastool 仓库已于 2023 年归档、只读**，作者把它重做成了 **MoviePilot**；现在的主线是 **V3**。而且 V3 改了初始化方式——**首次进网页自己建管理员**，网上旧教程照抄 V2 写法，会在「找初始密码」这步卡死。

这一章解决两个问题：**为什么不再讲 nastool 原版**（最短交代，不展开沿革），以及**提前拆掉一个照抄陷阱**（V2 口径的 Compose 会让你在 V3 上卡在初始化）。看完这一章，你在第 4 章照做时就不会被旧教程带偏。

### 2.1 原版 nastool 的结局：归档、只读、旧地址 404

三句话说完：

- 原版仓库 `NAStool/nas-tools` 已被作者归档，仓库页横幅明确写着：归档于 2023-05-16，现为只读[^c2-arch]。
- 它的旧地址 `jxxghp/nas-tools` 现在打开是 404——页面标题就是 GitHub 的「`Page not found`」（页面未找到）[^c2-404]。
- 所以任何「照 nastool 装」的老教程，本质是在教一个**已停更两年多**的软件——我们不跟。

这里不展开它的历史沿革。你只需要记住：**nastool 原版是上一代——看它了解背景可以，照它部署不行。**

### 2.2 同作者的换代：MoviePilot 是什么定位

MoviePilot 是同一作者基于 nastool 部分代码**重新设计**的作品，官方自述的定位是「聚焦自动化核心需求，减少问题、更易于扩展和维护」[^c2-readme-1]。

| 它的定位 | 官方原文 | 说人话 |
| --- | --- | --- |
| 自述定位 | 「基于 NAStool 部分代码重新设计，聚焦自动化核心需求，减少问题同时更易于扩展和维护。」 | 不是从零新写，而是把 nastool 拆解重做：砍掉杂项，只留自动化主线。 |

**一句话概括**：MoviePilot 是 nastool 的「重制版」，主线职责就是影视自动化。

它的 Docker 镜像也和旧版分开命名——V3 用独立镜像 `jxxghp/moviepilot-v3`，V2 和旧版镜像保持原名[^c2-readme-2]。**标准 V3 是普通用户的默认选择**[^c2-v2v3]。

### 2.3 V2 → V3 的分水岭：初始化方式变了

这是本章最实用的一节。V2 和 V3 最大的区别不在功能，而在**「管理员账号从哪来」**：

- **V2 的老做法**：在环境变量里预先写好超级管理员用户名 / 密码（`SUPERUSER` / `SUPERUSER_PASSWORD`），甚至预先填好 `API_TOKEN`。
- **V3 的新做法**：**什么都不预置**。首次打开网页时，系统进入初始化页面，你现场填管理员用户名、密码（填两次）并生成 API Key，保存后才跳到登录页[^c2-install-1]。

> [!warning] V3 模板里不需要这些变量
> V3 全新安装时，Docker 模板中**不需要**填写 `SUPERUSER`、`SUPERUSER_PASSWORD`、`API_TOKEN`[^c2-install-2]。这三个是 V2 口径，写到 V3 里没用。

### 2.4 照抄陷阱对照：「V2 式」写法 vs V3 正确写法

网上大量视频 / 博客的 Compose 仍是 **V2 口径**。照抄到 V3 上，最常见的结果是「容器起来了，但不知道密码是什么」——因为在 V3 里，你写进去的 `SUPERUSER_PASSWORD` 根本不会被当作初始密码。

| 你看到的旧教程（V2 口径） | V3 应该怎么做 |
| --- | --- |
| 环境变量写 `SUPERUSER=admin` / `SUPERUSER_PASSWORD=你的初始登录密码` | **删掉，别写**；改为首次访问网页时手动创建管理员 |
| 环境变量写 `API_TOKEN=建议大于16位的复杂字符串` | **删掉**；API Key 在首次初始化时自动生成并展示 |
| 「第一次启动去日志里搜『超级管理员』找密码」 | V3 **没有这一步**：密码是你自己首次访问时设的 |

> [!note] 为什么 V2 要预置、V3 不用
> V2 把初始化摊在「启动阶段」——启动前就得把账号密码灌进去；V3 把它挪到「首次访问」——容器先干干净净跑起来，你进网页再设。**这处改动，正是「照抄旧教程会卡死」的根源。**

> [!tip] 大白话
> 把初始化想成**新手机开箱**：V2 相当于「出厂就把你的名字和密码刻在机身上」；V3 相当于「出厂是空白的，开机第一屏让你自己设」。你要是拿着 V2 的「刻名字清单」去挑 V3 的手机，当然找不到该填哪儿。

**下一章预告**：知道主线是 V3 之后，动手前还有三件事必须先想清楚——网络通不通、目录怎么规划（直接决定硬链接成不成立）、配套软件装哪些。下一章就讲这三件事。

## 第 3 章 动手前的准备（网络、目录、配套软件）

> [!summary] 一句话看懂
> 开装前必须先想清三件事：**网络**要能顺畅访问 TMDB 与 GitHub；**目录**要让「下载目录」和「媒体库目录」待在**同一个根目录**下（否则硬链接不成立）；**配套软件**（下载器、媒体服务器、CookieCloud 插件）要装齐、版本达标。

这一章解决「动手之前必须先摆平的三件事」。任意一件没想清楚，后面都会返工：网络不通 → 元数据匹配、升级、装插件全失败；目录规划错 → 硬链接报错、白占硬盘；配套软件没装 → MoviePilot 起来了也「孤掌难鸣」。

### 3.1 网络前提：TMDB 与 GitHub 要能顺畅访问

MoviePilot 靠两件事「吃饭」：调 **TheMovieDb（TMDB）** 的 API 来读取和匹配媒体元数据；访问 **GitHub** 来执行程序升级、安装插件。官方把「有顺畅连接上述网址的网络环境」列为「能流畅使用本软件的前提」[^c3-ready-1]。

| 它要连谁 | 用来干嘛 | 连不上会怎样 |
| --- | --- | --- |
| TheMovieDb（TMDB）Api | 读取、匹配媒体元数据 | 刮削匹配不到，海报简介出不来 |
| GitHub | 程序升级、安装插件 | 升级失败、插件装不上 |

> [!tip] 大白话
> 把 MoviePilot 想成**只认两个供货商的采购员**：一个供「资料卡」（TMDB 的海报、简介），一个供「新工具」（GitHub 的插件、升级包）。渠道一断，采购员就两手空空——软件能开，但啥也干不成。网络怎么配（走代理、换 TMDB API 地址等）官方另有专章；本章你只要先确认一件事：**连得上**。

### 3.2 目录规划（本章的实体落点）：下载目录与媒体库必须同根

这是本章最该停下来想的一节。先给你**一棵可以直接照着建的目录树**：

```text
/media/                              ← 唯一根目录（整个映射进容器）
├── downloads/                       ← 下载器把片子下到这里
│   └── ...（qBittorrent / Transmission 的下载文件）
└── media/                           ← MoviePilot 整理后放这里（媒体库）
    ├── 电影/
    └── 剧集/
```

关键**只有一句**：如果你打算用**硬链接**来整理文件，那么「文件下载目录」和「整理后的媒体库目录」**只能映射一个根目录，不能分开映射**，否则会导致跨盘无法硬链接[^c3-install-1]。

> [!question] 为什么非要「同一个根目录」？
> 硬链接的本质是「同一个文件、两个名字」。**同一个文件，必须待在同一个文件系统里**——一旦跨盘（不同磁盘 / 同盘不同分区 / 被拆成两个映射路径），操作系统就造不出这个「第二个名字」，只能退化成「复制一份」，白白多占一份空间。
>
> 所以正确做法：先建一个根目录（如 `/media`），把下载目录和媒体库都放它下面，**把整个根目录一次性映射进容器**。

官方点明了三种「一定跨盘、一定失败」的情形[^c3-install-2]：

| 情形 | 为什么不行 |
| --- | --- |
| 下载目录和媒体库目录分别在两个不同磁盘 | 属于不同文件系统 |
| 同盘，但在两个不同分区 / 存储空间 / 存储池 | 仍是不同文件系统 |
| 同盘同分区，但被当作两个目录路径分别映射进容器 | 对容器而言已成两个挂载点，等同跨盘 |

> [!tip] 大白话
> 把硬链接想成**「给同一本书贴第二个书签」**：书得还在同一个书架（同一个文件系统）上，你才贴得上第二个书签；书一旦被挪到另一个书架，你就只能「再买一本」（复制）——费钱又费力。

### 3.3 配套软件清单与最低版本

MoviePilot 只是「一环」：它需要下载器来真正下载、需要媒体服务器来管理和展示[^c3-ready-2]。开装前先把这些装好，并确认版本达标[^c3-ready-3]：

| 配套软件 | 作用 | 版本要求 |
| --- | --- | --- |
| Qbittorrent（下载器） | 真正执行下载 | **>= 4.3.9** |
| Transmission（下载器） | 真正执行下载（与 QB 二选一） | **>= 3.0** |
| Emby（媒体服务器） | 展示、管理媒体库 | 建议 **>= 4.8.0.45** |
| Jellyfin（媒体服务器） | 展示、管理媒体库（与 Emby 二选一） | 推荐 **latest** 分支 |
| Plex（媒体服务器） | 展示、管理媒体库（三选一） | 无特定版本要求 |
| CookieCloud 浏览器插件 | 同步站点 Cookie、批量加站点 | 必装（服务端 MoviePilot 已内置） |

> [!warning] CookieCloud 浏览器插件必须装
> CookieCloud 服务端 MoviePilot 已经内置，**但浏览器插件是必装的**——它是把站点 Cookie 同步进 MoviePilot 的通道[^c3-ready-4]。
>
> 另外记住「二选一」：下载器在 QB / Transmission 里挑一个，媒体服务器在 Emby / Jellyfin / Plex 里挑一个，不必全装。

### 3.4 进阶可选：用 portainer 简化容器配置编辑（新手可跳过）

> [!tip] 新手可跳过
> 如果你习惯直接用命令行编辑 `docker-compose.yml`，这一节完全可以跳过。

官方建议：如果你计划用 Docker 部署，**先确认你的环境能否方便地编辑容器配置**，否则建议装 **portainer** 来简化容器操作[^c3-ready-5]。portainer 是一个带网页界面的 Docker 管理工具，改容器配置点点鼠标就行。

```bash
## 安装 portainer（装完访问 http://宿主机IP:9000）
docker run -d --restart=always --name="portainer" \
  -p 9000:9000 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  6053537/portainer-ce
```

> [!note] 这条命令在做什么
> `-p 9000:9000` 把网页界面开在宿主机的 9000 端口；`-v /var/run/docker.sock:/var/run/docker.sock` 把 Docker 的「操作手柄」交给 portainer，它才有权限管理你的容器。

### 3.5 fnOS 本地注意：3000 端口的社区说法（社区经验，待实机验证）

MoviePilot 的 Web 界面**默认走 3000 端口**（安装指引里写明默认用 3000 作 Web 服务端口，可按需调整）[^c3-install-3]。所以「3000 会不会被飞牛自己占用」值得你心里先有个数。

> [!warning] 社区经验，待实机验证——不要当结论
> 有社区帖称：飞牛应用中心的浏览器会**占用 3000 端口**，且改 MoviePilot 端口可能导致安装失败。
>
> 这条说法**一手未证实**（来源原文未能取得）。本节只做**提醒**，不写成结论。到第 4 章部署时，若正好撞上 3000 端口被占，再按实际报错处理；没撞上就无需理会。

> [!summary] 本章小结
> - 网络是前提：TMDB 供元数据、GitHub 供升级与插件，必须顺畅可达。
> - 目录是易错点：下载目录与媒体库必须在**同一个根目录**下、整体映射进容器，硬链接才成立。
> - 配套软件要装齐：下载器（QB >= 4.3.9 / TR >= 3.0）、媒体服务器（Emby / Jellyfin / Plex 三选一）、CookieCloud 浏览器插件（必装）。
> - portainer 属可选增强，新手可跳过。
> - 「fnOS 3000 端口被占用」是**社区经验，待实机验证**，不作结论。

**下一章预告**：三件事摆平之后，就可以真正动手了。下一章把 MoviePilot V3 的容器跑起来、把管理员建出来、用浏览器打开界面——这是全篇唯一必须「照着敲」的核心章。

## 第 4 章 动手实践①——部署 MoviePilot V3 并完成首次初始化

> [!summary] 一句话看懂
> 把 MoviePilot V3 的容器跑起来，用浏览器打开 `http://宿主机IP:3000`，在**首次访问的初始化页**现场创建管理员、生成 API Key——V3 不在启动阶段预置任何账号密码。

这一章解决「真正把容器跑起来、把管理员建出来、能用浏览器打开界面」。这是全篇唯一必须「照着敲」的核心章：前面第 1–3 章是认路和准备，从这一章开始动手。概念先讲清楚，命令集中收进两个「动手实践」小节。

### 4.1 先看懂部署流程（概念先行，不敲命令）

一次成功的 V3 部署，顺序是这样的：

```text
① 准备好目录（第 3 章已做：/media 下放 downloads + media）
        ↓
② 写一份 docker-compose.yml（只需改 3 个宿主机目录）
        ↓
③ docker compose up -d 启动容器
        ↓
④ 浏览器打开 http://宿主机IP:3000
        ↓
⑤ 首次访问进「初始化页」：现场建管理员 + 生成 API Key
        ↓
⑥ 保存 → 跳到登录页 → 用刚设的账号密码登录
```

和 V2 最大的不同就落在第 ⑤ 步——**V3 把「建管理员」从启动阶段挪到了首次访问网页时**（第 2 章已提前拆过这个坑）。

### 4.2 「动手实践」：Compose 骨架（新手可跳过）

> [!tip] 新手可跳过
> 如果你不熟 YAML / Compose，只要记住「有一份配置文件，先改 3 个目录」即可，其余交给熟悉的部署方式。下面骨架可直接复制。

**「小白版」只需要先改这 3 个宿主机目录**[^c4-14]：

| 要改的宿主机目录 | 它是什么 | 能不能删 |
| --- | --- | --- |
| `/media` | 媒体库和下载目录的**共同根目录**（第 3 章的目录树就建在它下面） | — |
| `/moviepilot-v3/config` | 保存配置、数据库和日志 | **不能删** |
| `/moviepilot-v3/core` | 保存浏览器内核，避免容器重建后重复下载 | — |

下面是一份**骨架示例**（单容器 + 内置 SQLite，对应官方「V3 小白版」；完整模板以官方 Wiki 为准）[^c4-skel]：

```yaml
## docker-compose.yml（骨架示例）
services:
  moviepilot:
    image: jxxghp/moviepilot-v3:latest
    container_name: moviepilot-v3
    ports:
      - '3000:3000'   # Web 页面：浏览器访问宿主机 3000 端口
      - '3001:3001'   # API 接口
    volumes:
      - '/media:/media'                                 # ← 改：下载目录与媒体库共用根目录
      - '/moviepilot-v3/config:/config'                 # ← 改：配置 / 数据库 / 日志（勿删）
      - '/moviepilot-v3/core:/moviepilot/.cloakbrowser' # ← 改：浏览器内核缓存
    environment:
      - 'NGINX_PORT=3000'   # Web 页面端口
      - 'PORT=3001'         # API 端口
      - 'PUID=0'            # 运行用户 ID
      - 'PGID=0'            # 运行用户组 ID
      - 'UMASK=000'         # 新建文件权限掩码
      - 'TZ=Asia/Shanghai'  # 时区
    restart: always
    stop_grace_period: 120s  # 留足优雅停止时间（见 4.3）
```

> [!warning] 这三个目录是硬链接的命门
> `/media` 是「下载目录 + 媒体库」的**共同根目录**。第 3 章讲过：硬链接要求下载目录与媒体库在同一个根目录下、整体映射；分开映射就会跨盘失败[^c4-17][^c4-18]。

> [!note] 基础环境变量都在这
> 上面那 6 行 `environment` 就是官方列的「基础设置」：`NGINX_PORT`（默认 3000）、`PORT`（默认 3001）、`PUID` / `PGID`（默认 0）、`UMASK`（默认 000）等，可按需调整[^c4-21]。

### 4.3 「动手实践」：启动、更新与优雅停止（新手可跳过）

在 `docker-compose.yml` 所在目录执行[^c4-15]：

```bash
## 启动（-d = 后台运行）
docker compose up -d

## 以后更新镜像时：
docker compose pull && docker compose up --force-recreate -d
```

启动完成后，在浏览器打开 `http://宿主机IP:3000`；若你改了宿主机端口，访问地址里的 `3000` 也要同步改[^c4-16]。

**为什么要留 120 秒的优雅停止？** V3 停止时会依次关闭后台任务、插件和其他运行模块；官方建议为容器预留 120 秒优雅停止时间，避免 Docker 用默认的较短等待时间**强制终止**仍在收尾的进程[^c4-19]。这正是骨架里 `stop_grace_period: 120s` 的来历（若用 `docker run`，则写 `--stop-timeout 120`）。

> [!tip] 大白话
> 把优雅停止想成**关电脑前先「保存并退出」**：直接拔电（Docker 默认的短超时）会丢未保存的东西；给足 120 秒，等于让程序把手头的活干完再关机。

### 4.4 首次访问与初始化：V3 不预置任何账号

这是第 2 章那条「分水岭」落到实操：

- **V3 全新启动不会预置管理员用户、密码或 API Key。** 首次访问 Web 地址时，系统会进入初始化页面；你在这里填写管理员用户名、密码（需确认两次）并生成 API Key，保存后才跳转到登录页面[^c4-12]。
- 因此 **Compose 模板里不需要填** `SUPERUSER`、`SUPERUSER_PASSWORD` 或 `API_TOKEN`[^c4-13]。

> [!tip] 大白话
> 把首次访问想成**新路由器开箱**：插上电（启动容器）后，第一件事是打开管理页**自己设 Wi-Fi 名和密码**——出厂不给预设密码。V3 就是这个逻辑，密码是你在这一步定的。

### 4.5 界面落点示例

- 访问地址形如：`http://宿主机IP:3000`（端口改了地址同步改）[^c4-16]。
- 首次进去是**初始化页**（不是登录页）：建管理员 → 保存 API Key → 才跳到登录页[^c4-12]。
- 登录后即进入 Web 管理界面，日常配置集中在「设定」一类的菜单里（站点、下载器、媒体服务器等，从第 5、7 章起逐个对接）。

### 4.6 V3 的架构变化对用户意味着什么

一个最容易被旧教程带偏的点：**V3 的 Web 内建重启，不需要映射 `/var/run/docker.sock`**。

V3 镜像内置 supervisor，同时托管 Nginx 和后端进程；Web 里的「重启」由容器内 supervisor 完成，不依赖 Docker 的容器重启策略[^c4-20]。对比 V2 模板里那行 `-v /var/run/docker.sock:/var/run/docker.sock:ro`（把宿主机 Docker 控制权交给容器，用于页面重启 / 自动更新）——在 V3 里**不需要**。

> [!note] 结论单独成句
> `restart: always` 只负责「容器整体异常退出、或主机重启后自动拉起」，**不负责**页面里的重启——页面重启由容器内 supervisor 干[^c4-20]。

> [!summary] 本章小结
> - V3 部署 = 写 Compose（改 3 个宿主机目录）→ `docker compose up -d` → 浏览器开 `http://宿主机IP:3000` → 首次访问初始化。
> - V3 **不预置**管理员 / 密码 / API Key，模板里不写 `SUPERUSER`、`SUPERUSER_PASSWORD`、`API_TOKEN`。
> - `/media` 必须是下载目录与媒体库的共同根目录，否则硬链接失败。
> - 建议预留 120 秒优雅停止（`stop_grace_period: 120s`）。
> - V3 内置 supervisor，Web 内建重启**不需要**映射 `/var/run/docker.sock`。

**下一章预告**：容器跑起来、管理员建好之后，就撞上本主题门槛最高的一关——PT 站点认证。下一章把「认证是什么、为什么必须有、没有账号怎么办」一次讲透，并且在你动手配置之前就先说明白「无 PT 的现实结论」。

## 第 5 章 关键门槛——PT 站点认证（本主题最容易被劝退的一步）

> [!summary] 一句话看懂
> MoviePilot 的「搜片 → 订阅 → 下载」必须先用 **PT 站点账号做用户认证**；没有账号，就把这几步全部挡在门外。这一章把「认证是什么、为什么必须有、没有怎么办」讲透，并**在你动手配置之前**就先说明白结论。

这一章解决本主题**最容易被劝退的一步**：认证。第 1 章已经给出「没有 PT 账号只能走一半」的底线；这一章把这条线讲细——认证在哪配、配什么、不配会发生什么。

### 5.1 名词扫盲表（先扫一遍）

| 名词 | 大白话 |
| --- | --- |
| **PT 站点** | 邀请制 / 考核制的下载站点，要账号才能访问；是 MoviePilot 主要的「货源」。 |
| **站点索引** | 在站点里「查货」的能力：搜资源、拉取资源清单。 |
| **用户认证** | 拿 PT 站点账号向 MoviePilot 证明「我是合格会员」。**认证通过，才能用站点相关功能。** |
| **AUTH_SITE** | 一个环境变量，告诉 MoviePilot「用哪个站点做认证」；可配多个，用英文逗号分隔。 |
| **IYUU** | 官方支持的认证站点之一（写作 `AUTH_SITE=iyuu`），需要 `IYUU_SIGN`（IYUU 登录令牌）。 |
| **HHClub（憨憨）** | 官方支持的认证站点之一（写作 `AUTH_SITE=hhclub`），需要用户名 + 密钥。 |

### 5.2 为什么 MoviePilot 要加认证

这是官方的一段自述，把动机说得很直白[^c5-7]：

| 它管什么 | 官方原文 | 说人话 |
| --- | --- | --- |
| 认证机制 | 「MoviePilot引入了PT用户认证机制，你需要有认证站点范围内的账号才能使用软件的资源搜索、订阅及下载功能，出此下策与利益无关，属NAStool一路走来，吸取失败经验的无奈之举。」 | 要有认证站点范围内的账号，才能用**资源搜索、订阅、下载**；官方自称这是「无奈之举」。 |

**一句话概括**：MoviePilot 用 PT 认证把「能用站点功能」和「有站点账号」绑在一起——没账号，站点功能就用不了。

### 5.3 三种认证方式

官方给了三种常见配置方式[^c5-11a][^c5-11b]：

| 方式 | 怎么用 | 适用 |
| --- | --- | --- |
| ① 初始化向导 | 首次安装时，在向导里顺带完成用户站点认证 | V1、V2 的安装向导 |
| ② 头像菜单「用户认证」 | 进系统后，点右上角头像 → 用户认证 | v2.0.7+（含 V3 登录后） |
| ③ 环境变量 `AUTH_SITE` | 在环境变量里写认证站点及参数 | 自动化部署 / 批量维护 |

> [!note] V3 读者看这里
> V3 的初始化页只负责建管理员和 API Key（第 4 章），**不含认证**；所以 V3 用第 ② 或 ③ 种方式——登录后在头像菜单里认证，或写环境变量。官方也推荐优先用前两种（UI 方式），因为系统会按当前支持情况动态列出可认证站点[^c5-11a]。

### 5.4 「动手实践」：`AUTH_SITE` 写法与示例（新手可跳过）

> [!tip] 新手可跳过
> 如果你在 Web 界面做认证（第 ② 种方式），这一节可以跳过。只有自动化部署 / 批量维护才需要写环境变量。

`AUTH_SITE` 支持配**多个**认证站点，用英文逗号分隔；系统会**依次执行认证操作，直到有一个站点认证成功**[^c5-10]。下面是一段**写法示例**（站点名与参数名取自官方表格；令牌 / 用户名 / 密钥是你的私人信息，用占位符，切勿照抄）：

```yaml
environment:
  - 'AUTH_SITE=iyuu,hhclub'        # 依次尝试 IYUU → 憨憨，直到有一个成功
  # 下面是对应站点的认证参数（值请换成你自己的）
  - 'IYUU_SIGN=你的IYUU登录令牌'
  - 'HHCLUB_USERNAME=你的用户名'
  - 'HHCLUB_PASSKEY=你的密钥'
```

> [!warning] 别把「示例值」当默认值
> `AUTH_SITE=iyuu,hhclub` 里的站点名是官方给的取值示例；`IYUU_SIGN` / `HHCLUB_USERNAME` / `HHCLUB_PASSKEY` 的具体值必须换成你自己的账号信息——官方表格给的是**字段名**，不是可用的值。

### 5.5 🚧 无 PT 账号的现实：你剩下什么、失去什么

> [!warning] 这是据官方功能二分做出的推断，不是官方原话
> **失去**：「资源订阅下载」这一半——搜片、订阅、自动下载，全部用不了。
> **剩下**：「文件整理刮削」这一半——对已经在本地的片子做整理、刮削，仍然可用。
>
> 依据：官方把 MoviePilot 功能一分为二——「文件整理刮削」与「资源订阅下载」，其中后者需要可用的 PT 站点并能认证[^c5-8]。
> 请注意：官方**没有**直接用「没账号也能做整理刮削」这句话表述；这是由上面的功能二分**推断**出来的，标为推断是为了让你知道它的确定性层级，而不是把推断当公告。

> [!tip] 大白话
> 把 MoviePilot 想成一台**双卡双待手机**：一张卡（整理刮削）不验证就能用；另一张卡（订阅下载）得插会员卡（PT 认证）。没会员卡，就把能用的那张先用起来——这正是第 6 章「备选路 C」要接上的地方。

### 5.6 未认证时的具体表现

不是「部分功能打折」，而是「站点功能整体不可用」：如果没通过用户认证，**私有站点和公开站点都无法维护到系统中，已维护的站点实际也无法使用**[^c5-9]。

| 场景 | 未认证时的表现 |
| --- | --- |
| 想新增私有站点 | 维护不进去 |
| 想新增公开站点 | 同样维护不进去 |
| 已经维护过的站点 | 实际也无法使用 |

**一句话概括**：没认证 ≈ 站点功能整体失效，与「站点是私有还是公开」无关。

> [!summary] 本章小结
> - 认证门槛：MoviePilot 的「搜索、订阅、下载」需要有认证站点范围内的账号。
> - 三种认证方式：初始化向导（V1/V2）、头像菜单「用户认证」（v2.0.7+）、环境变量 `AUTH_SITE`；V3 用后两种。
> - `AUTH_SITE` 可写多个站点，逗号分隔，依次尝试直到有一个成功。
> - **没有 PT 账号时只剩「整理刮削」**——这是据官方功能二分的**推断**，须标明依据。
> - 未认证时，私有 / 公开站点都维护不了，已维护的也实际不可用。

## 第 6 章 备选路 C——不依赖 PT 的网盘流媒体路线

> [!summary] 一句话看懂
> 没有 PT 账号也能立刻「有得看」：走**网盘流媒体**这条路——片子直接从网盘来，不经过 PT 站点认证。它的来龙去脉本库已有整套笔记，这一章只做**定位 + 双链指引**，不复述正文。

这一章解决「没有 PT 账号怎么办」。第 5 章结尾已经把话说透：没账号只剩「整理刮削」。那「片子从哪来」这个问题，由备选路 C 回答。这一章不重复原理，只讲清 C 路适合谁、细节去哪看、以及它怎么和主路 A 接上。

### 6.1 C 路是什么、适合谁

**C 路 = 不依赖 PT 认证的网盘流媒体路线**：片源放在网盘（或类似云资源）里，通过「指针文件 + 直链播放」的方式在你的媒体服务器里播放，全程不需要 PT 站点账号。一句话——**换一条「片子从哪来」的渠道，绕开认证门槛**。

适合这三类人：

- 手上**没有 PT 站点账号**，但想马上有一条能跑通、能看片的链路；
- 片源本来就主要来自**网盘**，对「站点自动订阅」没有刚需；
- 想先把播放链路跑顺，**以后再决定要不要**补 PT 认证。

> [!tip] 大白话
> 主路 A 像「办会员去批发市场进货」，门槛在会员（PT 认证）；备选路 C 像「直接网购到家」——进货渠道不同，但都能把菜端上桌。

### 6.2 细节去哪看：只用双链，不复述

C 路的**原理与操作细节**，库内既有笔记已经写全。这里只给入口，逐条标明「细节请见」——**正文不复制、不转述**：

- 在 fnOS 上怎么单容器部署（选型、避坑、运维全流程）——**细节请见** [[流媒体与影音/小雅 fnOS 单容器部署/小雅 fnOS 单容器部署（总览）]]
- 「指针文件」是什么、302 直链播放怎么工作——**细节请见** [[流媒体与影音/Strm流文件与302播放详解]]
- 网盘播放 / 直链 / 本地下载三条路线怎么取舍——**细节请见** [[流媒体与影音/网盘影视播放与本地存储的取舍]]
- 硬解 / 软解怎么选——**细节请见** [[流媒体与影音/硬件解码vs软件解码]]

> [!note] 为什么这里只放链接
> C 路是「已经写过的旧知识」，重复铺一遍既啰嗦又容易和原笔记口径漂移。把入口集中列在这里，你按需跳转即可。

### 6.3 A 与 C 的接口：两条路怎么接

两条路不是二选一，而是可以**叠加**：

- 用 **C 解决「片子从哪来」**（网盘提供片源）；
- 用 **A 的「文件整理刮削」管本地已下载的片**（整理命名、配海报简介）。

> [!warning] 这是推断，不是官方原话
> 上面的「A 与 C 可叠加」是由官方功能二分**推断**得出的：MoviePilot 的「文件整理刮削」不需要 PT 认证，所以这一半能和网盘流媒体路线共存——**细节依据**见第 1 章 1.3 与第 5 章 5.5，来源是官方对「文件整理刮削 / 资源订阅下载」的二分[^c6-8]。
> 官方并未直接表述「用 C 供片、用 A 整理」这种做法，故标为**推断**。

### 6.4 选型对比表

| 你的情况 | 推荐路线 | 为什么 |
| --- | --- | --- |
| 有 PT 账号，想要全自动 | **主路 A** | 搜片 → 订阅 → 下载 → 整理 → 刮削 → 播放，一条龙 |
| 无 PT 账号，想立刻有得看 | **备选路 C** | 不碰认证，播放链路直接跑通 |
| 无 PT 账号，但想省事 | **备选路 C** | 沿用库内既有笔记，照着做即可 |
| 有 PT 账号，也想深挖 | **A（+ C 叠加）** | A 做自动化，C 补充片源渠道 |
| 片源主要在网盘 | **备选路 C** | 与「片子从哪来」的实际情况一致 |
| 片源主要来自站点 | **主路 A** | 站点索引 + 下载器是 A 路的强项 |
| 只想玩公网 BT、不想办 PT | **第二备选路：下载器 RSS + 目录监控**（见 6.5） | 找种子交给下载器，整理刮削交给 MoviePilot，绕开站点认证 |

### 6.5 第二备选路：玩 BT（公网 BT 站）

先说结论：**公网 BT 站在 MoviePilot 的支持清单里确实有**（比如 `Nyaa`、动漫花园），**但公开站点和私有站点一样，都要先过「用户认证」这道闸**；而认证只能用 PT 站点账号[^c6-9]。所以「完全没有 PT、只想玩 BT」在官方主线里仍然走不通——要么**绕开它的站点功能**（6.5.2，推荐），要么先弄到一个认证账号（6.5.4）。

#### 6.5.1 官方口径：BT 站在清单里，但和 PT 站共用同一道闸

官方的支持站点清单分成两类，其中**「公开站点」这一类就是公网 BT 站**（不需要邀请、不考核分享率）：

| 分类 | 官方列出的站点 |
| --- | --- |
| 公开站点（公网 BT） | `Nyaa`、`TorrentGalaxy`、`ACG.RIP`、`MiKan`、动漫花园、`AniBT` |

但清单页**开头第一句提醒**就把门关上了（官方原文，逐字）：

> [!warning] 官方原文
> 提醒：如果你没有通过用户认证，私有站点和公开站点都无法维护到系统中，已维护的站点实际也无法使用。

讲 `AniBT` 的那一节，官方又把同一个门槛原地重申了一遍（逐字）：

> AniBT 的公开接口无需站点 Cookie 或 API Key；MoviePilot 自身的用户认证要求仍然适用。

上句里 `AniBT`、`Cookie`、`API Key` 三个词原文即写作英文，逐字照抄，未作改动。

说人话：**BT 站本身不难加**（甚至不用登录凭据），**难的是「加站」这个动作要先认证**。而认证站点那张表——官方给出的 `AUTH_SITE` 取值一共 **34 个**，全是 PT 站（`iyuu`、`hhclub`、`audiences` … `ptskit`），**没有一个公网 BT 站**[^c6-10]。

> [!tip] 大白话
> 把「站点管理」想成一间**仓库**：BT 站和 PT 站都摆在货架上，谁都能拿；但**进仓库的门要刷会员卡**（用户认证），而发卡处只认 PT 站。所以你手上没有 PT 账号时，货架上看得到的 BT 站也拿不出来——除非**不走仓库正门**（见 6.5.2）。

#### 6.5.2 路线 1（推荐，真的不依赖 PT）：让下载器自己去 BT 站抓

既然绕不开 MoviePilot 的站点认证，那就**不去碰它的站点功能**，把一件事拆成两半，各交给更合适的角色：

| 环节 | 交给谁 | 为什么能行 |
| --- | --- | --- |
| 找种子、自动下载 | **下载器自己的 `RSS` 订阅**（如 `qBittorrent`） | BT 站基本都提供 `RSS`，下载器直接订阅即可，与 MoviePilot 的站点认证无关 |
| 整理、刮削、入库 | **MoviePilot** | 官方功能二分的「文件整理刮削」这一半**不需要认证**（依据见 1.3 与 5.5，属官方口径[^c6-8]） |
| 播放 | 媒体服务器（飞牛影视 / `Jellyfin` 等） | 只读整理好的媒体库，与来源渠道无关 |

> [!tip] 这条路线和 C 路的关系
> C 路解决的是「**网盘**里的片怎么播」，这条路线解决的是「**BT 站**的片怎么自动落到硬盘」。共同点在于：两者都**不碰 MoviePilot 的站点认证**，只用它「整理刮削」那一半。

**动手实践（新手可跳过）**，四步：

1. **在下载器里加 `RSS` 订阅**：把 BT 站的 `RSS` 地址加进 `qBittorrent` 的 `RSS` 阅读器（选「影视」相关分类，条数拉到最大）。
2. **设 `RSS` 下载规则**：命中关键词就自动下载，并统一打上分类、指定保存目录。
3. **目录必须和 MoviePilot 对齐**：下载目录要**映射进容器**，并且**与下载器使用同一路径**，否则文件会落进容器内部[^c6-12]。
4. **在 MoviePilot 里开目录监控**：监控上一步的下载目录，有新文件就自动整理进媒体库（`目录监控` 在 `v2.0+` 已内置[^c6-11]）。

> [!warning] BT 资源的老毛病：命名不规范
> 官方自己说明过：内置识别程序是**针对 PT 站点资源做的优化**，而**网盘、BT以及动漫类**资源命名不规范，需要额外规则或插件来提高识别率[^c6-13]。所以走 BT 时，**识别不出来是常态**，不是你的配置错了。

#### 6.5.3 路线 2（存在这个插件，但我没核实过）：`Prowlarr` 扩展

官方 Wiki 的**公开插件仓库清单**里，有一个第三方插件仓库 `MoviePilot-ProwlarrExtend`[^c6-11]，用途是把 `Prowlarr` 的索引器（`Prowlarr` 支持大量公网 BT 站）接进 MoviePilot。

> [!warning] 别把它当结论
> 我只核实到「**这个插件出现在官方 Wiki 列出的公开插件清单里**」这一件事。它**能不能绕开用户认证**、**当前是否兼容 V3**，我**没有核实**——属于「知道有这条路存在」，不是「照做可用」。

#### 6.5.4 路线 3（最省事，前提是先有账号）：弄到一个认证账号

只要 `AUTH_SITE` 表里**任何一个站**认证成功，公开站点和私有站点就一起解锁了[^c6-9]。表里门槛最低的是 `iyuu`——它只需要一个 **`IYUU` 登录令牌**（`IYUU_SIGN`），不像其他站要「用户 ID + 密钥」两样[^c6-10]。

> [!question] 有一件事我没有替你打包票
> `IYUU` 账号**注册时是否要求你已有 PT 站点信息**，我**没有核实**。想走这条最短路径，先去 `IYUU` 官方站点确认注册条件，再回来配 `AUTH_SITE`。

#### 6.5.5 三条路线怎么选

| 你的情况 | 走哪条 | 代价 |
| --- | --- | --- |
| 只想玩 BT，不打算碰 PT | **路线 1**（下载器 `RSS` + 目录监控） | 要自己维护 `RSS` 规则；BT 资源识别率偏低 |
| 想试试 `Prowlarr` 生态 | 路线 2（**未核实**） | 兼容性与「是否绕开认证」都未知，不建议当主方案 |
| 能弄到一个 PT 账号 | 路线 3，然后回主路 A | 认证一次，公开站点与私有站点一起解锁 |

> [!summary] 本章小结
> - C 路 = 不依赖 PT 认证的网盘流媒体路线，适合没账号 / 想立刻能看 / 片源本就在网盘的人。
> - C 路细节不在此复述，逐条双链指向库内既有笔记（小雅单容器部署、STRM/302、网盘与本地取舍、硬解与软解）。
> - A 与 C 可叠加：C 供片源，A 的整理刮削管本地片——**这是据官方功能二分的推断，须标明依据**。
> - 想玩公网 BT：BT 站确实在官方支持清单里，但和 PT 站一样被「用户认证」挡着；绕开的办法是**下载器 `RSS` 抓种 + MoviePilot 目录监控整理**（6.5）。

**下一章预告**：片子有了、链路通了，接下来要让 MoviePilot 和另外两块拼上——对接下载器与媒体服务器，让它能查库存、能触发下载、能被媒体服务器展示。下一章讲这些对接。

## 第 7 章 对接下载器与媒体服务器（让 MoviePilot 成为「一环」）

> [!summary] 一句话看懂
> MoviePilot 自己既不下载、也不播放，它要和**下载器**、**媒体服务器**拼在一起才能转起来。这一章讲清三件事：它为什么只是「一环」、下载目录怎么映射才不出错、以及站点那一大堆维护项哪些必须**认证后**才能用。

这一章解决「把 MoviePilot 和另外两块拼上」：让它能查库存、能触发下载、能被媒体服务器展示。第 5 章已经把关口（认证）讲过，这一章讲对接。

### 7.1 为什么 MoviePilot 只是「一环」

先摆正位置[^c7-26]：

| 它管什么 | 官方原文 | 说人话 |
| --- | --- | --- |
| 它的定位 | 「MoviePilot只是媒体库自动化管理的一环，需要通过调用下载器来完成资源的下载，需要通过媒体服务器来管理和展示媒体资源，同时通过媒体服务器Api来查询库存情况控制重复下载，通过CookieCloud来快速同步站点Cookie和新增站点。安装前需要先完成配套软件的安装。」 | 下载靠下载器、展示靠媒体服务器；它还会通过媒体服务器 API 查库存，避免重复下载同一部片。 |

**一句话概括**：MoviePilot 是「指挥中心」，下载器是「手」，媒体服务器是「脸」——缺哪个，链路都不完整。

### 7.2 下载器对接：版本要求与配置要点

官方要求下载器达到一定版本[^c7-23]：

| 下载器 | 最低版本 |
| --- | --- |
| Qbittorrent | **>= 4.3.9** |
| Transmission | **>= 3.0** |

> [!note] 配置要点
> 在 MoviePilot 的「设定 → 连接 → 下载器」里填写下载器地址、账号密码，并**确保 MoviePilot 能访问到下载器**。下载器与 MoviePilot 如果都用 Docker 部署，注意两者看到的「下载目录路径」要对得上（见 7.3）。

### 7.3 下载目录映射：必须映射进容器，且与下载器一致

这是最容易出错的一步，官方这样要求[^c7-30]：

| 它管什么 | 官方原文 | 说人话 |
| --- | --- | --- |
| 下载目录 | 「在设定中添加下载目录配置。如果你是使用docker环境部署，下载目录对应的根目录需要映射到容器中，否则下载文件会存储到容器内导致容器异常。下载目录需要与下载器使用的目录一致，如使用docker可通过映射路径时转换成一致。」 | 下载目录（的根目录）必须映射进 MP 容器；而且 MP 里配的下载目录，要和下载器里配的下载目录**是同一个路径**。 |

两条硬要求，对照着做：

| 要保证的事 | 不做会怎样 | 做法 |
| --- | --- | --- |
| 下载目录**映射进容器** | 文件落进容器内部，容器一重建就丢、还占满容器空间 | 在 Compose 里把下载目录挂进 MP 容器 |
| 与下载器目录**一致** | MP 找不到下载器下的文件，无法触发整理 | 让两个容器里配置的下载目录路径字符串相同（用映射「转成一致」） |

```yaml
## docker-compose.yml（片段）：让两个容器看到同一个下载目录路径
services:
  moviepilot:
    volumes:
      - '/media:/media'                 # 下载 + 媒体库共用根目录（第 3 章）
  qbittorrent:
    volumes:
      - '/media/downloads:/downloads'   # 下载器把片下到 /downloads
## 关键：在 MoviePilot 与 qBittorrent 的「下载目录」配置里，都填 /downloads
```

> [!warning] 路径不一致 = 白下
> 如果 MP 里写 `/downloads`、下载器里写别的路径，MP 就「看不见」下好的文件，整理和刮削都无从谈起。

### 7.4 媒体服务器对接（Jellyfin / 飞牛影视）

官方给出的媒体服务器版本建议[^c7-24]：

| 媒体服务器 | 版本建议 |
| --- | --- |
| Emby | 建议 **>= 4.8.0.45** |
| Jellyfin | 推荐 **latest** 分支 |
| Plex | 无特定版本要求 |

> [!tip] 用飞牛影视也一样
> 「媒体服务器」是泛指——只要能把片子整理成海报墙、并能被 MP 通过 API 查库存即可。Jellyfin / Emby / Plex 是官方点名的三种；fnOS 自带的**飞牛影视**同样可作为展示端，把它当作「媒体服务器」接进来即可。接入后，MP 通过它的 API 查库存，避免重复下载。

### 7.5 站点维护项速查（哪些要认证后才能用）

站点维护项不少，官方逐个列了用途[^c7-29]。下表把每一项收成速查；**最后一列统一标注：这些站点项都需要通过用户认证才可用**（依据：没认证时站点无法维护、也无法使用，见第 5 章 5.6）。

| 维护项 | 它是什么 | 需要 PT 认证？ |
| --- | --- | --- |
| 站点地址 | 站点域名地址，须在「支持站点清单」内 | ✅ 需要 |
| 优先级 | 搜索时的站点排序，数值越小越优先（可拖动卡片调整） | ✅ 需要 |
| RSS 地址 | 站点 RSS 链接；订阅模式选「站点 RSS」时靠它取资源 | ✅ 需要 |
| 超时时间 | 搜索时等待站点返回的最大秒数（连通好设小、响应慢设大） | ✅ 需要 |
| 站点 Cookie | 从浏览器开发者工具里取站点 Cookie 填入 | ✅ 需要 |
| 请求头 Authorization | 个别站点不用 Cookie，改用 Authorization（已知：馒头） | ✅ 需要 |
| 令牌 API Key | 个别站点用 API Key 做访问控制（已知：馒头） | ✅ 需要 |
| 站点 User-Agent | 取 Cookie 时配套的浏览器标识，有助于跳过人机验证 | ✅ 需要 |
| 站点流控 | 控制单位周期内的访问次数与间隔，避免压垮站点 | ✅ 需要 |
| 代理 | 该站点是否走已配置的代理（需配 `PROXY_HOST`） | ✅ 需要 |
| 浏览器仿真 | 是否用浏览器仿真访问，适合人机验证严格的站点（会变慢、更耗资源） | ✅ 需要 |

> [!warning] 无 PT 账号的读者：这一整张表都可以先跳过
> 上面 11 项**全部依赖用户认证**。没认证时，站点既维护不进去、已维护的也不能用（第 5 章 5.6）。你的重心应放在第 8 章的「整理刮削」——那一半不需要认证。

### 7.6 「动手实践」：QB 完成时回调，省去轮询（新手可跳过）

> [!tip] 新手可跳过
> 不配这段也能用（只是靠轮询、稍慢一点）。想「下完立刻整理」再配。

官方推荐：用 QB 作为下载器时，可在「设置 → 下载完成时运行外部程序」处填入一条回调命令，实现**下载完成后立即整理入库**，无需等待轮询[^c7-31]：

```bash
## qBittorrent：设置 → 下载完成时运行外部程序
curl "http://localhost:3000/api/v1/transfer/now?token=moviepilot"
```

> [!warning] 地址、端口、token 要按你的实际改
> 示例里的 `3000`、`moviepilot` 是官方给的占位形式——请替换成你自己的实际端口和 token（`curl` 也可换成 `wget`）[^c7-31]。

> [!summary] 本章小结
> - MoviePilot 只是「一环」：下载靠下载器、展示靠媒体服务器，并通过媒体服务器 API 查库存防重复下载。
> - 下载器：Qbittorrent >= 4.3.9、Transmission >= 3.0。
> - 下载目录必须**映射进容器**且**与下载器目录一致**，否则文件落进容器内或整理不到。
> - 媒体服务器：Emby >= 4.8.0.45、Jellyfin latest、Plex 无要求；飞牛影视同样可作为展示端。
> - 站点 11 项维护项**全部需要 PT 认证**；无账号的读者可整表跳过。
> - QB 完成时回调可省去轮询（可选）。

**下一章预告**：站点那一半需要认证，但另一半——**文件整理与刮削**——不需要 PT 账号也能真正落地。下一章把「无 PT 读者真正能用」的那半边讲透。

## 第 8 章 文件整理与刮削：无 PT 也能落地

> [!summary] 一句话看懂
> 官方把功能分成两半：**文件整理刮削** 和 **资源订阅下载**，只有后者要求有 PT 站点并完成认证[^c8-8]。所以就算你没有 PT 账号，前一半（把文件改名、归目录、配海报）也照样能跑——这一章讲这半边怎么配、以及「硬链接」为什么不成立的三种情形。

上一章说站点那 11 项全要认证；这一章说好消息：**不需要认证的那一半**才是「把片子变得整齐好看」的核心。

> [!warning] 关于「无 PT 也能做」的性质说明
> 「不需要 PT 账号也能做文件整理刮削」**不是官方原话，而是根据官方功能二分的推断**。官方原话只说了「资源订阅下载功能需要有可用的 PT 站点，同时这些站点中需要有一个可用于认证」[^c8-8]——它**没有**正面说「整理刮削不需要认证」。推论是：既然认证要求只挂在「资源订阅下载」上，那么另一半「文件整理刮削」就没有被挂上这个要求。请把它当**推断**看，不是官方承诺。

### 8.1 整理模式怎么选（6 种对比）

MoviePilot 在「设定 → 目录 → 整理模式」里提供 6 种整理方式[^c8-27]。一句话先记住主角：**想保种又省空间，选硬链接**。

| 整理模式 | 文件怎么放 | 好消息 | 代价 / 限制 |
| --- | --- | --- | --- |
| **硬链接** | 一份文件多个入口，只占一份空间 | 省空间；改名不影响做种 | 必须在**同一磁盘/存储空间/映射路径**下；不能改文件内容 |
| 软链接 | 像快捷方式指向原文件 | 占空间少 | 原文件一删就失效；docker 里映射前后路径必须一致 |
| 复制 | 多存一份副本 | 简单、互不影响 | **多占一份空间** |
| 移动 | 把文件挪过去 | 不额外占空间 | **影响原文件做种** |
| Rclone 复制 | 用 Rclone 复制到网盘 | 本地文件保留 | 需映射 rclone 配置目录（`/moviepilot/.config/rclone`）；网盘配置名必须为 `MP` |
| Rclone 移动 | 用 Rclone 移动到网盘 | 本地不留副本 | 同上配置要求 |

> [!tip] 大白话：硬链接像「同一个房间开两扇门」
> 硬链接不是复制文件，而是给**同一份文件**再开一个「门」（入口）。你从媒体库那扇门进去看到的是同一间房、同一份数据，所以**不占第二份空间**；只有两扇门都拆了，房间才会被清空（文件才真正释放）。所以它既能给媒体库用，又不耽误下载器继续做种。
>
> 代价是：两扇门必须**开在同一栋楼**（同一磁盘/存储空间/映射路径）。跨楼就开不出「同一间房」，只能退化成复制——这正是 8.3 要讲的事。

### 8.2 覆盖方式（同名文件怎么办）

媒体库里已经有同名文件（后缀也相同）时，由「覆盖方式」决定策略[^c8-28]，共 4 种：

| 覆盖方式 | 行为 | 适合谁 |
| --- | --- | --- |
| 从不覆盖 | 有同名就**中断整理**，历史里留一条错误记录 | 想手动把关、不想被覆盖 |
| 按大小覆盖 | 下载的**更大**才覆盖，否则中断并留错误记录 | 想用高清版替换低清版 |
| 总是覆盖 | 直接用下载的覆盖同名文件 | 图省事、不在意旧文件 |
| 仅保留最新版本 | 删掉库里同片的**其它版本**（含文件名不一致的），只留最新 | 想保持库干净、一版到底 |

> [!warning] 「从不覆盖」会产错误记录，但不代表资源有问题
> 「从不覆盖」和「按大小覆盖」在中断时都会「在历史记录中将产生错误的整理记录」[^c8-28]。这不是文件坏了，而是**策略主动中止**留下的痕迹——知道这点，就不会被历史里的红字吓到。

### 8.3 硬链接为什么不成立（呼应第 3 章）

第 3 章规划目录时讲过「下载目录和媒体库要在一个根目录下」。这里给出官方的**完整原因**和三种典型翻车情形[^c8-17][^c8-18]：

| 它管什么 | 官方原文 | 说人话 |
| --- | --- | --- |
| 为什么只能一个根目录 | 「如果你计划使用硬链接来整理文件，那么文件下载目录和整理后的媒体库目录只能映射一个根目录不能分开映射，否则将会导致跨盘无法硬链接。这是由docker的目录映射机制决定的，下面这些情况都会导致跨盘无法硬链接：下载目录和媒体库目录分别属于两个不同的磁盘；下载目录和媒体库目录属于同一磁盘，但在两个不同的分区/存储空间/存储池中；下载目录和媒体库目录分别作为两个目录路径映射到docker容器中。」 | 想让硬链接成立，下载目录和媒体库目录必须共用**同一个根目录、同一次映射**；跨磁盘、跨分区/存储池、或分成两次映射，都会让硬链接失败。 |

三种「跨盘」情形，对照自查：

| 情形 | 一句话 | 结果 |
| --- | --- | --- |
| ① 不同磁盘 | 下载在一块盘、媒体库在另一块盘 | 硬链接不成立 |
| ② 同盘不同分区/存储池 | 同一块盘，但分属不同分区或存储池 | 硬链接不成立 |
| ③ 分成两次映射 | 两个目录分别映射进容器 | 硬链接不成立 |

> [!tip] 大白话：一次映射 = 一张「大桌子」
> 把整个根目录**一次性**摆上容器这张「大桌子」，下载区和媒体区就都在这张桌子上，硬链接才搭得起来。你把下载区、媒体区**分两次**分别搬上桌（情形③），系统会当成两块互不相通的地方，硬链接自然失败。

### 8.4 目录监控与兼容模式（网盘 / SMB / NFS 触发不了怎么办）

有些目录**不支持「事件触发」的实时监控**，比如网盘、Windows 共享给 Linux 的 SMB、NFS 共享。做法有三条[^c8-34]：

| 场景 | 处理 |
| --- | --- |
| 启动日志报 inotify 相关错误 | 在**宿主机（不是容器里）**调大文件句柄数并重启（见第 9 章 9.2 与第 3 章的 inotify 说明） |
| 挂载网盘 / SMB / NFS，目录监控不实时 | 打开目录监控的**兼容模式**（代价：性能较低、可能频繁读盘） |
| 想绕开目录监控 | 到「设定 → 连接 → 下载器」开启**下载文件自动整理**，改用监控下载器来整理 |

> [!warning] 网盘目录别开实时监控
> 对网盘目录用「目录监控 / 实时监控」容易触发大量 API 请求、被流控——应改用兼容模式，或改走「下载文件自动整理」[^c8-34]。

> [!summary] 本章小结
> - 官方功能分两半：整理刮削 / 资源订阅下载；认证要求只挂在后一半。
> - 「无 PT 也能做整理刮削」是**推断**（依据功能二分 #8），非官方原话。
> - 6 种整理模式里，硬链接最省空间且保种，但必须同盘同映射。
> - 覆盖方式 4 种；「从不覆盖 / 按大小覆盖」中断时会留下错误整理记录，属正常策略行为。
> - 硬链接不成立只有三种原因：不同磁盘、同盘不同分区/存储池、分两次映射。
> - 网盘 / SMB / NFS 触发不了实时监控时，用兼容模式或改走「下载文件自动整理」。

## 第 9 章 故障速查：症状 → 原因 → 处理

> [!summary] 一句话看懂
> 前面配得再齐，落地时也常撞见五个典型报错：硬链接报 `-1`、inotify 报错、网盘监控没反应、重复下浏览器内核、启动报 `No module named 'app.helper.sites'`。这一章把它们收成一张速查表，每条都给你「症状 → 原因 → 处理」，并指回讲原理的章节，不在这里重复原理。

用法：先在 9.1 表里按**症状**定位，再跳到 9.2 对应小节看人话解释和处理动作。

### 9.1 速查表

| 症状 | 原因 | 处理 | 详见 |
| --- | --- | --- | --- |
| 硬链接转移出现 `-1` 报错 | 下载目录与媒体库目录跨盘 / 跨存储空间 / 分成两次映射 | 让两者共用同一根目录、同一次映射 | 第 3 章、第 8 章 8.3 |
| 重启后日志输出 `No module named 'app.helper.sites'` | 容器自动更新到一半被手动重启，依赖没装完 | 重置或重建容器；配 `PROXY_HOST` 加速更新 | 9.2 |
| 启动日志报与 `inotify` 相关的错误 | 宿主机文件句柄数太小，监控功能失效 | 在**宿主机**调大并重启（注意两处文档数值不同） | 第 3 章、9.2 |
| 目录监控不自动整理（网盘 / SMB / NFS） | 这类目录不支持「事件触发」的实时监控 | 开兼容模式，或改用「下载文件自动整理」 | 第 8 章 8.4、9.2 |
| 启动时重复下载浏览器内核 | 没把浏览器内核目录映射出来 | 映射浏览器内核目录 | 第 4 章、9.2 |

### 9.2 逐条人话解释与处理动作

#### ① 硬链接转移出现「-1」

官方给的原因很直白[^c9-32]：「下载目录和媒体库目录出现跨盘/跨存储空间/单独映射路径的情况，导致无法实施硬链接」。

**人话**：硬链接的两扇门没开在同一栋楼里（第 8 章 8.3 讲过三种情形）。**处理**：回到第 3 章的目录规划，让下载目录和媒体库目录**共用同一个根目录、同一次映射**；跨盘就只能改用复制 / 移动 / 软链接等模式。

> [!note] 老版本的一个坑
> 官方还提到：`v1.9.4` 以前为兼容极空间，跨盘硬链接会**自动变成复制**，该问题在 `v1.9.4` 版本更正[^c9-32]。用新版镜像即可绕开这个历史行为。

#### ② 重启后日志输出 `No module named 'app.helper.sites'`

官方解释[^c9-36]：「该问题一般常见于容器启动时自动更新到一半，人为手动重启，更新进程被打断导致容器内依赖未安装完全」。

**人话**：容器自动更新到一半被你手动重启，依赖装残了。**处理**：`重置容器或者是重新创建一个新容器`[^c9-36]。**预防**：配置代理变量 `PROXY_HOST` 或全局接入代理网络，加速自动更新下载、避免超时中断[^c9-36]。

#### ③ 目录监控报 inotify 错误

官方做法是：在**宿主机**上（不是容器里）调大文件句柄数，然后重启[^c9-33a][^c9-33b]：

```bash
## 在宿主机（不是容器内）执行，然后重启宿主机
echo fs.inotify.max_user_watches=524288 | sudo tee -a /etc/sysctl.conf
echo fs.inotify.max_user_instances=524288 | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

> [!warning] 两处官方文档给的数值不一样，别盲目照抄
> 同一组命令，官方两个页面写的值**不同**：
> - 《环境准备》页写的是 `524288`[^c9-33b]；
> - 《故障排除》页写的是 `5242880`（多一个 0）[^c9-33a]。
>
> 两者相差 10 倍。这里**不下结论哪个才对**——请按你实际监控的文件量取下限够用的值（文件越多、需要越大），改完 `sudo sysctl -p` 生效并重启。照抄前先想清楚自己的量级。

#### ④ 目录监控不自动整理（网盘 / SMB / NFS）

官方原因[^c9-34]：「挂载网盘、Windows向Linux的SMB共享、NFS共享等不支持事件触发的目录实时监控」。

**处理**（三选一）：

| 做法 | 说明 |
| --- | --- |
| 开兼容模式 | 打开目录监控的**兼容模式**即可解决；代价是**性能较低、可能频繁读盘**[^c9-34] |
| 改用「下载文件自动整理」 | 到「设定 → 连接 → 下载器」开启，通过监控下载器来整理，**不使用目录监控**[^c9-34] |
| 调 inotify 参数 | 若报错是 inotify 引起，按上面 ③ 处理 |

> [!tip] 别对网盘目录硬开实时监控
> 网盘目录用实时监控容易触发大量 API 请求被流控（第 8 章 8.4）。优先走兼容模式或「下载文件自动整理」。

#### ⑤ 启动时重复下载浏览器内核

官方只给了一句检查项[^c9-35]：检查是不是有映射浏览器内核目录。

**人话**：浏览器内核（供「浏览器仿真」等功能使用）如果没映射到宿主机，容器一重置就丢，于是每次启动都重下一遍。**处理**：把这个目录映射出来。

> [!warning] 官方示例写的是 V2 时代路径
> 官方故障页给的示例是 `/moviepilot-v2/core:/moviepilot/.cloakbrowser`[^c9-35]，其中的 `moviepilot-v2` 是 **V2 时代的宿主机路径**。你用的是 V3（第 2 章），**不要把这条路径照抄进 V3 的 Compose**——请按你自己第 4 章实际使用的容器名与路径来映射，只要「宿主机目录 ↔ 容器内内核目录」对上即可。

> [!summary] 本章小结
> - 五个高频症状：硬链接 `-1`、`No module named 'app.helper.sites'`、inotify 报错、网盘监控不触发、重复下浏览器内核。
> - 硬链接 `-1` 的根因只有一个：跨盘/跨空间/分两次映射——回到目录规划解决。
> - 依赖装残（`No module named`）靠**重置/重建容器**解决，`PROXY_HOST` 预防。
> - inotify 参数**两处官方文档数值不一致（524288 vs 5242880）**，按实际文件量取值，别照抄。
> - 网盘 / SMB / NFS 触发不了实时监控：用兼容模式，或改走「下载文件自动整理」。
> - 浏览器内核要映射出来；官方示例是 V2 路径，V3 请按实际映射。
