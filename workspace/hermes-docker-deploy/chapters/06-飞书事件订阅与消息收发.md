# 第六章 飞书接入（下）：事件订阅、权限与消息收发

## 本章解决什么问题

上一章把飞书应用建好、WebSocket 长连接也通了，但「连上了」不等于「能收发」。飞书的逻辑是：**必须先在开放平台登记想监听的事件，bot 才收得到消息；必须先申请权限 scope，bot 才有资格发消息**。本章把「事件订阅 → 权限 → 消息收发」这三件事一次打通，给出可直接抄的 `config.yaml` 片段（产物 H），最后排掉四个高频坑。

## 6.1 事件订阅：先登记，才有通知

飞书采用「事件订阅」模型：开放平台把用户消息、卡片点击等行为包装成「事件」，只有你在应用后台订阅了对应事件，平台才会推送给你的 bot。

| 事件 | 含义 | 必选？ | 典型用途 |
|---|---|---|---|
| `im.message.receive_v1` | 收到消息（私聊 / 群聊） | ✅ 必选 | 不订阅它，bot 收不到任何消息 |
| `card.action.trigger` | 交互卡片按钮被点击 | 按需 | 按钮卡片、快捷操作、菜单响应 |
| 文档评论 / 会议邀请 | 文档被评论、被拉进会议 | 可选 | 扩展场景，入门基本用不上 |

> [!tip] 大白话
> 把「事件订阅」想成物业门铃登记表：你在飞书开放平台登记「有人按门铃（收到消息）请通知我」，平台才会把消息送到 bot 门口。没登记，就算 bot 在线也收不到任何通知——不是 bot 坏了，是登记表上没你的名字。

订阅入口在 open.feishu.cn 应用后台的「事件与回调」页面，勾选后通常还要等几分钟生效。两个细节值得注意：一是 `im.message.receive_v1` 会把私聊和群聊消息都算作「收到消息」，统一进这一个事件，bot 内部再用 sender / chat 类型区分；二是订阅事件和权限是两套独立系统——**事件决定「平台推不推给你」，权限决定「推给你后你能不能用」**，所以 6.2 的 scope 一个都不能省。进阶玩法（按钮交互）才需要额外开「交互卡片」能力，见 6.5 的 200340 坑。[^c6-1]

## 6.2 权限 scope 五件套

光订阅事件还不够——飞书把「能做什么」拆成一个个权限 scope，每个 scope 是一把独立的钥匙。Hermes 接入飞书至少需要五件套：

| Scope | 授权范围 | 缺了会怎样 |
|---|---|---|
| `im:message` | 读取消息内容 | 收得到「有新消息」的通知，但读不到内容 |
| `im:message:send_as_bot` | 以 bot 身份发送消息 | 收消息正常，发不出去 |
| `im:resource` | 下载图片 / 文件等资源 | 图片、文件类消息收发失败 |
| `im:chat` | 读取群组基本信息 | 拿不到 chat_id、群成员等元数据 |
| `im:chat:readonly` | 只读群组信息 | 部分群组数据不可见，权限判定易出问题 |

> [!tip] 大白话
> 五件套就是一张「授权清单」，像你给钟点工列的家务清单：能进哪个房间（`im:message`）、能碰哪些电器（`im:message:send_as_bot`）、能拿什么工具（`im:resource`）。清单上没写的，bot 一件事都做不了。少配一个，对应功能就静默失效，且通常不报错、只表现为「怎么不动」。

在应用后台「权限管理」里逐个申请，发布应用后生效。飞书权限遵循「按需最小」原则：先配这五件套跑通，不够再加，不要一上来全选。要特别留意，飞书的权限是**写进已发布应用版本**里的——改完 scope 后若应用没重新发布/审核，线上 bot 仍按旧权限运行，这也是「明明配了却报权限不足」的常见原因。个人自建应用改动即时生效，企业应用改动通常要走管理员审批后生效。[^c6-1]

## 6.3 消息发送能力：send 与媒体

Hermes 对飞书暴露了一套统一的发送能力，底层自动映射到飞书消息类型：

| 能力 | 说明 | 注意点 |
|---|---|---|
| `send` | 文本 / markdown | markdown 自动探测 rich post，被拒则回退纯文本 |
| `send_image` | 发图片 | 前置需 `im:resource` 才能「先收后发」 |
| `send_document` | 发文件 | 受飞书文件大小上限约束 |
| `send_voice` | 发语音 | — |
| `send_video` | 发视频 | — |
| `send_animation` | 发动画 / GIF | **GIF 会降级为普通文件**发送 |

> [!tip] 大白话
> `send` 的 markdown 自动探测像「双保险」：bot 先试着用带格式的富文本卡片发，若目标场景不支持（如某些群没开富文本），就自动降级成纯文本重发。所以看到「post 变纯文本」**不是故障**，而是保险丝熔断后的正常兜底，见 6.5。

需要提醒：发图片前一般得先「收到」过资源（用户在飞书里发给 bot 的图），而收资源依赖 `im:resource` scope——这也是五件套必须配齐的原因之一。飞书对文件类消息有出站上限（图片、文件、视频各自有体积上限，超限会被平台拒绝），所以大文件发送失败时先怀疑体积，而不是配置。[^c6-1]

> [!example] 一个完整链路
> 用户群里 @ bot 说「把刚才那张图发给我」→ `im.message.receive_v1` 把消息连同图片 resource 推给 bot（靠 `im:message` + `im:resource` 才能读）→ bot 用 `send_image` 把同一张图发回群里（靠 `im:message:send_as_bot` 才有资格发）。一次普通对话，背后其实动用了五件套里的三把钥匙。

## 6.4 产物 H：`config.yaml` 的 `platforms.feishu` 片段

先睹为快，完整片段如下：

```yaml
# ~/.hermes/config.yaml
platforms:
  feishu:
    enabled: true               # 开启飞书平台
    connection_mode: websocket  # websocket | webhook，默认 websocket（对应第 5 章两种连接方式）
    group_policy: allowlist     # open | allowlist | disabled，群聊门禁
    allowed_users:              # 只允许这些用户触发 bot（open_id，从开放平台获取）
      - "ou_xxxxxxxxxxxx"
      - "ou_yyyyyyyyyyyy"
    require_mention: true       # 群聊中必须 @ bot 才响应（true 防误触刷屏）
    home_channel: ""            # 默认消息投递的 chat_id，可留空
```

逐段拆讲：

- `connection_mode`：与第 5 章的 `CONNECTION_MODE` 对应，`websocket` 免公网、推荐；切 `webhook` 需要公网可达端点。
- `group_policy`：群聊门禁。`open` = 所有群都能响应；`allowlist` = 只响应名单内群/用户；`disabled` = 完全不理群消息。刚上手建议先 `allowlist`。
- `allowed_users`：允许名单，填用户的 `open_id`（在开放平台「用户列表」或消息 payload 里能拿到）。**只留自己人，别开 `open` 裸奔**。
- `require_mention: true`：群聊里要求必须 @ bot 才响应。开着能大幅减少误触和风控风险。
- `home_channel`：bot 的「默认回家地址」，指定默认消息投递目标，可留空。[^c6-2]

> [!tip] 大白话
> `REQUIRE_MENTION` 就像「不叫我，我不理你」：群里人多口杂，开着它 bot 只在被 @ 时才回应，不被无关消息刷屏；`GROUP_POLICY` 是群聊门禁，决定哪些群 bot 能进、能聊。两个一起配，等于给 bot 上了「群聊双保险」。

## 6.5 已知坑

> [!warning] 坑 1：同 app_id 只能跑一个实例
> 一个 `FEISHU_APP_ID` 同时只能有一个活跃长连接。你用同一个 app_id 起了两个 gateway 容器（比如第 2 章两个 gateway 共享数据目录的坑，或升级后旧容器没删），飞书平台会判定后者顶掉前者，结果**两边都收不到消息**。排查先 `docker ps` 看有没有残留容器，升级时务必先停旧容器再起新的。

> [!warning] 坑 2：群聊不响应 → 按顺序三连查
> 私聊正常、群聊死活没反应时，依次检查：① 有没有 @ bot（`REQUIRE_MENTION: true` 时没 @ 默认不理你）；② `group_policy` 是不是把该群挡掉了（`disabled` 直接全挡、`allowlist` 只放行名单）；③ `allowed_users` 名单里有没有群成员。三个环节任一不满足，bot 都会「装死」。按这个顺序排查，比瞎改配置快得多。

> [!warning] 坑 3：点按钮报 200340
> 点交互卡按钮返回错误码 200340 = 应用没开「交互卡片」（Interactive Card）能力。去开放平台应用后台把交互卡片能力打开、重新发布，再回来点按钮。

> [!warning] 坑 4：post 变纯文本
> 这**不是 bug**，是 6.3 讲的正常回退：markdown 探测到富文本 post 不被支持时，自动降级成纯文本发送。不用改配置，理解它是兜底机制即可。[^c6-1][^c6-3]

## 本章小结

- 事件订阅是「收」的开关：`im.message.receive_v1` 必选，`card.action.trigger` 做交互卡才需要。
- 权限五件套是「发」的资格：`im:message`、`im:message:send_as_bot`、`im:resource`、`im:chat`、`im:chat:readonly` 缺一不可，且缺权限通常静默失败、不报错。
- 发送能力里 markdown 自动探测富文本、失败回退纯文本；GIF 走 `send_animation` 会降级为文件。
- `config.yaml` 的 `platforms.feishu` 片段用 `connection_mode` / `group_policy` / `allowed_users` / `require_mention` 四键控制连接、群聊门禁和 @ 触发。
- 四个高频坑：同 app_id 只能一个实例、群聊不响应三连查、200340 = 未开交互卡片、post 变纯文本 = 正常回退。
