## 第一章：先搞懂 lunatv 的「源」机制

你已经把 lunatv 部署起来了，但打开首页大概率是一片空白——别慌，这是正常的。lunatv 天生是一个「空壳聚合播放器」，它自己不存任何视频，一切内容都来自你接进来的「源」。这一章我们先不上手，把「源」这套机制讲明白：它长什么样、影视站要满足什么条件才能接入、怎么一次性订阅一堆源。概念通了，后面第三章的实操才不会懵。

### 1.1 LunaTV 是什么：空壳聚合播放器

先记住一句话：**lunatv 不存储视频，它只负责聚合和播放**。[^c1-1] 项目定位上，它 fork 自 SzeMeng76/LunaTV，基于 MoonTV 深度二开，从 v4.3.1 一路迭代到 v6.6.2，累计 60+ 功能。[^c1-2]

「聚合」体现在它的内容生态上（#B1）：

| 内容类型 | 说明 |
|---|---|
| 网盘搜索 | 聚合网盘直链资源 |
| ACG 种子搜索 | 接入 Mikan 等番剧种子站 |
| IPTV 直播 | 支持 m3u/m3u8、FLV、EPG 电子节目单 |
| Emby 私有库 | 挂自己的 Emby 媒体库 |
| YouTube / Bilibili / Bangumi | 直接接入对应平台 |
| 短剧 | 聚合短剧资源 |

> [!tip] 大白话
> 把 lunatv 想成「电视遥控器」：它自己不生产任何节目，只是把一个个「频道」（也就是源）切到你面前。所以部署完打开首页一片空白是正常的——遥控器还没接上任何频道。

关键含义：**部署完的 lunatv 只是一个空壳，内容源需要你之后在管理后台运行时添加**，不需要改代码、也不用重启。[^c1-3] 后面所有操作，都是往这个空壳里「接源」。

### 1.2 核心源格式：api_site JSON

lunatv 的源配置文件是一段内嵌的 JSON，核心是一个叫 `api_site` 的对象，它是「源标识 → 源配置」的映射。[^c1-4] 每个源对象有 4 个字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `key` | 是 | 唯一标识，仅小写字母和数字；`openlist`、`xiaoya`、`emby*` 前缀为保留名（#B3） |
| `api` | 是 | 资源站的 vod JSON API 地址，支持苹果 CMS V10 格式 |
| `name` | 是 | 界面上显示的源名称 |
| `detail` | 否 | 网页详情页的根 URL |

顶层还有两个常用字段：`cache_time` 是接口缓存秒数（建议 3600–7200），`custom_category` 是数组，每项含 `name`/`type`/`query`，用于豆瓣搜索分类。[^c1-4]

一个完整的 `api_site` JSON 长这样（`mysite` 为示例占位，实际请换成你的真实站）：

```json
{
  "cache_time": 7200,
  "api_site": {
    "example_source": {
      "api": "http://example.com/api.php/provide/vod",
      "name": "示例资源站",
      "detail": "http://example.com"
    },
    "mysite": {
      "api": "https://mystation.example.com/api.php/provide/vod",
      "name": "我的影视站"
    }
  }
}
```

`key` 就是 `api_site` 里的键名（`example_source`、`mysite`），全局唯一；`name` 是你在界面上看到的名字。`detail` 可不写，比如第二个源就只填了必填的 `api` 和 `name`。

> [!tip] 大白话
> 把 `api_site` 想成一份「点菜单」：每个源就是一道菜，`api` 是去哪家后厨取菜（数据接口），`name` 是菜名。往配置里加一个源，就是在点菜单上添一道菜。

> [!tip] 大白话
> 把 `cache_time` 想成「冰箱冷藏时间」：接口数据取回来后先放冰箱 1–2 小时，不每次都去源站问。设 3600–7200 秒，能明显减轻源站压力、加快加载。

### 1.3 影视站接入标准：苹果CMS V10 接口

不是任何网站都能接入 lunatv。绝大多数国内影视站用的是**苹果CMS**（MacCMS），lunatv 的 `api` 字段支持的就是苹果 CMS V10 的 vod JSON 接口。[^c1-5]

接口标准（#B2）：

- 基础地址格式：`https://域名/api.php/provide/vod/`（注意带尾斜杠）
- `from` 参数以**路径段**追加，只返回该播放源的数据：`/api.php/provide/vod/from/m3u8/`
- 返回 JSON 关键字段：`vod_play_from`（播放源名，逗号分隔）、`type_name`（分类名）

一个实际的接口地址长这样：

```text
# 该站全部视频数据接口
https://example.com/api.php/provide/vod/

# 只取 m3u8 播放源的数据（from 以路径段追加）
https://example.com/api.php/provide/vod/from/m3u8/
```

> 说明：`from` 参数 B2 官方文档用路径段形式；部分资料把它写成 query 参数（如 `?from=m3u8`）。两种可能都被支持，具体以源站实现为准。

#### 怎么判断一个影视站能不能接入

非常简单：浏览器直接打开它的接口地址，如果返回一段 JSON，说明接口正常、可以接入。[^c1-6] 这是后面第二章「找站」的核心判据。

> [!tip] 大白话
> 把苹果CMS V10 想成「行业统一的插座规格」：影视站只要按这个规格预留好插座（接口），lunatv 这个插头插上就能通电。所以判断一个站能不能接，就去看它有没有这个插座——浏览器打开接口地址，返回 JSON 就有电。

### 1.4 远程订阅与多源聚合

一个个手动加源太累了，lunatv 支持**远程订阅**：把别人维护好的一大份源配置，用一条订阅 URL 拉回来。[^c1-7]

拉取和合并的链路（#B3）：

1. 客户端向 `POST /api/admin/config_subscription/fetch` 提交远程 URL
2. 拿到响应文本后做 `bs58.decode` 解码
3. 用 `TextDecoder` 转成 UTF-8 字符串
4. 存入数据库的 `ConfigFile` 字段
5. 更新时校验 JSON 语法，再通过 `refineConfig` 把外部源**合并进活跃配置**

因为订阅内容常用 **Base58 编码的 JSON** 来传输，所以订阅链接看起来是一串短码而不是明文 JSON。[^c1-8]

聚合到同一份配置后，每个源还有几个扩展字段控制行为（#B3）：

| 字段 | 取值 | 作用 |
|---|---|---|
| `from` | `config` / `custom` | 标记源是订阅导入还是手动添加 |
| `disabled` | true/false | 设为 true 时从搜索中排除该源 |
| `proxyMode` | true/false | 服务端代理 M3U8+TS 分片，解决跨域/被墙 |
| `weight` | 0–100 | 搜索权重，数值越高结果排越前 |

> [!tip] 大白话
> 把远程订阅想成「朋友发给你的点菜单」：不用自己一个个菜名敲进去，拉取一下整份菜单就自动合并进你的点菜单。所以一键订阅 = 批量加源，后面第三章会手把手走一遍。

### 本章小结

- lunatv 是**空壳聚合播放器**，不存视频，内容全靠「源」；部署完首页空白是正常的。[^c1-1]
- 源配置的核心是 **`api_site` JSON**：每个源要 `key`（唯一标识）、`api`（必填接口）、`name`（必填显示名），`detail` 可选；顶层 `cache_time` 建议 3600–7200。[^c1-4]
- 影视站的接入标准是 **苹果CMS V10 接口**，浏览器打开 `/api.php/provide/vod/` 返回 JSON 即可接入。[^c1-6]
- 多源可以靠 **远程订阅** 批量导入：Base58 解码 → UTF-8 → 存库 → `refineConfig` 合并。[^c1-7]
- 每个源还有 `weight`/`disabled`/`proxyMode` 等扩展字段，用来控制搜索权重、排除与代理。[^c1-9]

下一章我们就要真正动手找源了：怎么判断一个影视站能不能接入、有哪些现成的订阅源可以直接用，以及怎么用健康检测数据挑出靠谱的源。

带着「源」机制的完整图景，我们把视角从「它是什么」转向「去哪里找、怎么挑」。

## 第二章：找到能导入的影视站

上一章讲清了 lunatv 的「源」机制：它本身是空壳，靠 `api_site` JSON 把一个个影视站聚合进来。本章解决一个更实际的问题——**上哪儿找源、怎么判断一个站能不能接入、以及怎么在几十个源里挑出能用的**。读完你会得到一套可复制的「验源三步法」：先验接口、再用现成订阅源、最后用健康检测数据定夺。

### 2.1 判断一个影视站能否接入：一条 URL 见分晓

判断标准其实一句话就能说清：

> 在浏览器打开 `https://影视站域名/api.php/provide/vod/`，**返回 JSON 就是可接入**，返回 404、空白或报错页面就是不行。[^c2-1]

为什么是这个地址？因为 lunatv 支持的资源站接口是**苹果CMS V10（MacCMS V10）**标准[^c2-2]，这个标准把视频接口固定放在 `/api.php/provide/vod/` 路径下（注意带尾斜杠）。只要这个站点是用苹果 CMS 搭的，接口地址就是同一套格式，这也是 lunatv 能批量聚合几十个站点的底层原因——大家共用一套协议，插件式接入。

具体验证步骤如下：

```text
# 苹果CMS V10 接口验证 URL（浏览器直接打开）
https://影视站域名/api.php/provide/vod/

# 返回结果示意：一段 JSON，包含分类与视频列表信息
{
  "code": 1,
  "msg": "数据列表",
  "page": 1,
  "pagecount": 10,
  "limit": "20",
  "total": 200,
  "list": [ ... ]
}
```

验证时有两个进阶点，可以顺手确认：

- 接口只返回指定播放源：在路径后追加 `from` 段，例如 `/api.php/provide/vod/from/m3u8/`，就只返回该播放源的数据[^c2-1]。
- 返回 JSON 里两个关键字段：`vod_play_from`（该片有哪些播放源，逗号分隔）和 `type_name`（分类名）[^c2-1]。lunatv 播放页的「换源」列表，就是靠 `vod_play_from` 拼出来的。

> [!tip] 大白话
> 把影视站想成一个「自来水厂」，`/api.php/provide/vod/` 就是它对外公开的**出水口阀门**。你打开这个阀门看到水流（JSON 数据），就说明水厂能正常供水、lunatv 能直接接上；阀门拧开是干的（404/报错），那这个厂要么没开、要么不是苹果 CMS 体系，换一家吧。

### 2.2 现成订阅源：三档配置一次到位

如果不想自己一个个验证站点，可以直接用社区维护好的**现成订阅源**。社区项目 `hafrey1/LunaTV-config` 维护了三档配置，按「是否含成人内容」区分，按需选择[^c2-3]：

| 档位 | 说明 | 内置源数量（README 口径） |
| --- | --- | --- |
| `jin18` | 无成人内容 | 31 |
| `jingjian` | 含成人内容（精简版） | 61 |
| `full` | 含成人内容（全量版） | 88 |

每个档位对应两种订阅 URL：

1. **直链**：直接指向 GitHub raw 文件（`raw.githubusercontent.com/...`），适合能直连 GitHub 的网络环境。
2. **Base58 中转**：第三方把配置编码后用短链分发，适合不方便直连 GitHub 的环境。例如：

```text
# Base58 中转订阅 URL（format=2 表示 Base58 编码，source=jin18 选档位）
https://pz.v88.qzz.io?format=2&source=jin18
```

> [!tip] 大白话
> 把订阅 URL 想成一份**打包好的「可导入清单」**：别人已经把几十个影视站的地址、名字、分类都整理好了，你只需把这条 URL 粘进 lunatv，它就会自动把清单拆开、装进你的空壳里。`source=jin18/jingjian/full` 就是「我要无成人的」「我要精简含成人的」「我要全量含成人的」三种口味。

这里有一个值得注意的建议：**中转依赖第三方服务，推荐自己部署代理来维护订阅源**（自部署方式在第五章展开）[^c2-3]。因为第三方中转如果下线，你的配置就断了；自部署代理则把这份「清单分发」掌握在自己手里。另外素材里有个口径差异需要留意：A4 README 自述 jingjian=61，但正文又称「去除污染源后剩 57 个可用源」——**具体源数可能随维护更新变化，以实际拉取到的配置为准（待验证）**。

### 2.3 用健康检测挑源：别把失效站当宝贝

订阅源导入后，源并不是永久的。社区给出的健康检测报告（统计于 2026-08-25）提供了最真实的挑源依据[^c2-4]：

- **总体可用率约 92%**：共检测 72 个源，可用 65 个、不可用 7 个。其中 100% 可用 39 个，80–99% 档 29 个，50–79% 档仅 1 个（虎牙 76.7%），低于 50% 档 3 个。
- **完全失效源（30 次检测全失败）**：飘零资源、百万资源、丝袜资源。
- **连通但搜索无结果**：豆瓣资源、茅台资源、杏吧、色猫；另有「大地资源」属于接口不匹配（不是标准苹果 CMS 格式）。

把这些数据翻译成选源策略，就是三句话：

1. **优先选 100% 可用档**的源，它们的稳定性最好；
2. **避开完全失效名单**（飘零/百万/丝袜）和**连通但搜不到东西**的源（豆瓣/茅台/杏吧/色猫）——连得上不代表有内容，后者更坑，因为它不报错但永远搜不出结果；
3. **源失效是常态，要定期更新**。健康报告是 2026-08-25 的，今天能用的源明天可能就挂，反过来新的好源也可能不断出现。建议把「定期拉取一次订阅配置」当成和「给手机充电」一样的例行公事[^c2-4]。

> [!tip] 大白话
> 把影视源想成小区门口的小吃摊：**今天出摊（可用）不代表永远出摊**。有的摊子彻底关门了（飘零/百万/丝袜），有的摊子人还在但锅里没东西（豆瓣/茅台/杏吧/色猫——连得上但搜不出内容）。聪明的做法是记住哪几家生意最稳定（100% 可用档），并且每隔一阵去街上重看一圈（定期更新订阅），别守着一家关门摊干等。

### 本章小结

- 判断影视站能否接入，浏览器打开 `站点/api.php/provide/vod/`，返回 JSON 即可接入（苹果 CMS V10 标准）。
- 不想自己逐个验站，直接用社区维护的三档订阅源：`jin18`（无成人）、`jingjian`（含成人精简）、`full`（含成人全量）。
- 订阅 URL 分直链和 Base58 中转两种，`format=2` 表示 Base58 编码；中转依赖第三方，推荐自部署代理（第五章详解）。
- 健康检测显示总源可用率约 92%；完全失效：飘零/百万/丝袜资源；连通但无结果：豆瓣/茅台/杏吧/色猫。
- 选源策略：优先 100% 可用档、避开失效名单、定期更新订阅——**源失效是常态**。

### 下一章预告

源已经找到、也验过了，下一步就是把它们真正**导进 lunatv**。第三章讲核心实操：登录管理后台、用订阅 URL 一键导入、以及手动在 `api_site` JSON 里加单个站——记住那个最容易翻车的一步：**点完「拉取配置」一定要点「保存」**。

## 第三章：把影视站导入 lunatv（核心实操）

前面两章我们搞清楚了 lunatv 的「源」机制（`api_site` JSON、苹果 CMS V10 接口、远程订阅），也学会了怎么判断一个影视站能不能接入。但概念懂了不等于能播放——这一章我们把「找到的影视站」真正装进你本地部署的 lunatv，走完「登录 → 导入 → 保存 → 播放」全流程。这是整个笔记里最关键的一章，请跟着一步步照抄。

> [!tip] 大白话
> 把 lunatv 想成一台「空壳电视机」：它自己不存任何节目，前面两章学到的各种源（资源站、订阅清单）就是一个个「频道包」。这一章做的事，就是把这台电视机的「频道包」装进去——装对了，打开就有节目；装错了或忘了按「保存」，电视还是空的。

### 3.1 准备：登录管理后台

lunatv 的一切配置（加源、换源、调代理）都在**管理后台**里完成，不需要改代码、也不需要重启容器。[^c3-1]

**入口**：在浏览器打开 `http://你的地址:3000/admin`（如果你改了端口映射，把 `3000` 换成实际端口）。

**默认账号取决于你的部署方式**，这里最容易出现分歧，先说清楚：[^c3-2]

| 部署方式 | 默认账号 | 说明 |
| --- | --- | --- |
| 懒猫微服打包版 | `admin` / `admin123` | 懒猫社区教程默认用这套账号 |
| Docker Compose / 自行部署 | 由环境变量 `USERNAME` / `PASSWORD` 决定 | 部署时自设，一般没有「默认密码」这回事 |

> [!warning] 易错点
> 网上教程说「默认 admin/admin123」，但那只对懒猫打包版成立。如果你是 Compose 部署，登录失败时先回想部署时设的 `USERNAME` / `PASSWORD`，别在 admin123 上死磕。

如果你部署时用的是 Compose 方式，去当时的 `docker-compose.yml` 里查看 lunatv 服务段的环境变量，形如：[^c3-3]

```yaml
# docker-compose.yml（lunatv 服务环境变量节选）
services:
  lunatv:
    environment:
      USERNAME: your_admin_name          # 管理后台登录名
      PASSWORD: your_strong_password     # 管理后台登录密码
      NEXT_PUBLIC_STORAGE_TYPE: kvrocks  # 存储类型：kvrocks / redis / upstash
```

这里 `USERNAME` 和 `PASSWORD` 就是管理后台的登录凭证；`NEXT_PUBLIC_STORAGE_TYPE` 决定配置、缓存数据存在哪个存储——Compose 本地部署一般用 `kvrocks` 或 `redis`，Vercel 云上多用 `upstash`。这三项是部署时的**必填环境变量**；除了登录凭证，它直接关系到配置能不能写进去（比如源配置、订阅内容都存这）。[^c3-3]

> [!tip] 大白话
> 管理后台相当于这家「空壳电视机公司」的**控制室**：正式员工（站长账号）刷卡进门，一切进货、换频道、调代理都在这个房间里操作。`/admin` 入口就是控制室的门牌号。

登录成功后，你会进到一个**首页暂时是空白**的界面——别慌，这是正常的，因为还没有任何源。管理面板里模块很多（站点、用户、视频源、直播源、分类、网盘搜索、AI 推荐、YouTube、TVBox 安全、缓存等），我们这一章只关心 **配置文件** 和 **站点配置** 两个模块。[^c3-1] 接下来就用两种方法之一把源装进去。

（登录失败的其他原因——比如存储没起来、Redis/Kvrocks 连不上——属于部署环境问题，第四章排错再展开，先继续。）

### 3.2 方法一：订阅 URL 导入（推荐）

如果手里有一个「现成的订阅链接」（通常来自社区分享或现成源清单），方法一是最省事的：一条 URL 就能把几十个影视源一次性装进来，之后还能**自动更新**，源失效时不用手动一个个换。

#### 3.2.1 操作步骤（照抄）

进管理后台后，按下面的路径一步步点：[^c3-4]

1. 右上角人像图标 → **管理面板**；
2. 左侧选 **配置文件**；
3. 在 **订阅URL** 输入框粘贴订阅链接；
4. 打开 **「自动更新」** 开关——开启后 lunatv 会定期去订阅地址重新拉取最新配置，正好对抗「源失效是常态」的问题（选源策略见 2.3 与 A4 健康报告）；
5. 点 **「拉取配置」** 按钮，等待返回；
6. **点页面上的「保存」** ← 这一步最容易漏，见 3.2.3；
7. 拉取成功后，页面上会显示**拉取到的配置代码**（一段 JSON），看到它就说明导入成功了，可以回首页刷新验证。

#### 3.2.2 订阅 URL 从哪来

订阅 URL 本质是一个指向「配置清单」的远程地址。社区维护的现成源清单（以 LunaTV-config 为例）提供三档，按需选择：[^c3-5]

| 档位 | 源数量 | 是否含成人内容 | 用途 |
| --- | --- | --- | --- |
| `jin18` | 31 | 否 | 无成人，适合公共场合 / 家庭默认 |
| `jingjian` | 61 | 含 | 精简版，含成人 |
| `full` | 88 | 含 | 全量版，含成人 |

对应的订阅 URL 示例（Base58 中转形式）：[^c3-5]

```text
# 订阅 URL 示例（三选一）
https://pz.v88.qzz.io?format=2&source=jin18
https://pz.v88.qzz.io?format=2&source=jingjian
https://pz.v88.qzz.io?format=2&source=full
```

> [!warning] 易错点
> 上面这个 `pz.v88.qzz.io` 是**第三方 Base58 中转服务**，属于社区维护、随时可能挂的类型，素材里明确**推荐自部署代理**。另外 `format=2` 表示输出 Base58 编码，`source=jin18` 表示取哪一档配置——不同中转服务的参数不一样，照抄前先看对方文档。

订阅 URL 也可以是 `raw.githubusercontent.com` 上的直链配置 JSON。但订阅协议约定：下发内容要经过 **Base58 编码**再交给 lunatv 解码（详见下方技术细节），所以直接贴普通 JSON 地址不一定管用——中转服务的价值就是把「编码」这步替你做好了。[^c3-6]

#### 3.2.3 关键：点「保存」

这一步是整个章节最重要的提醒，素材里被连续强调了两遍：

> 粘贴订阅 URL → 打开「自动更新」→ 点「拉取配置」之后，**必须再点一次「保存」**，否则配置不生效。[^c3-4]

背后的逻辑是：**「拉取配置」只是把远程配置下载到临时态，点「保存」才把它落盘写入生效配置**。很多人拉取成功、看到配置代码弹出就以为完事了，结果回首页还是空白——就是漏了「保存」。

> [!tip] 大白话
> 把「拉取配置」想成**先把进货单从仓库调出来给你看**，「保存」才是**签字盖章确认进货**。光调出来看一眼，库房不会真的上货。所以看到配置代码弹出后，请务必再点一次保存。

技术细节（了解即可，不影响操作）：订阅拉取是向后端发 `POST /api/admin/config_subscription/fetch` 请求，把返回文本用 Base58 解码（`bs58.decode`）再转成 UTF-8 字符串，校验 JSON 语法后通过 `refineConfig` **合并进当前活跃配置**。[^c3-6] 注意是「合并」而不是「覆盖」——订阅导入不会清空你已经手动加的源，而是叠加，这点对手动加源（方法二）很有用。

### 3.3 方法二：手动添加单个站

场景：你手头没有现成订阅链接，只想把某一个具体的影视站（比如一个苹果 CMS V10 的资源站）单独加进来。那就用方法二：直接往配置文件的 `api_site` JSON 里加一个「源对象」。

> [!tip] 大白话
> 一个「源对象」就是一张**登记表**：表上两格必填——`api`（这个站的接口地址，相当于「送货地址」）和 `name`（界面上显示的名字，相当于「店铺招牌」）。你把表填好交进控制室，lunatv 就知道去哪进货了。

#### 3.3.1 操作步骤

1. 管理后台 → 管理面板 → **配置文件**（同上）；
2. 找到配置编辑区里的 `api_site` 部分（它是一个 `{ "源标识": { ... } }` 的键值对集合，订阅导入后这里会有一堆对象）；
3. 在集合里**追加一个源对象**，`api` 和 `name` 必填；
4. 点 **「保存」**（对，又是保存，别忘）。

#### 3.3.2 源对象长什么样

下面是一个**最小可用的完整配置示例**（也就是管理后台 → 配置文件编辑区的内容，先睹为快）：[^c3-7]

```json
{
  "cache_time": 7200,
  "api_site": {
    "my_new_site": {
      "api": "https://example.com/api.php/provide/vod/",
      "name": "我的影视站",
      "detail": "https://example.com"
    }
  }
}
```

各字段含义：[^c3-7]

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `key`（对象名，如上例 `my_new_site`） | 是 | 源的唯一标识；**仅允许小写字母和数字** |
| `api` | 是 | 资源站 vod JSON API 地址，支持苹果 CMS V10 格式（`/api.php/provide/vod/`） |
| `name` | 是 | 界面上显示的名称 |
| `detail` | 否 | 网页详情页根 URL（点进详情时跳转用） |

顶层 `cache_time` 是接口缓存秒数，素材建议设 `3600`–`7200`（1–2 小时）：设短了频繁请求接口，设长了源更新不及时。[^c3-7]

> [!warning] 易错点
> 如果你已经通过订阅导入了源，`api_site` 下已经有多个对象。手动加源时，新对象要和已有对象之间**用英文逗号隔开**。JSON 里漏逗号、多逗号、用中文引号，都会导致整个配置文件加载失败（连之前订阅的源一起失效）。加完务必仔细检查一遍语法再保存。

补充一个命名小知识（进阶）：`key` 有一些保留名不能随便用，比如 `openlist`、`xiaoya`、以及 `emby` 开头的名字——它们通常对应 lunatv 内置的特殊源逻辑。手动加源时避开这几个前缀即可。[^c3-6]

#### 3.3.3 判断你的影视站接口是否合格

手动加源的 `api` 地址必须指向**苹果 CMS V10 接口**。拿不准时，先在浏览器直接打开（带尾斜杠）：[^c3-8]

```text
# 验证影视站接口是否可用（浏览器直接打开）
https://你的影视站域名/api.php/provide/vod/
```

如果浏览器返回一段 JSON（而不是报错页或 404），说明接口正常，可以把这段地址作为 `api` 字段值填进去。[^c3-8] 如果打不开或返回的不是 JSON，这站进不了 lunatv——先别加，回第二章看看还有没有别的候选站。

> [!tip] 大白话
> 这一步相当于**收货前验货**：你先去仓库门口看看有没有人应门、门口挂的是不是公司招牌（JSON），确认是正牌货再填登记表。接口打不开的站，登记表填了也白填。

### 3.4 验证与播放

源导入并保存后，回首页做一次「验收」：[^c3-9]

1. **刷新首页**：首页从空白变成有内容 / 有分类入口，说明源已生效；
2. **搜索**：搜一个你想看的片名，能出结果就说明源数据进来了；
3. **点开播放**：进详情页点播放；
4. **换源**：如果默认源卡顿、画质差或播不了，在播放页找「换源」按钮切换其他播放源。

#### 3.4.1 换源与「无测速数据」

换源是 lunatv 用户的基本生存技能。素材里的健康检测报告显示：总源 72 个中，可用 65 个、不可用 7 个，平均可用率约 92%——也就是说**源失效是常态**，一个源挂了还有几十个可以换。[^c3-10]

> [!tip] 大白话
> 换源就像电视遥控器**切频道**：这个频道没信号（源失效），按一下遥控器换到别的台（别的源）接着看，不用重新装电视。lunatv 把几十个源的搜索结果聚在一起，正是为了让你有「台」可切。

播放页如果出现「**无测速数据**」红字，基本等于这个源当前不可用——不是网速慢，是该源失联了，直接换源比死等更实际。[^c3-10]

#### 3.4.2 站点配置：豆瓣代理（刮削海报 / 评分）

想让首页和详情页有海报、评分这些漂亮数据（俗称「刮削」），lunatv 默认会去豆瓣拉取。这一步在管理后台的**站点配置**里完成：[^c3-4][^c3-9]

1. 管理面板 → **站点配置**；
2. 分别设置 **「豆瓣图片代理」** 和 **「豆瓣数据代理」**（源清单或社区有推荐值就照填，具体代理值见第四章）；
3. 设好后**再次点「保存」**；
4. 回首页刷新查看效果。

> [!warning] 易错点
> 豆瓣代理这个坑**可能没有被完全根治**：素材里懒猫社区评论区有用户反馈「试了全部选项仍提示获取豆瓣分类数据失败」。[^c3-11] 如果你遇到同样问题，先别怀疑是自己操作错了——先确认源已经生效（能搜能播），海报 / 评分属于锦上添花，放后面排错。

> [!tip] 大白话
> 刮削就像给货架**贴标签**：源把「货」（视频数据）送来了，但货架上有没有好看的海报和评分，得靠豆瓣这个「外包美工」来贴。美工下班了（豆瓣被墙 / 代理没配好），货照样能卖（能播），就是货架丑一点。

### 本章小结

- 一切配置在**管理后台**完成（`/admin`，账号取决于部署方式：懒猫版 `admin/admin123`，Compose 自设 `USERNAME`/`PASSWORD`），不用改代码、不用重启。
- **方法一（订阅 URL，推荐）**：管理面板 → 配置文件 → 贴订阅 URL → 开「自动更新」→ 拉取配置 → **记得保存**。忘保存是第一大坑。
- **方法二（手动加源）**：在 `api_site` JSON 里追加源对象，`api`（苹果 CMS V10 接口地址）和 `name` 必填；注意 JSON 逗号 / 引号 / 命名保留字。
- 验收四步：刷新首页 → 搜索 → 播放 → 换源；「无测速数据」红字 = 该源失效，直接换源。
- 豆瓣代理设好后再保存一次；该坑可能未根治，不影响播放就先放着。

下一章我们把这一路踩过的坑系统整理一遍：配置不生效、源失效、刮削失败、部署环境问题（登录 / 端口 / 镜像 / 存储），到时候遇到问题可以直接对号入座。

导入实操走通之后，真实环境里反复出现的坑需要一个系统的排错清单。

## 第四章：常见坑与排错

前三章把「找站 → 导入 → 播放」的主线走通了，但真实环境里总有几个坑反复出现：配置明明填了却不生效、源突然看不了、海报刮削不出来、部署阶段各种「起不来」。本章不按流程讲，而是按**「现象 → 原因 → 解法」**把四个最高频的坑排开，遇到问题直接对号入座，不用从头读。

---

### 4.1 配置不生效：忘了点「保存」

#### 现象
在管理后台粘贴了订阅 URL，点了「拉取配置」，页面也显示了配置代码，但回首页还是空白：没有片源列表，搜索也搜不到任何内容。

#### 原因
「拉取配置」只是把远程配置**拉到页面里展示**，还没有真正写入运行中的配置。官方文档说明配置是在管理后台运行时填写、无需改代码重启，但写入动作依赖最后那一下「保存」[^c4-5]。社区唯一的完整实操教程里两次强调：忘点保存是配置不生效的**第一大坑**——「拉取」和「保存」是两步，缺一不可[^c4-1]。

> [!tip] 大白话
> 把「拉取配置」想成把快递搬进屋里，「保存」想成签收确认。没签收，快递员以为你没要，货就不会登记进系统。所以搬完快递（拉取）之后，一定要签收（点保存），配置才算真正生效。

#### 解法
1. 进入管理后台 → 配置文件。
2. 在订阅 URL 处粘贴订阅链接，打开「自动更新」。
3. 点「拉取配置」。
4. **点「保存」**。
5. 判断成功标准：拉取成功后页面显示配置代码，即配置已写入[^c4-1]。

> [!warning] 易错点
> 看到配置代码 ≠ 保存成功。保存后再回首页刷新，如果能刷出片源列表，才算真生效。养成「拉取完顺手点保存」的习惯，能省下大半排错时间。

---

### 4.2 源失效：换源与健康检测

#### 现象
点开某部片子一直转圈、无法播放，播放页出现**「无测速数据」**红字。

#### 原因
「无测速数据」红字 = 这个源当前不可用。源失效不是偶发，而是**常态**：一份 2026-08-25 的健康报告显示，72 个源里有 7 个不可用，平均可用率约 92%；更糟的是有些源会彻底死掉，30 次检测全部失败[^c4-2]。

> [!tip] 大白话
> 把「源」想成外卖店，「测速」想成下单前试接单。「无测速数据」就是这家店没人接单——不是你的问题，是店没营业。别死磕一家，换一家（换源），或先看评分（健康报告）再下单。

#### 解法
1. **播放页「换源」**：在播放器或详情页找到「换源」入口，切换到该片子的其他播放源[^c4-3]。
2. **用健康报告挑源**：挑订阅源时避开两类[^c4-2]——
   - 完全失效源：如飘零资源、百万资源、丝袜资源（30 次检测全失败）；
   - 连通但搜索无结果的源：如豆瓣资源、茅台资源、杏吧、色猫；大地资源则属于「不匹配」。
3. **定期更新配置**：因为源失效是常态，每隔一段时间重新拉取一次订阅、保存配置，能自动换上一批新源[^c4-2]。

> [!warning] 易错点
> 一个源「搜索不出结果」不一定代表网站挂了，也可能是「连通但无数据」。先用浏览器直接打开该源的接口地址：返回 JSON 说明接口正常，问题出在源内容本身，直接换源即可，不必排查半天。

### 4.3 刮削失败：豆瓣代理配置

#### 现象
首页空白、片源列表没有海报封面，或提示「获取豆瓣分类数据失败」。

#### 原因
lunatv 用豆瓣数据来刮削分类和封面。默认直连豆瓣经常失败（受网络环境影响），需要给豆瓣接口配置代理。

#### 解法
1. 进入管理后台 → 站点配置，分别设置「豆瓣图片代理」和「豆瓣数据代理」，设置完**再次保存**[^c4-1]。
2. 一个常见可用值：`cmliussss-cdn-tencent`（腾讯 CDN），出自部署避坑帖的示例配置[^c4-3]。也可以通过环境变量固化，避免每次重配：

```env
# .env 或 docker-compose environment 段
NEXT_PUBLIC_DOUBAN_PROXY_TYPE=cmliussss-cdn-tencent
NEXT_PUBLIC_DOUBAN_IMAGE_PROXY_TYPE=cmliussss-cdn-tencent
```

> [!tip] 大白话
> 把「豆瓣代理」想成给家电配的插座转接器——你家电（豆瓣）的插头跟家里插座不匹配，插上不亮。配代理就是换一个匹配的转接器，接上电（数据）封面就来了。

#### 需要并列呈现的一个坑：可能未根治
配了代理并不保证一定成功。配置技巧文的评论区有人反馈：**「试了全部选项仍提示获取豆瓣分类数据失败」**——也就是说，这个坑在部分版本 / 环境下可能还没根治[^c4-4]。如果你遇到同样情况，结论应是「这是已知未根治问题」，而不是你操作错了。

> [!warning] 易错点
> 不要因为「配了代理还失败」就反复重装系统。先把代理值换几个试一遍；仍然失败就接受该版本可能未根治，去社区搜对应版本反馈，或改用依赖搜索接口而非豆瓣分类的方式获取内容。

### 4.4 部署环境问题

这类问题集中在部署阶段，特征是「没反应」或「起不来」。按症状对号入座：

#### 登录失败：查账号密码与存储
- **现象**：访问 `/admin` 登录进不去。
- **原因**：账号密码由部署方式决定——Compose 部署由环境变量 `USERNAME` / `PASSWORD` 决定（都是必填项），不是固定默认值[^c4-5]；另一可能是存储（Redis / Kvrocks）没连上，登录态写不进去。
- **解法**：先核对 `.env` 里的 `USERNAME` / `PASSWORD`；再检查存储连接变量 `KVROCKS_URL` / `REDIS_URL` 是否可达[^c4-5]。

#### 端口冲突：改宿主侧映射
- **现象**：启动后 Web UI 打不开，或启动时报端口占用。
- **原因**：容器内部固定监听 3000 端口（管理后台入口示例 `http://your-domain:3000/admin`）[^c4-5]，但宿主机上的 3000 可能已被别的程序占用。
- **解法**：改 docker-compose 的**宿主侧**（冒号左边）端口，容器内部不用动：

```yaml
# docker-compose.yml（示意片段，具体镜像与路径以官方仓库 README 为准）
services:
  lunatv:
    image: ghcr.io/moontechlab/lunatv:latest   # 官方镜像名待验证，请以官方 README 为准
    ports:
      - "8080:3000"          # 宿主 8080 → 容器 3000；只改左边即可避开冲突
    environment:
      USERNAME: admin
      PASSWORD: 你的强密码
      NEXT_PUBLIC_STORAGE_TYPE: kvrocks
      KVROCKS_URL: <你的 Kvrocks 连接串>
      NEXT_PUBLIC_DOUBAN_PROXY_TYPE: cmliussss-cdn-tencent   # 见 4.3
    volumes:
      - lunatv-data:/data    # 数据持久化，见下方「数据丢失」
volumes:
  lunatv-data:
```

> [!tip] 大白话
> 端口映射像给房子贴门牌号：屋里房间号（容器 3000）不用改，把门牌（宿主端口）换成 8080，外人走新门就能进。所以端口冲突只动冒号左边，别去改容器内部端口。

#### 镜像拉取失败：配加速器
- **现象**：`docker pull` 卡住或超时，容器一直起不来。
- **原因**：镜像仓库拉取受网络环境影响。
- **解法**：给 Docker 配置镜像加速器（各云厂商有免费加速地址，具体值随环境变化，此处不列死）。加速器地址属于本地环境配置，不要写进共享的 `.env.example`。

#### 数据丢失：查 volumes
- **现象**：容器重建（如 `docker compose up -d` 或重装）后，配置、片源全没了。
- **原因**：容器是「临时房间」，数据如果没有挂载到宿主机，容器一重建就被清空。
- **解法**：确认 compose 里配置了 named volume 或 bind mount（如上例的 `lunatv-data:/data`），并把配置类数据放进挂载目录后再重建容器。

> [!tip] 大白话
> 容器像酒店房间，volumes 像前台保险柜。你不把行李存保险柜（挂 volumes），退房（重建容器）时行李就被清走；存了保险柜，换房间行李还在。所以数据丢失先查 compose 里有没有挂 volumes。

> [!warning] 易错点
> 建议固定排查顺序：登录失败先查密码、再查存储；起不来先查端口映射、再查镜像拉取；配置丢先查 volumes。一次只改一个变量，改完重建容器验证，避免多个改动混在一起找不到根因。

## 第五章：进阶：被墙源中转与扩展生态

> 适用场景：跑通前面几章的基础导入之后，发现有些影视站连不上（被墙/超时），或想让 lunatv 接进更多内容形态。本章为可选进阶，按需学习。

前面几章解决的是「找到站 → 导进来 → 能播放」这条主线。但真实环境里有两个常见需求：一是你精心挑好的源可能因为网络环境连不上，二是 lunatv 的能力远不止「播影视站」。本章先讲怎么用 CORSAPI 中转被墙源、怎么接私有源，最后给一张扩展生态地图。

### 5.1 被墙源中转：CORSAPI

#### 5.1.1 什么时候需要中转

现象：一个影视站接口在浏览器里能正常打开 JSON，但 lunatv 里一直加载失败、或搜索无结果。原因往往不是源坏了，而是你的服务器或设备访问不了这个域名（被墙、海外源、需要特定网络环境才能访问）。

判断方法还是第一章的验证法：先用浏览器直接打开 `站点/api.php/provide/vod/`，能返回 JSON；但放进 lunatv 就是不通。这种情况就轮到中转上场。

#### 5.1.2 原理：Cloudflare Workers 代理

CORSAPI 是一个跑在 Cloudflare Workers 上的代理，核心是一个 `_worker.js`，干两件事[^c5-1]：

1. **API 代理**：把 lunatv 的请求转发给真正的影视站，再把响应拿回来；
2. **api 字段前缀重写**：自动识别源配置里旧的 `?url=` 前缀，替换成新的代理前缀，让所有源都走代理。

> [!tip] 大白话
> 把 CORSAPI 想成「跑腿代购」：你自己进不去的店（被墙源），Cloudflare 的员工（Worker）能进去。你把订单（API 请求）交给它，它买完（拿到数据）再送回给你。源地址换成「代购地址」，就能买到本来买不到的东西。

#### 5.1.3 参数速查

CORSAPI 的核心是订阅 URL 上的四个参数[^c5-1]：

| 参数 | 含义 | 取值示例 |
| --- | --- | --- |
| `?source=` | 选现成的源配置档 | `jin18`（无成人）/ `jingjian`（含成人）/ `full`（含成人） |
| `?format=` | 输出编码方式 | `0` raw / `1` proxy / `2` base58 / `3` proxy-base58 |
| `?url=` | 代理任意一个影视站 API | `?url=https://某站/api.php/provide/vod/` |
| `?prefix=` | 自定义代理前缀 | 接入私有 API / 多 Worker 时使用 |

用法示例：

```text
# 用现成源档 + Base58 编码（订阅链接的常见形态）
https://pz.v88.qzz.io?format=2&source=jin18

# 代理任意一个影视站 API
https://pz.v88.qzz.io?url=https://example.com/api.php/provide/vod/

# 自定义前缀，指向自己的 Worker（格式=1 表示 proxy 编码）
https://pz.v88.qzz.io?source=jin18&format=1&prefix=https://my-worker.workers.dev
```

在 lunatv 里的用法和导入普通订阅源完全一样：管理面板 → 配置文件 → 订阅URL 粘贴上面的链接 → 拉取配置 → **保存**。

#### 5.1.4 限制与成本

中转不是无限量的免费代理，记下这三个数字[^c5-1]：

- **缓存 7200 秒**：同一个接口的响应会被缓存 2 小时，降低回源压力；
- **默认超时 9 秒**：影视站响应超过 9 秒就放弃，慢源会失败；
- **免费额度 10 万次请求/天**：公用的 `pz.v88.qzz.io` 是社区实例，量大或多人使用建议自部署。

> [!tip] 大白话
> 把免费额度想成「公共自行车」：偶尔骑一次（个人小流量）没问题，天天骑、一队人骑（高并发）就会把车借光。所以文档建议自部署——自己租一辆（用自己的 Cloudflare Worker），不限量还更稳。

### 5.2 自建源与私有源

#### 5.2.1 接入私有 API

如果你有自己的影视站 API（自己搭的、或买了别人的私有源），CORSAPI 支持用 `?url=` 直接代理任意接口[^c5-1]。把它包成订阅 URL 填进 lunatv 即可，不需要等社区维护的源清单。

```text
# 把私有 API 包成订阅链接，让 lunatv 走代理访问
https://pz.v88.qzz.io?url=https://your-private-api.com/api.php/provide/vod/
```

#### 5.2.2 多 Worker 与自定义 prefix

一个 Worker 跑多个源时，用 `?prefix=` 指向不同 Worker 地址，让每个 Worker 只代理一部分源，方便隔离和单独管理[^c5-1]。`prefix` 就是前缀重写要替换成的目标前缀——源越多，分开管越省心。

#### 5.2.3 自部署代理（推荐）

素材明确建议：公有中转实例只作演示，**推荐自部署代理**[^c5-1]。部署要点整理如下（素材只给了原理和参数，完整 `_worker.js` 代码与逐步骤属「待验证」，需以 A4 仓库 README 或官方 Workers 文档为准）：

1. 准备一个 Cloudflare 账号（免费版即可）；
2. 新建 Worker，把 `_worker.js` 部署上去；
3. 部署后得到 `https://你的项目.workers.dev` 地址；
4. 把示例里的 `pz.v88.qzz.io` 换成你自己的地址。

> [!tip] 大白话
> 把自部署想成「自己开店」：公共实例是别人的店，哪天老板不干了（停止维护）你就没得买。自己在 Cloudflare 开一家（部署 Worker），进货渠道（源清单）自己掌握，关门与否自己说了算。

### 5.3 扩展生态：网盘 / Emby / IPTV / YouTube

#### 5.3.1 功能矩阵速览

lunatv（Enhanced Edition fork）的能力远不止聚合影视站，官方功能清单包括[^c5-2]：网盘搜索、ACG 种子搜索（Mikan）、IPTV 直播（m3u/m3u8、FLV、EPG）、Emby 私有库、YouTube、Bilibili、Bangumi、短剧。

管理后台也有对应的独立模块：站点 / 用户 / 视频源 / 直播源 / 分类 / 网盘搜索 / AI 推荐 / YouTube / TVBox 安全 / 缓存[^c5-3]。

#### 5.3.2 各类源定位与用途

| 内容类型 | 定位 | 典型形态 |
| --- | --- | --- |
| 网盘搜索 | 网盘直链资源聚合 | 网盘 API / PanSou |
| ACG 种子 | 动漫番剧资源搜索 | Mikan 种子搜索 |
| IPTV 直播 | 电视直播 | m3u / m3u8 / FLV + EPG 节目单 |
| Emby 私有库 | 自建媒体库 | Emby API |
| YouTube / Bilibili / Bangumi | 在线视频平台 | 平台 API / 解析 |

> [!tip] 大白话
> 把这些扩展想成「一个遥控器切所有频道」：lunatv 是遥控器（空壳播放器），网盘、种子、直播、Emby 是不同频道的信号源。换一个入口，不用装一堆 App。

#### 5.3.3 接入方式说明（待验证）

素材只给了功能清单，**没有给各模块的具体配置步骤**（比如 IPTV 的 m3u 地址填在哪里、网盘源的确切 JSON 字段）。需要接入某类源时，建议：查官方仓库的 docs 目录，或到社区搜对应模块的配置教程。本章只确认「有这些能力」，以及它们对应的管理后台入口[^c5-3]。

### 本章小结

- CORSAPI 用 Cloudflare Workers 中转被墙源，核心是 `_worker.js` 的「API 代理 + api 字段前缀重写」；
- 订阅 URL 四个参数分工明确：`source`（用哪档源）、`format`（怎么编码）、`url`（代理谁）、`prefix`（前缀换成什么）；
- 三个数字要记住：缓存 7200s、超时 9s、免费 10 万次/天，量大就自部署；
- 自建源与私有源通过 `?url=` 和 `?prefix=` 接入，公共中转实例仅作演示，推荐自部署；
- 扩展生态包括网盘搜索、ACG 种子（Mikan）、IPTV 直播（m3u/m3u8/FLV/EPG）、Emby、YouTube/Bilibili/Bangumi、短剧——具体接入步骤素材未覆盖，标注「待验证」。

到这里，从「找到影视站」到「导入 lunatv 能播放」，再到「被墙源中转 + 扩展内容生态」的完整路径就走完了。下一步是把这几章组装成一篇完整学习笔记，再按 Obsidian 规范美化发布，就能在笔记库里长期查阅了。

至此，你从「理解 lunatv 的源机制」走到了「被墙源中转与扩展生态」。把这篇笔记当作日常排错的速查手册：配置不生效先想「保存」，源失效就换源 + 定期更新订阅，刮削失败配豆瓣代理，部署问题按症状对号入座。最后记住一件事——**源失效是常态**，定期维护订阅才是一劳永逸的做法。
