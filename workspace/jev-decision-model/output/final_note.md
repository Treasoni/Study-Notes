## 第一章：决策模型的位置——Jev 与 LLM 的分工

你已经会调 LLM API，也见过 Agent 里最常见的一类小调用：让模型对一段材料做一次判断——这条工单该不该转人工、这位客户属于哪个类别、这条内容的相关度打几分。这类「判断调用」看起来最简单，落地时却最烦：输出要自己解析、格式时不时崩、同一段材料重跑一遍答案还可能变。

本章要回答三件事：Jev 被厂商定义成什么、它和你已经在用的文本模型差在哪、以及它应该被放在你系统的哪一层。这一章只做定位，不涉及一次具体调用怎么写。

> [!warning] 口径声明
> 本章引用的官方原话全部来自 TypeSafe 官方文档（厂商口径），本轮素材中**没有**第三方对本章这些定性声明的独立验证。涉及性能与定价的厂商自报数字，都放到第二章并单独标注。

### 1.1 先看清问题：判断类调用的三个麻烦

想象你手里有一条客服消息，想得到三个结论：客户是否要求退款、紧急程度属于哪一档、这段内容属于哪个类别。

技术上，这类任务有一个共同点：**答案空间是你事先就知道的**。「是否退款」只有两种可能；「紧急程度」是几个有序档位；「类别」是有限的一组标签。它们都不需要「写一段话」，只需要在有限集合里选一个。

实践中，你却在用一个为「生成文本」而造的模型干这件事，于是要额外付出三份成本：

1. **解析成本**：输出是自由文本或 JSON 字符串，你得写解析逻辑，还要处理缺字段、多解释、前后加了一段客套话的情况。
2. **约束成本**：你得靠提示词、JSON mode 或约束解码去「求」模型别越界，而这是一条尽力而为的路径，不是数学保证。
3. **重复成本**：同一段材料重跑一次，答案可能不一样，你需要自己观察漂移并设计容错。

Jev 整篇存在的理由，就是声称把这三份成本从「你来实现」变成「由模型形态承担」。厂商把它归入一个自己造的新类别，见下一节。

### 1.2 厂商给它的类别名：System One Model

官方博客开篇的定性是这样一句话：

> releasing our first **System One Model**: a new class of frontier models built to make fast, structured decisions that software can use directly.[^c1-1]

把这句话拆开读，关键信息有三层：

- **这是一个厂商自定义的类别名**（原文用的是 "a new class of"），不是学术界或业界已存在的标准分类。你不需要先认可这个类别的存在，只需要知道厂商用它来标定自己的定位。
- **它服务的目标是「软件可直接消费」**（software can use directly）——注意落点是「软件」而不是「人」。给人看的东西要好看；给软件看的答案要能被直接断言、分支和记录。
- **它的两个卖点是「快」和「结构化」**，不是「聪明」。

> [!note] 关于 System One 这个名字
> 「System One」这个命名会让人联想到「快思考 / 慢思考」这类二分法。但本轮收集到的素材里，**没有**官方对这套心理学对照的独立说明页或引用来源，唯一依据就是 `g1-1` 这一处命名本身。所以这里只如实呈现「厂商用了这个名字」，不替厂商补充理论出处。

| 事项 | 本章能确认的 | 依据 |
|---|---|---|
| 类别名 | System One Model（厂商自定义） | `g1-1` |
| 目标场景 | 软件可直接消费的、快速的、结构化的决策 | `g1-1` |
| 命名与卡尼曼双系统的对照 | 仅有命名上的间接联想，无独立来源 | `g1-1`（仅命名） |
| Jevons / 杰文斯悖论的命名由来 | 本轮素材中**没有**对应来源，本章不展开、不猜测 | —— |

### 1.3 输入输出形态：非结构化进，带类型的概率化决策出

官方用一句话概括了它的调用形状：

> Think of Jev as a frontier-intelligence function call: unstructured state in, typed probabilistic decisions out.[^c1-1]

这句话是本章的骨架，值得逐词抠一次：

| 片段 | 含义 | 对你的意义 |
|---|---|---|
| unstructured state in | 进去的是「状态」——你想让它看的材料，可以是没有被整理成表格、数据库行的原始内容 | 你不用先把材料规整成严格结构，省掉了前置清洗 |
| typed probabilistic decisions out | 出来的是「带类型的」「概率化的」决策——不是一段话，而是一个有类型约束的取值，外加概率 | 你的下游代码拿到的是可以直接判断的东西 |
| function call | 厂商希望你把它当成一次函数调用来看 | 它是被调用的一环，不是陪你对话的伙伴 |

> [!tip] 大白话
> 把 Jev 想成**机读答题卡**，而不是一篇作文。作文你要读完才知道写了什么，还可能跑题；答题卡上只有有限的几个格子，涂错格子是另一回事，但你永远不用怀疑「它会不会涂在第 47 个不存在的格子上」。
> 所以：它的优势不是文笔，而是「答案的形状是事先商定的」。

这里有一个必须提前划清的边界：**本章不承诺原语的字段级 schema**。原因见 1.9——官方的原语定义页本轮没有抓取，本篇不会在任何地方把字段名、嵌套结构说成「官方规范」。要写第一次调用，请等到第三章。

### 1.4 与文本模型的本质差异：放弃字符串生成

官方把这次取舍说得非常直接：

> While Jev gives up string generation, it's optimized for structured outputs and _can't_ hallucinate.[^c1-1]

以及在同一页的对比表里：

> Possible outputs and structure are defined in advance. The model never makes type errors. All answers are accompanied with calibrated probabilities and confidence scores.[^c1-1]

第一句是**交换**：给出「会写字符串」的能力，换回「输出结构可被事先定义」。这个方向不是白拿的——它意味着你**不能**指望它给你写段落、总结成文章、生成一段自然语言回复。这是取舍，不是升级。

第二句是**保证的范围**：「预定义」「never makes type errors」。注意它保证的是**类型**，不是内容。这个区别是本篇最容易误读的地方，1.7 会专门拆开。

| 维度 | 你熟悉的文本模型 | Jev（厂商定义） |
|---|---|---|
| 输出空间 | 整个词表，逐 token 生成，理论上可以是任意字符串 | 事先定义好的有限取值集合 |
| 典型产物 | 一段文本 | 一次判断（取值 + 概率） |
| 格式越界 | 靠提示词 / 结构化输出模式「求」它守规矩 | 厂商称结构由 schema 匹配强制，类型错误「数学上不可能」（`g1-11`） |
| 长文本生成 | 支持 | 明确放弃（`g1-4`） |

> [!tip] 大白话
> 把输出空间想成**点餐的菜单**：文本模型是让厨师自由发挥，端上来什么你都得认；Jev 是只让你在菜单上勾选，勾什么都能做出来，但菜单上没有的菜它做不了。
> 所以：判断「该不该用它」的第一问不是「它够不够聪明」，而是「我的答案能不能提前写成一份菜单」。

### 1.5 单次查询并行生成全部输出

官方在对比表的采样一栏写：

> **Parallel.** Generates all outputs in a single query. Incredibly efficient and hardware-aware.[^c1-1]

字面意思是：一次查询里把所有输出一起生成，而不是你发 N 次请求串行等 N 个答案。对你设计调用方式的直接影响是——**一次调用里可以带多个问题**，它们的答案一起回来。

这条属于厂商自报口径，本轮素材中没有第三方对「并行采样」这一实现的独立验证，也没有独立测试覆盖它的效率主张。这里只做事实转述，不建议你现在就以此为依据设计架构。

### 1.6 校准与一致性：官方用了什么词

官方把置信信息列为一项独立能力：

> Always communicates confidence and uncertainty with every output. Calibrated: higher confidence means higher accuracy. More consistent: returns similar answers for similar inputs.[^c1-1]

同一页，作为对照，官方对文本模型的置信度评价是：

> Even if prompted for a confidence estimate, models tend to be overconfident and inconsistent.[^c1-1]

第二句是**作者观点**（素材已标注 support: low），同页没有给出任何测量来源。它的价值在于说明厂商的立场，不能当成一条经过验证的结论。

第一句更需要抠词，因为它承载了两个容易被顺手夸大的说法：

| 官方句子 | 逐字用词 | 阅读时要注意 |
|---|---|---|
| Calibrated: higher confidence means higher accuracy. | higher / means | 官方给的是**方向**——置信更高则准确更高。它没有在本句给出具体曲线、具体准确率或具体阈值 |
| More consistent: returns similar answers for similar inputs. | **similar** | 不是 same。官方目前的最强表述止于「相似输入返回相似答案」，没有承诺相同输入必然得到相同答案 |
| models tend to be overconfident and inconsistent. | tend to | 作者措辞，无测量来源，属观点而非实测结论 |

最后一行那半句还想提前说一句：`g1-5` 里出现的 "calibrated probabilities and confidence scores" 提到了 `probabilities` 与 `confidence` 两个词，它们在 Jev 里**不是一回事**。二者的分工、以及在官方另一个页面上存在的口径出入，都属于第四章的主题，本章不展开、也不混用这两个词。

### 1.7 「零幻觉」的确切边界

这是本章最需要小心的一节。官方给「零幻觉」的依据是这一句：

> This would be an easy thing to falsify with just a single counter-example, but it is mathematically impossible.[^c1-1]

紧接着，官方自己交代了那个画在图里的 0% 是怎么来的：

> Our number is not empirical. Schema matching is guaranteed, thus we can confidently add 0% into the plots.[^c1-1]

把这两句和前面的 `g1-5` 叠起来读，能得到一个清晰的三层结构：

| 层面 | 事实 | 依据 |
|---|---|---|
| 形状层 | **schema 匹配有数学保证**：输出不可能落在预定义类型之外。官方称只要找到一个反例就能推翻它，但它「数学上不可能」 | `g1-11` |
| 图表层 | 图中那个 0% **不是实测值**，是厂商根据 schema 保证直接写进去的 | `g1-12`（厂商自认） |
| 内容层 | 取值选对了没有、分数给偏了没有——**类型安全管不到这一层** | 纯逻辑推论，无需外部来源 |

也就是说：**「不会越出 Schema」和「判断不会错」是两件事**。一个永远在 A / B / C 三个选项里作答的模型，仍然可以把该选 B 的选成 C，而且这个错误和类型错误一样会进你的下游分支。

> [!tip] 大白话
> 把「零幻觉」想成**答题卡不会涂到格子外面**。这确实是个硬保证，监考老师也不用去数有没有第 47 格。但涂在格子里不等于涂对了——涂错、涂漏、涂串行的可能都还在。
> 所以：把「零幻觉」读成「格式不会崩」是可以的，读成「判断不会错」就越界了。判对判错要靠你自己的评测集来量，那是第六章和第七章的话题。

### 1.8 它在你系统里的位置：一个环节，不是一条流水线

官方对定位的表述很克制：

> TypeSafe is designed to sit within a larger system, powering decisions with AI.[^c1-2]

对使用方式，官方给出的第一要求是一项思维方式：

> Learning to think in terms of discrete, atomic decisions that compose into complex system behavior is a key skill[^c1-2]

把它落到你熟悉的分层架构里，大致是这样一张分工表（这是 Agent 架构里常见的分层说法，不是官方推荐架构）：

| 层 | 负责什么 | 典型内容 |
|---|---|---|
| 慢思考模型（frontier） | 开放式、需要长链推理和生成的事 | 拟方案、写长文、做模糊需求拆解 |
| 快判断层（Jev 声称的位置） | 在事先定义好的有限取值上，做一次快速判断 | 该不该转人工、属于哪个类别、相关度打几分 |
| 普通代码 | 精确、无概率、按写死的规则执行 | 算术、日期先后比较、状态机流转 |
| Harness / 调度层 | 决定谁调用谁，以及拿到低置信结果怎么办 | 路由、回退、二次确认 |

这张表也顺便说明了 Jev 的**权力边界**：它不负责把原材料变成成品，只负责在自己那个工位上做一次判断。上游给它什么材料、下游怎么消费它的答案，都是你的设计责任。

> [!tip] 大白话
> 把 Jev 想成**流水线上的一个工位**：它只拧自己那一颗螺丝，拧得快、规格固定、能直接进下一个工位。至于这颗螺丝该不该拧、拧完之后包装怎么写，都不归它管。
> 所以：接入它的第一步不是写代码，而是先想清楚「我的哪一步决策可以被拆成有限选项」。

#### 「离散、原子化」到底长什么样

`g1-36` 只给了原则（discrete, atomic decisions），没有给拆解方法。下面这个对照表是按该原则给出的**示例（非官方原文）**：

| 反面问法 | 正面问法（示例） |
|---|---|
| 「看看这条工单该怎么办？」 | ① 客户是否要求退款？ ② 紧急程度属于哪一档？ ③ 是否应立即转人工？ |
| 答案空间开放、需要生成一段建议 | 每问的答案空间都是有限的、可事先枚举的 |
| 结果无法直接进分支 | 每个答案都能直接写成 `if` 或查表 |

判断拆得好不好的一个实用标准：**把每个问题的候选答案写出来，如果写不出来，说明这个问题还不适合交给它。**

## 第二章：厂商自报的性能与定价（速查表）

上一章把概念立住了：输出空间事先定义、答案形状由 schema 匹配兜底。概念之后，工程师最先翻的是另一页——**它到底多快、多便宜**。

这一章只做一件事：把厂商自己给出的数字，和**厂商自己在同一页写下的限定条件**，放进同一行读。你会发现，这两样东西拆开看和合起来看，是两幅完全不同的图景。

> [!warning] 全章口径声明
> 本章所有数字均为**厂商自报**（vendor-spec / official-claim），来源是 TypeSafe 官方博客。[^c2-1]**本轮素材中没有任何中立第三方对这三项数字做过规模化复测。** 本章也**不列第三方数字**，原因见 2.3。

### 2.1 速查表（数字与限定同行）

| 指标 | 厂商自报数字（原文片段） | 厂商自带的限定条件 | 来源 |
|---|---|---|---|
| 端到端响应时间 | `End-to-end response time is 70ms-500ms` | 同页注明评测大多在**西海岸的笔记本**上跑；并且同一张对照表里 LLM 一侧的耗时是 **3–329 秒** | `g1-7` |
| 相对速度 | `40x-200x faster` | 同上（同一页、同一组对照条件） | `g1-7` |
| 智能水平 | 与现有 LLM 相近；快**两个数量级**（此条素材中无英文原文片段，按素材要点转述） | 同页**承认评测存在自选偏差**（self-selection bias） | `g1-3` |
| 输入 token 定价 | `Input tokens: $0.042 / MTok`（官方原文中间有省略号，完整片段为 `Input tokens: $0.042 / MTok ... Output tokens: FREE (too cheap to meter).`） | 同页**承认无法证明定价未被补贴** | `g1-8` |
| 输出 token 定价 | `Output tokens: FREE (too cheap to meter).` | 同上 |

表里三个细节值得单独点出来：

1. **速度是一个区间，不是一个数**（40x–200x）。厂商自己就没有给出单一倍率，说明这个倍率随任务和对照条件浮动。
2. **「输出免费」的括号里是厂商自己的话**——"too cheap to meter"（便宜到不值得计量），这是一句态度，不是一个成本结构说明。
3. **每一条自报数字旁边都跟着一条自认的局限**，这不是本节加的批注，是同一页面的原文内容。

| 计价单位 | 含义 | 厂商自报价格 |
|---|---|---|
| MTok | 一百万（Million）token | —— |
| 输入 token | 你送进去的材料 | **$0.042 / MTok**，即每一百万输入 token 约 0.042 美元 |
| 输出 token | 模型返回的答案 | **免费**（官方原文 "FREE (too cheap to meter)"） |

上面这一栏的换算只做了一件事：把「每 MTok」摊开成「每一百万 token」，让你对量级有个手感。**价格本身仍是厂商自报口径**（`g1-8`），且附带着厂商自认的「无法证明定价未被补贴」。

> [!tip] 大白话
> 把这张表想成**餐厅菜单上写着「本店招牌，出餐只需 30 秒」**。这句话可能是真的，但你得同时看两件事：它是和谁比（旁边那桌等了 3 分钟，不代表所有餐厅都这么慢），以及这个时间是在什么条件下测的（店里没人时测的，还是午高峰）。
> 所以：读厂商数字的正确姿势不是「信 / 不信」，而是**数字和它的测量条件必须一起读**，缺一个就不构成结论。

### 2.2 怎么读这张表：三条口径提醒

#### 2.2.1 这是厂商自测，不是第三方基准

这三条数字全部出自官方博客的同一页。素材明确记录：**它们没有任何中立第三方规模化复测**。也就是说，你目前无法从任何一个不隶属于厂商的来源，独立确认 70ms–500ms 或 $0.042/MTok 在你自己场景下是否成立。

这不等于数字是假的，而是说：**它的证据等级是「厂商自报」，不是「第三方实测」。** 两者在你的技术选型文档里不能写成同一句话。

#### 2.2.2 对照基准是谁，比倍数本身更重要

`g1-7` 这一条尤其需要盯住分母：同一张对照表里，**LLM 一侧的耗时是 3–329 秒**。40x–200x 这个倍率正是相对这组数字算出来的。这意味着两件事：

- 倍率同时受「Jev 多快」和「对面的 LLM 多慢」影响；
- 对面那一栏跨越两个数量级（3 秒到 329 秒），本身就说明测量条件的离散度很大。

结合 `g1-3` 同页承认的「评测存在自选偏差」，这条数字应当被读成**厂商在自选条件下的自测结果**，而不是一个可以外推到你生产环境的预期值。

#### 2.2.3 定价「免费」附带的是一句坦白

输出 token 免费是本章最容易被顺手引用的一条。但 `g1-8` 在同一页写下了一句厂商自己的坦白：**无法证明定价未被补贴**。

> [!tip] 大白话
> 把这条想成**开业期间的「首月免单」**：你现在确实不付钱，这是事实；但这是不是一个能长期维持的价格结构，商家自己都说不好。
> 所以：「输出免费」可以写进你的当下成本测算，但不要在架构决策里把它当成一个必然长期存在的成本优势。

### 2.3 为什么本章不列第三方数字

素材里已经有第三方实测数据，但**本章刻意不并排放**，只在这里预告一句：第三方单站实测的量级与官方自报**明显不同**——`S11`（品玩）测到 Jev 平均每题完整响应约 **0.73–0.75 秒**（`g3-4`，第三方实测口径，样本 50 条中文客服题）[^c2-2]。

为什么不在本章并列：

- 两套数据来自**不同的任务集、不同的对照设置、不同的测量口径**，本章的速查表只有「厂商自报」一列，硬把第三方数字塞进来，读者会不自觉地把两套量级当成同一把尺子的两个刻度。
- 每一项第三方实测都带自己的成立条件（样本量、判定规则、是否覆盖校准），这些条件在第六章才有足够篇幅交代清楚。

所以本笔记的顺序是：**第二章先只看厂商口径，第六章再看别人测出什么、以及那些数字各自的边界。**

### 3.1 一次调用的形状

官方文档给出的端点是：

> `POST https://api.typesafe.ai/v1/systemone`[^c3-1]

请求体有两个部分，它们的角色分工可以这样理解：

> The state is whatever you want the model to look at, and each key in questions becomes a key in answers.[^c3-2]

这句话是本章最重要的一句，因为它同时定义了三件事：

| 部分 | 是什么 | 谁决定它 |
|---|---|---|
| `state` | 你想让模型看的材料——「whatever you want the model to look at」 | 你，随便放什么，不需要先规整 |
| `questions` | 一组「问题键 → 带类型的问题」 | 你，每个问题的类型和取值空间都由你事先定义 |
| `answers` | 返回的答案，**键与 `questions` 的键一一对应** | 模型，键由你决定 |

「键一一对应」是这一段最实用的信息：你给问题起什么名，答案就用什么名回来。这意味着**问题的键就是你下游代码的变量名**，起名时按你代码里怎么用最方便来起（例如 `requestsRefund`、`urgencyLevel`），而不是按给人看的标题来起。

请求的整体形状（`scripts/example_request.jsonc`，**结构示意，字段名取自官方示例，嵌套与必填性未确认**）：

```jsonc
// scripts/example_request.jsonc —— 结构示意，非官方原文，需回官网核对
{
  "state": "客户留言：……（这里放你想让它看的材料）",
  "questions": {
    "requestsRefund": {
      "type": "noul",                 // 是否类问题
      "instructions": "客户是否要求退款"
    },
    "category": {
      "type": "choice",               // 多选一
      "instructions": "这条留言属于哪个类别",
      "criteria": {                   // choice 的 criteria 是「字典」：选项名 → 说明
        "billing": "账单与扣费问题",
        "logistics": "物流与配送问题",
        "technical": "技术故障问题"
      }
    }
  }
}
```

**预期结果（形状）**：`answers` 里出现同名的 `requestsRefund` 与 `category` 两个键，键名与你写的完全一致；具体字段见 3.4。

> [!note] 关于上面示例里的 `instructions` 字段
> 素材只在 **Noul** 的问题说明里明确提到问题带 `instructions`（`g1-16`）。本章示例为了让三段结构看起来一致，给 Choice / Score 也写了同名字段——**这只是示意的写法，Choice / Score 是否使用同名的问题描述字段，本轮素材无法确认**，请回官网原页核对。这正是 3.6 第 1、2 条要提醒的事情。

### 3.2 三原语：Noul、Choice、Score

先说命名，因为这是最容易在生态文档之间走丢的一处。官方文档里的名字是这三个：

> Mix Noul, Choice, and Score in one call and see all results at once.[^c3-1]

你在别的平台文档里会看到 `boolean` 这样的叫法（Vercel 平台侧，`S06`），网关文档里则写 `noul`（`S08`）。**这不是矛盾**：官方名是 **Noul / Choice / Score**，`boolean` 是平台侧的叫法，指的是同一种原语。写代码时以官方文档的字段值为准，读平台文档时知道它说的是同一个东西即可。

三者的区分不在「难易」，而在**答案空间的形状**：

| 原语 | 回答什么 | 答案空间 | `criteria` 字段的形态 |
|---|---|---|---|
| **Noul** | 是否类问题（yes / no） | 两个取值 | **没有 `criteria` 字段**，问题带 `instructions`（`g1-16`） |
| **Choice** | 多选一 | 事先枚举的选项集合，**上限 255 个选项**（`g2-2`） | `"criteria": {` —— **字典**：选项名 → 说明（`g1-17`） |
| **Score** | 有序等级打分 | 事先定义的有序等级序列 | `"criteria": [` —— **列表**：有序等级（`g1-18`） |

> [!tip] 大白话
> 把三个原语想成**三种不同的问卷题型**：Noul 是判断题（打勾或打叉），Choice 是单选题（选项必须提前印在卷子上），Score 是评分题（1 分到 5 分那种有序刻度）。
> 所以：**你不是在教它怎么思考，而是在给这三个题型写题目。** 选错题型的后果很直接——你想问「这条属于哪一类」却用了 Noul，就永远拿不到「技术故障」这个答案。

#### 3.2.1 Choice：criteria 是字典，选项名就是返回值

Choice 的 `criteria` 用**字典**表达「选项名 → 说明」。上面 3.1 的示例已经是这个形状。要点有两个：

- **字典的键（选项名）会直接出现在答案里**——它是你下游要分支的值，所以要起成代码里好用的标识符，而不是长句；
- **字典的值（说明）是给人/给模型读的补充描述**，用来消歧。选项边界模糊时，说明写得越清楚越省事。

选项上限是 **255**（`g2-2`，来源 `S06`）。这个上限的意义在第七章还会用到：第三方实测里「超大选项集」是已知弱项（Banking77 那一档），所以 255 是**能力上限，不是舒适区**。

#### 3.2.2 Score：criteria 是列表，等级是有序的

Score 的 `criteria` 换成**列表**，表示一条有序的等级序列（`g1-18`）。有序这两个字是关键：列表里的顺序就是等级顺序，`Score` 的答案取值落在这些等级上。示意（**结构示意，需回官网核对**）：

```jsonc
// scripts/example_score_question.jsonc —— 结构示意，非官方原文，需回官网核对
{
  "urgency": {
    "type": "score",
    "instructions": "这条留言的紧急程度",
    "criteria": [          // score 的 criteria 是「列表」：有序等级
      "不紧急",
      "低",
      "中",
      "高",
      "需立即处理"
    ]
  }
}
```

#### 3.2.3 Noul：没有 criteria，只有是 / 否加一个概率

Noul 的特别之处在于它**没有 `criteria` 字段**（`g1-16`）——因为答案空间是固定的两个取值，没什么需要枚举的。它返回的是「是 / 否」加上一个概率，这个概率的含义在第四章会专门拆开讲，这里只需要记住它的形状：

```jsonc
// scripts/example_noul_question.jsonc —— 结构示意，非官方原文，需回官网核对
{
  "requestsRefund": {
    "type": "noul",                    // 注意：noul 没有 criteria 字段
    "instructions": "客户是否要求退款"
  }
}
```

### 3.3 state：不用自己序列化

关于 `state` 的内容，官方给了一句很省事的说明：

> you can pass a record or a message history without serializing it yourself[^c3-2]

也就是说，`state` 既接受**一条记录**（JSON 对象），也接受**一段消息历史**（数组），你不需要先把它压成字符串再塞进去。实际影响是：

| 你想放进 state 的东西 | 需要自己序列化吗 |
|---|---|
| 一条工单的字段集合 | 不需要，直接作为对象传 |
| 一段多轮对话历史 | 不需要，直接作为数组传 |
| 一段纯文本材料 | 作为字符串传即可 |

> [!tip] 大白话
> 把 `state` 想成一个**透明文件袋**：你把手上的东西直接放进去就行，不用先扫描成 PDF、也不用先抄到标准表格上。
> 所以：省掉的不是一步代码，而是「为了让它能看懂而先规整一遍」的那种前置清洗。真正该操心的是「放多少进去」，那是第五章成本话题的内容。

### 3.4 读响应：答案怎么和问题对上

响应里 `answers` 的键与 `questions` 的键一一对应（3.1 已引 `g2-1`）。每种原语的答案内部形状不同：

| 原语 | 答案里有什么 | 说明 | 来源 |
|---|---|---|---|
| Noul | 一个「是 / 否」的取值 + 一个概率 | 概率的具体含义见第四章，**不要在第三章就把它当置信度用** | `g1-16` |
| Choice | `choice` + `probabilities` | `probabilities` 是**按选项键展开的完整分布**，选中项最高 | `g2-2`、`g2-6` |
| Score | `score` + `probabilities` | 分布的键是**字符串形式的等级下标**（如 `"0"`、`"1"`…），不是等级文字 | `g2-7` |

「字符串形式的等级下标」是一个很容易踩的坑：Score 的分布不是用你写的等级文字做键，而是用下标。这意味着把它映射回可读文字需要你自己持有一份 `criteria` 列表做对照（网关文档的响应示例里还带了一个 `legend` 字段做这件事，`g2-21`——注意那是平台侧的重新暴露形态，不构成对原语语义的另一套定义）。

响应里还带两个和运维直接相关的字段：

| 字段 | 内容 | 用途 | 来源 |
|---|---|---|---|
| `"model"` | 实际执行的具体版本，例如 `"model": "jev-1.13.0"` | 记录日志、复现问题时用这个，不要记请求侧的值 | `g1-22` |
| `"input_tokens"` | 本次请求的输入 token 数，例如 `"input_tokens": 392,` | 成本核算的唯一入场券（输入 token 是唯一付费项，详见第五章） | `g1-23` |

请求侧与响应侧的版本处理方式不同，这一点值得单独记住：

- **请求侧**默认传 `"jev-latest"`（`g1-22`）——你写的是「最新版」这个别名；
- **响应侧**回传的是具体版本号（`g1-22`）——真正跑了哪个版本。

> [!tip] 大白话
> 想成**点外卖**：你下单时写的是「主厨推荐」（`jev-latest`），小票上印的是真正做这道菜的那位师傅的工号（`jev-1.13.0`）。
> 所以：出问题时拿小票上的工号去查，别拿下单时那三个字。日志里记响应侧的 `model` 字段。

### 3.5 用 Python SDK 跑一次最小调用

官方 Quick start 给出的 SDK 前提与默认行为：

> Install the SDK (requires Python >= 3.10).[^c3-1]

> The client reads TYPESAFE_API_KEY from the environment and calls jev-latest by default.[^c3-1]

这两句合起来说明了三件事：**需要 Python 3.10 及以上**；**API key 从环境变量 `TYPESAFE_API_KEY` 读**，不用写进代码；**默认调 `jev-latest`**。

下面这个最小调用是**结构示意**（`scripts/jev_min_call.py`）：三个原语各问一个问题、一次调用拿回全部答案。

```python
# scripts/jev_min_call.py —— 结构示意，非官方原文，需回官网核对后再运行
# 前置：Python >= 3.10；环境变量 TYPESAFE_API_KEY 已设置
from typesafe import TypeSafe  # 客户端从环境读取 TYPESAFE_API_KEY

client = TypeSafe()

result = client.systemone.create(
    state="客户留言：上周下的单到现在还没发货，我要退款！",
    questions={
        # ① Noul：判断题
        "requestsRefund": {
            "type": "noul",
            "instructions": "客户是否要求退款",
        },
        # ② Choice：单选题（选项名会成为返回值）
        "category": {
            "type": "choice",
            "instructions": "这条留言属于哪个类别",
            "criteria": {
                "billing": "账单与扣费问题",
                "logistics": "物流与配送问题",
                "technical": "技术故障问题",
            },
        },
        # ③ Score：有序评分题（等级顺序即列表顺序）
        "urgency": {
            "type": "score",
            "instructions": "这条留言的紧急程度",
            "criteria": ["不紧急", "低", "中", "高", "需立即处理"],
        },
    },
)

# answers 的键与 questions 的键一一对应
print(result.answers)
print(result.model)          # 响应侧回传的具体版本，如 jev-1.13.0
print(result.input_tokens)   # 本次输入 token 数，用于成本核算
```

**预期输出（形状示意，数值为占位符，不是官方实测数据）**：

```text

{
  "requestsRefund": { "answer": true,  "probability": 0.9x },
  "category":       { "choice": "logistics",
                      "probabilities": { "billing": 0.0x,
                                         "logistics": 0.8x,
                                         "technical": 0.1x } },
  "urgency":        { "score": 3,
                      "probabilities": { "0": 0.0x, "1": 0.0x,
                                         "2": 0.2x, "3": 0.6x, "4": 0.1x } }
}
# model: jev-1.13.0（示意）
# input_tokens: 392（官方示例中出现的数值）
```

## 第四章：读结果——probability、confidence 与阈值设计

上一章你把调用的形状跑通了，也看到了答案里的数字。这一章回答三个问题：**这些数字分别是什么**、**哪一个是你真正能拿来卡阈值的**、以及**阈值该定多少、低于阈值时该做什么**。

这一章只差一个词，但这个词差得很关键：`probability` 和 `confidence` 在 Jev 里不是一回事。把它们当同义词用，会直接导致你的门控逻辑在错误的地方生效。

> [!warning] 本章引文范围
> 官方 Confidence 文档页（`G1a`）里的阈值**示例代码**在本轮抓取时**比较运算符丢失**（页面上只剩 `if confidence  0.5:` 这种残缺形态）。因此本章**只引用该页的散文句，不引用任何阈值代码**。若你需要可直接运行的阈值代码，请回官网原页获取。

### 4.1 一个答案里，有三种「看起来都像置信度」的数字

先把三种数字摆在一张表里，它们的区别一眼就能看清：

| 数字 | 回答的问题 | 取值范围 | 能不能直接卡阈值 | 出现在哪些原语上 | 来源 |
|---|---|---|---|---|---|
| `probability` | 「**这件事**成立的概率有多大」——例如客户想要退款的概率 | 0–1 | 不能当答案置信度用，它是**事件概率** | Noul | `g2-8` |
| `probabilities` | 「每个选项 / 每个等级**各自**有多大概率是答案」——一个覆盖全部选项的分布 | 一个分布 | 可以，但要你自己做数学 | Choice、Score | `g1-26`、`g2-6`、`g2-7` |
| `confidence` | 「把上面那个分布的**形状**压成一个数」 | 单一 0–1 | **可以，官方就是为了让你直接阈值而给的** | Choice、Score（**Noul 没有**） | `g1-27`、`g1-28`、`g2-9` |

其中分布那一行，官方 `G1a` 页的原话是：

> All Score and Choice answers from TypeSafe include a probabilities property representing the probability distribution across the options (for Choice) or levels (for Score).[^c4-2]

也就是说：**分布不是可选项，而是 Choice 与 Score 答案的固有组成部分**（`g1-26`）。`confidence` 是在它之上再加工出来的，官方对 `confidence` 的定义原话是：

> The answer's confidence property collapses that shape into a single number from 0 to 1, so you can threshold on it without doing the math yourself.[^c4-2]

> confidence is a statistic computed from the probability distribution the answer already gives you. TypeSafe computes it for you and returns it on every Choice and Score answer[^c4-2]

注意这两句里的两个动词：**collapses**（把分布压扁）和 **computed from**（由分布算出）。这说明 `confidence` 不是额外独立测量出来的东西，而是**对已有分布的一个加工结果**。这个认识是后面 4.5、4.7 两节的基础。

### 4.2 硬结论一：`probability` ≠ `confidence`

这是本章最需要刻进肌肉记忆的一条。官方在 Vercel 指南里的表述非常直白：

> requestsRefund.probability is the estimated probability that the customer wants money back, not a confidence in the answer.[^c4-3]

把这句话拆成两个方向读：

- `probability = 0.9` 的意思是「**客户有 90% 的概率想要退款**」——说的是**世界上的事实**；
- 它**不是**「模型有 90% 的把握」——模型对自己这个答案有多笃定，由 `confidence` 承担。

| 假设你拿到 | 正确的读法 | 错误的读法 |
|---|---|---|
| `requestsRefund.probability = 0.9` | 客户想要退款这件事发生的概率约 90% | 「模型很确定客户要退款」 |
| `category.confidence = 0.78` | 模型对「它所选的那个类别」的笃定程度被压成 0.78，可直接阈值 | 「这个类别正确率为 78%」 |

> [!tip] 大白话
> 把 `probability` 想成**天气预报的降水概率**：「明天 70% 概率下雨」说的是天会不会下雨，不是预报员对自己有没有把握。`confidence` 才是后者——是预报员那句「这次我挺有底」。
> 所以：**想判断「这件事会不会发生」，看 probability；想判断「这个答案靠不靠得住、要不要交给自动化」，看 confidence。** 两个问题，两个字段。

顺带说清一件事：`confidence` 也不等于「准确率」。它反映的是分布的形状，不是历史命中率。它跟准确率的关系，官方只给了一个方向性表述（「更高置信 = 更高准确」，见第一章 `g1-9`），没有给具体曲线。

### 4.3 硬结论二：`confidence` 只出现在 Choice 与 Score 上

官方 `G1a` 页在同一句里带了一个容易读漏的括号：

> The answer's confidence property collapses that shape into a single number from 0 to 1, so you can threshold on it without doing the math yourself. **(Noul answers don't carry one.)**[^c4-2]

Vercel 指南从另一侧独立印证了同一件事：

> TypeSafe AI also returns a separate confidence statistic for choice and score answers in result.providerMetadata.typesafe.confidence, keyed by question ID.[^c4-3]

两处合起来：

| 原语 | 有没有 `confidence` | 依据 |
|---|---|---|
| **Noul** | **没有** | `g1-27` 官方括号原话；`g2-9` 只提 choice 与 score |
| **Choice** | 有 | `g1-27`、`g1-28`、`g2-9` |
| **Score** | 有 | `g1-27`、`g1-28`、`g2-9` |

这个事实会直接改写你的代码组织方式：**如果你打算写一段通用的「低置信就转人工」的门控逻辑，它不能假设每个答案都带 `confidence` 字段。** Noul 的问题需要另一种判别方式（它自带的是事件概率），Choice / Score 才能走同一套阈值分支。

> [!tip] 大白话
> 把三个原语想成**三种发票**：Choice 和 Score 是那种印了「本单合计」的发票，你可以直接拿合计数字去对账；Noul 是那种只有明细、没有合计的发票，你得自己看明细。
> 所以：门控函数别写成「所有答案都读同一个字段」。先按原语分类，再决定读什么。

### 4.4 硬结论三：`confidence` 是答案对象自己的属性

官方 `G1a` 的措辞是 "**The answer's** `confidence` property"（`g1-27`）——它是答案对象自己的字段。三份响应示例都印证了这一点：

| 示例来源 | 观察到什么 |
|---|---|
| 官方 Quick start 响应示例（`g1-19`） | choice 答案对象内直接出现 `"confidence": 0.78,`，与 `"probabilities": { "technical": 0.85,` 并列[^c4-4] |
| 网关响应示例（`g2-20`） | `"confidence": 0.97,` 直接放在 choice 答案对象内，与 `choice`、`probabilities` 平级[^c4-4] |
| 网关 score 答案（`g2-21`） | 答案含 `score`、`confidence`，另有 `legend` 把等级下标映射回评分文字 |

那么 `result.providerMetadata.typesafe.confidence`（`g2-9`）是什么？它是**平台层把同一个信息重新暴露了一遍**——AI SDK 的调用面习惯把厂商元数据放到 `providerMetadata` 下，并**按问题 ID 索引**。

两处**并存，不是二选一，也不是两套语义**：原生的位置是答案对象内，平台层的位置是 `providerMetadata`。素材对这一点给出的判定是"澄清为调用面差异，非矛盾"。

> [!tip] 大白话
> 想成**快递单上的签收人**：原厂把签收人印在包裹面单上；平台又把这个名字抄了一份到自己系统里，方便按单号查。抄件和原件是同一个信息，不是两个人。
> 所以：你在 AI SDK 里从 `providerMetadata` 读到的 confidence，和原生响应里答案对象内的 confidence，是同一个值。别写两套逻辑去交叉校验它们。

### 4.5 `confidence` ≠ 最高选项的概率

这一条特别容易被顺手写错。看官方自己的响应示例（`g1-19`）：

| 量 | 官方示例里的值 | 是同一个数吗 |
|---|---|---|
| `confidence` | `"confidence": 0.78,` | —— |
| 选中项的概率 | `"probabilities": { "technical": 0.85,` | **不是**（0.78 vs 0.85） |

两个数字在同一份官方示例里明确不相等。结合 4.1 已经确立的事实——`confidence` 是「从**整个分布**算出来的统计量」（`g1-28`）——可以得出结论：**它不是「取最大值」**。差异来源是分布的形状：一个最高选项 0.85 但其余选项也各有分量的分布，压缩出来的置信度会低于 0.85。

> [!tip] 大白话
> 想成**评一支球队强不强**：不是只看它最好的那个球员得了几分，还要看剩下的人跟上没跟上。一个「一人 85 分、队友全是 5 分」的分布，和一个「一人 85 分、队友也都不弱」的分布，压出来的单一数字不会一样。
> 所以：**不要自己写 `max(probabilities)` 来代替 `confidence`。** 那是另一个量。

### 4.6 分布形状：越平坦，置信越低

官方对分布形状与置信度的关系给了一句很实用的判读：

> In both cases a flatter distribution means lower confidence: low confidence on a Choice often means none of the options are a clear winner over the others[^c4-2]

| 分布形状 | `confidence` | 适用场景下的解读 |
|---|---|---|
| 尖峰：一个选项明显高于其他 | 高 | 有明确的胜出选项，可以按阈值放行 |
| 平坦：几个选项彼此接近 | 低 | 对 Choice 而言，官方解释是**没有选项明显胜出**（`g1-30`） |
| 落在中间地带 | 中 | 最需要谨慎的区域——见 4.8 关于阈值余量的提醒 |

对设计者的一个直接推论（**这是推论，不是官方原文**）：遇到 Choice 低置信时，先回看你的选项集——是否存在选项之间互相重叠、或者真实答案根本不在你的选项里。这两种情况下，低置信是**题目设计问题的信号**，而不是模型不稳定。

### 4.7 官方没有锁定 `confidence` 的定义

这一条决定了你在这件事上有多少自由：

> We provide confidence as a convenient measure that fits most use-cases, but you are never locked into our definition.[^c4-2]

意思是：`confidence` 的定位是「**适配多数用例的便利度量**」，不是一个你必须接受的行业标准定义，也不是唯一可用的统计量。实践中的含义：

- 想直接用它做门控——可以，官方就是为此提供的；
- 想按自己的业务口径重新定义——也可以，因为 `probabilities` 本来就在答案里（`g1-26`），你可以自己算一个更贴合自己场景的量；
- 但**不要混着用**：一段门控逻辑里要么用官方 `confidence`，要么用你自算的量，两边来回切会让阈值失去意义。

### 4.8 阈值设计：官方给了一个起点和一条风险曲线

#### 4.8.1 第一句话就是「没有普适阈值」

> The correct threshold values depend on your domain and the performance of the model for your use case. Start with conservative thresholds, test with your own data, and adjust[^c4-2]

这句话把责任划得很清楚：**阈值是你要用自己的数据标定出来的**，官方不给一个通用数值。任何「业界通用阈值是 0.8」的传言，在官方口径里都没有对应依据。

#### 4.8.2 官方示例给出的起点

Vercel 指南的路由表示例给出了一组起始条件：**置信度 ≥ 0.6，且选中项的概率 ≥ 0.7**，两个条件同时满足才自动分派（`g2-10`）。

注意这里是「**且**」不是「或」——两个数字分别盯着两个不同的量（4.2 的 `confidence` 与 `probability`）。把它读成「达标其一即可」会让门控明显变松。

#### 4.8.3 按动作风险上调门槛

官方按「猜错的代价」给出了两档参照：

> Read-only actions like showing a screen can tolerate a wrong guess, so a probability of 0.7 might be enough. Destructive actions need a higher bar, closer to 0.9 or above[^c4-3]

| 动作类型 | 官方示例的参考线 | 为什么 |
|---|---|---|
| 只读动作（例如展示一个界面） | 概率 0.7 可能就够 | 猜错的代价低，用户能自己纠正 |
| 破坏性动作 | 门槛更高，接近 **0.9 或以上** | 猜错之后难以撤销 |

这张表的价值不在于那两个具体数字，而在于它给了一种**按后果设计阈值**的方法：不要把阈值当成模型参数来调，要当成**风险预算**来定。

#### 4.8.4 低于阈值时：不执行动作

> **Low confidence:** Do not act. Route to a human, request clarification, or fall back to a different system.[^c4-2]

官方给了三条出路，注意**第一条是「不要执行动作」**，后面三条才是怎么收场：

1. **转人工**——把判断交给人；
2. **请求澄清**——信息不足，向用户追问；
3. **降级到另一个系统**——换一个模型或换一条路径处理。

#### 4.8.5 关于 0.5 这个数字

官方 `G1a` 页里出现过一条 0.5 的阈值示例：

> The 0.5 confidence floor catches anything the model reports as genuinely uncertain.[^c4-2]

**这是该页示例里的取值，不是普适标准**——这一点必须和 4.8.1 的「没有普适阈值」放在一起读，否则很容易把一个示例数当成默认值抄进生产代码。同理，`S06` 的 0.6 / 0.7 与这里的 0.7 / 0.9 都是**示例起点**，它们之间数值不一致，恰恰印证的正是「按领域自测标定」这条原则。

#### 4.8.6 一条落地检查清单（本节建议，非官方原文）

| # | 动作 | 依据 |
|---|---|---|
| 1 | 用自己的数据标定，不要抄通用数值 | `g1-33` |
| 2 | 起点可用「置信度 0.6 **且** 选中项概率 0.7」 | `g2-10` |
| 3 | 按动作风险上调：只读约 0.7、破坏性接近 0.9 以上 | `g2-11` |
| 4 | 低于阈值**不执行动作**，转人工 / 澄清 / 降级 | `g1-32` |
| 5 | 日志里同时记下 `confidence`、`probability` 与响应侧的具体 `model` 版本 | `g1-22`（第三章 3.4） |

第 5 条不是官方要求，是让你能回测阈值的手段：只有记下当时用的具体版本和当时的置信度，事后才能回答「这个阈值到底该往上还是往下调」。

### 4.9 未解：同一厂商两个页面，口径互相矛盾

本节是本章必须如实交代的一处**未解矛盾**，请注意它的性质：**不是官方与第三方的分歧，而是同一个厂商的两个官方页面之间的分歧。**

**一侧：官方博客（`S01`）**

> All answers are accompanied with calibrated probabilities and confidence scores.[^c4-1]

> Always communicates confidence and uncertainty with every output.[^c4-1]

**另一侧：官方 Confidence 文档页（`G1a`）**

> (Noul answers don't carry one.)[^c4-2]

矛盾点很具体：博客的说法是「所有答案都伴随校准概率与置信分数」「每次都传达置信与不确定」；而 Confidence 页明确括号注明 **Noul 的答案不带 `confidence`**。

**本轮素材对这一条的裁决状态是「未解」。** 原话是：同一厂商两页互相矛盾，**本轮没有第三份官方材料可以裁决**。

本笔记在这里不做以下三件事：

- 不说「博客那句话只是写得宽泛」——这是猜测，不是依据；
- 不说「可能是两个页面更新不同步」——素材里没有任何时间戳证据支持；
- 不给一个「其实两边都对」的调和说法。

**存在的就是矛盾本身，本轮无法判定谁代表当前实现。**

对你的实际影响只有一条，但它很重要：**如果 Noul 的 `confidence` 字段对你的门控设计是必需的，不要依据博客那句话写代码**——先实测一次 Noul 的答案里到底有没有这个字段，再决定你的分支怎么写。Confidence 页与博客两处都已列在脚注里，你可以自己去核对这两个页面的当前状态。

> [!tip] 大白话
> 像**同一家店的两张宣传单**：一张写着「所有商品都送赠品」，另一张小字写着「赠品不含 X 类商品」。你不知道哪张是印刷错误、哪张是后来改的规。此时正确的做法不是自己挑一张信，而是去柜台问清楚。
> 所以：这一节的作用不是给你答案，是提醒你这块地界**还没定论**，别把它写进无人复核的自动化逻辑里。

### 本章小结

- 一个答案里有三种数字，**不能混用**：`probability` 说的是事件成立的概率（`g2-8`）；`probabilities` 是各选项 / 各等级的完整分布（`g1-26`、`g2-6`、`g2-7`）；`confidence` 是把分布形状压成的 0–1 统计量，专为直接阈值而给（`g1-27`、`g1-28`）。
- `confidence` **只出现在 Choice 与 Score 上，Noul 没有**（`g1-27` 官方括号原话 + `g2-9` 独立印证）；门控代码不能假设每个答案都带这个字段。
- `confidence` 是**答案对象自己的属性**；AI SDK 在 `providerMetadata.typesafe.confidence` 的暴露是平台层重新显影，**不是另一套语义**（`g1-27`、`g1-19`、`g2-20`、`g2-21`、`g2-9`）。
- `confidence` **不等于最高选项概率**：官方示例中 0.78 与 0.85 并不相等（`g1-19`）；它由整个分布算出，分布越平坦置信越低，Choice 低置信常意味着没有明显胜出选项（`g1-28`、`g1-30`）。
- 官方**没有普适阈值**，需按领域自测标定（`g1-33`）；示例起点为「置信度 ≥0.6 且选中项概率 ≥0.7」（`g2-10`），并按动作风险上调——只读约 0.7、破坏性接近 0.9 以上（`g2-11`）；低置信时**不执行动作**，转人工、请求澄清或降级（`g1-32`）；0.5 是该页示例取值，不是通用标准（`g1-34`）。
- **未解矛盾（C7）**：`S01` 博客称答案都伴随校准概率与置信分数、每次都传达置信与不确定（`g1-5`、`g1-9`），而 `G1a` 页括号写明 Noul 答案不带 `confidence`（`g1-27`）。同一厂商两页互相矛盾，本轮无第三份官方材料可裁决——本笔记并列原文，不做调和。

## 第五章：接入与设计模式——成本、SDK、三种官方模式

前四章走完了一条闭环：概念、数字、发一次调用、读一次结果。这一章换到工程视角，回答接入前必须定的三个问题：

1. **钱花在哪里**——预算该按什么结构来算；
2. **问题怎么组织**——官方给的三种设计模式分别解决什么；
3. **走哪条接入路径**——官方 SDK、平台侧 AI SDK、网关各自把什么包了起来。

> [!warning] 本章代码口径
> 本章出现的代码仍是**形状示意**：`S06`（Vercel 指南）的 TS 代码在抓取时被重排且**比较运算符丢失**，`S08`（AI/ML API 网关）的 JSON 代码块被截断。因此下面每段代码**只保证字段名与路径名与素材一致**，其余以官网原页为准。**Python SDK 的安装与最小调用已在第三章讲完，本章不重复。**

### 5.1 成本：输入 token 是唯一付费项

官方把成本模型压缩成了一句话：

> Input tokens are the only thing you pay for, so pass the fields the decision depends on rather than an entire record.[^c5-1]

这句话同时给出了**计价对象**和**优化手段**：

| 计费项 | 是否付费 | 来源 |
|---|---|---|
| 输入 token | **唯一付费项** | `g2-12` |
| 输出 token | 厂商自报为免费（见第一、二章） | `g1-8`（厂商自报） |

于是成本控制的全部着力点都在**你往 `state` 里放了多少东西**。与此配套的是两个硬上限：

| 项 | 上限 | 来源 |
|---|---|---|
| 单请求上下文 | **64,000 token** | `g2-12` |
| 其中 `state` | **32,000 token** | `g2-12` |

素材只记录到这两个数字，**没有说明剩余配额的构成**（问题定义、答案等各占多少），所以这里不推断、不补全。

优化原则就是 `g2-12` 的后半句：**只传决策所依赖的字段，而不是整条记录**。

| 做法 | 效果 |
|---|---|
| 把整条工单记录（含几十个用不上的字段）塞进 `state` | 输入 token 直接膨胀，而这正是唯一付费项 |
| 只挑这次决策真正依赖的几个字段 | 付费量最小，且决策质量不受无关字段干扰 |

> [!tip] 大白话
> 想成**寄快递按重量收费**：你要办的事只需要其中三页纸，那就只寄那三页，不要把整个档案盒一起寄过去——多出来的重量全是钱，而且不会让收件人判断得更准。
> 所以：设计 `state` 的第一原则不是「多给信息更保险」，而是**「这次决策依赖哪些字段」**。

配套的度量手段在第三章已经出现过：响应里带 `input_tokens`（`g1-23`），加上响应侧回传的具体版本（`g1-22`），你就能在日志里把「花了多少、跑的是哪个版本」记成一行——这是后面调阈值、算成本的基础数据。

### 5.2 设计范式：把问题拆成离散、原子化的决策

官方把这件事称为一项「关键技能」：

> Learning to think in terms of discrete, atomic decisions that compose into complex system behavior is a key skill[^c5-2]

这句话的重点在于**compose（组合）**：系统的复杂行为不是由一个复杂判断产生的，而是由许多**简单判断串联**出来的。所以接入时的实际工作不是「写一个更好的提示词」，而是：

- 把一个模糊的业务问题，拆成若干个**答案空间有限**的小问题；
- 让每个小问题的答案能直接进你的分支逻辑；
- 由你的编排代码（而不是模型）决定这些小答案怎么组合成最终行为。

这与第三章 3.1 的「问题键就是下游变量名」是同一件事的两面：**拆得好不好，看你能不能把每个问题的候选答案写出来。**

### 5.3 三个官方模式

官方 Patterns 页给出了三种使用模式。它们的定位可以先用一张表看清：

| 模式 | 一句话 | 关键点 | 来源 |
|---|---|---|---|
| **Speculative Fan-Out**（投机性一次多问） | 一次调用里发多个问题，包括投机性的问题 | **由调用方代码筛相关性** | `g1-38` |
| **Confidence-Gated Routing**（置信度门控路由） | 把置信度当成**第二条决策轴** | 答案与置信度分别过线才放行 | `g1-39` |
| **Composite Scoring**（多维度合成分） | 多维度合成单一得分 | 把分布式的分项收敛成一个可比较的量 | `g1-40` |

以上三条是官方页面的**要点转述**（该页素材中无英文原文片段可与正文对引），下面逐条展开时也只做**解读**，不替官方补充未写的内容。

#### 5.3.1 Speculative Fan-Out：一次多问，相关性由你的代码筛

做法是：既然单次调用可以并行生成全部输出（第一章 `g1-6` 的厂商口径），那就把**可能**相关的几个问题一次问完，拿回答案之后，**在调用方代码里判断哪些答案这次真的有用**。

这里最容易做错的一步是**把筛选交给模型**——但素材写明这一步的责任在**调用方代码**（`g1-38`）。也就是说，「这次该用哪几个答案」是你的程序逻辑的职责，不是给它再加一个问题。

#### 5.3.2 Confidence-Gated Routing：置信度是第二条轴

这个模式把「答案是什么」和「这个答案值不值得信」拆成两条独立的判据，**两条都过线才自动执行**：

| 判断轴 | 看什么字段 | 过线条件（示例起点） | 来源 |
|---|---|---|---|
| 第一轴：答案 | 答案本身（选项 / 分数） | 比如选中项概率 ≥0.7 | `g2-10` |
| 第二轴：置信 | `confidence` | 比如 ≥0.6 | `g2-10` |
| 未过线 | —— | **不执行动作**，转人工 / 请求澄清 / 降级 | `g1-32` |

两条实现上的注意：

1. **`confidence` 不是每个原语都有**——它出现在 Choice 与 Score 上，**Noul 没有**（第四章 `g1-27`、`g2-9`）。所以门控代码必须先按原语分类，不能假设答案里一定有这个字段。
2. **阈值不是通用值**，官方明确要按领域自测标定并按动作风险上调（第四章 `g1-33`、`g2-11`）。

#### 5.3.3 Composite Scoring：把多个维度收成一个分

做法是把多个维度的判断合成为一个单一得分，用于排序、比大小或统一卡一个阈值。它解决的是「我有好几个分项，但下游只想拿一个数做决策」的问题。

需要注意的是**这个"合成"发生在你的编排里，还是一个 Score 原语里**——素材只给出了模式名与一句话定位（`g1-40`），没有给出合成的具体公式或实现位置。这里不做推测。

> [!tip] 大白话
> 把三个模式想成**餐厅的三套流程**：
> **Fan-Out** 是「一次把可能点的菜全问了，后厨一起做，再由服务员判断哪几道是这桌真要的」；
> **Gated Routing** 是「菜做好了还要看火候达标没达标，没达标的菜不上桌」；
> **Composite Scoring** 是「几个评委打的分最后算成一个总分，用来排名」。
> 所以：三个模式不是三选一，它们解决的是流水线上三个不同位置的问题——**问什么、放不放行、怎么排序**。

### 本章小结

- 成本模型：**输入 token 是唯一付费项**，只传决策所依赖的字段而不是整条记录；硬上限是单请求 **64,000 token**、其中 `state` **32,000**（`g2-12`，剩余配额构成素材未记录）。
- 设计范式的核心是**把问题拆成离散、原子化的决策**，让复杂系统行为由这些小判断**组合**而成，组合动作由你的编排代码负责（`g1-36`）。
- 三个官方模式：Speculative Fan-Out（一次多问，**由调用方代码筛相关性**，`g1-38`）、Confidence-Gated Routing（置信度当**第二条决策轴**，`g1-39`）、Composite Scoring（多维度合成单一得分，`g1-40`）；后者的合成公式素材未给出，不做推测。
- 生态接入点目前可确认的是**调用面形态**：Vercel AI SDK 在 `providerMetadata.typesafe.confidence` 按问题 ID 暴露置信度（`g2-9`）；AI/ML API 网关把 `confidence` 放在答案对象内、score 答案另带 `legend`（`g2-20`、`g2-21`）。两者都是包装形态，不是另一套语义。
- **待补**：`S09`（LangChain judge 样板）与 `S10`（Claude Code 压缩插件）本轮均未抓取，只能作为入口列出；由此 **C3（state 精简 vs 逐字保留）未做裁决**。

## 第六章：独立实测——三方数据与它们各自的口径

第二章把厂商自报的数字列完了，但留了一个悬着的问题：**别人测出来是多少？**

这一章把三份独立来源分开成三节，每节只讲一份数据：它测了什么、数字长什么样、以及**这些数字在什么条件下才成立**。读之前先建立一条纪律，它比任何单个数字都重要。

> [!warning] 本章的读法（请先读完整节）
> **这三份数据不可相加、不可并列比较。** 它们的任务集不同、对手设置不同、测的指标也不同——把它们排成一张"谁更准"的表，是对三份数据的共同误读。6.1 会逐项说明。

### 6.1 三份数据各自的位置

| 来源 | 性质 / 时间 | 任务集 | 对手设置 | 实际测的是 |
|---|---|---|---|---|
| **`S11` 品玩** | news-media，2026-09-20 | 50 条中文客服问题，每题四项判断（紧急度 / 售前概率 / 类别 / 严重度），**四项全对才算正确**（`g3-1`） | 12 个模型同场对比，Jev 与"便宜小模型组"（DeepSeek V4 Flash、GPT-5 nano、Gemini 2.5 Flash Lite）同组（`g3-2`） | 一个具体业务场景下的**绝对准确率与成本** |
| **`S12` Wunderlandmedia** | community，2026-09-19 | 作者自有 183 篇文章 × 4 个问题 = **732 个判断**（`g3-14`） | **不与其他模型比** | 同一个模型重复运行的**稳定性** |
| **`S13` jev-decision-bench** | community，运行日 2026-09-18，模型 `jev-1.13.0`（`g3-26`） | **49 项任务 / 8,225 条样本** | 基线为 `gpt-5.6-luna` 的**无 / 低推理强度**设置 | **相对基线**的准确率、延迟、成本与校准误差 |

三条必须同时记住的纪律：

1. **不可相加或并列比较**：任务集与对手设置均不同。把 64%（`S11`）和 42/49（`S13`）放在一起比高低，是把两张不同的考卷混成一张。
2. **`S13` 的基线不是满血模型**：`gpt-5.6-luna` 被刻意限制了推理强度。因此「42/49 追平或领先」与「快约 1/7、便宜约 1/4」**不得读作「Jev 打得过前沿模型」**（素材对这一条有专门的警示）。
3. **`S11` 的 64% 是第三方口径**，不得写成官方口径；它来自一份 50 条样本的实测，作者自己也说明了样本限度。

> [!tip] 大白话
> 想成**三份不同学校出的考卷**：一份考中文客服（50 题、四项全对才算对），一份是"同一份卷子同一个人做三遍，看答案会不会变"，一份是和一位**被要求少思考**的对手比（49 项任务）。
> 所以：三份卷子上都写着分数，但**它们之间没有可比性**——你只能分别看"在这套规则下，它表现如何"。

### 6.2 `S11` 品玩：50 条中文客服题

#### 6.2.1 结果

> Jev 的平均得分大约在 32～32.6 分之间，50 道题的完整准确率约为 64%～65.2%。它排在便宜小模型组第二，只比 DeepSeek V4 Flash 少 1.2 分。[^c6-1]

注意这份成绩的判定标准很严：**每题四项判断（紧急度 / 售前概率 / 类别 / 严重度）全对才算这道题对**（`g3-1`）。这也是「完整准确率」这个词的含义——不是单项命中率。

#### 6.2.2 速度与成本

> Jev 平均每道题的完整响应时间约 0.73～0.75 秒，50 道题总成本约 0.002 美元，两项都是我们测试中的最低值。DeepSeek V4 Flash 虽然多拿了一点分，但平均每题需要 5.58 秒，成本约为 Jev 的 2.5 倍。[^c6-1]

| 指标 | Jev（第三方实测） | 对照 |
|---|---|---|
| 完整准确率 | 约 64%–65.2%（50 题） | DeepSeek V4 Flash 高 1.2 分 |
| 每题完整响应时间 | 约 0.73–0.75 秒 | DeepSeek V4 Flash 约 5.58 秒/题 |
| 50 题总成本 | 约 $0.002 | DeepSeek V4 Flash 约为其 2.5 倍 |

#### 6.2.3 跨组参照

同一份实测里还有一个不同档位的参照：MiniMax M3 约 38 分，`完整准确率高出约 10.8 个百分点`（`g3-5`）；代价是

> 50 道题，MiniMax M3 只多花了大约 0.0035 美元，平均每题响应时间约 1.80 秒。[^c6-1]

这三个数放在一起，正是这份实测最有价值的地方：**准确率的差距在跨档位时需要付出的成本和时间是有具体量级的**，不是抽象的"更好"。

#### 6.2.4 失分长什么样

> 人工标注认为某条客服消息的严重度下限应该是 2.00，Jev 给出了 1.99；某条临期食品问题的人工紧急度是 0.75，Jev 的结果在 0.71～0.72 左右。[^c6-1]

也就是说，**失分集中在阈值附近的临界判断上**——差的是小数点后两位，不是"答错了方向"。这一点在第七章讲阈值设计时会再次出现。

#### 6.2.5 重复测试与作者自述的局限

> 我们重复测试了 15 次，还有 3 道题出现过通过和失分交替的情况。[^c6-1]

作者对这份数据的适用范围很克制：

> 这 50 条中文客服样本，也不足以代表它在所有任务上的表现。[^c6-1]

> 我们这组按题目判分的测试，也不能验证概率校准做得有多好。[^c6-1]

第二条尤其要记住：**这份实测没有验证校准**。也就是说，它回答不了"置信度高的那些题是不是真的更准"这个问题。（本轮三份材料都没有提供独立的校准曲线，素材对这一点的记录是「无独立校准曲线」。）

#### 6.2.6 作者的结论

> 因此，这组测试很难支持"Jev 是更聪明的模型"这个结论。它展示的是一组具体取舍：少等一会儿，少花一点钱，同时接受一定的准确率差距。[^c6-1]

这句话可以作为整章的基调：**这份实测的结果是取舍，不是排名。**

### 6.3 `S12` Wunderlandmedia：同一输入跑三遍，答案会动

这份复测的规模与成本：

> That is 732 separate judgements. One run took **20.1 seconds** at eight parallel requests, burned 445,794 input tokens, and cost **$0.0187**.[^c6-2]

#### 6.3.1 逐位一致率

> I ran the same 732 decisions three times and diffed them. 177 answers were bit-identical across all three runs. That is 24 percent. The other 555 moved.[^c6-2]

**732 个判断里，只有 177 个（24%）在三次运行中逐位完全相同，其余 555 个都变了。**

#### 6.3.2 漂移有多大

| 统计量 | 漂移幅度 |
|---|---|
| 中位 | `0.010` |
| p90 | `0.030` |
| p99 | `0.050` |
| 最差 | `0.070` |

（`g3-17`；作者对最差值的描述是 `Seven hundredths, across 732 decisions, as the single worst thing that happened.`，并给出被标记文章数在三次运行中为 `56、56、57`，`g3-18`。）

漂移的大小还在分布上不均匀（`g3-20`）：

| 分数区间 | 漂移幅度 | 解读 |
|---|---|---|
| 端部（<0.15 / >0.85） | 最小（0.004 / 0.007） | 模型对很明确的情况很稳 |
| 中段（0.40–0.70） | 最大（0.020） | **最不确定的区间也正是漂移最大的区间** |

#### 6.3.3 什么时候漂移会变成"判定改变"

> Of 732 decisions, **12 crossed a threshold and changed the verdict** between runs.[^c6-2]

作者自己解释了这 12 次是怎么发生的：

> The slop_shapes scores across my archive run from 0.36 to 0.85 with a median of 0.55, so the distribution is one compressed lump and 0.70 lands inside the thick part of it.[^c6-2]

素材记录的作者归因是：**12 次翻转中有 10 次源于作者自己的阈值设计**（阈值正好落在分数最密集的区间里），其余与分布形态有关（`g3-22`）。

#### 6.3.4 作者修正了自己的说法

> So Jev is not deterministic in the sense I had claimed, and "the same input gives the same answer" is wrong. "The same input gives an answer within about a tenth" is right[^c6-2]

⚠ 这条修正**只针对打分型输出**，**未涵盖分类型输出**（素材在此处专门加了限定）。也就是说，「同一输入给出大约十分之一以内的答案」这句话，不要顺手搬到 Choice / Noul 的结论上。

#### 6.3.5 一个必须说清的边界

> The gate in front of a live production LLM I have not built or measured yet, so the cost saving I described is reasoning, not a result.[^c6-2]

作者把「用低置信门控挡住生产 LLM 调用」这个想法明确标注为**推理，不是实测结果**。所以这份材料能支持"漂移存在"，**不能**支持"门控能省下多少成本"。

### 6.4 `S13` jev-decision-bench：49 任务 / 8,225 样本

先看独立性声明：

> I have no affiliation with TypeSafe. Run date: 18 September 2026, model jev-1.13.0.[^c6-3]

#### 6.4.1 总成绩与分项

> **Jev matched or beat the LLM baseline on 42 of 49 tasks, at about a seventh of the latency and a quarter of the cost.**[^c6-3]

> Tasks where Jev led / tied / trailed the better baseline | **29 / 13 / 7**[^c6-3]

（分差小于 0.005 记为持平。）

#### 6.4.2 效率与校准误差

| 指标 | Jev | 基线（`gpt-5.6-luna`，低推理强度） |
|---|---|---|
| 中位服务端耗时 | `105 ms` | `710` / `808 ms` |
| 每千条成本 | `$0.04` | `$0.16` / `$0.19` |
| ECE（校准误差） | `0.07` | `0.18` / `0.14` |

（`g3-28`。**ECE 0.07 是这份基准自建口径的计算结果，不是第三方对官方声称的复测**——素材在"开放问题"里专门记录了这一点。）

#### 6.4.3 最关键的一条限定：只有 7 个领先"清楚"

> **clear** means the 95% bootstrap intervals do not overlap. Only seven leads are clear: six for Jev, one for the baseline.[^c6-3]

这一句把 42/49 的读法彻底改写了：所谓"领先"，大多数**落在误差范围内**；统计上站得住的清楚领先一共只有 7 个（Jev 6 个，基线 1 个）。

#### 6.4.4 强项与抗污染证据

- 强项任务：LogiQA 0.77 vs 0.59、WinoGrande 0.89 vs 0.66、ARC-Challenge 0.97 vs 0.87、MMLU 0.94 vs 0.87、NFCorpus reranking 0.73 vs 0.63（`g3-31`）。
- 抗污染证据：代码生成的 120 道新数学题得 `0.75`，与 GSM8K 的 `0.72` 相当（`g3-32`）——说明它的数学能力不太可能只是背下了公开基准。

#### 6.4.5 校准的可用性

> calibration error is about half the baseline's, and keeping only its most confident half of answers raised accuracy by 7.6 points on average.[^c6-3]

「只保留它最有把握的一半答案，准确率平均提升 7.6 个百分点」——**这是本轮材料里最接近"置信度能用"的量化证据**，但请注意它来自该基准的自建口径，不是官方数据的复测。

#### 6.4.6 作者自述的弱项与局限

> counting (0.87 vs 0.99), very large option sets (Banking77 0.81 vs 0.87), and a question plus its negation did not get consistent probabilities (off by 0.32 on average).[^c6-3]

> **Public benchmarks.** Most tasks are well known, and any model may have seen them in training. The only contamination control here is the fresh math task.[^c6-3]

> In a separate private test with around 100 long documents per request, Jev gave high relevance scores to a handful of plainly unrelated documents. Nothing in this repo reproduces that.[^c6-3]

最后这条是作者的**私有观察，素材标注 support: low**：约 100 篇长文档 / 请求的场景下，它对少量明显无关的文档给出了高相关分，**仓库里无法复现**。这条只能作为"存在这样一个观察"记录，不能当结论使用（第七章会再次提到它）。

### 6.5 三方合起来说明了什么

#### 6.5.1 兑现第二章的预告：两套量级差在哪里

第二章留了一个不做并列的对比，现在可以摊开讲清楚了。

| 口径 | 数字 | 测的到底是什么 |
|---|---|---|
| 厂商自报（`g1-7`，厂商口径） | 端到端响应 `70ms-500ms` | 官方在自己的对照表上测的端到端响应，评测多在西海岸笔记本上跑 |
| 第三方实测（`g3-4`，`S11` 口径） | 每题完整响应约 **0.73–0.75 秒** | 一份 50 题中文客服测试里，**每题四项判断全部完成**的完整响应时间 |

两套数字相差约一个量级。**但本轮素材不足以判定差异的原因**：任务不同（客服四项判断 vs 官方的对照任务）、测量口径不同（"完整响应" vs "端到端"）、环境不同（笔记本 vs 未说明）。所以本笔记在这里**只做并列陈述，不做判定**——尤其是，**不得据此宣称厂商数字为假**，也不能反过来认为第三方测错了。

> [!tip] 大白话
> 想成**两家店都卖同一道菜**：一家说"出餐 70 毫秒到 500 毫秒"，另一家的顾客自己掐表测出"0.73 秒"。你没法直接判断谁错——因为一个说的是"端到端"、另一个测的是"整份套餐做完"，连厨房和设备都不是同一套。
> 所以：正确的态度是**"两个都是各自条件下的观测"**，而不是"其中一个在撒谎"。

#### 6.5.2 三方共同指向的那一句话

三份材料从三个不同角度测了同一件事，最后收敛到同一个结论：**官方对一致性的最强表述，只有"相似输入返回相似答案"**（`g1-9` 的用词是 similar，不是 same）。

官方**没有任何「确定性」层面的承诺**。`S12` 测到的 24% 逐位一致率与打分型输出的漂移，`S11` 测到的 3 道题在 15 次重复中通过与失分交替，都落在这个表述的范围之内——它们不是"厂商说错了"，而是**读者如果把 similar 读成 same，就会得到错误的预期**。

#### 6.5.3 还没有的东西

| 缺什么 | 状态 |
|---|---|
| 独立的校准曲线 | **没有**：`S11` 自述不覆盖校准；`S13` 的 ECE 0.07 是自建口径，不是对官方声称的第三方复测 |
| 生产环境具名客户或故障报告 | **没有** |
| 对「零幻觉」的独立对抗性测试（提示注入 / 超长选项集 / 多语言） | **没有** |

这三项是本章——也是全篇——最重要的空白。它们意味着：**关于一致性与置信的结论目前只能来自小规模、自建口径的测试；关于「零幻觉」的类型安全声明，目前没有独立的对抗性验证。**

### 本章小结

- 三份独立来源**不可相加、不可并列比较**：`S11` 是 50 条中文客服题的绝对成绩，`S12` 是 732 个判断的重复运行稳定性，`S13` 是 49 任务 / 8,225 样本对**被刻意限制推理强度的**基线（`g3-1`、`g3-14`、`g3-26`）。

## 第七章：适用边界与已知弱项

前六章分别讲了它是什么、多快多便宜、怎么调用、怎么读结果、别人测出了什么。最后一章换个方向：**什么时候不该用它。**

这一章也是全篇的诚实账本——把第三方一致指出的弱项、必须显式设计的容错、以及本轮**所有未解与待补**一次列清。

### 7.1 不要在 Jev 里做的事

先看第三方给出的最明确的一句边界：

> It does not do arithmetic. It does not compare dates, because it reads them as text rather than as ordered quantities. Extraction of the pieces with it, then do the comparison in code.[^c7-1]

这句话里的**分工**是全篇最实用的一条：**让它负责"抽"，让代码负责"算"和"比"。**

| 不要交给它的任务 | 为什么 | 正确做法 | 依据 |
|---|---|---|---|
| **算术** | 明确弱点，`It does not do arithmetic.` | 用它抽字段，运算交给代码 | `g3-23` |
| **日期比较** | 它把日期**当文本读**，不是当有序量 | 用它抽出日期字段，**在代码里比较** | `g3-23` |
| **计数** | 基准测试中 `counting (0.87 vs 0.99)`，明显落后基线 | 数值统计一律交给代码 | `g3-34` |
| **超大选项集** | `very large option sets (Banking77 0.81 vs 0.87)` | 缩小选项集合，或分层提问 | `g3-34` |
| **问题与其否定式** | `a question plus its negation did not get consistent probabilities (off by 0.32 on average)` | 正反两问交叉校验，或改写问法 | `g3-34` |

#### 7.1.1 日期比较：这条最容易踩，因为它看起来"应该没问题"

问题不在"模型不聪明"，而在**数据的性质**：日期在文本里是字符串，模型读到的是一串字符，而不是一个可以在数轴上排序的量。所以它会"读懂"日期，但**不该指望它排对顺序**。

一个具体对照（**示例，非官方原文**；`g3-23` 只给了"抽出来、在代码里比"这个原则）：

| 做法 | 问法 | 结果 |
|---|---|---|
| ✗ 直接问 | 「订单日期是 3 月 5 日，今天是 3 月 8 日，是否超过 3 天？」 | 需要它做减法与顺序比较——正好落在禁区里 |
| ✓ 拆开做 | 让它抽出字段（例如 `orderDate` 与"是否催单"），**再在代码里比较两个日期的先后与间隔** | 比较交给普通代码完成（无概率、按写死的规则执行），结果可依赖 |

#### 7.1.2 超大选项集：255 是能力上限，不是舒适区

第三章提到 Choice 的选项上限是 **255**（`g2-2`）。把它和 `S13` 的弱项读数放在一起看，结论很清楚：**技术上能塞 255 个选项，不代表 255 个选项时它表现好**——Banking77 那一档的大选项集任务相对基线是落后的（0.81 vs 0.87）。

实用含义：选项集变大时，考虑先做一层粗分类，再在小集合里做第二次选择，而不是把几百个选项一次摊开。

#### 7.1.3 否定式问题：同一个问题正反两问，概率差 0.32

`a question plus its negation did not get consistent probabilities (off by 0.32 on average)`（`g3-34`）。这意味着"客户是否满意"和"客户是否不满意"这两个问法，**不能期望得到互补的概率**。

实用含义：不要用"正问一遍、反问一遍再取平均"这类自认为更稳的技巧；如果确实需要交叉验证，把它当成**两个独立的信号**看，并接受它们可能有明显差异。

> [!tip] 大白话
> 把它的角色想成**一位读得很快的读数员**：让它把仪表上的数字念出来（抽字段）、把材料归类、给个初判，它很擅长；但别让它拿计算器算账、别让它把日期排先后、别指望它数清一百个东西。
> 所以：设计的正确姿势是**"它出字段，代码做运算"**——把需要精确的部分从它手里拿走，交给不会飘的代码。

### 7.2 漂移必须显式处理

第六章的第三方复测给出了漂移的具体形状，这里把它翻译成设计动作：

| 现象 | 数字 | 你要做的设计动作 |
|---|---|---|
| 逐位一致率低 | 三次运行仅 **177/732（24%）** 逐位相同（`g3-16`） | 不要设计任何"重跑一次应该得到同样结果"的隐式依赖 |
| 漂移幅度 | 打分型输出中位 `0.010`、最差 `0.070`（`g3-17`） | 阈值不要卡在分数的密集区 |
| 漂移按区间不均匀 | 端部最小（0.004 / 0.007），中段 0.40–0.70 最大（0.020）（`g3-20`） | 中段判定要额外留余量 |
| 阈值附近的翻转 | **12/732** 跨阈值改变判定；作者自述其中 **10 次源于自身阈值设计**（`g3-21`、`g3-22`） | 设计阈值时留出余量，或**对临界结果二次确认** |

三条配套的注意：

1. **`g3-19` 的修正只针对打分型输出**——作者把自己的说法从"同输入同答案"修正为"大约十分之一以内"，这条修正**未涵盖分类型输出**。不要把它外推成 Choice / Noul 的结论。
2. **门控省钱的量级没有实测**：作者明确说生产 LLM 前的这道门**他还没建、也没测**，成本节省属于推理而非结果（`g3-24`）。所以不要拿"省多少钱"作为立项依据。
3. **这不是"厂商说错了"**：官方对一致性的最强表述一直是「相似输入返回**相似**答案」（`g1-9`）。上面这些读数是**在官方表述范围内**的观测；踩坑的往往是读者把 similar 读成了 same。

> [!tip] 大白话
> 想成**体温计有 ±0.1 度的读数波动**：你把"发烧线"画在 37.5 度，正好有一批人体温就在 37.5 上下——同一个人今天量出 37.4、明天量出 37.6，于是"今天没发烧、明天发烧"，而这和病人有没有好转没关系。
> 所以：**阈值不要画在分数最密的地方**；要么把线挪开一点，要么对压在线上的人再量一次。

### 7.3 一个必须纠正的误读：「零幻觉」不是「判断不会错」

第一章拆过这一层，这里再收一次口，因为它是全篇最容易被转发错的句子。

| 误读 | 事实 | 依据 |
|---|---|---|
| 「零幻觉」= 它的判断不会出错 | 保证的只是**答案形状**——schema 匹配有数学保证（`This would be an easy thing to falsify with just a single counter-example, but it is mathematically impossible.`），而图中那个 0% **不是实测值**（`Our number is not empirical...`） | `g1-11`、`g1-12` |
| 「放弃了字符串生成」= 它比 LLM 弱 | 那是**取舍**（`While Jev gives up string generation...`），代价是不能指望它写段落、做长文本生成 | `g1-4` |
| 「置信度高 = 答案正确」 | `confidence` 只反映**分布的形状**（由分布算出、越平越低）；官方与准确率的关系只给了方向性表述，没有曲线、没有阈值 | `g1-28`、`g1-30`[^c7-5]、`g1-9`[^c7-4] |

一句话记法：**不越出 Schema ≠ 判断正确。** 形状正确和内容正确是两层不同的保证，前者是数学性质，后者要靠你自己的评测集去量。

### 7.4 一条需要打低置信的观察

`S13` 的作者还留下一条无法复现的私有观察：

> In a separate private test with around 100 long documents per request, Jev gave high relevance scores to a handful of plainly unrelated documents. Nothing in this repo reproduces that.[^c7-2]

素材对这条的标注是 **support: low**。也就是说：

- 它是一条**真实存在的报告**（约 100 篇长文档 / 请求的场景下，对少量明显无关文档给出高相关分）；
- 但**仓库里无法复现**，也没有第三方重复过；
- 因此它**不能当结论使用**——既不能据此说"长上下文场景不可靠"，也不能因为无法复现就当作不存在。

如果你恰好要做长文档相关性判断，把它当成一条**值得自查的线索**：在你的评测里专门放几条明显无关的文档，看看会不会得到高相关分。

### 7.6 全篇要点回顾

| 章 | 一句话结论 |
|---|---|
| 一 | Jev 是厂商自定义的「System One Model」类别，为**软件可直接消费的快速结构化决策**而建；输出空间事先定义，代价是**放弃字符串生成**；「零幻觉」只保证不越出 Schema（`g1-1`、`g1-2`、`g1-4`、`g1-11`、`g1-12`） |
| 二 | 厂商自报：端到端 `70ms-500ms`、`40x-200x faster`、输入 `$0.042/MTok`、输出免费；**每条都自带限定**（自选偏差、西海岸笔记本、无法证明未被补贴），且**无第三方规模化复测**（`g1-3`、`g1-7`、`g1-8`） |
| 三 | 一次调用 = `state` + `questions` → `answers`（键一一对应）；三原语 **Noul / Choice（字典 criteria，≤255）/ Score（列表 criteria）**；`state` 免序列化；Python SDK 需 ≥3.10、读 `TYPESAFE_API_KEY`（`g1-15`、`g1-16`、`g1-17`、`g1-18`、`g2-1`、`g2-2`、`g2-5`、`g1-24`、`g1-25`） |
| 四 | **`probability` ≠ `confidence`**；`confidence` 只在 Choice / Score 上（Noul 没有）、是答案对象自己的属性、不等于最高选项概率；**没有普适阈值**，按领域自测标定并按风险上调，低置信**不执行动作**（`g2-8`、`g1-27`、`g1-28`、`g1-19`、`g1-33`、`g2-11`、`g1-32`） |
| 五 | **输入 token 是唯一付费项**（上限 64,000 / state 32,000），只传决策依赖的字段；三个官方模式：投机性多问、置信度门控路由、多维合成分；生态接入点只有调用面形态可确认（`g2-12`、`g1-36`、`g1-38`、`g1-39`、`g1-40`、`g2-9`） |
| 六 | 三方独立数据**不可并列比较**：`S11` 第三方口径约 **64%–65.2%**、每题约 **0.73–0.75 秒**；`S12` 逐位一致率 **24%**、**12/732** 跨阈值翻转；`S13` 42/49 但**仅 7 个领先清楚**，基线是被刻意限制推理强度的 `luna`（`g3-3`、`g3-4`、`g3-16`、`g3-21`、`g3-25`、`g3-30`） |
| 七 | 禁区：**算术、日期比较**（抽字段、在代码里比）、计数、超大选项集、否定式；漂移必须显式处理（阈值留余量 / 临界二次确认）；**不越出 Schema ≠ 判断正确**（`g3-23`、`g3-34`、`g3-17`、`g3-21`、`g1-11`） |

三条贯穿全篇的纪律，比上面任何单个数字都更值得带走：

1. **来源性质要标清**：厂商自报（vendor-spec）与第三方实测（`S11`/`S12`/`S13`）是不同证据等级，不能写成同一句话。
2. **限定条件与数字同行**：任何数字离开它的测量条件就不构成结论。
3. **未读到的东西不写**：待补、未解、support: low 都如实标注，不用猜测补全。

#### 7.7.2 下一步：把这篇用起来

建议按这个顺序动手，每一步都对应本篇的一章：

1. **写一次调用**——按第三章 3.7 的检查表组织 `state` 与 `questions`，先用三个原语各问一个问题，确认响应结构。**注意那张表里标"需核对"的项要先回官网原页确认。**
2. **做一次门控**——按第四章的规则给一个动作定阈值（起点：置信度 ≥0.6 **且** 选中项概率 ≥0.7，再按动作风险上调），低置信时走"不执行动作 → 转人工 / 请求澄清 / 降级"。
3. **复核你的问题设计**——用本章 7.1 的弱项清单过一遍：你的问题里有没有算术、有没有日期比较、有没有计数、选项集是不是过大、有没有依赖正反问法一致的假设。有就挪回代码。

做完这三步，你对这个模型的判断就不再来自任何一篇文档，而来自你自己的数据——**那才是本轮所有数字都替代不了的东西。**
