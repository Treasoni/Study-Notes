# LLM 提示词缓存优化策略

## 核心思路

> [!abstract] 核心观点
> 缓存不是"少传 token"就会命中，而是让高频请求拥有尽可能长、尽可能稳定的前缀。

减少总输入量只是 **Token 优化**的目标，**缓存优化**追求的是重复输入的前缀一致性——即使总 token 不多，每次动态拼接不同内容也会让缓存收益很低。

---

## 1. 区分两类成本

| 维度 | Token 优化 | 缓存优化 |
|------|-----------|---------|
| 目标 | 减少总输入输出量 | 复用已处理的上下文 |
| 手段 | 精简提示词、缩短输出 | 保持重复输入前缀一致 |
| 关系 | 两者最好同时做 | 但"少"不等于"稳定" |

> [!note] 缓存优化的本质不是做减法，而是做**结构化**——把变化的部分隔离到末尾，让不变的部分形成稳定的前缀。

---

## 2. 找出高频且变化小的内容

以下内容应进入稳定前缀：

- **系统规则**：项目级约束、安全策略、行为指南
- **角色说明**：Agent 身份、职责边界、行为模式
- **输出格式**：JSON Schema、Markdown 模板、代码格式化要求
- **固定工作流**：阶段定义、检查项、状态流转规则
- **工具使用约束**：可用工具列表、调用限制、参数规范
- **示例**：少量固定范例，不应频繁更换

---

## 3. 从策略到制度化：项目级落地

> [!tip] 关键洞察
> 缓存优化最有效的方式不是靠每次临时记得，而是**把策略固化为项目级规则文件**。

在项目仓库中放置以下 4 类文件，让缓存优化成为项目的默认行为：

| 文件 | 用途 |
|------|------|
| `AGENTS.md` / `CONTRIBUTING.md` | 入口规则：默认不读什么、什么时候按需读、上下文如何分层 |
| `rules/prompt-cache.md` | 专门约束 prompt 的组装方式，确保固定内容在前、动态内容在后 |
| `prompts/` 或 `templates/` | 把子代理、摘要、代码审查等高频提示词固化为模板 |
| `scripts/measure-cache.*` | 记录缓存读取 token、输入 token、调用类型，验证优化效果 |

实际落地时，**优先做三件事**：

1. 先写 `rules/prompt-cache.md` — 把提示词组装规则固定下来
2. 把最常用的 2-3 个子代理提示词模板化 — 放入 `prompts/` 目录
3. 接入 token / cached-token 日志 — 验证优化效果并持续监控

---

## 4. 固定提示词结构

### 4.1 通用结构

始终按同一顺序组织提示词：

```
[固定系统/项目规则]
[固定角色职责]
[固定输出格式与限制]
[固定示例或少量范例]

[动态参数]
- 用户请求
- 当前文件路径或局部片段
- 时间、ID、进度、git 状态
```

> [!warning] 关键规则
> 动态内容一定放后面。不要在请求开头插入时间戳、随机 ID、实时状态、完整待办列表。**前缀的任何"抖动"都会导致缓存 miss。**

### 4.2 Prompt-Cache 规则文件参考

可直接在项目中创建 `rules/prompt-cache.md`，内容如下：

```markdown
# Prompt Cache Rules

## Prompt Structure

所有高频请求按以下顺序拼装：

1. 固定角色与任务边界
2. 固定输出格式、约束和工具规则
3. 固定少量示例（仅在确有必要时）
4. 动态参数：用户请求、文件片段、时间、任务状态

## Stability

- 不在提示词前缀加入时间戳、随机 ID、git status、实时待办。
- 不随意调整固定规则的顺序、标点、空行或措辞。
- 高频子代理必须复用同一模板。
- 动态变量统一放在 `参数：` 区块，且位于提示词末尾。

## Context Loading

- 优先传文件路径、标题、锚点和摘要；仅在需要时读取局部正文。
- 不默认加载示例、历史对话、镜像目录、构建产物或无关规则。
- 长文档拆分为入口说明、模板、参考资料三层。

## Verification

每次调整后检查：
- 相同类型请求的前缀是否一致
- 动态数据是否只出现在末尾
- 缓存读取 token 是否上升
- 总输入 token 是否下降
```

## 5. 将"大而少用"的内容延迟加载

把完整案例、参考资料、长篇规则拆成 **入口文件** 和 **按需引用文件**。每次只加载当前任务需要的章节、锚点或检索结果，而不是把整个仓库、所有技能说明都塞进上下文。

```markdown
# ❌ 错误做法
加载所有模板 → 所有规则 → 所有历史 → 再执行任务

# ✅ 正确做法
加载当前任务模板 → 按需引用规则文件 → 只读相关片段
```

---

## 6. 子代理使用固定模板

> [!tip] 子代理最容易因为每次 prompt 改写而失去缓存。固定职责、边界、输出格式，最后再注入参数。

将高频子代理提示词存放在 `prompts/` 或 `templates/` 目录下，不让每个调用点各写一份：

```
project/
  prompts/
    research.md      # 资料收集
    review.md        # 代码/文档审查
    summarize.md     # 摘要生成
```

模板结构示例：

```markdown
你是资料收集助手。
只返回结构化摘要。
每条包含：标题、链接、摘要、可信度。
禁止返回网页正文和无关导航。

参数：
- 主题: {topic}
- 关键词: {keywords}
- 信源限制: {sources}
```

模板本身形成稳定的前缀缓存，只有末尾的 `{参数}` 部分变化。

---

## 7. 减少无意义的上下文波动

- 不要默认读取镜像目录、构建产物、重复配置
- 避免每轮自动生成状态文件、自动提交
- 避免把变化后的 git diff 自动注入提示词
- 状态应写在文件中，只有任务需要时才读取

> [!tip] 原则
> 每一次上下文变化都应有明确的目的，变化的内容应尽可能集中在末尾。

---

## 8. 建立可观测性

为请求记录以下指标：

| 指标 | 用途 |
|------|------|
| 输入 token | 基础用量 |
| 缓存读取 token | 复用了多少缓存 |
| 缓存写入 token | 新创建了多少缓存 |
| 缓存命中率 | 提示词稳定性的直接反映 |
| 请求类型 | 区分不同模板的缓存表现 |

在项目中放置 `scripts/measure-cache.sh` 或类似脚本，用于记录 LLM 调用的 token 消耗和缓存表现。按"命中率低且调用频繁"的提示模板优先治理。

缓存命中通常依赖以下条件：

- 相同模型
- 相同工具定义
- 足够一致的前缀

具体阈值以所用平台为准。

---

## 9. 一句话总结

> [!abstract] 核心原则
> 把规则和模板做成稳定的"壳"，把用户输入、文件片段和实时状态做成末尾可替换的"参数"。并且，**把这些策略固化为项目目录中的规则文件**，不要依赖每次临时记得。
