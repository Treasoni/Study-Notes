## 第一章 总览：经营场景拆解与开源工具全景地图

> 本章定位：先在地图上找到自己的位置，再决定走哪条路。这是「对比/选型盘点」笔记的总览章，只搭框架、不展开工具细节，后续各章按场景逐一深讲。

### 1.1 先拆场景：经营小红书/抖音的五个可工具化环节

很多人以为「用开源工具做小红书/抖音」等于「找一个一键发布的软件」，但真实经营是一条流水线，每个工位能被工具替代的程度完全不同。把这条流水线拆成五个环节：

| 环节 | 要解决的核心问题 | 代表性工具形态 |
|---|---|---|
| 自动发布 | 定时/批量把成品发到多个账号 | 浏览器自动化 + cookie（如 [[social-auto-upload 配置与使用指南|social-auto-upload]] 类） |
| 内容生产 | 从选题文案到成片/图文 | AI 文字成片、本地智能剪辑 |
| 一体化编排 | 「AI 生产 → 排期 → 发布」串成一条链 | 一站式内容营销平台 |
| 数据运营 | 自家账号复盘、竞品/对标观察 | 官方数据接口、自账号取数、采集器 |
| 合规选型 | 判断某个工具「能不能用、怎么用不踩线」 | 协议 + 平台条款 + 判例（横切所有环节） |

前四个是纵向业务环节，第五个「合规选型」是横切维度：它不产出内容，但决定前四个环节里哪些工具能进你的生产环境。本文全部候选工具，最终都会回到这一维打分。

[!tip] 大白话
把「经营两个平台」想成开一家内容工坊：生产间（做内容）、发货台（发内容）、调度室（编排）、监控台（看数据），外加一张贴在墙上的红线图。开源世界里没有「一个万能软件」，你是在为每个工位选趁手工具，并随时拿红线图对照。

### 1.2 候选全景：7 核心 + 4 边缘 + 2 显性缺口

盘点共 13 个坐标点（据深度研究素材 §1–§3）。核心候选首次出现给中文定位 + 仓库名，后续章节用简称展开：

#### 7 个核心候选（逐章深讲）

| 工具（中文定位 · 仓库） | 归属环节 | 一句话初判 |
|---|---|---|
| 自动发布标杆 social-auto-upload（`dreammis/social-auto-upload`，MIT） | 自动发布 | 11 平台视频上传，图文仅抖音/小红书/快手；供 AI Agent 调用的发布通道 |
| AI 内容营销一体化 AiToEarn（`yikart/AiToEarn`，MIT） | 一体化编排 | 生产/排期/发布/互动四大 Agent，入口多；云依赖边界待第 5 章核实 |
| 文字一键成片 MoneyPrinterTurbo（`harry0703/MoneyPrinterTurbo`，MIT） | 内容生产 | 文案→配音→字幕→成片全自动，GPU 非必需，维护活跃 |
| 本地智能剪辑 FunClip（`modelscope/FunClip`，MIT 源码） | 内容生产 | ASR 按句/说话人切段，本地运行，适合剪辑提效 |
| 数据采集事实标准 MediaCrawler（`NanmiCoder/MediaCrawler`，自定义非商用许可） | 数据运营 | 多平台采集；明示「仅学习研究、禁商用」 |
| 互动管理面板 CreatorHub（`3441293738/creatorhub`，license=null） | 数据运营 | 评论/私信/多账号面板；未声明标准开源协议，需谨慎判断 |
| 自账号取数 xhs_douyin_content（`cwjcw/xhs_douyin_content`，GPL-3.0） | 数据运营 | 抓自家创作者中心作品数据，属合规风险相对低的一类 |

#### 4 个边缘候选（不进正章，仅在相关章节简评）

- **可视化发布面板 MediaPublishPlatform**：Flask + Vue3 + Playwright，star 少需自测。
- **AI 短视频框架 ShortGPT**（`RayVentura/ShortGPT`）：已停更（2025-02 后无提交），仅作架构参考。
- **采集 + 展示一体 Visual_MediaCrawler**：MediaCrawler 派生，继承非商用许可，star 少。
- **多平台分支 omnipost**：social-auto-upload 衍生（另加头条/搜狐/知乎），仅 1 commit，质量依赖上游。

#### 2 个显性缺口（暂无好用现成方案）

1. **官方数据分析能力**：抖音开放平台虽有数据接口但门槛苛刻（粉丝≥1000、T+1 刷新、需逐项申请），小红书个人/专业号几乎没有批量导出 API——中小账号「官方口径数据复盘」的开源侧接近空白（第 6 章展开）。
2. **合规/风控边界**：自动化发布与采集的协议、司法边界没有工具能替你规避，只能靠选型判断（第 8 章收口）。

### 1.3 全文选型标尺：四维打分

后续每章都用四个问题给工具打分，避免「只看 star 数」：

1. **是否官方授权**：走官方开放平台/创作者中心，还是自建 cookie/浏览器自动化？
2. **是否标准开源协议**：MIT/Apache/GPL 等 OSI 协议，还是自定义非商用许可或干脆不声明协议？
3. **是否纯离线**：Docker 跑在自己机器 ≠ 数据不出网——是否仍硬依赖厂商云端 Key/Relay？
4. **维护活跃度**：近期是否有提交、issue 是否有人应答？停更项目只作历史参考。

[!tip] 大白话
把「开源协议」想成一份授权清单，它写明你能拿这套代码做什么。MIT 这类标准协议边界清楚（说能商用就真能商用）；「自定义非商用许可证」或「不声明协议」则像只在特定前提下把工具借你用，商用前必须自己确认，不能想当然。

[!tip] 大白话
「自部署」和「离线」是两回事：自部署像把店开在自己家，但食材仍可能由中央厨房统一配送。AiToEarn 即使 Docker 自部署，也可能强依赖官方 Relay/Key，所以第 5 章会专门核对它的云依赖边界。

### 1.4 风险分级预览

合规不是说教，而是选型的一部分。全篇把候选工具按风险分三层，细节在第 8 章汇总：

- **第一层 · 官方授权渠道**（抖音 OpenAPI、创作者中心导出）——风险最低，优先选用。
- **第二层 · 自账号 cookie/Playwright 取数**（xhs_douyin_content 一类）——自家数据，但走的是平台未必许可的通道，登录态需人工维护，风险中等。
- **第三层 · 爬他人公开数据 / 自动化发布 / 刷量与自动互动**（MediaCrawler 商用、AiToEarn Engage、CreatorHub 自动互动）——同时触碰平台条款与个保法/反不正当竞争法，风险最高。

[!warning] 合规与风控提示
凡涉及 cookie、浏览器自动化或自动互动的工具（social-auto-upload、CreatorHub、MediaCrawler 等），都可能违反平台用户协议；爬取他人数据还可能涉及个人信息保护与不正当竞争。本文仅做知识与选型盘点，标注「学习研究」用途的工具不得用于商用。抖音自动化发布/采集、小红书自动化批量同质内容均属平台明令禁止（详见第 6、8 章及各章风控 Callout）。

## 第二章 自动发布与多平台分发：social-auto-upload 深讲与同类简评

> 本章定位：内容做出来之后，怎么高效地铺到多个平台？这是「自动发布」环节的深讲章。我们以自动发布标杆 [[social-auto-upload 配置与使用指南|social-auto-upload]] 为主线，讲清它的能力边界、部署与登录态维护、已知的坑，再简评两个同类边缘工具。本文是**盘点视角**：完整安装与排错教程见既有笔记 [[social-auto-upload 配置与使用指南|social-auto-upload]]，本章不重复教程正文，只回答「它在全景里值不值得用、坑在哪、同类里怎么选」。

### 2.1 一句话定位与四维打分

在第 1 章拆出的五个环节里，自动发布负责把成品从本地搬到各平台账号上。social-auto-upload（仓库 `dreammis/social-auto-upload`）是这个环节的事实标杆：它不调用任何平台官方上传 API，而是用浏览器自动化**像真人一样登录并操作上传页**，把「逐个网页手工分发」固化成一条条 `sau` 命令。

沿用全文统一标尺做四维打分 [SAU-R](https://github.com/dreammis/social-auto-upload)：

| 维度 | 结论 | 说明 |
|---|---|---|
| 是否官方授权 | ❌ | 非开放平台 API，靠 patchright 驱动 Chromium + cookie 登录态模拟真人 |
| 是否标准开源协议 | ✅ MIT | 标准 OSI 协议，可商用（含闭源场景）；约 14.8k★ |
| 是否纯离线 | ✅ | 零云依赖：全部逻辑在本地 Python + chromium，不需要任何厂商 Key/Relay |
| 维护活跃度 | ✅ | 末提交 2026-09-02；2026-03 作者回归后进入密集重构，迭代快 |

[!tip] 大白话
把「官方授权 vs cookie 自动化」想成进商场两种方式：官方 API 是商场发的正规入场券（合规但门槛高）；social-auto-upload 是让一个替你干活的店员拿着你自己的会员卡去柜台办业务——卡是你本人的，但「店员代办」这件事商场未必允许。所以它能用，但存在违约风险（见本章风控 Callout）。

### 2.2 能力边界：能发什么、不能发什么

先看它能做什么，再看它**刻意不做什么**，边界比功能更重要。一张表看清 [SAU-R](https://github.com/dreammis/social-auto-upload)：

| 能力 | 覆盖范围 | 关键备注 |
|---|---|---|
| 视频上传 | 11 平台 | 抖音/B站/小红书/快手/视频号/百家号/支付宝生活号/微博/虎扑/YouTube/TikTok |
| 图文上传 | 仅抖音/小红书/快手 | 只有这 3 家支持 `upload-note`，其余平台找图文参数是浪费时间 |
| 定时发布 | README 矩阵列 6 平台 | 抖音/B站/小红书/快手/视频号/TikTok；CLI 实际可排期 **5 平台**（TikTok 尚未接入 CLI，见 2.5） |
| 多账号并发 | 每账号独立登录态 | 一个账号名 = 一个 cookie 文件，互不串号，可并行跑多条命令 |
| B站能力 | 封装自 biliup | B站上传内核复用 biliup，首次运行自动下载 |
| 数据看板 | ❌ 无 | 发完即走，不负责播放/涨粉复盘（那是第 6 章的事） |
| REST API | ❌ 无 | 不是常驻服务，是命令；供人/AI Agent 调用的进程入口 |

读这张表最该记住两条结论：**图文能力极稀缺，只有抖音/小红书/快手三行是 ✅**；**它只做「发」，不做「看」**——没有看板、没有 API，别拿它当运营管理平台。

### 2.3 定位真相：它是给 AI Agent 用的「发布通道」

为什么一个没有看板、没有 API 的工具会被当作标杆？因为它的设计定位根本不是「人类后台」，而是**供 AI Agent 调用的发布通道**：把「登录态维护好」之后，Agent 只需拼一条 `sau` 命令，就能把成品发到指定账号。仓库为此直接提供了抖音/小红书/快手/B站的 Skill，适配 Claude Code / OpenClaw / Codex 这类 Agent 环境 [SAU-R](https://github.com/dreammis/social-auto-upload)。

统一命令骨架只有一句话：

```bash
# 统一骨架：sau <平台> <动作> --account <账号名>
sau douyin upload-video --account demo \
  --file demo.mp4 --title "标题" --desc "描述"
```

对照第 5 章可知：AiToEarn 走的是「SaaS + 云 Relay」通道，而 social-auto-upload 走的是「本地 cookie」通道——正是这条差异，让它成了「纯离线 AI 生产 → 发布」组合里发布侧的首选（第 5 章细比）。

[!tip] 大白话
把 Agent 调 `sau` 想成你雇了个实习生：你把各平台的门禁卡（cookie 文件）都办好放在抽屉里，实习生只需要知道「拿哪张卡、去哪个平台、交哪份材料」（一条命令），就能替你跑腿。它不需要理解每个平台网页怎么点——那是 social-auto-upload 替它做的事。

### 2.4 部署与登录态维护（盘点视角，不重复教程）

部署主线一句话：**`uv` + patchright 驱动 Chromium**，Python 要求 `>=3.10,<3.13`。完整分步安装见 [[social-auto-upload 配置与使用指南|social-auto-upload]] 第 2 章，这里只给「先睹为快」的提醒片段 [SAU-I](https://github.com/dreammis/social-auto-upload/blob/main/docs/install.md)：

```bash
# 安装主线（完整教程见既有笔记 [[social-auto-upload 配置与使用指南|social-auto-upload]]，勿照抄第三方 pip+playwright 旧教程）
uv venv && uv pip install -e .          # 建环境 + 装依赖 + 注册 sau
patchright install chromium             # 下载浏览器内核；国内慢先设 PLAYWRIGHT_DOWNLOAD_HOST 镜像
cp conf.example.py conf.py              # 生成个人配置
```

登录态维护是这套工具最核心的日常操作，模型很固定：**一个 `account_name` = 一个账号文件**，落在 `cookies/[平台]/[平台]_[账号].json`。新平台首次用要人工登录一次，之后 `login` / `check` 就是唯一需要关心的命令：

```bash
# 首次登录（人工扫码或短信码）→ 之后发布前校验
sau douyin login --account demo     # 触发登录：抖音短信码写项目根目录 verify_code.txt（用完自动删除）
sau douyin check --account demo     # 校验登录态：出现登录 UI 即判失效
```

两个登录细节值得单独记：**抖音短信验证码**不是直接喂给命令，而是写进项目根目录 `verify_code.txt`，工具读到后自动提交并删除该文件；**B站建议本地扫码**完成登录，而不是短信。

[!tip] 大白话
把 `verify_code.txt` 想成递给门卫的一次性字条：你收到短信验证码后把它写在字条上塞进门缝，门卫看完当场撕掉（自动删除）。这个设计天生适合 Agent 场景——程序只负责「要码、写文件」，人只负责「看手机、报码」，登录就能自动化走完且不留残余。

[!warning] 文档口径提醒
README 与 install 文档对浏览器驱动的表述**互相矛盾**：README 的「重构计划」把 patchright 写成待更换项，install 文档却把 patchright 当作当前主线。实践判定：`sau` CLI + uv + patchright 即当前主线，一切以最新代码 + [docs/install.md](https://github.com/dreammis/social-auto-upload/blob/main/docs/install.md) 为准；看到第三方教程教你 `pip install playwright` 或强依赖 `LOCAL_CHROME_PATH`，先默认它已过时（详见既有笔记 [[social-auto-upload 配置与使用指南|social-auto-upload]] 第 2.3 节）。

### 2.5 已知的坑与能力缺口

工具不是没有代价。盘点视角下最值得知道的三个坑 + 一个缺口：

| # | 坑 / 缺口 | 影响 | 应对 |
|---|---|---|---|
| 1 | **登录态人工维护，无自动失效刷新** | cookie 过期后不会自愈，命令会「发到一半才发现失效」 | 养成发布前 `check` 的习惯；失效就重登一次，把登录态固化进文件后再无头跑 |
| 2 | **README 与 install 对 patchright 表述矛盾** | 只读 README 的用户会以为驱动要换，部署时被旧教程带偏 | 认准 install 文档 + 最新代码；见 2.4 的文档口径提醒 |
| 3 | **无数据看板、无 REST API** | 发完即走：看不到发布结果数据，也无法作为常驻服务被业务系统调用 | 接受它「发布通道」的定位；要复盘数据走第 6 章合规路径 |
| 4 | 平台改版致元素失效、headless 登录被风控 | login/check 卡住、超时或误判（真实案例见 GitHub Issues #224/#230） | 先 `git pull` 升最新代码再排查；高风控场景复用真实浏览器登录态——完整排错表见 [[social-auto-upload 配置与使用指南|social-auto-upload]] 第 6 章 |

缺口 3 是最容易被低估的：很多人以为装了它就有「多平台运营后台」，实际上它连「这条视频发出去有没有播放」都不负责。它的边界就是「发出去」，发出去之后的事请交给第 6、7 章的数据工具。

[!tip] 大白话
把「登录态无自动刷新」想成门禁卡到期不提醒：卡还能用时一切正常，某天突然刷不开门你才知道到期了。所以靠谱的做法不是等它失效，而是每次出门前先刷一下闸机（`check`）——确认卡还能用再办事。

### 2.6 同类简评：可视化面板与衍生分支

自动发布方向并非只有它一个。第 1 章列的 4 个边缘候选里，有两个与它同属发布环节，都进不了正章，这里一并简评（据深度研究 §3.9）：

| 工具 | 定位 | 与 social-auto-upload 的差异 | 一句话结论 |
|---|---|---|---|
| **MediaPublishPlatform** | Flask + Vue3 + Playwright 的**可视化**批量/定时发布面板，约 9 平台 | 有 Web 界面，不要求命令行；但约 153★、star 少 | 想要可视化后台可试，但需自测稳定性，别当生产级依赖 |
| **omnipost** | social-auto-upload 的**衍生分支**，另加头条/搜狐/知乎 | 在别人地基上盖楼；仅 1 commit | 增量太小、质量依赖上游，除非正好缺那 3 个平台否则不推荐 |

选型含义很清楚：如果你能接受命令行/Agent 调用，social-auto-upload 是发布侧更稳的选择；如果你「非要可视化界面不可」，MediaPublishPlatform 是唯一可试的同类，但要对它的成熟度有心理准备。

### 2.7 与既有笔记的关系及风险提示

本节收口两点。

**与既有笔记的分工**：[[social-auto-upload 配置与使用指南|social-auto-upload]] 是「配置与使用指南」——零基础上手、逐条命令、完整排错，解决「怎么装怎么用」；本章是「盘点评估」——解决「在全景里它值不值得选、坑在哪、同类里怎么比」。两者互链，阅读时教程细节请跳转既有笔记，本文不再展开。

**风险定级**：按第 1 章的三层框架，social-auto-upload 属**第二层风险**——发的是自家账号的自家内容，不是爬取他人数据，但「cookie + 浏览器自动化」本身已踩平台用户协议里「禁止第三方自动化工具接入」的条款。

[!warning] 风控与合规提示
用 cookie/自动化方式发布，无论发的是不是自己的内容，都可能违反抖音/小红书等平台的用户协议：平台明令禁止自动化程序或第三方工具批量接入，违规轻则限流、重则封号。social-auto-upload 属第二层风险（自账号、自内容，风险中等），但一旦升级为「矩阵批量发布」「搬运他人内容」或「刷量」用途，就跨入第三层高风险，还叠加不正当竞争与版权风险。自动化发布前请先评估账号价值与合规底线，完整红线与判例见第 8 章。

## 第三章 AI 内容生产（一）：MoneyPrinterTurbo 文字一键成片

> 本章定位：内容生产环节的头号工具。第 1 章把经营拆成五个环节，「内容生产」是决定产能的一环——批量起号缺的不是创意，是把选题快速变成初稿的速度。MoneyPrinterTurbo 恰好补上这一环：给一句话，它把文案、配音、字幕、素材、剪辑整条流水线替你跑完，产出的成片可直接投喂第 2 章的发布通道。

### 3.1 一条流水线：从一句话到一条可发布成片

MoneyPrinterTurbo（`harry0703/MoneyPrinterTurbo`，MIT）约 120.7k★，v1.3.6（2026-09-02），提交活跃，是内容生产环节星标最高、维护最勤的项目 [MPT-R](https://github.com/harry0703/MoneyPrinterTurbo)。它把「文字一键成片」做成了全自动链路：

| 环节 | 做什么 | 默认谁来干 |
|---|---|---|
| 输入 | 只需一个主题或几个关键词 | 你 |
| 文案 | 扩写成口播脚本 + 画面关键词 | LLM |
| 配音 | 脚本转语音 | TTS（默认免费 Edge TTS） |
| 字幕 | 生成时间轴并渲染进画面 | edge 时间戳 / whisper 转写 |
| 素材 | 按关键词取画面片段 | Pexels / Pixabay / Coverr 在线素材 |
| 剪辑 | 拼接、转场、配乐、合成导出 | 本地 ffmpeg |
| 输出 | 一条带字幕的 mp4 | — |

输出画幅三档可选：**9:16 竖屏**（1080×1920，抖音 / 小红书信息流）、**16:9 横屏**（1920×1080，西瓜 / B 站向）、**1:1 方形**（1080×1080）。一次可生成多条（`video_count`）、文案段落数、字幕开关等都可调 [MPT-R]。

[!tip] 大白话
把 MoneyPrinterTurbo 想成一家「文字进、成片出」的内容中央厨房：主笔（LLM）写稿、主播（TTS）念稿、采买（素材源）找画面、剪辑师（ffmpeg）合成装盒。你不需要亲自掌勺，只要下订单时写清主题、选好规格（竖屏 / 横屏 / 方形），出锅后负责试吃把关。所以它的上手门槛很低，真正的功夫全在「下订单」和「验收」这两端。

### 3.2 四种用法：Agent / WebUI / API / CLI

官方明示四种使用方式，「既能快速上手，也能接入自动化流程」[MPT-R]：

| 用法 | 入口 | 适合谁 |
|---|---|---|
| Agent | 把官方 Skill 文档交给能读文档并操作终端的 AI Agent（如 Claude Code 类），一句话让它自动安装、配置、生成 | 不想手动配置；想把成片编进 Agent 工作流 |
| WebUI | http://127.0.0.1:8501（Streamlit 界面） | 第一次体验、单条生成、在界面里挑音色与参数 |
| API | http://127.0.0.1:8080/docs（FastAPI OpenAPI），`POST /api/v1/videos` | 程序批量调用、n8n 等编排、Agent 编程式调用 |
| CLI | `uv run python cli.py --video-subject "..."` | 无浏览器 / SSH 环境、批量清单（`--batch-file`，上限 100 条） |

Agent 用法的意义在于它把「成片能力」变成可编排的一环：AI Agent 写完选题后直接调本地 MPT 出片，再转给第 2 章的 social-auto-upload 发布通道，就是一套「选题 → 成片 → 发布」的串链雏形；第 5 章会拿它和一体化平台 AiToEarn 做整体对比。

### 3.3 部署与依赖边界：GPU 非必需，重点是 Python ≥ 3.11

部署门槛在同级工具里算低：

- **语言**：Python 3.11+；本地跑推荐用 `uv sync` 或 Windows 一键启动包 [MPT-R]。
- **硬件**：官方给的最低配置是 4 核 CPU / 4 GB 内存，**GPU 非必须**。若主要依赖云端 LLM、在线素材和默认 Edge TTS，CPU 与内存比 GPU 更重要；只有启用本地 whisper 字幕、批量生成等更重的本地链路时，GPU 才明显提速 [MPT-R]。
- **镜像**：官方推荐 `docker-compose.release.yml`，直接拉取 GHCR 预编译镜像 `ghcr.io/harry0703/moneyprinterturbo:latest`；WebUI 服务映射 127.0.0.1:8501，API 服务映射 127.0.0.1:8080。仓库同时提供 **.gpu 版**（`docker-compose.gpu.yml` + `Dockerfile.gpu`，本地构建，需本机 NVIDIA 驱动 + NVIDIA Container Toolkit），用于 GPU 跑 Whisper 字幕 [MPT-R]。

起服务：

```bash
# 方式一：拉 GHCR 预编译镜像（推荐，无需本地构建）
cd MoneyPrinterTurbo
cp config.example.toml config.toml     # 先复制出配置文件，填好 Key 再启动
docker compose -f docker-compose.release.yml up -d
# 随后打开 WebUI  http://127.0.0.1:8501
#        API 文档  http://127.0.0.1:8080/docs

# 方式二：需要 GPU 跑本地 Whisper 字幕时才本地构建 GPU 版
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build
```

字幕默认走 **edge**（用 TTS 时间戳生成，速度快、免 GPU）；只有要更准字幕时间轴时才切 **whisper**（本地 faster-whisper 转写，首次需下载模型）[MPT-R]。

[!tip] 大白话
把容器跑在自己机器上，想成「把中央厨房开在自己家」——但食材仍由第三方供应：文案要调云端 LLM，配音默认走微软 Edge TTS（在线、免费），素材从 Pexels 等在线图库拉取。真正离线的是本地 whisper 字幕与最后的 ffmpeg 合成。这再次印证第 1 章的提醒：**自部署 ≠ 离线**，这条生产链路是「自托管」，不是「断网可跑」。

### 3.4 可选服务清单与配置

整条链路除了剪辑，几乎每步都可换供应商，配置统一收敛在 `config.toml`（Docker 以卷挂载进容器；首次运行也会自动从 `config.example.toml` 生成）。常用可选服务：

| 类别 | 可选服务 | 要点 |
|---|---|---|
| LLM（文案） | Kimi / OpenAI / Claude / Gemini / DeepSeek / Qwen / 火山方舟 Ark / MiniMax / OpenRouter / Ollama | 决定文案质量的核心；Ollama 是唯一真·本地选项 |
| TTS（配音） | 默认 Edge TTS（免费免 Key）；扩展 Azure V2 / SiliconFlow / Gemini / MiMo / ElevenLabs 等 | 中文短视频默认 Edge TTS 音色通常够用 |
| 字幕 | edge（默认）/ whisper | whisper 首次从 Hugging Face 下模型：large-v3 约 3 GB，turbo 约 1.6 GB |
| 素材画面 | Pexels / Pixabay / Coverr | 各需注册免费 API Key；支持多 Key 逗号分隔轮换 |
| 文生视频 | MiniMax H3、火山方舟 Seedance 等（按片计费） | 素材库搜不到合适画面时用 AI 直接生成片段 |
| 背景乐 | 内置 `resource/songs` | README 声明部分默认曲目来自 YouTube，商用前应替换 |

`config.toml` 最小改法（只填你实际用到的段落）：

```toml
[app]
llm_provider = "deepseek"              # 文案引擎：moonshot/openai/anthropic/gemini/deepseek/qwen/.../ollama
subtitle_provider = "edge"             # edge = 免 GPU 时间轴字幕；whisper = 本地转写（见下方 [whisper]）
video_source = "pexels"                # 素材源：pexels / pixabay / coverr，或文生视频源

# 例：DeepSeek
deepseek_api_key = "sk-..."
deepseek_model_name = "deepseek-chat"

# 素材源 Key（可填多个做轮换）
pexels_api_keys = ["你的PexelsKey"]

# 仅当 subtitle_provider = "whisper" 时需要
[whisper]
model_size = "large-v3-turbo"          # 更省资源；追求精度可换 large-v3
device = "cuda"                        # 无 NVIDIA GPU 时改回 "cpu"
compute_type = "int8"
```

若你的前端页面需要跨域直连 API，才需设环境变量 `CORS_ALLOWED_ORIGINS`；curl / Postman / n8n 等服务端调用不受 CORS 限制 [MPT-R]。

### 3.5 一条命令/一次请求出片

先看一眼成片效果最直接的方式是 WebUI；要接入程序则用 API 或 CLI。字段清单以 `http://127.0.0.1:8080/docs` 的 OpenAPI 为准：

```bash
# API：提交一条竖屏视频任务，返回 task_id，再用 GET /api/v1/tasks/{task_id} 轮询结果
curl -X POST http://127.0.0.1:8080/api/v1/videos \
  -H "Content-Type: application/json" \
  -d '{"video_subject":"人工智能如何改变普通人的日常生活","video_aspect":"9:16","video_count":1}'

# CLI：等价命令；--batch-file tasks.json 可一次排队多条（上限 100 条）
uv run python cli.py --video-subject "人工智能如何改变普通人的日常生活" --video-aspect 9:16
```

### 3.6 质量与版权提醒：它产的是「初稿」，不是「成品」

三点必须心里有数：

1. **生成质量的天花板是 LLM**。文案写得像水稿，后面配音、素材再好也救不回来；选更强模型、写更具体的主题、多生成几条挑最优，比调剪辑参数更值钱。若为「纯离线」选 Ollama 本地模型，文案质量通常弱于头部云模型——这是「离线」与「质量」的取舍。
2. **素材版权要自己把关**。Pexels / Pixabay / Coverr 各有授权条款，商用前逐一核对（通常允许商用，但普遍禁止「转售素材本身」之类用法）；文生视频片段按次计费，适合补空镜而非全片铺量。
3. **平台治理风险在前方**。用工具批量产出的同质内容直接铺量，可能撞上平台「自动化批量同质内容」的治理红线，合规细则在第 8 章收口。建议定位是「MPT 出初稿，人工改调性」——标题、封面、开头三秒钩子、素材取舍仍要人把一遍再进发布通道。

[!warning] 版权与调性提示
项目自带的默认背景乐中部分来自 YouTube，官方 README 已声明「如侵权请删除」[MPT-R]，商用前务必替换为自有或正版授权音乐。素材库与 AI 生成片段同样需按各自授权条款商用。别把 AI 初稿未经人工调整就批量铺号——这既影响账号调性，也可能触碰平台对批量同质内容的治理红线（详见第 8 章）。

### 本章小结

- MoneyPrinterTurbo 把「主题 → 文案 → 配音 → 字幕 → 素材 → 剪辑 → 成片」做成全自动链路，输出 9:16 / 16:9 / 1:1 三档画幅，MIT 协议、约 120.7k★、维护活跃。
- 四种用法覆盖从体验到自动化：Agent（一句话交给 AI Agent 干）、WebUI（8501）、API（8080，`POST /api/v1/videos`）、CLI（`cli.py`）。
- 部署门槛低：Python ≥ 3.11，GPU 非必需——只有本地 whisper 字幕/大批量处理才需要；Docker 直接拉 `ghcr.io/harry0703/moneyprinterturbo:latest`，.gpu 版需本地构建。
- 所有第三方服务（LLM / TTS / 素材 / 文生视频）在 `config.toml` 一处配置；默认 Edge TTS 免费免 Key。自托管但非离线，Ollama 是唯一本地 LLM 选项。
- 它擅长「批量出初稿」，不擅长「精」。素材与默认 BGM 的版权、AI 文案的调性都要人工把关后再发布。

下一章进入内容生产的另一半：当一条片子需要「人为精细控制」——按句子、按说话人切段、本地重剪时，MoneyPrinterTurbo 帮不上忙，轮到 FunClip（并顺带看一眼已停更的 ShortGPT 能留给我们什么架构参考）。

## 第四章 AI 内容生产（二）：FunClip 本地智能剪辑与 ShortGPT 停更参考

> 本章定位：第 3 章讲了 MoneyPrinterTurbo 如何「从零做出一条片」，本章补上内容生产流水线的另一半——「对已有素材的精细剪辑」，同时处理两个「不做推荐」的对象：已停更的 ShortGPT，以及素材/脚本管理的开源空白。

### 4.1 FunClip：ASR 驱动的本地智能剪辑

FunClip（仓库 `modelscope/FunClip`，~6.2k★，v2.2.1 于 2026-09-01）是 ModelScope 出品的本地智能剪辑工具。它的核心卖点不是「加特效」，而是把剪片子从「逐帧拖时间轴」变成「在文稿上勾选要保留的句子」。[^c4-1]

[!tip] 大白话
把 FunClip 想成一位「听稿剪辑师」：给它一段音视频，它先不剪，而是把每句话是谁说的、说了什么，转成一份带时间码的文稿；你在文稿上勾选要保留的句子，它就自动把对应画面片段拼出来。剪辑从「拖进度条找切割点」变成「对着文字勾句子」，零基础也能上手。

工作链路：输入音视频 → FunASR 语音识别（Paraformer / SeACo / CAM++ 等模型）→ 输出带时间戳的文本与说话人标签 → 按文本片段或按说话人切段 → 勾选/排除 → 导出剪辑结果。v2.2.1 起内置 Pillow 字幕渲染，识别后可直接把字幕烧进画面，省掉外挂字幕这一步。[^c4-1]

三个使用要点：

1. **基础能力可纯离线**：ASR 识别、按句/按说话人切段都在本地完成，素材不出本机，无云端 Key 依赖。
2. **可选 LLM 剪辑（云端）**：新版支持 TwelveLabs 的 Pegasus 模型做「结合画面 + 音频」的语义剪辑——注意这是云端服务，走这条路径就不再是纯离线。[^c4-1]
3. **资源边界要看清**：官方未给 CPU/显存硬指标；基础功能仅需 Python 即可跑，但 Whisper 时间戳识别需要较大显存。选型时把「要不要本机 Whisper」当作关键分叉。[^c4-1]

#### 4.1.1 安装与启动

pip 安装后直接起 Gradio 本地界面（首次运行会自动拉取模型权重）：

```bash
# 安装
pip install -U funclip

# 启动 Gradio 本地界面
python funclip/launch.py
```

启动后按提示打开 Gradio 地址即可上传素材操作。许可要分两层看：源码 MIT（可商用、可闭源），但底层**模型权重各有各的授权**，不等于随源码一并 MIT 授权。[^c4-1]

[!tip] 大白话
把「源码 MIT」与「模型权重各自授权」想成工具与耗材分离：工具箱（代码）开源随便用，但里面的钻头（训练好的模型）是各厂家单独借你的。改代码不受限，商用前却要把每个模型单独过一遍授权，不能因为仓库标了 MIT 就默认全部可商用。

### 4.2 与 MoneyPrinterTurbo 的分工

FunClip 常被误当成第 3 章 MoneyPrinterTurbo 的竞品，其实两者互补：

| 维度 | MoneyPrinterTurbo | FunClip |
|---|---|---|
| 输入 | 主题 / 文案 | 已有音视频素材 |
| 产出方式 | 从零批量成片 | 对素材精细剪辑 / 二次创作 |
| 典型场景 | 每天批量出 9:16 口播视频 | 把长直播 / 录播剪成多条短视频切片 |

对真实经营者更顺的路径是：批量口播用 MoneyPrinterTurbo；把已有的长内容（直播回放、访谈、课程）切成短视频切片时用 FunClip。两条链路互补，合起来才覆盖完「内容生产」环节。

### 4.3 ShortGPT：停更的参考样本

ShortGPT（仓库 `RayVentura/ShortGPT`）曾是 AI 短视频自动化框架的代表，~7.9k★、MIT。但它最后 push 停在 2025-02-10，到盘点时约 19 个月无提交，判定为停更。[^c4-2]

[!tip] 大白话
把停更项目想成一处停工工地：图纸和框架都还在，参观能学到设计思路，但没人继续施工，水电（依赖、浏览器适配）迟早出问题。把生产依赖押在它身上，等于把店开在停工工地上。

四维打分下它的结局很典型：协议没问题（MIT），但「维护活跃度」这一维归零。它内部的短视频脚本/编辑架构思路仍有参考价值，所以只作历史与架构参考，不作生产依赖——这是本笔记少数「明确劝退选型」的对象。

### 4.4 显性缺口：素材与脚本管理

第 1 章预告过两个开源缺口之一「官方数据分析能力」（第 6 章展开）；本章补上内容生产侧另一个隐性缺口——**素材与脚本管理**。你很难找到一个开源工具专门管「选题脚本库 + 已购素材资产 + 成片归档」；这个环节开源接近空白，商业 SaaS 主导。能部分缓解的是第 3 章 MoneyPrinterTurbo 内置的 Pexels/Pixabay/Coverr 免费素材源，以及第 5 章 AiToEarn 的 Create Agent（批量生成素材），但「管素材」本身仍无成熟开源方案——落地前先想清楚这块要不要用轻量表格/网盘自行顶上。

### 本章小结

- FunClip 基于 FunASR（Paraformer/SeACo/CAM++）做本地智能剪辑，把「剪视频」变成「对着 ASR 文稿勾句子」，v2.2.1 起内置 Pillow 字幕渲染。
- 部署边界：`pip install -U funclip` + `python funclip/launch.py` 起 Gradio；基础功能纯离线且仅需 Python，Whisper 时间戳需大显存；源码 MIT 但模型权重各自授权。
- FunClip 与第 3 章 MoneyPrinterTurbo 互补：前者精剪已有素材，后者从零批量成片。
- ShortGPT 已停更（2025-02 后约 19 个月无提交），仅作架构参考，不作生产依赖。
- 素材/脚本管理环节开源接近空白、商业 SaaS 主导，属显性缺口，需自行用轻量方案顶上。

下一章进入一体化视角：对比「一个 AiToEarn 搞定生产→发布」与「MoneyPrinterTurbo + social-auto-upload 纯离线组合」两条路线，并核实它「自部署 ≠ 离线」的云依赖边界。

## 第五章 一体化编排：AiToEarn 与「纯离线组合」对比

> 本章定位：前面几章看的是单件工具——生产归生产、发布归发布，得自己拼装。本章看另一条路线：一个把「生产→排期→发布→互动→变现」装进同一套 Agent 的一体化平台 AiToEarn。真正要回答的问题是：它开箱即用，但算「离线」吗？如果不想被云绑住，能不能用第 2、3 章的单品自己拼出等价流水线？

### 5.1 AiToEarn 是什么：四个 Agent 装下整条内容营销流水线

AiToEarn（`yikart/AiToEarn`，MIT）把自己定位为 OPC——AI 内容营销一体化 Agent 平台[^c5-ATE]。如果说第 2 章的 social-auto-upload 只是「发布这一个工位」、第 3 章的 MoneyPrinterTurbo 只是「生产这一个工位」，AiToEarn 则是试图把整条流水线直接做成四个岗位：

| Agent | 负责环节 | 主要能力 |
|---|---|---|
| Create | 内容生产 | 调 Grok / Veo / Seedance / Nano Banana 等模型批量生成素材 |
| Publish | 排期与分发 | 日历排期 + 一键分发到多平台 |
| Engage | 互动运营 | 浏览器插件自动互动、AI 回复、高意向评论挖掘 |
| Monetize | 变现结算 | CPS / CPE / CPM 等变现模式下的结算与归因 |

平台覆盖号称 14 个，含抖音/小红书/快手/B站/视频号，也含公众号、TikTok、YouTube、Facebook、Instagram 等海外与图文平台[^c5-ATE]。一句话：第 2、3 章的工具是「单品」，AiToEarn 是「中央厨房」。

[!tip] 大白话
把 AiToEarn 想成一座已经排好四个工位的中央厨房：Create 是切配、Publish 是出餐调度、Engage 是前厅招呼客人、Monetize 是收银对账。你不用自己买四台设备拼流水线，进去就能点菜——这就是「一体化」。代价是：这座厨房的食材配送和收银系统都归总部管，想完全独立运作？后面会讲为什么不行。

### 5.2 五种入口：从「云上开通」到「代码跑在自己机器」

AiToEarn 的接入方式很多样，这是它比单品组合更像「平台」的地方[^c5-ATE]：

| 入口 | 形态 | 一句话 |
|---|---|---|
| Web SaaS | 官方托管的网页版 | 注册即用，最省事 |
| OpenClaw 插件 | 装进 OpenClaw 的插件/skill | 把 AiToEarn 变成 agent 的一个能力 |
| MCP / SSE | 以 MCP Server 暴露，供 Claude / Cursor 接入 | 对话里直接指挥它干活 |
| Docker compose 自部署 | 本地起服务，访问 localhost:8080，官方称免装 DB | 进程与数据在自己机器 |
| 源码运行 | Node 20.18.x 起服务 | 想改代码 / 二次开发时用 |

[!tip] 大白话
把「MCP/SSE 入口」想成给 Claude 或 Cursor 发一张临时工牌：它们凭这张牌直接进 AiToEarn 的后厨下指令，不用你手动在网页里点。工牌（token / SSE 连接）过期就重新领，权限始终以 AiToEarn 账号为准——这张牌只授权「指挥」，不授权「拥有」。

五种入口里，「Docker compose 自部署」最容易让人产生「我已经离线了」的错觉。下一节专门拆这件事。

### 5.3 云依赖边界：Docker 自部署 ≠ 离线（本章核心结论）

AiToEarn 官方文档明确交代了几类云依赖[^c5-ATE]，把「自部署」与「离线」划开界限：

| 依赖类型 | 官方说法 | 含义 |
|---|---|---|
| 平台 API Key | **官方 API Key 硬依赖**，环境不匹配即 **401** | 没有合法官方 Key，服务直接拒绝——不是功能缺失，是进不去门 |
| 社交 OAuth | 可走官方 Relay 借用官方凭据，或**自备各平台开发者凭据** | 发布/分发走平台 OAuth 通道，绕不开「凭据从哪来」 |
| AI 模型 Key | 可自填各厂 Key，或经 Relay 转发 | Create 的模型调用至少需要一个出口 |

所以哪怕 docker compose 起来、界面在自己浏览器里，**进程与数据在本地，但鉴权与部分转发仍依赖 AiToEarn 官方 Relay/Key**。这正是第 1 章埋的伏笔：自部署是把店开在自己家，食材仍由中央厨房统一配送。

[!tip] 大白话
把「官方 API Key」想成一张只有总部认的门禁卡：你把整间办公室都搬到自己家里（自部署），可每道门还是得总部发的卡才能开。卡不匹配（Key 无效 / 环境不对）就直接 401 吃闭门羹——所以「程序在自己电脑上跑」和「能脱离官方独立运转」是两码事。

> 待核实：AiToEarn 开源版与云端版的功能裁剪边界、Create 支持哪些模型供应商，深度研究阶段未从 `DOCKER_DEPLOYMENT_CN.md` 核对[^c5-OQ]；下文 .env 骨架字段同样以仓库实际为准。

### 5.4 对照选型：AiToEarn 一体开箱 vs 纯离线组合

「想一体化、又不想有云锁」怎么办？当前开源侧没有第二个同体量的现成答案，最接近的纯离线路线是用第 3 章的 MoneyPrinterTurbo 做生产、第 2 章的 social-auto-upload 做发布，自己拼。两案对比如下：

| 维度 | AiToEarn 一体化 | MPT + social-auto-upload 组合 |
|---|---|---|
| 归属环节 | 一体化编排（生产/排期/发布/互动/变现） | 内容生产（第 3 章）+ 自动发布（第 2 章），两件拼接 |
| 部署形态 | Web SaaS / Docker / 源码，多入口开箱快 | 各自本地部署：MPT 需 Python + LLM/TTS/素材源；SAU 需 uv + patchright + cookie |
| 是否纯离线 | **否**——官方 Key/Relay 硬依赖，不匹配即 401 | 接近纯离线——除生成阶段可选外部 LLM/TTS/素材源外，链路可在本机闭环 |
| 平台覆盖 | 14 平台 + 互动 + 变现 | 发布 11 平台视频（图文仅抖音/小红书/快手）；无互动/变现 |
| 互动与变现 | Engage / Monetize 内置 | 无（SAU 定位就是纯发布通道） |
| 主要风险 | 云依赖故障面 + Engage 属第三层红线（见 5.6） | cookie 登录态人工维护（第二层），无自动互动 |
| 适合谁 | 想最短路径验证「生产→发布→互动」闭环、能接受官方 Relay/Key 约束 | 介意云锁 / 希望数据尽量不出网 / 已会用 MPT 与 SAU |

用第 1 章的四维标尺给 AiToEarn 打分，短板一眼可见：

| 官方授权 | 标准开源协议 | 纯离线 | 维护活跃度 |
|---|---|---|---|
| 部分——Publish 走平台 OAuth；Engage 触碰平台禁令 | MIT，代码层面可商用 | **否**（云依赖） | v2.5.0 / 2026-08-15 提交，较活跃 |

[!tip] 大白话
两案像「报团游」和「自由行」：AiToEarn 是报团游，导游（官方 Relay）把行程、车、门票全安排好，省心但路线被锁死；MPT + SAU 是自由行，车自己开、票自己买，自由但每个环节都要自己操心，还会遇到登录态过期这类「车在半路没油」的破事。

### 5.5 自部署骨架：docker compose 与 .env（示意，字段勿照抄）

下面按 ATE-R 描述整理成骨架示例，目的是让你动手前先看清「哪些变量是官方 Key/Relay 依赖」；**这不是官方模板，字段名以仓库 `DOCKER_DEPLOYMENT_CN.md` / `.env.example` 为准**[^c5-OQ]。

```yaml
# docker-compose.yml —— AiToEarn 自部署骨架（示意）
# 官方称免装 DB，因此这里不附加 postgres/redis 等依赖服务
services:
  aitoearn:
    image: <官方镜像名，见 DOCKER_DEPLOYMENT_CN.md>  # 待核实，勿直接使用
    container_name: aitoearn
    ports:
      - "8080:8080"            # 自部署入口：浏览器访问 localhost:8080
    env_file:
      - .env                   # Key/凭据集中在这里，便于审计
    restart: unless-stopped
```

```dotenv
# .env —— AiToEarn 自部署骨架（示意字段，勿照抄）
# 三组变量的依赖层级见 §5.3：第 ① 组是硬依赖，缺了会 401

# ── ① 官方 Key / Relay：硬依赖 ─────────────────────────
AITOEARN_API_KEY=            # 官方账号 API Key（环境不匹配 → 401）
AITOEARN_RELAY_URL=          # 官方 Relay 地址（OAuth 借用凭据 / 模型转发）
AITOEARN_RELAY_TOKEN=        # 官方 Relay 访问令牌

# ── ② 社交平台凭据：二选一 ─────────────────────────────
# 方案 A：留空，走官方 Relay 借用官方凭据（依赖上方 RELAY_*）
# 方案 B：自备各平台开发者凭据，按需填写
DOUYIN_CLIENT_KEY=           # 抖音开放平台开发者凭据（如选 B）
DOUYIN_CLIENT_SECRET=
XIAOHONGSHU_CLIENT_ID=       # 小红书开放平台开发者凭据（如选 B）
XIAOHONGSHU_CLIENT_SECRET=

# ── ③ AI 模型 Key：可自填，或留空走 Relay ───────────────
# Create Agent 涉及 Grok / Veo / Seedance / Nano Banana 等，完整清单待核实
OPENAI_API_KEY=              # 自填各厂 Key；留空则经官方 Relay 转发
```

骨架想传达的不是「照抄能跑」，而是三组变量的依赖层级：① 没有它直接 401；② 决定你走官方 Relay 还是自备开发者凭据；③ 决定模型调用是自费直连还是经 Relay 转发。动手前先把这三组搞清楚，就能避开「compose 起来了却满屏 401」的挫败。

### 5.6 风险提示：Engage 自动互动属第三层红线

AiToEarn 功能里最「诱人」的 Engage（自动互动 / AI 回复 / 高意向评论挖掘），恰恰是风险最高的部分——它落在第 1 章风险分级的第三层，也是第 8 章要系统汇总的红线。

[!warning] 高风险：自动互动 = 刷量 / 非正常手段，平台明令禁止
Engage 的浏览器插件自动互动与 AI 自动回复，落在抖音用户协议禁「自动化程序 / 第三方工具接入」、小红书 2026-06 治理公告禁「刷量伪造、自动化批量同质内容」的射程内（红线汇总见第 8 章）。一旦被判定为刷量或非正常手段，轻则限流降权，重则封号；规模化运作还可能被认定不正当竞争（参考抖音诉轻抖刷量案判赔 400 万）。**本文只把 Engage 当作能力地图的一部分，不推荐投入真实账号运营**；要互动就人工做，或走平台官方合规能力（第 6 章方向）。

### 本章小结

- AiToEarn 是 OPC 一体化平台，用 Monetize / Publish / Engage / Create 四个 Agent 覆盖变现结算、排期分发、互动运营与批量生产，号称覆盖 14 个平台。
- 五种入口（Web SaaS / OpenClaw 插件 / MCP-SSE / Docker compose / Node 源码）让它比单品更像平台；但**核心结论：Docker 自部署 ≠ 离线**——官方 API Key 硬依赖（不匹配即 401），社交 OAuth 与模型调用也绕不开官方 Relay 或自备凭据。
- 与「MoneyPrinterTurbo（第 3 章）+ social-auto-upload（第 2 章）」纯离线组合相比：一体案开箱快但被云依赖锁住；组合案基本离线、自由度高，但需自行拼装并人工维护 cookie 登录态。
- docker compose + .env 骨架的重点不是照抄，而是看清三组依赖层级：官方 Key/Relay（硬）、社交 OAuth（二选一）、AI 模型 Key（自填或走 Relay）。
- Engage 自动互动属第三层红线，本文不推荐用于真实账号运营。

一体化编排这条路，开箱即用的代价是把「钥匙」交给别人。下一章转向数据与运营的另一端：先讲合规底座——抖音开放平台、小红书官方导出与 xhs_douyin_content 自账号取数，哪些是官方放行的低风险路径。

## 第六章 数据与运营（合规向）：官方开放平台 API 与自账号取数

> 本章定位：生产与发布都有工具了，但「复盘自己发的内容到底表现如何」时，你会撞上同一个问题——官方到底给不给你数据？本章回答这个问题，并给出一条合规底座：先分清「官方 API 边界」，再看如何把「官方导出」脚本化。本章对应第一/二层风险，是数据运营里最该优先走通的口径。

### 6.1 抖音开放平台：能力真实存在，但门槛是「会员制」

先说好消息：抖音开放平台确实提供数据接口，不是完全没有。按官方文档，账号授权后可以取两类数据（官方文档，S1）：

- **主页维度**：近 30 天主页数据，含点赞、粉丝、评论、分享、主页访问。
- **视频维度**：指定视频近 30 天数据。

坏消息是，这套接口像「会员制健身房」——公开宣传里有，但进门要先过四道闸：

| 门槛 | 官方口径 | 对运营者的实际含义 |
|---|---|---|
| 粉丝门槛 | 仅粉丝 ≥ 1000 的账号可授权 | 新号、小号拿不到官方数据接口 |
| 数据新鲜度 | 授权次日约 10 点刷新 | T+1 口径，看不到实时，复盘天然滞后一天 |
| 聚合能力 | 无现成聚合能力 | 平台不提供「多作品汇总看板」，需自行分页拉取再本地汇总 |
| 申请方式 | 普通号需在控制台逐项申请；经营号（品牌/员工/合作号）默认授权 | 前置审批 + 权限逐项开通，不是开箱即用 |

[!tip] 大白话
把抖音官方数据接口想成一家「会员制健身房」：不是没有器材，而是没到 1000 粉这档会员，前台不给你门禁卡。就算进了门，器械上的读数也不是实时的，而是「昨天下班前结算好的报表」（授权次日约 10 点刷新）。所以官方口径的复盘，天然是「昨天的账」，不是秒级大屏。

再看「无聚合、需分页自算」这条——官方只给每一条原始流水，不给「本月涨跌」的总账。想在周报里看趋势，得自己写脚本把每页数据拉下来，在 Excel 或数据库里做透视汇总。加上个保法合规要求（取的是本人账号授权数据也要按个保法处理，官方文档，S1），「官方数据分析工具」对中小账号来说，体验上接近空白——这正是第一章识别出的两个显性缺口之一（见第 1.2 节），也解释了为什么数据侧的成熟开源项目大多绕开官方 API，走创作者中心自动化（见 6.3）。

还有一个待核实点：抖音经营号（品牌/员工/合作号）的具体能力范围与 scope，需要登录开放平台后台逐一核对（官方文档，S2?）。本章只引用文档字面口径，实操时以你账号后台实际能申请到的能力为准。

### 6.2 小红书：没有「官方 API」，只有「官方导出」

小红书的现状比抖音更朴素。按第三方数据合规路径综述，个人号 / 专业号**没有自账号批量导出 API**；合规取数只有两条腿（第三方综述，S9）：

| 账号类型 | 可用官方通道 | 说明 |
|---|---|---|
| 个人号 / 专业号 | 创作者中心导出 Excel | 人工在后台点「导出数据」，官方给 Excel |
| 企业专业号 | 专业号后台导出 CSV | 后台自带 CSV 导出能力 |
| 品牌 / 蒲公英 | 蒲公英数据 API | 门槛：品牌近一年消耗 > 500 万或进入白名单（第三方综述，S7） |

蒲公英的数据 API 门槛很高，个人和普通专业号基本无法接入；小红书开放平台入口存在（open.xiaohongshu.com），但登录后实际能申请到哪些能力未核（官方入口，S6?）。

[!warning] 边界说明
小红书《用户协议/社区规范》里禁止爬虫/外挂的具体条款，本次盘点未取得一手原文（第三方综述作者亦标注为 gap，S9?）。因此本章只把「创作者中心导出 Excel / 企业专业号导出 CSV」认定为无争议的官方口径；个人号若想批量拉取自己的数据但不想手动点导出，就落到了下一节工具的范畴——它自动化的是「官方导出按钮」，而非爬公开数据。

### 6.3 xhs_douyin_content：把「官方导出」脚本化

`cwjcw/xhs_douyin_content`（GPL-3.0，约 303★）抓的正是自家抖音 + 小红书**创作者中心**的每作品数据，而不是别人主页。它把 6.2 里「人工点导出」这件事脚本化：Selenium 驱动 Edge 登录创作者中心，自动点「导出数据」，再把下载的 Excel 合并成一张汇总表（项目 README / 源码，X-R）。

抓取指标覆盖了作品维度最常用的口径（字段映射见 `project_config/project.py`）：

- **播放表现**：播放量、完播率、5s 完播率、封面点击率、2s 跳出率、平均播放时长
- **互动表现**：点赞量、分享量、评论量、收藏量
- **账号成长**：主页访问量、粉丝增量
- **基础信息**：所属平台、数据日期、作品名称、发布时间、体裁、审核状态

工作机制一句话：**扫码登录 → cookies 存 pkl 缓存 → 之后每次跑脚本直接加载 pkl 免登录**。pkl 是 Python 的 pickle 序列化文件，放在 `pkl/` 目录，命名规则为 `douyin_*.pkl`、`xhs_*.pkl`（可多账号并存，工具会逐个处理）。

[!tip] 大白话
把 pkl 想成一张「门禁卡」：第一次扫码登录是办卡，之后每次脚本进创作者中心自动刷卡进门，不用再扫。卡会过期（登录态失效），过期就重新扫码补办一张。所以「扫码登录」只在第一次和卡过期时发生，不是每次运行都要扫。

它的风险定位处在第一层与第二层的交界：数据是自家账号的、动作是替人点「官方导出」按钮，在同类工具里合规风险相对最低；但它毕竟是浏览器自动化，创作者中心一改版、XPATH 一点、验证码一加，脚本就会失效，登录态也要人工续期——这是所有「自动点官方按钮」类工具的共同脆弱点（项目源码，X-R）。

### 6.4 实操示例：首次扫码登录与日常导出

下面按「先办卡、后刷卡」两步走。仓库目录结构大致如下（`pkl/` 与 `xlsx_file/` 为空文件夹，需自建）：

```text
xhs_douyin_content/
├─ main.py                  # 入口：依次跑 抖音 → 小红书 → 合并汇总
├─ requirements.txt
├─ project_config/
│  ├─ project.py            # 路径与字段映射（默认即可用）
│  └─ msedgedriver.exe      # Edge 驱动：需自行下载，见步骤 0
├─ spiders/
│  ├─ douyin.py             # 抖音创作者中心：加载 pkl → 点「导出数据」
│  └─ xhs.py                # 小红书创作者中心：加载 pkl → 点「导出数据」
├─ pkl/                     # 扫码登录后的 cookies：douyin_*.pkl / xhs_*.pkl
├─ xlsx_file/
│  ├─ douyin/douyin_汇总数据.xlsx
│  └─ xhs/汇总笔记列表明细表.xlsx
└─ data_processing/         # 二次分析脚本（按天增量对比，可选）
```

**步骤 0：准备依赖、目录与 Edge 驱动**

```bash
# 安装依赖（README 原句是 pip install requirements.txt，漏了 -r，正确如下）
git clone https://github.com/cwjcw/xhs_douyin_content.git
cd xhs_douyin_content
pip install -r requirements.txt
mkdir -p pkl xlsx_file/xhs xlsx_file/douyin
```

项目代码里驱动路径默认指向 `project_config/msedgedriver.exe`（`project_config/project.py`），所以还要下载与本机 Edge 主版本一致的 EdgeDriver 放到该目录；如果仓库里的 requirements.txt 在安装时报编码错误（Windows 上 pip freeze 常产出 UTF-16），先把它转成 UTF-8 再装即可。

**步骤 1：首次扫码登录，生成 pkl 门禁卡**

一个值得注意的坑：README 写「直接运行 main.py 第一次扫码登录」，但当前代码里 `Douyin.run_all()` / `Xhs.run_all()` 在 `pkl/` 目录为空时是直接「未找到任何 cookie 文件，任务终止」退出，并不会自动进入扫码流程。所以首次要先跑下面这段一次性脚本把 pkl 生成好（逻辑对齐 `xhs.py` 里的手动登录保存逻辑）：

```python
# login_first.py —— 首次扫码，运行一次后即可删除本文件
import pickle
from selenium import webdriver
from selenium.webdriver.edge.service import Service

DRIVER = "project_config/msedgedriver.exe"          # 与本机 Edge 版本匹配
HOME = "https://creator.xiaohongshu.com/statistics/data-analysis"
# 若给抖音办卡，把 HOME 换成：https://creator.douyin.com/creator-micro/home

driver = webdriver.Edge(service=Service(DRIVER))
driver.get(HOME)                                    # 打开创作者中心
input("在弹出的浏览器里扫码/登录，成功后回到终端按回车……")

# 小红书保存时会过滤 passport_csrf_token（对齐仓库源码）；抖音可不过滤
cookies = [c for c in driver.get_cookies() if c["name"] != "passport_csrf_token"]
with open("pkl/xhs_我的账号.pkl", "wb") as f:      # 抖音请命名 douyin_我的账号.pkl
    pickle.dump(cookies, f)
print("pkl 已保存，可以删除本脚本，直接跑 main.py")
driver.quit()
```

**步骤 2：日常运行与导出**

之后每天（建议低频，比如早上一次）直接跑入口脚本，它会自动加载 pkl、进创作者中心点「导出数据」、等待下载并把分散的 Excel 合并成汇总文件：

```bash
python main.py
```

预期输出的关键几行：

```text
▶ 开始处理 Douyin 数据
... ✅ 点击导出数据成功
... 📊 已成功导出汇总文件：xlsx_file/douyin/douyin_汇总数据.xlsx
▶ 开始处理 XHS 数据
... ✅ 汇总成功，已保存：xlsx_file/xhs/汇总笔记列表明细表.xlsx
```

README 还提到：如果只是关注单个平台，可以直接跑 `spiders/douyin.py` 或 `spiders/xhs.py`；想要「每天增量」对比，可以先把后台导出的文件命名为 `yesterday.xlsx`，再由 `data_processing/` 下的脚本做清洗对比（X-R）。

### 风险与失效提示

- 本层仍属「自动化」，虽然只是替人点官方导出按钮，但**不要高频并发**——创作者中心是后台，不是公开接口，短时间大量点击同样可能触发验证码或风控。
- pkl 登录态会过期；创作者中心页面一改版，代码里写死的「导出数据」按钮定位（XPATH）就会失效，需要跟进仓库更新或自行修。
- 若要研究他人数据 / 对标竞品，那是第 7 章采集器的范畴（第三层风险，须严守「学习研究」边界）；本章只解决「自己账号的官方口径复盘」。

### 本章小结

- 抖音官方数据接口真实存在（主页/视频近 30 天数据），但有四道门槛：粉丝 ≥ 1000、T+1 刷新、无聚合需分页自算、能力需逐项申请（经营号默认授权）。
- 小红书没有个人/专业号批量导出 API，合规取数靠创作者中心导出 Excel、企业专业号后台导出 CSV；蒲公英数据 API 门槛（年消耗 > 500 万或白名单）把普通账号挡在门外。
- `xhs_douyin_content`（GPL-3.0）把「创作者中心导出」脚本化：扫码登录 → pkl 缓存 → 自动点导出 → 合并 Excel，定位在官方口径与自账号自动化的交界，风险相对最低但依赖后台页面稳定。
- 首次使用要先跑一次性扫码脚本生成 pkl（README 与代码行为不一致：pkl 为空时 `main.py` 直接退出），之后才能低频跑 `python main.py`。
- 本章路径覆盖第一/二层风险，是数据复盘里的合规底座；想看「别人的数据」做对标，请带着第 7 章与第 8 章的红线再行动。

下一章进入数据运营的另一半：研究 / 对标向的采集器与互动管理——以 MediaCrawler 为代表的工具能力很强，但自定义非商用许可与第三层风险，决定了它们只适合标注「学习研究」的场景。

## 第七章 数据与运营（研究/对标向）：采集器与互动管理

> 本章定位：第 6 章回答了「自家账号的数据怎么合规取」，本章回答它的镜像问题——「别人的内容、行业热词、评论区民意」怎么取。先深讲数据采集的事实标准 MediaCrawler，简评同源的 Visual_MediaCrawler，再讲互动管理面板 CreatorHub，最后用两个司法信号划出「研究 vs 商用」的操作边界。

第 6 章的官方数据路径（抖音 OpenAPI、创作者中心导出、xhs_douyin_content 自账号取数）只能看到自己的一亩三分地。做运营迟早要回答一类「向外看」的问题：对标账号在发什么选题、某个行业关键词下哪些内容正在起量、评论区到底在争论什么。这些数据既不在你自家后台，官方接口也不提供，于是「采集器」成了研究/对标场景绕不开的一类工具——同时它也是全篇风险最高的一类（第 1 章风险分层的第三层）。

### 7.1 什么时候才需要「采集器」

先把两类路径并排看清楚，避免一上来就选错工具：

| 对比维度 | 第 6 章的合规路径 | 本章的采集器路径 |
|---|---|---|
| 取数对象 | 自家账号 / 自家作品 | 全网公开内容（含他人账号） |
| 通道 | 抖音 OpenAPI、创作者中心导出 | 浏览器自动化（Playwright/CDP）+ cookie |
| 能回答的问题 | 我这周数据如何、哪条内容表现好 | 对标账号在发什么、某关键词下什么在跑、评论在聊什么 |
| 第 1 章风险分层 | 第一 / 二层 | 第三层 |
| 使用判断 | 能覆盖就先走左边 | 左边覆盖不了、且只做学习研究时才走右边 |

[!tip] 大白话
把官方接口想成「店主查自家收银台流水」，把采集器想成「站在店外数客人」。前者数据是你自己的、名正言顺；后者能看到别人的生意，但站在别人店门口记录，本身就踩到了别人的规则。所以采集器只用于「官方给不了、又非看不可」的研究场景，用完即走、绝不商用。

### 7.2 MediaCrawler 深讲：数据采集事实标准

MediaCrawler（`NanmiCoder/MediaCrawler`，约 64.4k★）是中文内容平台采集领域事实标准级的项目：研究资料里它常被当作「先看它有没有做过」的基准 [^c7-mr]。但它不是一枚可以随手拿去商用的通用螺丝刀，下面从打分、能力、许可证到示例逐项拆。

#### 7.2.1 四维打分：事实标准，但不是「可商用工具」

用第 1 章的四维标尺过一遍：

| 维度 | 判断 | 说明 |
|---|---|---|
| 是否官方授权 | 否 | 采集的是平台公开内容，走浏览器自动化，非官方通道 |
| 是否标准开源协议 | 否 | 自定义「非商业学习使用许可证 1.1」，仅限学习研究 |
| 是否纯离线 | 是 | 本地 Python 运行，无厂商云依赖（与第 5 章 AiToEarn 相反） |
| 维护活跃度 | 高 | 社区事实标准，功能迭代快；另有付费 Pro 版（维护者自己的商业化出口） |

结论一句话：**自部署门槛低、离线干净、生态大，但它的许可证把你牢牢钉在「学习研究」这一格。** 这与第 6 章的 xhs_douyin_content（GPL-3.0、自账号数据）不是一回事——后者风险相对最低，前者是抓他人数据。

#### 7.2.3 许可证红线：自定义「非商业学习使用许可证 1.1」

MediaCrawler 没有用 MIT/Apache/GPL 这类标准 OSI 协议，而是自带一份自定义许可，核心限制是两条：**仅学习研究用途；禁止商用与大规模爬取** [^c7-mr]。这不是措辞游戏——没有标准协议背书，「能不能商用」就不由你自行推断，而是要看许可正文。

[!warning] 许可证与合规红线
MediaCrawler 官方许可明示「非商业、仅学习研究」，把它用于商业对标交付或生产系统，既违反项目许可，也触碰平台用户协议与数据权益边界（7.5 节的司法信号）。社区版只能做个人/学术性质的低频研究；想要商业采集能力，官方给的正路是付费 Pro 版，而不是把社区版改装商用。本文不推荐任何把采集器用于商用的用法。

[!tip] 大白话
把这份自定义许可想成「图书馆借书卡」：书借给你读、做笔记都行，但不许你拿去复印卖钱。MIT 那种标准协议等于「书送你了」，而这「非商业学习使用许可证」等于「只借不送」。所以读完用来写研究笔记没问题，拿去做收费的对标报告服务就出了借书范围。

#### 7.2.4 降风控设计：Playwright + CDP 复用登录态

采集器最大的现实障碍是风控——频繁扫码、验证码、接口封禁。MediaCrawler 的默认思路是：用 Playwright 通过 **CDP（Chrome DevTools Protocol）连到你本机已登录的 Chrome**，复用真实用户会话，而不是每次用无头浏览器重新过登录，从而显著降低被风控的概率；也可以走「扫码登录 + 登录态缓存」，扫一次后一段时间内免重复登录 [^c7-mr]。

[!tip] 大白话
把 CDP 想成「复用同一张已刷开的门禁卡」：你日常的 Chrome 已经登录过小红书，MediaCrawler 从这扇已开的门进出，比每次到前台重新登记（扫码验证）低调得多。所以**登录态质量直接决定采集的存活率**——用平时真实使用的浏览器会话，比用全新无头环境稳。

环境前提也值得注意：项目走 `uv`/`pip` 管理，**没有官方 Docker 镜像**，且 Playwright 依赖 **Node ≥ 16** [^c7-mr]——和第 2 章 social-auto-upload 一样是「源码直跑」形态，不是拉个容器就完事。

#### 7.2.5 上手示例：uv 环境 + 复用 Chrome 登录态

以下命令为要点示意，字段名与默认值以你 clone 到的版本为准（`config/base_config.py` 是主要开关集中地）：

```bash
# 0) 前置检查：Playwright 依赖 Node>=16；Python 侧交给 uv/pip
node -v
git clone https://github.com/NanmiCoder/MediaCrawler.git
cd MediaCrawler

# 1) 建环境装依赖（等效方案：pip install -r requirements.txt）
uv sync

# 2) 装浏览器内核
uv run playwright install chromium
```

```python
# file: config/base_config.py（关键项示意，完整键名以当前版本为准）
PLATFORM = "xhs"                # 平台：xhs/dy/ks/bili/wb/tieba/zhihu
CRAWLER_TYPE = "search"         # search(关键词)/detail(指定ID)/creator(指定主页)

# 关键词采集：搜什么
KEYWORDS = "数据分析"
# 指定ID / 指定主页采集则用下面两项（按需打开）
# SPECIFIED_ID_LIST = ["笔记或视频ID"]
# CRAWLER_CREATOR_ID_LIST = ["对标账号ID"]

LOGIN_TYPE = "qrcode"           # 首次扫码登录，登录态会缓存
IS_CDP = True                   # 复用你已登录的 Chrome 会话，降风控
CDP_PORT = 9222                 # 与你手动启动的 Chrome 调试端口保持一致

ENABLE_GET_COMMENTS = True      # 抓评论
ENABLE_GET_SUB_COMMENTS = True  # 抓二级楼中楼评论
CRAWLER_MAX_NOTES_COUNT = 20    # 研究向：把量压小，别当批处理跑
```

```bash
# 3) 复用登录态：手动起一份带调试端口的 Chrome（独立 user-data-dir，避免与日常 Chrome 冲突）
#    Windows 示例；用这份 Chrome 登录一次目标平台后别关
chrome.exe --remote-debugging-port=9222 --user-data-dir="D:/chrome-profile-mc"

# 4) 采集（研究向小样本，低频跑）
uv run python main.py
# 结果输出到 data/ 目录，如 keyword_xxx.csv / .json
```

跑完你会得到按配置导出的原始数据文件。注意把「样本量」当第一纪律：研究问题大多几十条内容 + 评论就够看清方向，不需要也不应该上代理池冲量。

#### 7.2.6 输出格式

支持 CSV / JSON / JSONL / Excel / SQLite / MySQL 多种落库方式 [^c7-mr]，小样本用 Excel/CSV 即可，样本大了再考虑 SQLite。采集完的数据是原始语料，离「洞察」还差一步分析——这步 MediaCrawler 不替你完成。

### 7.3 Visual_MediaCrawler 简评：采集 + 展示一体

Visual_MediaCrawler（约 69★）是 MediaCrawler 的派生项目，把「采集」和「看数据」合并成一个带界面的工具，降低了「跑完 CSV 还要自己写脚本看」的门槛（素材 §3.9）。它继承上游的**非商业许可**，风险属性与 MediaCrawler 一致。判断：如果你只是想要一个图形界面来浏览采集结果，可以一试；但 star 少、基本跟随上游迭代，别指望独立维护力度，遇到问题大概率要回到 MediaCrawler 的 issue 里找答案。

### 7.4 CreatorHub 简评：互动管理面板

CreatorHub（`3441293738/creatorhub`，约 1.9k★）和 MediaCrawler 走的是两条路：MediaCrawler 是「采集原始数据给你」，CreatorHub 是「本地多平台面板，帮你把作品、评论、私信管起来，甚至自动接住互动」[^c7-cr]。

| 能力 | 说明 |
|---|---|
| 账号面板 | 本地多平台：抖音 / 小红书 / 快手 / 视频号；同步作品、关注、粉丝、私信 |
| 监控 | 作品 / 评论 / 弹幕监控，断点续传；抖音 ↔ 小红书内容转发 |
| 采集 | 关键词采集目前仅抖音，小红书在规划中 |
| 自动互动 | 自动评论/回复、私信自动回复（关键词 / 排除词 / 模板 / 冷却） |
| 登录态 | 每账号独立 Chrome CDP Profile，默认 conservative（保守）模式 |

自动互动有个安全默认：回复默认生成**待审核草稿**而不是直接发出去 [^c7-cr]。但即便有这个默认值，它也要过下面两道「为什么慎用」的关。

[!warning] 许可证不明（license=null）
CreatorHub 在 GitHub 上 **license=null，未声明任何标准开源协议** [^c7-cr]。没声明协议 ≠ 可以自由使用，恰恰相反：按默认版权规则，作者保留所有权利，复制、修改、分发、商用的法律状态都不明确。和第 1 章讲过的自定义许可不同，license=null 连「借书卡上的条款」都没写清——所以只建议当个人学习参考，别进生产、别商用、别二次分发。

[!warning] 自动互动踩平台红线
自动评论、自动私信属于第 1 章风险分级里的第三层行为，触碰平台「禁止自动化第三方接入 / 批量互动」条款（第 8 章会列抖音用户协议与开放平台公约原文）。CreatorHub 用「默认草稿 + 冷却」把风险压了一档，但**「自动回复」这件事本身仍在红线内**，不是配置保守就能洗白。真要用，只做低频、只回自家账号的评论，且每条都人工审核后再发。

#### 7.4.1 冷却配置要点

既然自动互动踩线，「怎么把频率压到最低」就是唯一合理的配置方向。要点提示：

- **保持默认 conservative 模式**，不要为了「响应快」去调激进档。
- 依赖阶梯冷却：对 `403`（权限/风控）、`429`（请求过快）、`461`、`471`（平台侧风控码）分别设置递增的等待时间，触发后让出带宽 [^c7-cr]。
- **自动回复一律落草稿**，配合人工审核，别开「直接发布」。
- 每账号独立 Chrome CDP Profile，隔离登录态——一个号被风控时不连坐其他号。

```yaml
# file: creatorhub 配置示意（字段以当前版本 README 为准；目标是“冷却+保守”，不是提速）
mode: conservative          # 保持默认保守模式
auto_reply: draft           # 自动回复一律落“待审核草稿”，不直接发布
cooling:
  403: 300                  # 权限/风控响应   -> 停 5 分钟
  429: 600                  # 请求过快        -> 停 10 分钟
  461: 1800                 # 账号状态异常码  -> 停 30 分钟
  471: 3600                 # 平台风控码      -> 停 1 小时
per_account_profile: true   # 每账号独立 Chrome CDP Profile，隔离登录态
```

### 7.5 研究 vs 商用：法律分界与操作边界

为什么全章反复强调「学习研究、禁商用」？因为司法口径已经把「研究」和「商用」划出了不同待遇，两个信号值得记住（第 8 章会并入全书红线总结）。

**信号一：最高法数据权益指导性案例（2025-08）。** 未获许可爬取他人数据，并对平台服务形成「实质性替代」的，可依《反不正当竞争法》判赔 [^c7-s10]。这里的判赔触发器是**规模化 + 替代平台功能**——你把别人的内容库整个搬走做成一个可替代的服务，就撞上了这条线。

**信号二：抖音诉「轻抖」组织刷量案（2023 终审）。** 组织刷量、干扰推荐算法被认定构成不正当竞争，判赔 400 万元 [^c7-s11]。它警示的是另一件事：**用自动化手段操纵互动数据**，即使工具只提供「助力」，组织者也担责。

[!tip] 大白话
把「实质性替代」想成「在别人店门口开一家一模一样的店，货全从对方仓库搬」：偶尔去对方店里抄几个爆款摆放思路（研究）没事；把人家整个仓库搬空、开起自己的店（实质性替代、商用）就要赔钱。判例共同点是**「商用牟利 + 规模化损害」才是引爆点**，个人低频学习样本到不了那个量级——所以边界不是「能不能看」，而是「看完用来干嘛、看多少」。

据此把操作边界收敛成五条，前四条做「不越线」，最后一条做「不留后患」：

| # | 边界 | 具体做法 |
|---|---|---|
| 1 | 只做研究 | 个人学习、选题参考、对标内容拆解，不产出对外交付物 |
| 2 | 不商用 | 不进生产系统，不做收费对标报告/数据服务 |
| 3 | 低频 | 压小样本量（如 7.2.5 的 CRAWLER_MAX_NOTES_COUNT），不开代理池冲量 |
| 4 | 自账号优先 | 能用自家账号/自家内容解决的，绝不抓别人的（回到第 6 章路径） |
| 5 | 留存克制 | 只留分析结论与必要特征；含个人信息（昵称、评论正文等）的原始语料不长期留存 |

### 本章小结

- 采集器只在「官方路径覆盖不了 + 研究/对标」时启用：官方接口看自家，采集器看全网，前者优先。
- MediaCrawler 是事实标准：7 平台、5 种采集模式、CDP 复用登录态降风控、uv/pip 直跑无 Docker；但自定义「非商业学习使用许可证 1.1」把用途锁死在「学习研究、禁商用」。
- Visual_MediaCrawler = 采集 + 展示一体，继承非商用许可，star 少只作尝鲜。
- CreatorHub 强在「面板 + 监控 + 互动管理」，但 **license=null 未声明标准协议 + 自动互动踩线**，只建议个人参考，商用/生产慎用；确要用就把 conservative、草稿、阶梯冷却、账号隔离全配齐。
- 司法边界看两个信号：未获许可爬取并实质性替代平台服务可依反法判赔（最高法指导案例）；组织刷量判赔 400 万（抖音诉轻抖）。操作上守住「只做研究、不商用、低频、自账号优先、留存克制」。

## 第八章 合规红线与选型矩阵：怎么选、怎么用不踩线

> 本章定位：全篇收口。第 1 章立下「官方授权 / 标准开源协议 / 纯离线 / 维护活跃度」四维标尺，第 2–7 章逐个工具打分，本章把散落各章的红线收拢成三层框架，把候选工具收拢成一张矩阵，最后给三条不踩线的推荐组合。无代码，以表格 + Callout 为主。

### 8.1 风险三层框架：全文红线的统一出口

第 1 章 1.4 预览过三层分级，第 2、6、7 章又分别在发布、取数、采集场景展开过。现在把三层收口成一张表：

| 层级 | 通道形态 | 代表工具/路径 | 触碰的对象 | 风险量级 |
|---|---|---|---|---|
| 第一层 · 官方授权 | 抖音 OpenAPI、创作者中心导出、企业专业号后台 | 抖音开放平台、创作者中心 Excel/CSV、蒲公英（高门槛） | 平台授权范围内，基本不违约 | 低（但门槛高：抖音需 ≥1000 粉 + 逐项申请） |
| 第二层 · 自账号 cookie/浏览器自动化 | 自建登录态操作自家后台 | xhs_douyin_content、social-auto-upload | 自家数据，但走平台未必许可的通道 | 中（违约风险自担、登录态需人工维护） |
| 第三层 · 爬他人数据 / 刷量 / 自动互动 | 采集他人主页与评论、批量虚拟互动 | MediaCrawler（商用）、AiToEarn Engage、CreatorHub 自动互动 | 平台条款 + 个保法 + 反不正当竞争法 | 高（可被投诉、追责直至判赔） |

[!warning] 全文统一风控出口
三层的分界不是「是否自部署」，而是「走没走官方授权」+「动没动平台算法与他人的数据」。第一层优先选用；第二层默认违约风险自担，只适合低频、自家数据、愿意人工维护登录态的场景；第三层任何时候都不应进入商用生产链路——MediaCrawler 一类只能在「学习研究」边界内使用，自动互动类功能在商用场景直接跳过。

[!tip] 大白话
把三层想成进商场的三种方式：第一层走正门刷会员卡（官方 API），保安欢迎；第二层拿自家储物柜钥匙去开自己租的柜子（自账号 cookie），不偷不抢，但绕过了商场动线，出了事自己扛；第三层是翻墙抄别人柜台的数据、还雇人假排队（爬他人数据 + 刷量），商场和别的商户都能告你。所以选型先问一句：我打算从哪个门进去？

### 8.2 平台条款红线：抖音与小红书明令禁止什么

红线不是社区「建议」，是用户协议与治理规则里的「禁止」级表述。两个平台的要点如下：

| 平台 | 规则文件 | 明令禁止（要点） |
|---|---|---|
| 抖音 | 抖音用户协议（2026-02-20 生效） | 禁爬虫/镜像（2.4）；禁用自动化程序或第三方工具接入、收集平台信息（5.1）；禁爬虫抓取/模拟下载盗取内容（5.3）[^8-s3] |
| 抖音 | 抖音开放平台开发者公约 | 禁以非正常手段造假数据、批量注册虚拟账号、使用未授权第三方工具接入 [^8-s5] |
| 抖音 | 矩阵号治理规则（2023-12-01） | 针对批量同质矩阵账号的专项治理依据 [^8-s4] |
| 小红书 | 治理公告（2026-06-10） | 禁刷量/伪造数据；禁自动化批量生产同质内容；禁干预搜索结果与 AI 问答，违者降权/封禁 [^8-s8] |

把这些条款映射回前文工具，一目了然：

- **social-auto-upload** 属「自动化程序接入平台」，撞抖音用户协议 5.1，使用即违约风险自担（第 2 章）。
- **MediaCrawler** 爬取他人主页/评论，同时对应协议禁爬条款与个人信息保护问题（第 7 章）。
- **AiToEarn Engage / CreatorHub** 的自动评论、私信与批量互动，对应开放平台公约「造假数据」与小红书的「刷量 / 干预」红线（第 5、7 章）。
- **xhs_douyin_content** 抓自家创作者中心，虽是自家数据，仍属未授权自动化接入通道，风险高于官方路径（第 6 章）。

> 待核实：小红书《用户协议》中禁爬虫/外挂的具体条号未取得一手原文（深度研究素材亦标注此缺口）。上表只引用其 2026-06-10 治理公告的公开表述，作为「平台正在治理自动化批量行为」的官方信号。

### 8.3 司法边界：数据权益与刷量的两记警钟

条款之外还有法院。两个判例把「爬数据」与「刷量」从违约问题抬升到不正当竞争层面：

- **最高法数据权益指导性案例（2025-08）**：确认平台对投入收集、加工的数据享有分层权益；未获许可爬取并「实质性替代」平台服务的，可依反不正当竞争法判赔 [^8-s10]。
- **抖音诉「轻抖」刷量案（2023 终审）**：组织批量刷量干扰推荐算法构成不正当竞争，判赔 400 万元 [^8-s11]。

[!warning] 判例提示
「学习研究」不是免死金牌：指导案例打击的是实质性替代平台服务的商用行为，个人小规模研究性采集通常不在打击面；但一旦把采集数据用于经营同类服务，性质立即改变。刷量更无灰色空间——组织或使用批量虚拟互动干扰推荐算法已被判赔百万级，AiToEarn Engage、CreatorHub 自动互动功能在商用场景下直接不可用。

[!tip] 大白话
把「实质性替代」想成：你抄了别人店里辛苦整理的商品陈列，再在隔壁开一家一模一样的店抢客——法院会说这不是学习，是偷生意。买一本回家看（个人研究）没事，复制整店营业（商用替代）要赔。边界就划在「量」与「用途」上。

### 8.4 全篇选型矩阵

把 7 个核心候选收进一张表。列维度对回第 1 章四维标尺：「风控层级」≈ 是否官方授权，「开源协议」≈ 是否标准 OSI 协议，「云依赖」≈ 是否纯离线，「维护」列标注活跃度。

| 工具 | 开源协议 | 部署 | 云依赖 | 风控层级 | 适用场景 |
|---|---|---|---|---|---|
| social-auto-upload | MIT（活跃） | uv + patchright/Chromium | 无 | 第二层 | 自家账号多平台定时/批量发布；供 AI Agent 调用 |
| AiToEarn | MIT（活跃） | Web SaaS / Docker / MCP | 强（官方 Key/Relay 硬依赖） | 第三层（Engage） | 一体化「生产→分发→互动」；须接受云依赖 |
| MoneyPrinterTurbo | MIT（活跃） | Docker / 源码 | 选配（LLM/TTS/素材源） | 基本无 | 文字一键批量成片 |
| FunClip | MIT（活跃；模型权重另授权） | pip 本地 | 选配（LLM 剪辑） | 基本无 | 本地 ASR 按句/说话人剪辑提效 |
| MediaCrawler | 自定义非商用许可 1.1（活跃） | uv/pip（无 Docker） | 可选代理池 | 第三层 | 学习研究用采集；禁商用 |
| CreatorHub | 未声明（license=null；活跃） | 本地多平台面板 | 无 | 第三层（自动互动） | 评论/私信/多账号监控；慎用 |
| xhs_douyin_content | GPL-3.0（活跃） | 源码 + 扫码登录 | 无 | 第二层 | 自账号创作者中心作品数据复盘 |

4 个边缘候选按同一标尺快速落位：**MediaPublishPlatform**（MIT，可视化批量发布，star 少需自测）≈ 第二层；**omnipost**（MIT，social-auto-upload 衍生，仅 1 commit）≈ 第二层；**Visual_MediaCrawler**（继承非商用许可）≈ 第三层；**ShortGPT**（MIT，2025-02 后停更）只作历史参考，不入任何推荐组合。

### 8.5 三条推荐组合：怎么用不踩线

回到最初的问题——不是「哪个工具最好」，而是「我属于哪类经营方式，该走哪条组合」。

1. **合规发布组合（多数个人/小团队）**
   以官方后台 + 人工为主；确需提效时，用 social-auto-upload 低频辅助发布自账号，接受登录态人工维护与违约风险自担；不碰第三方采集，不开自动互动。
2. **纯离线 AI 生产组合（内容供给为王，不碰数据红线）**
   MoneyPrinterTurbo（批量成片）+ FunClip（精剪提效）+ social-auto-upload（发布通道）。全链路可在自己机器跑通，云依赖降到接近零，风险集中在「发布」一个环节。
3. **合规数据复盘组合（自账号复盘 / 官方口径）**
   有 ≥1000 粉走抖音 OpenAPI 取近 30 天官方数据；不够门槛就用创作者中心导出 + xhs_douyin_content 拉自家每作品明细；研究竞品只在「学习研究」边界内用 MediaCrawler，绝不商用。

[!warning] 三条组合的使用前提
第 3 条组合中的 xhs_douyin_content 仍属第二层违约通道：只用于复盘自家账号，创作者中心接口一变即失效，别在它之上搭对外服务。第 1、2 条组合里的 social-auto-upload 是「低频辅助」，不要做矩阵规模的高频群发——那会同时撞上抖音矩阵号治理规则与小红书自动化同质内容治理两条线。

### 本章小结

- 风险分三层收口：官方授权（低）/ 自账号 cookie（中）/ 爬他人数据 + 刷量 + 自动互动（高）；分界在「是否官方授权」与「是否动了平台算法及他人数据」。
- 两平台都有「禁止」级红线：抖音用户协议 2.4 / 5.1 / 5.3、开放平台公约、矩阵号治理规则（2023-12-01）；小红书 2026-06-10 治理公告禁刷量与自动化批量同质内容。
- 司法两记警钟：数据「实质性替代」可判赔（最高法指导性案例）；组织刷量干扰推荐算法判赔 400 万（抖音诉轻抖）。
- 选型回到第 1 章四维标尺：风控层级 ≈ 官方授权、开源协议 ≈ OSI 标准、云依赖 ≈ 纯离线、维护 ≈ 活跃度；7 核心 + 4 边缘已收拢成一张矩阵。
- 落地走三条组合之一：合规发布、纯离线 AI 生产、合规数据复盘——先定经营方式，再挑组合，最后对照红线检查一遍再上线。

到这里，全景（第 1 章）→ 发布（2）→ 生产（3–4）→ 一体化（5）→ 数据（6–7）→ 红线收口（8）的盘点闭环完成。把各章按此顺序组装成完整笔记，它就能作为一份可对照执行的选型手册。
