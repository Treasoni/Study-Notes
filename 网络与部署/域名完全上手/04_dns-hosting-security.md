# 第4章 解析托管、NS 委派与域名安全

域名合法归你、也过了实名/备案关之后，距离"能用"还差两件事：解析放在哪家管，以及万一被盗或被转走怎么办。本章解决三个问题：怎样把解析托管到更顺手的服务商、改动解析后怎么确认"真的生效了"，以及如何给域名上到安全基线。这三件事的共同前提，是把「注册」和「解析」先拆开看。

## 4.1 域名与解析分离

很多新手以为"在谁家买的域名，就必须在谁家解析"。实际上注册与解析是两套独立职责：

- **注册商**：在注册局数据库里登记"这个域名归谁所有"，负责实名、续费、转移、各类状态锁。
- **解析商 / DNS 托管**：在权威 DNS 服务器上维护你的记录（A/AAAA/CNAME/MX/TXT…），回答"这个域名现在解析到哪个 IP"。

> [!tip] 大白话
> 把域名注册想成**房产登记**：注册商是"房管局"，只管登记"这套域名登记在你名下"；解析商是"大厦前台"，负责告诉访客"去哪栋楼往哪边走"。房管局和前台完全可以不是同一家公司——你在 A 局登记产权，却请 B 家来做前台指引。

所以域名留在注册商 A、DNS 托管交给 B（DNSPod、阿里云云解析、Cloudflare 等）在国内外都是常态 [^c4-1][^c4-2]。这样做的实际收益：注册续费留在便宜的 A，解析用功能更强/更快/带 API 和 DNSSEC 的 B；两家互不绑架，换解析商不影响所有权，换注册商也不丢记录（只要提前导出）。

| 事项 | 归谁管 |
| --- | --- |
| 实名、续费、转移、注册商级状态锁 | 注册商 |
| 各记录内容（A/CNAME/MX/TXT…） | 解析商（权威服务器） |
| 根/TLD 里"你的 NS 指向谁" | 由注册商提交到注册局，全球据此找到你的权威 |

## 4.2 切换解析托管与子域 NS 委派

> [!note] 先认识 NS：Name Server（名称服务器）
> **NS 记录本身不负责解析**——它不回答"域名到哪个 IP"，而是回答"该找谁去问"：它把整域（或某个子域）的权威解析权**委派**给指定的服务器。放到 4.1 的比喻里，注册商是"房管局"、解析商是"大厦前台"，而 **NS = 房管局登记簿上写明的"这家大厦的前台是哪一家"**——所以下面的两条路线（整域换解析商、子域独立委派）本质上都是**改 NS 这件事**的不同范围版本。

### 4.2.1 整域换解析商：先搬家、后改 NS

把整个主域从旧解析商切到新解析商，通用做法是**先在目标商建好记录，确认无误后再动 NS**，避免空窗期网站直接解析失败：

1. 在新解析商添加你的域名（新建 zone），把旧解析商现有的 A/AAAA/CNAME/MX/TXT 等记录**完整照搬**过去。
2. 在新解析商后台找到它分配给你的 NS 主机名（通常是两个，形如 `ns1.xxx.net`、`ns2.xxx.net`）。
3. 回注册商后台，把该域名的 **NS 记录改成新解析商的 NS 主机名**。
4. 等旧 TTL 过期 + 根/TLD 更新后，全球递归器开始改用新权威（具体怎么确认见 4.3）。

> 控制台里的按钮名称各家不一，但"先复制记录 → 后改 NS → 再验证"的顺序是通用的。旧解析商的 zone 先别删，留到新权威稳定后再清理，方便回滚。

### 4.2.2 子域独立委派：NS 记录 + TXT 归属校验

不一定整个域都要搬家。你可以只把某个子域（如 `lab.example.com`）**独立委派**给另一家解析商：

- 在当前权威 zone 里，为 `lab.example.com` 添加一条 **NS 记录**，指向另一家解析商的 NS 主机名。委派完成后，`lab.example.com` 及其下级记录的解析由那家新权威负责。
- 委派前，目标解析商通常会要求你在**主域加一条它指定的 TXT 记录**，作为"你确实能管这个父域"的归属校验；校验通过，它才肯为你托管该子域 zone [^c4-2]。
- 委派后注意两点：**子域的解析优先于主域上同名记录**——主域里若还有 `lab.example.com` 的旧 A 记录，不再参与该子域解析；另外**子域名不支持 URL 转发**，别指望在子域上做"跳到某个链接"的转发（那属于父域解析商的功能）[^c4-2]。

> [!tip] 大白话
> 子域委派相当于**把分店的前台外包**：总店前台（主域权威）只在门口立一块牌子写"分店怎么走？去问分店自己请的物业"。访客从此直接找分店物业，总店不再回答分店内部怎么布置。TXT 归属校验则是新物业接手前，先要你在总店门口贴一张它指定的"认领凭证"，证明你有权把分店交给它。

## 4.3 改动生效排查（动手验证）

改了解析却"没生效"，多数时候不是没生效，而是缓存还没过期。第 1 章讲过 DNS 传播的真相：它并不是全球同步，而是各级缓存按 **TTL** 过期。所以排查有一条铁律：

> **上线前，先把要改的记录 TTL 调低（如 60s），等一个旧 TTL 周期后再动手改。** 旧缓存在一分钟内就会过期，新值能快速铺开；万一改错，也能快速再改回来。稳定运行几天后，再把 TTL 调回较高值（如 3600s）以减少递归器频繁回源查询 [^c4-1][^c4-3]。

TTL 调低后再改记录，用三步确认是否生效：

**第 1 步：区分"本地缓存旧"还是"真没生效"。** 对比默认递归器与公共递归器的查询结果。

```bash
dig example.com              # 走你机器当前配置的递归器，可能命中本地/ISP 缓存
dig @1.1.1.1 example.com     # 强制走 Cloudflare 公共递归器 1.1.1.1
dig @8.8.8.8 example.com A   # 或 Google 公共递归器 8.8.8.8
```

判断逻辑 [^c4-3]：

- 公共递归器已返回新值、默认查询还是旧值 → **本地/ISP 缓存未过期**，不是没生效，等 TTL 到期（或刷新本机 DNS 缓存）即可；
- 两边都还是旧值 → 记录在权威侧还没生效或委派未更新，继续查第 2、3 步；
- 两边都已是新值 → 确认生效。

**第 2 步：看委托链，确认 TLD 认可的 NS 是否已切换。** 用 `dig +trace` 从根一路走到权威，能直观看到"根 → .com TLD → 你的权威"每一级把解析权交给了谁。

```bash
dig +trace example.com        # 委托链逐步列出，末尾应看到新权威的 NS
dig example.com NS +short     # 顺手看当前 TLD 认可的 NS 集合
```

如果 TLD 那一段返回的还是旧 NS，说明注册商提交的新 NS 还没被注册局更新，耐心等待并重试。

**第 3 步：绕过一切缓存，直接问权威服务器要"最终事实"。** 把下面命令里的 `ns1.newdns.example` 换成第 2 步 `+trace` 结果末尾的权威 NS 主机名：

```bash
dig @ns1.newdns.example example.com A    # 直达权威，看它实际返回什么
```

如果权威直接返回的就是新值，说明**最终事实已正确**，剩下的只是等各级缓存过期 [^c4-3]。

**Windows / 不想装 dig 的对照**：用 nslookup 完成同样的三步 [^c4-3]。

```text
nslookup example.com            # 默认递归器
nslookup example.com 8.8.8.8    # 指定公共递归器
nslookup -type=NS example.com   # 看 NS 集合
```

配合第 1 章讲过的 RCODE 一起读：`NOERROR` 正常、`NXDOMAIN` 域名不存在、`SERVFAIL` 权威或上游故障（DNSSEC 校验失败时也常见）、`REFUSED` 拒绝递归。看到 `SERVFAIL` 先别急着改记录，回头查 4.5 的 DNSSEC 开关。

> [!tip] 大白话
> 把 TTL 想成**各层公告栏的刷新周期**。你在总部贴了新通知，但楼下保安、快递站、访客的公告栏都要等自己的周期到了才换内容。TTL 调成 60s，等于让所有公告栏最多一分钟就更新一次——所以"上线前先调低 TTL"，本质是**提前让全世界公告栏进入快速刷新模式**，再改内容。

## 4.4 域名转移规则

"转移"指把域名**从一个注册商转到另一个注册商**（如从老注册商转到 Cloudflare Registrar），所有权归属不变，只是换了注册服务商。按 ICANN 的通用规则（主要约束 .com/.net/.org 这类 gTLD）[^c4-4]：

- **注册满 60 天**且**距上次转出满 60 天**才可转出；
- **近 60 天内改过注册人信息**会触发一个新的 60 天锁定，期间不能转；
- 转出前须在注册商处**解锁**（去掉 `clientTransferProhibited` 状态），并索取**授权码 / EPP 码**——它像一把限时的过户钥匙，有效期很短，拿到后要尽快在新注册商处提交；
- gTLD 转移通常会让注册期限**顺延 1 年**（相当于免费续一年）；
- 若按成本价经营的注册商（如 Cloudflare Registrar），转入按注册局成本价收取、无加价 [^c4-4]。

> [!tip] 大白话
> EPP 授权码就是**过户时的临时钥匙**：房管局只认"你有这把限时的钥匙 + 房主已解锁"，才允许把登记挪到另一家中介名下。所以它有效期短、要妥善保管，绝不要截图发到网上——谁拿到钥匙，谁就可能发起转出。

转移与 4.2 的"换解析托管"是两码事：换解析商只改 NS、不动注册商；转移则换注册商。日常维护中，换解析商比转移频繁得多，也安全得多。

## 4.5 安全基线：从 MFA 到注册局锁到 DNSSEC

域名是"一失守全盘皆输"的资产：攻击者拿到你的注册商账户，能把域名转走、改解析指向钓鱼页。所以域名安全要按**分层**加固，越往上越难被单一漏洞击穿 [^c4-6]：

1. **账户 MFA**：注册商账户开启多因素认证——这是第一道门，防止密码泄露直接登入。
2. **注册商禁止转移锁 / 禁止更新锁**：在注册商处开启 `clientTransferProhibited`（禁止转移）、必要时加 `clientUpdateProhibited`（禁止更新）。没有这把锁，即使账户被登入，转出也会被拦截。
3. **注册局安全锁**：向注册局申请更高级的 `serverDeleteProhibited` / `serverTransferProhibited` / `serverUpdateProhibited`（server 级状态锁）。它由注册局侧施加，比注册商自设的 client 级锁更难被注册商账户失守连坐解除。
4. **DNSSEC**：用数字签名防止解析被欺骗与缓存污染 [^c4-5]。启用流程是：解析商对 zone 签名并生成 **DS 记录** → 你到注册商处把 **DS** 加上 [^c4-5]（Cloudflare 首推算法 13，ECDSA P-256 / SHA-256）。

对个人而言，**基线 = MFA + 禁止转移锁**；核心业务域名再加**注册局锁 + DNSSEC** [^c4-6]。

> [!tip] 大白话
> 把域名资产想成**带保险箱的家**：MFA 是家门指纹锁，禁止转移锁是保险箱上的双保险，注册局锁是银行侧的"非本人临柜不可动"登记，DNSSEC 则是你寄出的每份解析答案都盖**官方防伪封条**——收件方验封条才信内容，防止有人中途拆包调包（DNS 欺骗/缓存污染）。

> [!warning] 已开 DNSSEC 时，改 NS（换解析托管）前必须先关 DNSSEC，并等旧 TTL 过期（约 24–48h），再做 NS 切换
> 原因：DNSSEC 开启时，注册局里的 DS 记录指向的是**旧解析商**的签名密钥。若直接换 NS 到未签名的解析商，递归器按 DS 去找签名却找不到，校验失败会表现为 `SERVFAIL`，域名直接"解析不出来"。正确顺序是：先在解析商处关闭 DNSSEC → 等 DS 与旧签名从各级缓存过期（约 24–48 小时）→ 再改 NS → 新权威稳定后重新开启 DNSSEC 并更新 DS [^c4-4][^c4-5]。

## 4.6 补充提示：2FA 只保护登录，转移未必二次验证

社区里有一条值得警惕的经验：**注册商账户的 2FA 只保护"登录"这一环，真正执行"转移"的操作流程未必会再做一次二次验证**——曾有托管商事件（TrustName）暴露过这类缺口 [^c4-7]。

> 该提示来自社区整理（B8 附注），**未经官方原文复核，这里不作定论**。但它指向一个稳健的工程态度：不要把安全全部押在"账户登录"一道关卡上，而是回到 4.5 的分层——即便登录被绕过，**禁止转移锁 + 注册局锁**仍然是转出动作上的硬拦截。这也是为什么安全基线把"锁"看得和 MFA 一样重。

## 本章小结

- **注册与解析分离是常态**：域名留在注册商 A、DNS 托管交给 B，换解析商不动所有权，换注册商不丢记录。
- **切换解析托管先搬家后改 NS**：在新商建好全部记录，再回注册商改 NS；子域可单独用 NS 记录委派给别的解析商，并用 TXT 做归属校验。
- **排查生效三问**：`dig @1.1.1.1` 对比默认查缓存、`dig +trace` 查委托链、`dig @权威` 看最终事实；**上线前先把 TTL 调低到 60s**。
- **转移有硬规则**：注册满 60 天、近期未转出、解锁 + EPP 授权码；gTLD 转移通常顺延 1 年。
- **安全靠分层**：MFA → 禁止转移锁 → 注册局锁 → DNSSEC；个人基线至少 MFA + 禁止转移锁。
- **DNSSEC 是双刃剑**：换 NS 前必须先关并等约 24–48h 过期，否则会 `SERVFAIL`。

下一章，我们终于要把这个"解析正确、安全达标"的域名接上真正的服务：用 Caddy 或 Nginx+certbot 一键签发 HTTPS 证书，让访问者通过 `https://你的域名` 打开你的自建站点。
