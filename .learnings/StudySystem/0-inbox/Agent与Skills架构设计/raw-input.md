# Agent与Skills架构设计

## 核心问题
如果我的一个skills，新创建了一个subagent它会实现和这个skills一个的功能，那么是这个agent会调用这个skills还是这两个会争夺使用权？

## 两种情况

### 1. 糟糕的情况：争夺使用权（路由冲突）

如果你的主干流程（Claude Code）同时看得到这个 Skill 和这个 Subagent，并且你给它们的描述（Description 或 Prompt）高度重合，它们就会"打架"。

**为什么会打架？** 当你发出指令（比如"去整理一下这篇笔记"）时，主模型会进行工具检索。面对两个都能完成任务的选项，大模型会陷入路由混乱。它可能会随机选择一个，可能会反复横跳，甚至可能触发幻觉，凭空捏造一个不存在的调用路径。

**具体表现：**
- 你本想让底层确定性的 Skill 快速跑完一个脚本，主流程却唤醒了啰嗦的 Subagent，导致时间翻倍
- 或者 Subagent 被唤醒后，不知道该自己动手，还是该指挥那个 Skill 去干活

### 2. 理想的情况：层级调用（Agent 调用 Skill）

如果你确实需要它们共存，正确的设计模式是：将 Skill 从主流程的视线中隐藏，只将其作为"专属武器"暴露给 Subagent。

**如何运作？**
- 主流程只知道 Subagent 的存在
- 当任务下达时，主流程唤醒 Subagent
- Subagent 负责复杂的推理和规划，当它决定要执行具体的动作时，由它来调用那个具体的 Skill（底层脚本或工具）

**打个比方：**
Skill 是一把"电钻"，Subagent 是"装修工人"。主流程（老板）不应该同时对着电钻和工人下指令。老板只需把任务交给工人，工人自己知道什么时候该拿起电钻。

## 实操建议

### 果断取舍
在追求高效落地的系统中，出现"功能完全相同的 Skill 和 Subagent"通常是一种架构冗余。最直接的建议是：**必须二选一**。

### 保留 Skill，干掉 Subagent
如果任务是确定性的（例如：单纯抓取网页、处理 Markdown 排版、写入本地文件）：
- 这些任务不需要"自由意志"和反复思考
- 直接用指令调起脚本是最快、最稳的
- 让 Subagent 介入纯属大材小用，只会徒增延迟

### 保留 Subagent，将原来的 Skill 降级为工具
如果任务需要推理和容错（例如：抓取资料后发现缺漏，需要自动换关键词重新搜索；或者自我复盘评估）：
- 把这个 Skill 的调用入口从主流程的 CLAUDE.md 中删掉
- 只写进 Subagent 的系统提示词里
- 例如："你是一个复盘代理，你可以调用 write_log 技能来记录结论"

## 层级调用的实现方式

### 核心语法
在 Subagent 的 prompt 中声明 Skill 调用权限：
```markdown
## 可用工具
- 你可以调用 `write_log` 技能记录结论：`Skill({skill: "write_log"})`
- 你可以调用 `beautify` 技能进行排版：`Skill({skill: "beautify"})`
```

### 实现模式

| 层级 | 角色 | 可见范围 |
|------|------|----------|
| 主流程 | 指挥者 | 只知道 Subagent，不知道底层 Skill |
| Subagent | 规划者 | 既知道任务目标，也知道何时调用哪个 Skill |
| Skill | 执行者 | 被动等待 Subagent 调用，执行确定性任务 |

### 关键原则
1. **主流程隐藏 Skill**：从主流程的 `CLAUDE.md` 中移除 Skill 的暴露
2. **Subagent 声明依赖**：在 Subagent 的 `description` 或 `prompt` 中写明它可以使用哪些 Skill
3. **单向调用**：Subagent → Skill，而不是主流程 → Subagent + Skill
